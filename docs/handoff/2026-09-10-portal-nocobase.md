## 1. なぜ分けるのか（結論は出ている。次に読む人のための記録）

PM は 2026-09-10 に「分離」で確定した（当初 private、のち **public** に変更）。以降この問いを繰り返さないために、根拠を残す。**結論（分ける）は変わらないが、理由は入れ替わった**（§1-2b）。

### 1-1. 決定的な理由 —— **R1 ランタイム境界**

**動かし方が違う。**

現リポは「ビルド不要の静的モック ＋ 宣言ファイル ＋ Node/Python の検証スクリプト」。`package.json` に **`dependencies` が 1 つも無く**、`npm test` が `node tools/verify.mjs && node tools/regress.mjs` の 2 本で完結する。ブラウザで `mock/catalog.html` を開くだけで動く（`file://` 対応が `CLAUDE.md` §2-3・§2-8 で load-bearing になっている）。

NocoBase は **Koa の常駐サーバ ＋ Sequelize のリレーショナル DB ＋ Redis ＋ cron ＋ WebSocket**（§4-2 A2）。`npm ci`・lockfile・migration・docker が入る。

同じ `main` に混ぜると：

- **`npm test` の意味が変わる。** `CLAUDE.md` §3 の「1 つでも FAIL ならマージしない」ハーネスに、DB を要するテストが同居する
- **`dependencies` ゼロという現リポの性質が失われる。** これは「ビルド不要」を支えている土台で、`mock/` を `file://` で開ける前提（§2-8）と繋がっている
- **CI 時間が桁で変わる**（現状の `verify` ワークフローは数十秒）

### 1-2. 補強する理由

| # | 理由 | 根拠 |
|---|---|---|
| **R2** | **変更速度と参加者が違う** | カタログ・DSL は PM ＋ 3 エージェントで日次に回る。ポータルは情シス・人事の承認、人事システムへの読み取り権限申請が絡む。同じ `main` に混ぜると片方のレビュー待ちがもう片方のリリースを止める（`CLAUDE.md` §5 は squash マージ 1 本道） |
| **R3** | **`path: mock` の 1 行の負荷が増える** | いまは公開してまずいものが `mock/` の外にも無いので、`path: mock` は「安全側の設定」。NocoBase の docker-compose・migration・エクスポートが同居すると、Pages に何が出るかの判断がこの 1 行に集中する |
| **R4** | **検査の対象が違う** | 新リポには**現リポに無い検査**（§7-4 の `check-nodata.mjs`）が要る。逆に現リポの検査（多言語 3 言語一致・CSS トークン・`SCENARIOS` 整合・Pages 設定）は新リポで 1 つも FAIL しない。混ぜると**どちらのリポでも「自分に関係ない検査」が並ぶ** |

### 1-2b. 取り下げた理由（**消さずに残す**。次に読む人が同じ問いを立てるため）

> ~~**public リポジトリに、実在従業員の勤怠・年休・研修を扱う schema とデータを置く選択肢が無い。**~~

**この理由は成り立たない。**（2026-09-10、PM 確定事項 2 により取り下げ）

PM の設計では **リポジトリに実データが 1 バイトも入らない**（定義と架空のデモデータだけ。本番は空の定義をデプロイして中身を別途投入する）。したがって「public に実データを置く」という状況が発生しない。

本書の初版はこれを「決定的な理由」として §1-1 に置いていた。**入れ替えた。** いま決定的なのは **R1（ランタイム境界）**。

**ただし、この理由が取り下げられたことで新しく必要になったものがある**：「実データが入らない」は**運用のルールであって、機械で見なければ破られる**。→ **§7-4 の検査を設計した。**

なお **schema（列名）そのものは公開される**（`勤怠.打刻漏れ回数` など）。これは「実データ」ではないが**自社が何を測っているかが読める**ので、**§7-5 に公開されるものの一覧を置き、PM が 1 つずつ見られるようにした。**

### 1-3. PM 代行の見立てのうち、成り立たなかったもの（訂正）

> 「`check-world.mjs` の『全部が架空データ』という前提が曖昧になる」

**成り立たない。** `tools/check-world.mjs` は走査対象がディレクトリの **allowlist**（`mock/js/data/scenarios/**`・`dify/kb/**`・`dify/tests/**`・`docs/dify/usecases/**`・`dify/samples/**`）で、新しいディレクトリを足しても自動では見ない。「例外が要る」事態は自動的には起きない。

むしろ逆で、**ポータルのデモ用データを `data/world/` に足すのは §2-13 に沿った正しい行為**であり、現リポに残す理由になる（§6-2）。分ける理由としては使わない。

### 1-4. 「別リポジトリ」か「別デプロイ単位」か

**別デプロイ単位。** ポータルは `docs/dify/platform-components.md` の **PC-16 本番 UI (b)** そのものであり、67 サービス・管理番号・env レイヤーと同じ製品に属する。リポジトリを分けるのは**運用上の都合（可視性とランタイム）**であって、製品を切るのではない。

この区別が効く場面：**新リポは現リポの語彙（管理番号・分類・架空世界）に従う**。逆はしない（§6-4）。

## 3. 最初の制約 C1 —「実データで作り始める」を、後から差し替えられる形で始める

PM の問い「**まず実データで作る、を、デモ用データセットを後回しにして始めてよいか**」への答え：**始めてよい。ただし下の C1 を最初の日から守ることが条件。**

守らずに始めると、3 か月後に「デモ用インスタンスを作る」段になって、画面タイトル・選択肢・ワークフローの分岐条件に実在の部署名・拠点名・社内コードが焼き込まれており、**画面を作り直すことになる**。これは `CLAUDE.md` §2-12 が「マスタ DSL を環境ごとに fork すると差分が追えなくなる」と書いているのと同じ失敗。

### C1（設計全体の前提）

> **画面・スキーマ・ワークフローの「定義」を、データと別の器に置き、空のインスタンスへ流し込める形で持つこと。**

Dify 側の「マスタ DSL 1 本 ＋ `env.yml` 1 枚」（`CLAUDE.md` §2-12）と同じ形。ポータルに読み替えると：

| Dify 側 | ポータル側 |
|---|---|
| `dify/apps/*.yml`（マスタ DSL） | **定義エクスポート**（画面・コレクション・ロール・ワークフロー） |
| `dify/env/<env>/env.yml`（環境差分） | **接続設定 ＋ マスタテーブルの中身**（部署・拠点・お知らせ・データソースの向き先） |
| `render.py --env <env>` | 空インスタンスへの流し込み手順 |
| `render.py --check` がバイト一致 | **AC-4**（空のインスタンスに流し込むと同じ画面が出る） |

### C1-a — 定義に実データの語を焼き込まない

- 画面タイトル・ブロック名・選択肢・フィルタの既定値・ワークフローの分岐条件に、**実在の部署名・拠点名・社員名・社内コード・システム名を直値で書かない**
- 表示文言は **`plugin-localization`**（多言語リソース管理。Apache-2.0・確認済み）に置く
- 選択肢は**マスタテーブル**（`departments`・`sites`・`roles`）から引く。テーブルの**行**は環境ごとに違ってよい（＝ `env.yml` に相当）
- **`CLAUDE.md` §2-12 の「プレースホルダ（`{{…}}`）は入れない」とは方向が違う**点に注意：Dify は「Cloud にそのまま貼れること」を優先してプレースホルダを禁じている。ポータルは URL インポートの制約が無いので、**参照（テーブル引き）で解決する**

### C1-b — 実データを NocoBase の Master DB に取り込まない

- **勤怠・年休・研修・人事は、外部データソースの読み取り専用接続**にする（`plugin-data-source-manager`。Apache-2.0・確認済み。「built-in Master database, external databases, APIs, etc.」）
- ポータル自身が Master DB に持ってよいのは、**ポータル固有のテーブルだけ**：`announcements`・`announcement_reads`・`departments`／`sites`（表示用マスタ）・`feed_items`（PC-01 を内製する場合）・利用ログ
- **これが「差し替え」の本体**：デモ用インスタンスは**同じ定義のまま、外部データソースの向き先を架空世界の DB に変えるだけ**で成立する
- 副次的な効果：実データがポータルの DB にコピーされないので、ポータルのバックアップ・ログの保持期間（PC-10）の議論が軽くなる

#### C1-b と PM の言い方（「形だけ入れて、中身は別途投入」）は同じか

**同じ部分と、違う部分がある。判定してから採る。**

| | 一致するか |
|---|---|
| 「**リポジトリに実データを置かない**」 | **完全に一致。** これが C1・C1-c であり、public 化の前提 |
| 「**デプロイするのは定義（形）だけ**」 | **完全に一致。** これが AC-1／AC-4 |
| 「**中身は別途投入する**」 | **一致しない可能性がある。** 「投入」は *ポータルの DB にデータを入れる* とも読める。C1-b は *入れない（外部データソースを読むだけ）* |

**違いは 2 案として整理できる：**

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **b-1 読み取り専用の外部データソース**（＝ C1-b。**推奨**） | 勤怠・年休・研修は人事側の DB／API を**読むだけ**。ポータルの DB に行が入らない | 二重管理が無い／鮮度が常に正／バックアップ・保持期間・アクセス制御（PC-10）の議論が軽い／`demo` は**向き先を変えるだけ** | **U9 が未確認**（接続できるか）／人事側の権限申請が要る |
| **b-2 定期投入（ETL）** | 人事側から日次で吸い出してポータルの DB に**入れる** | 人事 DB に直接繋がなくてよい（ファイル授受でも成立）／表示が速い | **ポータルの DB に実データが載る** → 保持期間・アクセス制御・バックアップが重くなる／鮮度がずれる／`demo` へ移送するとき「データを除く」問題（U3）が再燃する |

**推奨：b-1。b-2 は U9 が否だったときの第 2 案。**

**重要（PM に伝えること）**：**b-1 と b-2 のどちらでも、リポジトリには 1 バイトも実データが入らない。** したがって **public にする判断は、この選択と独立**。b-1／b-2 は「ポータルのサーバの中に実データを置くか」の話で、「リポジトリに置くか」の話ではない。**急いで決めなくてよい。**

### 4-5. 中心の問い —— 同じ schema・同じ画面を 2 つのデータセットで動かせるか

**PM がいちばん確かめたい点。** 候補を 4 つ挙げ、確実に言えるところまで書く。

| 案 | 中身 | 判定 | 根拠 |
|---|---|---|---|
| **案 A** 同一インスタンス内のテナント分離（multi-app） | 1 プロセスに本番アプリとデモアプリを同居 | **採らない** | **A11**（配布者が本番非推奨と明記） |
| **案 B** 同一インスタンス内で collection を分ける | `attendance_prod` / `attendance_demo` を作り ACL で出し分け | **採らない** | ① **画面が 2 セットになり「同じ画面」でなくなる**（C1-a も破れる：画面定義にデータセット名が焼き込まれる）② 実データと架空データが**同じ DB に同居**し、顧客提示時の事故面が最大になる |
| **案 C** **別インスタンス 2 台 ＋ 定義の移送** | `本番` と `demo` を別プロセス・別 DB で立て、**定義だけ**を移送して画面を揃える | **土台にする** | A11 の帰結（本番は multi-app に載せられない）。移送手段の候補は **A12**（`plugin-backup-restore` ＝「application replication, migration」）。**ただし「データを除いて定義だけ」が可能かは U3** |
| **案 D** **外部データソースの向き先を差し替える** | 定義は 1 つ。勤怠・年休・研修・人事は外部データソースの読み取り接続で、`本番` は人事 DB、`demo` は架空世界の DB に向ける | **案 C の中で併用する** | **A7**（「external databases を管理する」）。**ただし U9（接続ドライバの入手経路）と U11（向き先だけの差し替え可否）が未確認** |

**採る形（案 C ＋ 案 D）**：

```
                     ┌──────────────── 定義（画面・コレクション・ロール・WF）───────────────┐
                     │  新リポ `shoulang0729/portal` にエクスポートしてコミット（C1-c）      │
                     └───────────┬───────────────────────────────┬───────────────────────┘
                                 │ 流し込む                       │ 流し込む
                     ┌───────────▼───────────┐       ┌───────────▼───────────┐
                     │ 本番インスタンス       │       │ demo インスタンス      │
                     │ Master DB:            │       │ Master DB:            │
                     │  announcements 等      │       │  announcements 等      │
                     │  ＝ ポータル固有だけ    │       │  ＝ 同じ定義・別の行    │
                     │ 外部データソース:      │       │ 外部データソース:      │
                     │  人事・勤怠・研修 DB   │       │  架空世界 DB           │
                     │  （読み取り専用）      │       │  （data/world/ から seed）│
                     └───────────────────────┘       └───────────────────────┘
                        社内限定・非公開                  顧客提示（画面共有 or 期間限定 URL）
```

**この形が成立する条件は C1-b（§3）だけ。** 実データが NocoBase の Master DB に入らなければ、`demo` は「同じ定義 ＋ 外部データソースの向き先が違う ＋ ポータル固有テーブルの行が違う」で成立する。**逆に C1-b が破れて実データが Master DB に入ると、定義とデータが同じ DB で絡み、案 C の移送が「データも一緒に運ぶ」問題に直面する。**

**だから C1-b は「あとで効いてくる制約」ではなく、最初の日から守る制約。**

### 4-6. U3／U9／U11 が否だったときの代替（作り直しにしないための逃げ道）

| 落ちたもの | 代替 | 作り直しの規模 |

### 4-9. マスキング（実データを伏せて顧客に見せる）を採らない理由

PM 代行の見立て（勧めない）に**同意する**。理由を 4 つ足す：

1. **漏れを機械で確かめられない。** この組織の検証文化は「`tools/verify.mjs` が FAIL する」で担保している（`CLAUDE.md` §3）。マスキングの網羅性は同じ形で機械検証できない。**検証できないルールは守られなくなる**（`CLAUDE.md` §2-13 が「例外は守られなくなる」と書いているのと同じ）
2. **伏せても営業秘密が残る。** 氏名を伏せても「当社の実際の残業時間・年休取得率・離職に効く数字」は残る。顧客に見せる場面でそれを出す判断を毎回することになる
3. **説明が事故る。** デモ中に「これは当社の実データを伏せたものです」と言う瞬間が発生しうる。顧客が自社データの扱いを不安に思う
4. **すでに資産がある。** `data/world/`（青嶺精工・碧洋銀行）は台本・KB・テスト・ユースケース 67 件と**語彙が揃っている**。デモ用データセットをそこに寄せるほうが、カタログ・Dify デモ・ポータルの 3 つで**同じ世界**が出る。これは顧客提示として強い

**例外として認める範囲**：開発者が自分の画面を確認するために、社外に出さない環境で伏せ字表示を使うのは可。**顧客提示には使わない。**

## 5. 勤怠・研修・年休・お知らせは PC-01 `feed_items` に乗るか

### 5-1. 原則

> **「状態」は読み取りビュー。「あなたが何かをする必要がある」だけが `feed_items`。**

`feed_items` は `owner_id`（個人宛）・`kind`（`due`/`routine`/`notify`）・`due_at`・`status`（`open`/`done`/`dismissed`）・`source_ref`（冪等キー）の**消化される To-Do の器**。PC-17 が既に「PC-01 は履歴を積まない」と境界を引いている。同じ線をここでも引く。

### 5-2. 判定表

| もの | `feed_items` に乗るか | 置き場 |
|---|---|---|
| 会社からのお知らせ（掲示） | **乗らない** | **新規 `announcements`**（§5-3）。フィード面には `notify` として合流表示 |
| 年休の残日数・取得率 | **乗らない**（集計値。消化されない） | 人事システムの**読み取りビュー**（PC-04・C1-b） |
| 当月の勤怠実績・残業時間 | **乗らない**（同上） | 同上 |
| 研修の受講状況・履歴 | **乗らない**（同上） | 同上 |
| 「年休の取得が基準に届いていない」 | **乗る**（`kind = notify`。期限があれば `due`） | `feed_items`。`source` に **`hr`** を追加。`source_ref` ＝ `社員 ID + 年度 + 閾値` |
| 「研修 X の受講期限が n 日後」 | **乗る**（`kind = due`） | 同上。`source_ref` ＝ `研修 ID + 社員 ID` |
| 「勤怠の打刻漏れが n 件ある」 | **乗る**（`kind = due`） | 同上。`source_ref` ＝ `社員 ID + 年月` |
| 「今月の工数入力が未提出」 | **乗る**（`kind = due`） | 同上 |

**PC-01 への変更は `source` の値に `hr` を足す 1 点だけ。** テーブル定義・API・`kind`・`status` は 1 文字も変えない。

### 5-3. `announcements`（新規）

`feed_items` に載せない理由を先に：

| 観点 | `feed_items` | お知らせ |
|---|---|---|
| 宛先 | `owner_id` ＝ **個人 1 人** | **全社／拠点／部署**（1 件が n 人に見える） |
| 生存期間 | `status` を `done`/`dismissed` にして**消える** | **掲載期間**の間ずっと出ている。読んでも消えない |
| 既読 | 概念が無い（`done` は「やった」） | **既読と未読**（やってはいない） |
| 履歴 | 積まない | **過去のお知らせを一覧で遡る**（PC-17 と同じ性質） |

**スキーマ案**（PC-01 の書き方に合わせる）：

`announcements`：`id` ／ `title`（ja/zh/en）／ `body`（ja/zh/en。Markdown）／ `category`（`hr`/`safety`/`system`/`general`）／ `audience`（`all`/`site`/`dept`/`role`）／ `audience_ref`（`site_id`／`dept_id`／`role_id`）／ `publish_from`・`publish_to`（掲載期間。**絶対日付を持つ**。`feed_items` と違い掲示は日付が本体）／ `pinned`（先頭固定）／ `author_id` ／ `attachments` ／ `created_at`・`updated_at`

`announcement_reads`：`announcement_id` ／ `user_id` ／ `read_at`（複合主キー）

**フィード面との関係**（PC-17 が `due` を PC-01 に併載しているのと同じ形）：
- **原則は「合流表示」で、`feed_items` に行を作らない**（二重管理を避ける。PC-01 のリスク欄「BPMS と二重通知」と同じ懸念）
- ポータルのフィード画面が `GET /feed/items` と `GET /announcements?audience_for=<me>&active=1` の**2 本を読んで 1 つの並びにする**
- 例外：`pinned` かつ**要対応**のお知らせ（例「9/30 までに全員が e ラーニングを完了すること」）だけは `feed_items` に `due` として起票してよい。`source = announcement`・`source_ref = announcement_id + user_id`

**PC 番号**：これは複数サービス（将来 KN-05 の通達巡回・KN-04・GN-06 も書き手になりうる）が共有する器なので、`platform-components.md` の粒度では **PC 相当**。**`PC-19 お知らせ・全社掲示ストア`** として提案する。ただし **PC 番号の採番は PM 承認事項**（`platform-components.md` 冒頭が「ID と名称は固定」と明記しており、`docs/handoff/2026-09-08-implementation-order-v2.md` §4 は「PC 番号を 1 つも発明していない」ことを成果として書いている）。**本 PR では追記しない**（§9-2・§11-2）。

### 5-4. 勤怠・年休・研修の読み取りビュー

- **新テーブルを作らない。** 人事・勤怠・研修（LMS）システムを**読み取り専用**で参照する
- 第 1 候補：**外部データソース接続**（`plugin-data-source-manager`。C1-b）。→ **U9 が未確認**
- 第 2 候補：**PC-04 のアダプタ**（社内 API ゲートウェイ経由の読み取り）。既存設計にそのまま乗る
- **PC-04 の「依存する外部システム」欄に「人事マスタ・勤怠・研修（LMS）（読み取り専用）」を足す**ことを提案（§9-2）。なお PC-04 は既に **GN-06 の依存として「人事マスタ」を挙げている**ので、拡張の幅は小さい
- **PC-10（個人情報）が最も重く効く箇所。** 勤怠・年休・研修は個人情報。**本人の分だけが見える**のが既定、上長は部下の分、人事は全員 —— この 3 層を `plugin-acl` ＋ `plugin-departments` で表現する。**この権限表は P0 では作らず、P0 は「本人の分だけ」に限定する**（§8-3）

## 7. 新リポを public で作るとき —— 何がそのまま使えて、何を新しく作るか

### 7-1. GitHub Pages —— **そもそも論点にならない**

**NocoBase は Koa の常駐サーバ ＋ DB（A2）なので、静的サイトホスティングである GitHub Pages に載らない**（A3）。public / private 以前の問題。

したがって：

| | 置き場 |
|---|---|
| **顧客に見せる UI モック（現状）** | **現リポの public Pages のまま。`pages.yml` の `path: mock` は無傷**（`CLAUDE.md` §2-8） |
| **ポータルのデモ用インスタンス** | PM が用意するサーバ（または PM のローカルの docker）。顧客提示は**画面共有**、または期間限定・認証つきの URL |
| **ポータルの本番インスタンス** | 社内。外部公開しない |

**新リポが public になったので Pages 自体は使える。** 使うとしたら用途は 1 つだけ：**定義エクスポートから生成した「スキーマの説明ページ」**（テーブル・列・ロールの一覧、ER 図）を顧客・社内に見せる。PM の「顧客や社内に見せたい」に直接効く。

**ただし P0 ではやらない**（P0 は AC-1／AC-4 に集中する）。将来やるときは現リポ §2-8 の作法をそのまま踏襲する：**1 ディレクトリを `path:` でサイトのルートにする／参照は相対パスのみ／`.nojekyll` を置く／`_` 始まりのディレクトリを作らない**。**その `path:` の 1 行が「何が公開されるか」を決める防壁になる**ので、§7-4 の `G1`（トップレベル構造の allowlist）と対で守る。

### 7-2. `dify-ops.yml` の仕組み —— **持ち込まない**

`.github/workflows/dify-ops.yml` は「**Dify Cloud のコンソールにセッションで入って DSL を投入・公開する**」ための仕掛け（`op: deploy`／`kb_upload`／`run_tests`／`token_*`／`site_probe`）。ポータルは Dify を**呼ぶ側**であって投入しない。**`DIFY_CONSOLE_REFRESH` の書き戻しも `GH_SECRETS_PAT` も要らない。**

ポータルの CI に要るのは 3 つだけ：(1) lint / 型 / ビルド、(2) migration が空の DB に通ること、(3) §3 の V1〜V3。

**ただし作法として持ち込みたいものが 1 つある**：本番デプロイの**承認ゲート**。

| 現リポのやり方 | public の新リポでどうなるか | 判断 |
|---|---|---|
| GitHub **Environment ＋ Required reviewers**（`environment: dify-cloud-master`） | **public になったので制約は緩む見込み。ただし本環境から未確認**（U12） | **設計を依存させない。** `workflow_dispatch` の **`confirm` 入力の文字列一致**で代替する（`dify-ops.yml` が既に `confirm: "deploy"` / `"revoke"` でやっている形）。使えるなら後から足せばよい |
| **Actions の従量** | **public なので無料。**（private を前提にした初版の懸念は消えた） | docker build を CI で回してよい |
| **秘密の置き場**（Environment secret） | **public リポジトリでも Environment / Repository secret は値がログに出ない。** ただし **fork からの PR では secret が渡らない**のが GitHub の一般的な挙動（未確認） | **P0 の CI は secret を 1 つも使わない**設計にする（lint ＋ migration ＋ §7-4 の検査はすべて秘密不要）。本番デプロイは**リポジトリの CI から行わず、サーバ側で `git pull` ＋ 流し込みスクリプト**を回す（§7-6） |

### 7-3. `CLAUDE.md` ／ `verify.mjs` ／ `regress.mjs` をどこまで持ち込むか

**丸ごとコピーしない。** コピーすると、ポータルに関係のない検査（多言語辞書 3 言語一致・CSS セマンティックトークン・`.mockbar`・`localStorage` の許可集合・Pages 設定・`SCENARIOS` 整合）まで抱え、**FAIL しない検査**が並ぶ。FAIL しない検査は誰も読まなくなる。

| 現リポの節 | 新リポに持ち込むか |
|---|---|
| §1 レーン判定（S / M-L） | **持ち込む**（そのまま） |
| §2-1〜2-9（多言語・CSS トークン・共通レイヤー・`.mockbar`・`localStorage`・`st`・Pages・顧客版差し替え） | **持ち込まない**（`mock/` 前提） |
| §2-5 応答言語の契約（入力言語で返す） | **持ち込む**（ポータルの UI 言語切替と Dify の応答言語は別、という説明が必要） |
| §2-10 シークレットを置かない | **持ち込む。public なので必須**（§7-6 が実装、§7-4 の N4/N5/N6・G1 が検査） |
| §2-11 管理番号 | **持ち込む**（Dify サービスを指すときの共通語彙） |
| §2-12 env レイヤー | **作法だけ書き直す**（§6-5） |
| §2-13 `data/world/` が正本 | **読み替えて持ち込む**：「**正本は現リポ。新リポは参照するだけ。新リポで架空データを作らない**」 |
| §3 検証コマンド | **書き直す**：`npm test` ＝ lint ＋ migration ＋ **V1／V2／V3**（§3）の 3 つだけ |
| §4 3 エージェント分業 | **持ち込む**（そのまま） |
| §5 Git 運用（`main` 直 commit 禁止・squash・設計書は `docs/handoff/`） | **持ち込む**（そのまま） |
| §6 バックログ | **持ち込まない**（新リポで書き起こす） |
| §2-8 Pages の公開方式（`path:` の 1 行・相対パス・`.nojekyll`） | **スキーマ説明ページを出すときだけ持ち込む**（§7-1）。P0 では不要 |
| §7 実行場所（`run:cloud`／`run:runner`／`run:mac`） | **持ち込まない。** ポータルの実行場所は「クラウド（設計・実装）」「ポータルのサーバ（デプロイ）」で軸が違う。新リポで独自に定義する |

**新リポの `npm test`**：`lint` ＋ `migration`（空 DB に通ること）＋ **`node tools/check-nodata.mjs`（V1・V2）** ＋ **エクスポート鮮度（V3）**。**この 4 つだけ。**

## 7-4. 実データが入らないことを機械で見る —— `tools/check-nodata.mjs`

**「実データを入れない」は運用のルールであり、機械で見なければ破られる。** 現リポでも今日だけで、書き換え・隣接崩し・`kpi.csv` に無い値の捏造が起きている。**public リポジトリでこれが起きると取り返しがつかない**（履歴に残る）。

`tools/check-world.mjs` と**同じ allowlist 方式**にする：**手書きの禁止語リストを作らない**（禁止語リスト自体が実名の一覧になり、それを public に置くのは本末転倒）。allowlist は **`data/world/` から機械で生成する**。

### 7-4-1. 走査対象（allowlist。ここに無いディレクトリは見ない）

| 対象 | 中身 |
|---|---|
| `export/**` | 定義エクスポート（画面・コレクション・ロール・WF） |
| `seed/**` | 架空のデモデータ（`data/world/` からコピー・生成したもの） |
| `docs/**` | 設計書 |
| `env/**`・`.env.example` | 変数名と公開してよい既定値 |
| `docker/**`・`scripts/**`・`tools/**` | 構成とスクリプト |

除外：`node_modules/`・`.git/`・`dist/`・`*.lock`。

### 7-4-2. 構造の検査（**FAIL**。これが「ファイルごと持ち込む」経路を塞ぐ本体）

| # | 検査 | 判定 |
|---|---|---|
| **G1** | **トップレベルに置いてよいディレクトリ・ファイルは決まった集合だけ**（上表 ＋ `README.md`・`CLAUDE.md`・`package.json` 等） | **FAIL** |
| **G2** | **`*.sql`・`*.dump`・`*.bak`・`*.xlsx`・`*.db`・`*.sqlite` を置かない**（DB dump と表計算は実データの主要な混入経路） | **FAIL** |
| **G3** | **`*.csv` は `seed/` の下にしか置けない**（`seed/` の CSV は §7-4-3 の検査を全部受ける） | **FAIL** |
| **G4** | **`.env`（`.env.example` を除く）・`*.key`・`*.pem`・`secrets/` を置かない**（現リポ `.gitignore` と同じ集合。`CLAUDE.md` §2-10） | **FAIL** |
| **G5** | **`seed/` 以外に 1 MB を超えるテキスト・データファイルを置かない**（dump は大抵デカい） | **FAIL** |

### 7-4-3. 中身の検査 —— **何を拾って、何を拾わないか**

**拾う対象は次の 6 本だけに固定する。増やすときは本設計書を改訂する。**（`data/world/README.md` の書き方を踏襲）

| # | 拾うもの | **拾わないもの（除外）** | 判定 |
|---|---|---|---|
| **N1** **氏名らしき文字列** | 「氏／様／さん／主任／課長／部長／次長／係長／総経理／経理」等の**役職・敬称語に隣接する漢字 2〜4 字**（前後 1 語）で、**allowlist に無いもの** | `data/world/{mfg,fin}/people.csv` の `name_ja`／`name_zh`／`name_en` **31 名**（mfg 17 ＋ fin 14）／記号取引先（`K 社`・`甲社`〜`戊社`・`R 社`・`己社`）／カタカナのみ／英字のみの語／`org.csv` の部署名の一部と一致する語 | **warn** |
| **N2** **社員番号らしきパターン** | `[A-Z]{1,3}-?\d{4,8}` および `\d{6,10}` の連続数字で、**allowlist に無いもの** | **管理番号** `^(KN\|QA\|DC\|LG\|NM\|EN\|GN\|PT\|RS\|CV\|FA\|PO\|EG)-\d{2}$`（67 件）／`data/world/**/documents.csv` の文書番号・レコード ID／`calendar.md` の文書番号体系に一致するもの／日付 `\d{4}-\d{2}-\d{2}`／`airports.csv` の IATA コード／`products.csv`・`equipment.csv` の品番・設備番号／ISO 等の規格番号／ポート番号・バージョン番号（`v?\d+\.\d+\.\d+`） | **warn** |
| **N3** **部署名・拠点名** | 「部／課／室／センター／工場／支店／本部／事業部」で終わる語で、**allowlist に無いもの** | `org.csv` の `dept_ja`／`dept_zh`／`dept_en`（mfg ＋ fin）／`company.md` の拠点名／**一般語の除外リスト**（`tools/nodata-common-words.txt`。「管理部門」「各部署」「本社」「現場」「関係部署」等。**1 行 1 語 ＋ `#` で理由コメントを必須にする**） | **warn** |
| **N4** **メールアドレス** | `[\w.+-]+@[\w-]+\.[\w.]+` | RFC 2606／6761 の予約ドメイン（`example.com`／`example.org`／`example.net`／`*.example`／`*.invalid`／`*.test`／`*.localhost`）／`data/world/**` に載っているもの | **FAIL** |
| **N5** **電話番号** | 日本 `0\d{1,4}-\d{1,4}-\d{4}`、中国 `1[3-9]\d{9}`・`\+86[\d-]{9,}` | `data/world/**/contacts.csv` の架空番号／すべて同じ数字（`000-0000-0000` 等）／`\+81-3-0000-0000` 形式の明示ダミー | **FAIL** |
| **N6** **実在ドメイン・生 IP** | `https?://` のホスト名、および `\d+\.\d+\.\d+\.\d+` | **URL の allowlist**（`dify.ai`／`cloud.dify.ai`／`api.dify.ai`／`github.com`／`nocobase.com`／`docs.nocobase.com`／`registry.npmjs.org`／`shoulang0729.github.io`／`localhost`／`127.0.0.1`）／プライベート IP（`10.`／`172.16-31.`／`192.168.`）／`0.0.0.0` | **FAIL** |

### 7-4-4. 誤検知を増やしすぎないための決め事

W8（`check-world.mjs` の強化）で学んだことをそのまま適用する。

1. **FAIL は機械的に判定でき誤検知が少ない 3 本（N4・N5・N6）と、構造の 5 本（G1〜G5）だけ。** 人名・社員番号・部署名（N1〜N3）は**必ず誤検知が出る種類**なので **warn**
2. **`--strict` で warn も FAIL にする**（掃除の PR 用）。現リポの `check-world.mjs --strict` と同じ作法
3. **warn の基準値をリポジトリに置き、増えたら FAIL**（`tools/nodata.baseline.json`。`regress.mjs` の baseline と同じ発想）。**残す warn は理由付きで 1 行ずつ台帳に書く**（`docs/nodata-known.md`。`data/world/README.md` の「未統一」と同じ形）
4. **allowlist は手で書かない。** `data/world/` から機械で生成する（`seed/world/` にコピーしたものを読む）
5. **除外リスト（`tools/nodata-common-words.txt`）だけは手書きを許すが、1 行 1 語 ＋ 理由コメントを必須**にし、**語数の上限を設ける**（初期 50 語。超えるときは設計書を改訂）
6. **CI に入れる**（`check-world.mjs` が warn のみで CI に入っていないのと**逆**。こちらは公開の防壁なので CI に入れる）

### 7-4-5. これで防げること／防げないこと

| 防げる | 防げない |
|---|---|
| DB dump・Excel・CSV をファイルごとコミット（G2・G3・G5） | **schema そのものの機微**（`勤怠.打刻漏れ回数` という列名は「実データ」ではないので拾えない）→ **§7-5 の一覧で PM が見る** |
| 接続文字列・API キー・メール・電話の混入（G4・N4・N5） | **業務ルールの数値**（「取得率 70% を下回ったら通知」）→ **§7-6 で `${VAR}` に逃がす** |
| 実在の人名・部署名が定義に焼き込まれる（N1・N3。warn） | 意味を変えずに書き換えられた実データ（例：実在の数字を 1 だけずらす）→ **機械では原理的に無理。C1-b（そもそも実データを持ち込まない）で塞ぐ** |

## 7-5. 公開されるものの一覧（PM が 1 つずつ見るための表）

**「実データが入らない」＝「何も分からない」ではない。** public にする以上、次のものは読まれる。**PM が 1 行ずつ「公開してよい」と言えるかを確認する。**

| # | 公開されるもの | 具体例 | 何が読み取れるか | 隠せるか | PM の判断が要るか |
|---|---|---|---|---|---|
| **P-1** | **テーブル定義（列名・型）** | `勤怠.打刻漏れ回数`・`年休.取得率`・`研修.未受講フラグ` | **自社が何を測っているか** | **隠せない**（定義がリポジトリの本体） | — |
| **P-2** | **部署の階層と職級コードの体系** | `dept_id` の親子関係・職級の値域 | 組織の形と等級制度の**体系** | **体系は隠せない。値の並びは架空にできる**（`data/world/org.csv` の部署に寄せる＝ C1-a） | — |
| **P-3** | **業務ルール（閾値・通知条件）** | 「取得率が◯% を下回ったら通知」「残業◯時間で警告」 | **自社の運用方針。数値は経営判断そのもの** | **ルールの形は隠せない。閾値の数値は `${VAR}` に逃がせる** | **要判断** |
| **P-4** | **外部システムの名前と接続の形** | 人事システム・勤怠 SaaS の製品名、API のパス | ベンダ構成（攻撃面の情報にもなる） | **隠せる**：データソース名を `hr` に固定（§4-6 代替 C）し、**製品名を書かない** | — |
| **P-5** | **画面の構成とロール** | 誰が何を見られるか（ロール × ブロック） | 権限設計 | 隠せない。**ただし顧客に見せたいものそのもの**（PM の狙い） | — |
| **P-6** | **ワークフローの分岐** | 承認の流れ・エスカレーション先の役職 | 決裁ライン | **役職名は `data/world/` の語に寄せる**（C1-a） | — |
| **P-7** | **デモデータ** | 架空社員の勤怠・年休・研修（`data/world/` 由来） | **架空。むしろ見せたい** | — | — |
| **P-8** | **カレンダー・所定労働時間・締め日** | 会計年度・月次締め・所定労働時間 | 会計年度は公知。**所定労働時間・締め日は就業規則相当** | **`${VAR}` か架空値に逃がせる** | **要判断** |
| **P-9** | **`.env.example` の変数名** | `PORTAL_DSN_HR`・`DIFY_API_KEY_KN01` | **何と繋がっているか** | 隠せない（型として必要）。**値は入らない** | — |
| **P-10** | **文言・エラーメッセージ（ja/zh/en）** | 「AI が応答しませんでした」等 | 自社の言い回し | 問題なし | — |
| **P-11** | **Dify の管理番号と 67 サービスの一覧** | `KN-01`〜`EG-01` | **既に現リポの public Pages で公開済み**（`mock/catalog.html`） | — | — |
| **P-12** | **NocoBase のバージョン・プラグイン構成** | `2.2.x` ＋ 使用プラグイン | 攻撃面（既知の脆弱性を突かれうる） | 隠せない（再現性に必要）。**バージョンを上げる運用で対応** | — |

**PM の判断が要るのは P-3 と P-8 の 2 つだけ。**

**architect の推奨**：**P-3 の閾値と P-8 の所定労働時間・締め日は `${VAR}` にして、`.env.example` に変数名だけを置く。** そうすれば公開範囲から外れ、**PM は 1 つも判断しなくてよくなる**。実装コストは「定義に直値で書かない」だけでゼロに近い（C1-a を守れば自動的にそうなる）。

## 7-6. 秘密と「公開したくない値」の置き場 —— `dify/env` の型をそのまま持ち込めるか

**判定：そのまま持ち込める。** ただし `scripts/dify/render.py` そのものは持ち込まない（Dify DSL 専用）。持ち込むのは**型（ファイルの役割分担と規約）**。

### 7-6-1. 対応表

| 現リポ | 新リポ | 同じか |
|---|---|---|
| `dify/apps/*.yml`（マスタ。**公開してよい既定値**だけを書く） | `export/**`（定義エクスポート） | **同じ** |
| `dify/env/<env>/env.yml`（環境差分。`${VAR}` で外から） | `env/<env>/portal.yml`（データソース名・閾値のキー名・既定値） | **同じ** |
| `scripts/dify/env.example`（変数名の一覧。値は入れない） | `env.example` | **同じ** |
| 設定ファイルはリポジトリの外（`~/.config/dify/<env>.env`） | `~/.config/portal/<env>.env` | **同じ** |
| `render.py --strict` が未定義の `${VAR}` で exit 1（**黙って空文字にしない**） | 流し込みスクリプトが `--strict` を持つ | **同じ（必須）** |
| `dify/env/README.md` の「置く／置かない」の表 ＋ 環境台帳 | 新リポの `env/README.md`。**中身は §7-5 の一覧** | **同じ** |
| `tools/verify.mjs` §12（env に秘密・実名が無い） | **§7-4 の N4/N5/N6 ＋ G1〜G5** | **同じ役割** |

### 7-6-2. `${VAR}` に入れるもの

| 分類 | 例 | 変数名の付け方 |
|---|---|---|
| **秘密（漏れると事故）** | 人事・勤怠 DB の接続文字列 | `${PORTAL_DSN_HR}` |
| | SSO のクライアント ID／シークレット | `${PORTAL_OIDC_CLIENT_ID}` / `${PORTAL_OIDC_CLIENT_SECRET}` |
| | Dify Service API キー（**アプリ単位・実機 12 本**） | `${DIFY_API_KEY_KN01}` …… **管理番号で命名**（`CLAUDE.md` §2-11 の語彙をそのまま使う。`dify/env/README.md` の `${DIFY_APP_ID_<番号ハイフン無し>}` と同じ形） |
| | NocoBase の `APP_KEY`・DB パスワード | `${PORTAL_APP_KEY}` / `${PORTAL_DB_PASSWORD}` |

### 7-6-3. `CLAUDE.md` §2-12 との違い（明記しておく）

**`CLAUDE.md` §2-12 は「マスタ DSL にプレースホルダ（`{{…}}`）を入れない」と決めている。** これは **Dify Cloud への URL インポート（マスタをそのまま貼る）を壊さないため**の制約であって、一般則ではない。

**ポータルには URL インポートの制約が無い。** したがって **定義側に `${VAR}` を書いてよい**。この 1 点だけが Dify 側と違う。**混同しないよう新リポの `CLAUDE.md` に明記する。**

### 7-6-4. 本番デプロイの経路

**リポジトリの CI から本番へ push しない。** 理由：public リポジトリの CI に本番の接続情報を持たせたくない（§7-2）。

```
新リポ（public）        本番サーバ（社内）
  export/**    ──────▶  git pull
  env/prod/*.yml        ＋ ~/.config/portal/prod.env（リポジトリの外）
                        ＋ 流し込みスクリプト --strict
                        ＝ 空の定義に形が入る。中身（実データ）は
                          外部データソース（b-1）または別途投入（b-2）
```

**CI がやるのは検査だけ**（lint ＋ migration ＋ V1／V2／V3）。**秘密を 1 つも使わない。**

## 10. Dify との接続点（PC-02 に既に書かれていることは繰り返さない）

PC-02 が既に決めていること（**繰り返さない**）：SSO で社員 ID・部署・拠点・言語を取る／**Dify Service API を呼ぶときに `user` に社員 ID を渡す**／**権限は前段（ポータル）で判定**／部署 → 帯 → 呼べるアプリ・KB を表で持つ。

足りないのは次の 4 点。

### 10-1. API キーの粒度と持ち方

- **Dify の Service API キーはアプリ単位。** 実機 12 本 ＝ **12 個のキー**を持つことになる
- **ブラウザに出さない。** ポータルのサーバが **BFF** になり、`POST /api/svc/{管理番号}/chat` のような**管理番号で受ける口**を出す。内部でキーを選ぶ
- 管理番号 → アプリ id ／ キー環境変数名 の対応表は §6-4（正本は現リポの `env.yml` の `apps:`）。**キー本体は環境変数**（`CLAUDE.md` §2-10）
- **P0 では 0 個**（iframe なので API キーを使わない）。これも iframe から始める利点

### 10-2. `user` に何を渡すか —— **社員 ID をそのまま渡さない**

PC-02 は「`user` に社員 ID」と書いているが、**PC-10（個人情報・秘密管理）と突き合わせると素通しにできない**：

- `user` は **Dify の会話ログの主体**として保存され、**PC-09 の Langfuse トレースにも乗る**（PC-09 のリスク欄「トレースに個人情報が残る」）
- 顧客環境では**社員 ID が個人識別子**になる（PIPL）

**提案**：`user` には **社員 ID から導いた安定な仮名**（例：`u-<ハッシュ先頭 12 桁>`、ソルトは環境ごと）を渡し、**仮名 → 社員 ID の逆引きはポータル側だけが持つ**。監査（PC-10 (5)「誰が・どのアプリで・何を聞いたか」）はポータル側のログで成立する。

PC-10 は既に個人の匿名 ID の体系（`C-2609-A`）を持っているので、**同じ考え方の延長**。ただし **`user` の仕様を変えることは PC-02 の記述に触れる**ので、**PM 判断事項**（§11-3）。

### 10-3. エラー時の見せ方（3 分類）

| # | 事象 | 見せ方 |

| **E1** | Dify に届かない／5xx | 「AI が応答しませんでした。時間をおいて試してください」＋ **その場の再送ボタン** ＋ **管理番号**（問い合わせのときに一意に指せる。`CLAUDE.md` §2-11） |

| **E3** | KB に無い・答えられない | **エラーとして扱わない。** これは正常な回答（`docs/dify/implementation-guide.md` の「不確実なときの定型」の系）。ポータルがエラー表示に変換しない |
