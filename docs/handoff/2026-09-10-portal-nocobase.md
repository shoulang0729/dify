## 1. なぜ分けるのか（結論は出ている。次に読む人のための記録）

PM は 2026-09-10 に「分離・private」で確定した。以降この問いを繰り返さないために、根拠を残す。

### 1-1. 決定的な理由（これ 1 つで決まる）

**public リポジトリに、実在従業員の勤怠・年休・研修を扱う schema とデータを置く選択肢が無い。** 現リポは `visibility: public`（API で確認済み）。「あとで private 化する」は履歴ごと移すことになり、コミット履歴・Issue・PR のリンクが load-bearing になっている現リポでは現実的でない。**最初から分けるほうが安い。**

### 1-2. 補強する理由（PM が挙げていなかったもの。こちらのほうが強い）

| # | 理由 | 根拠 |
|---|---|---|
| **R1** | **動かし方が違う（ランタイム境界）** | 現リポは「ビルド不要の静的モック ＋ 宣言ファイル ＋ Node/Python の検証スクリプト」。`package.json` に **`dependencies` が 1 つも無い**（`npm test` が `node tools/*.mjs` 2 本で完結）。NocoBase は **Koa の常駐サーバ ＋ Sequelize のリレーショナル DB ＋ Redis ＋ cron ＋ WebSocket**（§4-2 A2）。`npm ci`・lockfile・migration・docker が入ると `npm test` の意味が変わり、`CLAUDE.md` §3 の「1 つでも FAIL ならマージしない」ハーネスが別種のテストと同居する |
| **R2** | **変更速度と参加者が違う** | カタログ・DSL は PM ＋ 3 エージェントで日次に回る。ポータルは情シス・人事の承認、人事システムへの読み取り権限申請が絡む。同じ `main` に混ぜると片方のレビュー待ちがもう片方のリリースを止める（`CLAUDE.md` §5 は squash マージ 1 本道） |
| **R3** | **`path: mock` の 1 行の負荷が増える** | いまは公開してまずいものが `mock/` の外にも無いので、`path: mock` は「安全側の設定」。NocoBase の `.env.example`・docker-compose・migration・DB dump が同居すると、この 1 行が**唯一の防壁**になる。防壁は 1 枚にしないほうがよい |

### 1-3. PM 代行の見立てのうち、成り立たなかったもの（訂正）

> 「`check-world.mjs` の『全部が架空データ』という前提が曖昧になる」

**成り立たない。** `tools/check-world.mjs` は走査対象がディレクトリの **allowlist**（`mock/js/data/scenarios/**`・`dify/kb/**`・`dify/tests/**`・`docs/dify/usecases/**`・`dify/samples/**`）で、新しいディレクトリを足しても自動では見ない。「例外が要る」事態は自動的には起きない。

むしろ逆で、**ポータルのデモ用データを `data/world/` に足すのは §2-13 に沿った正しい行為**であり、現リポに残す理由になる（§6-2）。分ける理由としては使わない。

### 1-4. 「別リポジトリ」か「別デプロイ単位」か

**別デプロイ単位。** ポータルは `docs/dify/platform-components.md` の **PC-16 本番 UI (b)** そのものであり、67 サービス・管理番号・env レイヤーと同じ製品に属する。リポジトリを分けるのは**運用上の都合（可視性とランタイム）**であって、製品を切るのではない。

この区別が効く場面：**新リポは現リポの語彙（管理番号・分類・架空世界）に従う**。逆はしない（§6-4）。

## 3. 最初の制約 C1 —「実データで作り始める」を、後から差し替えられる形で始める

PM の問い「**まず実データで作る、を、デモ用データセットを後回しにして始めてよいか**」への答え：**始めてよい。ただし下の C1 を最初の日から守ることが条件。**

守らずに始めると、3 か月後に「デモ用インスタンスを作る」段になって、画面タイトル・選択肢・ワークフローの分岐条件に実在の部署名・拠点名・社内コードが焼き込まれており、**画面を作り直すことになる**。これは `CLAUDE.md` §2-12 が「マスタ DSL を環境ごとに fork すると差分が追えなくなる」と書いているのと同じ失敗。

### C1（設計全体の前提）

> **画面・スキーマ・ワークフローの「定義」を、データと別の器に置き、空のインスタンスへ流し込める形で持つこと。**

Dify 側の「マスタ DSL 1 本 ＋ `env.yml` 1 枚」（`CLAUDE.md` §2-12）と同じ形。ポータルに読み替えると：

| Dify 側 | ポータル側 |
|---|---|
| `dify/apps/*.yml`（マスタ DSL） | **定義エクスポート**（画面・コレクション・ロール・ワークフロー） |
| `dify/env/<env>/env.yml`（環境差分） | **接続設定 ＋ マスタテーブルの中身**（部署・拠点・お知らせ・データソースの向き先） |
| `render.py --env <env>` | 空インスタンスへの流し込み手順 |
| `render.py --check` がバイト一致 | **AC-4**（空のインスタンスに流し込むと同じ画面が出る） |

### C1-a — 定義に実データの語を焼き込まない

- 画面タイトル・ブロック名・選択肢・フィルタの既定値・ワークフローの分岐条件に、**実在の部署名・拠点名・社員名・社内コード・システム名を直値で書かない**
- 表示文言は **`plugin-localization`**（多言語リソース管理。Apache-2.0・確認済み）に置く
- 選択肢は**マスタテーブル**（`departments`・`sites`・`roles`）から引く。テーブルの**行**は環境ごとに違ってよい（＝ `env.yml` に相当）
- **`CLAUDE.md` §2-12 の「プレースホルダ（`{{…}}`）は入れない」とは方向が違う**点に注意：Dify は「Cloud にそのまま貼れること」を優先してプレースホルダを禁じている。ポータルは URL インポートの制約が無いので、**参照（テーブル引き）で解決する**

### C1-b — 実データを NocoBase の Master DB に取り込まない

- **勤怠・年休・研修・人事は、外部データソースの読み取り専用接続**にする（`plugin-data-source-manager`。Apache-2.0・確認済み。「built-in Master database, external databases, APIs, etc.」）
- ポータル自身が Master DB に持ってよいのは、**ポータル固有のテーブルだけ**：`announcements`・`announcement_reads`・`departments`／`sites`（表示用マスタ）・`feed_items`（PC-01 を内製する場合）・利用ログ
- **これが「差し替え」の本体**：デモ用インスタンスは**同じ定義のまま、外部データソースの向き先を架空世界の DB に変えるだけ**で成立する
- 副次的な効果：実データがポータルの DB にコピーされないので、ポータルのバックアップ・ログの保持期間（PC-10）の議論が軽くなる

### C1-c — 定義のエクスポートを、作り始めた日から毎週やる

- **エクスポート手段が無いと分かったら、その時点で §4-6 の代替 B（定義を手続きで持つ）へ切り替える。** 3 か月後に気づくと画面の作り直しになるので、**P0 の受け入れ条件の筆頭に置く**（AC-1）
- エクスポート結果は新リポにコミットする。**diff が読める形式であること**（1 ファイル巨大 JSON だと差分レビューが死ぬ → 分割の可否も P0 で確認する）
- 現リポの Issue #3（Dify の export 方向）と**同型の問題**。あちらで解けていないことを楽観しない

### C1 が守れているかの機械検査（新リポ側。§7-3）

| # | 検査 | 内容 |
|---|---|---|
| **V1** | 定義に実データの語が無い | エクスポートに現れる固有名詞のうち、**`data/world/` に存在しないもの**を warn（**禁止語リスト方式にしない**。禁止語リスト自体が実名の一覧になるため。allowlist 方式にする） |
| **V2** | 秘密が無い | `CLAUDE.md` §2-10 相当。private でも守る |
| **V3** | エクスポートの鮮度 | 最後のエクスポートが N 日以内（`tools/gen-index.mjs --check` が `docs/service-map.md` の鮮度を見ているのと同じ形） |

### 4-5. 中心の問い —— 同じ schema・同じ画面を 2 つのデータセットで動かせるか

| 案 | 中身 | 判定 | 根拠 |

**採る形（案 C ＋ 案 D）**：

**この形が成立する条件は C1-b（§3）だけ。** 実データが NocoBase の Master DB に入らなければ、`demo` は「同じ定義 ＋ 外部データソースの向き先が違う ＋ ポータル固有テーブルの行が違う」で成立する。**逆に C1-b が破れて実データが Master DB に入ると、定義とデータが同じ DB で絡み、案 C の移送が「データも一緒に運ぶ」問題に直面する。**

**だから C1-b は「あとで効いてくる制約」ではなく、最初の日から守る制約。**

### 4-9. マスキング（実データを伏せて顧客に見せる）を採らない理由

PM 代行の見立て（勧めない）に**同意する**。理由を 4 つ足す：

1. **漏れを機械で確かめられない。** この組織の検証文化は「`tools/verify.mjs` が FAIL する」で担保している（`CLAUDE.md` §3）。マスキングの網羅性は同じ形で機械検証できない。**検証できないルールは守られなくなる**（`CLAUDE.md` §2-13 が「例外は守られなくなる」と書いているのと同じ）
2. **伏せても営業秘密が残る。** 氏名を伏せても「当社の実際の残業時間・年休取得率・離職に効く数字」は残る。顧客に見せる場面でそれを出す判断を毎回することになる
3. **説明が事故る。** デモ中に「これは当社の実データを伏せたものです」と言う瞬間が発生しうる。顧客が自社データの扱いを不安に思う
4. **すでに資産がある。** `data/world/`（青嶺精工・碧洋銀行）は台本・KB・テスト・ユースケース 67 件と**語彙が揃っている**。デモ用データセットをそこに寄せるほうが、カタログ・Dify デモ・ポータルの 3 つで**同じ世界**が出る。これは顧客提示として強い

**例外として認める範囲**：開発者が自分の画面を確認するために、社外に出さない環境で伏せ字表示を使うのは可。**顧客提示には使わない。**

### 5-1. 原則

> **「状態」は読み取りビュー。「あなたが何かをする必要がある」だけが `feed_items`。**

`feed_items` は `owner_id`（個人宛）・`kind`（`due`/`routine`/`notify`）・`due_at`・`status`（`open`/`done`/`dismissed`）・`source_ref`（冪等キー）の**消化される To-Do の器**。PC-17 が既に「PC-01 は履歴を積まない」と境界を引いている。同じ線をここでも引く。

### 5-2. 判定表

| もの | `feed_items` に乗るか | 置き場 |
|---|---|---|
| 会社からのお知らせ（掲示） | **乗らない** | **新規 `announcements`**（§5-3）。フィード面には `notify` として合流表示 |
| 年休の残日数・取得率 | **乗らない**（集計値。消化されない） | 人事システムの**読み取りビュー**（PC-04・C1-b） |
| 当月の勤怠実績・残業時間 | **乗らない**（同上） | 同上 |
| 研修の受講状況・履歴 | **乗らない**（同上） | 同上 |
| 「年休の取得が基準に届いていない」 | **乗る**（`kind = notify`。期限があれば `due`） | `feed_items`。`source` に **`hr`** を追加。`source_ref` ＝ `社員 ID + 年度 + 閾値` |
| 「研修 X の受講期限が n 日後」 | **乗る**（`kind = due`） | 同上。`source_ref` ＝ `研修 ID + 社員 ID` |
| 「勤怠の打刻漏れが n 件ある」 | **乗る**（`kind = due`） | 同上。`source_ref` ＝ `社員 ID + 年月` |
| 「今月の工数入力が未提出」 | **乗る**（`kind = due`） | 同上 |

**PC-01 への変更は `source` の値に `hr` を足す 1 点だけ。** テーブル定義・API・`kind`・`status` は 1 文字も変えない。

### 5-3. `announcements`（新規）

`feed_items` に載せない理由を先に：

| 観点 | `feed_items` | お知らせ |
|---|---|---|
| 宛先 | `owner_id` ＝ **個人 1 人** | **全社／拠点／部署**（1 件が n 人に見える） |
| 生存期間 | `status` を `done`/`dismissed` にして**消える** | **掲載期間**の間ずっと出ている。読んでも消えない |
| 既読 | 概念が無い（`done` は「やった」） | **既読と未読**（やってはいない） |
| 履歴 | 積まない | **過去のお知らせを一覧で遡る**（PC-17 と同じ性質） |

**スキーマ案**（PC-01 の書き方に合わせる）：

`announcements`：`id` ／ `title`（ja/zh/en）／ `body`（ja/zh/en。Markdown）／ `category`（`hr`/`safety`/`system`/`general`）／ `audience`（`all`/`site`/`dept`/`role`）／ `audience_ref`（`site_id`／`dept_id`／`role_id`）／ `publish_from`・`publish_to`（掲載期間。**絶対日付を持つ**。`feed_items` と違い掲示は日付が本体）／ `pinned`（先頭固定）／ `author_id` ／ `attachments` ／ `created_at`・`updated_at`

`announcement_reads`：`announcement_id` ／ `user_id` ／ `read_at`（複合主キー）

**フィード面との関係**（PC-17 が `due` を PC-01 に併載しているのと同じ形）：
- **原則は「合流表示」で、`feed_items` に行を作らない**（二重管理を避ける。PC-01 のリスク欄「BPMS と二重通知」と同じ懸念）

**PC 番号**：これは複数サービス（将来 KN-05 の通達巡回・KN-04・GN-06 も書き手になりうる）が共有する器なので、`platform-components.md` の粒度では **PC 相当**。**`PC-19 お知らせ・全社掲示ストア`** として提案する。ただし **PC 番号の採番は PM 承認事項**（`platform-components.md` 冒頭が「ID と名称は固定」と明記しており、`docs/handoff/2026-09-08-implementation-order-v2.md` §4 は「PC 番号を 1 つも発明していない」ことを成果として書いている）。**本 PR では追記しない**（§9-2・§11-2）。

## 6. 共有する資産の境界

### 6-1. 方向は片方向（現リポ → 新リポ）。逆流させない

現リポは **public ＋ 機械検査あり**、新リポは **private ＋ 実データあり**。新リポから現リポへ資産を戻す経路を作ると、**実データの語が public に混入する経路になる**。**逆流禁止を最初のルールにする。**

## 7. private リポジトリにすると、いまの作り方のどこが使えなくなるか

### 7-1. GitHub Pages —— **そもそも論点にならない**

**NocoBase は Koa の常駐サーバ ＋ DB（A2）なので、静的サイトホスティングである GitHub Pages に載らない**（A3）。private かどうか以前の問題。

したがって：

| | 置き場 |
|---|---|
| **顧客に見せる UI モック（現状）** | **現リポの public Pages のまま。`pages.yml` の `path: mock` は無傷**（`CLAUDE.md` §2-8） |
| **ポータルのデモ用インスタンス** | PM が用意するサーバ（または PM のローカルの docker）。顧客提示は**画面共有**、または期間限定・認証つきの URL |
| **ポータルの本番インスタンス** | 社内。外部公開しない |

**注**：private リポジトリでの Pages 公開可否・Pages のアクセス制御はいずれも **GitHub のプラン依存で、本環境からは未確認**（リポジトリ所有者は User アカウント。plan は API から見えない）。ただし上の通り**依存しない設計**にしたので、確認しなくても進める。

### 7-2. `dify-ops.yml` の仕組み —— **持ち込まない**

`.github/workflows/dify-ops.yml` は「**Dify Cloud のコンソールにセッションで入って DSL を投入・公開する**」ための仕掛け（`op: deploy`／`kb_upload`／`run_tests`／`token_*`／`site_probe`）。ポータルは Dify を**呼ぶ側**であって投入しない。**`DIFY_CONSOLE_REFRESH` の書き戻しも `GH_SECRETS_PAT` も要らない。**

ポータルの CI に要るのは 3 つだけ：(1) lint / 型 / ビルド、(2) migration が空の DB に通ること、(3) §3 の V1〜V3。

**ただし作法として持ち込みたいものが 1 つある**：本番デプロイの**承認ゲート**。

| 現リポのやり方 | private でどうなるか | 代替 |
|---|---|---|
| GitHub **Environment ＋ Required reviewers**（`environment: dify-cloud-master`） | **プラン依存で未確認。** private リポジトリで deployment protection rules（承認者・待機時間・ブランチ制限）が使えるかは GitHub のプランによる | **`workflow_dispatch` の `confirm` 入力の文字列一致**で代替する。`dify-ops.yml` が既に `confirm: "deploy"` / `"revoke"` でやっている形をそのまま使う。**Environment secret は（保護ルール無しでも）使える前提だが、これも P0 で実機確認** |
| **Actions の従量** | **public は無料、private は無料枠を消費。** docker build を回すと効く | P0 では CI を最小（lint ＋ migration ＋ V1〜V3）にする。docker build は手元で回す |

### 7-3. `CLAUDE.md` ／ `verify.mjs` ／ `regress.mjs` をどこまで持ち込むか

**丸ごとコピーしない。** コピーすると、ポータルに関係のない検査（多言語辞書 3 言語一致・CSS セマンティックトークン・`.mockbar`・`localStorage` の許可集合・Pages 設定・`SCENARIOS` 整合）まで抱え、**FAIL しない検査**が並ぶ。FAIL しない検査は誰も読まなくなる。

| 現リポの節 | 新リポに持ち込むか |
|---|---|
| §1 レーン判定（S / M-L） | **持ち込む**（そのまま） |
| §2-1〜2-9（多言語・CSS トークン・共通レイヤー・`.mockbar`・`localStorage`・`st`・Pages・顧客版差し替え） | **持ち込まない**（`mock/` 前提） |

| §2-11 管理番号 | **持ち込む**（Dify サービスを指すときの共通語彙） |
| §2-12 env レイヤー | **作法だけ書き直す**（§6-5） |
| §2-13 `data/world/` が正本 | **読み替えて持ち込む**：「**正本は現リポ。新リポは参照するだけ。新リポで架空データを作らない**」 |

## 10. Dify との接続点（PC-02 に既に書かれていることは繰り返さない）

PC-02 が既に決めていること（**繰り返さない**）：SSO で社員 ID・部署・拠点・言語を取る／**Dify Service API を呼ぶときに `user` に社員 ID を渡す**／**権限は前段（ポータル）で判定**／部署 → 帯 → 呼べるアプリ・KB を表で持つ。

足りないのは次の 4 点。

### 10-1. API キーの粒度と持ち方

- **Dify の Service API キーはアプリ単位。** 実機 12 本 ＝ **12 個のキー**を持つことになる
- **ブラウザに出さない。** ポータルのサーバが **BFF** になり、`POST /api/svc/{管理番号}/chat` のような**管理番号で受ける口**を出す。内部でキーを選ぶ
- 管理番号 → アプリ id ／ キー環境変数名 の対応表は §6-4（正本は現リポの `env.yml` の `apps:`）。**キー本体は環境変数**（`CLAUDE.md` §2-10）
- **P0 では 0 個**（iframe なので API キーを使わない）。これも iframe から始める利点

### 10-2. `user` に何を渡すか —— **社員 ID をそのまま渡さない**

PC-02 は「`user` に社員 ID」と書いているが、**PC-10（個人情報・秘密管理）と突き合わせると素通しにできない**：

- `user` は **Dify の会話ログの主体**として保存され、**PC-09 の Langfuse トレースにも乗る**（PC-09 のリスク欄「トレースに個人情報が残る」）
- 顧客環境では**社員 ID が個人識別子**になる（PIPL）

**提案**：`user` には **社員 ID から導いた安定な仮名**（例：`u-<ハッシュ先頭 12 桁>`、ソルトは環境ごと）を渡し、**仮名 → 社員 ID の逆引きはポータル側だけが持つ**。監査（PC-10 (5)「誰が・どのアプリで・何を聞いたか」）はポータル側のログで成立する。

PC-10 は既に個人の匿名 ID の体系（`C-2609-A`）を持っているので、**同じ考え方の延長**。ただし **`user` の仕様を変えることは PC-02 の記述に触れる**ので、**PM 判断事項**（§11-3）。

### 10-3. エラー時の見せ方（3 分類）

| # | 事象 | 見せ方 |
|---|---|---|
| **E1** | Dify に届かない／5xx | 「AI が応答しませんでした。時間をおいて試してください」＋ **その場の再送ボタン** ＋ **管理番号**（問い合わせのときに一意に指せる。`CLAUDE.md` §2-11） |
| **E2** | タイムアウト／ストリーミングが途中で切れた | **途中まで表示したまま**「応答が途切れました」。**消さない**（消すと利用者は何も残らない） |
| **E3** | KB に無い・答えられない | **エラーとして扱わない。** これは正常な回答（`docs/dify/implementation-guide.md` の「不確実なときの定型」の系）。ポータルがエラー表示に変換しない |

加えて **E0：サービスの点検中**。Dify 側が落ちている／メンテ中のときは、カタログのカードに「点検中」を出す。**成熟度 `st`（1/2/3）とは別の軸**にする（`CLAUDE.md` §2-7 の `st` の値域を増やさない）。

### 10-4. ストリーミングをどう出すか

- **P0 では扱わない**（iframe に寄せる）
- P3 で自前チャット UI を作るとき、**U5（SSE を画面に出せるか）が最初の関門**。出せないなら (a) カスタムプラグインを書く (b) チャットだけ別の小さな SPA にして iframe で埋める、の 2 択。**(b) を先に検討する**（NocoBase を no-code の範囲に留められる）
