## 1. 踏んだ地雷（同じ穴に落ちないために）

### 1-1. 生成物の再生成を忘れると main が赤くなる
`docs/service-map.md` は `npm run index` の生成物で、`verify.mjs` §11 が鮮度を検査する。**実サービス・KB のファイル数・実装リファレンスが増減したら再生成が要る。**

実際に踏んだ：`docs/dify/usecases/GN-07.md` を足した PR（#147）をマージしたとき再生成を忘れ、**main の `npm test` が FAIL したまま約 21 分放置**された。次の PR（#149）のレビューで発見。

**さらに悪いのはここ**：その間にマージした #148 のコミットメッセージは「`npm test` ALL PASS」と書いてある。**PR 単体では本当に緑だった**。それぞれ緑の PR が合流すると赤くなる、という型で、**PR の緑は main の緑を保証しない**。

**教訓**：`docs/dify/usecases/**`・`dify/kb/**`・`mock/js/data/catalog.js` を触ったら `node tools/gen-index.mjs --check` を必ず通す。**マージした直後に main で `npm test` を回して確かめる**（PR の CI 結果を信じない）。

### 1-2. 共有ディレクトリで `git checkout` を打たない
`/home/user/Dify` は**サブエージェントも同時に使っている**。ここでブランチを切り替えると、作業中のエージェントの足元が変わり、**設計書が別ブランチの上に取り残される**（実際に起きた）。

**教訓**：状態確認は読み取り専用コマンドだけ。作業は必ず `git worktree` を切る。エージェントに作業を頼むときも**worktree のパスを指定する**（指定を忘れると共有ディレクトリで作業される）。

**副作用**：worktree はすぐ溜まる（1 日で 19 個になった）。`git worktree list` で確認し、用が済んだものは `git worktree remove` するか `git worktree prune` する。**共有ディレクトリが `main` 以外に乗っていないか**も、作業開始時に `git -C /home/user/Dify branch --show-current` で確かめる。

### 1-3. 「期待値を緩めて通す」は最悪の失敗
`dify/tests/*.json` の期待語は**絶対に削らない・緩めない**。テストが通らないときは、**期待値が間違っているのか挙動が間違っているのか**を切り分けて報告する。

reviewer には毎回「`git diff -- dify/tests/` が空であること」を最重要確認項目として渡している。

### 1-4. テストが見ていない領域がある
上の裏返し。`dify/tests/*.json` の期待語は**数値と条番号しか見ていない**ものが多く、**応答の言語そのものを検証していない**。そのため「`lang: zh` なのに応答が丸ごと日本語」でも PASS する（Issue #162）。

**教訓**：「全部 PASS」は「壊れていない」を意味しない。**何を検査していないか**を疑う。

### 1-5. 検査ツールの正本がツールの中にあった
`tools/check-world.mjs` は `data/world/*/calendar.md` を読み込みながら、**判定はコード内のハードコード配列で行っていた**（`calendarMd` が未使用のデッドコード）。CLAUDE.md §2-13 が「正本は `data/world/`」と定めているのに、実態は逆だった（#133 で修正）。

**教訓**：「正本」と書いてあるファイルが**本当に読まれているか**を疑う。書き換えて挙動が変わるか実験するのが確実。

### 1-6. 同じ内容を 2 言語で 1 つの KB に入れると両方沈む
日本語の規程と中国語の規程（同じ内容）を同一 KB に置いたら、**ベクトル検索で競合して両方とも圏外**になり、中国語の回答が 5/5 → 2/5 に退行した（DI-023）。

**教訓**：対訳を同一 KB に併存させない。言語をまたぐ情報が要るなら、**必ず上位に来る文書の中に併記**する（DI-022 はこれで解決）。

### 1-7. 検索に上がらない文書は存在しないのと同じ
「連絡先が回答から抜ける」を KB の言語非対称だと誤診し、日本語版を足したが**効かなかった**。Dify の検索テストで見たら、**規程はどちらの言語版も検索圏外**で、上位に来るのはアラームコード表だけだった。

**教訓**：KB の問題は**まず検索テストで、実際に何が返るかを見る**。プロンプトを疑う前にやる。

## 2. リモート環境の制約（できないこと）

| やりたいこと | 可否 |
|---|---|
| リモートブランチの削除（`git push --delete`） | **不可**。proxy が 403。REST の `DELETE /git/refs` も環境のセーフティに弾かれる。**Mac から実行してもらう** |
| `github.io` へのアクセス | **不可**（egress ポリシー）。Pages の確認は `file://` でローカルの `mock/catalog.html` を開く |
| `docs.github.com` などの参照 | **不可**。プラン仕様などは推測せず「確認してください」と言う |
| `gh` CLI | **無い**。GitHub 操作はすべて MCP ツール |
| 別アカウントのリポジトリを後から追加 | **不可**（cross-tier）。そのリポジトリを最初の対象にした**新しいセッション**が要る |

**GitHub MCP は落ちることがある**（`invalid session`。実績：約 1 時間）。落ちても **git は生きている**ので、実装・レビュー・push は続けられる。PR 作成とマージだけが止まる。

## 3. Mac との分業

**Dify Cloud への投入・公開・KB 操作は Mac にしかできない。** 理由は 3 種類あり、混同しないこと（詳細は `docs/handoff/2026-09-08-execution-split-and-runner.md`）。

| 理由 | 操作 | Mac 固有か |
|---|---|---|
| ブラウザのログイン済みセッションが要る | DSL の投入・公開・KB の紐づけ・キー発行 | **固有**（Cloud 1.17.0 は httpOnly Cookie ＋ `X-CSRF-Token`。`console_token` は無い） |
| 秘密がローカルにしかない | KB 投入・テスト実行 | **固有ではない** |
| 実行環境から Dify に到達できない | KB 投入・テスト実行 | **固有ではない** |

**KB 投入とテスト実行は GitHub ホストランナーで回せる**（#121 の W1）。これが入れば往復が半分になる。

### Mac への投げ方
1. **私から Mac へ直接届ける手段は無い。** PM がコピペする
2. **1 回で終わる形にまとめる。** 往復のたびに待ちが発生するので、修正は溜めてから一括で投げる
3. ブロックには必ず入れる：`git pull --ff-only` ／ 何を確認してほしいか（合否の判定基準）／ 効かなかったときの次の手 ／ **期待値は変えていない**旨

## 4. 進め方の型

- **3 エージェント分業**：architect（設計・Issue）→ implementer（実装・PR）→ reviewer（検証・マージ可否）。PM が判断する
- **reviewer は「実装者の申告を信じるな」と明示的に指示する。** 自分で grep・実行・突き合わせをさせる。これで実際に何度も救われている
- **設計書に「PM 判断」を推奨つきで列挙させる。** 判断の丸投げは受け取らない
- **PR 本文には「触っていない範囲」を必ず書かせる。** reviewer がそこを照合する
- **並列は「触るファイル集合が重ならないとき」だけ**（CLAUDE.md §5）
- **`git add -A` は禁止。** 変更ファイルを明示列挙する
- サブエージェントに**セキュリティ警告が付いたら、マージ前に自分で差分を検証する**（大量削除＋load-bearing ファイルの書き換えが同時に起きると付きやすい。実績あり）
