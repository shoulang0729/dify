### 1-5. 分かったこと（原因の整理）

1. **`lang` の意味は 12 本で揃っていない。** `lang` を「出力言語」と定義しているのは DC-01・GN-01・GN-05・NM-03、「表示言語（成果物は 2 版）」が DC-02、「返信言語（メール本文の言語）」が LG-04、DC-04・GN-02・LG-01 には `lang` が無い。**そして「出力言語」と定義した 4 本のうち 2 本（GN-01・NM-03）が `lang=zh` で日本語を返した。** 語の定義の問題ではなく、System の指示が「地の文まで含めて出力言語で書く」と読み切れないのが原因。実際、同じ「出力言語」でも DC-01 だけは `出力言語 {{…lang…}} で全文を書くこと（見出しを含む）` と**別行で念押し**していて、DC-01 T02 は S1（1 語）で済んでいる。
2. **横断ルール（#135・#155）の追記文が、自分が乗っている行と矛盾している。** GN-01・GN-05・NM-03 の該当行は「出力言語」を主語にしているのに、#155 が足した一文は「**見出し・分類名も入力言語で書く**」と書いてある。入力が中国語・`lang=ja` のケース（NM-03 T01・GN-05 T01）では文字どおり読むと逆の指示になる。**用語を「回答言語」に一本化する必要がある。**
3. **「地の文」と「引用」の区別がどこにも無い。** KN-02 T02 は KB の日本語文をそのまま引用ブロックに置いた結果、中国語の回答の中で安全注意だけが日本語になった。System には「引用は原語のまま」しか書いておらず、**引用を地の文の代わりに使ってよいのか**が定められていない。
4. **テストが応答言語を一切見ていない。** 48 ケースの `expect` は数値・管理番号・条文番号・定型文の断片だけで、S4 の 2 件が満点で通っている。

## 2. System の横断ルールの作り替え

### 2-1. 決めたこと

- **入れるのは 12 本すべて。** 6 本ではない。理由は 3 つ。
  1. 棚卸しで、横断ルールが入っていない 6 本の側にも実害が出ている（LG-01 T02＝S4、DC-04 T03＝S3、DC-01 T02＝S1、GN-02 T06＝S1）
  2. 「地の文は回答言語・引用の中だけ原語」は KB を読むかどうかに依存しない、`CLAUDE.md` §2-5 由来の**全サービス共通の契約**
  3. 12 本で**バイト一致の同一ブロック**にすれば `dify/check.py` で機械検証できる。6 本だけだと「入っている本／いない本」を人が覚えることになる
- 構造は **「アンカー 1 行（アプリごとに違う）」＋「共通 4 行（12 本でバイト一致）」**。アンカーで「回答言語」が何を指すかをアプリごとに定義し、共通 4 行はその語だけを使う。
- **#155 が足した `見出し・分類名も入力言語で書く（例：版ズレ → 版本差异）` は、共通 4 行に吸収して各行から削除する**（同じことを 2 か所で言わない。共通ブロックの 3 行目が上位互換）。

### 2-2. 共通 4 行（確定文言。12 本すべてでこの通り・1 バイトも変えない）

インデントは各ファイルの既存 System と同じ **半角スペース 12 個**。行末に空白を置かない。

```
言語の扱い（地の文と引用の区別。全サービス共通）：
- 地の文（見出し・小見出し・分析・コメント・注記・箇条書き・自分で書いた表の見出し）は、例外なく回答言語で書く。1 つの文の中で日本語と中国語を混ぜない。
- 原語のまま出してよいのは、引用符「」の中・引用ブロック（行頭 >）の中・番号や記号（E-47、7-12、ORG、MODE、SK-3310-A、TR-2024-007、§6.2）・文書の正式名称（取扱説明書、员工手册）だけ。
- 対応語がある概念は必ず回答言語の語を使う（手順→步骤、根拠→依据、備考→备注、版ズレ→版本差异、現地スタッフ→当地员工、保全課長→保全科长、ページ→页）。文書に「保全課長（保全科长）」のように両方の語が併記されているときも、回答言語の側の語だけを書く（併記の形のまま持ち込まない）。対応語が本当に無い語だけ、原語のまま書いて直後の括弧に回答言語の説明を添える。
- 引用した原文が回答言語と違う言語のときは、引用はそのままにして、その直後に回答言語で 1 行の要約を添える。引用を地の文の代わりに使わない。
```

**この 5 行（見出し 1 行＋箇条書き 4 行）がひとかたまりで「共通ブロック」。** `dify/check.py` はこの 5 行の連続が 12 本すべてに 1 回ずつ現れることを検査する。

## 4. テストに応答言語の検査を足す

### 4-1. どこに実装するか

**両方。役割を分ける。**

| 置き場 | 役割 |
|---|---|
| `dify/tests/*.json` | **何を期待するか**（宣言）。ケースごとに `expect_lang`（必須）・`lang_allow`（任意）・`lang_note`（`mixed`/`none` のとき必須） |
| `scripts/dify/lang_check.py`（**新規**） | **どう判定するか**（ロジック）。除外領域の切り出し・かな／簡体字の計数・判定。`run_tests.py` から import する純関数だけを置く（ネットワーク・ファイル I/O を持たない） |
| `scripts/dify/run_tests.py` | 呼び出しと合否への反映。結果表に列を 1 本足す |
| `scripts/dify/tests/test_lang_check.py`（**新規**） | 判定ロジックの単体検証。**実機ログから抜いた実際の出力**を固定文字列で持ち、いま壊れているケースが FAIL・正常なケースが PASS になることをオフラインで機械検証する |

判定ロジックを JSON 側に書かない理由：正規表現や文字集合を 12 個の JSON に散らすと、直すたびに 12 ファイルを触ることになり、`expect` を触らない約束と衝突する。**JSON は宣言だけ。**

### 4-2. `dify/tests/*.json` のスキーマ拡張

既存キーは一切変えない。ケースオブジェクトに次を足す。

```json
{
  "id": "NM-03 T02",
  "kind": "正常 zh",
  "mode": "workflow",
  "inputs": { "...": "..." },
  "query": "",
  "expect": ["0.42", "87.2", ["2140", "2,140"]],
  "expect_not": [],
  "expect_lang": "zh",
  "lang_allow": [],
  "lang_note": ""
}
```

| キー | 型 | 必須 | 意味 |
|---|---|---|---|
| `expect_lang` | `"ja"` / `"zh"` / `"mixed"` / `"none"` | **全 48 ケース必須** | 地の文の言語の契約 |
| `lang_allow` | 文字列の配列 | 任意（既定 `[]`） | 判定の前に本文から取り除く語。**文書の正式名称・型式・パネル表記など、原語のままが正しい語だけ**を入れる（例 `["取扱説明書"]`）。ここに一般語を入れて検査を骨抜きにしない |
| `lang_note` | 文字列 | `expect_lang` が `mixed` / `none` のときのみ必須 | なぜ単一言語で判定できないのかを 1 行で書く（JSON にコメントが書けないため） |

- `"ja"` / `"zh"`：地の文がすべてその言語
- `"mixed"`：仕様上、日中の両方が出る（DC-02 の 2 版・DC-04 の掲示文＋説明・LG-01 の訳文＋説明・LG-04 の本文＋解説）。**両方が存在すること**だけを検査する
- `"none"`：地の文が無い／契約が未定義。**検査しない**。`lang_note` に理由必須

### 4-3. 判定ロジック（`lang_check.py`）

#### 手順 1：除外領域を落として「地の文」を作る

上から順に、正規表現で置換して落とす。

| # | 落とすもの | 理由 |
|---|---|---|
| 1 | フェンス付きコードブロック ` ```…``` ` | JSON・CSV の出力がここに入る。キーは英字、値は入力の転記 |
| 2 | インラインコード `` `…` `` | 識別子 |
| 3 | 引用ブロック（行頭の空白 0〜3 ＋ `>` の行） | **KB 原文の引用は原語のままが正しい** |
| 4 | 表の行（行頭の空白 0〜3 ＋ `\|` の行） | 入力からの転記（`产量`・`计划`）が正しく入る。ここを見ると NM-03 T01（ja 期待）が誤判定する |
| 5 | URL・メールアドレス | — |
| 6 | 引用符の中：`「…」` `『…』` `《…》` `"…"` `“…”` `'…'`（行をまたがない・非貪欲） | 原文の直引き |
| 7 | 括弧の中：`（…）` `(…)` `〔…〕`（行をまたがない・非貪欲・入れ子は非対応） | **原語の括弧併記（`保全課長（保全科长）`・`（深さ60mm）`）を許すため。** 括弧内の地の文まで落ちるが、それは見逃す側に倒れるだけで誤検出は生まない |
| 8 | `lang_allow` の各語（単純な文字列置換） | 文書の正式名称など |
| 9 | ASCII・数字・記号・空白・絵文字 | — |

残った文字列が**地の文**。空になったら判定不能として **PASS ＋ warn**（結果表の言語列に `—（地の文なし）`）。

#### 手順 2：数える

- `kana` … ひらがな・カタカナの数。範囲は `U+3041–U+309F` ∪ `U+30A1–U+30FA` ∪ `U+30FC–U+30FF`。
  **`U+30FB`（`・`）は除く**（中国語の地の文でも区切りに使っている。実例：DC-02 中文版の `待办事项（负责人・期限）`）
- `han` … CJK 統合漢字（`U+4E00–U+9FFF`）の数
- `ja_only` … **JA_ONLY_HAN**（日本の新字体で簡体字と字形が違う字）の出現数と出現位置
- `zh_mark` … **ZH_MARKER**（簡体字のうち日本語の正書法に存在しない字）の出現数

#### 手順 3：判定

| `expect_lang` | 判定 |
|---|---|
| `"zh"` | **`kana >= 1` なら FAIL**（Tier A）。**`ja_only >= 1` なら FAIL**（Tier B）。両方 0 なら PASS |
| `"ja"` | **`han >= 20` かつ `kana / (kana + han) < 0.10` なら FAIL**（Tier A）。それ以外は PASS。**Tier B は適用しない** |
| `"mixed"` | `kana >= 1` かつ `zh_mark >= 1` なら PASS。片方が 0 なら FAIL |
| `"none"` | 常に PASS（列に `—` と出す） |

**なぜ非対称にするのか（設計の中心）**

- 中国語の回答に日本語（かな・和製漢字）が出るのは、引用・括弧併記・文書名を除いて**許されない**。だから **`zh` は厳格（かな 1 文字で落とす）**。
- 逆に、日本語の回答に中国語の原語が出るのは、`CLAUDE.md` §2-5 と横断ルールが**明示的に許している**（`保全課長（保全科长）`・中国語条文の引用・日報原文の転記）。**機械では正誤を分けられない**ので、`ja` には語レベルの検査（Tier B）を入れない。入れると KN-02 T01・KN-03 T01・NM-03 T01 の**正しい応答が落ちる**。
- 代わりに `ja` は「かな比率」で見る。日本語の地の文は必ず助詞・語尾を含むのでかな比率が高く、中国語で返ってきた瞬間に 0 に落ちる。GN-01 T01・NM-03 T02 はこれで確実に落ちる。

#### 手順 4：誤判定をどう避けるか（明示的に潰したケース）

| 誤判定のリスク | 対策 |
|---|---|
| **数値だけ・固有名詞だけの短い応答**（GN-05 T03 の定型文、GN-02 の CSV 1 行） | `ja` 判定に **`han >= 20` のガード**。これ未満は判定しない。`zh` 判定は「かな 0」なので短くても安全 |
| **意図的な原語引用**（KN-03 T01 が中国語条文を引く、NM-03 T01 が日報原文を引く） | 除外 3（引用ブロック）・6（引用符）で落とす |
| **括弧の原語併記**（`保全課長（保全科长）`） | 除外 7（括弧）で落とす |
| **入力から転記した表のラベル**（NM-03 の `产量`・`计划`） | 除外 4（表の行）で落とす |
| **CSV／JSON の出力**（GN-02・DC-01・DC-02・DC-04 の JSON ブロック） | 除外 1（コードブロック）で落とす。フェンス無しで出た場合は英字キーが除外 9 で落ち、値は入力転記なので `ja` のガードに掛かる |
| **文書の正式名称**（`取扱説明書`・`员工手册`） | `lang_allow` に列挙。既定では KN-02 に `["取扱説明書"]` を入れる |
| **中国語で使う `・`** | `U+30FB` をかなから除外 |
| **JA_ONLY_HAN の取りこぼし／入れすぎ** | 文字集合を**実機ログで観測した字から始める**。増やすときは「どの結果ファイルの何行目で観測したか」をコメントに書く。**推測で足さない**（入れすぎると正しい応答が落ちる） |

#### 文字集合（初期値）

`JA_ONLY_HAN`（日本の新字体で、簡体字と字形が異なる字。観測済みの `順`・`拠`・`現` を含む）

```

圧 労 権 従 帰 帳 達 録 認 議 課 連 絡 確 準 拡 増 戻 緊 練 級 給 齢 頼 顧 難 額 類
題 頻 働 込 畑 峠
```

`ZH_MARKER`（簡体字のうち日本語の正書法に存在しない字。`mixed` の「中国語が居ること」の判定にだけ使う）

```
这 个 们 说 请 应 确 时 关 无 为 该 须 处 结 员 议 认 计 报 产 电 长 门 问 间 见
货 质 费 资 车 东 马 农 汉 观 边 达 运 连 进 远 还 过
```

**どちらも「観測した字だけ足す」運用。`lang_check.py` の 1 か所にだけ置き、単体テストで守る。**

## 5. FAIL を許容する順序

### 5-1. 前提の整理

`run_tests.py` の実機実行は **CI に入っていない**（API キーが要る）。`npm test` も CI の `verify` も走らせるのは `verify.mjs` / `regress.mjs` / `dify/check.py` / `render.py --check` / `test_sync_back.py` / `test_run_tests.py` だけ。
つまり **「検査を足した瞬間に main の CI が赤くなる」ことは起きない。** 起きるのは「Mac で実機を回したときに FAIL が出て、その結果ファイルを `dify/results/` に commit する」だけ。

### 5-2. 決めた順序

1. **PR-1（検査）と PR-2（是正）を並列で作り、両方 main へ入れる。実機は回さない。**
   - この時点で CI は緑（オフラインの検査だけ）
   - 「壊れていることを機械が知っている」状態になる（`test_lang_check.py` が実機ログで NG を再現している）
2. **Mac で 1 回だけ実機反映＋全 12 本テスト（§6）。**
3. **PR-3 で結果ファイルと台帳を main に入れる。残った FAIL があってもそのまま入れる。**
   - `dify/results/**` は**記録**であって CI ゲートではない。#154 が未解決の記録を入れたのと同じ扱い
   - 残った FAIL は `dify/KNOWN_ISSUES.md` に **DI-025 以降**として `open` で 1 行ずつ書く
   - **絶対にやらないこと：緑にするために `expect_lang` を `none` に落とす／`lang_allow` に一般語を積む／`expect` を削る。** どうしても契約を変える必要があると判断したら、**この設計書の追補版を書いて PM の承認を取ってから**変える（`CLAUDE.md` §4）

### 5-3. なぜ「先に検査、後で実機」なのか

- 是正の効き目を測る**基準（before）は、この設計書 §1 の棚卸し表と `test_lang_check.py` の 15 本**で足りている。実機を 2 回回す必要は無い
- 逆順（先に是正 → 実機 → あとで検査）にすると、Mac をもう 1 回使うことになる（Issue の制約に反する）

## 10. 想定される反論と答え

**「`zh` でかな 1 文字を FAIL にするのは厳しすぎないか」**
DC-01 T02 の `翌月见通し` は、まさにその 1 文字（`し`）だけの混入で、**顧客に見せたら一発で分かる種類の粗**。逆に、正しい原語併記は括弧・引用符・引用ブロックの中にあり、除外領域で落ちる。§4-7 の #8〜#12 でそれを機械検証する。緩めるなら `lang_allow` に語を足す形にして、**なぜ許すのかが 1 語ずつ残る**ようにする。

**「`ja` に語レベルの検査を入れないのは片手落ちでは」**
入れると KN-02 T01（`保全課長（保全科长）`）・KN-03 T01（中国語条文の引用）・NM-03 T01（日報原文の転記）という**正しい応答**が落ちる。§2-5 と横断ルールが原語併記を明示的に許している以上、機械で正誤を分けられない。**誤検出ゼロを優先**し、`ja` 側は「丸ごと中国語で返ってきた」だけを確実に捕まえる。

**「KB を触らず System だけで直せないか」**
直せない。KN-02 T02 の安全注意は**KB に日本語しか無い情報**で、System が「地の文は回答言語」と言っても、モデルが自分で訳語を作ることは横断ルールが禁じている（`自分で訳語を創作しない`）。KB 側に中国語の対応語を置いて初めて、System の「対応語がある概念は回答言語の語を使う」が効く。**KB と System は対。**

**「12 本に入れると差分が大きい」**
差分は 1 本あたり 6 行（アンカー 1 ＋ 共通 5）＋ 6 本は 1 行削除。合計 78 行の追加・6 行の削除。**共通 5 行がバイト一致なので、reviewer は 1 回読めば 12 本ぶん読んだことになる**。`dify/check.py` が機械で守る。
