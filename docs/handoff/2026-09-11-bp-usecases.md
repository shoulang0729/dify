### 2-3. 契約レビュー —— なぜ「新規」なのか（一致 3/5 の分かれ目）

`/usecase` S4 の分かれ目は「**画面を分けないと使えないなら分割。フォームの 1 項目で切り替えられるならモード**」。

| | DC-07 契約ドラフト支援 | 契約レビュー |

### 2-4. PPT 自動生成をサービスにしない理由

DC-01・DC-09 は「**何を書くか**」を決めるサービスで、出力が Markdown か Word か PPTX かは**出口の形式**にすぎない。形式ごとにサービスを増やすと、同じ業務が 2 件並んで 5 軸一致 5/5 のサービスができてしまう（統廃合ルール違反）。**PC-13（ファイル出力）の実現手段候補**として `build-or-buy.md` に記録する。

### 2-5. アパレルデザインを対象外にする理由

架空世界は 3 つ（製造＝青嶺精工／金属加工の精密部品、金融＝碧洋銀行、IT＝翠雲システムズ／SIer）。アパレルはどれにも当たらず、5 軸すべて 0。**新分類を立てても、それを使うペルソナ・拠点・データがマスタ（`data/world/`）に無い**（§2-13）。無理に作ると架空世界の一貫性が崩れる。

**記録は残す**：`build-or-buy.md` に「対象外。アパレル業種の顧客が現れたら、まず `data/world/<新業種>/` を立てるところから」と 1 行。

### 2-6. 採点を「対象外」にする理由（**PM 判断 2026-09-11**）

**PM 判断：#6 は「PO-03 に部分統合」ではなく対象外。** 理由（PM の言葉）：**教育向けの製品で、3 つの世界のどの業務にも主用途が無い。研修の理解度テストは PO-03 の範囲で足りる。**

### 2-7. 履歴書スクリーニング統合の但し書き（**重要な発見**）

**PT-05 は「氏名・連絡先はエージェント側に留め、匿名化された候補者 ID だけを受け取る」設計**（`SVCS.pt5.desc` に明記。PC-10 個人情報・PC-15 パートナー連携ゲートウェイの前提）。

BP 履歴書スクリーニング製品は **履歴書そのものを自社側で解析する**。統合すると **PT-05 の前提が裏返る**：

| | PT-05 の現行設計 | BP 製品を使う場合 |
|---|---|---|
| 個人情報の所在 | エージェント側（自社は匿名 ID のみ） | **自社側**（履歴書の原本を取り込む） |
| PIPL 上の位置づけ | 最小限の受領 | **個人情報の取扱者になる** |
| PC-15 の `not_sent` 表示 | 「氏名・連絡先・個人の給与は送信していない」 | **成り立たない** |

→ **`usecases/PT-05.md` §10（未確定・リスク）に、この 1 点を必ず書く。** 「BP 製品で実現する場合、PT-05 の匿名 ID 前提は採れない。PIPL 評価と保管・削除の経路（PC-10）を先に決める」。
→ **`SVCS.pt5.desc` は変えない**（現行の設計が正しい。BP 製品を採るかどうかはまだ決まっていない）。

「6 軸のスコア表」は結果パネルの表現。**モックの結果パネルは `items` と `columns+rows` の 2 型しかない**ので、レーダーチャートは描けない（§5-3）。

## §3. 「BP 実装済み」をカタログでどう表すか —— 本書の本体

### 3-1. まず線を引く —— `st` は動かさない

`CLAUDE.md` §2-7：成熟度 `st` は **1 提供中 / 2 試行版 / 3 構想**。この 3 つは「**我々の Dify 実機がどこまで動いているか**」を指す。`st: 1` が 12 件しかないのは、`dify/apps/` に DSL があり Cloud で動いている 12 本と一致しているからで、`docs/service-map.md` の ②DSL 列・④テスト列がその証拠になっている。

**BP の製品が存在することは `st` を上げる理由にならない。** 上げたら、`st: 1` の意味が「我々が動かせる」から「世の中に何かがある」に化けて、`service-map.md` の列と食い違い、実機の投入状況が追えなくなる。**この線は動かさない。**

## §5. 台本（`SCENARIOS`）への反映方針

### 5-1. 原則 —— 実現手段は台本に書かない

台本は**顧客に見せる画面**（GitHub Pages で公開される）。**製品名・ベンダ名・記号（`ζ 社`）を台本に書かない。**

### 5-2. BP 製品の特徴を、台本に入れてよいか（4 件の判定）

有識者フィードバック（`2026-09-10-expert-feedback.md` §9）の基準は「**何と何をつなぎ・どのインプットをどう読み・どこまで確認しているか**」。**利用者から見える業務の事実なら入れてよい。内部の実装挙動は入れない。**

| 特徴 | 判定 | 理由・書き方 |
|---|---|---|
| **レイアウト復元** | **入れてよい**（ただし本件では実施しない。§5-4） | 「元の Word の体裁のまま訳文を返した」は利用者から見える事実。ただし **LG-01 の台本は現在 `template: 'form'`（原文を貼り付ける）** で、ファイルを渡す話ではない。入れるならテンプレートごと `upload` に変わる＝**台本の作り直し** |
| **SQL 自己修復** | **入れない** | 内部の実装挙動。利用者に見えない。**ただし業務語に翻訳できる部分だけは可**：「1 回目の集計が空だったので、期間の取り方（締め日基準か暦月基準か）を変えて再集計した」。これは「どこまで確認しているか」に当たる |
| **逸脱項目のチェック** | **入れる** | **DC-11 の本体**。新規サービスなので新規台本で書く（§4-5 の観点 4） |
| **6 軸のスコア表（レーダー）** | **図としては入れられない** | 結果パネルは `items` と `columns+rows` の 2 型のみ。**`columns+rows` の「評価軸 × スコア × 根拠」の表**として書く。「六角レーダー」という言葉は使わない |

### 7-2. コンテンツ監査 —— **ポータルの PostgreSQL に持つ**（推奨）

#### 7-2-1. rev3 に何が無いか

rev3 は `ai_usage_log`（P1）を持っている：`log_id` / `service_no` / `staff_id` / `invoked_at` / `screen_key?` / `pipeline_stage?` / `mode` / `ok` / `saved_minutes_est`。
**これは「誰がいつ何を呼んだか」のメタデータだけで、入出力の本文を持たない。** K8 の集計元としては十分だが、**コンテンツ監査には足りない**。

#### 7-2-2. 置き場の 3 候補と判定

| | 候補 | 成立するか | 評価 |
|---|---|---|---|
| **(A)** | **`portal/` の PostgreSQL に `ai_audit_log` を新設**（Flyway の DDL） | ✓ | **推奨** |
| (B) | ζ 社製品に持たせる | △ | **(a′) の呼び出しを拾えるか未確認**（U29。§7-7）。監査のためだけに BP の GW を経路に挟むことになり、§7-3 と一体でないと成立しない |
| (C) | Dify Enterprise の機能に任せる | △ | **(a′) は「ポータルの Workflow → HTTP request → Dify Service API」なので、本文は最初にポータル側にある。** Dify 側のログは**二重の記録**にはなるが、ポータル側でマスクした後の文字列と一致する保証が無い |

**(A) を推奨する理由 4 つ**

1. **rev3 の流儀に揃う。** §0-2 の「監査・履歴」行は既に「NocoBase の Record history（Professional+）・Audit logs（Enterprise+）に依存しない。業務 DB 側に `*_history` を Flyway で作る。**境目＝無し**」と決めている。同じ器に足すだけで、**デモ → 本番の置き換えが 1 つも増えない**
2. **漏れが最も少ない。** rev3 §14-5 の置き方は 3 つ（(a′) 画面のボタン → Workflow → HTTP request ／ (b) iframe ／ (c) 夜間の一括）。**(a′) と (c) はポータルが本文を組み立てる**ので、ポータル側で記録すれば確実に拾える。(b) の iframe だけは拾えないが、**(b) は「公開 Web アプリにログイン不要で入る」用途に限る**と rev3 が決めているので、そこに業務データは流れない（流れたら (a′) に寄せる、が rev3 の歯止め）
3. **Community の制約に当たらない。** Flyway の SQL とテーブルは**無料**。Audit logs（Enterprise+）を買う話にならない
4. **public リポジトリの前提を壊さない。** DDL は定義、データは架空世界。`tools/check-nodata.mjs`（rev3 §7-4）がそのまま効く

#### 7-2-3. テーブル —— **`ai_usage_log` とは別テーブルにする**

| テーブル | 段階 | 列 | 保持 |
|---|---|---|---|
| `ai_usage_log`（rev3 既存） | P1 | `log_id` / `service_no` / `staff_id` / `invoked_at` / `screen_key?` / `pipeline_stage?` / `mode` / `ok` / `saved_minutes_est` | **FY+2 年**（K8 の前年同期比に要る） |
| **`ai_audit_log`（rev4 新設）** | P1 | `log_id`（`ai_usage_log` への 1:1 FK）／`prompt_redacted`／`response_redacted`／`attachments`（**ファイル名とハッシュだけ。本体は持たない**）／`model`／`provider`／`tokens_in`／`tokens_out`／`redaction_applied`（bool）／`redaction_rules_version`／`retention_until` | **90 日** |
| **`ai_audit_access`（rev4 新設）** | P1 | `access_id`／`viewer_staff_id`／`log_id`／`viewed_at`／`reason` | **FY+2 年** |

**★ なぜ 2 テーブルに分けるのか（本節でいちばん重要）**

- `ai_usage_log` は **K8 の集計元で全社が読む**。`ai_audit_log` は**本文を持つので閲覧者が限られる**
- 1 テーブルにすると「列単位で隠す」ことになるが、**NocoBase Community の ACL は画面・ブロック・行（データスコープ）で切るのが素直で、列単位の制御は弱い**。**テーブルを分ければロールで切れる**
- **保持期間を別々にできる。** 本文は 90 日で物理削除、メタは FY+2 年。**本文を消しても K8 が壊れない**——これが実利
- **`ai_audit_access`（誰が本文を見たか）を持つ。** 監査ログを見た事実が記録されないと、監査そのものが統制されない

#### 7-2-4. 誰が見るか

| 役割（C3 の 5 区分） | 集計（回数・サービス別・失敗率） | **本文** |
|---|---|---|
| **General User（本人）** | 自分の分 | **自分の行だけ**（データスコープ `staff_id` = Current user） |
| **PM / Delivery** | 自分の担当分 | **見ない** |
| **Management（組織長）** | **見る**（部門の集計） | **見ない** |
| **PMO** | **見る**（全社の集計） | **失敗した呼び出し（`ok=false`）の本文だけ**（改善のため） |
| 情シス（Management ロールに含める or 別ロール） | 見る | **全件**（インシデント調査時。**`ai_audit_access` に必ず残る**） |

**★ 「組織長は本文を見ない」を既定にする。** rev3 §5-18-4 の決め「**誰が AI を使っていないかを出す画面を作らない**（作った瞬間に使われなくなる）」と同じ理由。**中身を上司に読まれると分かった時点で、誰も業務の本音を入力しなくなる。**

#### 7-2-5. 保持期間と削除

- `ai_audit_log`：**90 日**。`retention_until` を列で持ち、**日次の Workflow が期限切れ行を物理削除**（rev3 の PC-10「Dify 会話ログ・Langfuse トレースの保持期間（例 90 日）」に揃える）
- 削除するのは**本文だけ**。`ai_usage_log` のメタは残る
- **個人情報削除依頼**（rev3 §5-12-2 の `pii_erasure_requests` ＋ 1 トランザクションの論理削除）の**対象テーブルに `ai_audit_log` を必ず含める**。**含め忘れると「消せないところ」が 1 つ残る**（rev3 が最も警戒していた形）

#### 7-2-6. 個人情報のマスキング

- **記録する前にマスクする。** PC-10 の Code ノードのマスク（身分証 18 桁・電話 11 桁・メール・銀行口座・氏名リスト → `[ID]` 等）を、**Dify に送る文字列に対して 1 回だけ掛け、その同じ文字列を記録する**
- **★ 送る文字列と記録する文字列を同一にする。** 別々にマスクすると、送った内容と記録が食い違い、**監査の役に立たなくなる**
- `redaction_applied`（掛かったか）と `redaction_rules_version`（どの版のルールか）を持つ。**ルールを変えたら版が上がる**ので、過去ログがどの基準でマスクされたかが後から分かる
- **添付は本体を持たない**（ファイル名とハッシュだけ）。本体を持つと `pii_erasure_requests` の経路が一気に重くなる

#### 7-2-7. K8 との関係（**出所はメタであって本文ではない**）

### 7-3. LLM ゲートウェイ —— **出口は Dify 1 本のまま**（推奨）

#### 7-3-1. いまの設計では出口が既に 1 本

rev3 §14-5：ポータルは **LLM を直接叩かない**。(a′) は「画面のボタン → Workflow → **HTTP request → Dify の Service API**」。モデル・プロバイダ・`completion_params` は **`dify/env/<env>/env.yml` の `models:` に閉じている**（`CLAUDE.md` §2-12）。

→ **キー管理・利用量・モデル切替・国内モデルの使い分けは、すでに 1 か所（Dify ＋ env）に集約されている。**

#### 7-3-2. 3 つの置き方と判定

| | 置き方 | 成立するか | 評価 |
|---|---|---|---|
| **(i)** | **Dify（Cloud → Enterprise）に寄せる**（rev3 の現行設計） | ✓ | **推奨** |
| (ii) | ζ 社 GW を **Dify の手前**に置く | ✓ | **ポータル → ζ GW → Dify → ζ GW → LLM** になり、**同じ層を 2 回通る**。キー管理が 2 か所、利用量の数字が 2 系統 |
| (iii) | ζ 社 GW を **Dify と並べ**、一部の呼び出しは Dify を通さず直接 LLM へ | ✓ | **出口が 2 本になる。** 管理番号（`service_no`）で追えない呼び出しが生まれ、**rev3 §10-1「管理番号が移行のキー」が崩れる**。K8 の集計も 2 系統になる |

#### 7-3-3. 集約先の一覧（(i) を採った場合）

| 何を | どこで集約するか |
|---|---|
| **キー管理** | `dify/env/<env>/env.yml` の `${VAR}`（`CLAUDE.md` §2-12）。ポータル側は `${DIFY_BASE_URL}` と `${DIFY_API_KEY_<番号>}` だけを持つ |
| **利用量（技術面）** | **Langfuse**（PC-09。サービス別コスト・p95・失敗率） |
| **利用量（業務面）** | **`ai_usage_log`**（§7-2。K8 の 3 指標） |
| **モデル切替** | `env.yml` の `models:`（用途 `chat`/`reasoning`/`embedding`/`rerank`）。**マスタ DSL は触らない**（§2-12） |
| **国内モデル（Qwen / Kimi 系）の使い分け** | 同じく `env.yml`。マスタ DSL の既定は `langgenius/openrouter` `qwen/qwen3.8-max`。**中国側は `models/siliconflow`、人事・図面は `models/ollama`（越境ゼロ）**という使い分けが PC-08 に既にある |

#### 7-3-4. **1 つだけ例外を認める**

**Dify Enterprise を入れない（本番も Cloud のまま）と決めた場合**、rev3 §14-5 の歯止め（「本番の実データを Dify Cloud に送らない。(a′)/(c) は Enterprise に切り替わるまで有効にしない」）により、**(a′) と (c) が本番で永久に無効になる**＝ポータルの AI がほぼ死ぬ。
そのときは **国内に置ける LLM の出口が別途要る**ので、**ζ 社 GW が候補になる**。

→ **本当の問いは「LLM ゲートウェイを買うか」ではなく、「Dify Enterprise を入れるか」**（§10 Q6）。

#### 7-3-5. **rev3 §0-2 の対応表に足す 2 行**（rev4 の差分。これが本節の成果物）

### 9-1. 全 PR 共通（**最重要**）

**禁止語リストそのものをリポジトリに置かない。** 置いた時点で §1-1 に違反する（grep のパターンに書いても公開されることに変わりはない）。

**手順**：

1. PM が禁止語リストを **リポジトリの外** に作る（`~/.config/dify/bp-denylist.txt`。1 行 1 語。ベンダ名・製品名の ja/zh/en・ドメイン・担当者名・電話番号・金額）。`CLAUDE.md` §2-10 の「設定ファイルはリポジトリの外（`~/.config/dify/`）」と同じ置き場

```bash
git grep -n -i -f ~/.config/dify/bp-denylist.txt -- . || echo "OK: 0 hits"
```

→ **0 hit であること。**

3. **リストが手元に無い環境**（CI・別の担当者）では、**形だけで引っかかる汎用パターン**で代替する。これらは何も明かさない：

```bash
# 11 桁の連番（中国の携帯番号の形）
git grep -nE '[^0-9][0-9]{11}[^0-9]' -- docs/ data/ mock/ || echo "OK"

git grep -nE '¥[0-9,]{4,}|人民币[0-9]' -- docs/ data/ mock/ || echo "OK"
# 生の URL（設計書・台帳に外部ドメインを持ち込まない）
git grep -nE 'https?://[a-z0-9.-]+' -- docs/handoff/2026-09-11-bp-usecases.md docs/handoff/bp-usecases.issue.md docs/dify/build-or-buy.md data/world/it/vendors.csv || echo "OK"
```

> ```bash
> git diff origin/main...HEAD | grep -E '^\+' | grep -nE '¥[0-9,]{4,}|[^0-9][0-9]{11}[^0-9]|https?://' || echo "OK: 追加行に無し"
