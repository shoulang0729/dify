**S6 の必須手順（今日の 2 回で効いたもの。省略不可）**

1. リテラル（`SVCS.<id>` / `SCENARIOS.<id>`）を**設計書に全文**書く。implementer に翻訳・言い換え・数字の作り直しをさせない
2. **作業用コピーで先に verify / regress を実走する**
   ```
   cp -r <repo> <scratchpad>/verify-<slug>
   # <scratchpad>/verify-<slug>/mock/catalog.html にリテラルを差し込む
   node <scratchpad>/verify-<slug>/tools/verify.mjs
   node <scratchpad>/verify-<slug>/tools/regress.mjs
   ```

4. 「触らない範囲」を**ファイル・関数・データ構造の粒度**で列挙する（reviewer の diff 監査基準になる）
5. 差し替え位置は**行数と目印**で書く（例：「`dc7` の直後、`/* ---- lg: ---- */` の直前。新リテラルは 5 行」）

## 3. 統廃合の判定基準（S4）

### 3-1. 5 軸で一致数を数える

| 軸 | 見るもの | 一致の判定 |
|---|---|---|
| **A 分類** | 大分類・中分類（`cat`/`sub`） | 同じ中分類なら一致 |
| **B タグ** | `tags` の重なり | 2 つのうち 1 つ以上が同じなら一致 |
| **C ペルソナ** | 誰が使うか（役職・部署・母語） | 同じ人が使うなら一致 |
| **D 入出力** | 入力の種類（報告書／図面／伝票／自由文）と出力の形（表／論点／ドラフト） | 入力と出力の**両方**が同種なら一致 |
| **E 出口** | 結果が誰の判断に効くか、どこへ残るか（台帳・Outline・BPMS・通知） | 同じ後工程なら一致 |

### 3-2. 一致数 → 判定

|---|---|---|---|
| **5 / 4** | **統合** | 既存サービスの `name`/`desc`/`SCENARIOS` を差し替える。**新規採番しない**（`SVCS` 件数は不変） | DC-08 改訂（Notion 2 本 → 既存 `dc8` を差し替え。`regress` 差分 0 行） |

### 3-3. 「モード化」と「目的別分割」の分かれ目（最重要）

> **画面を分けないと使えないなら分割。フォームの 1 項目で切り替えられるならモード。**

| | モード化 | 目的別分割 |
|---|---|---|
| 判定条件 | 入力の種類が同じで、**出力の中身と語調だけが変わる** | 入力の種類そのものが違う、または**両方を同時に出すと片方が邪魔になる**うえに切替項目で表せない |
| データ層 | **1 サービス**。`SCENARIOS.<id>.input.fields` にモード選択項目を置く | **2 サービス**。それぞれ採番する |
| 顧客への説明 | 「同じ画面で目的を選ぶ」 | 「別のエージェント」 |
| 前例 | **DC-08**：報告種別 × 読み手 × 目的 の 3 項目をフォームに置き、`template` を `upload` → `form` に変えただけで表現できた（描画関数・CSS の変更 0） | 今日は該当なし |

- **モード化を選んだら `template: 'form'` を第一候補にする**。`form` の `input.<lang>.fields`（`label` ＋ `value`）が**モード選択をそのまま描ける**唯一のテンプレート
- モードを 10 個以上並べるときも **`if-else` で分岐を作らない**。プロンプトに `{{extra_criteria}}` `{{tone}}` `{{output_blocks}}` を差し込む形にして、モードマスタ（表 1 枚）を顧客がカスタムする（`docs/dify/usecases/DC-08.md` §1-2・§8-3）
