# QA01の同じチャットで記録作成と過去検索と比較

2026-10-12。M/L、`run:mac`。ユーザーはQA-01を同じチャットで使い、依頼内容から写真での記録作成、過去の検索、記録の比較へ切り替えることと、それぞれの入出力の重要箇所を黄色にすることを確定した。A/B選択メニュー、モード切替、別のサービス番号は追加しない。写真入力・草案更新・NM-05のまとめ・お気に入りの既存動作を保つ。Issue／PR／公開操作は行わない。お気に入りとstの追加変更は値が未指定のため本設計では行わない。

## 1. チャットで始める

QA-01のtemplate:'upload'は保持し、`startMode:'chat'`を追加する。ただしNM-05の「完了数だけで分析表を出す」共通分岐とは分け、QA-01専用の入力・結果を描く。初期はチャットと質問例を表示し、左の固定アップロード欄と実行ボタンを出さない。

質問例はメニューではなく、クリックするとその自然言語を送るchip。次のja／zhリテラルを `qaPrompts` に置く。

| 目的 | ja | zh |
|---|---|---|
| 写真で作成 | この写真から不具合の記録草案を作って | 根据这些照片制作不良记录草案 |
| 検索 | NC-2025-0912に似た過去の塗装ブツを探して。記録の根拠と当時の対策も見たい | 查找与NC-2025-0912相似的过去涂装颗粒记录，也想看依据与当时的措施 |
| 比較 | NC-2025-0912と過去の塗装ブツの記録を比較して | 比较NC-2025-0912与过去涂装颗粒记录 |

記録作成依頼を受けたら、チャット入力に連なる添付領域に既存のファイル選択・サンプル・プレビュー・upNoteを表示する。写真がない場合は添付を促すだけでAの第1回答を消費しない。「サンプルを使う」で既存3原票を載せられる。添付操作だけで草案を完成させず、依頼を送った時点で既存Aへ進む。添付ファイルは従来のupFilesと表示処理を使う。写真の読み取りや送信を新設しない。

検索・比較は写真必須にしない。切替時もupFilesと原票プレビューを保持し、写真を削除しない。写真添付欄は記録作成時に見せ、検索だけを始めた利用者には要求しない。実際の登録・業務記録の保存は行わず、画面上の草案まで。

## 2. 意図判定と確認質問

判定はこのモックの対応例に限定したローカル規則で、任意の自然言語を正確に理解できると主張しない。app.jsで依頼語と対象を読む。`記録を比較`は記録作成へ誤分類しない。日本語・中国語の検索、比較、写真での草案、原票確認、日中版確認の語句を扱う。曖昧な内容を勝手に次のAターンへ進めない。

| 依頼 | 処理 |
|---|---|
| 写真から記録・報告草案を作る | 添付があれば既存A第1回答。写真なしは添付を促す |
| 過去の塗装ブツを探す | 対象番号なしでも既存の2候補を示せる。今回の品番・ライン・濃度を仮定しない |
| NC-2025-0912に似た過去を探す | 既知の今回記録を対象として2候補。比較時もその対象を使える |
| 記録を比較・分析する | 比較する今回記録と過去候補が明示／会話で特定済みなら比較。対象不明は質問 |
| 次に見る資料、過去対策の根拠を確認 | 検索・比較の対象に応じてB第3回答。原本や根拠箇所を生成しない |
| 原票で3.8と12を確認した | 既存A初稿があり、濃度・撹拌時間・確認者を特定できる場合だけA第2回答 |
| 日中版を確認する | A第2回答完了後に既存A第3回答。確認値不足は先に質問 |
| 目的／対象が曖昧、未知の記録番号、サンプルと異なる確定値 | 条件を聞く。既存の3.8／12に黙って置き換えない |

継続の短い依頼は最後に完了した会話の対象を使える。ただし、明示的な検索・比較・原票確認は直前の会話と異なっても切り替える。対象不明の「今回」からNC-2025-0912を推定しない。

確認質問はqa1のja／zhメタデータに置く。例：

| 条件 | ja | zh |
|---|---|---|
| 目的不明 | 何を進めたいですか。対象の不具合や記録番号を教えてください。 | 想进行什么操作？请说明不良现象或记录编号。 |
| 検索条件不足 | どの不具合を探しますか。現象、工程、記録番号のいずれかを教えてください。 | 想查找哪类不良？请说明现象、工序或记录编号。 |
| 比較対象不足 | どの記録と何を比較しますか。今回の記録番号と、比較したい過去の記録や条件を教えてください。 | 想比较哪些记录、哪些内容？请说明本次记录编号及要比较的过去记录或条件。 |

質問も同じチャット履歴へ残すが、A草案やB比較の段階は進めない。

## 3. 同じ会話の履歴と結果を保持する

`state.log`は既存の `[{lang,q,a}]` のまま。state必須キー・localStorageの3キー・一般サービスのconsume／nextTurn／log.length進行は変更しない。QA-01だけ、依頼で選ぶ回答をappendする専用入口を設ける。単一のA台本に全発話数を当てはめない。

app.jsにstate外の一時メタ `qaTurnMeta` を設け、各state.log要素と同じindexに置く。形は `{route:'record'|'history'|'clarify', step:1|2|3|null, action, targetNc, variant, inputPhrases, outputRef}`。新しい会話保存は行わない。履歴とメタは同じ関数で同期してappendし、どちらかだけ更新しない。

- recordのstepは既存Aの1／2／3。最新の**完了したrecordメタ**だけからdraftStageを算出する。
- historyのstepは検索1／比較2／次資料3。明示的な再検索はstep1、再比較はstep2を再表示してよい。検索回数をA工程へ足さない。
- clarifyはstep:null。質問を残すだけで草案・検索結果を更新しない。
- pendingは最後のlog／メタを未完了として扱う。前の草案と検索結果を維持し、返答描画完了時に対応する結果だけ更新する。
- Aの結果言語は最初のrecordターンのlangを使い、3段階目の版確認は既存どおりUI言語へ連動。Bの結果言語はそのhistoryターンのlang。UI英語でも台本はjaフォールバック。UI切替でユーザー入力を翻訳・上書きしない。
- 再描画はlogとメタから履歴・回答・印・最新結果を復元する。A→B→Aで最新A草案と確認履歴が残り、B→A→Bで検索条件・候補と比較対象が残る。
- 初回start、restart、別サービス／業種へ移る際のlog初期化に合わせてメタも初期化する。単なるUI言語／テーマ切替では初期化しない。確認値はリロード後の業務記録として保存しない。

左の結果領域には、完了済みの最新A草案、Bの候補表、比較表、次の確認資料を保持する。直近で更新した結果を上へ置き、以前の結果は既存見出しのdetailsで開いて読めるようにする。別モードのタブは作らない。A草案そのものを検索表で上書きしたり、検索後に消したりしない。

## 5. 入力と出力の黄色マーカー
