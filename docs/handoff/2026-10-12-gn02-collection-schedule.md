# GN-02に集金予定表作成を追加する

2026-10-12／M/L／ローカルレビュー用。Issueは末尾の草案のみ、外部未投稿。

## 1. 目的と範囲

既存GN-02「請求書（発票）処理」に、売掛側の「集金予定表作成」を追加する。同じチャットで、受領発票・発注・入庫の三点照合（AP）と、元請求・納品情報を完成見本の形へまとめる予定表（AR）を依頼から区別する。サービス、番号、分類、ステータス、お気に入りを増減しない。SVCSは前後とも88件、変更idはgn2の説明文のみ。gn2のname、st=2、industries、tagsは保持する。

参照する番組はNHK第1回 lOlsgsX_G1s の18:38–22:00。親の確認では20:20付近にExcel2件と「納品書を集計して集金予定表のようにまとめてほしい」が示される。番組元データと全列は未入手のため、架空の入力・完成見本で流れを再現する。番組の「約1時間→約1分」を本デモの実測・性能保証には使わない。

別セッションのスライド3／7で確認された「元資料→完成見本→AI→人の照合確定」「取込→抽出→整形照合→出力→人の確認確定」に対応させる。初稿を人が照合し、追加入力で修正版を確認する場面を必ず残す。スライド原本は保持し、親が用意する別artifactのシナリオスライドから完成後のローカルデモへリンクする。

今回はブラウザのカタログモックだけを変更する。既存APのinput、result、ja/zhの3ターンq/aと数値はバイト保持。QA、NM、原画像、全st/fav、localStorage3キー、stateの必須キー、logの{lang,q,a}、一般サービスのnextTurnを保持する。Dify実接続、任意Excel読取、OCR、会計登録、実機state、公開操作は対象外。

## 2. 画面と操作

GN-02はtemplate:'upload'を維持し、startMode:'chat'と専用分岐を加える。開始時はチャットと自然文の質問例2件（既存AP第1q／AR作成依頼）だけ。モードメニュー、別番号は設けない。候補クリックはtextareaへdraftを入れるだけで、送信・台本進行・添付消費はしない。

```
GN-02 同じチャット
  初期：APの既存依頼 / 集金予定表の作成依頼
  添付：元データ.xlsx + 完成見本.xlsx → 送信
  結果：初稿表＋Excelリンク → 照合・整形の追加入力
  結果：修正版表＋Excelリンク［初稿はdetailsに保持］
```

添付panelはチャットの添付ボタンから開く。GN-02のAR質問例をdraftへ入れた状態、または直前のAR発話がある状態の「サンプルを使う」でAR2件を選択する。APを明示したdraftではAR2件を選ばず、AP既存inputを扱う。未指定の状態でARファイルを選ぶ場合は同梱AR2件だけを使い、表示するファイル名もその2件に限定する。新規panelはupFilesだけを表示し、旧AP3名を架空の送信済み添付として出さない。候補変更だけで選択済みファイルを消去・差し替えない。

受理送信時にupFilesをsentAttachmentsのlog:indexへ移してpanelを閉じる。送信済み2件は発話下の既存添付欄へ残す。新規添付を開き直すと空。本文がある場合はraw全文を保持。本文空＋同梱AR2件ならAR第1q、本文空＋APならAPの次qを表示文とする。ファイル0件＋空本文、読込中、pending中は送信しない。

AR第1送信の返答完了で初稿を表示する。待ち時間中は前の完成結果を保持し、未完了の表・DLを出さない。AR初稿後は整形・照合の質問例1件、AR修正版後は候補0。APは従来の次q1件、3ターン終了で0。手入力でAP↔ARを切替でき、前の成果物はdetailsで保持する。

既存のtextarea64–160px、送信/添付40px、余白、書体、light/darkを継承。結果は既存tableを使い、数値は右寄せ、日付・短いIDは折り返さず、表の横幅は結果panel内でスクロールする。追加の装飾・新dialog・画像化は不要。

## 3. 状態と呼び分けの契約

app.jsにGN-02限定の外部配列gn2TurnMetaを置き、state.logと同じ順で{route:'ap'|'ar'|'clarify',step,outputRef,sampleId}を持つ。AP/ARそれぞれの完了段階は同routeの完了メタだけから求める。AR発話や確認質問でAP3ターンを進めず、APでAR修正版を進めない。pending末尾は未完了として除外する。restart、start、service/industry変更時の既存resetにGNメタを加え、途中の言語/theme/redrawでは保持する。

初期に「集金／回収予定／入金予定／納品書を集計／收款计划／回款计划」を明示した依頼はAR、「受領発票／発注・入庫／三点照合／仕訳／会計登録／进项发票／三单匹配／记账」はAP。初期の「請求書を処理」などAP/AR不明の依頼や両方を頼む依頼は確認質問へ進み、どちらの段階も消費しない。継続中の短い追加入力は直前のrouteを使うが、具体的な他方の依頼を優先する。「支払予定」は売掛集金と同一視しない。既存APの第2/3qはそのままAPとして受理する。

同梱ARサンプルはupUseSampleでsampleIdを付ける。ファイル名の一致だけで読取済みと判定しない。任意実ファイルを選択したときは内容未解析と返し、サンプル操作へ案内する。固定サンプルを選択していないAR初稿に、同梱Excelの結果を利用者のファイルの解析結果として返さない。AR2は完了AR1のsampleIdと送信済み2件を参照し、upFilesが空でも再添付を要求しない。入力不足・未対応の整形条件はclarifyに残し、修正版の生成済み演出はしない。

chatRenderHistory／addMsg／chipsHTML／panelHTML／updateDemoPanels／sendChatとrunの入口へisGn2Chatの局所分岐を加える。既存QA分岐を置換せず、一般consume/nextTurnも変更しない。AP既存runの入口を残す場合はGN専用AP第1送信へ渡し、state.log.lengthでARの有無を判定しない。GN開始時に初期左入力を出さないため、主操作は候補→添付→送信となる。

## 4. データと実在Excel

gn.jsのgn2へ任意collectionScheduleリテラルを追加する。形は{sampleId,input:{ja:{files,assets},zh:{files,assets}},steps:{ja,zh,en},script:{ja:[初稿,修正版],zh:[初稿,修正版]},results:{ja:[初稿表,修正版表],zh:[初稿表,修正版表]},artifacts:[{stage,file,name}],clarify:{ja,zh},inputHighlights:{ja,zh},outputHighlights:{ja,zh}}。既存APのキー・配列本文は変更しない。入力/結果/回答はja/zh、enUIは既存scriptLangでjaへ戻す。

素材ownerは親から依頼を受けたcollection_assets。4つのxlsx（架空元データ、完成見本、初稿、修正版）とmanifestをmock/assets/demo/に先に保存する。数値は同じサンプル原データから作り、完成見本の列・順序・表示形式に沿い、初稿と修正版の差、未確認箇所、照合した集計値をmanifestへ記録する。今回の追加は親が承認した独立した架空デモで、デモA社〜デモE社、INV-D01〜D07と以下の値をcollectionSchedule subtreeと専用xlsxに閉じる。CLAUDE§2-13の通常の世界正本ルールに対するこの局所例外を明記し、旧GN-02や既存data/world/mfgの実物へ混ぜない。番組の実表・実顧客データを複製したとは言わない。

入力assetsは{file:'assets/demo/gn2-collection-invoices.xlsx',kind:'doc',download:'gn2-collection-invoices.xlsx',sampleId:'gn2-collection'}と同じ形のgn2-collection-template.xlsx。画面のfiles名は日中で共通の「請求データ_サンプル.xlsx」「集金予定表_完成見本.xlsx」とし、内部のasset.fileやdownload先は変えない。upUseSampleで任意download/sampleIdを引き継ぎ、upItemHTMLのdoc分岐でdownload指定の同梱ファイルだけ実在相対リンクにdownload属性を付ける。既存doc、画像、音声は保持する。手動選択docは現状どおり名前のみ、Excel画面previewを装わない。相対assetの実在とlocalhostからの取得を確認し、file://のブラウザ検証が利用できない場合は未検証と記録する。

成果Excelは完了stageに対応するartifactsの相対パスを結果panelへ表示する。最新表の下に1本、以前の表にもその版のリンクを置く。回答文字列からファイル名を解析しない。hrefをmetadataの既知相対assetに限定し、ラベル・filenameはDOM text nodeまたはescで描画する。Excelをクリック時に生成した、任意入力をAI解析したとは言わない。用意済みサンプルの実在ファイルをDLする。

### 4.3. INV-D04確認の境界と黄色マーカー

明示した別年は「FY2026」や別の句に置いた年も拾い、2025以外なら修正版へ進めない。「金額が最も高い順」など、金額をキーとする明示的な並べ方も固定の予定日順と異なるため確認質問へ残す。肯定の確認後に「間違いでした」「確認を取り消します」「确认结果有误」と撤回した場合も初稿を保持する。日付を確認したという肯定と「金額と転記漏れも確認して」という通常の照合依頼は通す。

修正版へ進む条件は、AR初稿完了後に、同じINV-D04について2025年9月30日を確認したという肯定の完了報告があること。日付順・同じ取引先/日付の集約・金額と転記漏れの照合はcanonical依頼で明示する。肯定の確認だけを伝えた場合も、このサンプルの決められた整形を行ってよい。根拠なく確認完了を補わない。QA確認guardと意図は同じだが、gn2CollectionConfirmationIsClear等の別functionにして既存QAの判定を変更しない。

「INV-D04の入金予定日を確認して」「9月30日で確認する予定です」「9月30日か未確認です」「9月30日では確認できません」「10月1日で確認できました」、別ID・2026年の確認・確認値が欠落した発話はclarify、AR stage1と前表/リンクを保持する。中文も「请确认」「准备确认」「尚未确认」「无法确认」「已确认是10月1日」、他ID/他年を同じ負例とする。部分文字一致のINV-D040、他行の確認、否定や未来形の近くの「確認」を利用者の完了報告と誤認しない。

この場合の固定確認文ja：「このサンプルの修正版には、INV-D04の入金予定日が2025年9月30日と確認できたことが必要です。現状は未確認として初稿を保持します。確認結果と、並べ方・集約方法を教えてください。」zh：「此示例的修订版需要确认INV-D04的预计收款日为2025年9月30日。目前按待确认处理并保留初稿。请告知确认结果以及排序和汇总方式。」

GNのAR入力/回答/表だけを既存appendMarkedText／markで安全に強調する。文字列は短い完全一致、行全体を塗らない。AP、QA、NM、他サービス、xlsx原本へマーカーを描かない。既存var(--status-warning)と読みやすいセマンティック文字色を使い、HTML挿入やユーザー入力のMarkdown解釈はしない。
