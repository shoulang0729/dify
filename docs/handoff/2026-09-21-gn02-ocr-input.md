### 2-2. 推奨と、その理由

> **推奨＝案 B。** ただし **案 A を捨てない**。案 A は「プラグインを入れた環境から export → `dependencies` のハッシュを Git に取り込む」という手順（O8）を一度通せば実現できるので、**DP-41 が「追加できる」で決着したら第 2 段階として案 A に載せ替える**（同じ Start 変数・同じテストがそのまま使える形にしておく＝§3-6）。

理由は 3 つ。

1. **案 A はクラウド側で着手できない。** `dependencies` のプラグイン識別子は実環境の export からしか得られず、PM の `run:mac` 作業 → export → Git 取り込みが先に要る。**PM 判断（DP-41）を待つ間、案 A は 1 行も書けない**。案 B は今日から書ける。
2. **案 A は `CLAUDE.md` §2-12 と衝突する。** 版固定のプラグイン識別子はどう見ても環境固有の値だが、`render.py` は `dependencies` を env で出し分けない（R10）。マスタ 1 本を社内・顧客 A へ配るモデルが、GN-02 だけ崩れる。
3. **有識者の指摘に答えるのに必要なのは「写真を投げたら項目が返る」という事実 1 個**であって、OCR エンジンの選定ではない。**エンジンの選定は DP-34 として既に台帳に載っており、本 Issue で決める話ではない**。

### 3-1. 変更前後の構成

```
変更前： Start(invoice_text / invoice_file)
           → Document Extractor(invoice_file)  ─┐
                                                 └→ LLM（発票項目抽出） → Code（CSV 整形） → End(csv / warnings)

変更後： Start(invoice_text / invoice_file / invoice_image)
           → Document Extractor(invoice_file)
```

- **ノードは 1 個だけ増える**（`llm`。`tool` ノードは 1 個も増えない＝プラグイン不要）

### 3-4. 変更 ③：vision ノードを 1 個挿す（新規ノード `1757280000006`）

```yaml
    - data:
        context:
          enabled: false
          variable_selector: []
        desc: '発票の写真・スキャン画像を、書いてある文字のまま書き起こす。項目の解釈・計算はしない（それは次の LLM の仕事）。画像が無いときは（画像なし）とだけ返す'
        model:
          completion_params:
            exclude_reasoning_tokens: true
            max_tokens: 4096
            reasoning_effort: minimal
            temperature: 0.2
          mode: chat
          name: qwen/qwen3.8-max-vl
          provider: langgenius/openrouter/openrouter

        - id: 3c4d5e6f-9fa5-4041-ad3b-4e5f6a7b8c03

            1. 画像に**書かれている文字だけ**を書き起こす。読めない文字は ？ に置き換え、その行の末尾に （判読不能） と書く。

            3. 項目の解釈（どれが税額か等）をしない。並んでいる順にそのまま書く。
```

- `vision.configs.detail: high` の形は `docs/dify/templates/02-long-document-chunk-iteration-translate.yml` の実物に合わせた。**`configs.variable_selector` に Start の file 変数を指す形は、リポジトリ内に実例が無い＝未確認（§6 C-2）**。実機で弾かれたら、`variable_selector` を外して `sys.files` 参照に落とす（同 §6）
- **書き起こしに徹させ、項目抽出は既存 LLM に残す。** 1 つのノードに「読む」と「構造化する」を混ぜると、読めなかったときに何が起きたか分からなくなる。`warnings` に「読み取れなかった」を出す責任は既存の抽出 LLM 側にある（既存 System の 1. をそのまま使える）
- **応答言語の契約（`CLAUDE.md` §2-5・`docs/dify/implementation-guide.md` §6-1）との関係**：このノードは**書き起こし専用**で、利用者への回答文を作らない。したがって「入力言語で返す」の対象ではなく、**画像の言語のまま書き起こす**（翻訳しない）ことを System に明記した。利用者に返る文（`warnings`）の言語は従来どおり既存の抽出 LLM が決める＝ **T01・T02・T04・T06 の `expect_lang: ja` は変わらない**

#### なぜ第 1 段階では if-else（分岐）を入れないか

分岐（画像があれば vision、無ければ素通り）を入れるには ①file 変数に対する条件式の書き方 ②合流の `variable-aggregator` の 2 つが要る。**①はリポジトリ内に実例が 1 つも無い**（`if-else` の実例 `templates/01`・`03`・`05` はいずれも**文字列変数**の条件）。未確認の要素を 2 つ同時に入れると、落ちたときに原因が切り分けられない。第 1 段階は**直列 1 本**にして、`invoice_image` が空のときは vision ノードが `（画像なし）` を返すだけにする。

**代償（設計書に明記して PM に見せる）**：テキストだけを入れる既存 4 ケースでも LLM が 1 回余計に走る。所要が数秒伸び、トークンを少し余分に使う。**実機で緑になったら第 2 段階で分岐を入れる**（§3-6 の (2)）。

### 3-5. 変更 ④：エッジの張り替えと、抽出 LLM の user プロンプト

エッジは **1 本を張り替え、1 本を足す**（`document-extractor → llm` を `document-extractor → 新 llm → llm` にする）。

```yaml
    # 削除するエッジ（id: 1757280000002-source-1757280000003-target）
    # - source: '1757280000002' / target: '1757280000003'

    # 新規 1：文書抽出 → LLM（発票画像の読み取り）
    - data:
        isInIteration: false
        isInLoop: false
        sourceType: document-extractor
        targetType: llm
      id: 1757280000002-source-1757280000006-target
      source: '1757280000002'
      sourceHandle: source
      target: '1757280000006'
      targetHandle: target
      type: custom
      zIndex: 0
    # 新規 2：LLM（発票画像の読み取り） → LLM（発票項目抽出）
    - data:
        isInIteration: false
        isInLoop: false
        sourceType: llm
        targetType: llm
      id: 1757280000006-source-1757280000003-target
      source: '1757280000006'
      sourceHandle: source
      target: '1757280000003'
      targetHandle: target
      type: custom
      zIndex: 0
```

抽出 LLM（`1757280000003`）の **user プロンプトだけ**に 1 ブロック足す。**System プロンプトは 1 文字も変えない**（応答言語の共通ブロックが 12 本でバイト一致していること＝`dify/check.py` の検査対象のため）。

```yaml
        - id: 2b3c4d5e-9fa5-4041-ad3b-4e5f6a7b8c02
          role: user
          text: |-
            発票テキスト：
            {{#1757280000001.invoice_text#}}
            アップロードされたファイルからの抽出内容（あれば）：
            {{#1757280000002.text#}}
            アップロードされた画像からの書き起こし（あれば。（画像なし）のときは無視する）：
            {{#1757280000006.text#}}
```


### 5-4. `run_tests.py` の拡張（PR-1 に含める）

**方針：`inputs` の値が `{"@file": "<リポジトリ相対パス>", "type": "image"}` の形のときだけ、送信前にアップロードして差し替える。** それ以外の挙動は 1 行も変えない。

1. `--dry-run`：**ネットワークを呼ばず**、`@file` のパスが実在するかだけを検査する（実在しなければ NG 行にする）。既存の dry-run の表の形は変えない

5. 結果表の「入力」欄は、`@file` を含むケースでは **ファイル名だけ**を出す（`upload_file_id` を出さない）
6. docstring の「テスト JSON の形」に `@file` の 1 行を足す
