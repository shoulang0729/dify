## §1. 背景 —— 「1 つの機能の裏表」をどう表現するか

PM の要望は「**アプリ（カタログ）としてはシステム運用監視、ポータルとしてはシステム稼働状況。同じ 1 つの機能の裏表**」である。
本設計はこれを次のように分解した。

| 層 | 何を持つか | 誰のものか |
|---|---|---|
| **運用監視ツール**（既存の製品。リポジトリの外） | 閾値・アラート・ログ・一次切り分けの操作 | **運用担当（保守当番）**。ここは作らない。**事実の出どころ** |
| **AI アプリ（カタログの SO-01〜SO-04）** | アラートを読む・稼働状況に答える・報告を書く・障害報告を書く | **システム担当・ユーザー**。カタログは「どの業務ができるか」の台帳 |
| **ポータルの画面（システム稼働状況）** | いまどうなっているかの一覧・履歴・そこから呼ぶ AI・To Do と顧客連絡への接続 | **ユーザー・システム担当・CIO・CEO**。業務の画面 |

**「裏表」はデータの二重持ちではない。** ポータルは運用監視ツールから取り込んだ事実（`system_events`）と台帳
（`systems`）を持ち、カタログは**その事実を読む AI サービスの台帳**を持つ。同じ事実を 2 か所に書かない
（`portal-mock-pages` D5・D6 と同じ考え方）。

### 1-1. なぜ「運用担当は運用監視ツール側」なのか

運用監視ツールは**閾値と操作の道具**で、情報密度が高く、運用担当以外には読めない。ポータルに出すのは
**「使えるか・いつ戻るか・誰が見ているか」**だけで、閾値もログ本文も出さない。**ポータルは運用監視ツールの
劣化コピーではなく、読み手が違う別の画面**である。この線引きが §9 の役割表になる。

### 4-3. `industries` を `['it']` に限る理由

  `mfg`／`fin` の台本（無ければ汎用チャットにフォールバックする＝壊れない）。

### 6-4. 導出規則 —— 「サービス時間対象外」「夜間バッチ処理中」は人が入力しない

**`system_status` が持つのは「人と監視ツールが決めた事実」だけ**（`normal` / `incident` / `degraded` / `blocked` / `maint`）。
`offhours` と `batch` は**保存しない**。表示のたびに、台帳（`systems.service_hours`・`systems.batch_window`）と
カレンダー（休日・月次クローズ）と「いま」から計算する。

```
表示状態 = 次の順に最初に当てはまったもの（上ほど強い）

 1. incident   未クローズのアラートがあり、重大度が high/critical
 2. degraded   未クローズのアラートがあり、重大度が warn（一部機能のみ停止）
 3. maint      いまが計画停止の窓（maintenance window）の中
 4. blocked    閉塞フラグが立っている（運用担当が業務都合で意図的に止めた）
 5. batch      いまがバッチ窓の中（systems.batch_window × カレンダー）
 6. offhours   いまがサービス時間の外（systems.service_hours × カレンダーの休日）
 7. normal     上のいずれでもない
```

**なぜこの順か**

- **1・2 が最上位**：障害はサービス時間外に起きても障害。夜間に気づかないための一覧ではない。
- **3（計画停止）が 4・5・6 より上**：利用者にとって「予定どおり止まっている」が最も知りたい答えで、
  「時間外だから止まっている」より情報量が多い。
- **計画停止の窓の中で上がったアラートは監視ツール側で抑止されている前提**なので、1 と 3 の競合は実務上起きない。
  それでも来た場合は **1 が勝つ**（抑止の設定漏れを隠さない）。
- **5・6 が最下位**：この 2 つは**事実の不在**（何も起きていない）から導かれる状態で、上の 4 つと競合したら
  必ず負ける。

**カレンダーの入力**（`data/world/it/calendar.md` に節を足す。§8-3）

| 何を | どこから |
|---|---|
| 平日／休日 | 会計年度と週の定義＋中国の法定休日（架空の運用でよい。`calendar.md` に列挙） |
| サービス時間 | `systems.service_hours`（例 `平日 07:00-22:00; 土 07:00-13:00`。時刻はすべて **CST（上海）**） |
| バッチ窓 | `systems.batch_window`（例 `日次 01:00-04:00`・`月次 月初3営業日 20:00-24:00`） |
| 月次クローズ | `calendar.md` の「翌月第 3 営業日」（会計システムの月次バッチ窓がこれに従う） |

**日本本社（JST）との時差**：台帳は CST で書き、**表示は見る人の拠点のタイムゾーン**に直す（`company.md` の
`shanghai +8` / `jp_hq +9`）。モックでは上海固定とし、**時刻の横に必ず拠点名を出す**（「22:40（上海）」）。

### 6-7. 稼働率・MTTR の定義（K5 に足す指標）

| 指標 | 定義 |
|---|---|
| **稼働率** | `1 − （サービス時間内の incident/degraded/blocked の合計時間 ÷ サービス時間の総量）`。**計画停止・バッチ窓・サービス時間外は分母にも分子にも入れない**（事前に合意して止めている時間を稼働率で罰しない） |
| **障害件数** | 期間内に検知した `incident` の件数（`degraded` は別に数える） |
| **重大障害** | `criticality === '高'` のシステムの `incident` |
| **一次回答までの時間** | 検知 → 最初の顧客連絡（接触履歴の登録）までの平均 |
| **MTTR** | 検知 → 復旧までの平均。一次回答までの時間とは**別指標**として並べる |
| **再発率** | 同じシステム・同じ原因分類で 90 日以内に再発した障害の割合 |

`mock/js/data/portal/mgmt.js` の `PKPITOPIC` の **K5 の行だけ**を次のように変える（他 8 行は触らない）：

- 指標：`['障害件数', '重大障害', '再発率', '一次回答までの時間', '顧客からの指摘件数']`
  → `['稼働率', '障害件数', '重大障害', 'MTTR', '再発率', '一次回答までの時間', '顧客からの指摘件数']`

## §7. 運用監視ツールからの取り込み（NocoBase Community の制約下）

`portal-nocobase` rev3 §4-13 **F-8**：**Workflow の Webhook トリガーは Professional+**。Community では使えない。
代替は 3 つあり、**本設計は (1) を本命、(2) を任意の追加、(3) を最後の手段**とする。

| 方式 | 仕組み | 遅れ | 監視ツール側の変更 | 採否 |
|---|---|---|---|---|
| **(1) Schedule トリガのポーリング** | NocoBase の Workflow（Schedule・**無料**）が 5 分ごとに HTTP request ノードで監視ツールの API を読み、前回取得時刻からの差分を `system_events` に upsert | 最大 5 分 | **不要**（読むだけ） | **本命** |
| **(2) Auth: API keys ＋ REST 直書き** | 監視ツール（またはその横に置く小さな中継）が、重大度 high/critical のときだけ NocoBase の REST API に POST。API キーは **Auth: API keys（無料）** | 数秒 | **要る**（通知先の設定と鍵の配布） | **任意の追加**（重大障害の遅れが許容できないときだけ） |
| **(3) ファイル連携** | 監視ツールが出力する CSV を共有フォルダに置き、Schedule で取り込む | 出力周期に依存 | 出力設定が要る | **最後の手段**（API が無い／開けられない場合） |

### 7-1. (1) を本命にした理由

1. **監視ツール側に手を入れずに始められる。** 運用部門との調整が「読み取り用の資格情報をもらう」だけで済む。
2. **落ちても次の周期で回復する。** Webhook 型は受け側が落ちている間の通知が消える（再送の保証は製品による）。
3. **資格情報がポータル側に閉じる**（NocoBase の **Variables and secrets（無料）**）。鍵を配らない＝§2-10 に沿う。
4. **重大障害だけ (2) を足せば、遅れの問題は局所的に解ける。**（1) を捨てずに済む。

### 7-2. 取りこぼしと二重取り込みの歯止め

- **差分取得**：`last_polled_at` を保持し、`occurred_at > last_polled_at` を取る。API が「以降」検索を持たない場合は
  **直近 N 分を重複込みで取り**、`system_events.src_id` の **unique 制約**で潰す（Flyway で index を作る。方式 (a) なので素直にできる）。
- **順序の逆転**：アラートより先に復旧通知が届いても、`base_state` は**未クローズのイベントの集合から再計算**する
  （最後に来たイベントで上書きしない）。
- **時計のずれ**：`occurred_at` は **UTC で保存**し、表示のときだけ拠点のタイムゾーンに直す。

### 7-3. ポータルに持ち込まないもの（§2-10・越境）

- **生ログ・スタックトレース・ホスト名・IP・接続文字列は持ち込まない。** 持つのは
  「どのシステムが・いつ・どの重大度で・何が起きたか（要約）」まで。
- **顧客環境の事象は顧客ごとに分離**して見せる（`system_events` の顧客スコープ）。
  SO-03 の顧客版報告には**その顧客の環境の事象だけ**を載せる（§5-2 の `desc` に明記済み）。
- 中国拠点 → 日本本社へ出す報告は `cross_border` / `pipl_mask` のフラグに従う
  （env の扱いは `CLAUDE.md` §2-12。**本設計では `dify/env/**` を触らない**）。

### 7-4. AI の呼び方（NocoBase 側）

| サービス | 置き方 | 呼び方 |
|---|---|---|
| SO-01 | `flow`（裏で回す） | 取り込み Workflow の続きで **HTTP request ノード → Dify を同期（blocking）で呼ぶ**。名刺 OCR と同じ判断（rev3 §4-13） |
| SO-02 | `embed` | iframe ブロックに Dify の画面を埋める（KN-04・KN-03 と同じ） |
| SO-03・SO-04 | `btn` | Custom request アクションで行の文脈（期間・障害番号）を渡す |

#### B. `day` プリセットの `degraded` と AC-18

**矛盾の所在**：§6-9 の `day` は「ほぼ定常運転中。**1 件だけ `degraded`**」。一方 **AC-18** は
「ホームの『いま止まっているシステム』は **`day` で 0 件**の 1 行になる」。ホームに出すのは
`incident` / `degraded` / `blocked`（§6-1）なので、`day` に `degraded` が 1 件あると AC-18 は成立しない。
implementer は `degraded` を `night` へ移した（SYS-03 の 20:00 の `warn` アラート）。

**決定 B**：**AC-18 を正とし、§6-9 の `day` 行の「1 件だけ `degraded`」を

**理由**：① ホームは全員の入口で、「赤いものだけを出して画面へ誘導する」（§6-1）のが役割。**平常時に何も出ない**ことを

→ `holiday`（全部が灰）という**3 段の対比**の方が、デモの語りとして強い。③ §6-9 の `day` 行には既に
「導出状態が出ない『ふつうの朝』」と書いてあり、**全件 `normal` の方が §6-9 の中で整合する**。

**3 プリセット × 9 行の確定状態**（`PSYSEV` から §6-4 の 7 段で導出した結果。**architect が実走して確認済み**）

#### D. 行内 AI ボタン（`prowAi` / `PCTXDEF.sys`）は PR-4 の範囲か

**不足の所在**：§6-2 の ASCII と §5-6 の `place` の説明には「**障害の行から呼ぶ**」（SO-01）・
「**復旧した障害の行から呼ぶ**」（SO-04）とあるが、**行内ボタンの配線**（`PCTXDEF.sys` の宣言・`pctxRow('sys', …)`・
一覧の行への `prowAi`）は本文のどこにも書いていない。AC-17 が求めているのは「この画面の AI」ブロックだけ。
implementer は行内を未配線にした（画面ブロックの AI のみ）。

**決定 D**：**PR-4 は画面ブロックの AI だけで完了とする。行内 AI の配線は PR-5（台本）で `PCTXDEF.sys` と一緒に足す。**

**理由**：行内から呼ぶときに文脈カードへ渡すのは**障害番号・システム名・顧客・重要度**で、これは
**台本の文脈カードが何を表示するか**と対で決めないと、空の文脈カードだけが増える。SO-01〜SO-04 の台本は PR-5 の範囲であり、
**台本と `PCTXDEF` を同じ PR で入れた方が、`demo.js` の汎用組み立て（`PCTXDEF[scr]` のフィールド名リスト）と
一度に検証できる**。§5-6 の「行から呼ぶ」は `place` の**説明文**であって、PR-4 の受け入れ条件ではない。

**PR-5 への申し送り（PR-4 では実装しない）**

- `PCTXDEF.sys` を宣言する。渡す行は **`{ sys: 'SYS-01', name, client, criticality, inc: 'INC-2026-014' }`** 相当
  （フィールド名の最終形は PR-5 の設計で確定してよい。**`data/world/it/` にある値だけ**を渡す）。
- `pctxRow('sys', id)` を足し、一覧の行に `prowAi` を置く。**行の状態で出し分ける**：
  `incident` / `degraded` の行 → **SO-01（初動案）**、直近のイベントが `recover` の行 → **SO-04（障害報告）**。
- **`prowAi` を置いても一覧の列は増やさない**（既存の「直近の出来事」列の中に入れる）。列を増やすと §6-2 の寸法が崩れる。

**reviewer 申し送り → PM 判断（2026-09-11・決定 4）：現状維持。** reviewer から「行内 AI を PR-5 で配線すると、
平常時（`day` プリセット）にも**過去に復旧した行**に SO-04（障害報告・再発防止のドラフト）のボタンが出る。
`day` は全件 `normal`（決定 B）なので『何も起きていない画面に障害報告のボタンが出る』ことになる。
**時間窓で絞る**（直近 N 時間以内に `recover` した行だけに出す）べきではないか」という申し送りがあった。
**PM 判断は「今のままで可。時間窓で絞らない」。理由：復旧後に報告を書く導線をデモで見せられるから。**
`day` プリセットは顧客に最初に見せる画面で、ここに SO-04 が出ていないと「障害のときだけ使う AI」に見える。
**「落ち着いてから報告を書く」のが SO-04 の実際の使われ方**であり、平常時の画面にこそ置きたい。
したがって **PR-5 の出し分け規則は決定 D のまま**（`incident` / `degraded` → SO-01、直近のイベントが `recover` → SO-04）で、
**`PSYSEV` の時刻と現在時刻の差を見る条件を足さない**。
