## §0. 目的と PM 決定

### 0-1. 1 行

**イベントで入手したノーコード業務 DB（kintone）の製品パンフレットから、青嶺精工・蘇州工場の世界に置き換えた新規ユースケースを 4 件起こし、あわせて「kintone は⑤ポータル（NocoBase）の代替候補である」という位置づけを 1 節だけ残す。**

### 0-2. なぜやるか

パンフレットが扱っているのは**基幹システムの周辺に散らばった Excel と紙**（巡回記録・点検表・修理依頼・棚卸・購買申請・承認ワークフロー）である。ここは当カタログの既存 82 件が**薄い領域**でもある：

| パンフの領域 | 既存カタログの状態 |
|---|---|
| 5S・安全巡回／ヒヤリハット | **1 件も無い**（`safety` タグは DC-04〔現場掲示の翻訳〕にしか付いていない） |
| 設備保全・点検・修理依頼 | KN-02（設備マニュアル検索）だけ。**依頼が来てからの判断**を扱うものが無い |
| 棚卸 | NM-04（在庫・納期の照会）だけ。**差異が出たあと**を扱うものが無い |
| 承認ワークフロー | DC-05（申請を**書く**側）だけ。**読む＝承認する側**が無い |

いずれも「台帳に貯める」ところはノーコード業務 DB（または既存の業務システム）の仕事で、**貯まったものを突き合わせて判断材料にする**ところが Dify の仕事になる。この分担がはっきり見える 4 件を選んだ。

### 0-3. PM 決定（再検討不要の前提）

1. **4 件とも新規採番**（5 軸一致 1〜2／5。§2）。番号は予約済み：**QA-05**（`qa5`）・**KN-12**（`kn12`）・**NM-06**（`nm6`）・**DC-12**（`dc12`）。**永久欠番・改名なし**（`CLAUDE.md` §2-11）
2. 業種は `industries: ['mfg']` のみ。成熟度は全件 **`st: 3`（構想）**
3. 配置：QA-05 ＝ `qa`／**新中分類 `safety`**（`qa.subs` に追加。35 → 36）、KN-12 ＝ `kn`/`tech`、NM-06 ＝ `nm`/`actual`、DC-12 ＝ `dc`/`apply`
4. テンプレートは既存 5 種から選ぶ（**増やさない**）
5. ポータル配置 `place` は**既存の画面 id からだけ**選ぶ（**新画面を作らない**）。`PSVC` にも 4 件追加
6. **kintone 連携の実証（PoC）はやらない。** 位置づけの整理を §11 に 1 節だけ置き、Issue にしない
7. `mock/**` のリテラル（`name`／`desc`／台本）と `docs/demo/**` に**実在製品名（kintone）を書かない**。「ノーコード業務 DB」「業務台帳」と書く。OCR／STT ベンダ名・発票 SaaS 名・クラウド AI 名も台本に出さない

## §1. 出典 —— パンフレットの要約と着想の対応

### 1-1. 原本の扱い

- 原本は画像 30 頁。**リポジトリにコミットしない**（`CLAUDE.md` §2-10・`2026-09-07-usecase-intake.md` S1）。本書に載せるのは**要約と、青嶺精工・蘇州工場の世界に置き換えた表現だけ**
- 参照した頁：p13-14（製造業現場パック）／p03-04（WMS 倉庫管理）／p11-12（workflow 審批管理）／p19-20（固定資産）／p23-24（購買管理）

### 1-2. 要約（各 2 行）

| 頁 | パンフが言っていること（要約） |
|---|---|
| p13-14 製造業現場パック | 基幹システムの周辺にある**バラバラな Excel・紙**を 1 つの台帳にする。アプリの例として「品質不良報告／生産設備／不良マスタ」「日常巡回報告／ヒヤリハット管理／エリア情報／巡回点検マスタ」「設備台帳／修理依頼／月次点検管理／点検表」を挙げる。中国のユーザー事例として「5S パトロールチームが巡回中にその場で登録 → 指摘された部署が改善計画〜完了まで実行し、総務課は最終合否判断のみ → **総務課のとりまとめ工数が大幅に削減**」を載せる |
| p03-04 WMS | 受注から倉庫までを一体で管理する。**盘点管理（棚卸計画・棚卸リスト生成・棚卸結果の承認）**を 1 つの柱として立て、「正しい在庫がリアルタイムに分からない」「人手の照合が非効率で間違えやすい」を課題に挙げる |
| p11-12 workflow | 紙・メール・電話の申請を電子化する。**申請人・審批人・管理部**の 3 者それぞれに Before/After を書き、審批人の困りごとを「外出時は口頭で、戻ってから手続きを追認」「**申請の書式と審批の流れが正しいか担保できない**」とする |
| p19-20 固定資産 | 資産の**ライフサイクル**（購入申請 → 利用開始 → 変更/移動 → 修理 → 廃棄/処分）と**資産棚卸**（棚卸計画 → 棚卸実施）を 1 つの台帳に集約。「台帳と現物は合っているか」「棚卸に手間がかかり、**差異確認も大変**」を課題に挙げ、「棚卸差異アラート」を機能として持つ |
| p23-24 購買管理 | 購買申請 → 見積依頼 → 申請承認 → 発注 → 納品 → 照合＆支払。効果として「**見積・過去価格で適正価格を実現**」を挙げる |

### 1-3. 着想の対応表（パンフの機能 → 当カタログのサービス）

| パンフの機能 | 台帳側（= ノーコード業務 DB／既存業務システムの仕事） | **判断側（= 本設計で起こす Dify のサービス）** |
|---|---|---|
| 日常巡回報告・ヒヤリハット管理・巡回点検マスタ（p13） | 巡回・ヒヤリハットのレコードと写真を貯める。改善計画の進捗を持つ | **QA-05**：週次の要約、**同じ場所・同じ型の再発**の検知、過去の是正との重なり、未完了の一覧、工場長向け 1 段落 |
| 設備台帳・修理依頼・点検表（p13） | 設備・依頼・点検の記録を貯める | **KN-12**：依頼が来た瞬間に台帳・履歴・点検表を突き合わせ、原因候補と**止める／続けるの判断材料**を出す |
| 盘点管理（p03）・棚卸差異アラート（p19） | 棚卸計画と結果、差異の一覧を持つ | **NM-06**：差異行ごとの**原因仮説（根拠の伝票番号つき）**・確認手順・処理案。2 期連続の同じ向きを「計上の型」として示す |
| workflow 審批（p11）・購買申請と過去価格（p23） | 申請と承認の状態、過去の申請を持つ | **DC-12**：**承認者の側から**の要点 3 行、過去の同種申請との違い、規程のしきい値のどちら側か、差し戻し理由の下書き |
| 固定資産のライフサイクル（p19） | 資産台帳 | **NM-06 の `scope: fixed_assets`**（画面は分けない。§2-3 の判定） |

**書式を選んだ理由（`tools/check-world.mjs` W6 のパーサに乗せるため）**

| 書式 | パーサ上の扱い | 備考 |
|---|---|---|
| `HH-YY-MMDD` `CK-YY-MMDD` | `YY`→`\d{2}`、`MMDD`→`\d{4}` | 既存の `8D-YY-MMDD`・`CL-YY-MMDD` と同型 |

| `ST-YY-QN` | `Q` は 1 文字リテラル（パーサの `QL` 許可集合）・`N`→`\d` | 既存の `QR-YYYY-QN-NN` と同じ仕掛け |

当リポの原則は「**判断・調査は Dify、承認・実行は BPMS**」（`docs/dify/implementation-guide.md`）。kintone が入るのは**後半の「BPMS／台帳／通知」の枠**であり、Dify と競合しない。

### 14-2. 順序

```
PR-B（世界マスタ）─→ PR-A（docs）─→ PR-C（データ層）
       └──────────────── 並列可（PR-B を先にマージ） ────┘
```

**推奨は PR-B → PR-A → PR-C の直列。** 並列にするなら PR-B と PR-A の 2 本までで、PR-C は必ず最後。

- **PR-A は PR-C より先**。理由は §10-4：`gen-index` は「実装リファレンスの実ファイルが在るか」を見るため、PR-C を先に入れると `service-map.md` が `③68` のまま生成され、後から PR-A を入れた瞬間に**索引が古くなって verify §11 が FAIL する**（PR-A 側で `npm run index` をやり直す羽目になる）
- **PR-B は PR-A より先を推奨**。`check-world` は `docs/dify/usecases/**` と `mock/js/data/scenarios/**` を走査するので、マスタが無い状態で番号だけ先に入ると warn が **12 件 → 26 件**に増える（§13-3 で実測）。**`check-world` は warn のみで CI に入っていない**（`CLAUDE.md` §3）ので**マージはブロックされない**が、中間状態を残さないほうが reviewer の照合が楽
- ファイル集合としては **PR-A と PR-B は重ならない**（`docs/**` ⇄ `data/world/**` ＋ `portal/seed/world/**`）ので、**並列でも成立する**（その場合は PR-B を先にマージする）

### 14-3. PR-B と PR-C は並列できるか（PM の問い）

**結論：ファイル集合としては重ならないので並列できる。ただし直列（PR-B → PR-C）を推奨する。**

| 観点 | 判定 |
|---|---|
| `tools/regress.baseline.json` | **PR-C だけが触る**（PR-B は `data/world/**` で `SVCS` を動かさないので `regress` の counts が変わらない）。衝突しない |

| `CLAUDE.md`／`README.md`／`tools/verify.mjs` | **どちらも触らない**（`CLAUDE.md` §5 の「常に直列」条項に当たらない） |
