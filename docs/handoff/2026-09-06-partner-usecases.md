## 0. 目的 / 背景

顧客（**青嶺精工・蘇州工場**：在中日系の自動車部品メーカー。日本本社あり。担当者は日本人駐在員と中国人スタッフ）の AI エージェントカタログに、**構想中のパートナー 6 者と協働するユースケース**を追加する。

7. **固有名**：パートナーは役割名のみ。台本のデータ（財務数値・給与・求人条件・見積額）はもっともらしい**架空値**。既存台本の架空名（K 社・S 社・T 社・S 工具・TC-Tools・U 刀具、部品番号 `SK-`、不具合 `NC-`、技術報告 `TR-`）は**そのまま再利用**して接続を見せる。

## 2. 設計判断（architect の決定）

### 2-1. 分類：8 分類目 `pt`「パートナー連携」を新設（推奨）。中分類は 2

| 中分類 id | ja | 収容 | 意図 |
|---|---|---|---|
| `data` | データ・リサーチ | pt1 pt2（情報ベンダ）pt3（記事アーカイブ）pt4（給与 DB） | パートナーが**データ／検索基盤**を提供し、社内エージェントが引いて答える |
| `service` | 代行・エージェント | pt5（採用エージェント）pt6 pt7（購買エージェント）pt8（研修ベンダ） | パートナーの **AI エージェント／人**に業務を**引き継ぐ**（受け渡し・代行・戻り） |

- 中分類 id は全体で一意（A §2-1 の注意）。`data` / `service` は承認済み 15 中分類（tech rule defect change report site apply trans align cost actual spec bom office daily）と重複しない。旧（A 以前）の `ana/data` は A で削除済みなので regress 上も衝突しない。
- 並び順は**末尾**（`gn` の後）。「探す → 品質 → 作る → 言葉 → 数字 → 図面 → 汎用 → **社外と組む**」で、顧客に「ここまでが社内、ここからはエコシステム」と説明できる。
- **既存分類に入れて `partner` タグで示す案（対案）**との比較は §7 PT-1。要旨：対案だと `nm` が 5 → 8 件、`kn` が 5 → 7 件に膨らみ、A §2-1 の「1 分類 3〜7 件」を崩す。また「構想」バッジが既存分類に 5 件混ざり、提供中／試行版の中に混ぜて見せることになる。新設なら「パートナー連携は構想フェーズ」と分類単位で説明できる。

### 2-2. id 体系

`pt1`〜`pt8`（分類 id ＋ 連番）。承認済み id と重複しない。`SCENARIOS` のキーも同じ id。

### 2-3. 成熟度の付け方（PM ルール 4 の適用）

| st | 基準（本書） | 該当 |
|---|---|---|
| 2 試行版 | **一方向の読み取り**：パートナーの REST API／データフィード／検索基盤を `http-request` か External Knowledge API で引き、社内データと並べて答える。個人情報を外に出さない。契約が結べれば今日作れる | pt1 pt2 pt3 |
| 3 構想 | **双方向の受け渡し／人による代行／個人情報**：AI エージェント同士の引き継ぎ・進捗の戻り（Webhook）、購買代行会社・研修ベンダの実施、応募者・給与データの取り扱い（PIPL） | pt4 pt5 pt6 pt7 pt8 |

内訳：**st2 = 3 / st3 = 5**。pt4（給与 DB）は技術的には pt1 と同じ「照会」だが、社内給与（個人情報）と突き合わせる設計のため st3 に置く（§7 PT-3 で PM 判断）。

### 2-4. タグの方針

- パートナーは**役割ベースのタグ** 6 つ（`partner_infovendor` 等）。「全サービス共通の前提」ではなく本当の区別なので §2-5 に抵触しない。
- 業務キーワードとして `credit`（与信・リスク）と `market`（市況・業界）を新設。それ以外は承認済みタグを再利用（`search` `hr` `purchase` `order` `education`）。
- 1 サービス 2 タグ（パートナー 1 ＋ 業務 1）。**未使用タグを残さない**（新 8 キーはすべて pt1〜pt8 で使う）。

## 5. Dify 実現性（8 件）

前提は `docs/dify/feasibility-33-services.md` §1 と同じ（Dify 1.15.x／DSL 0.6.0、セルフホスト、中国側モデルは SiliconFlow 中国版）。パートナーは**構想中**なので、連携方式は Dify 側の**汎用パターン**で書く：
(a) `http-request` ノードでパートナーの REST API／データフィードを取得、(b) External Knowledge API でパートナーの検索基盤を KB として接続（検索のみ）、(c) Webhook Trigger（1.10.0〜）でパートナーからの戻り（進捗・結果）を受ける、(d) Data Source プラグイン／定期取込（S3・COS 等）でファイル配信を KB 化。

### 5-1. 集計

| 評価 | 件数 | id |
|---|---|---|
| ◎ 標準機能で今日作れる | 0 | — |
| **○** パートナー側 API と契約があれば作れる（Dify 側は汎用パターン） | **4** | pt1 pt2 pt3 pt8 |
| **△** 双方向の受け渡し・個人情報・人による代行が本体の一部 | **4** | pt4 pt5 pt6 pt7 |

- ◎ が無いのは「パートナーが存在しない（構想中）」ためで、Dify 側の技術要因ではない。pt1〜pt3 はパートナーの API さえあれば承認済み △ 群（nm4 等の lookup）と同じ構成。
- st との整合：○ 4 件のうち pt8 を st3 にしているのは「研修の実施代行（人）」が本体で、Dify が作るのは引き継ぎと受講管理の集約だから。
