# チャット候補の入力と送信済み添付

2026-10-12。M/L、run:mac。ユーザーは候補を入力欄へ置いてから送信する流れ、QA-01の候補を現在の工程だけへ絞ること、送信済み添付をチャットから開くことを指定した。追加確認質問は不要。先行するステータス変更のレビュー完了後、共通ファイルの変更を直列に実装する。設計作成ではコードを変更しない。Issue／PR投稿と外部公開は行わない。

## 1. 現物から確認した問題

現在のevents.jsは候補クリックで一般サービスをconsumeし、QA-01をqaSubmitRequestへ直接送る。qaChipsHTMLは毎回record／search／compareを日中両方へ並べ、Aの次工程とBの次資料も追加する。renderMainは入力欄を作り直し、添付プレビューはupFilesだけを参照する。upClearは配列を空にしてobjectURLを破棄するため、送信後も同じ配列を使うと新規添付と履歴を混同する。

これを、未送信の入力・添付と、送信された会話・添付の役割に合わせる。state.logの形、一般nextTurnの進行、QAの工程メタ、localStorage3キーは維持する。

## 2. 候補の決定とクリック

すべてのチャット候補クリックは、入力欄へ質問全文をセットしてフォーカスを移すだけ。consume、qaSubmitRequest、ログ追加、添付送信、結果更新、タイマー開始は行わない。選んだ後に編集でき、送信ボタンまたは既存Enter操作で初めて送る。IME変換中のEnterは送信しない。

候補の言語はUIのscriptLang(state.lang)だけ（enはja）。日中入力対応とdetectLangは保ち、手入力した文や未送信draftをUI言語切替で翻訳しない。一般サービスはnextTurn(scn, scriptLang(state.lang))のqを1候補だけ出す。送信時は現行どおりlog.lengthから次ターンを1回consumeし、入力文をqOverrideへ使う。

QA-01はモードや別メニューを作らず、完了済みqaTurnMetaから次を決める。

| 完了状態 | 表示候補 |
|---|---|
| 初期 | 既存qaPrompts.recordとsearchの2つ |
| A初稿 | 既存A第2質問の原票確認1つ |
| A原票確認後 | 既存A第3質問の日中版確認1つ |
| A日中版確認後 | なし |
| B検索後 | 既存qaPrompts.compareの1つ |
| B比較後 | 既存qaPrompts.nextの1つ |
| B次資料後 | なし |

初期に比較は出さない。比較候補の全文には既存の対象NCがあり、利用者が入力欄で確認・編集してから送る。手入力での任意の作成／検索／比較への切替は残す。確認質問は工程を進めず、元の工程候補を維持する。写真不足の質問後は、添付してから送れるrecord候補を1つにする。未対応の条件を質問中に無関係な候補を増やさない。

pending中は候補と送信／run／添付変更を無効化するか候補を隠し、クリックでdraftを上書きしない。入力欄には次の文を編集できるが、送信は待つ。送信済み添付の閲覧は可能。返答完了時に新しい候補へ局所更新し、入力中の文を消さない。

## 3. 未送信draft

app.jsのstate外に `chatCompose={text,selectionStart,selectionEnd,attachmentVisible}` を置く。入力イベントと必要な選択位置の変更で更新し、再描画前にも現物の入力を読み取る。renderMain後は同じサービスのdraftとキャレットを復元する。候補クリックは明示的にdraft全文を置き換える操作であり、その時だけ以前の文を置換する。

ファイル選択、サンプル、クリア、原票preview、言語／テーマ切替、履歴再描画でdraftを失わない。送信が受け付けられたら、その送信文のdraftを空にする。pending拒否や空送信では消さない。送信後に新たに入力した文を、返答タイマーの完了で空にしない。start／restart／別サービス／業種のlogリセットではdraftもリセットする。保存キーは追加しない。

## 4. 送信済み添付の保持

upFilesは**新しい入力に選んだ未送信ファイルだけ**を持つ。受理された送信ごとに、state外の `sentAttachments` へその時点のバッチを移す。state.logの各要素に新フィールドは追加せず、台本メッセージのlog indexに対応する参照キーを使う。QAのclarifyも受理されたユーザー発話なので、添付がある場合はその発話に結び付ける。A／Bの進行メタは変更しない。

送信成功時は次を同じ処理で行う。

1. そのユーザー発話へ選択中添付のバッチを対応付ける。
2. チャットのユーザー発話の下に、送信したファイル名とプレビューを表示する。写真は現在のサムネイル／拡大操作、音声はaudio、既存のサンプル文書はリンク、ローカル文書は名前だけの扱いを維持する。
3. upFilesを新しい空配列へ替え、添付panelを閉じる。結果・草案・原票の送信履歴は残す。

「ファイルを添付」またはQAの既存「写真を添付」を再度開くと、新しい入力用の空panelになる。既送信バッチを未送信欄へ戻さない。新しいサンプル選択、ファイル追加、未送信クリアで過去バッチは変わらない。

一般サービスの台本終了後／通常chatの汎用発話はstate.logに積まれていないため、送信済み添付をlog.lengthへ上書きしない。state外の表示履歴にその発話と回答／pending情報を保持し、一意なextra参照キーを付ける。再描画でこの履歴と添付を復元するが、一般nextTurnのindexには数えない。QAは既存どおり全発話がstate.logとqaTurnMetaへ同期して入る。

既存runによるuploadテンプレートの初回実行にも同じ添付移送とユーザーメッセージ表示を適用する。添付0件の既存runの動作は保ち、選んでいないサンプルを送信済みと捏造しない。候補クリックだけでは添付は送信されない。form／diff／lookupの既存入力・結果は保ち、添付用の表示切替を広げない。

## 5. 原票previewと非同期処理

previewはupFiles固定参照から、`{source:'pending'|'sent',messageKey,index}` で対象バッチを解決する形へ拡張する。既送信写真はその発話に属する画像だけで前後切替し、新規選択ファイルへ切り替わらない。拡大縮小・全体表示・画像失敗・Esc・close・フォーカス／スクロール復帰を維持する。再描画で起点DOMが変わっても同じ送信済み添付ボタンへ戻す。

送信時はファイルの表示メタとURLの所有権をバッチへ移す。objectURLを送信直後／未送信クリアでrevokeしない。送信済みバッチと新規入力は配列を共有せず、再選択で以前のファイルを書き換えない。画像DataURLとサンプル相対パスはそのまま使い、画像の加工・外部送信・永続保存は追加しない。

upClearは未送信だけを片付け、start／restart／サービス・業種リセット時の全片付けは送信済みも含めてURLを一度ずつ破棄する。FileReader読込中は送信／runを止める。セッションepochまたは同等の識別で、リセット前のonload／onerrorが新しいupFilesへ混入しないようにする。async完了でdraftを消さず、既存の画像読込失敗の名前チップも保持する。

送信済み写真はA初稿・確認・日中版でも参照できる。upFilesが空になったことを理由にA工程を後退させず、A2の原票確認は既存の送信済み資料と工程メタを使う。チャットのファイル名は既存の完全一致引用だけ安全にmarkとし、未知のファイル名をHTMLとして解釈しない。

## 9. 添付だけを送信する場合の補足

親の追加指示により、本文が空でも未送信upFilesがある場合は無反応にしない。§8のraw保持条件には以下の例外だけを追加する。空かどうかはtrimで判定してよいが、本文がある場合は常にraw全文を送信し、既定文を混ぜない。

| 入力状態 | 送信する表示文 |
|---|---|

| 一般uploadで本文空、添付あり、次台本あり | UI言語のscriptLangに対応するnextTurnの既存q。runと同じ既定の台本依頼 |
