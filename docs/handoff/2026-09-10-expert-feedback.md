## §1. 「シナリオは現状で十分」と「見直しを進めて」の矛盾をどう解いたか

### 1-1. 判定：PM 代行の解釈は**正しい。ただし 1 点、決定的に不足している**

PM 代行の解釈は「シナリオの一覧（67 サービスの粒度・カバレッジ）は変えない。変えるのは台本が何を実演しているか」。これは次の 2 点で正しい。

1. 有識者の「シナリオは問題なく、そもそも顧客ごとに変わるものなので現状で十分」は、**同じ文の中で「具体的に見せるのは一覧といくつかのテストアプリでよいのでは」と続いている**。つまりこれは *デモで見せる範囲* の話であり、「一覧（カタログ）＋実機少数」という見せ方の指定である。カタログの粒度・カバレッジを変えろとは言っていない。
2. したがって **67 サービスの id・分類・件数は変えない**（§2-9・§2-11 のコストを払う理由がない）。

不足している点は次の 1 つ。

> **穴は台本ではなく実機にある。** 「きれいなインプットが無くても動く／手書き・音声から読み取れる」が実演できないのは文言の問題ではなく、**実機 12 本の実装がそうなっていない**からである（§2-2 の実測）。台本の日本語をいくら直しても、この指摘には答えられない。

## §4. 音声・手書き・写真をどう扱うか（判断 1）

### 4-1. 結論：**(b) 既存サービスの入力手段として広げる。(a) と (c) は採らない。**

### 4-2. (a)（新サービスとして足す）を採らない理由

音声・手書き・写真は**業務ではなく入力手段**である。この 67 件は「1 件 = 1 業務シナリオ」で作られており（`docs/handoff/2026-09-06-customer-catalog-data.md` 以来の粒度）、`現場メモの音声・手書き取り込み` のようなサービスを立てると「それを**どの業務のために**やるのか」が消える。有識者の言葉も「**インターフェースが優れていることを見せるべき**」であって「入力専用のサービスを作れ」ではない。加えて §2-9・§2-11 のコスト（`regress.baseline.json` の更新、`docs/service-map.md` 再生成、`data/world/` へのペルソナ追加、台本 1 本、usecase 文書 1 本）を、業務価値を増やさない項目のために払うことになる。

### 4-3. (c)（`TAGS` に入力手段の軸を足す）を採らない理由

1. 現在の `TAGS` 57 個は**すべて業務テーマ軸**（検索・設備・不具合・原価・在庫…）で統一されている。入力手段を混ぜると絞り込みの軸が 2 本になり、「タグで絞る」の意味が壊れる。
2. `CLAUDE.md` §2-5 が「**日中対応をサービスの区別タグにしない（全サービスの前提だから）**」と決めたのと同じ罠に入る。音声・写真は将来ほぼ全 upload 型に広がる前提の機能であり、いま 2〜3 件に付けると**すぐに嘘になる**。
3. **タグを足さなくても一覧から見つかる。** `mock/js/app.js` の `filtered()` は検索対象に `desc` の ja/zh/en を含む：
   ```js
   const hay = [x.name.ja, x.name.zh, x.name.en, x.desc.ja, x.desc.zh, x.desc.en, ...x.tags.map(...)].join('');
   ```
   → **`desc` に「手書き」「音声」「写真」と書けば、検索欄に「音声」と打つだけで一覧に出る。** 有識者の「見せるのは一覧」に (b) だけで応えられる。

（結果として `TAGS` は 57 個のまま、`regress.baseline.json` の `tags`・`counts.tags` に差分が出ない。§9 参照。）

**提供中（st1）12 本の `desc` は 1 文字も触らない。** 理由は §2-2：実機に入力経路が実装されておらず、テストも file 入力を通していない。**「提供中」と書いてあるものは実機で動く**という現在の約束を壊さないための線引きである。

## §6. 「工数がどれだけ減るか」を、どこにどう書くか（判断 3）

### 6-1. 現在地（§2-3 の再掲）

### 6-2. 設計：**数字を作らず、数字に区分ラベルを強制する**

#### (1) `dify/tests/<管理番号>.json` のトップレベルに `baseline` を足す（12 本）

```json
    "measured_n": null

}
```

- `basis` は **`assumption` / `interview` / `measured` の 3 値のみ**。
- `manual_minutes` は `docs/dify/usecases/<管理番号>.md` §1 の Before 値を**そのまま**転記する（新しい数字を作らない）。範囲がある場合は**上限を取らず下限**を取る（KN-01 の「30〜60 分」→ `30`）。過小に見積もる側に倒すのは、**削減を大きく見せない**ため。

### 6-3. `docs/demo/faq.md` Q33

> **Q33. 工数はどれくらい減りますか？**
> A. **現時点では削減率をお示ししていません。** お示しできるのは、AI 側で実際に計測した応答時間（各サービスで数秒〜数十秒）と、対象業務にいまどれくらい時間がかかっているかの**想定**です。想定は当社が業務内容から置いた数字で、御社で実測したものではありません。御社の実際の所要時間を数件測らせていただければ、想定を実測に置き換えてお出しします。根拠のない削減率は出さない方針です。

## §7. 「1 時間で作れる」の訴求（判断 4）
