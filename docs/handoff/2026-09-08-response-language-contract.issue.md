```
言語の扱い（地の文と引用の区別。全サービス共通）：
- 地の文（見出し・小見出し・分析・コメント・注記・箇条書き・自分で書いた表の見出し）は、例外なく回答言語で書く。1 つの文の中で日本語と中国語を混ぜない。
- 原語のまま出してよいのは、引用符「」の中・引用ブロック（行頭 >）の中・番号や記号（E-47、7-12、ORG、MODE、SK-3310-A、TR-2024-007、§6.2）・文書の正式名称（取扱説明書、员工手册）だけ。
- 対応語がある概念は必ず回答言語の語を使う（手順→步骤、根拠→依据、備考→备注、版ズレ→版本差异、現地スタッフ→当地员工、保全課長→保全科长、ページ→页）。文書に「保全課長（保全科长）」のように両方の語が併記されているときも、回答言語の側の語だけを書く（併記の形のまま持ち込まない）。対応語が本当に無い語だけ、原語のまま書いて直後の括弧に回答言語の説明を添える。
```

`render.py` は cloud-master では**恒等**（`rendered == data` なら出力はマスタの生バイト）なので、次を守れば必ず 12/12 で通る：ブロックスカラー内で **12 スペースのインデント**を守る／**行末に空白を残さない**／`{{#…#}}` は実在する Start ノード id を使う／`\t`・全角スペースを入れない。

## 4. テストに応答言語の検査を足す

### どこに実装するか —— **両方。役割を分ける**

| 置き場 | 役割 |
|---|---|
| `dify/tests/*.json` | **何を期待するか**（宣言）。`expect_lang`（必須）・`lang_allow`（任意）・`lang_note`（`mixed`/`none` のとき必須） |
| `scripts/dify/lang_check.py`（新規） | **どう判定するか**（純関数のみ。I/O を持たない） |
| `scripts/dify/run_tests.py` | 呼び出しと合否への反映。結果表に `応答言語` 列を追加。**`judge()` は 1 バイトも触らない** |
| `scripts/dify/tests/test_lang_check.py`（新規） | **実機ログから抜いた実際の出力 15 本**で、いま壊れているケースが NG・正常なケースが OK になることをオフラインで機械検証 |

`expect_lang` の値：`"ja"` / `"zh"` / `"mixed"`（仕様上 2 言語が出る＝DC-02・DC-04・LG-01・LG-04）/ `"none"`（検査しない。`lang_note` に理由必須）

### 判定ロジック

**手順 1：除外領域を落として「地の文」を作る**
コードブロック → インラインコード → **引用ブロック（行頭 `>`）** → **表の行（行頭 `|`）** → URL → **引用符の中（`「」`『』《》""''`）** → **括弧の中（`（）`・`()`・`〔〕`）** → `lang_allow` の語 → ASCII・数字・記号。

**手順 2：数える**
`kana`（ひらがな＋カタカナ。**`・` U+30FB は除く**＝中国語でも区切りに使うため）／`han`（CJK 統合漢字）／`ja_only`（日本の新字体で簡体字と字形が違う字。`順` `拠` `現` など）／`zh_mark`（日本語の正書法に無い簡体字）

**手順 3：判定（意図的に非対称）**

| `expect_lang` | 判定 |
|---|---|
| `zh` | **`kana >= 1` で FAIL**、**`ja_only >= 1` で FAIL** |
| `ja` | **`han >= 20` かつ かな比率 `< 0.10` で FAIL**。**語レベルの検査は入れない** |
| `mixed` | `kana >= 1` かつ `zh_mark >= 1` なら PASS |
| `none` | 常に PASS |

**なぜ非対称か。** 中国語の回答に日本語が出るのは引用・括弧併記・文書名を除いて許されない。逆に**日本語の回答に中国語の原語が出るのは §2-5 と横断ルールが明示的に許している**（`保全課長（保全科长）`・中国語条文の引用・日報原文の転記）ので、機械では正誤を分けられない。`ja` 側に語レベルの検査を入れると **KN-02 T01・KN-03 T01・NM-03 T01 という正しい応答が落ちる**。誤検出ゼロを優先した。

### 誤判定の回避（潰したケース）

| リスク | 対策 |
|---|---|
| 数値だけ・短い定型文（`GN-05 T03`・`GN-02` の CSV） | `ja` に `han >= 20` のガード。`zh` は「かな 0」なので短くても安全 |
| 意図的な原語引用（`KN-03 T01` の中国語条文、`NM-03 T01` の日報原文） | 引用ブロック・引用符を除外 |
| 括弧の原語併記（`保全課長（保全科长）`） | 括弧の中を除外 |
| 入力から転記した表のラベル（`产量`・`计划`） | 表の行を除外 |
| CSV／JSON の出力 | コードブロックを除外。フェンス無しでも英字キーが落ちる |
| 文書の正式名称（`取扱説明書`） | `lang_allow`（KN-02 の 4 ケースに `["取扱説明書"]`） |
| 中国語で使う `・` | かなから `U+30FB` を除外 |
| 文字集合の入れすぎ | **実機ログで観測した字だけ足す**。増やすときは観測元の結果ファイルをコメントに書く |

### どのケースに適用するか

**全 48 ケースに `expect_lang` を必須**（`none` を明示するのも含む）。`lang` 変数があるケースだけにすると chat の 3 本（KN-01/02/03）が丸ごと検査外になり、#162 が挙げた 3 件のうち 2 件を取り逃がす。
`run_tests.py --dry-run` でスキーマを検査し、CI（`verify.yml`）に足す。**キー無し・オフラインで「12 本すべてに宣言がある」ことを機械検証できる。**

### 既存の期待語を守る

`expect` / `expect_not` は 1 語も削らない・緩めない・並べ替えない。reviewer が `origin/main` の JSON と deep-equal 比較する 10 行のスクリプトを設計書 §7-1 に置いた。**12 行すべて `OK` でなければマージしない。**

## 5. FAIL を許容する順序

**前提**：`run_tests.py` の実機実行は CI に入っていない（キーが要る）。**検査を足した瞬間に main の CI が赤くなることは起きない。**

1. **PR-1（検査）と PR-2（是正）を並列で作り、両方 main へ。実機は回さない。** CI は緑。この時点で「壊れていることを機械が知っている」状態（`test_lang_check.py` が実機ログで NG を再現）
2. **Mac で 1 回だけ実機反映＋全 12 本テスト**
3. **PR-3 で結果と台帳を main へ。残った FAIL があってもそのまま入れる**（`dify/results/**` は記録であって CI ゲートではない。#154 と同じ扱い）。残った FAIL は `KNOWN_ISSUES.md` に `open` で 1 行ずつ

**絶対にやらないこと**：緑にするために `expect_lang` を `none` に落とす／`lang_allow` に一般語を積む／`expect` を削る。契約を変える必要が出たら**設計書の追補版を書いて PM の承認を取ってから**。

「先に検査、後で実機」にした理由：before の基準は §1 の棚卸し表と `test_lang_check.py` の 15 本で足りている。逆順にすると Mac をもう 1 回使うことになる。
