# Outline Wiki 前提のユースケース案

PM の予定「Outline で社内 Wiki を作る」を前提に、(1) Outline の事実整理、(2) 既存 41 サービスへの影響、(3) Outline があるからこそ成立する新規ユースケース案（`OW-xx`。**管理番号は付けない**）、(4) PM 判断待ち、をまとめる。
連携の実装は `platform-components.md` **PC-05**。architect 成果物。モック・`docs/handoff/**` には触れていない。

## 3. 新規ユースケース案（OW-01〜OW-10）

成熟度案は既存の基準（提供中＝標準機能で動く／試行版＝データ整備・連携が要る／構想＝運用・判断が先）で仮置き。**既存サービスと重なるものは統合を第一候補**にし、管理番号を増やさない。

### OW-01 会議録 → Wiki ページ化

| 項目 | 内容 |
|---|---|
| 狙い | 議事録を Outline に**下書き**で置き、決定事項・宿題をページに残す。次回はそのページを入力にして論点を引き継ぐ |
| インプット | 録音／メモ（DC-02 と同じ）、前回議事録ページ（`documents.info`） |
| Dify 構成の要点 | DC-02 の Workflow 末尾に `http-request`（`documents.create`、`publish: false`、`collectionId`＝会議体のコレクション）。見出しは議事録テンプレート（`documents.templatize`）に合わせる |
| Outline 側で必要なもの | 会議体ごとのコレクション、議事録テンプレート、公開担当 |
| 成熟度案 | 提供中 |
| 既存との重なり | **DC-02 に統合**（§9「書く」）。新サービスにしない |

### OW-02 Wiki 更新差分の担当者通知

| 項目 | 内容 |
|---|---|
| 狙い | 規程・手順ページが公開されたら、影響する分類の担当者に **③ `notify`** を出す（モックの EN-01／KN-05 の `notify` と同じ見え方） |
| インプット | Outline Webhook `documents.publish`／`documents.update`（`Outline-Signature` 検証） |
| Dify 構成の要点 | Webhook Trigger → `documents.export` で新旧版を取得 → PC-12 `diff-core`（Workflow as Tool）→ 影響索引で宛先分類を決定 → PC-01 に `notify` を POST → PC-14 で通知 |
| Outline 側で必要なもの | Webhook 購読、コレクション → 分類（`mine`）のマッピング表 |
| 成熟度案 | 試行版 |
| 既存との重なり | EN-01（取引先仕様）・KN-05（当局通達）は**外部**文書の差分。OW-02 は**社内 Wiki** の差分で入口が違う。PC-12 を共用し、**新規候補**（KN 系） |

### OW-03 質問 → 該当 Wiki が無ければ FAQ ドラフト起票

| 項目 | 内容 |
|---|---|
| 狙い | KN-04 で「回答できなかった質問」を捨てず、FAQ の下書きを Outline に自動起票する |
| インプット | KN-04 の会話ログ（Langfuse で `correctness` 低、または定型文返答）、質問文 |
| Dify 構成の要点 | 週次 Schedule（PC-11）→ Langfuse から未回答質問を取得（PC-09）→ LLM でクラスタリング → FAQ 案（質問・仮回答・要確認点）→ `documents.create`（下書き、FAQ コレクション） |
| Outline 側で必要なもの | FAQ コレクション、HR 帯の公開担当 |
| 成熟度案 | 試行版 |
| 既存との重なり | **KN-04 に統合**（FAQ 育成の経路）。PC-09 と PC-05 の組み合わせ |

### OW-04 Wiki の日中同期（ja ページの zh 版下書き）

| 項目 | 内容 |
|---|---|
| 狙い | ja で更新されたページの zh 版を**下書き**で生成し、版ズレ（KN-03 が検出する事故）を防ぐ |
| インプット | `documents.publish`（ja コレクション）、用語集（PC-06） |
| Dify 構成の要点 | Webhook Trigger → export（Markdown）→ LG-01 の翻訳 Workflow（`templates/01` 系）を Workflow as Tool で呼ぶ → zh コレクションに `documents.create`（下書き）。ページ対応表 `ja_doc_id ↔ zh_doc_id` を別表で持つ |
| Outline 側で必要なもの | ja／zh のコレクション対、対応表、zh 側の公開担当 |
| 成熟度案 | 試行版 |
| 既存との重なり | LG-01（翻訳）・DC-04（掲示物）・KN-03（版ズレ検出）と重なる。**翻訳エンジンは LG-01 を共用**。「同期ジョブ」を新サービス化するか PC-05 の機能にするかは **O-7** |

| 成熟度案 | 試行版 |
| 既存との重なり | **LG-02 に統合**（入力を「複数ファイル」から「コレクション」に広げる） |

## 4. PM 判断待ち

| # | 論点 | 選択肢 | architect の推奨 |
|---|---|---|---|
| O-1 | Outline を文書の**正本**にするか | (a) 規程・手順・議事録・用語集は Outline 正本、KB は派生／(b) 正本はファイルサーバ（Word/PDF）、Outline は閲覧用の写し／(c) 当面 Outline は「AI ドラフト置き場」のみ | **(a)**。§2 の「読」16 件が同期で回り、PC-03 の手動投入が減る。(b) は Wiki と PDF の二重管理になり、版ズレ（KN-03）が Wiki 側でも起きる |
| O-2 | ファイルサーバとの二重管理 | (a) Outline 化する文書種を限定（規程・手順・議事録・用語集・FAQ）、図面・帳票・契約はファイルサーバ／(b) 全部 Outline | **(a)**。図面・契約は PDF 原本と権限が要る（PC-02・PC-10）。Outline のページ先頭に「原本の場所」を書く運用 |
