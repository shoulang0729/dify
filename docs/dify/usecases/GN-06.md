## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：
  - 担当者が能動的に開く（頼まれた直後・朝いちの残件確認）
  - `PC-11` の定時（毎朝 8:30 のエイジング判定、毎週金曜 16:00 の週次まとめ、四半期末の棚卸し）
  - ③業務フィードの **`due`**（期限つきの票）**`routine`**（繰り返し票）**`notify`**（放置閾値超過・WIP 上限超過・**相談中になった**）
- **登場人物**：
  - **振られた側**（担当者）＝票を持つ人。確定・着手・完了・相談を操作する
  - **振った側**（依頼者）＝票を作った人。進捗と「止まっている理由」だけを見る（相手の他の票は見えない）
  - **上長**＝相談の宛先。四半期の集計を見る
- **いまの手順（Before）**：口頭・チャット・立ち話で頼まれる → 手帳／付箋／頭の中に散る → 定型は「今週は忙しいから来週」を繰り返す → 低優先（PC 在庫・固定資産・倉庫）は期限が無いので永久に後回し → 3 か月後に「あれどうなった」で発覚。**誰も催促しないので、誰も気づかない**
- **エージェント導入後の手順（After）**：
  1. 頼まれた内容をチャットかフォームに 1 行入れる（**30 秒**）
  2. エージェントが**票のドラフト**（担当・種別・大きさ・期限・繰り返し・重要度）を作り、**重複する既存票**と**現在の WIP**を示す
  3. **人が確定**する（AI は登録しない）。確定で `tasks` に INSERT、期限つきなら `PC-01` に `due` を POST
  4. 放置日数は毎朝の Code が更新。**14 日で本人／30 日で依頼者**に `notify`（催促の代わり）
  5. 今週の残件は「期限切れ → 今週期限 → 2 分で終わる → WIP 上限内で今週やる 3 件」の順に提示。**今週に入らない票は相談メモのドラフト**を出す（送信は人）
  6. 四半期末に完了率・種別別滞留・放置延べ日数・止まっている依頼を集計。**個人評価に直結させない注記つき**
- **成功の定義**：30 日以上放置の件数が四半期で半減／低優先の完了率 43% → 60%／「あれどうなった」の口頭確認が減る／振られた側が**催促される前に相談を出せる**

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 依頼文（自然文） | テキスト（`sys.query`） | ja / zh 混在 | 1 人 1 日 2〜5 件 | 「PC の在庫、今月中に棚卸ししといて」 | 入力欄（チャット／フォーム） | 言語判定（`PC-07`）、日付表現の解決（「今月中」→ 2025-09-30、`Asia/Shanghai`）、人名 → 社員 ID |
| フォーム入力 | 構造化（6 項目） | ja / zh | 同上 | 内容・依頼者・期限・種別・大きさ・繰り返し | 本番 UI（`PC-16`） | 既定値の補完 |
| 既存票 | JSON（`tasks` API） | — | 1 人 10〜30 件 | `{id, title, type, size, due, aging_days, status}` | `PC-01` / `tasks` テーブル | 担当者・状態で絞る。**他人の票は依頼者として関わるものだけ** |
| 業務分担表・定例業務一覧 | md | ja / zh | 月次更新 | 「入館証申請＝総務」「週報＝毎週金曜」 | Outline（`PC-05`）→ KB | 担当推定と繰り返し設定の根拠 |
| 人事マスタ | JSON | — | 日次同期 | 社員 ID・部署・**直属の上長** | `PC-04` | 相談メモの宛先解決 |
| 稼働カレンダー（両国祝日） | md / json | — | 年 1 回 | 春節 2/16〜22、秋分 9/23 | Outline → Code 定数（**GN-04 と共用**） | 営業日計算（期限・表示開始日） |

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。票の `title` は**入力された言語のまま保存**し、表示時に翻訳しない（原文が証拠。必要なら併記フィールド）
- **入力の欠け・曖昧さ**：
  - 期限が無い → **「期限なし」を許す**（聞き返さない。低優先を扱うための前提）。ただし種別を `low` として提案し、レビュー日（次の棚卸し日）を入れる
  - 依頼者が不明 → 「誰からの依頼ですか。自分で作った票なら『自分』と入れてください」（**匿名の依頼は作らない**）
  - 担当が不明 → 業務分担表 KB から候補 1〜2 名を提示し、人が選ぶ。**勝手に他人へ割り当てない**
  - 大きさが判断できない → `30min` を既定にし、「30 分でよいですか」と 1 回だけ聞く

## 3. 観点（LLM に守らせる業務ルール）

1. **票を登録しない**。エージェントの出力は常に**ドラフト**。「登録しました」「送信しました」と書かない。`tasks` への書き込みは人が確定ボタンを押したときだけ
2. **期限を作らない**。入力に無ければ「期限なし」。日付表現の解決は Code の結果を転記する（「今月中」→ 2025-09-30 は Code が計算）
3. **優先度を主観ラベル（高／中／低）で言わない**。並べ替えの根拠は **期限・大きさ・放置日数・重要度**の 4 つ。「重要だが緊急でない」＝**やる日を決める**と書く（アイゼンハワー）
4. **2 分で終わるものは票を増やさない**。「今すぐやってください」と勧める（2 分ルール）
5. **半日（`halfday`）の票は 30 分 × 3 に分解案を出す**。分解しないと着手されない
6. **WIP 上限（既定 3 件）を超えたら新規は「待ち」**。上限は設定値。超過していることを必ず明示する
7. **放置日数は計算値の転記**。「だいぶ経っています」のような曖昧表現をしない。**14 日／30 日の閾値も設定値**
8. **相談を勧める条件（4 つ。1 つでも当たれば相談メモのドラフトを添える）**
   - (i) 今週の枠（WIP 上限）に入らないのに期限が今週中
   - (ii) 期限超過が **3 日以上**、または同じ票で 2 回続けて先送りされた
   - (iii) 依頼が重複している／担当範囲が業務分担表と食い違う（自分の仕事か分からない）
   - (iv) 依頼者が複数いて優先順位が決められない
   - **勧めない場合**：2 分で終わる票、期限なしで放置 14 日未満の票（相談の乱発は催促と同じ害になる）
9. **相談メモは責めない書き方**。人の名前を主語にした評価（「◯◯さんが遅い」）を書かない。**事実（票番号・期限・日数・枠）と選択肢**だけ。選択肢は必ず **期限延長／優先順位の入れ替え／担当変更／取り下げ**の 4 つから提示し、**推奨は 1 つ**（理由 1 行）。**返答期限を必ず入れる**
10. **相談メモを自動送信しない**（`PC-14` を呼ばない）。「送る場合は画面のボタンで」
11. **集計は Code / SQL の結果の転記**。完了率・平均放置日数・件数を LLM が計算しない。**割り算を文章内でやらない**
12. **個人の評価をしない**。「◯◯さんの完了率が低い」と書かない。落ちている**種別・工程**を指す。四半期の出力には必ず注記を入れる：

    > この数字は業務の流れを見るためのものです。個人の評価に直接使うと票を起こさなくなり、かえって見えなくなります。個人別の完了率は本人と直属の上長だけが見ます。評価に反映するかどうかは人が判断してください。

13. **禁止**：票の内容に個人情報（病名・家庭事情・給与）を書かせない（`PC-10`。入力にあればマスクして「私用」とだけ）／他人の票の中身を依頼者以外に見せる／取り下げを AI が決める
14. **出力形式**：票ドラフト（項目の表）／今週の残件（期限切れ → 今週 → 2 分 → 今週やる 3 件）／四半期（全体 → 種別別 → 放置 → 止まっている依頼 → 読み取り → 次の 3 か月の案 → 注記）／相談メモ（§5-2d の 6 ブロック）

## 4. Dify 構成

- **アプリ種別**：**Chatflow**（多輪。票の作成 → 確認 → 相談 → 集計が同じ会話で続く）。Agent にしない理由 — 手順が固定でツール呼び出しの順序が決まっており、`../implementation-guide.md`／dsl-skill の指針どおり通常の tool / Code ノードの方が安定する
- **ノード列**：

  1. `Start`（`sys.query` ／ フォーム入力 `form_json` ／ `sys.user_id`）
  2. `Question Classifier`（4 分岐）：**A 票を作る** ／ **B 残件を見る** ／ **C 集計する** ／ **D 相談する**
  3. **A：** `Parameter Extractor`（`title` `requester` `due_raw` `type` `size` `recurrence` `importance`）→ `Code(resolve)`（日付表現の解決・営業日計算・社員 ID 解決）→ `HTTP Request(GET /tasks?owner=&status=open)`（重複候補・WIP）→ `Knowledge Retrieval`（KB `gn-task-rules`：業務分担・定例業務）→ `LLM(draft_ticket)`（§5-2a）→ `Answer`。**確定は UI のボタン** →（別 Workflow）`POST /tasks` ＋ `POST /feed/items`
  4. **B：** `HTTP Request(GET /tasks?owner=&status=open)` → `Code(plan_week)`（期限切れ／今週／2 分／WIP 上限内の 3 件を**Code で決める**）→ `LLM(week_summary)`（§5-2b）→ `if-else`（§3-8 の相談条件） →（該当時）`LLM(escalation_note)`（§5-2d）→ `Answer`
  5. **C：** `HTTP Request(GET /tasks/stats?from=&to=&scope=)` → `Code(shape_stats)`（完了率・種別別・放置延べ・前期比を**すべて計算**）→ `LLM(quarter_review)`（§5-2c）→ `Answer` →（任意）`PC-13` で xlsx/pdf
  6. **D：** `HTTP Request(GET /tasks/{id})` ＋ 人事マスタ（上長）→ `LLM(escalation_note)`（§5-2d）→ `Answer`（**送信ボタンは `PC-16`。Workflow から送らない**）
- **Knowledge**：`gn-task-rules`（Outline 同期：業務分担表、定例業務一覧（週次／月次／四半期の締切）、部署ごとの担当範囲、票の運用ルール〔WIP 上限・閾値・種別の定義〕）。**票データは KB に入れない**（更新・集計ができないため。テーブルが正）
- **テーブル（`tasks`。`PC-01` の隣に置く。実体は `PC-01` と同じ小さな Web サービスでよい）**

  | 列 | 型 | 備考 |
  |---|---|---|
  | `id` | text | `TK-25-0087` 形式。**票の番号であって管理番号（GN-06）ではない** |
  | `owner_id` / `requester_id` | text | 社員 ID（`PC-02`）。氏名は持たない（`PC-10`） |
  | `title` / `note` | text | 入力言語のまま |
  | `type` | enum | `routine` / `adhoc` / `low` |
  | `size` | enum | `2min` / `30min` / `halfday` |
  | `due_at` | date **null 可** | **null＝期限なし**（低優先を扱う前提） |
  | `recurrence` | enum | `none` / `weekly` / `monthly` / `quarterly` / `halfyear` |
  | `importance` | enum | `high` / `mid` / `low`（依頼者が付ける） |
  | `status` | enum | `open` / `wip` / **`consulting`** / `done` / `dropped` |
  | `last_touched_at` | timestamp | **`aging_days` の基準**（毎朝 Code が再計算） |
  | `parent_id` | text | 半日 → 30 分 × 3 の分解 |
  | `source` | enum | `manual` / `chat` / `schedule` / `import` |
  | `escalation_id` | text | 相談メモ（`escalations` 表）への参照 |

  API：`GET /tasks?owner=&status=`／`GET /tasks/stats?from=&to=&scope=`／`POST /tasks`（人の確定のみ・冪等キー `owner_id + title + due_at` のハッシュ）／`PATCH /tasks/{id}`／`POST /escalations`。第 1 段階は `tools/jiandaoyun`（简道云）または `tools/microsoft_excel_365` の表で代替可
- **プラグイン／ツール**：`http-request`（`tasks` API・`PC-01`）／`tools/jiandaoyun` または `tools/hap` または `tools/microsoft_excel_365`（第 1 段階の台帳）／`tools/wecom`・`tools/email`（週次まとめの配信。**相談メモは人が送る**）／`tools/echarts`（四半期の棒グラフ。種別別完了率）／Code ノード（営業日計算・集計整形。祝日定数は GN-04 と共用）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（構造化抽出と日中両方の文章）。代替 DeepSeek-V3.x。**票の内容に個人の事情が混じりうる**ため、越境を避ける構成では `models/ollama`（Qwen 32B 級）でも足りる（自由記述の判断が少ないタスクなので小さいモデルで劣化しにくい）
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`（フォーム入力と会話変数の持ち方＝本サービスの form 型に最も近い）、`../templates/06-text-to-sql-http-api-echarts.yml`（`http-request` の型と ECharts）
- **入出力変数**：`sys.query` string ／ `form_json` object ／ `sys.user_id` string ／ 会話変数 `draft_ticket` object・`week_plan` object・`escalation` object ／ 出力 `answer` string ＋ `actions[]`（`confirm_ticket` / `merge_ticket` / `send_escalation` — **すべて人が押す**）

## 5. プロンプト

### 5-1. System（全分岐で共通の前置き）

```text
あなたは青嶺精工 蘇州工場の業務追跡アシスタントです。担当者が抱える小さな仕事（定型・頼まれ事・後回しにされがちな低優先業務）を票として扱い、期限と放置日数を見えるようにします。
守ること：
1. あなたは票を登録・更新・送信しない。出力は常にドラフト。「登録しました」「送信しました」と書かない。確定は担当者が画面のボタンで行う。
2. 日付・営業日・放置日数・件数・完了率・平均は、与えられた JSON の値をそのまま転記する。自分で計算・推定しない。割り算を文章の中で行わない。
3. 期限が入力に無ければ「期限なし」とする。期限を作らない。
4. 優先度を高・中・低の主観ラベルで言わない。並べ替えの根拠は期限・大きさ・放置日数・重要度の 4 つ。緊急でないが重要な仕事は「やる日を決める」と書く。
5. 2 分で終わる仕事は票を増やさず、いま片付けることを勧める。半日の仕事は 30 分 3 つへの分解案を出す。
6. 同時着手の上限（既定 3 件）を超えている場合は必ず明示し、新しい票は「待ち」に置く。
7. 個人を評価しない。誰かが遅い・怠けているという書き方をしない。落ちているのは種別か工程だと書く。
8. 票の内容に病名・家庭事情・給与などの私的な情報が含まれていたら「私用」とだけ書き、内容を復唱しない。
9. 出力言語：利用者の入力言語。日本語なら日本語、中国語なら中国語。票の題名は入力された言語のまま引用する。
10. 分からないことは「分かりません」と書き、担当者に確認する項目として並べる。
```

### 5-2. User テンプレート（分岐ごと。変数は {{...}}）

#### 5-2a. 票ドラフトの生成（分岐 A）

```text
【依頼の原文】{{sys.query}} または {{form_json}}
【解決済みの値（Code 出力・転記のみ）】{{resolve.result}}
  例: {"title":"...","requester_id":"E-0007","due_at":"2025-09-30","due_source":"今月中","type":"low","size":"halfday","recurrence":"none","importance":"mid","workdays_left":12,"suggested_workday":"2025-09-26","blocked_days":["2025-09-29","2025-09-30"]}
【既存票（同じ担当者・open）】{{tasks.list}}   ← 重複候補・放置日数つき
【現在の WIP】{{tasks.wip}}   ← {"open":14,"with_due":9,"no_due":5,"wip":5,"wip_limit":3}
【業務分担・定例業務（KB）】{{knowledge.result}}

次の順で出力する（見出しは固定）：
1. 票の内容（票番号は仮・依頼者・担当・種別・大きさ・期限・繰り返し・状態・放置日数）
2. 優先度の判定（4 つの根拠と、いつ着手するかの推奨日。理由は blocked_days を引く）
3. 大きさの分解（size が halfday のときだけ。30 分 3 つ）
4. 重複・関連する票（tasks.list から。放置日数を必ず付ける。統合するかは質問で終える）
5. 今の持ち件数（WIP。上限を超えていれば「待ち」に置いたと書く）
6. 業務フィードへの登録（種類 due/routine、表示開始日、閾値 14 日／30 日）
```

#### 5-2d. 相談メモの生成（分岐 D。分岐 B から続けて呼ぶ場合も同じ）

```text

固定の 6 ブロックで出力する。ブロックの順序・見出しを変えない：
1. 宛先の上長 ／ 写し：依頼者

最後に本文の外へ 1 行：この文面はドラフトです。送信は画面のボタンで担当者が行ってください。
```

### 5-4. Few-shot（ja / zh を 1 組ずつ）

- **ja（分岐 A）**：入力「PC の在庫、今月中に棚卸ししといて」＋ `resolve` で `due_at=2025-09-30, size=halfday, workdays_left=12, blocked_days=[9/29,9/30]`、`tasks.wip = {open:14, wip:5, wip_limit:3}`、重複候補 `TK-25-0058(aging 31)` → 出力の要点：票ドラフト／「重要だが緊急でない」ので **9/26（金）**に着手を推奨（9/29〜30 は月次締め）／半日 → 30 分 × 3 の分解／`TK-25-0058` との統合を質問／WIP 超過につき「待ち」／確認 2 点（期限の解釈・台数の基準）／「まだ登録していません」

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|

## 8. 別出しが必要なもの（このサービス固有の準備）

- **`tasks` テーブルと API**（最優先。`PC-01` の隣に置く）：§4 の列と 5 本の API。第 1 段階は `tools/jiandaoyun`／`tools/microsoft_excel_365` の表でも成立する
- **エイジングの日次ジョブ**（`PC-11`）：毎朝 8:30 に `aging_days` を再計算し、14 日／30 日の閾値超過を `PC-01` に `notify` として POST（冪等キー `task_id + threshold`）
- **定型の自動起票**（`PC-11`）：`recurrence` から次回票を作る。祝日・締め日を避ける（GN-04 と共用の稼働カレンダー）
- **上長の解決**（`PC-04` 人事マスタ）：相談メモの宛先。**駐在員と現地社員でレポートラインが違う**場合があるので、人事に確認して 1 人に定める（曖昧なら担当者に選ばせる）
- **`escalations` 表**：相談メモの本文・状態（`draft` / `sent` / `answered`）・回答・決定（延長／入れ替え／担当変更／取り下げ）。**決定を票に反映するのは人の操作**
- **`PC-17` との境界の実装**：DC-08 の指摘から生まれた期限つきの約束は **PC-17 が正本**。`tasks` に同じものを作らない。③ の画面で並ぶが `source` が違う（`review_log` と `task`）。重複検知は `source_ref` で行う
- **無くても動く範囲**：`tasks` が無くても「依頼文 → 票ドラフトの整形」だけは動く（Excel に貼る運用）。ただし放置日数・完了率・相談の判定はすべて出せない＝**このサービスの価値の 8 割は表側にある**。逆に `PC-11` が無くても手動実行で回る（定型の自動起票だけ落ちる）

## 10. 未確定・リスク

- **最大のリスクは技術ではなく定着**：票を起こさなくなれば何も見えなくなる。対策 — 入口を 30 秒に保つ／2 分ルールで票を増やしすぎない／**数字を個人評価に直結させない**（設計書 §9 D-2）／WIP 上限と相談メモで受け側を守る（同 D-4）
- **PM 判断待ち**（設計書 §9）：D-1 定型の自動起票を第 1 段階から PC-11 で回すか（推奨：回す）／D-2 棚卸しは四半期・評価は人（推奨）／D-3 閾値 14 日・30 日（推奨・設定値）／D-4 誰でも振れる（推奨）／D-5 `platform-components.md` PC-01 への GN-06 追記（推奨・別 PR）
- **`PC-01` との重複通知**：本サービスが `notify` の主要な書き手になるため、他サービスの通知と合わせて量が増える。週次まとめ 1 通に束ねる／閾値超過は 1 票につき 1 回だけ（冪等キー）
- **他人に票を振れることの副作用**：「振っておけば自分の責任ではない」が起きうる。依頼者名を必ず残す／振った側のダッシュボードに**自分が振って止まっている件**を出す（人に押し付けた量が自分に見える）
- **中国側と日本側の運用差**：駐在員と現地社員でレポートラインと業務分担の書き方が違う。KB の業務分担表を**両言語で 1 本**にする（LG-02 の用語統一と同じ問題）
- **タイムゾーン**：期限・営業日は `Asia/Shanghai` を既定。日本本社が依頼者の票は表示だけ `Asia/Tokyo` を併記（GN-04 と同じ扱い）
- **成熟度**：`st2`（試行版）のまま。`tasks` テーブル ＋ 日次エイジング ＋ T01〜T12 通過 ＋ 1 部署 3 か月の運用で `st1` 候補。実現性 **○**（Dify 側は易しいが、外側のテーブルと運用が要る）
