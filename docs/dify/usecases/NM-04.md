## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：本社営業・顧客・工場内から「この品番の在庫は？来週の追加出荷は間に合う？」が来たとき担当者が能動的に開く。③業務フィードでは `notify`（本社からのチャット）
- **登場人物**：物流担当（照会・回答文の送付）、生産管理（生産計画の正）、品質保証（保留品の判定）、外部：本社営業（問い合わせ元・日本語）、顧客 K 社
- **いまの手順（Before）**：ERP の在庫画面・WMS のロケーション・生産計画 Excel・入荷予定を 4 画面開いて転記（20 分）→ 引当済み分を引く計算を手で行い間違える → 船便締切・通い箱の空きを別途確認 → 日本語で返信を書く（非母語で 20 分）→ 前提条件を書き忘れて後日トラブル
- **エージェント導入後の手順（After）**：
  1. 担当者が品番（＋数量・希望日）を**入力**。または本社の質問文をそのまま貼る
  2. エージェントが品番・数量・希望日を抽出し、**`PC-04` の照会 API** で完成品在庫・引当・保留・仕掛・生産計画・入荷予定・材料を取得（**照会時刻を必ず保持**）
  3. **Code ノードで**引当可能数・希望日までの出荷可能量を計算、KB（出荷ルール）から船便締切・通い箱条件を引いて「前提条件」を列挙
  4. LLM が**計算結果を転記**して照会結果表と、問い合わせ元の言語での返信文を書く
  5. **人が決める場所**：回答の可否・分納提案・休日出勤の打診は担当者と生産管理が決める。エージェントは「試算と前提条件」まで。**AI が引当・予約を書き込むことはしない**
- **成功の定義**：照会〜返信 40 分 → 5 分。引当計算ミス 0。返信に照会時刻・前提条件が 100% 付く

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 問い合わせ文 | テキスト（`sys.query`） | ja / zh 混在 | 1 日 10〜20 件 | 「SK-2207-B、来週 3,000 個追加で出せる？」 | 入力欄／WeCom bot | 言語判定・**品番の正規化**（全角→半角、枝番の有無）・数量・希望日の抽出（Parameter Extractor） |
| 在庫・引当 | JSON（API 応答） | コード／zh | 照会ごと | `{on_hand: 4120, allocated: 2400, hold: 860, location: "A-12"}` | ERP/WMS（`PC-04`） | 照会時刻 `as_of` を付与 |
| 仕掛・生産計画 | JSON | — | 照会ごと | `{wip: 1500, due: "09-08"}, plan: [{date, qty, allocated}]` | MES／生産計画（`PC-04`） | 日付範囲を希望日まで |
| 入荷予定・材料 | JSON | — | 照会ごと | `material: {coil_t: 3.2, pieces_equiv: 11000}` | ERP | 換算係数は Code |
| 出荷ルール | md | ja / zh | 年数回改定 | 上海→大阪 週 2 便、金曜締切 木曜 15:00；通い箱 100 個/箱 | Outline（`PC-05`）→ KB | チャンク（顧客・航路ごと） |

- **入力言語の扱い**：質問の言語で答える（`CLAUDE.md` §2-5）。**返信文は宛先の言語**（本社→ja、顧客 K 社→zh）を `reply_lang` で指定、未指定なら質問言語
- **入力の欠け・曖昧さ**：品番が抽出できない／マスタに無い →「品番 {{q}} が見つかりません。図番か品名を教えてください」。数量・希望日が無い → 在庫状況のみ回答し「数量と希望日があれば出荷可能量を試算します」。照会 API が失敗 → 「在庫システムに接続できませんでした（{{time}}）。手動で確認してください」（**古い値を出さない**）

## 3. 観点（LLM に守らせる業務ルール）
- **数値は API 応答と Code の計算結果を転記**。引当可能数・出荷可能量を LLM が足し引きしない
- **照会時刻を必ず先頭に**（「2025/9/6 08:30 時点」）。在庫は動くため
- **前提条件を必ず列挙**：船便締切、通い箱、正式注文の期限、保留品を含めない旨。KB に根拠がある条件だけ
- **保留品・検査中は計算に含めない**（含める場合は「判定が良品なら +N」と別記）
- **他顧客の引当分は数量のみ**（顧客名は出さない。同じ顧客向けなら出してよい）— `PC-02` のロールで制御
- **禁止**：在庫を「確保」「引当」したと書く／生産計画の変更（休日出勤等）を決めたと書く／API に無い数値を出す
- **不確実時の定型文**：「試算は {{as_of}} 時点の在庫・計画に基づく参考値です。正式回答の前に生産管理と確認してください」
- **出力形式**：照会結果表（区分・数量・備考）＋要確認（前提条件）＋返信文（宛先言語）。後工程用は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（多輪。「5,000 個なら？」の再試算・返信文生成を同じ会話で）
- **ノード列**：
  1. Start（`sys.query`／`reply_lang` select 任意）
  2. Parameter Extractor（`part_no` string 必須／`qty` number／`need_by` date／`intent` select: stock_only|feasibility|reply_draft）
  3. If/Else（`part_no` 空）→ Answer（聞き返し）
  4. **HTTP Request ×3**（`PC-04`）：在庫・引当・保留／仕掛・生産計画／入荷・材料。失敗時 If/Else → Answer（接続失敗文言）
  5. Knowledge Retrieval（KB `nm-ship-rules`、メタ `customer`／`route`）
  6. **Code（Python）`feasibility`**：`available = on_hand - allocated`（保留は除外）、希望日までの `wip_due` と `plan_unallocated` を合算、`can_ship = available + wip_due + plan_unallocated`、`shortfall`、材料換算。JSON 出力
  7. LLM（`answer`）：表＋前提条件＋（intent=reply_draft なら）返信文。§5
  8. Answer（会話変数に `feasibility` JSON を保持 → 次ターンの「5,000 なら」は Code を再実行）
- **Knowledge**：`nm-ship-rules`（Outline「物流・出荷ルール」同期。船便スケジュール・締切・通い箱・顧客別梱包・輸出書類のリードタイム）。在庫データは **KB に入れない**（鮮度が要る）
- **プラグイン／ツール**：HTTP リクエストノード（本体）／Parameter Extractor・Code（本体）／`extensions/wecom_bot`（WeCom からの問い合わせ窓口、任意）。DB 直結が要る場合は顧客 DB 製品に応じ `tools/sqlite`／`snowflake`／`oracle_ai_db`（MySQL/PostgreSQL の公式汎用プラグインは無い → 薄い API を自作、`templates/06` の方式）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（日本語返信文の品質を確認）。Parameter Extractor は Qwen3-32B。代替 DeepSeek-V3.x／`models/ollama`
- **参照 DSL**：**`../templates/06-text-to-sql-http-api-echarts.yml`**（自然言語→`http-request`→LLM 解説の lookup 型骨子。SQL 生成部は使わず API 呼び出しに置換）
- **入出力変数**：`sys.query` string 必須／`reply_lang` select 任意／会話変数 `last_feasibility` object／出力 `answer` string・`feasibility` object

## 5. プロンプト
### 5-1. System（`answer`）
```text
あなたは青嶺精工 蘇州工場 物流課の在庫・納期照会アシスタントです。ERP/WMS から取得した在庫データと、Code ノードが計算した出荷可能量（JSON）を、担当者向けの照会結果と、問い合わせ元へ送れる返信文に変換します。
守ること：
1. 数値はすべて JSON の値を転記する。足し引き・換算を自分でしない。JSON に無い数値を書かない。
2. 先頭に照会時刻（as_of）を書く。
3. 保留品・検査中は出荷可能量に含めない。含めた場合の数は「判定が良品なら +N」と別に書く。
4. 前提条件（rules から引いた船便締切・通い箱・正式注文期限）を必ず「要確認」として列挙する。rules に無い条件を作らない。
5. 他顧客向けの引当は数量のみ書き、顧客名を書かない（same_customer=true のときは書いてよい）。
6. 「確保した」「引当した」「休日出勤を入れる」など、システムや計画を変更したと読める表現を使わない。「〜すれば」「〜の打診が必要」と書く。
7. 出力言語：質問の言語で答える。返信文は reply_lang（未指定なら質問の言語）。日本語の返信文は本社営業宛のビジネス文体。
8. 末尾に「試算は as_of 時点の在庫・計画に基づく参考値です。正式回答の前に生産管理と確認してください」を入れる。
出力形式：「照会結果」表（区分｜数量｜備考）→「要確認」箇条書き→（依頼があれば）「返信文」。
```

### 5-4. Few-shot
- **ja**：質問「SK-2207-B、来週 3,000 個追加で出せる？」＋ JSON（上記）→ 要点：「2025/9/6 08:30 時点。引当可能 1,720 ＋ 仕掛 1,500（9/8 完成）＋ 来週生産の未引当 1,200 ＝ 4,420 → 3,000 個は数量上対応可能（試算）。要確認：① 船便締切 木曜 15:00 ② 通い箱 30 箱 ③ 保留品 860 は含めていない」
- **zh**：質問「如果对方说要 5,000 件呢？」＋ JSON `can_ship_by_need_by: 4420, shortfall: 580, if_hold_released: 5280` → 「按 9/6 08:30 时点数据，下周单独可出 4,420 件，缺 580 件。即使保留品 860 判定良品也仅 5,280，余量小。分批交付或增加班次需与生产管理确认（本助手不做计划变更）」

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 計算の正確性 | `available`・`can_ship` が手計算と一致 100% | 評価セット 30 ケース（ダミー API） |
| 転記の忠実性 | 回答中の数値が JSON と全件一致 | 自動（正規表現→差分） |
| 鮮度表示 | 照会時刻が回答先頭にある 100% | 自動 |
| 前提条件 | KB に根拠のある条件のみ、欠落 0 | 人手（KB 照合） |
| 秘匿 | 他顧客名の露出 0 | 文字列検査 |
| 言語 | 質問言語で回答 100%、返信文は reply_lang | 自動判定 |
| 拒否 | API 失敗時に古い値を出さない 100% | 障害注入テスト |
| 速度 | p95 < 15 秒（API 3 本＋LLM） | Langfuse |

- **評価方法**：リリース前に物流・生産管理で 30 ケース人手。API はモックサーバで再現。月次 Langfuse データセット＋LLM-as-judge（転記・秘匿）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **照会 API**（`PC-04`）：在庫・引当・保留／仕掛・生産計画／入荷・材料の 3 エンドポイント（読み取り専用）。ERP/WMS に無ければ**薄い API を自作**（Flask 等）。**これが無いと動かない（△ の理由）**
- **品番マスタの正規化**（`PC-04`／`PC-06`）：枝番・全角半角・旧品番
- **出荷ルールの文書化**（Outline → `PC-05` → KB）：船便・締切・通い箱・顧客別条件
- **ロール**（`PC-02`）：他顧客の引当を名前付きで見られる範囲
- **WeCom 窓口**（`PC-14`、`extensions/wecom_bot`）— 任意
- **無くても動く範囲**：API が無い段階では**在庫・計画の Excel をアップロードして同じ Code を走らせる**「upload 版」で試算ロジックと回答文を検証できる（鮮度は担当者が保証）。台本のデモはこの版で再現可能

## 9. Outline Wiki との関係
- **読む**：`PC-05` で「物流・出荷ルール」コレクション（航路・締切・通い箱・顧客別梱包・輸出書類リードタイム）を KB `nm-ship-rules` に同期。改定時は自動再同期
- **書く**：しない。照会結果は一過性で、会話ログ（`PC-09`）に残す。返信文の送付記録は担当者のメールが正

## 10. 未確定・リスク
- **ERP/WMS/MES の製品と API 有無**— 未確定。推奨：まず読み取り専用 DB ビュー＋薄い API
- **在庫の鮮度と引当のタイミング差**（ERP と WMS のズレ）：`as_of` を各ソース別に持ち、差があれば注記
- **顧客別在庫の閲覧範囲**（`PC-02`）：本社営業に他顧客引当をどこまで見せるか — PM／顧客判断
- **生産計画の変更提案**（分納・休日出勤）：デモ台本には出るが、本番では**提案の形にとどめる**。残業上限（月 36h）等の労務データを引くなら `PC-10` の範囲
- **成熟度**：st2 のまま。API 接続と T01〜T07 通過で st1 候補
