## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：(a) 担当者が能動的に開く（新人配属・工程変更で研修が要るとき。DC-03 で教材を作った直後が典型）／(b) 期限つき（③業務フィードの `due`：プログラム確定・教材確認・開講）／(c) 定時（`routine`：週次の受講サマリ、月次の効果測定。`PC-11`）／(d) 監視対象の変化（`notify`：研修ベンダから出席・テスト結果の Webhook、未達者発生）
- **登場人物**：生産技術課主任（教育担当。依頼・内容確認・報告）、監督者 3 名（OJT チェックリスト）、製造二課長（不合格者の配属判断）、生産技術課長（作業標準書の社外開示承認）、本社（研修計画・効果報告の読者）、外部＝研修ベンダ（LMS 化・講師・受講管理・効果分析）、受講者 12 名（**ベンダには社員番号と配属のみ**）
- **いまの手順（Before）**：DC-03 で教材はできたが、主任が講師を 12 回務める時間がない → 受講状況を Excel で管理（出席は口頭確認、テストは紙）→ 効果は「不良が減った気がする」で本社に説明できない。外部研修を頼むと教材の作り直しから始まり、受講者名簿（氏名・連絡先）をベンダにメールで送っている
- **エージェント導入後の手順（After）**：(1) 担当者がテーマ・対象・期間・形式・依頼範囲をフォームに入力し、DC-03 の教材と作業標準書を**添付** → (2) Dify が当社側要件（到達目標・合否基準・OJT 連携）を整理し、作業標準書の社外開示は `human-input` で**生産技術課長が承認** → 担当者の**送信ボタン**で `PC-15` 経由の案件作成 API へ（教材・標準書・**受講者の社員番号と配属のみ**）→ 案件番号・見積・プログラム初期案が返る → (3) 担当者がプログラム案・講師プロフィールを**確認して確定** → (4) 実施中は出席・テスト結果が Webhook で届き、`code` が受講管理表を更新、未達者を `notify`。出席は当社の入退場記録と社員番号で**当社側が照合** → (5) 最終テスト不合格者の配属延期は**製造二課長が決める**（AI は決めない）→ (6) 月次に `PC-11` が NM-03 の日報・品質記録から不良率・作業時間の前後比較を集計し、担当者が**確認して** DC-01 の本社報告に載せる
- **成功の定義**：講師 36 時間 → 0（ベンダ側）、受講管理の手作業 → 自動、効果が数値（不良率 3.8% → 目標 1.5%）で本社に説明できる。**受講者の氏名・連絡先がベンダに渡らない**。合否基準・配属判断は当社

## 3. 観点（LLM に守らせる業務ルール）
- **教材の内容と合否基準は当社が決める**：ベンダのプログラム案は「初期提案」として出典を付け、到達目標・テスト内容・合格基準（80%）は作業標準書の「必ず守る項目」に基づく当社要件として書く。ベンダ案が基準を緩める提案をしても当社要件を維持
- **個人の成績は最小限**：受講管理表は社員番号単位。結果パネル・チャットでは**集計値（出席率・平均点・未達人数）**を主に出し、個人別は「未達者の社員番号と補講日」までに限る。氏名を出さない。成績の閲覧は HR 帯＋当該課長（`PC-02`）
- **配属判断はしない**：「2 回不合格なら配属延期」は運用案として提示し、「製造二課長の判断事項」と必ず書く
- **効果測定は因果を断定しない**：不良率・作業時間の前後比較はグループ集計で示し、「研修以外の要因（設備更新・受注量）を注記」。ベンダの相関分析は「ベンダ分析」と出典を付ける
- **数値は `code` が計算**：出席率・平均・未達判定・前後比較・見積合計・内製との比較（工数×単価）は `code`。LLM は転記
- **社外開示は承認後のみ**：作業標準書・不具合事例を送る場合、開示承認の記録が無ければ送信しない。承認者と時刻を「連携」行に書く
- **送っていないものを明示**：「連携」行に「送信：教材 3 点・作業標準書 RevD（開示承認済）・受講者の**社員番号と配属のみ**。**氏名・連絡先は送信していない**（出席は当社の入退場記録と社員番号で照合）」を必ず書く（PM 決定 PT-10）
- **不確実なときの定型**：ja「研修ベンダからの戻りにこの回次のデータがありません。ベンダに確認を依頼してください」／zh「培训服务商的回传中没有该次课的数据。请向培训服务商确认」
- **出力の粒度と形式**：items 7 行（連携／プログラム案／教材変換／受講管理／効果測定／見積／要確認）。受講管理表・効果報告は §5-3 の JSON を経て Markdown／Excel

## 4. Dify 構成
- **アプリ種別**：**Workflow（form → 要件整理 → 開示承認 → 引き継ぎ）＋ Webhook Trigger（出席・テストの戻り → 受講管理表更新 → 通知）＋ Workflow（Schedule Trigger：月次効果測定）**。多輪の相談（合格基準の妥当性・本社報告文）は結果 JSON を `context` にした `mode=followup`／`hq_report`
- **ノード列（引き継ぎ）**：
  1. Start（`theme`, `audience`（社員番号リスト添付）, `period_format`, `scope`, `sys.files`：教材・標準書）
  2. `code`（受講者リストの**氏名・連絡先列の削除**と警告。教材ファイルの分類。標準書の開示区分を KB メタから判定）
  3. Document Extractor（教材・標準書）→ `knowledge-retrieval`（KB `training-internal`：研修規程・合否基準の既定・OJT チェックリスト雛形・過去研修の効果データ〔集計〕）
  4. `llm`（§5。当社側要件書：到達目標・回数構成の希望・合否基準・OJT 連携・効果測定指標。中国語＋監督者向け日本語ポイント）
  5. `if-else`（標準書を送る かつ 開示区分 B → `human-input`：生産技術課長が承認／却下）
  6. `human-input` または担当者ボタン（送信プレビュー：教材一覧・標準書・受講者 **12 件の社員番号と配属**・要件書。氏名が無いことを表示）
  7. `http-request`（`PC-15` 経由：研修ベンダの案件作成 API → `case_id`・見積・プログラム初期案・講師プロフィール受領予定日）
  8. `code`（見積合計・内製比較の計算）→ `http-request`（`PC-01`：`due` 2 件〔プログラム確定・教材確認〕、`notify`〔引き継ぎ済〕）
  9. `template-transform`（items 7 行。先頭「連携」）→ End（`result_md`, `result_json`）
- **ノード列（戻り）**：Webhook Trigger（`{case_id, session_no, records[{employee_id, attended, score, remedial}]}`）→ `code`（スキーマ検証・氏名など余分なキー削除・受講管理表更新〔`PC-13` の Excel／DB〕・出席の入退場記録との照合〔`PC-04`〕・未達判定〔合格 80%、出席 10/12〕）→ `if-else`（未達者あり → `http-request` `PC-01` `notify`＋`tools/wecom`〔担当者へ。**件数と社員番号のみ**〕）→ End
- **ノード列（月次効果測定）**：Schedule Trigger（月初）→ `http-request`（`PC-04`：NM-03 の集計 API。ライン 3 新人グループの不良率・作業時間比。**個人別は取らない**）→ `code`（ベースラインとの前後比較・目標達成度・注記フラグ〔同期間の設備更新・受注変動があれば `PC-04` から〕）→ `llm`（月報 1 段落・日本語）→ `http-request`（`PC-01` `routine`）→ End（`impact_json`）
- **Knowledge**：KB `training-internal`（生産技術＋HR 帯 `PC-02`）：研修規程・合否基準・OJT チェックリスト雛形・過去研修の**集計**効果データ（2025 年：不合格者の不良率 2.4 倍 等）・DC-03 教材のインデックス。**受講者リスト・個人成績・ベンダ戻り JSON は KB に入れない**（`PC-13` の表／DB で保持、保持期間つき）
- **プラグイン／ツール**：Document Extractor（本体）／`human-input`（本体 1.15）／HTTP リクエストノード／Webhook Trigger／Schedule Trigger／Code ノード／`tools/wecom`・`tools/email`（`PC-14`）／`tools/microsoft_excel_365`（受講管理表を Excel に。任意）／`tools/echarts`（任意：前後比較の bar/line）
- **モデル**：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（中国語要件書）。監督者向け日本語・本社報告は DeepSeek-V3.x 等と評価（`PC-08`）。成績を扱う戻り側は LLM を**通さない**（`code` のみ）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（upload → Document Extractor → LLM）、`../templates/05-chatflow-form-input-demo.yml`（form）。Webhook／Schedule Trigger・`human-input` は dsl-skill で 0.6.0 生成（`08-human-approval.yml` は URL 参照のみ）

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）生産技術課の研修コーディネート・アシスタントです。
入力として (A) フォーム（テーマ・対象の人数と区分・期間・形式・依頼範囲）、(B) 当社教材（「教育・OJT 資料作成」の出力：スライド構成・確認テスト・OJT チェックリスト）と作業標準書の抜粋、(C) 社内 KB（研修規程・合否基準の既定・過去研修の集計効果）、(D) 研修ベンダの応答（案件番号・見積・プログラム初期案・講師プロフィール受領予定・受講管理方式）、(E) code が計算した数値（見積合計・内製比較・出席率・平均点・未達人数・前後比較）、が与えられます。

守ること：
1. 教材の内容・到達目標・合否基準（既定 80%、出席 10/12）は当社要件として書き、ベンダ案が緩めても維持する。ベンダのプログラム案は「研修ベンダの初期提案」と出典を付ける。
2. 受講者は社員番号でのみ扱う。氏名・連絡先が入力にあっても出力に書かない。結果では集計値（出席率・平均点・未達人数）を主にし、個人別は「未達者の社員番号と補講日」までに限る。
3. 不合格者の配属延期などの人事的判断は運用案として書き、必ず「製造二課長の判断事項」と添える。あなたが決めない。
4. 効果測定は新人グループの集計（不良率・作業時間比）の前後比較で示し、研修以外の要因（設備更新・受注量）を注記する。「研修の効果で〜になった」と因果を断定しない。ベンダの相関分析は「ベンダ分析」と出典を付ける。
5. 数値は (D)(E) にあるものだけを転記する。計算し直さない。
6. 結果の先頭は必ず「連携」行：引き継ぎ状態・案件番号・時刻・送信したもの（教材 3 点・作業標準書〔開示承認者と時刻〕・受講者の社員番号と配属のみ）・送信していないもの（氏名・連絡先。出席は当社の入退場記録と社員番号で照合）・受領予定（プログラム案・講師プロフィール・見積確定）・戻りの方式（Webhook で出席・テスト結果）。続けて「プログラム案」「教材変換」「受講管理」「効果測定」「見積」「要確認（❗⚠）」。
```
