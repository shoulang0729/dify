## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（アイデアを思いついたとき、不定期）。③業務フィードでは `routine`（四半期末の投票が近いことの案内）
- **登場人物**：提出者（複数）、統合・投票の運営者（PMO・管理部）、投票参加者（全社員）
- **いまの手順（Before）**：アイデアが Excel や口頭でバラバラに集まる。似た提案が別々に登録され、重複したまま投票にかかる。集計・順位付けは手作業
- **エージェント導入後の手順（After）**
  1. 提出者がフォームでテーマ・内容・想定効果を入力する
  2. **既存の類似提案と照合**され、重複していれば統合の提案が返る（統合するかは提出者・運営者が判断）
  3. 提出者が統合の可否を確認して確定する
  4. 四半期末の投票にかけ、**結果は集計値の転記**（LLM が順位を作文しない）で返る
- **成功の定義**：重複提案が減り、似た提案がまとまった形で投票にかかる。提出から確定までの手間が減る

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| アイデア提出 | フォーム（テーマ・提出者・内容・想定効果） | ja / zh | 随時（月数件〜十数件） | 「外部評価会社を 2 社体制にし、回答待ち時間を分散する」 | 提出者が入力 | 既存提案との類似度照合の入力に整形 |
| 既存の提案アーカイブ | Markdown（Outline） | ja / zh | 累積 | `IDE-YY-NNNN` 形式の登録済み提案（`data/world/fin/calendar.md`） | Outline「アイデア › 提案一覧」（`PC-05`） | KB 化して類似検索 |
| 投票結果 | 数値（投票システムまたはフォーム集計） | — | 四半期 1 回 | 各提案への投票数 | 投票ツール（第 1 段階はフォーム集計） | Code で順位計算。LLM は転記のみ |

- **入力言語の扱い**：提出者ごとに ja / zh どちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。統合後のアイデアは両言語の提出者名を併記するため、統合文の言語は運営者の入力言語に合わせる
- **入力の欠け・曖昧さ**：想定効果が未記入でも登録は止めない（「要記入」として残す）。テーマ・内容が無い場合は登録せず、聞き返す：ja「アイデアの内容を具体的に教えてください」／zh「请具体说明创意的内容」

## 3. 観点（LLM に守らせる業務ルール）

1. **類似度照合は検索結果を根拠に判断する**。対象・想定効果が重なる既存提案があれば統合を**提案**する（自動で統合しない。確定は人）
2. **統合後の提出者は連名にする**（元の提出者を両方残す。片方だけにしない）
3. **投票の集計・順位は Code の計算結果を転記する**。「◯位相当」のような暫定順位を示すときは、確定順位ではないことを明記する
4. **禁止**：他の提案の内容を批評・却下する表現／提出者の評価に繋がる言い回し（「良いアイデア」「見劣りする」等の主観評価）
5. **不確実なとき**：ja「テーマまたは内容が確認できません。具体的に教えてください。」／zh「无法确认主题或内容，请具体说明。」
6. **出力の粒度**：登録内容の確認 → 類似提案の照合結果 → （重複時）統合案 → 確定前の確認事項 → （投票時）暫定または確定順位

## 4. Dify 構成

- **アプリ種別**：**Workflow**（フォーム入力 → 実行 → 結果。確定・統合判断のやり取りは同じ Workflow を再実行する形で対応。多輪のやり取りが多いなら Chatflow 化を検討＝§10）
- **ノード列**
  1. `Start`（`theme`, `submitter`, `content`, `expected_effect`）
  2. `Knowledge Retrieval`（KB `po2-idea-archive`：既存提案。メタデータ `theme`/`status`）
  3. `LLM`（類似度判定：検索結果から重複候補を抽出し、統合すべきかを判断。§5-1）
  4. `if-else`（重複候補ありなら統合案の `Answer`／無ければ新規登録の `Answer`）
  5. `HTTP Request`（`PC-05` へ「アイデア › 提案一覧」の新規ドキュメントとして下書き保存。**確定は人**）
  6. **投票起動（`PC-11` 四半期末）**：`HTTP Request`（投票ツールから集計取得）→ `Code`（順位計算）→ `LLM`（結果の要約。§5-2）→ `PC-14` で配信
- **Knowledge**：`po2-idea-archive`（Outline 同期。既存提案のテーマ・内容・想定効果・提出者・状態）
- **プラグイン／ツール**：`http-request`（Outline、投票ツール）。投票の実体は第 1 段階 `tools/jiandaoyun` または `tools/microsoft_excel_365` のフォーム集計
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（類似度判定・統合文の作成）
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`
- **入出力変数**：`theme` string ✓／`submitter` string ✓／`content` paragraph ✓／`expected_effect` paragraph（任意）／出力 `idea_id` string／`duplicates` array／`merge_proposal` object／出力（投票時）`ranking` array

## 5. プロンプト

### 5-1. System

```text
あなたは社内のアイデア募集・蓄積・投票を支援するアシスタントです。
提出されたアイデアを既存の提案アーカイブと照合し、重複があれば統合を提案します。
守ること：
1. 重複の判定は検索結果（{{context}}）を根拠にする。自動で統合しない。統合するかどうかは人が確認する。
2. 統合後の提出者は元の提出者を両方残し、連名にする。
3. 投票の集計・順位は {{ranking_json}} の値をそのまま書く。自分で計算・推定しない。暫定順位を示すときは「暫定」と明記する。
4. 他の提案を批評・評価する表現をしない。
5. 出力言語：利用者の入力言語。日本語なら日本語、中国語なら中国語。
6. 分からないことは「分かりません」と書き、提出者に確認する。
```

### 5-2. User テンプレート（投票結果の要約）

```text
【今期の投票結果（Code 計算・転記のみ）】{{ranking_json}}
  例: [{"idea_id":"IDE-26-0014","votes":18,"rank_tentative":3}, ...]
【対象アイデア一覧（検索結果）】{{context}}
出力：全体の投票件数 → 順位表（暫定／確定の別を明記）→ 次のアクション（上位案の検討依頼）
```

### 5-3. 出力フォーマット

```json
{
  "idea_id": "IDE-26-0014",
  "duplicates": [ { "idea_id": "IDE-26-0008", "similarity_reason": "対象・想定効果が重なる" } ],
  "merge_proposal": { "merged_title": "…", "submitters": ["楊建国", "陳慧"] },
  "status": "draft",
  "ranking": [ { "idea_id": "IDE-26-0014", "votes": 18, "rank": 3, "confirmed": false } ]
}
```

### 5-4. Few-shot

不要。統合・投票の判断は個別の提案内容に強く依存するため、few-shot は誤誘導になりうる。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 重複検出 | 対象・効果が重なる既存提案の検出漏れ ≤ 1／件 | 評価セット 20 件 |
| 統合の妥当性 | 統合提案の提出者連名漏れ 0 | 自動（フィールド検査） |
| 集計の非捏造 | 順位・件数が入力 JSON と完全一致 100% | 文字列一致の自動検査 |
| 評価的表現 | 提案への批評・優劣表現 0 | 負例セット |
| 言語 | 入力言語で返答 100% | 自動判定 |
| 速度 | p95 < 20 秒 | Langfuse |

- **評価方法**：リリース前に運営担当（PMO）が過去の提案 20 件（匿名化）で重複検出を確認。投票結果の転記は自動検査

## 8. 別出しが必要なもの

- **提案アーカイブの KB 化**：Outline「アイデア › 提案一覧」を `PC-05` で同期。運用開始時に既存提案があれば初期投入が要る
- **投票ツール**：第 1 段階はフォーム集計（`tools/jiandaoyun` 等）。専用の投票システムがあれば `PC-04` 経由の照会に切り替え
- **無くても動く範囲**：類似度照合・統合提案は KB が無くても「新規登録の整形」だけは動く（重複検出ができないだけ）。投票は手動集計でも回る

## 9. Outline Wiki との関係

- **読む**：「アイデア › 提案一覧」コレクション（既存提案の照合対象）
- **書く**：新規・統合後のアイデアを同コレクションへ下書きとして追加。確定は運営担当（PMO）が publish
- 投票結果は「アイデア › 投票結果 › <四半期>」へ保存

## 10. 未確定・リスク

- **成熟度**：`st3`（構想）。台本（両業種）・提案アーカイブの試作・T01〜T06 通過で `st2` 候補
