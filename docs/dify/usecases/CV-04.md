## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（定期 KYC レビュー、新規取引開始時）。③業務フィードでは `due`（定期レビューの期日）
- **登場人物**：コンプライアンス部の担当者（スクリーニングする側）、対象先（実質的支配者・登記情報の提出者）
- **いまの手順（Before）**：担当者が登記情報・申告書・ネガティブ情報を個別に照合し、確認できた点・裏付けが取れない点を手作業で整理する。エスカレーションの要否判断も個人の経験に依存する
- **エージェント導入後の手順（After）**：
  1. 提出書類（登記情報・実質的支配者申告書等）をアップロードする
  2. 確認できた点・裏付けが取れない点・追加で必要な書類が一覧で返る
  3. 担当者が**コンプライアンス部への上申が必要かどうかを判断する**（AI はエスカレーションを確定しない）
- **成功の定義**：確認作業の時間が減り、エスカレーション基準への当てはめが一貫した形で行える

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 登記情報 | PDF | zh | 対象先ごと 1 件 | 登記情報_丙社.pdf | 提出書類 | `Document Extractor`。**個人情報（住所等）はマスク対象（`PC-10`）** |
| 実質的支配者申告書 | PDF | zh / ja | 対象先ごと 1 件 | 実質的支配者申告書_丙社.pdf | 提出書類 | 同上。氏名・出資比率のみ抽出し、住所・連絡先はマスク |
| ネガティブ情報 | PDF/構造化 | ja / zh | 任意 | rs1_ネガティブ情報_丙社.pdf | `RS-01` の出力 | 審査の一次判断材料として参照 |
| KYC 審査基準 | Markdown | ja | マスタ | 実質的支配者の身元確認書類は必須提出物 等 | Outline「KYC 審査基準」コレクション（`PC-05`） | KB 化せず都度読む（版が変わるため） |

- **入力言語の扱い**：提出書類は中国語が主体（現地企業の登記情報）。担当者とのやり取りは**入力言語で返す**（`CLAUDE.md` §2-5）。確認結果は日本語・中国語のどちらでも出せる（コンプライアンス部の運用に合わせる）
- **入力の欠け・曖昧さ**：申告書はあるが身元確認書類が無い等、部分的な提出は「裏付けが取れない点」として明示する。ネガティブ情報（`RS-01`）が無い場合は「ネガティブ情報のチェックは実施していません」と明示する

## 3. 観点（LLM に守らせる業務ルール）

- **確認できた点／裏付けが取れない点／追加で必要な書類を明確に分ける**：それぞれ根拠となった提出書類を示す
- **エスカレーションの要否は基準に照らして判定する**：Outline の KYC 審査基準に照らし、通常のフォローアップで足りるか、緊急エスカレーションが必要かを分ける。**この判定は「案」であり、コンプライアンス部内での確認を必ず促す**
- **実質的支配者の個人情報を最小限に扱う**：氏名・出資比率など審査に必要な項目のみを扱い、住所・連絡先・身分証番号は出力に転記しない（マスク済みの入力を前提とする。`PC-10`）
- **重大な懸念とそうでないものを混同しない**：単純な書類未提出（フォローアップで足りる）と、虚偽の疑いがある場合（緊急エスカレーション）を区別する基準を明示する
- **禁止**：ネガティブ情報の重要度を勝手に格上げ・格下げする／提出書類に無い情報を推測で埋める／個人情報を出力に転記する
- **不確実なとき**（入力言語で）：ja「この点は提出書類だけでは確認できません。追加の書類が必要です。」／zh「此点仅凭提交材料无法确认，需要补充材料。」
- **出力の粒度**：確認できた点 → 裏付けが取れない点 → 追加で必要な書類 → ネガティブ情報の参照 → エスカレーションの要否（案） → 確定前の確認

## 4. Dify 構成

- **アプリ種別**：**Workflow**（ファイルアップロード → 抽出 → 照合 → 結果）
- **ノード列**：
  1. `Start`（登記情報・申告書等のファイル）
  2. `Document Extractor`（PDF → テキスト）
  3. `Code`（**PC-10 のマスクスニペット**：身分証番号・電話番号・住所を `[ID]` 等に置換）
  4. `HTTP Request`（`RS-01` のネガティブ情報を取得。無ければ空）
  5. `Knowledge Retrieval`（KB `cv4-kyc-rules`。KYC 審査基準・エスカレーション基準）
  6. `LLM`（照合・エスカレーション要否の判定案。§5 のプロンプト）
  7. `Code`（検算：個人情報が出力に含まれていないかの検査）
  8. `Answer`
- **Knowledge**：`cv4-kyc-rules`（Outline「KYC 審査基準」を `PC-05` で同期。章単位チャンク、メタデータ `version`）
- **プラグイン／ツール**：`Document Extractor ノード`、`tools/paddleocr`（スキャンされた登記情報が混ざる場合。`../plugins-and-references.md` §1）、`Code` ノード（マスク）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（照合・判定）。**個人情報を扱うため、越境要件によっては `models/ollama` 等の自前モデルへの切替を検討**（`PC-08`・`PC-10` と同じ論点）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `client_id` | string | ✓ | 対象先（`data/world/fin/clients.csv` の記号） |
  | `files` | file[] | ✓ | 登記情報・申告書等 |
  | 出力 `confirmed` | string[] | ✓ | 確認できた点 |
  | 出力 `unverified` | string[] | ✓ | 裏付けが取れない点 |
  | 出力 `additional_docs` | string[] | ✓ | 追加で必要な書類 |
  | 出力 `escalation` | object | ✓ | エスカレーション要否（案） |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 コンプライアンス部の KYC スクリーニング担当です。
対象先（{{client_id}}）の提出書類（マスク済み。{{documents_json}}）を、KYC 審査基準（{{kyc_rules}}）に照らして確認します。
守ること：
1. 確認できた点・裏付けが取れない点・追加で必要な書類を明確に分け、根拠となった書類を示す。
2. 実質的支配者の個人情報（氏名・出資比率を除く住所・連絡先・身分証番号）は出力に書かない。入力は既にマスク済みだが、万一残っていても転記しない。
3. エスカレーション要否は KYC 審査基準に照らして判定するが、この判定は「案」であり、コンプライアンス部内での確認が必要と必ず明記する。
4. 単純な書類未提出（通常のフォローアップ）と、虚偽の疑いなど重大な懸念（緊急エスカレーション）を区別する。
5. ネガティブ情報（{{rs1_json}}）の重要度は与えられた分類をそのまま転記する。自分で格上げ・格下げしない。
6. 提出書類だけで確認できない点は「追加の書類が必要」と書き、推測で埋めない。
7. 言語：担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：確認できた点 → 裏付けが取れない点 → 追加で必要な書類 → ネガティブ情報の参照 → エスカレーションの要否（案）→ 確定前の確認 の順。
```

### 5-2. User テンプレート

```text
対象先={{client_id}}
提出書類（マスク済み・転記）：{{documents_json}}
ネガティブ情報（RS-01。無ければ「未実施」）：{{rs1_json}}
KYC 審査基準（Knowledge Retrieval 結果）：{{kyc_rules}}
```

### 5-3. 出力フォーマット

```json
{
  "client_id": "丙社",
  "confirmed": ["登記情報と申告書の代表者名が一致", "出資比率の記載が登記情報と整合"],
  "unverified": ["実質的支配者の公的な身元確認書類の写しが未提出"],
  "additional_docs": ["実質的支配者の身分証明書の写し"],
  "negative_info_ref": { "checked": true, "summary": "軽微な行政指導（環境規制・是正済み）。重大な懸念事項には該当しないと評価" },
  "escalation": { "level": "normal_followup", "reason": "書類未提出は常規審査基準上フォローアップの対象", "note": "コンプライアンス部内で確認してください" }
}
```

### 5-4. Few-shot

**不要**。対象先ごとに提出書類の状況が異なるため、書式は System と JSON スキーマで固定する。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 分類の正確性 | 確認済み／未確認の分類が正しい ≥ 95% | 評価セット 15 件を人手採点 |
| 個人情報の非転記 | 住所・連絡先・身分証番号の出力混入 0 | 負例セット（`PC-10`） |
| エスカレーション判定の妥当性 | 基準どおりのレベル判定 ≥ 90%、必ず「案」の明記 100% | 人手＋自動 |
| 越境なし | 判定の確定を断定する表現 0 | 禁止語 + LLM-as-judge |
| 言語 | やり取りは入力言語 100% | 自動判定（`PC-07`） |
| 拒否 | 未実施の明示 100% | 自動 |
| 速度 | p95 < 40 秒 | Langfuse |

- **評価方法**：リリース前にコンプライアンス部で 15 件（うち個人情報の負例 5 件）を人手採点

## 8. 別出しが必要なもの

- `PC-05`：「KYC 審査基準」コレクションの同期。版が変わるたびに反映されることが重要
- `PC-03`：登記情報・申告書の抽出。スキャン品質が低い場合は `tools/paddleocr`
- **`PC-10` の強化適用**：実質的支配者の個人情報を扱う唯一の RS/CV/FA サービスであり、マスクスニペットの適用と、越境（中国インフラのモデルに個人情報を渡してよいか）の法務確認が他サービスより優先度高
- **無くても動く範囲**：ネガティブ情報連携（`RS-01`）が無くても、提出書類の照合のみは動く

## 9. Outline Wiki との関係

- **読む**：「KYC 審査基準」コレクション（`PC-05`）
- **書く**：使わない。エスカレーション判定・確認結果は Wiki に残さず、コンプライアンス部の台帳（本番システム、未確定）に記録する運用を想定
- 提出書類そのものは Wiki に置かない（個人情報を含むため）

## 10. 未確定・リスク

- **実現性を ○ とした理由**：ファイルアップロード・抽出・照合は標準機能で足りるが、(1) 個人情報（実質的支配者情報）の越境可否の法務確認、(2) KYC 審査基準の Outline 整備状況、の 2 点が前提のため ◎ にしていない
- **越境の可否**：実質的支配者情報を中国側 SiliconFlow に渡してよいかは法務確認が必須（`PC-10`・`PC-08` と同じ論点）。NG の場合は `models/ollama` 等の自前モデルへ切り替える
- **エスカレーション先の台帳**：確認結果・エスカレーション判定を記録する台帳（コンプライアンス部専用）は未設計。`PC-17`（指摘・回答台帳）を KYC 領域に転用できるかは architect 判断
