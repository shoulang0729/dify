## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：サプライヤーから材料ロットの不具合疑い連絡、または社内で部品・材料の問題が見つかったとき（③業務フィードの `notify`）。**時間との勝負**（出荷停止・洋上分の連絡）
- **登場人物**：品質保証係長（照会・影響範囲の確定・初動指示）、物流（在庫隔離）、生産管理（ロット記録の正）、営業（顧客一報）、外部：サプライヤー S 社（発生元）、顧客 K 社・日本本社
- **いまの手順（Before）**：材料ロット→受入記録→生産日報の材料欄→生産ロット→出荷記録を 4 つの Excel／ERP 画面で人手追跡（2〜3 時間、手書き記録の欠落で不確実）→ 出荷先・数量を表にまとめ → 上司に報告してから隔離指示。洋上分の連絡が到着後になる
- **エージェント導入後の手順（After）**：
  1. 係長がキー（材料ロット／部品番号／サプライヤー名）を**入力**
  2. エージェントがキー種別を判定し、**`PC-04` のトレース API** で 材料ロット → 生産ロット → 製品・上位アセンブリ → 出荷先・出荷日・在庫 を展開（**トレース不能な経路は「不能」と明示**）
  3. **Code ノードで**数量を集計（生産数・出荷済・在庫・未使用材料）、状態区分（全数出荷／一部／洋上／在庫／未使用）を付与
  4. LLM が一覧表と「すぐ動くべき 3 点」（隔離・保留・先行連絡）を書き、規格 KB から該当条項を引く
  5. **人が決める場所**：影響範囲の確定、隔離・保留・出荷停止の指示、顧客への連絡内容は係長。**エージェントは在庫ステータスを変更しない**
- **成功の定義**：影響範囲の一次特定 2〜3 時間 → 10 分。トレース欠落が明示され、見落としによる追加連絡 0

- **入力言語の扱い**：質問の言語で答える（`CLAUDE.md` §2-5）。顧客への一報文は宛先言語（`reply_lang`）

## 3. 観点（LLM に守らせる業務ルール）
- **数量・展開は API と Code の結果を転記**。LLM が合算しない
- **トレース不能を隠さない**：紐付け `null` の生産ロットは「トレース不能」行として必ず出す。候補は「候補（未確認）」
- **状態区分は Code の値のまま**（全数出荷済／一部出荷／洋上／在庫／未使用材料／該当なし）
- **顧客一報は「事実と対応」だけ**：不具合の程度・原因・良否判定を書かない（判明していない）。判定は実測と規格（KB 条項）に基づき人が行う
- **「良品扱い可」を言わない**：測定結果が規格内でも、規格 KB の手順（ミルシート再発行・第三者測定）を引いて「判断前に必要なこと」を示す
- **禁止**：隔離・保留を実行したと書く／他顧客の情報を当該顧客向け文面に書く／規格値を記憶で書く（KB 引用のみ）
- **不確実時の定型文**：「{{as_of}} 時点の記録に基づく一次特定です。トレース不能 {{n}} 件があるため、影響範囲は生産管理と確認してください」
- **出力形式**：影響範囲表（製品／上位 ASSY／生産ロット／生産数／出荷先／出荷日／在庫／状態）＋すぐ動くべき 3 点＋トレース不能一覧＋（依頼時）顧客一報文。後工程は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（多輪：一報文、実測後の再判断を同じ会話で）
- **ノード列**：
  1. Start（`sys.query`／`reply_lang` select 任意）
  2. `tools/regex`（キー種別・値の抽出）→ If/Else（material_lot／part_no／supplier／不明→聞き返し）
  3. **HTTP Request（`PC-04` トレース API）**：`GET /trace?material_lot=…` または `?part_no=…`／`?supplier=…`（API 側で BOM 結合済みの展開結果を返す設計を推奨）。失敗 → Answer（接続失敗）
  4. **Code（`expand`）**：展開結果を正規化、数量集計、状態区分、洋上判定、トレース不能抽出、「すぐ動くべき」候補（未使用材料あり→隔離、在庫あり→保留、洋上あり→先行連絡）を規則で生成
  5. Knowledge Retrieval（`en-material-spec`：材料規格・許容差／顧客要求の材料不具合条項）
  6. LLM（`answer`）：表＋3 点＋不能一覧＋（intent により）一報文・判断前チェック（§5）
  7. Answer（会話変数 `trace_result`）／`tools/wecom`（隔離指示の送信は**人がボタンで実行**、任意）
- **Knowledge**：`en-material-spec`（Outline 同期：材料規格・許容差、顧客要求仕様の該当条項、初動手順書）。**BOM・ロット・出荷データは KB に入れない**（結合と鮮度が要る）
- **プラグイン／ツール**：HTTP リクエストノード・Code（本体）／`tools/regex`／DB 直結が要る場合は DWH 製品に応じて `tools/snowflake`／`oracle_ai_db` 等。MySQL/PostgreSQL の公式汎用は無い → 自前 API（`templates/06` 方式）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct。代替 DeepSeek-V3.x／`models/ollama`（顧客・出荷情報の越境回避）
- **参照 DSL**：**`../templates/06-text-to-sql-http-api-echarts.yml`**（lookup 型骨子）。事例：`../plugins-and-references.md` §11 知乎 ERP 在庫照会（`get_erp_stock` の型）
- **入出力変数**：`sys.query` string 必須／`reply_lang` select 任意／会話変数 `trace_result` object／出力 `answer` string

## 5. プロンプト
### 5-1. System（`answer`）
```text
あなたは青嶺精工 蘇州工場 品質保証課の BOM 逆引きアシスタントです。ERP/MES のトレース結果を Code ノードが整理した JSON を、影響範囲の一覧と初動の提案に変換します。
守ること：
1. 数量・展開・状態区分は JSON の値をそのまま転記する。合算・推定をしない。
2. untraceable（トレース不能）の行を必ず一覧に出す。候補は「候補（未確認）」と明記する。
3. 「すぐ動くべき」は JSON の actions を転記し、「〜を指示してください」の形で書く。自分が実行したと書かない。
4. 顧客への一報文を求められたら、事実（使用製品・数量・出荷日）と当社の対応（隔離・実測・報告予定）だけを書く。不具合の程度・原因・良否は書かない。
5. 良否判定を求められたら判定しない。spec（KB）から規格値と顧客要求の手順を引用し、「判断前に必要なこと」を列挙する。
6. 規格値・条項は spec にあるものだけ引用する。
7. 出力言語：質問の言語で答える。一報文は reply_lang（未指定なら質問の言語）。
8. 末尾に「{{as_of}} 時点の記録に基づく一次特定です。影響範囲は生産管理と確認してください」を入れる。
出力形式：「影響範囲」表 →「すぐ動くべき 3 点」→「トレース不能」→（依頼時）「一報文」または「判断前チェック」。
```
### 5-2. User テンプレート
```text
【質問】{{sys.query}}

【トレース結果（Code 出力・転記のみ、as_of={{expand.as_of}}）】{{expand.result}}

【前回の結果（多輪）】{{conversation.trace_result}}
【返信言語】{{start.reply_lang}}
```

### 5-4. Few-shot
- **ja**：質問「板厚不良の程度が分からないと、K 社に何て言えばいい？」＋ JSON（K 社向け 1,970 出荷、在庫 380）→ 一報文の要点：「S 社より材料ロットの調査連絡を受領。当該材料使用の貴社向け製品は SK-3310-A 1,970 個（8/28・9/5 出荷）と特定。当社在庫は隔離済み（指示後）。板厚実測を本日実施し 9/8 午前に報告予定」— 程度・原因は書かない
- **zh**：質問「测了 30 件全部在 1.16〜1.21，可以当良品处理吗？」＋ spec（下限 1.14、K 社 Rev.D §3.1）→ 「不做良否判定。判断前需要：① 向 S 公司确认卷料可疑位置（卷内板厚有波动，库存合格不代表 8/25 生产分合格）② K 公司 Rev.D §3.1 要求材料疑有不良时提供供应商材质单重发或第三方测量。建议保留库存至 S 公司调查结果」

## 8. 別出しが必要なもの（このサービス固有の準備）
- **ロットトレース API**（`PC-04`）：材料ロット⇄生産ロット⇄製品・上位 ASSY⇄出荷・在庫を**結合済みで返す**読み取り API。ERP/MES に無ければ台帳（Excel）を DB 化して薄い API。**これが本体（△ の理由）**
- **台帳の持ち方**：生産日報の「材料ロット」欄の**入力必須化**（手書き欠落がトレース不能の主因）。バーコード運用は現場側の準備
- **規格・顧客要求 KB**（Outline → `PC-05`）：材料規格・許容差、顧客要求の材料不具合条項、初動手順
- **出荷先・顧客情報のロール**（`PC-02`）
- **無くても動く範囲**：API が無い段階は**台帳 Excel（材料・生産・出荷）をアップロードして Code で結合**する「upload 版」で展開ロジックと出力形式を検証。デモ台本はこれで再現できる

## 9. Outline Wiki との関係
- **読む**：`PC-05` で「材料規格」「顧客要求仕様 抜粋（材料不具合手順）」「品質初動手順書」を KB `en-material-spec` に同期
- **書く**：しない。影響範囲一覧は QA-01（8D）の D2/D3 に人が持ち込む。会話ログは `PC-09` に残す

## 10. 未確定・リスク
- **ERP/MES のトレース粒度**（コイル内位置まで追えるか、日報の材料欄が電子か）— 未確定。推奨：まず「材料ロット⇄生産ロット」の 1 段だけ確実にする
- **洋上判定のルール**（出荷日＋リードタイム）：航路別に KB 化（NM-04 の `nm-ship-rules` と共用）
- **緊急時の可用性**：夜間・休日に使うため SiliconFlow 障害時のフォールバック（`PC-08`）と、API 失敗時の「手動手順」を UI に表示（`PC-16`）
- **通知の自動化**（`tools/wecom` で隔離指示）：AI が送るのではなく人がボタンで送る設計を推奨（`PC-14`）
- **成熟度**：st2 のまま。トレース API 接続と T01〜T07 通過で st1 候補
