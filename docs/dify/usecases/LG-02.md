## 1. 業務シナリオ
- **トリガー**：担当者が能動的に開く（本社から呼称の不一致を指摘されたとき、四半期ごとの用語集見直し）。定期実行（`routine`、月次）は `PC-11` で第 2 段階。Outline 横断の検出は OW-05（`../outline-wiki-usecases.md`）と統合
- **登場人物**：実行者＝用語集管理者、確認者＝各部署の代表（呼称の当事者：製造・保全・品質・本社生産管理）、受け手＝全員（周知文）
- **いまの手順（Before）**
  1. 会議で噛み合わない語に気づいてから、議事録・チャットを検索して出現例を集める（1〜2 日）
  2. 同じものかどうかを部署に聞いて回る（数日）
  3. 用語集（Excel）を更新し周知文を書く。周知後も旧呼称が残り、再周知の手間
  4. 用語集の版と実文書のズレを把握する手段がない
- **エージェント導入後の手順（After）**
  1. 【入力】対象文書（議事録・チャットログ・作業標準書一覧）を複数選択でアップロード（Outline コレクション指定は `PC-05`）
  2. 【生成】呼称の揺れ一覧（同一物候補ごとの別名・出現数・出典）、標準呼称案（ja/zh/en）と根拠（用語集 ID／図面名称／システム登録名）、用語集更新案（登録形式）、周知文ドラフト
  3. 【確認】管理者が「同一物」の判定を確認（AI の判定は候補）。部署代表に確認が要る組を対話で洗い出す
  4. 【決める】**標準呼称の決定と用語集の更新は用語集管理者**。AI は用語集を書き換えない。旧呼称の扱い（廃止／通称として併存）も人が決める
  5. 【周知】更新案を Outline「用語集 › 更新案」に下書き → 管理者が用語集本体へ反映 → 周知（`PC-14` は文面まで）
- **成功の定義**：揺れの発見から用語集更新まで 2 週間 → 3 日。本社会議での呼称起因の確認往復が減る（定性）。用語集の `candidate` が月次で処理される

- **入力言語の扱い**：文書は ja / zh 混在で受ける。一覧・更新案は **ja/zh/en の 3 列**で出す（用語集の形式）。対話（「深穴ラインを標準にしてはダメ？」）には**入力言語で返す**（§2-5）。周知文は指定言語（既定：現場向け zh）
- **入力の欠け・曖昧さ**：文書が 1 件だけでも動く（1 文書内の揺れ検出。st1 相当）。用語集が無いと「既存標準との照合」欄が空になる旨を表示。聞き返し文：「対象の文書を複数選択でアップロードしてください（zip は読めません）。Outline のコレクションを指定することもできます」／「请多选上传对象文件（无法读取 zip）。也可以指定 Outline 的合集」

## 3. 観点（LLM に守らせる業務ルール）
- 「同一物」の判定は**候補**として出し、根拠（同じ品番・同じ図面名称・同一文脈での言い換え）を必ず添える。根拠が弱いものは「要確認（部署代表）」に分ける
- 標準呼称案の根拠の優先順：①用語集の承認済み ②図面名称＋品番 ③本社システムの登録名 ④月次報告など公式文書の定義。**根拠なしの新造語を標準にしない**
- 出現数は Code の集計値をそのまま書く（LLM が数えない）。出典（文書名・行）を各別名に 1 件以上
- 旧呼称の扱いは「廃止」「通称として併存」の**選択肢**を示し、決めない。現場で通じている呼称を否定しない（併存案の提示）
- 部署によって**別物を指す同形語**（治具／夹具、红牌／红色标签）は「揺れ」ではなく「衝突」として別枠に出す
- 個人情報（`PC-10`）：チャットログの発言者は Code でマスク済み（`U001`）。**出力に発言者を書かない**（出典は文書名・行番号まで）。個人の言い間違いを特定する使い方をしない
- 不確実時の定型：「この組が同一物かどうか根拠が不足しています。部署代表（○○課）に確認してください」／「该组是否为同一事物依据不足，请与部门代表（○○科）确认」
- 出力形式：揺れ一覧（表：#／揺れている呼称（出現数）／同一物／標準呼称案 ja/zh/en／根拠／確認先）＋ 衝突一覧 ＋ 用語集更新案（登録形式）＋ 周知文 ＋ §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（file-list → iteration 抽出 → 集計 → 判定 → 1 回出力）。対話は `question` 付き再実行（前回 JSON を渡す）
- **ノード列**
  1. `start`：`files`（file-list、上限は環境設定）、`collection_ref`（任意、`PC-05`）、`domain`（分類フィルタ）、`question`（任意）, `prev_result`（任意）
  2. `iteration`（files、並列）：`document-extractor` → `code`（`PC-10` マスク・定型除去・行分割）→ `llm`（用語候補抽出：部品名・工程名・略語・設備名を JSON。**小型 Qwen3-32B**）
  3. `code`（集計・正規化）：表記ゆれの正規化（全半角・大小・記号）、出現数・出典集計、用語集 CSV との照合（既存標準あり／なし）、同形語の衝突検出
  4. `knowledge-retrieval`：KB `pc06-glossary`（定義・備考で同一物判定の補助）
  5. `llm`（判定・提案：Qwen3-235B）：同一物のクラスタリング候補、標準呼称案と根拠、確認先、旧呼称の選択肢
  6. `llm`（更新案・周知文）：登録形式の更新案、周知文（指定言語）
  7. `template-transform` → `end`
- **Knowledge**：`pc06-glossary`（用語 → 定義・備考。`tools/qa_chunk` で「用語→定義」の Q&A チャンク。`PC-06` が投入）。対象文書自体は KB にしない（都度アップロード。Outline 横断は `PC-05` が Markdown を渡す）
- **プラグイン／ツール**：`tools/dify_extractor`（多形式）、`tools/qa_chunk`（用語集 KB）。`tools/microsoft_excel_365`／`tools/jiandaoyun` は用語集の正本が Excel／简道云のとき（§10）。**zip 非対応**（Document Extractor の対応形式外）
- **モデル**：抽出は Qwen3-32B（84 文書＋3,000 行で数百回呼ぶ。コスト監視 `PC-09`）、判定は Qwen3-235B-A22B-Instruct。埋め込み `bge-m3`
- **参照 DSL**：`../templates/04-trilingual-consistency-checker.yml`（言語版の不一致列挙）、`../templates/02-long-document-chunk-iteration-translate.yml`（iteration の型）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `files` | file-list（docx/txt/csv/xlsx/md） | ✓（または `collection_ref`） | 対象文書 |
| `collection_ref` | string | — | Outline コレクション（`PC-05`） |
| `domain` | select | — | 分類フィルタ（製造／保全／品質 …） |
| `notice_lang` | select | — | 周知文の言語（既定 zh） |
| `question` | paragraph | — | 対話 |
| `variants_table` | string | 出力 | 揺れ一覧 |
| `conflicts` | array | 出力 | 同形語の衝突 |
| `glossary_updates` | array | 出力 | 登録形式の更新案 |
| `notice` | string | 出力 | 周知文 |
| `result_json` | object | 出力 | §5-3 |

## 5. プロンプト
### 5-1. System（判定・提案用）
```text
あなたは青嶺精工（蘇州）の用語集管理者を支援するアシスタントです。文書から抽出された用語候補と出現集計をもとに、同じものを別の名前で呼んでいる組（呼称の揺れ）を見つけ、標準呼称案を提案します。
守るルール：
- 「同一物」は候補として出し、根拠（同じ品番／同じ図面名称／同一文脈での言い換え）を必ず添える。根拠が弱い組は「要確認（部署代表）」に分ける。
- 標準呼称案の根拠は優先順で：①{{glossary}} の承認済み ②図面名称＋品番 ③本社システム登録名 ④公式文書の定義。根拠のない新しい語を標準にしない。
- 出現数・出典は {{stats_json}} の値をそのまま書く。数えない・推定しない。
- 旧呼称は「廃止」「通称として併存」の選択肢を示し、決めない。現場で通じている呼称を否定しない。
- 部署によって別物を指す同形語は「衝突」として別枠に出す（揺れではない）。
- 発言者・個人名を書かない。出典は文書名と行番号まで。
- 更新案は登録形式（term_id（新規は「新規」）／ja／zh／en／分類／備考（廃止・通称）／出典）。用語集の書き換えは行わない。
- 質問への回答は質問の言語で（日本語なら日本語、中国語なら中国語）。周知文は {{notice_lang}} で。
- 根拠不足の組は「この組が同一物かどうか根拠が不足しています。部署代表（○○課）に確認してください」と書く。
出力：JSON（指定スキーマ）→ 区切り線 → 揺れ一覧表 → 衝突一覧 → 用語集更新案 → 周知文。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 検出再現率 | 人手で既知の揺れ組の検出 ≥ 85% | 既知 20 組を埋めた評価セット |
| 判定精度 | 「同一物」候補の誤り ≤ 15%（要確認に分けられていれば可） | 管理者採点 |
| 集計 | 出現数が Code 集計と一致 100% | 自動 |
| 根拠 | 標準案の根拠付与率 100%、新造語 0 | 人手 |
| 言語 | 3 列出力、対話は入力言語、周知文は指定言語 100% | 自動判定（`PC-07`） |
| コスト | 100 文書＋5,000 行で LLM 呼び出しコストが予算内（値は `PC-08` で設定） | Langfuse（`PC-09`） |
| 速度 | 100 文書で 10 分以内（並列 iteration） | Langfuse |
| 安全 | 出力に発言者名・個人名 0 | 負例セット |

- **評価方法**：リリース前に匿名化した 3 か月分の実文書で管理者が採点。運用後は候補承認率と誤判定を月次で記録

## 8. 別出しが必要なもの
- `PC-06`：用語テーブル（`approved`/`candidate`/`status`/`owner`）、注入 CSV、定義 KB。**正本の所管は用語集管理者（生産技術）**。本サービスは `candidate` の主要な供給源
- `PC-05`：Outline コレクション横断の Markdown 取得（OW-05 と統合）、更新案の下書き
- `PC-10`：チャットログの発言者マスク規則（WeCom エクスポートの形式に合わせる）
- `PC-03`：多数文書の抽出（並列上限・文字列長 `CODE_MAX_STRING_LENGTH` の調整）
- `PC-04`（任意）：品番マスタ・図面名称・本社システム登録名の参照
- **無くても動く範囲**：数十文書のアップロード → 揺れ一覧＋更新案（Markdown）まで。Outline 横断・定期実行・マスタ参照は段階導入

## 9. Outline Wiki との関係
- **読む**：「用語集」（`PC-06` 正本）、対象コレクション（「会議録」「作業標準書」等）の Markdown（`PC-05`。OW-05「用語の不統一チェック（Wiki 横断）」と同一エンジン）
- **書く**：揺れ一覧と更新案を「用語集 › 更新案 › YYYY-MM」に**下書き**。管理者が確認して用語集本体（承認済み表）に反映し publish。**AI は用語集本体を編集しない**
- **用語集の正本を誰が持つか**：**用語集管理者（生産技術課）が Outline「用語集」コレクションで持つ**。Dify の KB・注入 CSV は派生物（`PC-06`）。部署代表は「確認先」として Outline のコメントで回答する
