## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（提案資料・与信審査資料に使うバリュエーションを作成した後）。③業務フィードには乗らない
- **登場人物**：市場業務部の担当者（レビューする側）、資料の作成者（営業第一部等。`CV-01` の候補企業比較で使った資料が題材になることもある）
- **いまの手順（Before）**：担当者が出来上がったバリュエーション資料を、比較企業の選び方・手法の適用・社内のレビュー基準に照らして手作業で点検する。基準からの逸脱に気づかず提出されることがある
- **エージェント導入後の手順（After）**：
  1. 出来上がったバリュエーション資料をアップロードする
  2. 比較企業の選び方・手法の適用・社内のレビュー基準に照らした点検結果が返る
  3. 担当者が**基準から外れている箇所の説明を用意し、資料を修正するかどうかを判断する**（AI は資料を修正しない）
- **成功の定義**：レビューにかかる時間が減り、社内基準からの逸脱（出所の未明示・共通要因の未調整等）が資料の提出前に見つかる

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| バリュエーション資料 | xlsx | ja / zh | 案件ごと 1 件 | 比較企業分析_候補先3社_2026-09.xlsx | 資料の作成者（`CV-01` 等） | `tools/dify_extractor`（行レコード化） |
| 社内レビュー基準 | Markdown | ja | マスタ | 実データと業界推計値を並べるときは出所を明示する 等 | Outline「バリュエーションレビュー基準」コレクション（`PC-05`） | 照合の基準として参照 |
| セクター共通要因（調整の根拠） | 数値 | — | 任意 | 原材料コスト+6%（`RS-02` の調査結果） | `RS-02` の出力（連携する場合） | 補正提案の根拠として利用 |

- **入力言語の扱い**：バリュエーション資料は日本語・中国語どちらもあり得る。**点検結果は日本語**が既定（担当者とのやり取りは入力言語に従う。`CLAUDE.md` §2-5）
- **入力の欠け・曖昧さ**：社内レビュー基準が Outline に無い場合は「レビュー基準が未整備のため、一般的な観点でのみ点検しています」と明示する

## 3. 観点（LLM に守らせる業務ルール）

- **比較企業の選び方を確認する**：実データのある与信先と業界推計値ベースの候補先が同じ表に並ぶ場合、出所（実データ／業界推計）が明示されているかを確認する
- **手法の適用を確認する**：セクター共通の要因（原材料コスト上昇等）が調整されずに単純比較になっていないかを確認する
- **社内基準との整合を確認する**：候補先が正式な与信先でない場合、「参考資料」である旨の注記があるかを確認する
- **基準から外れている箇所には修正案を示す**：「注記を追加する」「セクター共通要因を補正する」など、具体的にどう直せば基準を満たすかを示す
- **禁止**：バリュエーションの結論（数値そのもの）の当否を判断する（本サービスは手法・基準への照合が範囲で、数値の正しさそのものは判断しない）／資料を自動で修正する
- **不確実なとき**（入力言語で）：ja「社内レビュー基準が未整備のため、一般的な観点でのみ点検しています。」／zh「行内评审标准尚未健全，仅从一般观点进行检查。」
- **出力の粒度**：比較企業の選び方 → 手法の適用 → 社内基準との整合 → 基準から外れている箇所 → 説明の候補

## 4. Dify 構成

- **アプリ種別**：**Workflow**（ファイルアップロード → 抽出 → 照合 → 結果）
- **ノード列**：
  1. `Start`（バリュエーション資料 xlsx）
  2. `tools/dify_extractor`（行レコード化）
  3. `Knowledge Retrieval`（KB `fa5-valuation-standards`。社内レビュー基準）
  4. `HTTP Request`（`RS-02` のセクター共通要因を取得。連携する場合）
  5. `LLM`（照合・修正案の生成。§5 のプロンプト）
  6. `Code`（検算：数値の当否を判断する表現が無いかの禁止語チェック）
  7. `Answer`
- **Knowledge**：`fa5-valuation-standards`（Outline「バリュエーションレビュー基準」を `PC-05` で同期）
- **プラグイン／ツール**：`tools/dify_extractor`（`../plugins-and-references.md` §1）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `valuation_file` | file | ✓ | バリュエーション資料 |
  | `context_ref` | string | — | 元になった資料（例：`CV-01` の案件参照） |
  | 出力 `checks` | array[object] | ✓ | 比較企業の選び方・手法の適用・基準整合の点検結果 |
  | 出力 `deviations` | array[object] | ✓ | 基準から外れている箇所と修正案 |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 市場業務部のバリュエーションレビュー担当です。
出来上がったバリュエーション資料（{{valuation_json}}）を、社内レビュー基準（{{standards}}）に照らして点検します。
守ること：
1. 比較企業の選び方（実データ／業界推計の区別）、手法の適用（セクター共通要因の調整有無）、社内基準との整合（参考資料の注記有無）を確認する。
2. 基準から外れている箇所には、具体的な修正案（注記の追加・補正の方法）を示す。
3. バリュエーションの結論（数値そのもの）の当否は判断しない。手法・基準への照合が範囲であることを明示する。
4. 資料を自分で修正しない。修正案の提示にとどめる。
5. 社内レビュー基準が不足しているときは「レビュー基準が未整備のため、一般的な観点でのみ点検しています」と明示する。
6. 言語：点検結果は日本語。担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：比較企業の選び方 → 手法の適用 → 社内基準との整合 → 基準から外れている箇所 → 説明の候補 の順。
```

### 5-2. User テンプレート

```text
バリュエーション資料（Code 転記）：{{valuation_json}}
社内レビュー基準（Knowledge Retrieval 結果）：{{standards}}
セクター共通要因（RS-02。無ければ空）：{{rs2_json}}
参照案件（任意）：{{context_ref}}
```

### 5-4. Few-shot

**不要**。案件ごとに資料の内容が異なるため、書式は System と JSON スキーマで固定する。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 点検の網羅性 | 比較企業・手法・整合の3観点すべてに言及 100% | スキーマバリデータ |
| 修正案の具体性 | 各逸脱に修正案（誰が何をすればよいか）が付く 100% | 人手 |
| 数値当否の非判断 | バリュエーションの結論の妥当性を断定する表現 0 | 禁止語 + LLM-as-judge |
| 言語 | 点検結果は日本語、やり取りは入力言語 100% | 自動判定（`PC-07`） |
| 拒否 | レビュー基準未整備の明示 100% | 自動 |
| 速度 | p95 < 30 秒 | Langfuse |

- **評価方法**：リリース前に市場業務部で 10 件を人手採点

## 8. 別出しが必要なもの

- `PC-05`：「バリュエーションレビュー基準」コレクションの同期
- `PC-03`：バリュエーション資料の抽出
- `RS-02` のセクター共通要因を補正提案の根拠として利用（連携。台本参照）
- **無くても動く範囲**：レビュー基準・`RS-02` 連携が無くても、一般的な観点（出所の明示・注記の有無）での点検は動く

## 9. Outline Wiki との関係

- **読む**：「バリュエーションレビュー基準」コレクション（`PC-05`）
- **書く**：使わない。点検結果は資料の作成者へのフィードバックとして画面表示にとどめる

## 10. 未確定・リスク

- **実現性を ○ とした理由**：ファイルアップロード・照合・修正案の提示は標準機能で足りるが、(1) 社内レビュー基準の Outline 整備状況、(2) `FA-04`（モデル作成）や `CV-01`（提案資料）との入力連携の経路、の 2 点で ◎ にしていない
- **`FA-04` との関係**：バリュエーションを「作る」のは FA-04、「レビューする」のは FA-05（`docs/handoff/2026-09-08-finance-catalog.md` §2-1 の判定どおり）。両者が同じ資料形式（列構成）を前提にできるよう、入出力のスキーマを揃える必要がある
- **社内レビュー基準の粒度**：候補先の匿名化レベル（`CV-01` §10 と同じ論点）や、セクター共通要因の補正方法の詳細は基準の整備次第で変わる
