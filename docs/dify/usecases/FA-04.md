## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（決算開示を受けて、または前提の見直しが必要になったとき）。③業務フィードには乗らない（都度実行のため）
- **登場人物**：市場業務部の担当者（モデルを保守する側）、審査部（モデルの結果を与信評価の材料として使う）
- **いまの手順（Before）**：担当者が開示資料とデータフィードから財務モデルを Excel で個別に構築・更新する。前提を変えた箇所とその影響を追跡する仕組みが無く、履歴が残らない
- **エージェント導入後の手順（After）**：
  1. 開示資料とデータフィードをアップロードする（新規作成モード：初めてモデルを作る／決算反映モード：既存モデルに実績を反映）
  2. 実績が反映され、前提との差が示される
  3. 担当者が**前提を変えた箇所と、その結果どの数字が動いたかを確認する**（AI はモデルを確定・公開しない）
- **成功の定義**：モデル更新にかかる時間が減り、前提変更の履歴が残ることで説明責任を果たせる

- **入力の欠け・曖昧さ**：既存モデルの前提が無い（新規作成モード）場合は、開示資料・データフィードから初期の前提を作る。中国事業単体の数値が開示に無い場合は「モデルに直接反映できません」と明記する（`RS-03`・`RS-04` と同じ制約）

## 3. 観点（LLM に守らせる業務ルール）

- **実績と前提を明確に分ける**：開示資料から取得した実績値と、モデルの前提（推定値）を混同しない
- **前提の変更は履歴として残す**：どの前提を・いつ・なぜ変えたか（根拠：セクター調査等）を記録する
- **数値の計算は Code で行う**：前提から導かれる予測値の再計算は Code が行い、LLM は結果の解説のみを行う
- **中国事業単体の数値を推計しない**：開示に無い数値は「開示情報からは推計できません」と明記し、モデルに組み込まない
- **与信判断をしない**：モデルの結果（収益性の変化等）が与信評価にどう影響するかは断定せず、判断材料の提示にとどめる
- **禁止**：開示資料に無い数値をモデルに組み込む／前提変更の根拠を示さずに数値だけ変える
- **不確実なとき**（入力言語で）：ja「この項目は開示情報からは推計できません。モデルには反映していません。」／zh「该项目无法从披露信息中推算，未反映到模型中。」
- **出力の粒度**：反映した実績 → 前提との差 → 変更した前提（根拠付き） → 与信への含意（判断材料のみ） → 要確認

## 4. Dify 構成

- **アプリ種別**：**Workflow**（ファイルアップロード → 抽出 → モデル更新 → 結果）
- **ノード列**：
  1. `Start`（開示資料 PDF、データフィード CSV、`mode`：新規作成／決算反映）
  2. `Document Extractor`（PDF → テキスト）／`tools/dify_extractor`（CSV → 行レコード）
  3. `HTTP Request`（§8 のモデルストアから既存の前提・履歴を取得。新規作成モードなら空）
  4. `LLM`（軽量）— 開示資料から主要指標（売上高・営業利益率等）を抽出
  5. `Code`（実績と前提の差分計算。前提変更時の予測値再計算）
  6. `LLM`（本体）— 更新結果の解説・与信への含意の整理。§5 のプロンプト
  7. `HTTP Request`（§8 のモデルストアに今回の前提・実績・履歴を保存）
  8. `Answer`
- **Knowledge**：使わない（開示資料は都度アップロード、前提・履歴は§8のストア）
- **プラグイン／ツール**：`Document Extractor ノード`、`tools/dify_extractor`（`../plugins-and-references.md` §1）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（解説）／Qwen3-32B（指標抽出）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `client_id` | string | ✓ | 与信先の親会社（`data/world/fin/clients.csv` の記号） |
  | `mode` | select | ✓ | `new` / `update` |
  | `disclosure_file` | file | ✓ | 開示資料 |
  | `feed_file` | file | ✓ | データフィード |
  | `assumption_change` | object | — | 前提を変更する場合の指示（項目・新しい値・根拠） |
  | 出力 `actuals_reflected` | object | ✓ | 反映した実績 |
  | 出力 `assumption_diff` | array[object] | ✓ | 前提との差・変更履歴 |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 市場業務部の財務モデル保守アシスタントです。
与信先の親会社（{{client_id}}）の開示資料・データフィードから実績を反映し、既存の前提・履歴（{{model_state}}）との差を示します。
守ること：
1. 実績（開示資料からの数値）と前提（推定値）を明確に分けて書く。
2. 前提を変更するときは、どの前提を・いつ・なぜ変えたか（根拠）を必ず記録する。
3. 予測値の再計算は与えられた {{recalc_json}} をそのまま使う。自分で計算しない。
4. 中国事業単体の数値が開示に無いときは「開示情報からは推計できません」と明記し、モデルに組み込まない。
5. モデルの結果が与信評価にどう影響するかは断定せず、判断材料の提示にとどめる。
6. 言語：解説は日本語。担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：反映した実績 → 前提との差 → 変更した前提（根拠付き）→ 与信への含意（判断材料のみ）→ 要確認 の順。
```

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 実績と前提の分離 | 混同した記述 0 | 人手（負例含む） |
| 前提変更の記録 | 変更時に根拠・影響が付く 100% | スキーマバリデータ |
| 計算の非捏造 | 予測値が Code 再計算結果と完全一致 100% | 自動突合 |
| 推計の禁止 | 開示に無い中国事業単体の数値を作らない 100% | 負例セット |
| 与信判断の非断定 | 断定表現の出現 0 | 禁止語 + LLM-as-judge |
| 言語 | 解説は日本語、やり取りは入力言語 100% | 自動判定（`PC-07`） |
| 速度 | p95 < 40 秒 | Langfuse |

- **評価方法**：リリース前に市場業務部で 10 件を人手採点

## 8. 別出しが必要なもの

- **モデルストア**（本サービス固有・最優先）：与信先ごとにモデルの前提・実績・変更履歴を保存する小さなテーブル（`id`／`client_id`／`period`／`assumptions_json`／`actuals_json`／`change_log`）。次回実行時にここを読んで差分を出す。第 1 段階は `tools/microsoft_excel_365` の表でも代替できる
- `PC-03`：開示資料・データフィードの抽出
- `RS-02`・`RS-03`・`RS-04` の出力を前提根拠・実績データとして利用（連携。台本参照）
- **無くても動く範囲**：モデルストアが無くても「新規作成」モードでの単発分析は動く（継続的な保守・履歴管理ができないだけ）

## 9. Outline Wiki との関係

- 使わない。モデルの前提・履歴は数値の蓄積が中心で、Wiki のドキュメント形式より構造化ストアの方が扱いやすいため

## 10. 未確定・リスク

- **実現性を △ とした理由**：ファイルアップロード・抽出・差分計算は標準機能で足りるが、(1) モデルストアが新規に要る、(2) 「モデル」という継続的な成果物の版管理・確定フローが未設計、の 2 点でリスクが高いため。単発の決算反映だけなら ○ 相当だが、モデルの保守という性質上 △ とした
- **モデルストアの正本**：Excel か専用テーブルかは運用量による。まずは Excel で開始し、案件数が増えたらテーブル化する
- **`FA-05`（バリュエーションレビュー）との関係**：作る（FA-04）とレビューする（FA-05）は別サービス（`docs/handoff/2026-09-08-finance-catalog.md` §2-1 の判定）。両者が同じモデルストアを参照する設計は次の段階で詰める
