## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（新しい仕様書・追加モジュールの仕様が届いたとき）。③業務フィードでは `notify`（仕様の版更新・矛盾点の検知時）
- **登場人物**：仕様書を読む担当者（開発・審査・技術側の窓口）、仕様の発行元（システム部・設計部門）
- **いまの手順（Before）**：専門用語が多い仕様書を頭から読み、該当箇所を都度探す。エラーコードの対処が仕様書に無いと個別に確認が要り、仕様間の矛盾（初期値の記載が章によって異なる等）に気づかないまま運用に入ることがある
- **エージェント導入後の手順（After）**
  1. 仕様書の該当箇所についてチャットで質問する
  2. **根拠箇所を引用した回答**と、確認すべき点が質問の形で返る
  3. エラーコードを入力すると対処の候補が返る（仕様書に説明が無い場合はその旨を明示し、近い記載からの類推であることを示す）
  4. **仕様間の矛盾**（例：初期値の扱いが章によって異なる）が指摘される。**Q&A 欄への追記は候補として示し、送るかどうかは担当者が決める**
- **成功の定義**：仕様書の読解にかかる時間が減り、矛盾・未記載点が運用開始前に洗い出される

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 仕様書 | PDF / Markdown | ja / zh | 改定・新規モジュールごと | 「与信枠自動再算定機能」の章立て仕様書 | システム部・設計部門から受領 | `PC-03` でチャンク化（章単位）、メタデータ `doc_id`／`section`／`rev` |
| 質問文 | テキスト（チャット） | ja / zh | 1 人 1 日数件 | 「初期値は契約金額の何%？」 | 入力欄 | 言語判定・章の絞り込み |
| エラーコード | テキスト（コード） | — | 都度 | `ERR-402` | 入力欄 | エラーコード表（KB メタデータ）との照合 |
| エラーコード表・既知の対処 | Markdown / CSV | ja / zh | 更新は仕様改定時 | `ERR-401`「区分コード未登録」の対処（`data/world/fin/documents.csv`） | Outline または仕様書内の表 | KB へメタデータ `kind=error_code` で登録 |

- **入力言語の扱い**：ja / zh どちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。根拠文書が質問と異なる言語のときも、他言語の文書を根拠にしてよく「該当なし」とはしない（`implementation-guide.md` §6-1 補足）
- **入力の欠け・曖昧さ**：質問がどの仕様書・どの版を指すか特定できないときは候補（複数版がある場合）を提示して選ばせる。エラーコードが仕様書・エラーコード表のどちらにも無い場合は「未記載」と明示し、近い記載からの類推であることを断って対処候補を出す

## 3. 観点（LLM に守らせる業務ルール）

1. **回答には必ず根拠箇所（章番号・節番号）を引用する**。根拠の無い断定をしない
2. **仕様書に記載が無いエラーコードは「未記載」と明示する**。近い記載（類似のエラーコード等）から類推した対処を示すときは「類推」であることを必ず書く
3. **仕様間の矛盾は機械的な突合（章ごとの記載の食い違い）として指摘する**。どちらが正しいかを LLM が決めない。「どちらを正としますか」と確認を求める
4. **Q&A 欄への追記・仕様書の修正は行わない**。追記文の**案**を示し、送るかどうかは担当者が決める
5. **禁止**：仕様書に無い数値・条件を推測で埋める／複数版の仕様書の内容を混同する
6. **不確実なとき**：ja「該当箇所が見つかりません。対象の仕様書名と版を確認してください。」／zh「未找到相关内容。请确认对象规格书的名称与版本。」
7. **出力の粒度**：質問への回答（根拠引用つき）→ 確認すべき点（質問の形）／エラーコード対処候補（根拠の有無を明示）／矛盾点一覧（章番号ペア・優先関係の確認依頼）

## 4. Dify 構成

- **アプリ種別**：**Chatflow**（仕様書についての質疑応答が中心。同じ会話でエラーコード照会・矛盾点の一覧化まで続く）
- **ノード列**
  1. `Start`（`sys.query`）
  2. `Code`（PC-07 言語判定、質問文からエラーコードらしき文字列を抽出）
  3. `if-else`（エラーコードの照会か、通常の質問か）
  4. **通常の質問**：`Knowledge Retrieval`（KB `eg1-specifications`。メタデータ `doc_id`/`section`/`rev` でフィルタ）→ `LLM`（回答生成。§5-1）→ `Answer`
  5. **エラーコード照会**：`Knowledge Retrieval`（KB `eg1-error-codes`）→ `if-else`（該当コードがヒットしたか）→ `LLM`（対処候補の生成。ヒットしないときは近い記載からの類推であることを明示）→ `Answer`
  6. **矛盾点の一覧化**（担当者が明示的に依頼したとき）：`Code`（章ごとの記載を突合し、数値・条件の食い違いを機械的に検出。`PC-12` の `diff-core` を流用可）→ `LLM`（矛盾点の要約・Q&A 欄への追記案。§5-2）→ `Answer`
- **Knowledge**：`eg1-specifications`（仕様書本体、章単位のチャンク、メタデータ `doc_id`/`section`/`rev`）、`eg1-error-codes`（エラーコード表。メタデータ `code`/`kind=error_code`）。いずれも `PC-03`／`PC-05` 経由で投入
- **プラグイン／ツール**：`tools/mineru`（複雑レイアウトの仕様書 PDF）、Outline API（`documents.info` で読む、Q&A 欄への追記は `documents.update` の下書き）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（仕様読解・矛盾の要約）
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（質疑応答の型）、`../templates/04-trilingual-consistency-checker.yml`（矛盾点の突合に近い型）
- **入出力変数**：`sys.query` string ✓／出力 `answer` string・`citations` array（`doc_id`/`section`）・`error_code_result` object（任意）・`contradictions` array（任意）

## 5. プロンプト

### 5-1. System

```text
あなたは仕様書の読解を支援するアシスタントです。担当者の質問に、根拠箇所を引用して答えます。
守ること：
1. 回答には必ず根拠（文書名・章番号・節番号）を付ける。根拠の無い断定をしない。
2. 仕様書に記載が無いエラーコードは「未記載」と明示する。近い記載から類推する場合は「類推」と明記する。
3. 仕様間の矛盾を見つけたら、どちらが正しいかを自分で判定せず、担当者に確認を求める。
4. 仕様書の修正・Q&A欄への追記は行わない。追記文の案を示し、送るかどうかは担当者が決める。
5. 出力言語：利用者の入力言語。日本語なら日本語、中国語なら中国語。
6. 根拠が見つからないときは「該当箇所が見つかりません」と書き、対象の仕様書名・版の確認を求める。
```

### 5-2. User テンプレート

```text
【質問】{{sys.query}}
【検索結果（仕様書・エラーコード表）】{{context}}
【矛盾点の一覧化を依頼された場合、既に指摘済みの矛盾（重複回避）】{{known_contradictions}}
```

### 5-3. 出力フォーマット

```json
{
  "answer": "…", "citations": [ { "doc_id": "…", "section": "3.2" } ],
  "error_code_result": { "code": "ERR-402", "found": false, "analogy_from": "ERR-401", "candidate_action": "…" },
  "contradictions": [ { "sections": ["3.2", "3.4"], "issue": "初期値の優先関係が未定義", "needs_confirmation": true } ]
}
```

### 5-4. Few-shot

ja / zh を 1 組ずつ。「仕様書に記載の無いエラーコードを、近い記載から類推して答える」ケース（台本 `eg1` を実例に、`data/world/fin/documents.csv` の `ERR-401`／`ERR-402` を使う）。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 根拠の正確性 | 引用した章番号と回答内容が一致 ≥ 90% | 評価セット 30 件を人手採点 |
| エラーコードの正確性 | 未記載を「未記載」と正しく判定 100%（誤って断定しない） | 負例セット |
| 矛盾検出 | 既知の矛盾パターンの検出漏れ 0 | 評価セット（仕込んだ矛盾ペア） |
| 数値の非捏造 | 仕様書に無い数値・条件の作文 0 | 負例セット |
| 言語 | 入力言語で返答 100% | 自動判定（`PC-07`） |
| 速度 | p95 < 12 秒 | Langfuse |

- **評価方法**：リリース前に技術・審査部門で 30 件を人手採点。仕様改定のたび評価セットを追加

## 8. 別出しが必要なもの

- **仕様書・エラーコード表の KB 化（`PC-03`／`PC-05`）**：章単位のチャンク、メタデータ（`doc_id`/`section`/`rev`）の運用。エラーコード表は別 KB として持つ（照合を明確にするため）
- **矛盾検出のロジック**：`PC-12` の `diff-core`（版ペアの機械的 diff）を流用できるが、EG-01 は「同一版内の章間矛盾」を扱うため、対象が版ペアではなく章ペアになる点が異なる。共有できる部分（正規化・比較ロジック）は `PC-12` 側の実装時に確認
- **無くても動く範囲**：矛盾検出・Q&A 欄への追記候補が無くても「仕様書 Q&A・エラーコード照会」だけは動く

## 9. Outline Wiki との関係

- **読む**：仕様書本体・関連 Q&A のコレクションを `PC-05` で KB に同期
- **書く**：確認事項・矛盾点の追記案を仕様書の Q&A 欄へ下書きとして提案。**確定・追記の実行は担当者**が行う
- 使わない場合の理由：該当なし（読み書きとも使う）

## 10. 未確定・リスク
