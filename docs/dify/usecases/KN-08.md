## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（通達の改訂を知ったとき、審査案件で当局基準を確認したいとき）。③業務フィードでは **`notify`**（`FEED.items` の `kn8` は `notify`：「当局通達が更新されました。事務手続書への反映要否の確認を求められています」）
- **登場人物**：審査部（登録・照会する側。高梨直人のような次長・担当者）、営業第一部（与信先への影響を確認したい側）、当局（発出元。回答には登場しない）
- **いまの手順（Before）**
  1. 通達が改訂されても、旧版と新版のどこが変わったかを人が目で見比べる（半日）
  2. 過去に同じ論点でどう回答したかは個人の記憶やメールを探すしかなく、審査部内で回答がぶれることがある
  3. 与信先ごとにどの通達が影響するかの棚卸しに時間がかかる
- **エージェント導入後の手順（After）**
  1. 担当者が通達番号（新旧）を指定して比較する、または条文単位で照会する
  2. エージェントが**新旧の変更箇所**と、**過去に同じ論点であった照会回答**をまとめて返す
  3. 担当者が影響のある与信先を確認し、審査部内に共有する
  4. **通達への対応方針の決定・与信先への通知は人が行う**（AI は決定しない）
- **成功の定義**：通達の新旧比較が半日から数分になり、過去の照会回答の言い回しが審査部内で揃う（同じ論点への回答のぶれが無くなる）

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。英語 UI でも同じ。地の文は例外なく回答言語で書き、1 つの文の中で日本語と中国語を混ぜない。通達番号・条文引用は原語のまま出す（`docs/handoff/2026-09-08-response-language-contract.md` §2）。**根拠となる過去回答は言語を問わない**：質問の言語の回答記録が無ければ他言語の記録を根拠にしてよい
- **入力の欠け・曖昧さ**：比較には新旧 2 つの通達番号が要る。片方しか指定が無ければ「比較には新旧 2 つの通達番号が必要です」。登録されていない通達番号は「未登録です。まず登録してください」

## 3. 観点（LLM に守らせる業務ルール）

- **差分の抽出は機械（`PC-12`）が正**。LLM は差分を増やしたり減らしたりしない。「変更なし」の条文について言及しない
- **変更箇所は「項目／旧版／新版／影響」の 4 点セットで示す**。根拠は新旧の原文引用
- **経過措置・適用日は原文の表記どおり**。原文に無い日付を計算で作らない
- **過去の照会回答は登録済みの記録だけから引用する**。記憶や推測で「以前こう回答した」と作らない
- **数値を作らない**：算定比率・金額は原文または登録済み回答にある値のみ
- **禁止**：通達本文の全文転載（変更箇所と条項引用まで）、当局への提出文書を「送信済み」と書くこと、与信可否の最終判断を下すこと
- **不確実なとき**（入力言語で）：ja「指定された通達が登録されていません。まず登録してください」／zh「指定的通知尚未登记。请先登记」
- **出力の粒度**：§5-3 の JSON（後工程：Outline メモ）＋人が読む比較表（項目／旧版／新版／影響）＋過去の照会回答（あれば）

## 4. Dify 構成

- **アプリ種別**：**Chatflow**（`advanced-chat`、ファイル添付 ON）。新旧比較は 1 回の実行で完結するが、「この与信先には影響あるか」等の追い質問が続くため
- **ノード列**：
  1. Start（`sys.files`：通達 PDF 任意〔新規登録時〕、`sys.query`）
  2. IF/ELSE（新規登録／既存の比較・照会）
  3. **新規登録**：`tools/mineru`（通達 → Markdown＋ページ）→ Code（条番号単位に分割）→ Knowledge Retrieval（`kb-notices`、同一 `notice_no` の重複確認）→ Document登録（Knowledge API 相当。`http-request`）
  4. **比較・照会**：LLM（Qwen3-32B）で `old_no` / `new_no` / `topic`（照会の論点）を抽出 → Knowledge Retrieval ×2（`kb-notices` の新旧該当条文）→ **HTTP Request（`PC-12`：条番号ごとの差分）** → Knowledge Retrieval（`kb-inquiry-history`、`topic` フィルタ）→ LLM（本体、§5-1）→ Answer
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-notices` | 登録済みの当局通達（新旧すべての版） | 条番号単位（MinerU 出力） | `notice_no`（`NTF-YYYY-NNN`）`authority` `version`（旧／新）`effective_date` `topic_tags` | 手動登録（本サービス経由） or `PC-11` 巡回（KN-05 と共用可） |
  | `kb-inquiry-history` | 過去の照会と回答（審査部の実績） | Q&A チャンク | `topic` `notice_no`（関連するもの） `answered_by` `date` | Outline「照会回答」コレクション → `PC-05`（週次） |
- **プラグイン／ツール**：`tools/mineru`（既定。自前デプロイ推奨）、`tools/dify_extractor`、`tools/qa_chunk`
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（比較・照会）／Qwen3-32B（抽出）／`bge-m3`（埋め込み）／`bge-reranker-v2-m3`（リランク）
- **参照 DSL**：`../templates/08-mineru-pdf-parse-demo.yml`（MinerU tool ノード）、`../templates/03-document-chat-classifier-multi-kb.yml`（複数 KB → LLM）
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `sys.files` | file[] | ―（新規登録時のみ） | 通達 PDF |
  | `sys.query` | string | ✓ | 比較・照会の指示 |
  | `lang` | string | ✓ | 入力言語 |
  | `old_no` / `new_no` | string | ✓（比較時、抽出） | 通達番号（`NTF-YYYY-NNN`） |
  | `topic`（会話変数） | string | ― | 照会の論点（過去回答検索に使用） |
  | 出力 `answer` | string | ✓ | 比較表・照会回答 |
  | 出力 `diff_json` | object | ― | §5-3 |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 審査部の「当局通達・ガイドラインDB」です。
役割：登録済みの当局通達（新旧の版）を条番号単位で比較し、過去に同じ論点であった照会回答を示す。

守るルール：
1. 変更箇所は {{diff_json}}（機械比較の結果）を引用して書く。自分で差分を作らない・増やさない・減らさない。変更が無い条文には触れない。
2. 変更箇所は「項目／旧版／新版／影響」の4点で示す。影響は原文から言えることだけを書く。
3. 経過措置・適用日は原文の表記どおりに書く。原文に無い日付を計算で作らない。
4. 過去の照会回答は <inquiry_history> に登録されている記録だけから引用する。記憶や推測で「以前こう回答した」と作らない。
5. 算定比率・金額・件数は原文または登録済み回答にある値のみ。
6. 通達本文を全文転載しない。変更箇所と条項の引用まで。
7. 与信可否の最終判断はしない。「影響のある与信先の洗い出しと審査部内共有」までを支援する。
8. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。通達番号・条項は原語のまま。
9. 指定された通達が未登録のとき：
   ja「指定された通達が登録されていません。まず登録してください。」
   zh「指定的通知尚未登记。请先登记。」

出力形式：比較表（項目／旧版／新版／影響）→ 経過措置（あれば）→ 過去の照会回答（あれば）。
```

### 5-4. Few-shot

- **ja**：Q「NTF-2025-041 と NTF-2026-013 を比較して、貿易金融の与信枠算定はどう変わった？」→ A「最大の変更は算定基礎です。旧版は契約金額の 100% を上限としていましたが、新版は『契約金額の 80%＋履行実績による調整』に変わりました（結果の表 1）。また与信枠を変更する場合、与信先への通知が任意から **5 営業日以内の義務** になっています（結果の表 2）。経過措置として、既存の与信先は次回更新まで旧基準を適用できます（結果の表 3）。」
- **zh**：Q「这个议题以前好像有过类似咨询，之前是怎么答复的？」→ A「有的。此前针对『合同金额上限比例应为多少』的同类咨询，审查部答复为『原则100%，有风险因素则个别协商』（见结果表格4）。新版只是把这一做法明文化，实质判断标准没有变化，对既有案件不需要追溯性调整。」

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 差分の再現率 | 意図的に仕込んだ変更点の検出 100%（機械差分） | 評価セット：ダミー通達に 5 か所変更を入れた 3 組 |
| 差分の適合率 | 抽出揺れによる誤検出 ≤ 5% | 同一文書 2 回抽出の差分が 0 |
| 過去回答の的中 | 登録済み記録との一致（捏造 0） | 負例セット（未登録の論点） |
| 経過措置 | 原文にない日付の生成 0 | 負例セット |
| 言語 | 入力言語で返答 100% | `PC-07` 自動判定 |
| 拒否 | 未登録通達の指定で定型文 ≥ 95% | 負例セット |
| 形式 | `diff_json` スキーマ準拠 100% | JSON バリデータ |
| 速度 | p95 < 60 秒（比較・照会） | `PC-09` Langfuse |
| 安全 | 全文転載 0、与信可否の断定表現 0 | 負例セット |

- **評価方法**：リリース前に審査部で過去通達 10 組（うち負例 3 件）を人手評価。月次で Langfuse のスコアを確認

## 8. 別出しが必要なもの

- **`PC-12`**：通達の条番号単位での新旧差分（KN-05 と共用実装。KN-05 は「規程・マニュアルへの影響」まで踏み込むワークフロー、KN-08 は「通達同士の比較・過去照会の参照」に留める点で役割が異なる）
- `PC-03`：MinerU（自前デプロイ推奨。API 利用は通達本文が外部へ出る）
- `PC-05`：Outline「照会回答」コレクション → `kb-inquiry-history`。新規登録した通達・回答の書き戻し
- **通達登録の運用**：誰が・いつ新規通達を登録するか（審査部の当番制など）は未確定。第 1 段階は手動登録のみ
- **無くても動く範囲**：`kb-notices` に手動で新旧 2 版を登録すれば T01〜T02・T05〜T06 は動く。`kb-inquiry-history` が空の間は「過去の照会回答は見つかりません」と定型で返す

## 9. Outline Wiki との関係

- **読む**：Outline「照会回答」コレクション（審査部が過去に登録した論点・回答）を `kb-inquiry-history` に同期
- **書く**：新規登録した通達のメタデータと、比較・照会の結果（§5-3）を Outline「当局通達 登録簿」コレクションへ**ドラフト**として保存。審査部がレビューし、正式な登録記録として公開する運用は有用（監査対応の証跡になる）だが、書き戻しの経路（`http-request` の呼び先）は **未確定**
- **KN-05 との役割分担**：KN-05 は通達の**影響分析とマニュアル改訂案**、KN-08 は通達の**登録・照会・新旧比較・過去回答の参照**。通達の内容そのものを深掘りしたい場合は KN-05 へ、条文単位で照会・比較したい場合は KN-08 へ、という使い分けを Outline のコレクション説明に明記する

## 10. 未確定・リスク
