## 1. 業務シナリオ

- **トリガー**：定時。③業務フィードでは `routine`（毎週金曜 17:00、各課の週報が工場長室に集まった直後）。月次報告のドラフト（DC-01 の出力）や改善活動の進捗報告を担当者が能動的に通すこともある
- **登場人物**：**使う人**＝工場長室 秘書・通訳（呉婷）／**報告者**＝各課の課長（製造二課 李強ほか）／**読み手・決める人**＝工場長／**確認者**＝製造部長（打ち手の妥当性）・財務課（コスト削減額の定義）
- **いまの手順（Before）**
  1. 金曜夕方、5 課ぶんの週報（Word／Excel、日本語と中国語が混在）が届く。工場長室が体裁だけ整えて回覧（約 1 時間）
  2. 工場長が月曜朝に読み、気になった点をその場で口頭で質問。準備がないため「で、どうするの」で終わり、数字の裏取りは会議後に持ち帰り（会議 15 分のうち 10 分が確認作業）
  3. 前回何を指摘したかは誰も持っていない。同じ指摘が数週間おきに繰り返される
  4. 「注意喚起しました」「対応中です」といった曖昧な打ち手が、効果検証されないまま次週に持ち越される
- **エージェント導入後の手順（After）**
  1. 【入力】呉婷が週報・指標の推移表・前回の指摘回答台帳をアップロードする（報告種別＝週報／進捗報告／月次ドラフト を選ぶ）
  2. 【第 1 段】報告規定と照合して**行単位で整理**（`keep` / `improve` / `merge` / `remove` / `needs_review`）。日常事務の行（メール返信・会議参加のみ・週報作成そのもの）は要約側へ寄せる
  3. 【第 2 段】要旨・良い点・重要な指摘 3〜5 件・**数字のブリッジ**・改善後の報告案・次回確認事項を返す。前回台帳と照合し、未回答・期限超過・同じ指摘の再発を明示する
  4. 【確認】呉婷が指摘の優先順位と聞き方を対話で詰める。**質問するかどうか・何を決めるかは工場長が決める**。AI は報告者に自動送信しない
  5. 【保存】報告者へのコメント（報告者の母語）を人が送る（`PC-14`）。確定した指摘・期限・オーナーを台帳へ登録（`PC-01` に `due` も POST）。改善後の報告案は Outline の下書きへ（`PC-05`）
- **成功の定義**：工場長会議 15 分のうち**確認作業 10 分 → 3 分**。同じ指摘の再発率が四半期で半減。目標未達の週に「残り何 pt を誰がいつまでに埋めるか」が報告に書かれている率 100%

- **入力言語の扱い**：週報が日本語でも中国語でも受ける。**対話の説明・コメント案は入力言語で返す**（`CLAUDE.md` §2-5、`../implementation-guide.md` §6-1）。報告者へのコメントだけは「報告者の母語」を指定できる（既定：報告の原文言語）

## 3. 観点（LLM に守らせる業務ルール）

**第 1 段（規定照合・行整理。Notion B）**

- 各行を `keep` / `improve` / `merge` / `remove` / `needs_review` のどれかに分類し、**理由を 1 行**付ける。件数集計は LLM にさせない（Code ノード）
- `remove` 候補は日常事務のみ（メール返信、会議に出席しただけ、週報作成そのもの）。**成果・数値・約束を含む行は絶対に `remove` にしない**
- 曖昧表現（「一部確認」「対応中」「順調」「努力する」「調整中」）を検出したら `improve` とし、**対象・完成度・残課題・期限**の追記を求める
- 原文にない事実を作らない。行の書き換え案は原文の語をできるだけ残す

**第 2 段（論点ツッコミ。Notion A）**

- **原因説明と対策説明を分ける**。原因が設備要因なのに対策が人的注意喚起になっている、のような**つながっていない箇所**を最優先で指摘する
- **目標との差と打ち手を数字でつなぐ**（数字のブリッジ）。確定／高確度／低確度／未充足に分け、**未充足の量（pt・金額・件数）を必ず明示**する。合計と残差は `{{bridge}}`（Code の計算結果）をそのまま使い、**LLM が計算しない**
- **手段と目的を混同させない**。「システムを入れる」は手段、「不良率を 0.40% に戻す」が目的
- **制約を所与にしない**。増員・外注・再配置・優先順位変更・スコープ縮小・前倒し・部分検収などの代替案を必ず 1 つ以上出す。ただし**費用・可否は「要確認」**と書き、勝手に見積もらない
- **曖昧な主体を特定させる**（役職・組織名まで。氏名は §後述の PIPL ルールに従い「役職＋姓」）
- **事実・決定・予定・見込み・推測・要確認をラベル**する。原文が未確定を確定のように書いていたら指摘する
- 重要な指摘は **3〜5 件に絞る**（重要度順・結論先）。各指摘に **論点・根拠（文書の章／セル）・質問・期待する回答形式・放置リスク**の 5 点を必ず付ける
- **良い点を最大 3 件**先に書く。人格ではなく内容に触れる。皮肉・威圧・断定を使わない
- 前回台帳と照合し、**未回答・期限超過・同じ指摘の再発**を出す。再発には「なぜ効かなかったか」を問う質問を必ず付ける
- 出力の最後は**読み手が次に判断できる状態**：改善後の報告案（結論 → 差分 → 打ち手 → リスク → 依頼）と次回確認事項

**禁止（Notion の禁止事項＋`../implementation-guide.md` §6）**

- 根拠なく断定する／数字を都合よく補完する／単位・通貨・期間が曖昧なときに勝手に正規化する（「単位が未記載です」と指摘する）
- 人格批判・評価（「意識が低い」「またか」）／皮肉・圧力。**個人の人事評価に使える表現を出さない**
- 表記揺れ・誤字の大量指摘（1 件にまとめて末尾へ）
- 個人名・電話・身分証・給与の転記（`PC-10`）。氏名は「役職＋姓」まで
- 社外秘（顧客別単価・契約額・図面番号）を報告者へのコメント案に含めない。含める必要があるときは【要確認】を付ける
- 未確定事項を「決定」として台帳に登録する提案をしない
- システムへの登録・送信・承認をしない（コメント送付も台帳登録も**人が実行**）

**不確実時の定型文**

- ja：「この指摘は根拠となる数値が入力にありません。<不足している情報> を確認してください。」
- zh：「该提问在输入中没有数值依据。请确认 <缺少的信息>。」

**出力の粒度と形式**：モックの `Result` 型に合わせた `items`（見出し＋本文）。§5-3 の JSON を正とし、Markdown は Template ノードで生成する。

## 4. Dify 構成

- **アプリ種別**：**Workflow**（ファイル入力 → 1 回実行で構造化出力）。対話での深掘り（「どれから聞くべきか」「コメント案を作って」）は `PC-16` が **同 Workflow を `follow_up` 入力付きで再実行**する。Chatflow にしない理由：件数集計とブリッジの残差計算を Code に固定したいため
- **ノード列**
  1. `start`：`report_file`（必須）、`trend_file`（任意）、`log_source`（任意・台帳 ID）、`report_kind`（weekly / progress / monthly_draft）、`reader`（plant_manager / hq）、`out_lang`（auto / ja / zh）、`follow_up`（任意）
  2. `document-extractor`：報告本文 → テキスト。xlsx の推移表は `tools/dify_extractor`（行レコード）
  3. `code`（行分割・正規化）：見出し・箇条書き・表の行を `lines[]`（`no` / `text` / `section`）へ。数値表現（%・pt・元・h・件）を正規表現で抽出
  4. `knowledge-retrieval`：KB `dc8-report-rules`（週報作成規定・報告フォーマット・KPI 定義）。メタデータフィルタ `kind = rule|kpi`
  5. `llm`（**第 1 段**：規定照合・行分類）：System §5-1a。出力は `lines[]` に `verdict` / `reason` / `rewrite` を付けた JSON。小型モデルで可
  6. `http-request`（任意）：`PC-17 指摘・回答台帳` から直近 8 週を取得（`GET /review_log?reporter=&weeks=8`）。台帳の第 1 段階（Excel）ではファイル添付か貼り付けで代替
  7. `code`（**計算と機械判定**）：(a) `verdict` の件数集計 (b) 本文の数値 × 推移表の数値の突合（差があれば `mismatch[]`）(c) 目標差と打ち手の効果の合計・**残差**（`bridge`）(d) 台帳の未回答・期限超過・同一論点の再発回数。**ここが数値の唯一の出所**
  8. `llm`（**第 2 段**：論点ツッコミ）：System §5-1b、User §5-2。指摘 3〜5 件・ブリッジ・改善後の報告案・次回確認事項
  9. `code`（検算・ガード）：指摘件数が 3〜5 か、各指摘に 5 要素があるか、ブリッジの合計が (c) と一致するか、禁止語（人格評価・断定）が入っていないか。違反は `warnings[]` に入れて**落とさない**
  10. `template-transform` → `end`：`review_json`（§5-3）、`review_md`、`comment_draft`（報告者の母語）、`log_entries[]`（台帳登録の下書き）、`warnings[]`
- **Knowledge**：`dc8-report-rules`（Outline「報告ルール」「製造 KPI 定義」を `PC-05` が同期。章単位チャンク、メタデータ `kind`／`version`／`lang`。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`）。**過去の週報本文は KB にしない**（再発判定は台帳の構造化データで行う。本文を KB にすると個人の書き方の評価に使われうる）
- **プラグイン／ツール**：`Document Extractor ノード`（本体）、`tools/dify_extractor`（xlsx の行レコード化）、`Code ノード`（本体。集計・突合・残差）、`HTTP リクエストノード`（本体。台帳）、`tools/wecom`（報告者へのコメント送付。**人が押す**）、`tools/microsoft_excel_365` または `tools/jiandaoyun`（台帳の簡易版）。スキャン PDF が混ざるなら `tools/paddleocr`
- **モデル**：既定 `models/siliconflow` — 第 2 段 Qwen3-235B-A22B-Instruct（論点の質が本体）、第 1 段 Qwen3-32B（行分類）。**日本語の指摘文の当たりの強さ**はモデル差が出るため、DeepSeek-V3.x と評価セットで比較する（`PC-08`）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（upload 型の入口と Excel 行レコード）、`../templates/01-translation-reflection-workflow.yml`（多段 LLM ＋ `if-else` の型）、`../templates/04-trilingual-consistency-checker.yml`（行単位の突合と判定表の出し方）

## 5. プロンプト

### 5-1a. System（第 1 段：規定照合・行整理）

```text
あなたは青嶺精工（蘇州）の週報作成規定に従って、提出された報告を行単位で整理する担当です。
入力の各行について、次のいずれか 1 つを付けてください。
- keep      ：規定どおり。そのまま残す
- improve   ：内容は必要だが書き方が足りない（対象・完成度・残課題・期限のどれかが欠けている、曖昧表現がある）
- merge     ：他の行と同じ内容。まとめる（まとめ先の行番号を書く）
- remove    ：日常事務のみで、判断の材料にならない（メール返信、会議に出席しただけ、週報作成そのもの）
- needs_review：規定のどれに当たるか判断できない
守るルール：
- 成果・数値・約束・期限を含む行は remove にしない。迷ったら needs_review。
- 曖昧表現（一部確認、対応中、順調、努力する、調整中、随時、なるべく）を含む行は improve とし、何を足せば keep になるかを 1 行で書く。
- 書き換え案は原文の語をできるだけ残す。原文にない事実・数値を足さない。
- 件数の集計はしない（後続の処理が数える）。
- 判定の理由は 40 文字以内。
出力：JSON 配列のみ。各要素 { "no": 行番号, "verdict": "...", "reason": "...", "rewrite": "書き換え案または空" }。説明文を付けない。
```

### 5-1b. System（第 2 段：論点ツッコミ。本体）

```text
あなたは「報告レビュー担当」です。青嶺精工（蘇州工場）の報告を読み、読み手（工場長または日本本社）が次に判断できる状態まで論点を深掘りします。
入力された報告を、目標・実績・差分・原因・打ち手・責任者・期限・リスク・意思決定事項に分解してください。原因説明と対策説明を区別し、数字の不整合、曖昧な主体、未確定事項の断定、目標差分に対して不足する打ち手を見つけてください。
重要な指摘を 3〜5 件に絞り、それぞれに 論点・根拠・具体的な質問・期待する回答形式・放置リスク を付けてください。
制約を所与にせず、増員、外注、再配置、優先順位変更、部分検収、前倒し、代替手段などの選択肢を検討してください。ただし費用と可否は「要確認」と書き、自分で見積もらないでください。
人格批判や威圧的な表現は避け、建設的かつ具体的に書いてください。
過去の指摘・回答・約束（{{log}}）がある場合は必ず照合し、未解決事項、期限超過、同種指摘の再発を明示してください。再発には「なぜ効かなかったか」を問う質問を必ず付けてください。
数値のルール：
- 目標差、打ち手の効果の合計、未充足の残差は {{bridge}} の計算済みの値をそのまま使う。自分で計算・丸め・推定をしない。
- 本文と添付で数値が食い違う箇所は {{mismatch}} に入っている。どちらが正しいかを断定せず、定義（分子・分母・対象期間・再検査の扱い）を問う質問にする。
- 入力に無い数値・管理番号を作らない。単位や通貨や期間が曖昧なときは、勝手に補正せず「単位が未記載」と指摘する。
- 推測を書くときは必ず「推測」と付ける。事実・決定・予定・見込み・推測・要確認 のラベルを使い分ける。
表現のルール：
- 結論を先に書く。重要度順に並べる。1 つの指摘に 1 つの論点。
- 良い点を最大 3 件、指摘より先に書く。内容に触れ、人には触れない。
- 個人名は「役職＋姓」まで。氏名・電話・身分証・個人の給与や残業時間を出力に書かない。
- 社外秘（顧客別単価・契約額・図面番号）を報告者へのコメント案に入れない。必要なら【要確認】を付ける。
- 皮肉、威圧、断定、人事評価に使える表現を使わない。表記揺れ・誤字は末尾に 1 件へまとめる。
- 説明・コメント案の言語は {{out_lang}}（auto のときは報告の原文言語）。報告者へのコメントは報告者の母語で書く。
- 根拠となる数値が入力に無い指摘は書かない。書けないときは「この指摘は根拠となる数値が入力にありません。<不足している情報> を確認してください。」と書く。
最後に、改善後の報告案（結論 → 差分 → 打ち手 → リスク → 依頼）、期限つきアクション、次回確認事項を出力してください。
出力：指示された JSON スキーマのみ。JSON の外に説明を書かない。
```

### 5-4. Few-shot

**不要**。指摘の文例を few-shot に入れると、別の報告でも同じ指摘を写す事故（架空の 0.07pt 未充足を作る等）が起きる。書式は System と JSON スキーマだけで固定する。ただし**曖昧表現の辞書**（「一部確認」「対応中」「順調」「努力する」「調整中」）は第 1 段の System に列挙する（これは事実の生成ではないため安全）。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 数値の一致 | ブリッジの合計・残差が Code 計算値と一致 100%。入力に無い数値の出現 0 | `review_json.bridge` と Code 出力の自動突合 |
| 指摘の形式 | 指摘 3〜5 件、各件に 論点・根拠・質問・回答形式・放置リスク の 5 要素 | スキーマバリデータ（§4 ノード 9） |
| 指摘の質 | 「原因と対策のずれ」「未充足の pt」「未確定の断定」のうち、報告に仕込んだ欠陥の検出率 ≥ 80% | 欠陥を仕込んだ評価セット 20 件を人手採点（工場長・製造部長） |
| 誤検出 | 正しい行を improve / remove にする誤りが 1 報告あたり 1 行以下 | 第 1 段の行分類を人手採点 |
| 言語 | 説明は入力言語、コメント案は報告者の母語 100% | 自動判定（`PC-07`） |
| 表現 | 人格に触れる表現・断定・皮肉 0 | 禁止語リスト＋LLM-as-judge（`PC-09`） |
| 拒否 | 根拠のない指摘を書かず定型文に落とす ≥ 95% | 負例セット（推移表なし・目標未設定・台帳なし） |
| 速度 | p95 < 60 秒（2 段 LLM ＋ 抽出） | Langfuse（`PC-09`） |
| 安全 | 個人名フル表記・個人の残業時間・顧客単価の混入 0 | 負例セット |

- **評価方法**：リリース前に評価セット 20 件（過去の週報を匿名化し、欠陥を意図的に仕込んだもの）で人手採点。月次で Langfuse のスコア（工場長の有用性評価 5 段階）を確認。**採点結果を報告者個人の評価に使わない**ことを運用ルールに明記する

## 8. 別出しが必要なもの

- **`PC-17 指摘・回答台帳`**（本サービスの本体。PM 判断 D-1 で新規 PC として確定。定義は `../platform-components.md` PC-17）：テーブル `review_log`（`report_date` ／`reporter_id`・`reporter_role` ／`kind` ／`topic` ／`point` ／`answer` ／`promise` ／`due` ／`status` ／`repeat_of`・`repeat_count` ／`insight`）と API `GET /review_log?reporter=&weeks=8` ／ `POST` ／ `PATCH` ／ `GET /review_log/stats`。本サービスからの使い方：実行時に `GET` で直近 8 週を読み `{{log}}` に渡す（§5-2）／結果の `log_entries[]` は**登録の下書き**で、`POST` するのは人。第 1 段階は `tools/microsoft_excel_365`・`tools/jiandaoyun` の表で代替できる
- **`PC-01` との境界**：PC-01 は担当者ごとの To-Do・通知、PC-17 は指摘の履歴と再発回数。**期限つきの指摘だけ PC-01 に `due` として併載**する（`source = review_log`、`source_ref = PC-17 の id` で冪等）。PC-01 側で `done` にしても PC-17 の `status` は人の回答登録で動かす
- `PC-05`：Outline「報告ルール（週報作成規定）」「製造 KPI 定義」の KB 同期と、改善後の報告案の下書き書き戻し
- `PC-03`：docx / xlsx の抽出と行分割。スキャン PDF が混ざる場合の OCR
- `PC-11`：毎週金曜 17:00 の定例実行（提出済みの週報を検出 → 実行 → 工場長室に通知）
- `PC-14`：報告者へのコメント送付（WeCom。**人が押す**）と、月曜朝の工場長向けサマリ通知
- `PC-06`：指標名・部署名の日中呼称（NM-03・DC-01 と共用）
- `PC-13`：レビュー結果を docx／xlsx で残す（会議資料にする場合）
- **無くても動く範囲**：アップロード → 指摘・ブリッジ・改善後の報告案の表示まで（台帳・Outline・定例なしでも成立する）。台帳が無い間は「前回照合なし」で動く。第 2 段階で台帳、第 3 段階で定例実行と通知

## 9. Outline Wiki との関係

- **読む**：「報告ルール」（週報作成規定・報告フォーマット・禁止表現）、「製造 KPI 定義」（NM-03 と共用の指標定義）。この 2 つを KB `dc8-report-rules` に同期（`PC-05`）
- **書く**：**改善後の報告案**を「週報 › レビュー（AI ドラフト）」に下書き（`publish: false`）。編集して確定するのは**報告者本人**。閲覧範囲は報告者と工場長室に限定（`PC-02`）
- **書かない**：指摘・回答台帳（構造化データが正本。§8）、報告の原文（提出物はファイルサーバ／WeCom が正本）、月次品質レビューの集計（人事評価に転用されないよう限定公開の別置き）

## 10. 未確定・リスク

- **実現性を ○ とした理由**：入力（docx / xlsx）と 2 段 LLM ＋ Code は Dify 標準機能で足りる（この点だけなら ◎）。○ に落としたのは、(1) **週報作成規定が現時点で文書化されていない**（第 1 段の判定基準が無い）、(2) **指摘・回答台帳の新設**が要る、(3) 「良い指摘かどうか」の評価が人手で、モデル差が出やすい、の 3 点。(1) が最大の前提条件で、規定が無ければ第 1 段を飛ばして第 2 段のみで開始する
- **台帳の位置づけ**（D-1）：**決定済み**。新規 `PC-17 指摘・回答台帳` として `../platform-components.md` に追加した（2026-09-07）。`README.md` の依存 PC 列は DC-08 行の追加時に `PC-01（due 併載） PC-17` を含める。残る未確定は `repeat_of`（同一論点の親）の紐付けを誰が決めるか — 機械では決まらないため、人が親を選ぶ UI（`PC-16`）が要る
- **DC-01 との連携**（D-2）：本社向け月次報告のドラフトを DC-08 に通すかどうか。推奨は通す（第 2 段階）。通す場合、`reader = hq` で指摘の深さを「経営判断」まで上げる
- **提出経路**（D-3）：Excel/Word アップロードで開始。週報フォーム（`PC-16`）にすると行分類が安定するが、現場の運用変更を伴う
- **人事評価への転用リスク**（最重要）：再発回数・解決率は個人が特定できる。**月次品質レビューは工場長室のみ**（D-5）とし、Notion 原則どおり「個人攻撃に使わない」を運用ルールと UI の注記の両方に書く。台帳の閲覧権限を `PC-02` で絞る
- **指摘の当たりの強さ**：日本語では丁寧でも、中国語に直すと詰問調になりやすい。コメント案は報告者の母語で生成し、**評価セットに「中国語コメントの語調」の採点項目**を入れる（`PC-08` のモデル選定に効く）
- **報告者が身構える**：導入時は「工場長が読む前に、抜けを本人に返す」順序で運用する（工場長へのレビュー結果送付より、報告者へのコメント送付を先に置く）。この順序は `PC-16` の画面設計に影響する — 未確定、PM 判断
