## 1. 業務シナリオ

### 1-1. モードという考え方

このサービスは「報告を読む AI」を 1 つ持ち、**3 つの選択でふるまいを切り替える**。

```
モード ＝ 報告種別（何の報告か） × 誰が誰に出すか（書き手 → 読み手） × 目的（提出前 / 受領後）
```

| 目的 | 誰に返すか | 何を返すか | 何を返さないか |
|---|---|---|---|
| **提出前セルフチェック**（`pre_submit`） | **書いた本人** | 規定との照合、行の整理（そのまま / 書き足し / 統合 / 削除候補 / 判断保留）、曖昧表現の直し方、必須項目の欠落、改善後の報告案 | 読み手向けの論点、数字のブリッジ、台帳照合（本人がその場で直せる範囲に絞る） |
| **受領後の論点整理**（`post_receipt`） | **報告を受け取った人（読み手）** | 要旨、良い点、確認したい論点 3〜5 件、数字のブリッジ、前回台帳との照合、改善後の報告案、次回確認事項 | 書き方の助言（誤字・表現の細かい直し。末尾に 1 件へまとめるのみ） |

- **語調**：`pre_submit` は「本人への助言」（〜すると規定を満たします）。`post_receipt` は「読み手が使える問い」（〜を確認してください）。どちらも人格に触れない・皮肉を使わない（§3 の禁止）
- **モードで変わるもの**：System への差し込み（追加観点・語調・出力テンプレ）と、出力ブロックの取捨だけ。**ノード構造・入出力変数・Code の計算は共通**（§4）

### 1-3. 業務の流れ

- **トリガー**：定時（③業務フィードでは `routine`。毎週金曜 17:00＝週報、月初 3 営業日＝月次）と、担当者からの随時実行（障害報告・クレーム報告は発生ベース）
- **登場人物**：モードごとに変わる（§1-2）。デモのペルソナは工場長室 秘書・通訳（呉婷）＝ `post_receipt` の代表利用者
- **いまの手順（Before）**
  1. 提出前：書き手は規定を読み返さずに前回のコピーを直して出す。日常事務が本文を占め、期限や担当が抜ける
  2. 受領後：読み手は当日その場で読み、「で、どうするの」で終わる。数字の裏取りは会議後に持ち帰り
  3. 前回何を確認したかは誰も持っていない。同じ確認が数週間おきに繰り返される
  4. 報告種別が違っても同じ様式で書かれ、障害報告に顧客連絡欄が無い・人事報告に判断期日が無い、といった抜けが起きる
- **エージェント導入後の手順（After）**
  1. 【モード選択】報告種別・書き手→読み手・目的を選ぶ（既定値は利用者の所属と直近の実行から補完）
  2. 【入力】報告本文（貼り付け or ファイル）＋任意で指標の推移表・前回の台帳
  3. 【第 1 段】報告規定（種別ごと）と照合して**行単位で整理**
  4. 【第 2 段】モードの追加観点を差し込んで論点を作る。`pre_submit` は書き手向けの助言、`post_receipt` は読み手向けの問いに整形
  5. 【確認】人が優先順位と聞き方を詰める。**AI は送信も台帳登録もしない**（人が実行）
- **やらないこと**：報告の自動送信、台帳への自動登録、個人の評価・ランキング（§10）

## 3. 観点（LLM に守らせる業務ルール）

### 3-1. 共通観点 A〜H（全モードで必ず見る）

| | 観点 | 見るところ |
|---|---|---|
| A | 目標・差分 | 目標が書かれているか。実績との差が数字で示されているか |
| B | 数字の整合性 | 本文と添付、章と章で数字が食い違っていないか。定義（分子・分母・対象期間）が固定されているか |
| C | 事実と解釈 | 事実・決定・予定・見込み・推測・要確認が混ざっていないか。未確定を確定のように書いていないか |
| D | 打ち手の具体性 | **原因説明と対策説明がつながっているか**。効果・確度・実施日・オーナーがあるか |
| E | 制約と代替案 | 「承認されないので対策できない」で止まっていないか。増員・外注・再配置・優先順位変更・スコープ縮小・前倒しの代替案があるか |
| F | 主体・責任 | 「関係者で」「順次」といった曖昧な主体になっていないか。役職・組織まで特定できるか |
| G | リスク・依存関係 | 前提が崩れたときの影響。他部門・外部への依存 |
| H | 報告表現 | 曖昧語（一部確認・対応中・順調・努力する・調整中・随時・なるべく）、主語なし、結論が最後 |

- **深さ 5 段階**：確認 → 差分 → 打ち手 → 代替案 → 経営判断。読み手が経営・本社のときは「経営判断」まで、組織長のときは「代替案」までを既定にする
- **原則**：①原因説明と対策説明を分ける ②不足分と補填策を数字でつなぐ ③手段と目的を混同させない ④制約を所与にしない ⑤曖昧な主体を特定する ⑥未確定を確定のように書かせない ⑦読み手が次に判断できる状態を作る

### 3-2. 報告種別ごとの追加観点（一般レベル。顧客が §8 で差し替える）

> 各 3〜5 個まで。**多くしない**。増やすと共通観点の指摘が押し出される。

| 報告種別 | 追加観点 |
|---|---|
| 担当週報 | ①予定と実績の差が書かれているか ②未完了の理由（自分の都合か他律か）③来週の予定に期限があるか ④日常事務（メール返信・会議出席のみ・週報作成）が本文を占めていないか |
| 組織長週報 | ①部門 KPI の目標差 ②打ち手の効果の合計と**残差** ③担当報告の寄せ集めになっていないか（組織長としての判断が書かれているか）④今週決めること・決めてほしいこと |
| 組織長月次報告 | ①目標差分 ②前月比と累計 ③年度着地の見込みと根拠 ④**前月に約束した打ち手の実施状況** ⑤次月の前提条件（需要・要員・設備） |
| 人事・要員報告 | ①**決定と検討中の区別** ②面談・意向確認をしたか ③判断者と判断期日 ④欠員の穴埋め計画（誰が・いつまで）⑤個人情報の粒度（氏名フル・給与・評価語を書いていないか） |
| システムトラブル（障害）報告 | ①**影響範囲**（対象システム・業務・件数・金額・時間）②**復旧時刻**（検知／一次対応／復旧の 3 点）③**暫定策と恒久策の区別**（担当・期限つき）④**再発防止**（同種の過去事象と、その恒久策が実施済みか）⑤**顧客・関係先への連絡の有無と期限** |
| 営業・受注活動報告 | ①目標との不足額と補填する案件 ②確度の根拠（相手の言質か自社の希望か）③失注理由 ④次アクションの相手と期日 |
| 案件・プロジェクト進捗報告 | ①計画と実績の差（工程・工数・費用）②遅延がクリティカルパス上かどうか ③決裁待ちの事項 ④外部依存 |
| 生産・稼働実績報告 | ①計画比・前期比 ②停止時間の内訳 ③要因の分解（設備・人・材料・方法）④納期・在庫への影響 |
| 品質・不具合報告 | ①発生と流出の区別 ②暫定処置と恒久処置 ③横展開の範囲 ④効果確認の期日 |
| 顧客クレーム対応報告 | ①顧客への回答期限と回答済みか ②責任範囲の記述が推測でないか ③費用負担の合意状況 ④再発防止の顧客提示 |
| 安全・環境報告 | ①重大度の区分 ②法令・届出の要否 ③再発防止の実施状況 ④**人に原因を帰していないか**（仕組み・設備側の対策があるか） |
| 監査・是正対応報告 | ①指摘事項と是正の 1 対 1 対応 ②期限 ③証跡の有無 ④水平展開 |
| 予算実績・コスト報告 | ①差異の要因分解（数量・単価・為替・一時要因）②年度着地の見込み ③削減策の実現時期 |
| 改善活動・提案報告 | ①件数だけでなく効果額 ②定着の確認 ③未実施の理由 ④横展開先 |
| 出張・外部会議報告 | ①目的の達成可否 ②持ち帰った宿題と期日 ③相手の言質と自社の約束の区別 ④次アクション |

### 3-3. 目的（モード）ごとの語調と出力の取捨

| | `pre_submit`（提出前セルフチェック） | `post_receipt`（受領後の論点整理） |
|---|---|---|
| 相手 | 書いた本人 | 読み手 |
| 語調 | 「〜を足すと規定を満たします」「〜が空欄です」 | 「〜を確認してください」「〜をこの会議で決める必要があります」 |
| 行整理 | **出す**（そのまま / 書き足し / 統合 / 削除候補 / 判断保留、件数つき） | 出さない（要約側に寄せた件数だけ 1 行） |
| 論点 3〜5 件 | 出さない（代わりに「直し方」3〜5 件） | **出す**（論点・根拠・質問・期待する回答形式・放置した場合） |
| 数字のブリッジ | 出さない（目標差だけ 1 行） | **出す** |
| 台帳照合 | 出さない | **出す** |
| 改善後の報告案 | **出す**（本人が上書きできる形） | 出す（読み手が書き手に返す骨子として） |
| 次回確認事項 | 出さない | **出す**（台帳登録の下書きつき） |

- **削除候補は日常事務のみ**（メール返信、会議に出席しただけ、報告作成そのもの）。**成果・数値・約束・期限を含む行は絶対に削除候補にしない**。迷ったら判断保留
- 曖昧表現には**対象・完成度・残課題・期限**の 4 点の追記を求める
- 件数の集計は LLM にさせない（Code ノード）

### 3-4. 禁止（全モード共通。Notion の禁止事項＋`../implementation-guide.md` §6）

- 根拠なく断定する／数字を都合よく補完する／単位・通貨・期間が曖昧なときに勝手に正規化する（「単位が未記載です」と指摘する）
- 人格批判・評価（「意識が低い」「またか」）／皮肉・圧力。**個人の人事評価に使える表現を出さない**
- 表記揺れ・誤字の大量指摘（1 件にまとめて末尾へ）
- 個人名・電話・身分証・給与の転記（`PC-10`）。氏名は「役職＋姓」まで。**人事・要員報告モードでも同じ**
- 社外秘（顧客別単価・契約額・図面番号）を書き手へのコメント案に含めない。必要なら【要確認】を付ける
- 未確定事項を「決定」として台帳に登録する提案をしない
- システムへの登録・送信・承認をしない（コメント送付も台帳登録も**人が実行**）
- **画面に出す言葉**：「ツッコミ」「指摘」は使わない（PM 判断 D-6）。「論点」「確認したいこと」「確認事項」を使う。中国語は「议题」「需要确认的事项」（「指摘」は非難の語感になるため使わない）

### 3-5. 不確実時の定型文

- ja：「この論点は根拠となる数値が入力にありません。<不足している情報> を確認してください。」
- zh：「该议题在输入中没有数值依据。请确认 <缺少的信息>。」

## 4. Dify 構成

**モードで分岐するのは「プロンプトの差し込み」と「出力テンプレ」だけ。ノード構造は全モード共通。**

- **アプリ種別**：**Workflow**（フォーム入力 → 1 回実行で構造化出力）。対話での深掘り（「どれから聞くべきか」「別のモードだとどう返る？」）は `PC-16` が**同 Workflow を `follow_up` 付きで再実行**する。Chatflow にしない理由：件数集計とブリッジの残差計算を Code に固定したいため
- **ノード列**

| # | ノード | 役割 | モードで変わるか |
|---|---|---|---|
| 1 | `start` | モード 3 つ（`report_kind` / `reporter_to_reader` / `purpose`）＋入力（§4 の変数表） | — |
| 2 | `code`（モード解決） | **モードマスタ**（§8）から `extra_criteria` / `tone` / `output_blocks` / `kb_filter` / `maturity` を引く。未定義の種別なら共通のみ＋`warnings` | **ここだけがモードの入口** |
| 3 | `document-extractor` | 報告本文 → テキスト。xlsx の推移表は `tools/dify_extractor` | — |
| 4 | `code`（行分割・正規化） | 見出し・箇条書き・表の行を `lines[]`（`no` / `text` / `section`）へ。数値表現（%・pt・元・h・件）を正規表現で抽出 | — |
| 5 | `knowledge-retrieval` | KB `dc8-report-rules`。**メタデータフィルタ `kind = {{report_kind}}` と `kind = common`** の 2 本 | フィルタ値のみ |
| 6 | `llm`（第 1 段：規定照合・行分類） | System §5-2。`lines[]` に `verdict` / `reason` / `rewrite` を付けた JSON。小型モデルで可 | 差し込み `{{rules_excerpt}}` のみ |
| 7 | `http-request`（任意） | `PC-17` から直近 8 週を取得（`GET /review_log?reporter=&kind=&weeks=8`） | `kind` を渡すだけ |
| 8 | `code`（計算と機械判定） | (a) `verdict` の件数集計 (b) 本文の数値 × 推移表の突合（`mismatch[]`）(c) 目標差と打ち手の合計・**残差**（`bridge`）(d) 台帳の未回答・期限超過・再発回数。**数値の唯一の出所** | — |
| 9 | `llm`（第 2 段：論点／助言） | System §5-1（共通）＋ §5-3 の差し込み（`{{extra_criteria}}` `{{tone}}` `{{output_blocks}}`）、User §5-4 | **差し込みのみ** |

## 5. プロンプト

### 5-1. 共通 System（第 2 段の土台。全モードで同一）

```text
あなたは「報告レビュー担当」です。提出された報告を読み、目的に応じて次のどちらかを返します。
- 提出前セルフチェック：書いた本人が自分で直せるように、規定との差と直し方を返す。
- 受領後の論点整理：報告を受け取った読み手が次に判断できるように、確認したい論点を返す。
入力された報告を、目標・実績・差分・原因・打ち手・責任者・期限・リスク・意思決定事項に分解してください。原因説明と対策説明を区別し、数字の不整合、曖昧な主体、未確定事項の断定、目標差分に対して不足する打ち手を見つけてください。
共通して必ず見る観点は次の 8 つです。A 目標・差分／B 数字の整合性／C 事実と解釈／D 打ち手の具体性／E 制約と代替案／F 主体・責任／G リスク・依存関係／H 報告表現。
この報告種別で追加で見る観点は {{extra_criteria}} です。共通の観点より優先して探し、該当が無ければ「該当なし」と書いてください。観点を自分で増やさないでください。
重要なものを 3〜5 件に絞り、それぞれに 論点・根拠・具体的な質問または直し方・期待する回答形式・放置した場合に起きること を付けてください。
制約を所与にせず、増員、外注、再配置、優先順位変更、部分検収、前倒し、代替手段などの選択肢を検討してください。ただし費用と可否は「要確認」と書き、自分で見積もらないでください。
過去のやり取りの台帳（{{log}}）がある場合は必ず照合し、未回答、期限超過、同種の論点の再発を明示してください。再発には「なぜ効かなかったか」を問う質問を必ず付けてください。
数値のルール：
- 目標差、打ち手の効果の合計、未充足の残差は {{bridge}} の計算済みの値をそのまま使う。自分で計算・丸め・推定をしない。
- 本文と添付で数値が食い違う箇所は {{mismatch}} に入っている。どちらが正しいかを断定せず、定義（分子・分母・対象期間・再検査の扱い）を問う質問にする。
- 入力に無い数値・管理番号を作らない。単位や通貨や期間が曖昧なときは、勝手に補正せず「単位が未記載」と書く。
- 推測を書くときは必ず「推測」と付ける。事実・決定・予定・見込み・推測・要確認 のラベルを使い分ける。
表現のルール：
- 結論を先に書く。重要度順に並べる。1 つの項目に 1 つの論点。
- 良い点を最大 3 件、先に書く。内容に触れ、人には触れない。
- 個人名は「役職＋姓」まで。氏名・電話・身分証・個人の給与や残業時間を出力に書かない。
- 社外秘（顧客別単価・契約額・図面番号）を書き手へのコメント案に入れない。必要なら【要確認】を付ける。
- 皮肉、威圧、断定、人事評価に使える表現を使わない。表記揺れ・誤字は末尾に 1 件へまとめる。
- 「ツッコミ」「指摘」という語を出力に使わない。「論点」「確認したいこと」を使う。中国語では「议题」「需要确认的事项」を使う。
- 説明の言語は {{out_lang}}（auto のときは報告の原文言語）。書き手へのコメントは書き手の母語で書く。
- 根拠となる数値が入力に無い論点は書かない。書けないときは「この論点は根拠となる数値が入力にありません。<不足している情報> を確認してください。」と書く。
語調と出力の指定：{{tone}}
出力するブロック：{{output_blocks}}。ここに無いブロックを出さないでください。
出力：指示された JSON スキーマのみ。JSON の外に説明を書かない。
```

### 5-2. System（第 1 段：規定照合・行整理。`pre_submit` では本体、`post_receipt` では件数のみ使う）

```text
あなたは {{org_name}} の報告規定に従って、提出された報告を行単位で整理する担当です。
適用する規定：{{rules_excerpt}}（報告種別 {{report_kind}} の規定と共通規定）
入力の各行について、次のいずれか 1 つを付けてください。
- keep      ：規定どおり。そのまま残す
- improve   ：内容は必要だが書き方が足りない（対象・完成度・残課題・期限のどれかが欠けている、曖昧表現がある）
- merge     ：他の行と同じ内容。まとめる（まとめ先の行番号を書く）
- remove    ：日常事務のみで、判断の材料にならない（メール返信、会議に出席しただけ、報告作成そのもの）
- needs_review：規定のどれに当たるか判断できない
守るルール：
- 成果・数値・約束・期限を含む行は remove にしない。迷ったら needs_review。
- 曖昧表現（一部確認、対応中、順調、努力する、調整中、随時、なるべく）を含む行は improve とし、何を足せば keep になるかを 1 行で書く。
- 書き換え案は原文の語をできるだけ残す。原文にない事実・数値を足さない。
- 件数の集計はしない（後続の処理が数える）。
- 判定の理由は 40 文字以内。
出力：JSON 配列のみ。各要素 { "no": 行番号, "verdict": "...", "reason": "...", "rewrite": "書き換え案または空" }。説明文を付けない。
```

### 5-3. モード別の差し込み（**KB か変数で持つ。System を書き換えない**）

差し込みは 3 つだけ。**モードマスタ（§8）の 1 行から生成する**。顧客が観点や語調を変えるときは、この 3 つを編集する。

| 変数 | 中身 | 例（`incident` × `post_receipt`） |
|---|---|---|
| `{{extra_criteria}}` | §3-2 の追加観点を箇条書き 3〜5 行にしたもの | 「影響範囲（対象・件数・金額・時間）／復旧時刻（検知・一次対応・復旧）／暫定策と恒久策の区別（担当・期限つき）／再発防止（同種の過去事象と恒久策の実施状況）／顧客・関係先への連絡の有無と期限」 |
| `{{tone}}` | §3-3 の語調の指定 | 「読み手（工場長・本社IT）が判断できるように書く。書き方の助言はしない。決めることを 1〜2 件に絞って最後に書く」 |
| `{{output_blocks}}` | §3-3 の表の「出す」ブロックの列挙 | 「要旨／良い点／論点 3〜5／数字のブリッジ／台帳照合／改善後の報告案／次回確認事項」 |

- `pre_submit` の `{{tone}}` 例：「書いた本人に返す。直し方を具体的に書く。読み手向けの論点や会議の進め方は書かない。規定の条番号を根拠に挙げる」
- `{{output_blocks}}` 例（`pre_submit`）：「行整理（件数つき）／曖昧表現の直し方／必須項目の欠落／改善後の報告案」
- **差し込みの保管場所**：モードマスタ（JSON）を正本とし、Outline の「報告ルール › モード一覧」に人が読む版を置く（`PC-05` で同期）。System の本文には差し込みを埋め込まない

### 5-4. User テンプレート

```text
報告種別：{{report_kind}}（{{report_kind_label}}）／書き手→読み手：{{reporter_to_reader}}／目的：{{purpose}}
原文言語：{{in_lang}}／出力言語：{{out_lang}}／書き手：{{reporter_role}}（母語 {{reporter_native}}）
報告本文（行番号つき・第 1 段の判定つき）：{{lines_json}}
行整理の集計：{{verdict_counts}}
指標（本文と推移表の突合済み）：{{metrics_json}}
数値の食い違い：{{mismatch}}
数字のブリッジ（計算済み。合計と残差はこの値を使う）：{{bridge}}
前回までのやり取り台帳（未回答・期限超過・再発回数つき）：{{log}}

```

### 5-5. 出力フォーマット

`items` はモックの `Result` 型（`title` ＋ `items[]`）にそのまま流し込める形にする。`purpose` によって**使わないキーは省略**する（空配列を返さない）。

      "question": "…", "answer_format": "施策・想定効果(pt)・確度・実施日・オーナー", "risk": "…" }

### 5-6. Few-shot

**不要**。論点の文例を few-shot に入れると、別の報告でも同じ論点を写す事故（架空の 0.07pt 未充足を作る等）が起きる。書式は System と JSON スキーマだけで固定する。ただし**曖昧表現の辞書**（「一部確認」「対応中」「順調」「努力する」「調整中」）は第 1 段の System に列挙する（事実の生成ではないため安全）。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| **モードの反映** | `extra_criteria_applied` が選んだ種別の観点と一致 100%。他種別の観点が混ざらない | `review_json.mode` の自動突合 |
| **目的の越境なし** | `pre_submit` で `bridge` / `log_check` / `next_checks` が出ない 100%。`post_receipt` で `line_review.lines` が出ない | スキーマバリデータ（§4 ノード 10） |
| 数値の一致 | ブリッジの合計・残差が Code 計算値と一致 100%。入力に無い数値の出現 0 | `review_json.bridge` と Code 出力の自動突合 |
| 形式 | 論点／直し方 3〜5 件、各件に 5 要素 | スキーマバリデータ |
| 質 | 「原因と対策のずれ」「未充足の pt」「未確定の断定」「種別固有の抜け（例：障害報告の顧客連絡欄）」の検出率 ≥ 80% | 欠陥を仕込んだ評価セット 20 件を人手採点 |
| 誤検出 | 正しい行を improve / remove にする誤りが 1 報告あたり 1 行以下 | 第 1 段の行分類を人手採点 |
| 言語 | 説明は入力言語、コメント案は書き手の母語 100% | 自動判定（`PC-07`） |
| 表現 | 人格に触れる表現・断定・皮肉 0。**出力に「指摘」「ツッコミ」が出ない 0 件** | 禁止語リスト＋LLM-as-judge（`PC-09`） |
| 拒否 | 根拠のない論点を書かず定型文に落とす ≥ 95% | 負例セット（推移表なし・目標未設定・台帳なし・種別未定義） |
| 速度 | p95 < 60 秒（2 段 LLM ＋ 抽出） | Langfuse（`PC-09`） |
| 安全 | 個人名フル表記・個人の残業時間・給与・顧客単価の混入 0 | 負例セット（人事・要員報告モードを必ず含む） |

- **評価方法**：リリース前に評価セット 20 件（過去の報告を匿名化し欠陥を仕込んだもの。**最低 5 モードを各 4 件**）で人手採点。月次で Langfuse のスコアを確認。**採点結果を書き手個人の評価に使わない**ことを運用ルールに明記する（§10）

## 8. 別出しが必要なもの

### 8-1. `PC-17 指摘・回答台帳`（本サービスの本体）

PM 判断 D-1 で新規 PC として確定。定義は `../platform-components.md` PC-17。テーブル `review_log`（`report_date` ／`reporter_id`・`reporter_role` ／**`kind`（報告種別。モードマスタのキー）** ／`topic` ／`point` ／`answer` ／`promise` ／`due` ／`status` ／`repeat_of`・`repeat_count` ／`insight`）と API `GET /review_log?reporter=&weeks=8` ／ `POST` ／ `PATCH` ／ `GET /review_log/stats`。

- **本改訂での追加（PM 判断 R-4 で確定・`../platform-components.md` PC-17 に反映済み）**：`kind` は §1-2 のモードマスタのキー（`staff_weekly`／`mgr_weekly`／`mgr_monthly`／`headcount`／`incident` ほか）を持ち、`GET /review_log?reporter=&kind=&weeks=8` で種別を絞る。**再発は同じ `kind` の中だけで数える**（`repeat_of` の親は同一 `kind` のレコードからしか選べない。週報の論点と障害報告の論点を同一視すると `repeat_count` が意味を失うため）
- `log_entries[]` は**登録の下書き**で、`POST` するのは人。第 1 段階は `tools/microsoft_excel_365`・`tools/jiandaoyun` の表で代替できる
- **`PC-01` との境界**：PC-01 は担当者ごとの To-Do・通知、PC-17 は確認事項の履歴と再発回数。**期限つきのものだけ PC-01 に `due` として併載**する（`source = review_log`、`source_ref = PC-17 の id` で冪等）。PC-01 側で `done` にしても PC-17 の `status` は人の回答登録で動かす
- **`pre_submit` は台帳に残さない**（PM 判断 R-3 で確定）。本人の自己点検であり、記録が個人評価に転用されうるため（D-5 と整合）

### 8-2. 報告種別ごとの規定 KB

- Outline「報告ルール」配下に**種別ごとのページ**を作る（週報規定／月次報告規定／障害報告規定／人事報告規定 ほか）。共通の禁止表現・必須項目は「共通規定」ページに 1 つ
- KB `dc8-report-rules` にメタデータ `kind` を付けて同期（`PC-05`）。検索は `kind = {{report_kind}}` と `kind = common` の 2 本
- **前提条件**：現時点で文書化されているのは週報規定に近いものだけ。**種別ごとの規定が無い間は共通規定＋モードマスタの追加観点だけで動く**（§10）

| `kb_filter` | 規定 KB のメタデータ値 | `incident` |
| `maturity` | `trial` / `concept` | `trial` |
| `depth_default` | 深さの既定（確認／差分／打ち手／代替案／経営判断） | 経営判断 |

- **顧客が種別を足す手順**：この表に 1 行足す → Outline に規定ページを作る（無くても動く）→ 再実行。**Workflow は触らない**

- **書く**：**改善後の報告案**を「報告 › レビュー（AI ドラフト）」に下書き（`publish: false`）。編集して確定するのは**書き手本人**。閲覧範囲は書き手と読み手の組織に限定（`PC-02`）
- **書かない**：確認事項の台帳（構造化データが正本。§8-1）、報告の原文（提出物はファイルサーバ／WeCom が正本）、月次品質レビューの集計（人事評価に転用されないよう限定公開の別置き）

## 10. 未確定・リスク

- **実現性を ○ とした理由**：入力（docx / xlsx / 貼り付け）と 2 段 LLM ＋ Code は Dify 標準機能で足りる（この点だけなら ◎）。○ に落としたのは、(1) **報告規定が種別ごとには文書化されていない**、(2) **指摘・回答台帳の新設**が要る、(3) 「良い論点かどうか」の評価が人手でモデル差が出やすい、の 3 点。(1) が最大の前提条件で、規定が無い種別は共通観点＋モードマスタの追加観点だけで開始する
- **モードを増やしすぎるリスク**：種別を足すほど「どれを選べばいいか分からない」になる。**最初に出すのは 5 種**、残りは「その他」から選ぶ形にする。UI の既定値は利用者の所属と直近の実行から補完する（`PC-16`）— 画面設計は未確定
- ~~モードマスタの正本~~：**確定**（R-2。Outline ＋ 同期 JSON。§8-3）
- ~~`pre_submit` を台帳に残すか~~：**確定**（R-3。残さない。§8-1）
- **人事評価への転用リスク（最重要）**：再発回数・解決率は個人が特定できる。**月次品質レビューは読み手側の組織のみ**（D-5）とし、「個人攻撃に使わない」を運用ルールと UI の注記の両方に書く。台帳の閲覧権限を `PC-02` で絞る。**`pre_submit` の結果は本人以外に出さない**
- **人事・要員報告モードの個人情報**：このモードだけ入力に個人情報が濃い。`PC-10` のマスクを**入力側でも**かけ、台帳には役職＋姓しか残さない。KN-04（労務・総務の問い合わせ）と同じ扱い
- **語調**：日本語では丁寧でも、中国語に直すと詰問調になりやすい。コメント案は書き手の母語で生成し、**評価セットに「中国語コメントの語調」の採点項目**を入れる（`PC-08` のモデル選定に効く）
- **書き手が身構える**：導入は `pre_submit`（本人が自分で使う）から始め、`post_receipt` は後から入れる（**PM 判断 R-5 で確定**）。ただし**デモは `post_receipt` で見せる**（工場長に価値が伝わるのは受領後モードのため）。この順序は `PC-16` の画面設計に影響する — 画面設計自体は未確定
- **DC-01 との連携**（D-2）：本社向け月次報告のドラフトを DC-08 の `mgr_monthly × pre_submit` に通す。第 2 段階。モックには導線を作らない

## 11. 用途が重なるサービスとの整理

> 統廃合の方針：**DC-08 は「できあがった報告を読む」だけ**。作る・集める・技術判断するのは既存サービスの仕事。境界を越えて機能を足さない。

| サービス | 関係 | 入口 / 出口 | 重なりの整理（どちらがやるか） |
|---|---|---|---|
| **DC-01** 日本本社への報告資料作成 | **入口**（作る → 読む） | DC-01 の出力（月次報告ドラフト）を DC-08 の `mgr_monthly × pre_submit` に通す（D-2・第 2 段階） | **DC-01 は書く専用**。記載漏れ検出・論点整理を DC-01 に足さない。DC-08 に「報告を作る」機能を足さない |
| **DC-02** 議事録作成と次回論点整理 | **隣接**（対象が違う） | 会議 → DC-02、報告書 → DC-08 | DC-02 の「次回論点」＝**会議の未決事項**。DC-08 の論点＝**報告の穴**。DC-08 の `trip`（出張・外部会議報告）は議事録ではなく**報告書**のレビュー。議事録そのものは DC-02 |
| **NM-03** 日報・実績の集計と要約 | **入口**（数字の供給元） | NM-03 の週次／月次サマリが DC-08 の `trend_file` | **集計は NM-03**。DC-08 は集計をしない（数字を作らない）。KPI 定義 KB は 2 サービスで共用 |
| **QA-01** 不具合原因分析・報告書（8D）作成 | **入口**（作る → 読む） | QA-01 が作った 8D を DC-08 の `quality × pre_submit` に通せる | **8D の技術的妥当性（なぜなぜ・是正処置の妥当性）は QA-01**。DC-08 は報告としての穴（発生と流出の区別、期日、横展開の記載）だけを見る |
| **QA-02** 変更点影響予測（4M） | **入口** | 4M 変更報告書を DC-08 の `quality` / `project` に通せる | **変更の技術影響予測は QA-02**。DC-08 は変更報告書の記載の穴だけ |
| **KN-04** 労務・総務の社内問い合わせ対応 | **隣接**（対象が違う） | 担当者の質問 → KN-04、人事・要員**報告書** → DC-08 | KN-04 は**手続きの質問に答える**。DC-08 は**報告書を読む**。個人情報の扱い（`PC-10`）は同じルールを使う |
| **DC-05** 稟議・申請書の作成と記載漏れ検出 | **隣接**（似ているが対象が違う） | 稟議・申請 → DC-05、報告 → DC-08 | DC-05 は**様式の記載漏れ**（決まった欄が埋まっているか）。DC-08 は**論理と数字の穴**。DC-08 の `pre_submit` も「必須項目の欠落」を見るが、対象は報告規定であって申請様式ではない |

- **サービスを増やさない**：読み手向け／書き手向けを 2 サービスに分けない（PM 決定）。報告種別ごとにサービスを分けない（モードで表す）
- **カタログ上の見え方**：DC/report は DC-01（書く）・DC-02（会議）・DC-08（読む・整える）の 3 件。この 3 件で「報告の仕事」が一巡する
