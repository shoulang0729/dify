## 1. 業務シナリオ
- **トリガー**：定時（毎月 5 日の本社経営会議に向け、月初 1〜3 日に作成）。③業務フィードでは `routine`（毎月 1 日）。突発の会議資料・トピック報告にも担当者が能動的に使う
- **登場人物**：作成者＝工場長（または秘書・通訳が代行）、確認者＝財務課（数字の根拠）・製造部長（課題・対策の妥当性）、外部（受け手）＝日本本社 経営会議
- **いまの手順（Before）**
  1. 中国語の日報・月報（Excel／WeCom 投稿）から数字を拾い、日本語に読み替える（約 1 時間）
  2. 本社フォーマット（要旨・実績・課題・対策）に流し込み、前月報告と突き合わせて前月比を計算（約 1 時間）
  3. 課題・対策の文章を書く。品質・購買・人事の各課に裏取り（半日〜1 日）
  4. 工場長が推敲し提出。月あたり 3〜4 時間、締切直前に集中
- **エージェント導入後の手順（After）**
  1. 【入力】対象月・実績（中国語のまま貼り付け可）・トピックス・出力言語をフォームに入れる
  2. 【生成】本社フォーマット 4 章の日本語ドラフトが返る。前月値は Outline の前月報告から引く（無ければ「前月比：前月値未取得」と表示）
  3. 【確認】担当者が数字の根拠（入力値との一致、試算値の脚注）を確認し、文体を対話で調整（前向きに／未達は隠さない、など）
  4. 【決める】課題の取り上げ順・対策の約束（期日・担当）は工場長が決める。AI は提出も送信もしない
  5. 【保存】Outline「月次報告 › ドラフト」に保存 → 工場長の承認後に「月次報告 › 提出済」へ人が移動
- **成功の定義**：作成時間 3〜4 時間 → 1 時間以内。数字の転記ミス 0。前月報告との文言・定義の一貫性（不良率の定義など）が保たれる

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 実績数字 | テキスト（貼り付け）。将来は xlsx 添付 | zh（日報・月報の原文）／ja | 月 1 回、5〜10 指標 | 「产量 186,400件（计划 190,000）。不良率 0.42%（目标 0.40%）…」 | 中国語月報（Excel／WeCom） | LLM で指標名・実績・計画・単位を JSON 化 → Code で達成率等を計算 |
| トピックス | テキスト | ja / zh 混在 | 月 3〜6 件 | 「K 社クレーム 1 件（塗装ブツ、8D 提出済）／材料 S 社 +9% 値上げ」 | 担当者のメモ | 箇条書きへ正規化。管理番号（CL-／ECR-）はそのまま保持 |
| 前月報告 | Markdown（Outline ドキュメント） | ja | 月 1 件、直近 3 か月分を保持 | 7 月報告の「2. 実績」章 | Outline「月次報告 › 提出済」（`PC-05`） | 章単位でチャンク。メタデータ：`month`, `site`, `status` |
| 本社フォーマット定義 | Markdown | ja | 1 件、年 1 回改定 | 章立て・各章の記載ルール・NG 表現 | Outline「報告ルール」（`PC-05`） | System プロンプトに埋め込む（KB にはしない） |
| 出力言語 | 選択 | — | — | 日本語（本社フォーマット）／中国語対照付き | フォーム | — |

- **入力言語の扱い**：実績・トピックスは ja / zh どちらでも受ける。**成果物の言語は「出力言語」欄で指定**（既定：日本語。本社向けだから）。対話での質問・修正依頼には**入力言語で返す**（`CLAUDE.md` §2-5）。中国語対照版は同時出力オプション
- **入力の欠け・曖昧さ**：対象月と実績が無いと生成しない。計画値が無い指標は達成率を出さず「計画値未入力」と書く。聞き返し文：「対象月と実績（生産数・不良率など）を入力してください。中国語のままで構いません」／「请填写对象月份与实绩（产量、不良率等），中文即可」

## 3. 観点（LLM に守らせる業務ルール）
- **数字は入力値をそのまま使う**。達成率・前月比・年間影響額などの**計算は Code ノードが行い**、LLM は計算結果を受け取って文章にするだけ。LLM 自身に計算させない
- 試算値（例：年間影響額）には必ず**「試算」「参考値」と根拠式を脚注**で付ける。根拠が入力に無い数字は書かない
- 未達・悪化は**隠さない**。前向きな表現にする場合も事実（未達・件数）は残す
- 前月比は前月報告の値が取得できたときだけ書く。取得できなければ「前月値未取得」と明示（勝手に埋めない）
- 用語は本社フォーマットの定義（不良率＝出荷ベース、稼働率の定義）に揃える。中国語の指標名は本社の日本語呼称へ（`PC-06` 用語集を参照。無ければ入力の表記を保持し「※呼称確認」を付す）
- 管理番号（CL-25-0906、ECR-25-0088 等）は**改変・生成しない**。入力に無い管理番号を作らない
- 禁止：個人名の記載は役職＋姓まで（PIPL、`PC-10`）。人事情報（残業超過者の個人名など）は書かない。社外秘の単価・顧客契約額は入力に含まれていても本社版に書く前に「※社外秘」を付す
- 不確実時の定型文：「この項目は入力に根拠がないため空欄にしています。値または出典を追記してください」／「该项在输入中没有依据，已留空。请补充数值或出处」
- 出力形式：Markdown。章立ては固定（1. 要旨／2. 実績／3. 課題／4. 対策・見通し）。後工程（`PC-13` docx 化・Outline 保存）向けに §5-3 の JSON も併せて返す

## 4. Dify 構成
- **アプリ種別**：**Workflow**（フォーム入力 → 1 回実行で構造化出力。修正依頼の対話は `PC-16` 側が同 Workflow を「修正指示」入力付きで再実行する）。Chatflow にしない理由：数字の計算を Code に固定したいため
- **ノード列**
  1. `start`：`month`, `results_raw`, `topics`, `out_lang`, `revise_note`（任意）, `prev_report`（任意・手入力）
  2. `llm`（抽出）：`results_raw` → 指標 JSON（name_ja/name_zh/actual/plan/unit/prev）。小型モデルで可
  3. `code`（計算）：達成率、前月比、差分、単位整形。計画値欠落は `null` のまま返す
  4. `knowledge-retrieval`（任意）：KB `dc1-monthly-reports`、メタデータフィルタ `month = 前月`。ヒットしなければ空
  5. `llm`（生成）：System §5-1、User §5-2。4 章ドラフト＋脚注＋JSON
  6. `template-transform`：Markdown 整形（本社フォーマットの見出し・表）
  7. `end`：`draft_md`, `draft_json`, `warnings[]`
- **Knowledge**：`dc1-monthly-reports`（前月報告。Outline「月次報告 › 提出済」を `PC-05` が同期。章単位チャンク、メタデータ `month`/`site`/`status`。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`）。本社フォーマット定義は KB ではなく System に埋め込む（改定時は System を更新）
- **プラグイン／ツール**：なし（Dify 本体ノードのみ）。docx／pptx 化は `PC-13`（Dify の外）。`tools/slidespeak` は SaaS のため中国拠点では非推奨（`../plugins-and-references.md` §7）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（生成）／Qwen3-32B（抽出）。**本社向け日本語の経営会議文体**が要るため、DeepSeek-V3.x と評価セットで比較して決める（§4 横断リスク「日本語品質」）。日本本社側で動かすなら `models/azure_openai` 等（`PC-08` で拠点別に切替。アプリは分ける）
- **参照 DSL**：`../templates/01-translation-reflection-workflow.yml`（多段 LLM と `if-else` の型）、`../templates/05-chatflow-form-input-demo.yml`（form 型の入力受け）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `month` | string | ✓ | 対象月（YYYY-MM） |
| `results_raw` | paragraph | ✓ | 実績（zh/ja 貼り付け） |
| `topics` | paragraph | — | トピックス |
| `out_lang` | select（ja / ja+zh） | ✓ | 成果物の言語 |
| `prev_report` | paragraph | — | 前月値の手入力（KB に無いとき） |
| `revise_note` | paragraph | — | 修正指示（2 回目以降） |
| `draft_md` | string | 出力 | 4 章ドラフト（Markdown） |
| `draft_json` | object | 出力 | §5-3 |
| `warnings` | array[string] | 出力 | 計画値欠落・前月値未取得・試算値の一覧 |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工（蘇州）の工場長室スタッフとして、日本本社の経営会議向け月次報告のドラフトを書きます。
役割：中国語・日本語の現場データを、本社フォーマット（1. 要旨／2. 実績／3. 課題／4. 対策・見通し）に整える。
守るルール：
- 数字は {{metrics_json}} の値をそのまま使う。自分で計算・丸め・推定をしない。metrics_json に無い数字は書かない。
- 達成率・前月比は metrics_json の計算済みフィールドを使う。null の指標は「（計画値未入力）」「（前月値未取得）」と書く。
- 試算値には脚注「※ 試算：<根拠式>」を付ける。根拠式は {{topics}} または metrics_json にある値だけで組む。
- 未達・悪化・クレームは隠さない。表現を前向きにする指示があっても事実は残す。
- 管理番号（CL-／ECR-／NC- など）は入力どおりに書く。新しい番号を作らない。
- 個人名は「役職＋姓」まで。人事情報・個人の残業時間は書かない。
- 用語は本社定義に揃える：不良率＝出荷ベース、稼働率＝設備稼働率。中国語の指標名は日本語呼称にする（产量→生産数、不良率→不良率、稼动率→設備稼働率、加班→残業時間）。
- 成果物の言語は {{out_lang}}（ja／ja+zh）。ja+zh のときは日本語の後に中国語対照を同じ章立てで付ける。
- 質問・修正依頼への説明文は、依頼者の入力言語（日本語なら日本語、中国語なら中国語）で書く。
- 根拠が無い項目は空欄にし「この項目は入力に根拠がないため空欄にしています」と書く。
出力：Markdown の 4 章 → 区切り線 → JSON（スキーマは指示どおり）。JSON 以外の説明は Markdown 側に書く。
```
### 5-2. User テンプレート
```text
対象月：{{month}}
計算済み指標（JSON）：{{metrics_json}}
トピックス：{{topics}}
前月報告の該当章（無ければ空）：{{context}}
成果物言語：{{out_lang}}
修正指示（無ければ空）：{{revise_note}}
前回ドラフト（修正時のみ）：{{prev_draft}}

本社フォーマットで 4 章ドラフトを作成してください。課題は最大 3 件、対策には期日と担当（役職）を付け、最後に「翌月見通し」を 1 行。
```
### 5-3. 出力フォーマット
```json
{ "month": "2025-08", "site": "suzhou",
  "summary": "…", 
  "metrics": [ { "name_ja": "生産数", "actual": 186400, "plan": 190000, "unit": "個", "rate": 0.981, "prev": null } ],
  "issues": [ { "no": 1, "title": "…", "ref_ids": ["CL-25-0906"] } ],
  "actions": [ { "issue_no": 1, "action": "…", "due": "2025-09-30", "owner_role": "製造部長" } ],
  "footnotes": [ { "mark": "※1", "text": "試算：S 社年間購入額 4.7M × 9%" } ],
  "warnings": ["前月値未取得：設備稼働率"] }
```
### 5-4. Few-shot
不要。台本の数字を few-shot に入れると実運用で**数字を写す事故**が起きるため、フォーマットは System の指示だけで固定する。

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 数字の一致 | 入力値と出力値の不一致 0 | `draft_json.metrics` と入力 JSON の自動突合（Code） |
| 計算 | 達成率・前月比の誤差 0（Code 計算） | 単体テスト（Code ノード） |
| 網羅 | 4 章すべて存在、課題に管理番号が保持 | チェックリスト（人手） |
| 日本語品質 | 経営会議で手直し 2 か所以内 | 工場長・本社受け手による 5 段階評価、月次 |
| 言語 | 成果物は `out_lang`、説明は入力言語 100% | 自動判定（`PC-07`） |
| 拒否 | 根拠のない数字・番号を作らない ≥ 95% | 負例セット（計画値欠落・前月報告なし） |
| 速度 | p95 < 40 秒（2 段 LLM） | Langfuse（`PC-09`） |
| 安全 | 個人名フル表記・人事情報の混入 0 | 負例セット |

- **評価方法**：リリース前に評価セット 20 件（過去 6 か月の実報告を匿名化）で人手採点。月次で Langfuse のスコア（受け手評価）を確認

## 8. 別出しが必要なもの
- `PC-05`：Outline「月次報告」コレクションの同期（前月報告を KB へ）と、ドラフトの書き戻し（`http-request` で Outline API。専用データソースは無い）
- `PC-13`：Markdown → 本社様式 docx／pptx。Dify はファイルを作らない
- `PC-06`：指標名・部署名の日中呼称（用語集）。初期は System 内の対応表で足りる
- `PC-08`：日本語品質の評価と、本社側モデル切替の判断
- **無くても動く範囲**：フォーム入力 → Markdown ドラフト（前月比は手入力）まで。Outline 連携・docx 化・KB は第 2 段階

## 9. Outline Wiki との関係
- **読む**：「月次報告 › 提出済」（前月値・前月の課題の継続確認）、「報告ルール」（フォーマット定義。System へ反映）
- **書く**：生成ドラフトを「月次報告 › ドラフト › YYYY-MM」に保存（`PC-05`）。**提出済への移動・本社送付は人が行う**。Outline 上でコメント（財務課の確認）を付けてから確定する運用
- Outline に無い前月値は入力欄で補う（`prev_report`）
