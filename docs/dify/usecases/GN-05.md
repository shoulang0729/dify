## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：長文（通達・報告書・仕様書・メールスレッド）が届き、全部読む時間がないとき、担当者が能動的に開く（③業務フィードの `notify`）
- **登場人物**：依頼者（工場長・管理職：目的と粒度を指示、要約を確認して転送）、原文の所管部署（詳細確認）、外部：当局・顧客・本社（原文の発行元）
- **いまの手順（Before）**：38 ページの中国語通達を駐在員が辞書を引きながら読む（半日）か、現地スタッフに口頭で説明してもらう（要点の抜け・「当社に関係あるか」が判断できない）→ 本社への説明用に日本語で書き直す（1 時間）→ 関係者への転送メールを日中で書く
- **エージェント導入後の手順（After）**：
  1. 依頼者が**PDF をアップロード**し、**目的・粒度・出力言語**を指示（「日本語で 1 枚に。当社への影響中心で」）
  2. `PC-03` が Markdown 化（ページ番号保持）→ Code が章単位に分割 → **Iteration で章ごとの要点＋「当社関連箇所」を抽出**（原文ページ付き）
  3. LLM が統合：要点・当社への影響（KB の工程・拠点情報を根拠に）・期限・担当部署案・**原文の重要箇所（p.xx）**を 1 枚に
  4. **人が決める場所**：影響の有無の最終判断・担当と期限の決定・転送先は依頼者。エージェントは「担当部署**案**」「期限（原文記載）」まで。法規・罰則は原文引用のみ（法的助言をしない）
  5. 依頼で転送メール（日中併記）をドラフト
- **成功の定義**：38 ページの把握 半日 → 10 分。要点の脱落（人手要約との差）≤ 1 項目。原文ページ参照が 100% 付き、詳細確認にすぐ戻れる

- **入力言語の扱い**：**出力言語は指示に従う**（既定は指示文の言語）。原文が中国語で出力が日本語のクロスリンガル要約が主用途（`CLAUDE.md` §2-5：指示の言語で返す）。原文の重要箇所は**原語で引用**しページを付ける

## 3. 観点（LLM に守らせる業務ルール）
- **原文に書かれていることだけ**を要約する。外部知識で補わない。数値・期限・罰則・条文番号は**原文どおり転記**し、**ページ番号を付ける**
- **「当社への影響」は KB（社内情報）と原文の対応を根拠に**書く。KB に無い社内事情を推定しない（「当社の該当工程は KB に記載なし。所管部署に確認」）
- **法的助言をしない**：罰則・義務は「原文 p.31 に〜と記載」まで。「当社は違反になる／ならない」の断定をしない。「法務・当局への確認を推奨」
- **担当部署は「案」、期限は原文記載の日付のみ**（社内期限を作らない）
- **脱落防止**：章ごとの中間要約を保持し、統合時に「各章から少なくとも 1 項目」を確認。統合で消えた章は「（略）」と明示
- **個人情報**（`PC-10`）：原文の担当者名・電話（当局窓口を除く）を要約に転記しない。メールスレッドの署名は除外
- **禁止**：原文に無い期限・金額を書く／要約に自分の意見を混ぜる／翻訳と要約で意味を変える（用語集の訳語を使う）
- **出力形式**：粒度プリセットに応じた見出し。1 枚版＝「要点（3 点）／当社への影響／期限／担当部署案／原文の重要箇所」。後工程は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（1 文書→要約）。追加質問（「小規模の基準は原文のどこ？」）は章要約 JSON を会話変数に持つ **Chatflow** 版（同じノードを共有）
- **ノード列**：
  1. Start（`doc` file 必須／`purpose` paragraph 任意／`granularity` select（one_page|bullets10|lines3|per_chapter）／`out_lang` select（ja|zh|en、既定＝指示文の言語）／`focus` select（company_impact|general））
  2. If/Else（形式）→ Document Extractor（電子 PDF・docx・txt）／`tools/mineru`（スキャン・複雑）。Code でページ区切りを `<!-- p.N -->` として保持
  3. **Code（`split`）**：章見出し（第 n 章／§／数字見出し）で分割、無ければ 3,000 字目安。各チャンクに `page_from/page_to`
  4. Knowledge Retrieval（KB `gn-company-facts`：工程・拠点・物料。`focus=company_impact` のとき）
  5. **Iteration**（chunks）→ LLM（`chapter_summary`、小型可）：要点・当社関連箇所・数値/期限/罰則・原文引用（ページ付き）を JSON
  6. LLM（`integrate`）：§5 の System で統合、`granularity`・`out_lang` に従う
  7. （任意）LLM（`forward_mail`）：転送メール日中併記（`purpose` に依頼があるとき）
  8. Template Transform → md／`PC-13`（docx 任意）／End（`summary` JSON・`summary_md`・`chapter_summaries`）
- **Knowledge**：`gn-company-facts`（Outline 同期：会社概要・工程一覧・拠点・主要物料・外注先の役割）。**要約対象の文書は KB に入れない**（一過性。恒久的に参照する通達は KN-05 の KB へ）
- **プラグイン／ツール**：Document Extractor・Code・Iteration・Template Transform（本体）／`tools/mineru`（自前デプロイ推奨）／`tools/dify_extractor`（KB 投入）／`tools/microsoft_excel_365` は不要
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（**日本語 1 枚の品質が要**。DeepSeek-V3.x と評価セットで比較、`PC-08`）。`chapter_summary` は Qwen3-32B（章数×呼び出しのコスト対策）。越境不可の文書（契約・人事）は `models/ollama`
- **参照 DSL**：**`../templates/02-long-document-chunk-iteration-translate.yml`**（Code 分割→Iteration→Template 結合の標準形。翻訳 4 段を要約 1 段に置換）、`../templates/08`（MinerU）。URL 参照：difyhub `basic-text-summarizer`、dify-for-dsl「PDF 原格式翻訳」
- **入出力変数**：`doc` file 必須／`purpose` string 任意／`granularity` select 必須／`out_lang` select 任意／`focus` select 任意／出力 `summary` object・`summary_md` string・`chapter_summaries` array・`pages_total` number

## 5. プロンプト
### 5-1. System（`integrate`）
```text
あなたは青嶺精工 蘇州工場の文書要約アシスタントです。章ごとの要約（JSON、原文ページ付き）を統合し、依頼者の目的・粒度・言語に合わせた要約を作ります。
守ること：
1. 原文（章要約に引用された内容）に書かれていることだけを書く。外部知識で補わない。
2. 数値・期限・罰則・条文番号は原文どおり転記し、必ずページ番号（p.N）を付ける。
3. 「当社への影響」は company_facts（KB）と原文の対応を根拠に書く。KB に無い社内事情は推定せず「所管部署に確認」と書く。
4. 法的助言をしない。「違反になる／ならない」を断定せず、原文の記載と「法務・当局への確認を推奨」に留める。
5. 担当部署は「案」と明記。期限は原文に記載された日付のみ。社内期限を作らない。
6. 各章から少なくとも 1 項目を残す。粒度の都合で省いた章は「（略：第 n 章）」と書く。
7. 個人名・電話番号（当局の公開窓口を除く）を転記しない。
8. 出力言語は out_lang。原文の重要箇所は原語のまま引用し、必要なら訳を添える。用語は glossary の訳語を使う。
9. 粒度：one_page＝「要点（3 点）／当社への影響／期限／担当部署案／原文の重要箇所」の 5 見出し・A4 1 枚以内。bullets10＝箇条書き 10 行以内。lines3＝3 行。per_chapter＝章ごとの要点。
```


- **ja**（原文 zh、`focus=company_impact`、KB に「塗装は外注 S 社／社内に接着工程」）→ 当社への影響：「当社の塗装は外注だが、**社内の接着工程が対象**（原文 p.7 対象企業の定義、KB：工程一覧）。接着剤の年間使用量が p.22 の『5 t 未満』基準に該当するかは購買実績で確認（所管：購買・管理部）。※ 該当可否の最終判断は法務・当局確認を推奨」
- **zh**（指示「「小规模」的标准在原文哪里？」、Chatflow 版）→ 「原文 p.22 第五章第 12 条：『年间VOC物料…使用量合计不足 5 吨的企业，可采用简易在线监测或定期手工监测替代』。另 p.23 写明使用量以近 1 年采购实绩证明。本公司是否符合请以采购科记录确认（本助手不做判定）」

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 要点の再現 | 人手要約の要点との一致 ≥ 90%、脱落 ≤ 1 項目 | 評価セット 20 文書（ダミー通達・報告書）を人手採点 |
| ページ参照 | 数値・期限・罰則にページ番号 100%、参照先に該当記述がある 100% | 人手抜取（自動でページ内キーワード照合） |
| 捏造 | 原文に無い期限・金額・条文 0 | LLM-as-judge（原文照合）＋負例 |
| 法的助言の抑制 | 「違反になる」等の断定 0 | LLM-as-judge |
| 日本語品質 | 本社担当が「修正なしで使える」≥ 80% | 月次 5 件人手 |
| 個人情報 | 担当者名・電話（架空）の転記 0 | 文字列検査 |
| 言語 | out_lang で出力 100% | 自動判定 |
| 速度 | 40 ページで p95 < 3 分 | Langfuse |

- **評価方法**：リリース前に工場長＋管理部で 20 文書。月次 Langfuse データセット（章要約 JSON を保存し、脱落分析に使う）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **社内情報 KB**（Outline → `PC-05`）：工程一覧・拠点・物料・外注先。「当社への影響」の精度はこれ次第
- **MinerU 自前デプロイ**（`PC-03`）：スキャン PDF・契約書など越境不可文書のため
- **用語集**（`PC-06`）：LG-02 の成果物を流用
- **粒度プリセットと出力テンプレ**（`PC-16`／`PC-13`）：1 枚 md／docx
- **無くても動く範囲**：KB・用語集・MinerU 無しでも Document Extractor＋分割＋Iteration＋統合で**一般要約は動く**（st1 の中身）。影響判断は依頼者が `purpose` に社内事情を書けば代替できる

## 9. Outline Wiki との関係
- **読む**：`PC-05` で「会社概要」「工程一覧」「拠点・組織」「主要物料・外注先」を KB `gn-company-facts` に同期
- **書く**：要約（§5-3）を元文書の Outline ページ（当局通達は KN-05 のコレクション）に「要約（AI ドラフト・確認前）」セクションとして保存する運用は有用（同じ文書を何度も要約しない）。`http-request` で Outline API を呼ぶ経路は `PC-05` の定義待ち — **未確定**

## 10. 未確定・リスク
- **日本語品質**：Qwen3-235B vs DeepSeek-V3.x を本社担当の採点で決める（`PC-08`）。不足なら本社側アプリを別モデルに（F-4）
- **要約の脱落**：章単位の中間要約を保存し（Iteration 出力）、統合で「各章 1 項目」を機械チェック。長大文書は階層要約（章→部→全体）に拡張
- **法規文書の扱い**：本サービスは「読む補助」。当局通達の継続監視・マニュアル反映は KN-05 の責務。両者の境界を UI で示す（`PC-16`）
- **越境**：契約・人事・顧客文書を SiliconFlow に送る可否は文書分類（`PC-10`）で分岐。分類ラベルを Start の select で選ばせる
- **成熟度**：st1 維持
