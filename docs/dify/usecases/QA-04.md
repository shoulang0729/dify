## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：顧客から工程監査の通知とチェックリストが届く（**期限つき案件**：監査日の 3 週間前など。③業務フィードでは `due`）。担当者がチェックリストをアップロードして開く
- **登場人物**：監査対応担当（品質保証課・zh）、証拠を持つ各部署（生産技術・設備保全・営業・物流）、確認者（品質保証課長）、外部：顧客監査員（提出先）
- **いまの手順（Before）**：
  1. チェックリスト 80〜100 項目を Excel で開き、項目ごとに「どの文書・記録が証拠になるか」を担当者の記憶で埋める（2〜3 日）
  2. 文書管理台帳・ファイルサーバ・Outline を横断検索し、最新版か・承認印があるかを確認（2 日）
  3. **不足項目の発見が監査 1 週間前**になり、他部署への依頼が間に合わない
  4. 提出資料をフォルダに集め、ファイル名を整え、日本語文書に中国語表紙を付ける（1 日）
- **エージェント導入後の手順（After）**：
  1. 担当者がチェックリスト（xlsx）と前回監査の指摘事項（PDF）をアップロード
  2. エージェントが各項目を管理文書 KB と照合し、「証拠あり（文書番号・版・場所）／不足／要確認」を項目ごとに判定、区分別の集計表と不足項目の解説を返す。前回指摘の是正状況も突合
  3. **担当者が判定を確認し、不足項目の担当者と期限を決める**（AI は割り振り案まで。組織表があれば候補を出す）
  4. 「提出資料一覧を」でフォルダ構成・ファイル名規約付きの一覧（`PC-13` xlsx）を受け取り、**資料の収集・提出は人**
- **成功の定義**：証拠紐づけの初版を 3 日 → 半日。**監査 2 週間前に不足項目が見える**。前回指摘の是正証拠の欠落 0

## 3. 観点（LLM に守らせる業務ルール）
- **証拠は文書番号で**：「証拠あり」には `doc_no`・版・保管場所（Outline URL／フォルダ）を必ず付ける。文書名の一致だけで「あり」としない（要求事項の内容と文書の内容が対応しているかを見る）
- **最新版・承認済みか**：台帳の `rev`・`approved` を見て、旧版しか無い／承認印なしは「要確認」に落とす
- **期間要件を守る**：「直近 3 か月」「年 1 回」など期間指定は記録の日付で判定。期間外の記録しか無ければ「不足（期間外）」
- **KB 外の証拠は「不足」で正しい**：顧客承認メール・外部校正証明書など KB に無い記録は「不足（KB 外・要取得）」と書く。**あるはずだと推測して「あり」にしない**
- **前回指摘を優先**：前回指摘項目は是正報告・効果確認記録の両方が揃って「あり」。片方なら「要確認」
- **割り振りは案**：担当者・期限は組織表と監査日からの逆算による「案」。確定・依頼は担当者（依頼メールドラフトは作れる）
- **数値を作らない**：項目数・証拠あり件数は Code 集計の値のみ
- **社外秘**：提出資料一覧は「提出予定」。文書本文を顧客向けに要約・改変しない。他顧客名が入る記録（ECR 一覧等）は「他顧客行のマスキング要」と注記
- **不確実なとき**（入力言語で）：「項目 X.X に対応する管理文書が特定できません。要求事項の解釈（どの記録が証拠になるか）を品質保証課長に確認してください」
- **出力の粒度**：区分別集計表（区分／項目数／証拠あり／不足／主な不足項目）→ 不足項目の解説（優先度付き）。詳細は §5-3 JSON → `PC-13` xlsx

## 5. プロンプト
### 5-1. System（項目判定：iteration 内）
```text
あなたは青嶺精工 蘇州工場 品質保証課の監査対応を支援します。工程監査チェックリストの 1 項目について、社内管理文書が証拠として揃っているかを判定します。

守るルール：
1. 判定は <context>（管理文書の検索結果）と <register>（文書管理台帳）だけから行う。あるはずだと推測して「あり」にしない。
2. 「あり」は、要求事項の内容と文書の内容が対応し、台帳上 最新版・承認済み（approved=true）で、期間要件（例：直近 3 か月）を満たすときだけ。
3. 旧版のみ・承認印なし・期間外・是正報告のみ（効果確認なし）は「要確認」。該当文書が無い、または顧客承認メール・外部証明書など KB に無い種類の証拠は「不足」とし、gap_reason に理由（KB 外／期間外／旧版／該当なし）を書く。
4. doc_no・rev・location は文書メタデータの値をそのまま書く。作らない。
5. 出力は JSON 1 個のみ（説明文を付けない）。
6. gap_reason と note は <lang> の言語で書く（日本語なら日本語、中国語なら中国語）。文書番号・文書名は原文のまま。
```

- **`PC-03`／`PC-05`**：管理文書の体系的 KB 化。特に **`section_tag`（監査区分）と `doc_type`・`rev`・`approved`・`period` メタデータ**の付与規約（本サービスの精度はここで決まる）

## 9. Outline Wiki との関係
- **読む**：Outline「管理文書」コレクション（手順書・様式・品質マニュアル）を `kb-control-docs` に同期。Outline の階層（区分フォルダ）を `section_tag` に写像し、文書 URL を `location` に使う。記録類（点検記録・SPC）は Outline ではなくファイルサーバ／MES から
- **書く**：任意。監査ごとの「対応状況・不足項目・提出資料一覧」を Outline「監査対応」コレクションに**ドラフト**として残す（次回監査の `kb-audit-history` 元データになる）。公開・確定は担当者
- Outline を使わない場合：文書管理台帳と SharePoint／ファイルサーバから `PC-03` 直接投入

## 10. 未確定・リスク
