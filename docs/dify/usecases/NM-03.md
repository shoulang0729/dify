## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：毎週金曜（③業務フィードの `routine`）。または本社から実績を問われたとき担当者が能動的に開く
- **登場人物**：製造課長（入力・数字の確認・送付）、ライン班長（日報の書き手）、工場長・本社（読み手）、生産技術（異常値の技術コメント）
- **いまの手順（Before）**：3 ライン×5 日＝15 枚の中国語日報（生産・品質）と設備稼働 CSV を開き、生産数・不良数・停止時間を Excel に転記して合計・率を計算（1 時間）→ 日本語で週報を書く（1 時間）→ 異常値の理由を班長に聞き直す。毎週 2 時間、月末はさらに月報
- **エージェント導入後の手順（After）**：
  1. 課長が当週の生産日報・品質日報・設備稼働記録を**アップロード**（または `PC-11` が金曜 15:00 に共有フォルダから取得）
  2. **Code ノードで**ライン別に生産数・計画・達成率・不良率・稼働率・残業時間を集計し、目標値との差と**異常値**（不良率 > 目標×1.2、停止 > 30 分 等）を判定
  3. LLM が日報の備考欄（中国語）から異常値の理由を引き、**日本語の週報**（表＋トピックス＋異常値コメント）を書く。数値は Code の値を転記
  4. **人が決める場所**：課長が数字と表現を確認して修正、送付先を決める。「対処済み」と書くかどうかは課長の判断
  5. `PC-13` で xlsx/md を出力、任意で `PC-14`（WeCom）に配信
- **成功の定義**：週報作成 2 時間 → 15 分（確認のみ）。集計ミス 0。異常値に理由コメントが毎回付く。日本語品質は本社がそのまま読める

## 3. 観点（LLM に守らせる業務ルール）
- **数値はすべて Code の集計結果を転記**。合計・率・前週比を LLM が計算しない。丸めも Code（率は小数 2 桁）
- **異常値の理由は日報の備考欄に書かれたことだけ**を引く（「日報 9/3 備考：待料 40 分」）。備考が無ければ「理由は日報に記載なし。班長に確認」
- **「対処済み」「収束」等の評価語は根拠（日付・数値の推移）を添え、無ければ書かない**
- **個人名の扱い**：日報の記名（班長名・作業者名）は週報に転記しない（`PC-10`）。技術者名は課長が指示した場合のみ
- **禁止**：欠落データを補完する／目標値を勝手に変える／不良の原因を推測して断定する
- **不確実時の定型文**：「{{line}} {{date}} の {{item}} が読み取れませんでした。集計から除外しています」
- **出力形式**：ライン別表（生産数（計画）・達成率・不良率（目標）・稼働率・トピックス）＋合計行＋異常値コメント（箇条書き）＋任意の「本社向け 3 行」。後工程用は §5-3 の JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（ファイル→週報。`PC-11` からも同じ Workflow を起動）。台本 Q1〜Q2 の深掘りは、集計 JSON を会話変数に持つ **Chatflow** 版で第 2 段階
- **ノード列**：
  1. Start（`files` file-list 必須／`week_label` text／`report_lang` select（ja/zh、既定 ja）／`instruction` paragraph 任意）
  2. Iteration（files）→ Document Extractor（xlsx/csv → 行レコード文字列）
  3. **Code（Python）`aggregate`**：列名正規化（日中辞書）→ ライン×日の生産・不良・停止・残業を集計 → 達成率・不良率・稼働率 → 目標比較・異常値判定（閾値は KB 定義を JSON で渡す）→ 欠落一覧。出力 §5-3 JSON
  4. Knowledge Retrieval（KB `nm-kpi-def`：KPI 定義・目標・不良分類の日中対応）
  5. LLM（`write_report`）：表と異常値コメントを日本語で（§5）
  6. LLM（`hq_summary`、`instruction` があるとき）：3 行サマリー
  7. Code → CSV/xlsx（`PC-13`）／`tools/wecom`（任意配信）
  8. End（`kpi` JSON／`report_md`／`missing` array）
- **Knowledge**：`nm-kpi-def`（Outline 同期。KPI 定義・目標値・不良分類 ja/zh・設備アラームコード表）。日報本体は KB に入れない（毎週の一過性データ。集計は Code）。※ 履歴を溜めて KN-02 の「同じアラームが今月何回」に答える場合は月次で `nm-daily-history` KB に投入（`PC-03`）
- **プラグイン／ツール**：Document Extractor（本体）／Code（本体）／`tools/dify_extractor`（KB 投入）／`tools/microsoft_excel_365`（週報 xlsx、任意）／`tools/wecom`（配信、任意）／Schedule トリガー（本体、`PC-11`）／`datasources/tencent_cos_storage` or `sharepoint_datasource`（定期取得）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（**日本語週報の品質が要**。DeepSeek-V3.x と評価セットで比較）。本社側で海外モデルを使う選択肢は `PC-08`（F-4）
- **参照 DSL**：**`../templates/07-excel-document-extractor-echarts.yml`**（file-list→Document Extractor→LLM）。dsl-skill `03-excel-markdown-analysis`（URL のみ、構成参考）
- **入出力変数**：`files` file-list 必須／`week_label` string 任意／`report_lang` select 必須（既定 ja）／`instruction` string 任意／出力 `kpi` object・`report_md` string・`missing` array・`file_url` string

## 5. プロンプト
### 5-1. System（`write_report`）
```text
あなたは青嶺精工 蘇州工場 製造二課の週報作成アシスタントです。Code ノードが集計した KPI（JSON）と、日報の備考欄（中国語）から、日本本社が読む週報を書きます。
守ること：
1. 数値は JSON の値をそのまま転記する。合計・率・前週比を自分で計算しない。
2. 異常値（anomalies）のコメントは、日報備考（remarks）に書かれた事実だけを引く。書かれていなければ「理由は日報に記載なし。班長に確認」と書く。
3. 「対処済み」「収束」などの評価は、日付と数値の推移が JSON にあるときだけ書く。
4. 作業者・班長の個人名は書かない。設備名・NC 番号・ライン名は書く。
5. missing にある欠落は冒頭に注記する。補完しない。
6. 出力言語は report_lang（既定は日本語）。日本語は本社向けの簡潔な報告文体（「〜です・ます」不要、体言止め可）。用語は glossary（KB）の日本語名を使う。
7. 質問（instruction）が中国語で来た場合、その回答は中国語で書く。ただし週報本体は report_lang。
出力形式：
- 表：ライン｜生産数（計画）｜達成率｜不良率（目標 x%）｜稼働率｜トピックス。最終行に合計。
- 「異常値コメント」：箇条書き 2〜4 件。各件に日付・数値・日報備考の引用。
- 「欠落・注記」。
```
### 5-2. User テンプレート
```text
【週】{{start.week_label}}
【KPI 集計（Code 出力・転記のみ）】{{aggregate.result}}
【日報備考（ライン・日付つき）】{{aggregate.remarks}}
【KPI 定義・用語（KB）】{{knowledge.result}}
【追加指示】{{start.instruction}}
週報を作成してください。
```

### 5-4. Few-shot
- **ja**：anomalies に L3 不良率 0.52%、remarks に「9/1 条件表切换后刀具磨损变化」「9/3 换刀基准 200→180」があるとき → 「L3：新加工条件の適用初日（9/1〜2）に穴径不良が集中し不良率 0.52%。9/3 に工具交換基準を 200→180 本に暫定変更（日報備考）。9/3 以降 0.28%（Code 集計）」
- **zh**（instruction が中国語「L3 9/1〜2 的不良具体是什么？」）→ defect_breakdown を転記：「9/1 不良 58 件（孔径偏小 41、毛刺 12、其他 5）、9/2 39 件（孔径偏小 27、毛刺 9、其他 3）。日报备注：条件表切换后刀具磨损趋势变化」

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 集計の正確性 | Code 出力と Excel 手集計の一致 100% | 評価セット 4 週分（ダミー）を照合 |
| 転記の忠実性 | 週報中の数値が JSON と全件一致 | 正規表現抽出→差分（自動） |
| 異常値の根拠 | コメントの理由が日報備考に存在 100% | 人手（備考との照合） |
| 欠落の扱い | 欠落を補完しない・注記する 100% | 負例セット（日報 1 枚欠け） |
| 日本語品質 | 本社担当が「修正なしで送れる」≥ 80% | 月次 5 件を本社担当が採点 |
| 個人情報 | 作業者名の転記 0 | 文字列検査（名簿ダミー） |
| 速度 | 3 ファイル 15 枚で p95 < 90 秒 | Langfuse |

- **評価方法**：リリース前に製造課長＋本社担当で 4 週分。月次で Langfuse データセット（転記忠実性は LLM-as-judge、日本語品質は人手）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **日報テンプレの固定**（現場運用）：列名・シート構成が揺れると Code 集計が壊れる。揺れる場合は LLM 抽出に切替（精度・コスト増）
- **KPI 定義・目標・不良分類の日中対応表**（Outline → `PC-05` → KB、`PC-06`）
- **共有フォルダの定期取得**（`PC-11`＋`datasources/tencent_cos_storage` or `sharepoint_datasource`）と **WeCom 配信**（`PC-14`）— 任意
- **履歴 KB**（`PC-03`）：月次で集計 JSON を投入すれば NM-05／KN-02 の「先月と比べて」に使える — 任意
- **無くても動く範囲**：手動アップロード＋Code 集計＋日本語週報は KB・スケジューラ・通知が無くても動く。**これが st1 の中身**。KB が無い間は目標値をフォームで入力
