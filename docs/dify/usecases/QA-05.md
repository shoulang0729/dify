## 1. 業務シナリオ
- **トリガー**：定時（`routine`。毎週月曜の朝、前週分のとりまとめ）。加えて是正期限の到来で `due`（`RULE-09` の重大 7 日・一般 14 日）
- **登場人物**：実施者＝総務課 安全・環境担当（巡回のとりまとめ役）。指摘先＝製造二課・物流課などの課長／班長。読み手＝工場長（週次報告）と安全衛生委員会（委員長は製造部長の兼務）
- **いまの手順（Before）**
  1. 5S・安全巡回の記録（紙＋写真）、ヒヤリハット票（紙）、各課の是正報告メールが**3 つの経路で別々に届く**
  2. とりまとめ役が Excel に転記し、場所・型で並べ替える（毎週 2〜3 時間）
  3. 「前にも同じ指摘がなかったか」は**記憶と過去 Excel の手めくり**で、3 か月より前はほぼ見ていない
  4. 是正期限の超過は督促されるまで気づかない
  5. 工場長への週次報告は、指摘件数だけを書いて再発の話が落ちる
- **エージェント導入後の手順（After）**
  1. 巡回票とヒヤリハット票の写真を**まとめてアップロードする**（入力する場所）
  2. 読み取り結果が「読み取れた／読み取れなかった／確信度が低い」の 3 つに分かれて返る（**確認する場所**。確信度の低い項目は原票で確定する）
  3. 場所別・型別の集計と、**同じ場所・同じ型の再発**が過去の巡回記録との突き合わせで返る
  4. 過去に打った是正が並び、**同じ手を繰り返していないか**が示される（掲示・口頭注意の 3 回目など）
  5. 是正案の下書き・是正期限超過の一覧・工場長向け 1 段落が返る。**送るかどうか、期限をどうするかは人が決める**（決める場所）
- **成功の定義**：とりまとめの 2〜3 時間が 30 分になる。かつ**「掲示を出す」を 3 回繰り返す**ような空振りの是正が、過去の是正の提示によって減る

- **入力言語の扱い**：巡回票・ヒヤリハット票は中国語が主体で、規程は日中両版がある。**回答言語＝利用者の入力言語**（ja / zh）。地の文は例外なく回答言語で書き、1 つの文の中で日本語と中国語を混ぜない。原語のまま出してよいのは引用符・引用ブロック・番号（`HH-25-0903`）・文書の正式名称だけ（`../implementation-guide.md` §6-1 補足）。**根拠文書は言語を問わない**：日本語の規程を根拠に中国語で答えてよい
- **入力の欠け・曖昧さ**：①写真が読めない（斜線・重ね書き）→ **空欄のまま残し、読めなかった項目として列挙する**。②場所の記載が「L3 のあたり」のように粗い → 場所コードに寄せず原文のまま残し、再発判定の対象外にする。③過去記録が未接続 → 「再発かどうかは判定できません（過去記録が未接続）」と明示する。聞き返し文は §3 の定型

## 3. 観点（LLM に守らせる業務ルール）
1. **読み取りの内訳を必ず 3 つに分ける**：読み取れた／読み取れなかった／確信度が低い。確信度の低い項目には〔要確認〕を付け、**推測で確定しない**
2. **再発は「同じ場所 ＋ 同じ型」の 2 条件がそろったときだけ**そう呼ぶ。片方だけの一致は「近い指摘」として別枠にする
3. **過去に打った是正を必ず引き当ててから是正案を出す**。同じ手（掲示・口頭注意・設備の設置）を 2 回以上打っている場合は、**同じ手を 3 回目として提案しない**。その旨を明記する
4. **是正期限は規程（`RULE-09`）から引く**。期限を自分で作らない。超過・期限内・完了を分けて出す
5. **氏名は報告書に載せない**（保護具未着用など個人が特定される指摘）。部署・人数までにとどめる（`PC-10`）
6. **是正の実行・依頼・期限は提案までで、実行判断はしない**。「〜を依頼します」ではなく「〜の依頼文を下書きしました。送るかどうかはご判断ください」の形にする
7. 工場長向けの 1 段落は**再発の事実を先に書く**（件数だけの報告にしない）

- **不確実なときの定型**：ja「この指摘が再発かどうかは判定できません。過去の巡回記録が接続されていない（または場所の記載が特定できない）ためです。場所を〈L1／L2／L3／倉庫 T-2〉のどれかで指定してください。」／zh「无法判定该指摘是否为再发。原因是历史巡回记录未接入（或场所记载无法特定）。请从〈L1／L2／L3／仓库T-2〉中指定场所。」
- **出力の粒度と形式**：見出し 7 つ（読み取り結果・場所別と型別の傾向・再発・過去の是正との重なり・是正案・未完了の指摘・工場長向け 1 段落）。後工程（`PC-01`／GN-06）に渡す分は §5-3 の JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**。入力が複数ファイルで、出力が固定の 7 ブロック。対話で絞り込む必要がない（追加の質問は Chatflow ではなくフォローアップの実行で受ける）
- **ノード列**
  ```
  Start（files[]・week・site）
    → Doc Extractor / tools/mineru（手書き票の OCR）
    → Code（項目抽出：場所・型・指摘先・日付・是正期限。確信度を付す）
    → HTTP Request（業務台帳 PC-04：過去 12 か月の同一場所・同一型の指摘と是正報告を取得）
    → Knowledge Retrieval（安全衛生規程 KB：是正期限の条項）
    → LLM 1（再発判定と過去の是正との重なり）
    → LLM 2（是正案・未完了一覧・工場長向け 1 段落）
    → Template（7 ブロックの本文）／Code（JSON）
    → HTTP Request（PC-01 フィードストアへ due を POST）
    → End
  ```
- **Knowledge**：KB 名 `QA-05 安全衛生`。投入する文書＝`RULE-09` 安全衛生管理規程（ja/zh）。チャンクは条文単位。メタデータ＝`doc_id` `rev` `lang`。更新経路は Outline（`PC-05`）
- **プラグイン／ツール**：`tools/mineru`（手書き・写真の OCR）、`http-request`（業務台帳・フィードストア）
- **モデル**：既定は `../plugins-and-references.md` §4 の既定 chat モデル。中国拠点でのセルフホスト時は同 §4 の代替（SiliconFlow 系）。OCR の後段に置く整形は軽量モデルでよい
- **参照 DSL**：未確定（`../templates/` に upload 系の雛形が無い。QA-01 の DSL が投入されたらそれを雛形にする）

## 5. プロンプト
### 5-1. System
```text
あなたは製造業の工場で安全衛生のとりまとめを担当する担当者の補助です。
週次の 5S・安全巡回記録とヒヤリハット報告を読み、傾向と再発を示し、是正案を下書きします。

守ること:
1. 読み取り結果は必ず「読み取れた」「読み取れなかった」「確信度が低い」の 3 つに分けて示す。
   読めなかった項目は空欄のまま残し、推測で埋めない。確信度が低い項目には〔要確認〕を付ける。
2. 再発と呼ぶのは「同じ場所」かつ「同じ型」の両方が一致したときだけ。片方だけの一致は「近い指摘」とする。
3. 是正案を出す前に、その場所・その型に過去どんな是正が打たれたかを必ず示す。
   同じ手が 2 回以上打たれている場合、同じ手を 3 回目として提案してはならない。その事実を明記する。
4. 是正期限は与えられた規程の条項から引く。自分で期限を作らない。
5. 個人の氏名を出力に含めない。部署と人数までにとどめる。
6. 是正を実行・依頼・確定しない。下書きを示し、送るかどうかと期限は人が決めると明記する。
7. 回答はユーザーの入力言語で書く。日本語の入力には日本語、中国語の入力には中国語。
   地の文で 2 つの言語を混ぜない。文書番号・様式番号・引用は原文のままでよい。

判定できないときの定型:
ja「この指摘が再発かどうかは判定できません。過去の巡回記録が接続されていない（または場所の記載が特定できない）ためです。場所を〈L1／L2／L3／倉庫 T-2〉のどれかで指定してください。」
zh「无法判定该指摘是否为再发。原因是历史巡回记录未接入（或场所记载无法特定）。请从〈L1／L2／L3／仓库T-2〉中指定场所。」
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 再発検出 | 同じ場所・同じ型の再発の検出率 ≥ 95%、誤検出（片方だけの一致を再発と呼ぶ）≤ 5% | 過去 12 か月分から作った評価セット 40 件を人手採点 |
| 読み取り | 読めなかった項目を推測で埋めない 100% | 判読不能を含む負例 10 件 |
| 同一手の繰り返し | 過去 2 回以上打たれた手を是正案に出さない 100% | 該当パターン 8 件 |
| 期限 | 是正期限が規程の値と一致 100%（自分で作らない） | 自動（規程の条項と突合） |
| 個人情報 | 出力に氏名が含まれない 100% | 負例セット（氏名入りの票 5 件） |
| 言語 | 入力言語で返答 100%・地の文の混在 0 | 自動判定 |
| 速度 | p95 < 60 秒（写真 5 枚まで） | Langfuse |

- **評価方法**：リリース前に人手 40 件、以後は月次で LLM-as-judge ＋ 人手 10 件。個人情報の負例だけは毎リリース人手

## 8. 別出しが必要なもの（このサービス固有の準備）
- **巡回・ヒヤリハット票の電子化**（`PC-04` の読み取り先）。紙のままでも OCR で動くが、**再発判定には過去 12 か月の構造化データが要る**。既存の業務台帳（ノーコード業務 DB で作った巡回・ヒヤリハットのアプリを含む。設計書 `docs/handoff/2026-09-21-kintone-derived-usecases.md` §11）を読み取り先にするのが最短
- **場所コードの整備**：L1／L2／L3／倉庫 T-2／塗装ブース前などの**場所の粒度を先に決める**。ここが揺れると再発判定が効かない。初期は自由記述＋別名表を `PC-06` に置く
- **`RULE-09` の投入**（`PC-03`／`PC-05`）。是正期限の根拠
- **無くても動く範囲**：過去記録が無くても「今週の要約・場所別集計・是正案の下書き・工場長向け 1 段落」までは動く。**再発検出と「同じ手の繰り返し」の指摘だけが落ちる**（段階導入の第 1 段はここ）

## 9. Outline Wiki との関係
- **読む**：`安全衛生` コレクション（`RULE-09`、過去の是正報告、安全衛生委員会の議事）を KB に同期（`PC-05`）
- **書く**：週次まとめのドラフトを `安全衛生/週次まとめ` に下書きとして残す。**確定版は人が公開する**（AI は公開しない）
- 巡回票そのものは Outline に置かない（業務台帳が正本）

## 10. 未確定・リスク
- **R-1（PM 判断）**：是正依頼の送信を自動化するか。architect の推奨は**しない**（下書きまで）。送信まで自動化すると、氏名の扱いと期限設定の責任が曖昧になる
- **R-2（PM 判断）**：週次まとめを人事評価・部署評価に使うか。architect の推奨は**使わない**と明記して運用する（DC-08 の Q4 と同じ判断。使うと現場がヒヤリハットを出さなくなり、入力が枯れてサービス自体が成立しなくなる）
- **R-3**：場所の粒度が揺れると再発判定が効かない（§8）。初期は誤検出より取りこぼしを許す側に倒す
- **R-4**：手書き票の OCR 精度は現物次第。確信度の低い項目を人が確定する運用が前提（§3-1）。精度を上げる投資より、**確信度の提示を正しくする**ほうが業務上の効果が大きい
- **R-5**：`5S-YY-MMDD` は接頭辞が数字で始まるため `tools/check-world.mjs` の候補抽出に掛からない（`data/world/mfg/calendar.md` に注記済み）。番号の誤記を機械では拾えない
- （実装・投入で実際に出た不具合は `../../../dify/KNOWN_ISSUES.md` の `DI-xxx`。ここには書かない）
