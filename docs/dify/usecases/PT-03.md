## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：担当者が能動的に開く。典型は「社内ナレッジ（KN-01）を使い切ったとき」＝KN-01 の回答に「社内記録に該当なし」が出た後の次の一手。本社への設備提案・技術報告の裏付けが要るとき
- **登場人物**：生産技術課主任（質問・まとめ）、生産技術課長（確認）、本社設備部（提案の読者）、外部＝記事アーカイブ（検索・要約の返却のみ）
- **いまの手順（Before）**：ライン 3 の切りくず詰まりが再発 → 社内の技術報告（TR-）・不具合票（NC-）を読み直す（30 分）→ 業界誌のバックナンバーを棚から探す・Web で断片的に検索（1〜2 時間）→ 見つけた記事の条件と当社の条件を Excel で並べる → 本社提案の裏付け文を書く（30 分）。出典が曖昧で、翌年同じ問題で同じ検索をする
- **エージェント導入後の手順（After）**：(1) 担当者が中国語（または日本語）で**質問を入力**する → (2) Dify が社内技術 KB（KN-01 と同じ）と、`PC-15` 経由の外部 KB（記事アーカイブ）を**並列に検索**し、社内記録と社外記事を並べて要点・出典（記事 ID）付きで返す → (3) 担当者が追加質問で当社ライン条件との比較を求め、**投資判断の材料を確認**する → (4) 担当者が「3 行にまとめて」と頼み、**内容を確認して** DC-01 の設備投資テンプレートに貼る（貼るのは人）
- **成功の定義**：他社事例の探索 2.5 時間 → 15 分。回答に必ず「社内記録」と「社外記事（ID）」の両方の出典が付き、本社提案の裏付けとして再利用できる

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |

| 社外記事 | JSON（記事 ID・誌名・号・タイトル・要約・言語・種別〔記事／広告〕・公開日） | zh / ja / en | 1 質問 3〜10 件 | 『精密加工技術』2026/5「MQL＋高圧内部給油」 | 記事アーカイブ（External Knowledge API または検索 API。`PC-15` 経由） | 種別「広告」の明示・言語タグ・本文は保持しない（要約とメタのみ） |

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。英語 UI でも同じ。記事の言語が回答言語と違うときは、記事タイトルは原語のまま・要約は回答言語で書き、**記事の言語を明示**する（例「（中国語記事）」）
- **入力の欠け・曖昧さ**：材料・加工法・困りごとの 3 つが揃わないと検索精度が落ちる。欠けたら 1 回だけ聞き返す：ja「材料（例：SUS304）、加工（例：深穴ドリル L/D=8）、困りごと（例：切りくず詰まり）のうち無いものを教えてください」／zh「请补充材料（如 SUS304）、加工（如深孔钻 L/D=8）、问题（如切屑堵塞）中缺少的项目」。両 KB とも 0 件なら「社内記録・記事アーカイブともに該当がありません。条件を広げるか、記事アーカイブの収録範囲外の可能性があります」

## 3. 観点（LLM に守らせる業務ルール）
- **社内と社外を分けて並べる**：回答は「社内記録（TR-/NC-）」と「社外記事（ID）」を別の塊にし、最後に「差分＝当社の改善余地」を書く。混ぜて 1 つの結論にしない
- **出典は記事 ID 単位**：誌名・号・タイトル・記事 ID・公開日・言語・種別。**本文の転載禁止**（要約 3 行以内、引用 1 文以内）。広告記事は「（広告）」を付け、性能主張は「メーカー主張」と書く
- **数値は記事に書かれた条件を条件つきで**：「記事① は SUS316・L/D=10 で 7 MPa」のように材料・条件を添え、当社条件（SUS304・L/D=8）にそのまま当てはまるとは言わない
- **設備台帳に無い当社仕様は推測しない**：「当社の現行圧力は台帳に記載なし。設備課に確認してください」
- **投資額・効果は出典付きの範囲で**：記事の値を転記し「当社換算は概算」と明示。ROI の断定をしない
- **送っていないものを明示**：外部へ送ったのは検索語（材料・加工・症状）のみ。社内の技術報告番号・不具合番号・図番・顧客名・ライン番号は送信していない、と回答の末尾（または「連携」相当の 1 行）に書く
- **不確実なときの定型**：ja「記事アーカイブに該当する記事が見つかりません。検索語を変えるか、収録範囲（誌名・期間）を確認してください」／zh「文章档案中未找到相关文章。请更换检索词或确认收录范围（期刊・期间）」
- **出力の粒度と形式**：多輪チャット。1 回目は「社外記事 3 件（各 3 行）→ 社内記録との差分 1 段落」、2 回目以降は質問に応じた比較表（Markdown）、「3 行にまとめて」は番号付き 3 行＋出典行

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（多輪。社内記録と社外記事を往復しながら深める用途。KN-01 と同型）
- **ノード列**：
  1. Start（`sys.query`, `sys.files` なし）
  2. `code`（言語判定 `PC-07`／外部クエリの生成：`PC-06` で工法・材料を正規化し、**社内識別子・顧客名・図番・ライン番号を正規表現で除去**した `external_query` を作る）
  3. `knowledge-retrieval` ①（社内技術 KB。KN-01 と同じ dataset。`bge-m3`＋`bge-reranker-v2-m3`）
  4. `knowledge-retrieval` ②（**External Knowledge API** で記事アーカイブを外部 KB として接続。クエリは `external_query`。`PC-15` が Dify 仕様の `POST /retrieval` を中継し、ライセンス・レート制限・送信ログを担う）
     - 代替：External Knowledge API がパートナー側で用意できない場合は `http-request`（`PC-15` の検索エンドポイント）→ `code`（Dify の retrieval 結果形式に整形）
  5. `if-else`（両方 0 件 → 定型文／片方 0 件 → その旨を明示して続行）
  6. （設備比較の質問のとき）`http-request` or `knowledge-retrieval` ③（社内設備台帳。`PC-04` か Outline。無ければスキップ）
  7. `llm`（§5。社内／社外を分けて回答。入力言語）
  8. Answer（末尾に送信最小化の 1 行）
- **Knowledge**：(a) 社内技術 KB＝KN-01 の dataset を参照（**再投入しない**。更新経路も KN-01 と共通＝Outline → `PC-05`）。(b) 外部 KB＝External Knowledge API（検索のみ。Dify 側にデータを持たない。**KB へのコピー禁止**＝ライセンス）。(c) 設備台帳 KB（任意。メタデータ `line` `equipment_id`）
- **プラグイン／ツール**：External Knowledge API（本体。`../plugins-and-references.md` §6）／HTTP リクエストノード（代替）／Code ノード／`tools/regex`（識別子除去をノーコードで済ませたい場合）
- **モデル**：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（中国語主）。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`（`PC-08`）。日本語の 3 行まとめは本社向けなので DeepSeek-V3.x と比較
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（複数 KB を分けて検索して LLM に渡す骨格。外部 KB を 2 つ目の `knowledge-retrieval` として置き換える）。External Knowledge API の DSL 例は保存 DSL に無いため、Dify 画面で外部 KB を作成してから export したものを正にする
- **入出力変数**：

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `sys.query` | string | ✓ | 質問（多輪） |
| `external_query` | string | 内部 | 識別子除去後の検索語（`PC-15` へ送る唯一のデータ） |
| `internal_hits` | array | 内部 | 社内 KB の検索結果 |
| `external_hits` | array | 内部 | 記事メタ＋要約（本文なし） |
| `answer` | string | 出力 | 回答（Markdown） |
| `citations` | array | 出力 | `[{type: internal|external, id, title, lang, kind: article|ad}]` |

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）生産技術課の技術リサーチアシスタントです。
入力として (A) 社内技術 KB の検索結果（技術報告 TR-、不具合票 NC-、作業標準書）、(B) 記事アーカイブの検索結果（記事 ID・誌名・号・タイトル・要約・言語・種別〔記事／広告〕・公開日。本文は無い）、(C) あれば社内設備台帳の該当行、が与えられます。

守ること：
1. 回答は「社外記事」と「社内記録」を分けて書き、最後に「当社との差分（改善余地）」を 1 段落で書く。混ぜて 1 つの結論にしない。
2. 記事は 1 件ごとに「誌名・号／タイトル／記事 ID／言語／種別」を付け、要約は 3 行以内、引用は 1 文以内。本文の転載をしない。種別が広告なら「（広告・メーカー主張）」と明記する。
3. 記事中の数値・条件（材料・L/D・圧力・送り・費用・効果）は、その記事の条件を添えて転記する。当社条件にそのまま当てはまるとは書かない。
4. 当社の仕様値は (C) にあるものだけを使う。無ければ「設備台帳に記載なし。設備課に確認してください」。
5. 投資額・効果の当社換算は「概算」と明示し、ROI や採用可否を断定しない。決めるのは担当者と課長。
6. 回答の最後に 1 行：「記事アーカイブへ送信した検索語：〈{{external_query}}〉。社内の報告番号・不具合番号・図番・顧客名・ライン番号は送信していません。」
7. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。記事タイトルは原語のまま、要約は回答言語で。記事の言語が回答言語と違えば「（中国語記事）」「（日本語記事）」と添える。
8. 該当なしの定型：「記事アーカイブに該当する記事が見つかりません。検索語を変えるか、収録範囲（誌名・期間）を確認してください」／中国語「文章档案中未找到相关文章。请更换检索词或确认收录范围（期刊・期间）」。社内 KB も 0 件なら両方に該当なしと書く。
9. パートナーは「記事アーカイブ検索サービス」と呼ぶ。実名・製品名を作らない。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（出典整合） | 記事の要約・数値がアーカイブ応答の要約と矛盾しない ≥ 95% | 人手 30 件（生産技術課長） |
| 分離 | 社外／社内／差分の 3 部構成 100% | チェックリスト（自動：見出し検出） |
| 出典 | 記事ごとに ID・誌名・号・言語・種別 100% | 正規表現チェック |
| 転載 | アーカイブ要約との連続 40 字以上一致 0 件（本文は保持しないので要約との比較） | n-gram 照合 |
| 言語 | 入力言語で返答 100%。記事言語の明示 100% | 自動判定（`PC-07`）＋抜き取り |
| 拒否 | 両 KB 0 件で定型文 ≥ 95%。設備値を推測しない 100% | 負例セット 20 件 |
| 安全 | `external_query` に TR-/NC-/図番/顧客名/ライン番号が含まれない 100% | `PC-15` 送信ログ監査（正規表現） |
| 検索品質 | 上位 3 件に「関連あり」と人が判定 ≥ 70%（パートナー依存） | 評価セット 30 問・人手 |
| 速度 | p95 < 15 秒（2 KB 並列） | Langfuse |

- **評価方法**：リリース前に生産技術課 2 名が 30 問を採点。月次は Langfuse データセット＋LLM-as-judge（3 部構成・出典有無・転載なし）。`external_query` の除去規則は pytest（識別子パターン網羅）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-15`**：記事アーカイブとの**ライセンス契約**（検索 API の利用範囲、要約の社内保存・日本本社への転送可否、記事本文の閲覧権＝誰がアーカイブ側で読めるか、レート制限、課金＝月額か検索従量か）。External Knowledge API 仕様（`POST /retrieval`）の中継実装、または検索 API → retrieval 形式への変換。送信クエリのホワイトリスト（識別子除去は Dify 側 `code` と `PC-15` の**二重**で）と送信ログ
- **`PC-10`**：API キー管理。著作権方針（要約・ID のみ保持、本文は Dify に入れない）。個人情報は原則なし（記事著者名は表示可の範囲を契約で確認）
- **`PC-06`**：工法・材料・工具用語の日中英対訳（深穴／深孔、ステップ送り／分段进给、MQL 等）
- **社内**：KN-01 の技術 KB が前提（PT-03 単独では社内側が空になる）。設備台帳の整備は任意（無くても動く）
- **無くても動く範囲（段階導入）**：
  - 段階 0（契約前）：`PC-15` モックモード＋KN-01 の KB。3 部構成・識別子除去・出典表示の確認とデモ
  - 段階 1：記事アーカイブの検索 API 接続（`http-request` 代替でも可）
  - 段階 2：External Knowledge API へ移行（Dify 標準の外部 KB として運用）、設備台帳 KB の追加

## 9. Outline Wiki との関係
- **読む**（`PC-05`）：「生産技術／技術報告」「品質／不具合票」「生産技術／作業標準書」＝KN-01 と同じコレクション（同期先の dataset を共用）。「設備／台帳」（あれば）
- **書く**：「3 行まとめ」と出典（記事 ID・社内記録番号）を「生産技術／調査メモ」にドラフト保存（担当者のボタン操作。`PC-13`）。**記事の要約本文は保存しない**（ID とタイトルのみ。ライセンス）。保存したメモは次回の社内 KB 検索で「過去に調べた」として引けるようになる（KN-01 の KB に自然に入る）
- 記事アーカイブの検索結果そのものは Outline に置かない

## 10. 未確定・リスク
- **External Knowledge API をパートナー側が用意できるか**：未確定。用意できなければ `http-request` 代替（`PC-15` が retrieval 形式に変換）。どちらでもプロンプトは同じ
- **著作権・ライセンス**：要約の社内保存と日本本社への転送は契約次第（PM／法務）。architect 推奨：**Dify・Outline には ID・タイトル・自分で書いた 3 行まとめだけを残す**運用を初期値にする
- **検索品質はパートナー依存**：日本語・中国語の記事が混在し、クロスリンガル検索の精度が読めない。`PC-06` の対訳で検索語を 2 言語併記して送る案は、送信データが増えるので `PC-15` のホワイトリストと整合を取る
- **KN-01 との境目**：KN-01 の回答に「社内に該当なし」が出たら PT-03 を勧める導線は `PC-16` 判断。台本は「社内記録は使い切った」を前提にしている
- **設備台帳**：`PC-04` で設備管理システムから引くか Outline に表で置くかは未確定。無い間は「記載なし」で動く
