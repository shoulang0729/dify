## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（訪問・面談の前）。③業務フィードでは `due`（訪問予定日が近いと促す想定。本 PR では未実装）
- **登場人物**：法人営業の担当者・部門長（面談に臨む側）、面談相手（既存与信先・候補先）
- **いまの手順（Before）**：担当者が過去のやり取り記録・稟議の進捗・公開情報を個別に見て回り、頭の中で整理してから訪問する。移動中に見返せる形にまとまっておらず、聞き忘れが起きる
- **エージェント導入後の手順（After）**：
  1. 面談相手と目的（同行者含む）をフォームに入れる
  2. 直近の取引・接触履歴・公開情報・未了の宿題を 1 枚にまとめたブリーフが返る
  3. 担当者が**聞くべき質問の候補を確認し、訪問に備える**（AI は面談内容を代行しない）
- **成功の定義**：移動中に読める分量のブリーフが用意され、訪問前の情報整理にかかる時間が減る

## 3. 観点（LLM に守らせる業務ルール）

- **1 枚に収める**：移動中に読める分量（見出し 5 項目・各 2〜3 行）に絞る。網羅性より簡潔さを優先する
- **未了の宿題は期限・状態を必ず添える**：`GN-06` から取得した宿題は「未着手」「決裁待ち」等の状態と期限をそのまま転記する。**担当者が代わりに進めたことにしない**
- **公開情報が無いときは「モニタリング対象外」と明示する**：`RS-01` の監視設定が無い相手について、ネガティブ情報が無いことと、そもそも調べていないことを混同しない
- **聞くべき質問は 2〜3 件に絞る**：業務上の意味がある質問（決算・与信に影響するもの）を優先し、世間話レベルの質問は含めない
- **禁止**：接触履歴・宿題の状態を推測で埋める／面談相手の個人情報（家族構成等）を含める
- **不確実なとき**（入力言語で）：ja「接触履歴の情報が不足しています。手元の記録を追加で入力してください。」／zh「接触记录信息不足，请补充手头的记录。」
- **出力の粒度**：直近の取引 → 接触履歴（要約）→ 公開情報 → 未了の宿題 → 聞くべき質問の候補（2〜3 件）

## 4. Dify 構成

- **アプリ種別**：**Workflow**（フォーム入力 → 実行 → 1 枚のブリーフ）
- **ノード列**：
  1. `Start`（面談相手・同行者・目的）
  2. `HTTP Request`（`GN-06` の `tasks` API から未了の宿題を取得。`owner`/`client` で絞る）
  3. `HTTP Request`（`RS-01` の監視設定・直近収集結果を取得。無ければ空）
  4. `Code`（接触履歴の手入力欄と①②の結果をまとめ、時系列に整理）
  5. `LLM`（ブリーフの組み立て・質問候補の生成。§5 のプロンプト）
  6. `Answer`（1 枚のブリーフ）
- **Knowledge**：使わない
- **プラグイン／ツール**：**HTTP リクエストノード**（`GN-06`・`RS-01` の API 呼び出し。`../plugins-and-references.md` §6 の型）
- **モデル**：既定 `models/siliconflow` Qwen3-32B（要約中心のため軽量モデルで足りる）
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`、`../templates/06-text-to-sql-http-api-echarts.yml`（外部 API 連携の型）
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `client_id` | string | ✓ | 面談相手（`data/world/fin/clients.csv` の記号） |
  | `companions` | string[] | — | 同行者 |
  | `purpose` | string | ✓ | 目的 |
  | `contact_history_manual` | string | — | 接触履歴の手入力（`KN-07` 未実装の間） |
  | 出力 `brief` | object | ✓ | ブリーフ本体（§5-3） |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 営業第一部の面談前ブリーフ作成アシスタントです。
指定された面談相手・目的について、直近の取引・接触履歴・公開情報・未了の宿題（{{tasks_json}}）を1枚のブリーフにまとめます。
守ること：
1. 移動中に読める分量（見出し5項目・各2〜3行）に絞る。
2. 未了の宿題は状態と期限をそのまま転記する。担当者が対応済みであるかのように書かない。
3. 公開情報のモニタリング対象外の相手には「モニタリング対象外」と明示する（ネガティブ情報が無いことと区別する）。
4. 聞くべき質問は2〜3件に絞り、業務上の意味がある質問だけを挙げる。
5. 接触履歴・宿題の情報が不足しているときは推測で埋めず、不足している旨を書く。
6. 面談相手の個人情報（家族構成等）を含めない。
7. 言語：担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：直近の取引 → 接触履歴（要約）→ 公開情報 → 未了の宿題 → 聞くべき質問の候補（2〜3件）の順。
```

### 5-2. User テンプレート

```text
面談相手={{client_id}}／同行者={{companions}}／目的={{purpose}}
未了の宿題（GN-06 tasks API 転記）：{{tasks_json}}
公開情報（RS-01 監視結果。無ければ「モニタリング対象外」）：{{rs1_json}}
接触履歴（手入力）：{{contact_history_manual}}
```

### 5-3. 出力フォーマット

```json
{
  "client_id": "甲社",
  "recent_deals": ["運転資金貸出（既存極度2,000万元）", "設備資金貸出の増額を稟議中（RNG-2026-0142）"],
  "contact_history": ["前々回：設備資金貸出の追加枠を打診", "前回：為替予約の更新時期を確認（TK-26-0041として対応中）"],
  "public_info": { "status": "monitoring_not_set", "note": "甲社は当行の日常モニタリング対象外" },

  "questions": ["新ライン増設の稼働開始予定時期", "クロスボーダー人民元送金の利用頻度が増える見込みか"]
}
```

**不要**。面談相手ごとに事実が異なるため、書式は System と JSON スキーマで固定する。

## 8. 別出しが必要なもの

- **`GN-06` の `tasks` API への依存**：`GET /tasks?owner=&client=` で未了の宿題を取得する。GN-06 のテーブル設計（`docs/dify/usecases/GN-06.md` §4）に `client_id`（面談相手）で絞る列が無いため、**GN-06 側にフィルタ項目の追加が必要**（本ファイルでは提案のみ。GN-06 の担当 PR で確認）
- **`KN-07`（行内営業情報の検索）との連携**：本 PR では KN-07 が未実装のため、接触履歴は手入力で代替する。KN-07 実装後は自動取得に切り替える
- **無くても動く範囲**：`GN-06`/`RS-01` との連携が無くても、担当者が接触履歴・宿題を手入力すればブリーフ作成自体は動く
