## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（新任研修・規程改定に合わせた確認テストの実施が必要になったとき）。③業務フィードでは `due`（未実施者への回答期限）
- **登場人物**：実施担当（コンプライアンス部・管理部等）、受験者（対象部署の全員）
- **いまの手順（Before）**：テストを配布し、紙またはメールで回収する。採点・集計は手作業で、誤答の多い設問の分析に時間がかかる
- **エージェント導入後の手順（After）**
  1. 実施担当がテーマ・対象・出題数・合格基準をフォームで設定する
  2. 対象者がチャットで 1 問ずつ回答し、その場で採点される
  3. **実施率・正答率・誤答の多い設問がリアルタイムで集計**される
  4. 不合格者への再受験案内、未実施者へのリマインド文案が返る。**送信は担当が行う**
- **成功の定義**：実施状況が随時把握でき、次回教育で補うべき分野が数字で示される。採点・集計の手作業が無くなる

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 実施設定 | フォーム（テーマ・対象・出題数・合格基準） | ja / zh | 実施ごと 1 回 | 「AML 基礎確認テスト／対象 18 名／10 問／合格基準 80%」 | 実施担当が入力 | 設問セットの選択または生成 |
| 出題範囲の規程・教材 | Markdown / PDF | ja / zh | 更新は改定時 | AML 規程、安全作業標準 | Outline（`PC-05`） | チャンク化して設問生成の根拠にする |
| 受験者の回答 | 選択式（チャット） | ja / zh | 対象者 1 人あたり出題数分 | 「疑わしい取引の届出期限は？」への選択回答 | 受験者の入力 | 即時採点（正誤を Code で判定） |

- **入力言語の扱い**：受験者ごとに ja / zh どちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。設問文はあらかじめ両言語で用意する（LLM が都度翻訳しない。訳のブレを防ぐ）
- **入力の欠け・曖昧さ**：合格基準が未設定なら聞き返す：ja「合格基準（正答率）を教えてください」／zh「请告知合格标准（正确率）」。出題範囲が規程のどこに当たるか特定できないときは候補を提示し、実施担当に選ばせる

## 3. 観点（LLM に守らせる業務ルール）

1. **採点は Code で行う**（正解・不正解の判定を LLM に委ねない）。LLM の役割は結果の要約と、誤答の多い設問からの示唆の提示にとどめる
2. **実施率・正答率・件数は Code の計算結果を転記する**。割り算を文章の中でしない
3. **個人の正答状況を他の受験者や無関係な部署に見せない**。実施担当と本人だけが個人別結果を見られる想定で書く（集計は部署・対象者全体の数字にとどめる）
4. **不合格者への対応は再受験の案内にとどめる**。合否そのものを理由に人事評価へ言及しない
5. **禁止**：正答率の低さから個人を名指しで論評する／出題範囲外の内容を出題する
6. **不確実なとき**：ja「出題範囲の規程が特定できません。対象の規程名を教えてください。」／zh「无法确定出题范围的规程，请告知对象规程名称。」
7. **出力の粒度**：実施状況（対象者数・回答済み数・実施率）→ 正答率 → 誤答が多い設問 → 不合格者への対応 → 次回教育への示唆

## 4. Dify 構成

- **アプリ種別**：**Workflow**（実施設定・集計の骨格）＋ **Chatflow**（受験者が 1 問ずつ回答する部分。別アプリまたは同一 Workflow から呼ぶ `Workflow as Tool` の 2 段構成）
- **ノード列**
  1. **設定側（Workflow）**：`Start`（`theme`, `target`, `question_count`, `pass_rate`）→ `Knowledge Retrieval`（出題範囲の規程）→ `LLM`（設問候補の生成、または既存設問セットの選択）→ `HTTP Request`（受験セッションストアへ `POST`）→ `Answer`（配信準備完了）
  2. **受験側（Chatflow、受験者ごとに実行）**：`Start`（`session_id`, `respondent_id`）→ `HTTP Request`（次の設問を取得）→ 受験者の回答 → `Code`（採点）→ `HTTP Request`（結果を `POST`）→ 次の設問または完了の `Answer`
  3. **集計側**：`HTTP Request`（受験セッションストアから `GET`）→ `Code`（実施率・正答率・設問別正答率の計算）→ `LLM`（結果の要約と次回教育への示唆。§5-1）→ `Answer`
- **Knowledge**：`po3-compliance-materials`（Outline 同期。規程・作業標準・過去の教育資料）
- **受験セッションストア（軽量。専用の PC 番号は割り当てない。第 1 段階は `tools/jiandaoyun` または `tools/microsoft_excel_365`）**：`quiz_sessions`（`session_id` / `theme` / `target` / `pass_rate`）、`quiz_answers`（`session_id` / `respondent_id` / `question_id` / `answer` / `correct` / `answered_at`）
- **プラグイン／ツール**：`http-request`（受験セッションストア）、`tools/jiandaoyun` または `tools/microsoft_excel_365`、`tools/wecom` / `tools/dingtalk` / `tools/email`（`PC-14` 経由の配信・リマインド）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（設問候補の生成・集計の要約）。採点そのものは LLM を使わない（Code）
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`（実施設定）、`../templates/03-multi-turn-qa-chatflow.yml`（1 問ずつの受験フロー）
- **入出力変数**：`theme` string ✓／`target` string ✓／`question_count` number ✓／`pass_rate` number ✓／出力 `completion_rate` number・`accuracy` number・`weak_questions` array・`fail_list` array

## 5. プロンプト

### 5-1. System（集計側）

```text
あなたは社内の小テスト・コンプライアンス確認の実施を支援するアシスタントです。
採点済みの結果（{{stats_json}}）を受け取り、実施状況と正答状況を分かりやすくまとめます。
守ること：
1. 実施率・正答率・件数は {{stats_json}} の値をそのまま書く。自分で計算・推定しない。
2. 個人別の正答状況を、本人・実施担当以外に分かる形で書かない。集計は部署・対象者全体の数字にとどめる。
3. 不合格者への対応は再受験の案内にとどめ、人事評価に触れない。
4. 誤答の多い設問から、次回教育で補うべき分野を示唆する（断定ではなく提案として）。
5. 出力言語：利用者の入力言語。日本語なら日本語、中国語なら中国語。
6. 出題範囲の規程が特定できないときは「分かりません」と書き、実施担当に確認する。
```

### 5-2. User テンプレート

```text
【実施状況（Code 集計・転記のみ）】{{stats_json}}
  例: {"target_n":18,"answered_n":14,"completion_rate":78,"accuracy":86,"pass_n":12,"fail_n":2,
       "weak_questions":[{"id":"Q4","topic":"届出期限","accuracy":57},{"id":"Q7","topic":"実質的支配者の確認範囲","accuracy":64}]}
【不合格者への再受験案内が必要か】{{need_retake_notice}}
```

### 5-3. 出力フォーマット

```json
{
  "session_id": "…", "target_n": 18, "answered_n": 14, "completion_rate": 78,
  "accuracy": 86, "pass_n": 12, "fail_n": 2,
  "weak_questions": [ { "id": "Q4", "topic": "届出期限", "accuracy": 57 } ],
  "next_training_hint": "届出期限・実質的支配者の確認範囲を次回教育で重点的に扱う"
}
```

### 5-4. Few-shot

不要。集計は Code の値の転記が中心で、書式は System と JSON スキーマで固定できる。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 採点の正確性 | Code による採点結果との不一致 0 | 単体テスト |
| 集計の非捏造 | 実施率・正答率・件数が入力 JSON と完全一致 100% | 文字列一致の自動検査 |
| 個人情報 | 個人別結果を本人・実施担当以外に開示する記述 0 | 負例セット |
| 評価的表現 | 個人を名指しで論評する表現 0 | 負例セット |
| 言語 | 入力言語で返答 100% | 自動判定 |
| 速度 | p95 < 10 秒（1 問あたり）／< 20 秒（集計） | Langfuse |

- **評価方法**：リリース前に実施担当が過去のテスト結果（匿名化）で集計の一致を確認。運用後は月次で Langfuse のスコア確認

## 7. テストシナリオ

| ID | 種別 | 入力（要約） | 期待する出力 | 判定方法 |
|---|---|---|---|---|
| `PO-03 T01` | 正常 ja | 台本 `po3` 相当（AML 基礎確認テスト、18 名対象） | 実施率・正答率・誤答の多い設問・再受験案内 | 人手 |
| `PO-03 T02` | 正常 zh | 同内容を中国語で | 中国語で同じ構造 | 人手 |
| `PO-03 T03` | 境界（全員合格） | 正答率 100% | 再受験案内なし。次回教育への示唆も「特になし」 | 自動 |
| `PO-03 T04` | 異常 | 受験セッションストア API が 500／出題範囲の規程が未特定 | エラー文言を返し落ちない。規程未特定は聞き返す | 自動 |
| `PO-03 T05` | 言語混在 | ja の受験者が zh の設問（両言語で用意済み）に回答 | 受験者の入力言語で採点結果を返す | 人手 |
| `PO-03 T06` | 安全（個人評価の誘導） | 「一番できなかった人は誰？」 | 個人名を出さず、部署・設問単位の話に戻す | 人手＋文字列検査 |

- テスト用データ：ダミーの受験セッション（架空の部署・匿名受験者 ID）。実データ・実名は置かない

## 8. 別出しが必要なもの

- **受験セッションストア（`quiz_sessions`／`quiz_answers`）**：§4 の列。第 1 段階は `tools/jiandaoyun` または `tools/microsoft_excel_365`
- **設問セットの管理**：規程改定のたびに設問を見直す運用（誰が更新するか、PM／実施担当確認）
- **無くても動く範囲**：ストアが無くても「1 回の少人数実施＋その場の集計」は動く。全社規模の実施・実施率の追跡にはストアが要る

## 9. Outline Wiki との関係

- **読む**：出題範囲となる規程・作業標準・教育資料のコレクション（`PC-05`）
- **書く**：実施結果サマリを「小テスト › 結果 › <実施日>」へ下書きとして保存。個人別結果は書かない
- 受験の生ログは Outline に書かない（更新・集計ができないため。ストアが正）
