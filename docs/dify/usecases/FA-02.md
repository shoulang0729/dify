## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（クローズ期間中、日々の進捗確認）。③業務フィードでは `due`（第 5 営業日の締め期日。`data/world/fin/calendar.md`）
- **登場人物**：事務統括部の主管（クローズを進める側）、各項目の担当者（未了項目を持つ側）、リスク統括部（与信関連の最終承認）
- **いまの手順（Before）**：チェックリストを Excel で手作業に管理し、誰の作業で止まっているかが締めの終盤にならないと分からない。クローズ報告も締め日ぎりぎりに作成する
- **エージェント導入後の手順（After）**：
  1. 対象月とチェックリストの進捗（何項目中何項目完了か、未了項目の起票状況）を送信する
  2. 未了の項目・必要な仕訳・期日超過が可視化され、クローズ報告のドラフトが返る
  3. 担当者が**未了項目の担当者に確認し、クローズ報告を確定する**（AI は仕訳計上・報告確定をしない）
- **成功の定義**：締め期日までの進捗が毎日見え、締めの終盤で慌てることが減る

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| チェックリスト進捗 | フォーム（対象月・進捗・未了項目の起票状況） | ja / zh | 日次〜週次 | 18 項目中 15 完了、`FA-01` の差異調査2件を含む | フォーム（`PC-16`） | 未了項目のリストと締め期日までの残り営業日を計算 |
| チェックリストマスタ | Markdown | ja | マスタ | 18 項目の内容・担当・締め期日 | Outline「月次クローズチェックリスト」コレクション（`PC-05`） | 進捗フォームの項目と突合 |
| `FA-01` の差異一覧 | JSON | — | 月次 | 区分コード差異・端数調整 | `FA-01` の出力（連携する場合） | 未了項目として取り込む |

- **入力言語の扱い**：フォーム入力・追い質問は日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。クローズ報告ドラフトは日本語が既定（事務統括部の報告様式に合わせる）
- **入力の欠け・曖昧さ**：チェックリストマスタが Outline に無い項目は「マスタ未登録」として明示し、進捗の可視化から除外する。締め期日までの残り営業日は `data/world/fin/calendar.md` の会計年度・締め日ルールに基づいて計算する

## 3. 観点（LLM に守らせる業務ルール）

- **進捗率・残り営業日は Code の計算結果を転記する**：18 項目中何項目完了かの割合、締め期日までの残り営業日を LLM が計算しない
- **未了項目の重大度を勝手に判定しない**：「軽微」「リスク」の分類は、締め期日までの残り営業日と項目の性質（承認待ちか作業待ちか）から機械的に判定した結果を転記する
- **クローズ報告ドラフトは「ドラフト」と明示する**：確定は事務統括部が行う旨を必ず書く
- **仕訳の計上・確定はしない**：「暫定仕訳を計上済み」等、既に行われた処理があればその事実を転記するが、本サービス自体が新しく仕訳を作ることはしない
- **禁止**：締め期日に間に合わない項目について、担当者の責任を問う書き方をする／承認の可否を代行する
- **不確実なとき**（入力言語で）：ja「この項目はチェックリストマスタに登録がありません。事務統括部にご確認ください。」／zh「该项目未在检查表主数据中登记，请与事务统筹部确认。」
- **出力の粒度**：進捗（件数・割合）→ 必要な仕訳（あれば）→ 期日超過リスク → クローズ報告ドラフト → 確定前の確認

## 4. Dify 構成

- **アプリ種別**：**Workflow**（フォーム入力 → 実行 → 進捗とドラフト）。`PC-11` の日次リマインドも同じ Workflow を呼ぶ
- **ノード列**：
  1. `Start`（対象月・チェックリスト進捗・未了項目の起票状況）
  2. `HTTP Request`（`PC-05` からチェックリストマスタを取得）
  3. `Code`（進捗率の計算、締め期日までの残り営業日の計算（`data/world/fin/calendar.md` の第 5 営業日ルール）、未了項目のリスク判定）
  4. `LLM`（クローズ報告ドラフトの生成。§5 のプロンプト）
  5. `Code`（検算：ドラフトに「ドラフト」の明記があるか、進捗率が Code 出力と一致するか）
  6. `HTTP Request`（`PC-13` でクローズ報告のファイル出力）
  7. `HTTP Request`（`PC-05` にクローズ報告ドラフトを保存）
  8. `Answer`
- **Knowledge**：使わない（チェックリストマスタは Outline から直接取得）
- **プラグイン／ツール**：**HTTP リクエストノード**（Outline API、`PC-13`）、`Code` ノード（進捗率・営業日計算）
- **モデル**：既定 `models/siliconflow` Qwen3-32B（ドラフト生成。計算は Code）
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `period` | string | ✓ | 対象月 |
  | `checklist_status` | object | ✓ | チェックリスト進捗（項目 id → 状態） |
  | `open_items_source` | string | — | 未了項目の起票状況（`FA-01` の差異調査 等） |
  | 出力 `progress` | object | ✓ | 進捗率・締め期日までの残り営業日 |
  | 出力 `close_report_draft` | string | ✓ | クローズ報告ドラフト |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 事務統括部の月次クローズ進捗管理アシスタントです。
チェックリストの進捗（{{progress_json}}）から、未了項目・必要な仕訳・期日超過リスクを整理し、クローズ報告のドラフトを作成します。
守ること：
1. 進捗率・残り営業日は与えられた {{progress_json}} をそのまま使う。自分で計算しない。
2. 未了項目のリスク判定（軽微／リスク）は与えられた分類をそのまま転記する。自分で格上げ・格下げしない。
3. クローズ報告は「ドラフト」であり、確定は事務統括部が行う旨を必ず末尾に書く。
4. 仕訳の計上・確定はしない。既に行われた処理があればその事実だけを転記する。
5. 締め期日に間に合わない項目について、担当者の責任を問う書き方をしない。
6. チェックリストマスタに無い項目は「マスタ未登録」と明示する。
7. 言語：クローズ報告ドラフトは日本語。担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：進捗（件数・割合）→ 必要な仕訳 → 期日超過リスク → クローズ報告ドラフト → 確定前の確認 の順。
```

### 5-2. User テンプレート

```text
対象月={{period}}
進捗（Code 転記のみ）：{{progress_json}}
未了項目の起票状況：{{open_items_source}}
チェックリストマスタ（Outline から取得）：{{checklist_master}}
```

### 5-4. Few-shot

**不要**。月ごとの進捗状況に依存するため、書式は System と JSON スキーマで固定する。

## 6. 検証観点

| 観点 | 基準 | 測り方 |

| 進捗率の非捏造 | 進捗率・残り営業日が Code 出力と完全一致 100% | 自動突合 |

| リスク判定の転記 | 未了項目のリスク分類の格上げ・格下げ 0 | 自動突合 |
| 言語 | ドラフトは日本語、やり取りは入力言語 100% | 自動判定（`PC-07`） |
| 速度 | p95 < 20 秒 | Langfuse |

## 8. 別出しが必要なもの

- `PC-05`：「月次クローズチェックリスト」マスタの同期。クローズ報告ドラフトの保存
- `PC-11`：締め期日前の日次リマインド（`data/world/fin/calendar.md` の第 5 営業日ルールに基づく）
- `PC-13`：クローズ報告のファイル出力（docx/xlsx）

- **無くても動く範囲**：チェックリストマスタが無くても、フォームに入力された進捗のみでの可視化は動く（マスタとの突合ができないだけ）

## 9. Outline Wiki との関係

- **読む**：「月次クローズチェックリスト」マスタ（`PC-05`）
- **書く**：クローズ報告ドラフトを「クローズ報告（AI ドラフト）」コレクションへ保存（`publish: false`）。確定は事務統括部が行う
- 仕訳そのものは Wiki に書かない（会計システムが正本）

## 10. 未確定・リスク

- **実現性を ○ とした理由**：フォーム入力・進捗計算・ドラフト生成は標準機能で足りるが、(1) チェックリストマスタの Outline 整備、(2) `FA-01` との自動連携経路、の 2 点が未確定のため ◎ にしていない
- **リスク統括部の承認状況の取得**：与信関連の期末評価承認がどのシステムで管理されているか（BPMS 等）は未確認。現状はフォームでの手入力を前提とする
- **速報値での報告の可否**：締め期日に承認が間に合わない場合の運用（速報値で報告するか、締め日を動かすか）は事務統括部の判断であり、本サービスは選択肢の提示のみに留める
