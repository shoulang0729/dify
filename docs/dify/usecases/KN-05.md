## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：2 通り。(a) 銀行・会計事務所・当局サイトから通達 PDF が届き、担当者が能動的に開く。(b) `PC-11` の定期巡回で新着通達を検知し ③業務フィードに **`notify`** として乗る（`FEED.items` の `kn5` は `notify`）
- **登場人物**：担当者（財務・法務駐在員＝日本語母語、または現地財務課長＝中国語母語）、確認者（財務課長・総経理）、日本本社（要約の受け手）、外部（取引銀行・当局。回答には登場しない）
- **いまの手順（Before）**：
  1. 中国語原文 10〜30 ページを駐在員が読む（半日〜1 日。読み落としが怖い）
  2. 「自社に関係あるか」「期限はいつか」を会計事務所に照会（数日）
  3. 影響を受ける社内マニュアル（資金管理・経費・貿易）の該当箇所を人が探す（半日）
  4. 改訂案を書き、本社へ日本語で報告。**期限を読み違えると当局対応漏れ**
- **エージェント導入後の手順（After）**：
  1. 担当者が通達 PDF と（任意で）関連マニュアルをアップロードする
  2. エージェントが通達の要旨・対象業務・期限・必要対応を**原文ページ引用付き**で整理し、社内規程 KB との照合で影響箇所を特定する（`PC-12`：通達の要求事項 ↔ 規程条項のマッピング＋現行手順との差分）
  3. **担当者が「自社に本当に該当するか」「期限の読みは正しいか」を原文引用で確認する**（法的判断は人）
  4. 「§5.3 の改訂案を」「本社向け 5 行要約を」でドラフトを受け取り、財務課長レビュー → 版上げは人が行う
- **成功の定義**：通達 1 件の影響整理を 1〜2 日 → 1 時間。**期限・対象の読み違え 0**（必ず原文ページで裏取りできる状態）

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。通達原文（zh）の引用は原語のまま添え、要約・影響・改訂案は入力言語で書く。「本社向けに日本語で」のように**出力言語を明示指定されたらそれに従う**
- **入力の欠け・曖昧さ**：通達が無いと始まらない（マニュアルだけの投入は「通達を添付してください」）。マニュアル未添付なら規程 KB から探す。会社属性が未設定なら「該当判定は仮」と注記

## 3. 観点（LLM に守らせる業務ルール）
- **原文ページ引用**：要旨・対象・期限・必要対応の各項目に「原文 p.X 第 X 条」を付ける。引用できない主張は書かない
- **期限は原文の表記どおり**：「施行日」「初回報告期限」「移行期間」を区別し、原文に無い日付を計算で作らない（営業日換算が必要なら「要確認」）
- **該当判定は条件付き**：`company_profile` と照らして「該当／該当しない／要確認」を明示し、理由（原文の適用範囲条項）を引く。**法的助言ではない**旨を末尾に 1 行
- **規程マッピング**（`PC-12`）：影響箇所は「規程 doc_id §節・現行文言・通達要求・差分」の 4 点セットで出す。差分が無い節を「影響あり」と書かない
- **改訂案は差分で示す**：変更前／変更後を並べ、変更理由に通達番号を付ける。「ドラフト」「承認前」を明記。**版上げ・公開はしない**
- **数値を作らない**：金額・残高（例 USD 1.2M）は入力・KB にある値のみ
- **禁止**：通達本文の全文転載（要旨と条項引用まで）、当局・銀行への提出文書を「送信済み」と書くこと
- **不確実なとき**（入力言語で）：「通達の適用範囲に自社が含まれるか原文から判断できません。第 X 条の対象定義を財務課長／会計事務所に確認してください」
- **出力の粒度**：§5-3 の JSON（後工程：Outline メモ・docx）＋人が読む表（要旨／影響／期限／改訂箇所／要確認）

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`、ファイル添付 ON）。upload 型だが「改訂案を書いて」「5 行要約」の追い指示が多いため。バッチ巡回（b）は別に **Workflow**（Schedule トリガー → 同じ抽出ノード → `PC-01` へ `notify`）
- **ノード列（Chatflow）**：
  1. Start（`sys.files`：通達 PDF 必須、マニュアル docx 任意／`sys.query`）
  2. IF/ELSE（ファイル添付あり＝初回解析／なし＝追い指示）
  3. **初回解析**：Tool `tools/mineru`（通達 → Markdown＋ページ）→ Code（節分割・ページ対応表）→ Iteration[ LLM（Qwen3-235B）：節ごとに要求事項を JSON 抽出 ]（`../templates/02` の型）→ Code（統合）→ LLM（会社属性との該当判定・期限整理）→ Document Extractor（添付マニュアル）＋ Knowledge Retrieval（`kb-internal-rules`、`owner_dept`・`category` フィルタ、top-k 8）→ **HTTP Request（`PC-12`：要求事項 × 規程節のマッピングと差分）**（`PC-12` 未整備時は LLM＋Code `difflib` で代替）→ LLM（影響分析）→ Variable Assigner（会話変数 `analysis_json`）→ Answer
  4. **追い指示**：LLM（`analysis_json`＋`sys.query` → 改訂案／要約）→ Answer。docx が要る場合は `PC-13` へ HTTP Request
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-internal-rules` | 規程・マニュアル（ja/zh） | 節単位 | `doc_id` `title` `section` `version` `owner_dept` `category`（資金／税務／貿易／労務）`lang` | Outline → `PC-05`（週次） |
  | `kb-notice-history` | 過去通達＋対応記録 | 行単位 | `notice_no` `authority` `year` `affected_docs` | 管理部 xlsx（月次） |
  | `kb-notices-archive`（任意） | 巡回で取得した通達本文 | ページ単位 | `notice_no` `authority` `issued` `source_url` | `PC-11`（`datasources/firecrawl_datasource` 等）or `http-request` |
- **プラグイン／ツール**：`tools/mineru`（既定。自前デプロイ推奨）、`tools/dify_extractor`、（任意）`triggers/rsshub_trigger`・`datasources/firecrawl_datasource`／`jina_datasource`（当局サイトへの到達性と規約は要確認。国内サイトは `http-request` 直取得が確実な場合あり）、`tools/wecom`（新着通知）
- **モデル**（`PC-08`）：既定 SiliconFlow `DeepSeek-V3.x`（中国語公文書の読解）または `Qwen3-235B-A22B-Instruct`。本社向け日本語要約は同モデルで評価し、不足なら本社側アプリを海外モデルに。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`
- **参照 DSL**：`../templates/02-long-document-chunk-iteration-translate.yml`（長文分割→iteration→統合）、`../templates/08-mineru-pdf-parse-demo.yml`（MinerU tool ノード）

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工 蘇州工場 管理部（財務・法務）を支援する「当局通達 影響分析」です。
役割：所管当局（外貨管理・税関・税務・地方政府。業種により金融当局を含む）の通達を読み、要旨・対象・期限・必要対応を整理し、社内規程・マニュアルの影響箇所と改訂案（ドラフト）を示す。

守るルール：
1. 要旨・対象・期限・必要対応の各項目に、通達原文のページと条項（例：原文 p.3 第二条）を付ける。引用できない内容は書かない。
2. 期限は原文の表記どおりに「施行日」「初回報告期限」「移行期間」を区別する。原文に無い日付を計算で作らない（必要なら「要確認」）。
3. 自社への該当は <company_profile> と原文の適用範囲条項を照らし、「該当／該当しない／要確認」と理由を書く。
4. 影響箇所は「規程 doc_id §節／現行文言／通達の要求／差分」の 4 点で示す。差分が無い節を影響ありと書かない。
5. 改訂案は「変更前」「変更後」を並べ、理由に通達番号を付け、見出しに「ドラフト（承認前）」と書く。版上げ・公開・当局への提出は行わない。
6. 金額・残高・件数は入力または規程にある値のみ。
7. 通達本文を全文転載しない。要旨と条項の引用まで。
8. 末尾に 1 行「本分析は法的助言ではありません。適用判断は財務課長・会計事務所の確認を経てください」を付ける。
9. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。「日本語で」「中文で」と出力言語を指定されたらそれに従う。原文引用は中国語のまま。
10. 判断できないとき：
   ja「通達の適用範囲に自社が含まれるか原文から判断できません。第 X 条の対象定義を財務課長／会計事務所に確認してください。」
   zh「无法根据原文判断本公司是否在通知适用范围内。请与财务科长／会计师事务所确认第X条的适用对象。」

出力形式：表（要旨／自社への影響／期限／マニュアル改訂箇所／要確認）→ 注記。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（期限・対象） | 期限・適用範囲の読み取りが原文と一致 **100%**（読み違え 0） | 評価セット 15 通達を財務課長＋会計事務所が採点 |
| 引用 | 各項目に原文ページ・条項 100%、引用先が実際に該当 ≥ 95% | 自動（`p.\d+`）＋人手抜取 |
| マッピング | 影響ありと判定した規程節の適合率 ≥ 85%、取り漏れ（人が見つけた影響箇所）≤ 1 件/通達 | 過去通達 20 件の対応記録と突合 |
| 言語 | 入力言語（または指定言語）で返答 100% | `PC-07` |
| 拒否 | 適用範囲不明の通達で「要確認」定型 ≥ 95% | 負例 10 件（他業種向け通達） |
| 形式 | `analysis_json` スキーマ準拠 100% | バリデータ |
| 速度 | 初回解析 p95 < 120 秒（30 ページ） | `PC-09` |
| 安全 | 全文転載 0、「提出済み」等の虚偽動作記述 0 | 負例 |

- **評価方法**：リリース前に過去通達 15 件で人手評価。以後、通達ごとに担当者が「読み違えの有無」を Langfuse にスコア（月次レビュー）

## 8. 別出しが必要なもの
- **`PC-12`**：通達要求事項 × 規程節のマッピングと差分（本サービスの核。初期は Chatflow 内 LLM＋`difflib` で代替し、精度が出たら `PC-12` へ切り出す）

- `PC-05`：Outline 規程・マニュアル → `kb-internal-rules`。改訂ドラフトの書き戻し
- `PC-11`＋`PC-01`＋`PC-14`：当局サイト巡回 → 新着を ③フィードに `notify`、WeCom 通知（任意。到達性・規約を確認）

## 9. Outline Wiki との関係
- **読む**：Outline「規程・マニュアル」コレクション（財務・税務・貿易・労務）を `kb-internal-rules` に同期。`doc_id`・`section` を Outline の見出し構造から取る
- **書く**：影響分析メモ（§5-3 を Markdown 化）と改訂案を Outline「規程改定ドラフト」コレクションに**ドラフト**として作成（`http-request`）。財務課長がレビューし、版上げ（v4.2→v4.3）と公開は人が行う。過去通達との対応記録（`kb-notice-history`）も Outline で管理できる
- Outline を使わない場合：docx を `PC-03` へ投入し、ドラフトは `PC-13` の docx で受け取る

## 10. 未確定・リスク
- **法的判断の誤り**（期限・対象の読み違え）が最大リスク。対処：原文ページ引用の必須化（実施）、人のレビューを必ず挟む運用、免責 1 行。**「AI が判断した」と顧客に見せない**
- **当局サイト巡回の可否**：海外 SaaS（firecrawl/jina）から中国当局サイトへの到達性と規約、RSSHub 自前運用 — 未確定。推奨：初期は手動アップロード（a）のみ、巡回（b）は第 2 段階
