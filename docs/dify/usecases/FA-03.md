## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（月次クローズ後、監査対応の準備）。③業務フィードでは `due`（監査前の準備期限）
- **登場人物**：事務統括部の主管（レビューする側）、監査人（想定される質問者）、リスク統括部（引当金見積りの妥当性を判断する先）
- **いまの手順（Before）**：担当者が財務諸表と注記を読み込み、表間の整合や前期との継続性を手作業で確認する。監査で聞かれそうな点を事前に洗い出す作業も個人の経験に依存する
- **エージェント導入後の手順（After）**：
  1. 財務諸表と注記をアップロードする
  2. 表間の整合・前期との継続性・開示の抜けが点検され、指摘が根拠付きで返る
  3. 担当者が**監査で聞かれやすい点を確認し、説明を準備する**（AI は引当金見積りの妥当性を判断しない）
- **成功の定義**：監査対応の準備時間が減り、開示の抜けが事前に見つかる

- **入力言語の扱い**：財務諸表・注記は日本語・中国語どちらもあり得る。**指摘は日本語**が既定（事務統括部の報告様式に合わせる。台本参照）。担当者とのやり取りは入力言語に従う（`CLAUDE.md` §2-5）

## 3. 観点（LLM に守らせる業務ルール）

- **表間の整合は機械的な突合結果を使う**：貸借対照表・損益計算書・附属明細の数値一致は `Code` で突合した結果をそのまま転記する
- **継続性は前期の方針と比較する**：計上方法が変わっていないかを確認し、変わっている場合は「変更あり」と明示する（変更の当否は判断しない）
- **開示の抜けは規定・様式との照合結果として示す**：「新様式（区分コード欄あり）を反映していない」のように、根拠となる規定・様式を明示する
- **引当金見積りの妥当性は判断しない**：延滞率の悪化を受けて見積り前提の確認が必要な場合、その旨を示すにとどめ、**リスク統括部への確認を促す**（事務統括部単独で判断できない旨を明記）
- **禁止**：会計上の判断（引当金の額の妥当性等）を断定する／規定に無い基準で指摘する
- **不確実なとき**（入力言語で）：ja「会計方針の照合基準が未整備のため、一般的な整合性チェックのみ行っています。」／zh「会计方针的核对基准尚未健全，仅进行一般性一致性检查。」
- **出力の粒度**：表間の整合 → 前期との継続性 → 開示の抜け → 監査で聞かれやすい点 → 確定前の確認

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 事務統括部の財務諸表レビュー担当です。
突合済みの財務諸表データ（{{consistency_json}}）と会計方針（{{accounting_policy}}）から、
表間の整合・前期との継続性・開示の抜けを点検し、監査で聞かれやすい点を整理します。
守ること：
1. 表間の整合は与えられた {{consistency_json}} をそのまま使う。自分で数値を突合しない。
2. 継続性は前期の会計方針と比較し、変更があれば「変更あり」と明示する。変更の当否は判断しない。
3. 開示の抜けは根拠となる規定・様式（{{accounting_policy}} 中の該当箇所）を明示する。
4. 引当金見積りの妥当性など、事務統括部単独で判断できない事項は断定せず、リスク統括部への確認を促す。
5. 会計方針マスタが不足しているときは「会計方針の照合基準が未整備」と明示し、一般的な整合性チェックのみである旨を書く。
6. 言語：指摘は日本語。担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：表間の整合 → 前期との継続性 → 開示の抜け → 監査で聞かれやすい点 → 確定前の確認 の順。
```

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 整合の非捏造 | `consistency` の値が Code 出力と完全一致 100% | 自動突合 |
| 継続性の判定 | 前期との計上方法の変更検知が正しい ≥ 95% | 評価セット 10 件を人手採点 |
| 開示の抜けの根拠 | 各指摘に規定・様式の根拠箇所が付く 100% | スキーマバリデータ |
| 会計判断の非断定 | 引当金の妥当性を断定する表現の出現 0 | 禁止語 + LLM-as-judge |
| 言語 | 指摘は日本語、やり取りは入力言語 100% | 自動判定（`PC-07`） |
| 拒否 | 会計方針未整備の明示 100% | 自動 |
| 速度 | p95 < 40 秒 | Langfuse |

- **評価方法**：リリース前に事務統括部で 10 件を人手採点

## 8. 別出しが必要なもの

- `PC-05`：「会計方針」コレクションの同期。KPI 定義は `NM-03` 相当（本番では顧客側の KPI マスタ）と共用する想定

## 9. Outline Wiki との関係

- **読む**：「会計方針」コレクション（`PC-05`）
- **書く**：使わない。指摘結果は監査対応の準備資料として画面表示・ファイル出力にとどめ、Wiki には残さない（版が頻繁に変わる都度資料のため）
- 財務諸表そのものは Wiki に置かない（会計システムが正本）

## 10. 未確定・リスク

- **実現性を ○ とした理由**：ファイルアップロード・突合・点検は標準機能で足りるが、(1) 会計方針マスタの Outline 整備状況、(2) 監査で聞かれやすい点の粒度が監査人・監査法人によって異なる可能性、の 2 点で ◎ にしていない
- **`FA-01`・`FA-02` との連携**：未了項目・差異一覧を自動で本サービスに引き継ぐ経路は未確定。本 PR では担当者が手動で参照する前提
- **KPI マスタの正本**：`data/world/fin/kpi.csv` はデモ用の架空値。本番では顧客側の KPI マスタとの連携経路が必要（`RS-05` と共通の論点）
