## 1. 業務シナリオ
- **トリガー**：期限つき案件が振られる（`due`）。製造現場から修理依頼が起票され、**現場が止めるか続けるかの返事を待っている**状態で保全課に届く
- **登場人物**：実施者＝設備保全課 技師。依頼者＝製造現場の班長。確認者＝設備保全課長・製造二課長（止める判断）
- **いまの手順（Before）**
  1. 修理依頼（現象・設備・写真）が口頭またはメールで届く
  2. 技師が設備台帳でアラームコードの意味を引き、取扱説明書の該当章を探す（10〜20 分）
  3. 「前にも同じことがあったか」を**紙の修理台帳とベテランの記憶**で当たる（30 分〜。3 年前の事例はまず出てこない）
  4. 直近の点検表を現場から取り寄せる（提出が遅れていると分からないまま進む）
  5. 止めるか続けるかを判断し、依頼者に電話で返す。**判断の根拠が記録に残らない**
- **エージェント導入後の手順（After）**
  1. 現象・設備 id・発生状況・生産への影響をフォームに入力する（**入力する場所**）
  2. 設備台帳のアラーム定義・同じ設備の修理履歴・直近の点検表が**突き合わせ済みで**返る
  3. 原因候補が「最有力／可能性が低い／保留」に分かれ、**発生の偏り（立ち上げ直後に集中など）が過去のどの事象と同じ形か**が示される（**確認する場所**）
  4. 「止める場合／続ける場合」に何が起きるかが材料として並ぶ。**止めるかどうかは技師と製造課が決める**（決める場所）
  5. 保全課への引き継ぎ文と、依頼者への一次回答・暫定対処の下書きが出る
- **成功の定義**：一次回答までの 40〜60 分が 10 分になる。かつ**過去の同型事象（3 年前を含む）が毎回引き当たる**ことで、同じ調査を一からやり直さない

- **入力言語の扱い**：依頼文は中国語、取扱説明書は日本語のことが多い。**回答言語＝利用者の入力言語**。地の文で言語を混ぜない。アラームコード・設備 id・文書番号は原文のまま。**根拠文書は言語を問わない**（日本語の説明書を根拠に中国語で答えてよい。「該当なし」とはしない）
- **入力の欠け・曖昧さ**：①設備 id が無い → 「設備 id（型式）を教えてください。同じアラームでも設備が違えば原因が変わります」と聞き返す。②点検表が未提出 → **推測せず未確認と明示**し、原因候補の確定を保留する。③写真だけで現象の記述が無い → アラーム画面が読めれば読み、読めなければ現象を 1 行で聞き返す

## 3. 観点（LLM に守らせる業務ルール）
1. **原因候補は「最有力／可能性が低い／保留」の 3 段に分け、それぞれに根拠（履歴の番号・点検表の項目）を付ける**。根拠の無い候補を挙げない
2. **発生の偏り（時間帯・立ち上げ直後・特定の金型使用時など）を必ず見る**。過去の同型事象と偏りの形が一致するかを明示する
3. **材料が欠けているとき（点検表が未提出など）は、その候補を「確かめていない」と書く**。欠けたまま確定しない
4. **緊急度は材料の提示までで、止める／続けるの結論を出さない**。「止める場合」「続ける場合」の双方に何が起きるかを書き、**決めるのは人だと明記する**
5. 続ける場合の暫定対処は、**作業標準書に既にある手順を優先して引く**（新しい手順を作らない）。標準書の版（Rev.）を必ず添える
6. **不適合の流出リスクに触れる**：設備側の処置だけでなく、検査側の手当て（初品・定時の寸法確認）を暫定対処に含める
7. 担当割り当ては提案までとし、**起票・アサインはしない**

- **不確実なときの定型**：ja「原因を絞り切れません。〈9/15 以降の点検表〉が未提出のためです。提出後に再度実行してください。それまでの暫定対処は下に示します。」／zh「无法确定原因。因为〈9/15之后的点检表〉尚未提交。提交后请重新执行。在此之前的临时处置如下。」
- **出力の粒度と形式**：見出し 7 つ（設備台帳・修理履歴・直近の点検表・原因候補・緊急度の材料・保全課への引き継ぎ文・依頼者への一次回答）。`PC-01` へ渡す分は §5-3 の JSON

## 4. Dify 構成
- **アプリ種別**：**Chatflow**。1 回目はフォーム入力からの要約だが、**2 回目以降の「続けるなら何を見ればいい？」という追い質問が業務上必ず来る**（台本 ja#2）。会話の文脈を保つ必要がある
- **ノード列**
  ```
  Start（equip_id・symptom・requester・impact・photo）
    → 言語判定（PC-07）
    → HTTP Request（PC-04：設備台帳 → アラーム定義・使用中の金型・関連基準）
    → HTTP Request（PC-04：修理履歴 3 年分を equip_id ＋ alarm_code で取得）
    → HTTP Request（PC-04：直近 4 週の点検表。無ければ not_submitted フラグ）
    → Knowledge Retrieval（KN-12 設備 KB：取扱説明書・作業標準書。メタデータフィルタ equip_id）
    → LLM 1（発生の偏りの抽出と、過去事象との形の一致）
    → LLM 2（原因候補 3 段・緊急度の材料・引き継ぎ文・一次回答）
    → Template（7 ブロック）／Code（JSON）
    → Answer
  ```
- **Knowledge**：KB 名 `KN-12 設備`（KN-02 の KB を共用してよい。文書の重複投入はしない）。投入＝取扱説明書（設備ごと）・作業標準書（`WS-L3-04` ほか）・金型予熱基準。チャンクは章／条単位。メタデータ＝`equip_id` `doc_no` `rev` `lang`。更新経路は Knowledge Pipeline ＋ Outline（`PC-05`）
- **プラグイン／ツール**：`http-request`（業務台帳）、`tools/mineru`（スキャン説明書の投入時のみ）
- **モデル**：既定 chat モデル。原因候補の並べ替えは推論寄りのモデルが望ましい（`../plugins-and-references.md` §4 の `reasoning` 用途）
- **参照 DSL**：`KN-02` の DSL（`dify/apps/KN-02-*.yml`）を雛形にする。Knowledge Retrieval のメタデータフィルタがそのまま使える
- **入出力変数**

| `equip_id` | string | ✓ | 設備 id（例 `PX-200`） |

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 履歴の引き当て | 同一設備・同一アラームの過去事象の再現率 ≥ 95% | 評価セット 30 件（3 年分から抽出） |

| 標準書の版 | 引用に Rev. が付く 100% | 自動 |
| 言語 | 入力言語で返答 100% | 自動判定 |
| 速度 | p95 < 25 秒 | Langfuse |

## 8. 別出しが必要なもの
- **修理履歴の電子化と 3 年分の遡及**（`PC-04`）。紙台帳のままでは §1 の Before が解消しない。既存の業務台帳（ノーコード業務 DB の設備台帳・修理依頼・点検表アプリを含む。設計書 `docs/handoff/2026-09-21-kintone-derived-usecases.md` §11）を読み取り先にするのが最短
- **アラームコード表の構造化**（設備型式 → コード → 意味 → 初動）。説明書の PDF からの検索だけでは初動の提示が安定しない
- **点検表の提出状況が分かること**（未提出を未提出と知るために必要。`not_submitted` フラグの供給元）
- **無くても動く範囲**：設備台帳と説明書だけでも「アラームの意味・説明書の該当章・一般的な初動」は返る。**過去事象の引き当てと偏りの一致判定が落ちる**（第 1 段はここ、第 2 段で修理履歴、第 3 段で点検表）

## 9. Outline Wiki との関係
- **読む**：`設備保全` コレクション（作業標準書・予熱基準・アラーム初動メモ）を KB へ同期（`PC-05`）
- **書く**：使わない。修理の記録は業務台帳が正本で、Outline に二重に残さない
- ただし**新しく分かった初動**（今回の「予熱してから立ち上げる」など）は、人が Outline のメモに追記する運用を推奨（AI は書かない）
