## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く。典型は**共同訪問・担当交代の前**。③業務フィードの項目にはならない
- **登場人物**：営業担当（陳慧のような主管。日々の接点を記録する側）、営業部長（森下隆一のような管理職。訪問前に経緯を把握する側）、共同訪問者、与信先（甲社など。回答には登場しない）
- **いまの手順（Before）**
  1. 過去の営業日誌・面談記録を個人のメモや共有フォルダから手作業で探す（30 分〜1 時間）
  2. 誰が・いつ・何を約束したかが記録に散らばっていて、抜け漏れに気づけない
  3. 担当交代・共同訪問の直前になって、保留中の論点を思い出せず訪問時に対応が漏れる
- **エージェント導入後の手順（After）**
  1. 担当者が対象先の名前を日本語または中国語で入力する
  2. エージェントが過去の営業日誌・面談記録を横断検索し、**時系列で経緯**を整理して返す
  3. 「保留中の論点は何か」「訪問で話すべきことは」の追い質問に、記録に基づいて答える
  4. **訪問で何を話すか・約束を守るかどうかの判断は担当者が行う**（AI は判断しない）
- **成功の定義**：訪問・引き継ぎ前の経緯確認が「記録を探す」作業から「聞けば返ってくる」作業に変わり、保留中の論点の見落としが無くなる

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。英語 UI でも同じ。地の文は例外なく回答言語で書き、1 つの文の中で日本語と中国語を混ぜない。記録番号（`CLM-26-2211` 等）は原語のまま出す（`docs/handoff/2026-09-08-response-language-contract.md` §2）。**根拠記録は言語を問わない**：質問の言語の記録が無ければ他言語の記録を根拠にしてよい
- **入力の欠け・曖昧さ**：対象先名が無いと検索できない。聞き返し定型：「対象先の名前を教えてください（例：甲社）」。該当記録が 0 件でも「記録が見つかりません」と明示し、検索自体の失敗と区別する

## 3. 観点（LLM に守らせる業務ルール）

- **回答は検索結果の記録だけから作る**。記録に無い会話内容・約束を推測で補わない
- **時系列を明示する**：「前々回」「前回」「直近」のように相対的な順序を示し、日付や記録番号（分かる範囲）を添える
- **保留中の論点を明示する**：約束したが実施記録が無い項目は「保留」として区別する。実施済みかどうかを勝手に推測しない
- **他担当者の記録の扱い**：`PC-02` の権限に従い、閲覧できる範囲の記録だけを検索対象にする。範囲外の記録があることは示唆しない（存在自体を含めて見せない）
- **禁止**：与信・取引継続の可否を判断すること（KN-07 は経緯の整理のみ）、記録に無い金額・条件を作ること
- **不確実なとき**（入力言語で）：ja「対象先の記録が見つかりません。対象先名を確認してください」／zh「未找到该对象的记录。请确认对象名称」
- **出力の粒度**：時系列の経緯（箇条書き）→ 保留中の論点（あれば）。優先度づけを求められたら記録に基づく理由を添えて順位を示す

## 4. Dify 構成

- **アプリ種別**：**Chatflow**（`advanced-chat`）。追い質問（保留事項の深掘り、論点の絞り込み）が多いため
- **ノード列**：
  1. Start（`sys.query`、`user`＝担当者 ID を `PC-02` から）
  2. LLM（Qwen3-32B）— `client`（対象先記号）／`intent`（`timeline` / `open_points` / `agenda`）を JSON 抽出
  3. Knowledge Retrieval（`kb-sales-logs`、メタデータ `client` フィルタ＋ `rep_id` の閲覧権限フィルタ、top-k 20、日付順）
  4. LLM（本体）— §5-1。時系列整理・保留論点の抽出
  5. Answer
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-sales-logs` | 営業日誌・面談記録・業務記録 | 行単位（1 件＝1 レコード） | `client` `rep_id` `date` `kind`（visit／call／mail）`record_no`（あれば）`visibility_scope`（`PC-02` の帯） | Outline「営業日誌」「面談記録」コレクション → `PC-05`（日次） |
- **プラグイン／ツール**：`tools/dify_extractor`（docx の取込）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（本体・時系列整理）／Qwen3-32B（抽出）／`bge-m3`（埋め込み）／`bge-reranker-v2-m3`（リランク）
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（分類抽出 → KB 検索 → LLM の型）
- **入出力変数**：

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 上海本部の営業担当を支援する「行内営業情報の検索」です。
役割：営業日誌・面談記録・業務記録を横断検索し、対象先との経緯を時系列で整理し、保留中の論点を明示する。

守るルール：
1. 回答は <context> に含まれる記録だけから作る。記録に無い会話内容・約束・金額を推測で補わない。
2. 経緯は時系列（前々回・前回・直近、分かる日付・記録番号）で示す。
3. 「約束したが実施記録が無い」項目は保留として明示し、実施済みかどうかを断定しない。
4. <context> に含まれない担当者・対象先の記録には触れない（権限外の記録が存在することも示唆しない）。
5. 与信・取引継続の可否は判断しない。経緯と論点の整理にとどめる。
6. 訪問で話すべき論点の優先順位を求められたら、記録に基づく理由（保留の解消・関係深耕など）を添える。
7. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。記録番号は原語のまま。
8. 該当が無いとき：
   ja「対象先の記録が見つかりません。対象先名を確認してください。」
   zh「未找到该对象的记录。请确认对象名称。」

出力形式：時系列の経緯（箇条書き）→ 保留中の論点（あれば）。
```

### 5-4. Few-shot

- **ja**：Q「甲社との直近のやり取りを時系列でまとめて」→ A「甲社（陳慧担当）との直近 3 か月の営業日誌・面談記録から時系列でまとめました。…保留中の論点は 2 件です（為替予約資料の送付、送金手数料の回答）。」
- **zh**：Q「把与甲社最近的往来按时间顺序整理一下」→ A：同構成を中国語で

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | 時系列の内容が記録と一致 ≥ 90% | 評価セット 15 件を営業部長が採点 |
| 保留の検出 | 実施記録の無い約束の検出漏れ 0 | チェックリスト＋人手 |
| 権限遵守 | 閲覧範囲外の記録の混入 0 | 負例セット（他担当者の記録を含む検索） |
| 断定なし | 与信・取引継続可否を断定する表現の出現 0 | 禁止語＋LLM-as-judge |
| 言語 | 入力言語で返答 100% | `PC-07` 自動判定 |
| 拒否 | 該当なしのとき定型文 ≥ 95% | 負例セット |
| 速度 | p95 < 10 秒 | `PC-09` Langfuse |

- **評価方法**：リリース前に営業第一部で人手 15 件（うち権限負例 3 件）。月次で Langfuse のスコアを確認

## 8. 別出しが必要なもの

- `PC-03`：営業日誌・面談記録の docx／Outline からの日次取込
- `PC-02`：担当者 ID と対象先の担当割当を突き合わせ、KB のメタデータフィルタに使う閲覧範囲表
- `PC-05`：Outline「営業日誌」「面談記録」コレクションの同期
- **無くても動く範囲**：`PC-02` の権限フィルタが無い間は、営業第一部内など閲覧範囲を broad に設定して段階導入（範囲を絞る前提で「試行版」に留めている理由の 1 つ）

## 9. Outline Wiki との関係

- **読む**：Outline「営業日誌」「面談記録」コレクションを `kb-sales-logs` に同期
- **書く**：書かない。本サービスは既存の記録を検索・整理するのみで、面談記録そのものの作成は既存フロー（人が Outline に書く）に任せる
- 記録の正本は Outline のまま。本サービスが独自にコピーを作らない（`PC-05` の同期は検索用のインデックスに限る）

## 10. 未確定・リスク

- **構造化データとしての揃い方**：営業日誌・面談記録が自由記述の docx のままだと `client`／`rep_id`／`date` のメタデータ付与が手作業になる。実装前に記録フォーマットの統一（テンプレート化）が要る
- **閲覧範囲の設計**（`PC-02`）：部署単位か担当先単位かで検索対象が変わる。共同訪問時は「相手の担当分も見せる」運用が必要になり、権限設計が単純な部署帯では足りない可能性がある — PM／営業部長判断
- **KN-04（社内問い合わせ受付）との重なり**：KN-04 は部署をまたぐ FAQ 的な問い合わせ、KN-07 は対象先ごとの営業経緯の検索。対象先名を含む質問は KN-07 側で受ける運用とする
- **成熟度が構想（st3）である理由**：記録のメタデータ整備・閲覧範囲設計が先に要るため。台本自体は動くが、実データでの検証は未実施
