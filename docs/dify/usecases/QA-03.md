## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：顧客からクレーム連絡（メール・帳票・電話メモ）が届く。(a) 担当者がフォームに貼り付けて能動的に開く。(b) `PC-04` のメール受付（`triggers/outlook_trigger`／Webhook）で自動起票し ③業務フィードに **`notify`**、協定期限（重大：当日一次回答・2 営業日 D1〜D3）を **`due`** として乗せる
- **登場人物**：営業・顧客対応担当（ja 母語の駐在員、または zh 母語の現地営業）、製造課（原因側）、品質保証課（8D＝QA-01 へ引き継ぎ）、確認者（品質保証課長・工場長：重大時）、外部：顧客品質部（回答先）、日本本社品質保証部（報告先）
- **いまの手順（Before）**：
  1. 中国語のクレームメールを駐在員が読み、部品・ロット・数量・停線の有無を把握（30 分）
  2. 重大かどうか、どの部署が主担当かを電話で確認（1〜2 時間。夜間は翌日）
  3. 一次回答を中国語で書き、現地営業に文面チェックを頼む（1 時間）。**協定の提出期限（2 営業日）を読み違えて過度な約束をする**
  4. 本社に日本語で別途報告（30 分）。同種クレームの再発かどうかは台帳を手で検索
- **エージェント導入後の手順（After）**：
  1. 担当者がクレーム原文・顧客・部品番号・回答言語をフォームに入力（or 自動受付）
  2. エージェントが要約・重要度・区分・担当部門を判定し、台帳から同種クレームの件数と傾向を引き、**顧客言語の一次回答文（ドラフト）**を作る。重大なら `PC-14` で関係者に即時通知（**通知は社内、顧客への送信はしない**）
  3. **担当者が重要度判定と回答文の約束事項（期日・処置）を確認・修正する**（協定の期限を根拠に AI が指摘）
  4. 担当者がメールで顧客へ送信（人）。「本社に日本語で報告を」でドラフトを受け取り送る。8D が要るなら QA-01 へ
- **成功の定義**：一次回答ドラフトまで 2〜3 時間 → 15 分。**重大クレームの社内エスカレーション遅れ 0、協定期限に反する約束 0**。同種クレームの再発を一次回答時点で把握

- **入力言語の扱い**：担当者への説明・判定結果は**入力言語で返す**（`CLAUDE.md` §2-5）。**一次回答文だけはフォームの「回答言語」（顧客の言語）で書く**（日本の顧客→ja、中国の顧客→zh）。本社報告は指示どおり日本語
- **入力の欠け・曖昧さ**：顧客と部品番号が無いと担当部門・協定を引けない → 「顧客名（納入先）と部品番号を入力してください」。停線・数量が原文に無いときは重要度を「要確認」とし、聞き返し文を一次回答に含める（「発生数量と貴社ラインへの影響を確認させてください」）

## 3. 観点（LLM に守らせる業務ルール）
- **重要度は基準で判定**：協定・社内基準（停線あり／安全関連／再発＝重大）を引いて判定し、根拠を書く。基準に当たらなければ「中」以下、判断材料不足なら「要確認」
- **担当部門は対応表から**：部品→工程→部署の表にある値。無ければ「品質保証課（暫定）」と明記
- **一次回答で約束しすぎない**：処置（全数検査・訪問）は担当者がフォームで選んだもの、または「検討中」に留める。**提出期日は協定の期限以内かを検証し、協定より早い約束には注意を出す**（当日 9/6 起点の 2 営業日は 9/9、等。営業日計算は Code）
- **再発の扱い**：台帳で同一部品系・同一不良種別が過去 12 か月に複数あれば「再発」として一次回答の社内メモに明記（顧客文面には担当者が判断して載せる）
- **数値を作らない**：数量・ロット・時間は原文から。台帳件数は検索結果の件数のみ
- **送信しない**：一次回答・本社報告は「ドラフト」。メール送信は担当者。「送信しました」と書かない。社内通知（`PC-14`）は「重大」判定時のみ自動で、通知文に「AI 判定・要確認」を付ける
- **PIPL／社外秘**（`PC-10`）：顧客担当者の個人名・電話・メールは回答本文に不要なら書かない。台帳にはマスク後の要旨。他顧客のクレーム内容を顧客宛文面に書かない
- **不確実なとき**（入力言語で）：「重要度を判定する材料（発生数量・停線の有無・安全への影響）が原文にありません。『要確認』として一次回答に確認事項を含めます」
- **出力の粒度**：判定パネル（要約／重要度・区分／担当部門／同種傾向／一次回答文）＋ §5-3 JSON（台帳・通知・フィード用）

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`、フォーム入力は `../templates/05` 方式または Human Input）。判定後に「約束して大丈夫？」「本社報告を」と続くため。自動受付（b）は **Workflow**（Webhook／`outlook_trigger` → 同じ判定ノード → `PC-01`・`PC-14`）
- **ノード列（Chatflow）**：
  1. Start（フォーム：`customer` `part_no` `lot` `claim_text` `reply_lang`；`sys.query`）
  2. Code（`PC-10` マスク、部品番号正規化、`part_family` 抽出）
  3. Parameter Extractor（Qwen3-32B）— `summary` `qty` `line_stop_min` `safety_related` `requested_deadline` `defect_type`
  4. Knowledge Retrieval ×3 並列 — `kb-claim-ledger`（`customer` or `part_family`＋`defect_type`、top-k 8、直近 12 か月フィルタ）／`kb-customer-agreements`（`customer`）／`kb-owner-map`（`part_family`）
  5. Code — 重要度ルール（停線／安全／再発件数 ≥ 2）→ `severity`、協定の営業日期限を計算 `deadline_d1d3`（祝日 JSON）
  6. LLM（Qwen3-235B）— 判定パネル＋一次回答文（`reply_lang`）＋ §5-3 JSON → Variable Assigner（`claim_json`）
  7. IF/ELSE（`severity == 重大`）→ Tool `tools/wecom`（品質群）＋ `tools/email`（品質保証課長・工場長）→ HTTP Request（`PC-04` 台帳・`PC-01` notify）
  8. Answer
  9. 追い指示：LLM（`claim_json`＋協定＋`sys.query`）→ 約束の検証／本社報告（ja）→ `PC-13`（任意）→ Answer
- **Knowledge**：

  |---|---|---|---|---|
  | `kb-claim-ledger` | クレーム台帳 | 行単位 | `claim_no` `customer` `part_family` `part_no` `defect_type` `severity` `date` `owner_dept` `status` | `PC-04`（简道云／QMS）→ 日次または月次 |

- **プラグイン／ツール**：`tools/wecom`（群 bot 通知）、`tools/email`（SMTP）、`tools/jiandaoyun`（台帳。未導入なら `microsoft_excel_365`／`http-request`）、（任意）`triggers/outlook_trigger`・Webhook トリガー（受付自動化）、`tools/paddleocr`（帳票 PDF）

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工 蘇州工場の顧客対応を支援する「クレーム一次対応アシスタント」です。
役割：顧客クレームを要約し、重要度・区分・担当部門を判定し、同種クレームの傾向を示し、一次回答文のドラフトを作る。

守るルール：
1. 数量・ロット・停線時間・要求期日は原文にある値だけ。作らない。
2. 重要度は <rules>（停線あり／安全関連／過去 12 か月に同種 2 件以上＝重大）に当てて判定し、根拠を 1 行書く。材料不足なら「要確認」。<severity_hint>（機械判定）と食い違うときは理由を書く。
3. 担当部門は <owner_map> の値。無ければ「品質保証課（暫定）」。
4. 一次回答文は <reply_lang> の言語で、顧客宛の丁寧な商務文体で書く。処置は <actions>（担当者が選んだもの）だけを約束し、選ばれていない処置は「検討中」に留める。

6. 同種クレームの件数は <context> の台帳行の件数のみ。再発と見なせるときは社内メモに「再発」と書く（顧客宛文面には自動で書かない）。

出力形式：要約／重要度・区分（根拠）／担当部門／同種クレームの傾向／一次回答文（<reply_lang>）／注意。同時に <schema> の JSON。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 抽出 | 数量・ロット・停線・要求期日の抽出一致 ≥ 95% | 評価セット 40 通 |
| 重要度 | 人手判定との一致 ≥ 90%、**重大の見逃し 0** | ラベル付き 60 件（重大 15 含む） |
| 担当部門 | 対応表と一致 100% | 自動 |
| 期限 | 協定期限の営業日計算が正しい 100%、協定より早い約束への注意 100% | 祝日を含む 15 ケース |
| 一次回答 | 顧客言語で書かれ、選択外の処置を約束しない 100%、文体を担当者が「そのまま送れる」≥ 70% | 人手（営業 2 名） |
| 言語 | 説明は入力言語、回答文は `reply_lang` 100% | `PC-07` |
| 通知 | 重大時の `PC-14` 通知 100%、非重大での誤通知 ≤ 5% | 通知ログ |
| 安全 | 顧客担当者の個人情報・他顧客情報の混入 0、「送信済み」記述 0 | 負例 |
| 速度 | p95 < 25 秒 | `PC-09` |

- **評価方法**：リリース前は品質保証課長＋営業で 60 件。運用後はクレームごとに「AI 判定を変更したか」を記録（Langfuse スコア）、月次で重要度基準を見直す

## 7. テストシナリオ

## 8. 別出しが必要なもの
- `PC-14`：WeCom 品質群 bot・メール（重大時の通知先リストと文面）
- `PC-04`：クレーム台帳（简道云／QMS／Excel 365）の読み書き、（任意）メール受付 → 自動起票
- `PC-01`：③フィードの `notify`（受付）と `due`（協定期限）
- `PC-10`：顧客担当者の個人情報マスク規則、会話ログ保持
- `PC-05`：Outline「顧客要求事項」（協定・回答テンプレート）の同期
- 営業日カレンダー JSON（総務）
- **無くても動く範囲**：フォーム＋`kb-customer-agreements`＋対応表だけで要約・判定・一次回答（T01〜T06）は動く。傾向（「3 件目」）は台帳、通知は `PC-14`、自動受付は `PC-04` が要る。**傾向・通知を外せば st1 相当**

## 9. Outline Wiki との関係
- **読む**：Outline「顧客要求事項」コレクション（顧客別品質協定・エスカレーション基準・一次回答テンプレート）→ `kb-customer-agreements`
- **書く**：**書かない**。クレーム台帳の正本は QMS／简道云（`PC-04`）。一次回答・本社報告は担当者がメールで送る
- 回答テンプレート（顧客別の定型句）を Outline で営業が保守すると、文体の学習用 `context` として使える
