## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（月次 KPI の確認時、数値の悪化に気づいたとき）。③業務フィードには乗らない（都度実行のため）
- **登場人物**：経営企画部の調査役（分析する側）、KPI に関わる各部門（審査部・事務統括部など）
- **いまの手順（Before）**：担当者が BI ダッシュボードの出力（PDF・CSV）を目で見て、傾向・外れ値・前月との差を手作業で拾い出す。気づきを言語化するのに時間がかかり、担当者の経験によって拾える論点にばらつきが出る
- **エージェント導入後の手順（After）**：
  1. BI ダッシュボードから出した PDF や CSV をそのまま渡す
  2. 傾向・外れ値・前月との差が文章で返る
  3. 担当者が**確認すべき点を整理し、次のアクション（誰に何を確認するか）を決める**（AI は原因を断定しない）
- **成功の定義**：数字を眺めるところから「次に何を調べるか」までを 1 往復で進められ、月次報告レビュー（`DC-08`）への論点提供が速くなる

| KPI の目標値・定義 | 参照データ | — | マスタ | `data/world/fin/kpi.csv` 相当（延滞率・稟議処理日数 等） | 顧客側の KPI マスタ（本番は Outline または DB） | 目標値との差分計算に使う |

- **入力言語の扱い**：アップロードされる PDF・CSV は日本語・中国語どちらもあり得る。担当者とのやり取りは**入力言語で返す**（`CLAUDE.md` §2-5）
- **入力の欠け・曖昧さ**：目標値が無い指標は差分を出さず「目標未設定」と書く。前月分のデータが無い（初回）場合は「前月比較なし」と明示する

## 3. 観点（LLM に守らせる業務ルール）

- **数値は Code の計算結果を転記する**：差分・比率の算出は LLM にさせない。前月比・目標差は `Code` の出力をそのまま使う
- **外れ値と因果関係を区別する**：「同時期に悪化している」という事実と、「原因である」という断定を混同しない。**この 1 か月分のデータだけでは因果関係は特定できない**、と明示する
- **示唆は仮説として書く**：「〜の可能性が考えられるが、確認するには〜が必要」の形で書き、断定しない
- **確認すべき点は 3 件程度に絞る**：優先順位をつけ、それぞれ誰が・何を確認するかを示す
- **禁止**：1 か月分のデータから因果関係を断定する／個人・部署の責任を名指しで問う書き方をする（DC-08 §3-4 と同じ禁止事項を準用）
- **不確実なとき**（入力言語で）：ja「この指標は目標値が設定されていません。」／zh「该指标未设定目标值。」
- **出力の粒度**：指標ごとの状況（値・目標・前月差）→ 外れ値 → 前月との差 → 示唆（仮説） → 確認すべき点（3 件程度）

## 4. Dify 構成

- **アプリ種別**：**Workflow**（`Start(file-list)` → 抽出 → 分析 → 結果）
- **ノード列**：
  1. `Start`（PDF・CSV。複数可）
  2. `Document Extractor`（PDF → テキスト・表）／`tools/dify_extractor`（CSV → 行レコード）
  3. `Code`（指標ごとの値・目標との差分・前月比の計算。外れ値の機械的検出：目標未達が継続している指標のフラグ立て）
  4. `LLM`（傾向・外れ値の言語化、示唆の生成。§5 のプロンプト）
  5. `Code`（検算：示唆が「断定」表現になっていないかの禁止語チェック）
  6. `Answer`（指標ごとの状況・外れ値・前月差・示唆・確認すべき点）
- **Knowledge**：使わない
- **プラグイン／ツール**：`Document Extractor ノード`、`tools/dify_extractor`（`../plugins-and-references.md` §1）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（言語化・示唆の生成）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（PDF/CSV 入口の型）
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `files` | file[] | ✓ | KPI ダッシュボード PDF・CSV |
  | `targets` | object | — | 指標の目標値（無ければ「目標未設定」扱い） |
  | 出力 `findings` | array[object] | ✓ | 指標ごとの状況 |
  | 出力 `insight` | string | ✓ | 示唆（仮説として） |
  | 出力 `checks` | string[] | ✓ | 確認すべき点（3 件程度） |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 経営企画部のダッシュボード分析アシスタントです。
アップロードされた月次 KPI の傾向・外れ値・前月との差を、計算済みの数値（{{metrics_json}}）から言語化します。
守ること：
1. 数値は与えられた {{metrics_json}} をそのまま使う。自分で計算・推定しない。割り算を文章の中で行わない。
2. 同時期に複数の指標が悪化している事実と、原因であるという断定を区別する。「この1か月分のデータだけでは因果関係は特定できない」ことを明示する。
3. 示唆は仮説として書き、「〜の可能性が考えられるが、確認するには〜が必要」の形にする。
4. 確認すべき点は3件程度に絞り、誰が・何を確認するかを示す。
5. 個人・部署の責任を名指しで問う書き方をしない。落ちているのは指標・工程だと書く。
6. 目標値が無い指標は「目標未設定」と書き、差分を出さない。
7. 言語：担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：指標ごとの状況 → 外れ値 → 前月との差 → 示唆（仮説）→ 確認すべき点（3件程度）の順。
```

```text
指標ごとの計算結果（Code 転記のみ）：{{metrics_json}}
目標値（無い指標は null）：{{targets}}
```

```json
  "checks": [ "延滞先の与信先の稟議更新が遅延していないか", "丙社関連の稟議集中が他の案件の処理を遅らせていないか", "延滞率の目標未達が続く場合の対応方針" ]
```

### 5-4. Few-shot

**不要**。示唆は月ごとの数値に依存するため、書式は System と JSON スキーマで固定する。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 数値の非捏造 | `findings`/`outliers` の数値が入力 JSON と完全一致 100% | 自動突合 |
| 因果の非断定 | 「原因は〜」のような断定表現の出現 0 | 禁止語 + LLM-as-judge |
| 示唆の仮説表現 | 「可能性が考えられる」等の仮説表現を含む ≥ 95% | 自動（表現パターン検査） |
| 確認事項の件数 | 3 件程度（2〜4 件） | スキーマバリデータ |
| 非個人化 | 個人・部署名を名指しで問う表現 0 | 負例セット |
| 言語 | やり取りは入力言語 100% | 自動判定（`PC-07`） |
| 速度 | p95 < 30 秒 | Langfuse |

- **評価方法**：リリース前に経営企画部で 15 件を人手採点（欠陥を仕込んだ評価セット含む）

## 10. 未確定・リスク

- **実現性を ○ とした理由**：ファイルアップロード・Code 計算・LLM 言語化は標準機能で完結するが、(1) BI ダッシュボードの出力形式（PDF のレイアウト・CSV の列構成）が顧客ごとに異なる可能性、(2) 因果関係を断定しない書き方が LLM のモデル・プロンプト調整に依存する、の 2 点で ◎ にしていない
- **DC-08 との連携**：本サービスの「確認すべき点」は月次報告レビュー（`DC-08`）の `trend_file` や論点の元データとして使える（台本参照）。連携経路（自動で DC-08 に渡すか、担当者が手動で転記するか）は未確定
- **KPI マスタの正本**：`data/world/fin/kpi.csv` はデモ用の架空値。本番では顧客側の KPI マスタ（Outline または DB）を参照する経路が必要
