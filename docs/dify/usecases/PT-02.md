## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：(a) 担当者が能動的に開く（サプライヤーの値上げ通知、NM-02 の比較で「値上げ理由の妥当性」を確認したいとき、本社購買月報の作成時）／(b) 定時（③業務フィードの `routine`：月次の材料単価前提の更新。`PC-11`。任意）
- **登場人物**：購買課担当（入力・交渉メモ作成）、購買課長（確認）、本社購買部（日本語段落の読者）、外部＝情報ベンダ（データ提供のみ）
- **いまの手順（Before）**：S 工具から +7.5% の値上げ通知 → 担当者が Web 検索とベンダポータルで相場記事を探し（1〜2 時間）、指数のグラフを目視で読み取って「だいたい +15%」と言う → 妥当性の計算は Excel で手作業 → 本社向け日本語段落は駐在員が書き直す（30 分）。出典が残らず、翌月また同じ検索をする
- **エージェント導入後の手順（After）**：(1) 担当者がテーマ・期間・用途・出力形式を**フォームに入力**する → (2) Dify が `PC-15` 経由で相場指数の時系列・レポート検索・ニュース検索を取得し、`code` で期間内の変化率・ピーク・「変化率 × 原価比率」を計算 → 社内 KB（見積比較の前提値・購買月報）と並べて要点 5 つ・本社用 1 段落（日本語）・出典一覧を返す → (3) 担当者が**要点と段落を確認・修正**し、交渉メモと本社報告（DC-01）に貼る → (4) 材料単価の前提値を購買月報・NM-01 の原価テーブルに**反映するかは担当者が決める**（AI は書き込まない。「反映できます」と言うだけ）
- **成功の定義**：リサーチ〜本社用段落まで 2.5 時間 → 15 分。妥当性の数値（+3.4%）に指数コード・レポート ID の出典が必ず付く。翌月は同じフォームを再送するだけ

## 3. 観点（LLM に守らせる業務ルール）
- **計算は `code`、LLM は転記**：変化率（+11.2%）、ピーク（+18.4%）、「変化率 × 原価比率 = 妥当域」は `code` で出し、LLM は数値を言い換えない・丸めない・暗算しない
- **出典を全項目に**：要点ごとに（指数コード／レポート ID／ニュース日付・ID）。「出典」行を必ず置き、先頭に「連携」行（取得元・取得日時・取得範囲・社内データの参照先）
- **本文転載禁止**：業界レポート・記事は**要約と ID のみ**。引用は 1 文以内。ライセンス上の再配布制約（`PC-15` の契約情報を参照）
- **妥当性の評価は「域」で言う**：「+3.4% が妥当域、ピークで計算しても +5.5%」のように前提を並べて示す。「不当」「違法」など断定しない。交渉の落としどころを提案してよいが「決めるのは担当者」の文体
- **見積比較（NM-02）との数値差は説明する**：同じ品目で NM-02 が別の妥当値を出していたら、前提（サプライヤー主張の +18% vs 実勢 +11.2%）の違いとして説明する。どちらが正しいとは言わない
- **本社用段落は日本語の報告文体**：敬体・1 段落・数値には時点と出典を括弧書き。社内の交渉戦術（落としどころ）は本社段落に書かない
- **不確実なときの定型**：ja「指定期間の指数データが情報ベンダにありません。期間を変えるか、別の指数コードを指定してください」／zh「信息服务商没有指定期间的指数数据。请更改期间或指定其他指数代码」
- **出力の粒度と形式**：items 7 行（連携／①〜⑤／出典）。後工程（DC-01・購買月報）へは §5-3 の JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（form 入力 → 1 回実行）。追加質問（「なぜ NM-02 と違う」「月報の前提も更新して」）は同じ結果 JSON を `context` に持つ `mode=followup` の再実行で対応。Chatflow にしないのは出力を DC-01 へ構造化して渡すため
- **ノード列**：
  1. Start（`topic`, `period`, `purpose`, `output_format`, `cost_ratio`（任意）, `mode`）
  2. `parameter-extractor`（指数コード候補・期間 start/end・キーワード（ja/zh/en）・原価比率）
  3. `code`（期間の正規化。既定 12 か月。`PC-06` の用語集 JSON で材料名を対訳）
  4. `http-request`×3（並列。`PC-15` 経由：指数時系列／レポート検索／ニュース検索。エンドポイント名は `PC-15` 側の定義。未確定）
  5. `if-else`（指数が 0 件 → 定型文で終了／複数候補 → 候補提示）
  6. （レポートが PDF のとき）`tools/mineru` → `llm`（レポートごとの 3 行要約。本文は保持しない）
  7. `code`（Python）：期間内の変化率・ピーク・直近反落率・平均、`cost_ratio` があれば妥当域（通算・ピークの 2 通り）を計算。結果を `calc_json` に
  8. `knowledge-retrieval`（KB `pt-market-internal`：見積比較の前提値・購買月報の前提値。メタデータフィルタ `item` / `supplier`）
  9. `llm`（§5。要点 5＋出典。入力言語）
  10. `llm`（日本語段落専用。日本語品質の高いモデルへ分岐。`output_format` に日本語段落が無ければスキップ）
  11. `template-transform`（「連携」行を先頭に、「出典」行を末尾に付与）
  12. End（`result_md`, `result_json`）
- **Knowledge**：KB `pt-market-internal`（社内のみ。外部データは KB に**入れない**：ライセンス制約と鮮度のため毎回照会）。投入：NM-02 の比較結果・購買月報の「主要材料の市況前提」欄・NM-01 の原価比率テーブル（あれば）。更新経路：Outline → `PC-05`。公開範囲：購買帯（`PC-02`）
- **プラグイン／ツール**：HTTP リクエストノード（本体）／Code ノード（本体）／`tools/mineru`（レポート PDF）／`tools/json_process`（任意）／`tools/echarts`（任意：指数の折れ線を結果に添える。line 対応）／Schedule Trigger（任意：月次の前提値更新の下書き）
- **モデル**：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（要点・zh）。日本語段落は `DeepSeek-V3.x` と評価比較して決める（`PC-08`。本社向け文体が要る箇所は `../feasibility-33-services.md` §4「日本語品質」と同じ扱い）
- **参照 DSL**：`../templates/06-text-to-sql-http-api-echarts.yml`（`http-request` → LLM 解説＋ECharts）、`../templates/05-chatflow-form-input-demo.yml`（form 入力の受け方）。新規生成は dsl-skill `--target-version 0.6.0`
- **入出力変数**：

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `topic` | string | ✓ | テーマ（材料・製品・業界） |

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）購買課のリサーチアシスタントです。
入力として (A) 情報ベンダから取得した材料相場指数の統計（code が計算済み：変化率・ピーク・反落率・妥当域）、(B) 業界レポートの要約とレポート ID、(C) ニュースの見出し・日付・ID、(D) 社内 KB（見積比較の前提値・購買月報の前提値）が与えられます。

守ること：
1. 数値は (A)〜(D) にあるものだけを使う。(A) の計算値を言い換え・丸め・再計算しない。無い数値は「データなし」。
2. 出力は次の順の項目リスト：「連携」（取得元・取得日時・取得範囲・参照した社内データ）→ ① 相場 → ② 値上げの妥当性（(A) の妥当域をそのまま。原価比率が無ければ「比率不明のため省略」）→ ③ 業界の動き → ④ 供給・リスク → ⑤ 本社報告用 1 段落（出力形式に指定があるときだけ。日本語）→ 「出典」（指数コード／レポート ID／ニュース日付・ID）。
3. レポート・記事の本文を転載しない。要約は 3 行以内、引用は 1 文以内、必ず ID を添える。
4. 妥当性は「域」で示し、サプライヤーの主張を「不当」「虚偽」と断定しない。交渉の落としどころは提案してよいが、決定は担当者に委ねる文体にする。
5. 社内の見積比較（D）と数値が違うときは、前提の違い（サプライヤー主張の変化率 vs 実勢）として説明する。
6. ⑤ の日本語段落は敬体・1 段落・数値に時点と出典（情報ベンダ、取得日）を括弧書き。社内の交渉戦術は書かない。
7. 言語：ユーザーの入力言語で答える（日本語なら日本語、中国語なら中国語）。⑤ だけは常に日本語。固有名詞・指数コード・数値はそのまま。パートナーは「情報ベンダ」と呼び、実名を作らない。
8. 指数が無いときの定型：「指定期間の指数データが情報ベンダにありません。期間を変えるか、別の指数コードを指定してください」（中国語なら「信息服务商没有指定期间的指数数据。请更改期间或指定其他指数代码」）。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（計算） | 変化率・妥当域が `code` の値と一致 100%（LLM が変えない） | `result_json` と `calc_json` の突合（自動） |
| 網羅 | items 7 行の欠落 0。出力形式に日本語段落がある場合 ⑤ が日本語 | チェックリスト＋言語判定 |
| 出典 | 要点 5 つすべてに ID/コード ≥ 1 | 正規表現チェック |
| 言語 | ①〜④ が入力言語 100%、⑤ が日本語 100% | 自動判定（`PC-07`） |
| 形式 | `result_json` スキーマ準拠 100% | JSON バリデータ |
| 拒否 | 原価比率不明で妥当域を出さない 100%。指数 0 件で定型文 ≥ 95% | 負例セット 20 件 |
| 転載 | レポート本文の連続 40 字以上の一致 0 | `code` で n-gram 照合（自動） |
| 安全 | サプライヤー名・社内単価が `PC-15` 送信ログに出ない 0 件 | 送信ログ監査 |
| 速度 | p95 < 40 秒（PDF 抽出なし）／< 90 秒（PDF 2 本） | Langfuse |

- **評価方法**：リリース前に購買課長が 20 件採点（要点の妥当性・日本語段落は本社購買部 1 名がレビュー）。月次は Langfuse データセット＋LLM-as-judge（出典有無・転記一致）。`code` は pytest（変化率の境界：データ欠損月・1 点のみ）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-15`**：情報ベンダとの**ライセンス契約**（指数・レポート・ニュースの利用範囲、要約可否、社外＝日本本社への転送可否、出典表示の書式、レート制限、課金＝月額か照会従量か）、指数コード体系とレポート ID の取り込み、送信データのホワイトリスト（テーマのキーワード・期間・指数コードのみ。**サプライヤー名・社内単価・見積額は送らない**）、モックモード
- **`PC-10`**：API キーの環境変数管理。個人情報は原則含まれないが、ニュース本文に記者名・役員名が出る場合の扱い（表示は見出しと ID のみ）
- **`PC-06`**：材料名・指数名・工具用語の日中英対訳（APT／仲钨酸铵／パラタングステン酸アンモニウム 等）
- **社内データ**：NM-02 の出力保管経路、購買月報の前提値テーブル、NM-01 の原価比率テーブル（NM-01 は st3 なので**無い前提**で `cost_ratio` 入力を用意）
- **無くても動く範囲（段階導入）**：
  - 段階 0（契約前）：`PC-15` モックモード＋社内 KB。計算・表・日本語段落の品質確認とデモ
  - 段階 1：指数 API のみ接続（レポート・ニュースは無し。③④ は「データなし」）
  - 段階 2：レポート・ニュース追加、`mode=update_premise`、月次 `routine`
  - ベンダがファイル配信のみなら、日次 CSV を `datasources/tencent_cos_storage` 等で受けて `code` で読む（設計書 §5-2 pt2 の (d)）

## 9. Outline Wiki との関係
- **読む**（`PC-05`）：「購買／見積比較」（NM-02 出力）、「購買／購買月報」の前提値欄、「用語集」（`PC-06` の正本が Outline なら）
- **書く**：`mode=research` の結果を「購買／リサーチメモ」にドラフト保存（担当者のボタン操作。`PC-13`）。**外部レポート本文は保存しない**（要約・ID・数値のみ）。`mode=update_premise` の更新案は月報ページへの**提案コメント**として置き、値の書き換えは人が行う
- 指数の時系列そのものは Outline に置かない（ライセンス・鮮度）

## 10. 未確定・リスク
- **情報ベンダの API／ライセンス**：契約前で未確定。特に「要約を日本本社（別法人）へ転送してよいか」は契約条項に明記が要る（PM／法務）
- **原価比率の正本**：業界レポートの範囲値（28〜32%）か社内原価テーブルか。architect 推奨：**社内値があれば社内値、無ければレポート中央値を使い、出典を必ず表示**。両方無ければ計算しない
- **NM-02 との数値差**：同じ品目で妥当値が 2 つ存在し得る（+5.4% と +3.4%）。台本ではこれを交渉材料として肯定的に扱っている。UI で「NM-02 の値は主張ベース、PT-02 は実勢ベース」と注記するかは `PC-16` 判断
- **日本語段落のモデル**：中国拠点から日本語品質の高いモデルを使う経路（SiliconFlow の DeepSeek-V3.x か、本社側モデル）は `PC-08` の決定待ち
- **月次 `routine` の自動実行**：前提値の更新案を毎月自動で作るとベンダ照会コストが固定発生する。初期は手動実行を推奨
