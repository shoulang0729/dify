## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：スタッフが能動的に開く（多くは WeCom からスマホで、就業時間外も含む）。③業務フィードには、人事側の「未回答の引き継ぎ」が `notify` として乗り得る（`PC-01` 連携は任意）
- **登場人物**：質問者（現場作業者〜事務職。中国語母語が大半、新入社員が多い）、人事窓口担当（引き継ぎ先）、IT・総務担当（申請系の引き継ぎ先）
- **いまの手順（Before）**：
  1. 新入社員が「誰に聞けばいいか分からない」ままラインリーダーに聞き、リーダーが人事に WeCom で聞く（往復 半日〜1 日）
  2. 人事窓口には同じ質問（証明書・社保・休暇申請・IT アカウント）が**月 200 件以上**届き、担当 2 名の時間の 3 割を占める
  3. 問い合わせの記録は残らず、FAQ が育たない
- **エージェント導入後の手順（After）**：
  1. スタッフがスマホ（WeCom）から中国語で質問する
  2. エージェントが社内 FAQ・申請手順から**申請先・必要書類・所要日数**を返す。分からない問いは「推測せず」引き継ぎを提案
  3. **スタッフが「引き継いでほしい」と選ぶ**（勝手に引き継がない）→ 受付番号を発行し、担当部署へ WeCom/メール通知、台帳に記録（`PC-04`）
  4. 人事担当は台帳の分類を月次で見て **FAQ に追加するかを決める**（ドラフトは AI、公開は人）
- **成功の定義**：定型問い合わせの人事到達を 5 割削減。未解決を受付番号付きで**取りこぼし 0**。FAQ を月次で育てる

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。駐在員が日本語で聞いても同じ FAQ から日本語で答える

## 3. 観点（LLM に守らせる業務ルール）
- **FAQ の範囲で答える**：申請先・必要書類・所要日数・受け取り方法は FAQ／手順にある値のみ。所要日数を推測で短縮・延長しない
- **社外要件は断定しない**：市の学校・銀行の要件は「一般に」「学校（銀行）により異なる」を付け、会社発行書類の範囲だけ確実に答える
- **引き継ぎは人が選ぶ**：回答できないときは「人事窓口に引き継ぎますか？」と聞き、同意後に受付番号を発行する。**自動で転送しない**
- **PIPL**（`PC-10`）：身分証番号・電話番号・住所を回答に繰り返さない。「必要な情報」は項目名（身分証番号）で示し、値は入力させない案内を添える。台帳には質問要旨と分類のみ保存（本文は保存しない設定も可）
- **推測しない**：担当者名・内線番号は窓口一覧にあるものだけ。無ければ「部署名」まで
- **登録しない**：申請そのものは行わない（ポータルの申請フォームを案内する）
- **不確実なとき**（入力言語で）：「社内 FAQ に該当がありません。人事窓口に引き継ぎますか？（はい／いいえ）」
- **出力の粒度**：箇条書き（申請先／必要なもの／所要日数／受け取り）4 行 → 補足 1 行。引き継ぎ時は受付番号と連絡予定を 1 行

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`）。多輪（用途の聞き返し・引き継ぎ同意）と WeCom bot 接続のため。引き継ぎ同意は会話変数 `handoff_pending` で管理
- **ノード列**：
  1. Start（`sys.query`、`sys.user_id`）
  2. Code（`PC-10` マスク：身分証 18 桁・電話 11 桁を `***` に。マスク後テキストを以降に渡す）
  3. Question Classifier — `入社手続き` / `社会保険` / `休暇` / `証明書` / `IT 申請` / `引き継ぎ同意` / `その他`
  4. 分類ごとに Knowledge Retrieval（`kb-hr-faq` を `category` フィルタ、top-k 4）＋ `kb-hr-procedures`（top-k 3）→ LLM（本体）→ Answer
  5. LLM 出力の `can_answer=false` → Answer「引き継ぎますか？」＋ `handoff_pending=true`（Variable Assigner）
  6. `引き継ぎ同意` 分岐（`handoff_pending` かつ肯定）→ Code（受付番号 `HD-MMDD-NNN` 生成、分類・要旨 JSON）→ Tool `tools/wecom`（人事群 bot へ通知）または `tools/email` → HTTP Request（`PC-04` 台帳：`tools/jiandaoyun` か `tools/microsoft_excel_365`）→ Answer（受付番号）
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-hr-faq` | 社内 FAQ | **Q&A チャンク** | `category` `owner_dept` `updated` `lang` | Outline FAQ → `PC-05`（週次）。月次で人事が追加 |
  | `kb-hr-procedures` | 申請手順・様式・窓口一覧・対外要件メモ | 一般チャンク | `category` `owner_dept` `version_date` | 同 |
- **プラグイン／ツール**：**`extensions/wecom_bot`**（入口）、`tools/wecom`（群通知）、`tools/email`（代替）、`tools/qa_chunk`、`tools/dify_extractor`、`tools/jiandaoyun` または `tools/microsoft_excel_365`（台帳。未導入なら `http-request` で `PC-04` の薄い API）
- **モデル**（`PC-08`）：既定 SiliconFlow `Qwen3-32B`（中国語主体・短文・コスト低）。分類は同モデル。日本語質問の品質が不足なら `Qwen3-235B-A22B-Instruct` へ。**人事系のため越境ゼロ（`models/ollama` Qwen）が候補**（F-4 (c)）
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（question-classifier → KB 別検索）。dsl-skill `05-question-classifier` / `08-human-approval` は URL 参照のみ（`../templates/README.md`）
- **入出力変数**：
  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `sys.query` | string | ✓ | 質問（マスク前） |
  | `masked_query` | string | ✓ | `PC-10` マスク後 |
  | `lang` | string | ✓ | 入力言語 |
  | `category` | enum | ✓ | 分類結果 |
  | `handoff_pending` | boolean（会話変数） | ✓ | 引き継ぎ同意待ち |
  | `ticket_no` | string | — | 受付番号 |
  | 出力 `answer` | string | ✓ | 回答 |
  | 出力 `ticket` | object | — | §5-3（台帳・通知用） |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工 蘇州工場の「労務・総務ヘルプデスク」です。社内 FAQ と申請手順から、社員の定型質問に答えます。

守るルール：
1. 申請先・必要書類・所要日数・受け取り方法は <context>（FAQ・手順）にある内容だけを答える。所要日数を推測で変えない。
2. 市役所・学校・銀行など社外の要件は「一般に」「学校（銀行）により異なります」を必ず付け、会社が発行できる書類の範囲だけ確実に答える。
3. 答えられないときは推測せず、「社内 FAQ に該当がありません。人事窓口に引き継ぎますか？」と聞く。ユーザーが同意する前に引き継ぎ・転送を行ったと書かない。
4. 身分証番号・電話番号・住所などの個人情報を回答に繰り返さない。必要な情報は項目名（例：身分証番号）で示し、「チャットには入力せず窓口で提示してください」と添える。
5. 担当者の氏名・内線は窓口一覧にあるものだけ。無ければ部署名まで。
6. 申請を代行しない。申請フォーム・窓口の場所を案内する。
7. 言語：ユーザーの入力言語で答える。中国語なら中国語、日本語なら日本語。
8. 出力は 4 行の箇条書き（申請先／必要なもの／所要日数／受け取り）＋補足 1 行。最後に JSON 1 行で can_answer と category を出す（表示はしない）。
```
### 5-2. User テンプレート
```text
<context>
[faq] {{#kb_faq.result#}}
[procedures] {{#kb_proc.result#}}
</context>
<meta>入力言語: {{lang}} / 分類: {{category}} / 引き継ぎ待ち: {{handoff_pending}}</meta>
質問（個人情報はマスク済み）: {{masked_query}}
```
### 5-3. 出力フォーマット（引き継ぎ時に `PC-04` 台帳と `PC-14` 通知へ渡す）
```json
{ "ticket_no": "HD-0906-014", "category": "证明开具", "owner_dept": "人事窓口",
  "summary": "子女入学用 在职证明＋社保缴纳证明 の申請期限相談", "lang": "zh",
  "requester": "<sys.user_id>", "contains_pii": false, "promised_contact": "翌営業日中", "status": "open" }
```
- 台帳に**質問本文は保存しない**（要旨のみ）。`contains_pii=true` なら要旨も人事のみ閲覧
### 5-4. Few-shot
- **zh**：Q「社保参保证明在哪里可以开？」→ A「・申请渠道：人事窗口（管理部2楼）或内部门户「证明申请」／・所需信息：身份证号、用途／・所需时间：3个工作日／・领取：本人到窗口。补充：若用于房贷，请先向人事提供银行格式。」
- **ja**：Q「社会保険の加入証明書はどこで貰える？」→ A：同 4 行を日本語で

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | 申請先・書類・日数が FAQ と一致 ≥ 95% | 評価セット 40 件を人事担当が採点 |
| 分類 | Question Classifier の一致率 ≥ 90% | ラベル付き 100 件 |
| 引き継ぎ | 回答不能時に「引き継ぎますか」提示 100%、同意前の自動転送 0 | 負例 20 件＋台帳突合 |
| 言語 | 入力言語で返答 100% | `PC-07` |
| 安全（PIPL） | 個人情報の回答内繰り返し 0、台帳本文保存 0 | 負例 15 件＋台帳監査 |
| 形式 | `ticket` JSON スキーマ準拠 100% | バリデータ |
| 速度 | p95 < 8 秒（スマホ体感） | `PC-09` |

- **評価方法**：リリース前は人手。運用後は Langfuse で「引き継ぎ率」「同一質問の再発」を月次集計し、FAQ 追加候補を人事に提示

## 9. Outline Wiki との関係
- **読む**：Outline「総務・人事 FAQ」「申請手順」コレクション → `kb-hr-faq`（Q&A）／`kb-hr-procedures`。FAQ は Outline 上で Q/A の見出し規約（`## Q:` / `A:`）を決めると `qa_chunk` に乗せやすい
- **書く**：月次で「未回答・引き継ぎになった質問の分類と回答案」を Outline「FAQ ドラフト」コレクションに**ドラフト**として作成（`http-request`）。公開は人事が判断
- Outline を使わない場合：FAQ を xlsx で管理し `PC-03` に月次投入

## 10. 未確定・リスク
- **引き継ぎ先と台帳の実体**（WeCom 群 or メール／简道云 or Excel 365 or DB）— 顧客確認。推奨：WeCom 群通知＋简道云台帳（中国側で完結）
- **個人情報の越境**：質問文に個人事情が含まれる → `PC-10` マスクを Dify 到達前（WeCom 中継層）で行うか、`models/ollama` 構成にするかを顧客法務と決める
- **就業時間外の利用**（夜間・休日の問い合わせ）に「翌営業日中に連絡」の約束文言でよいか — 人事と合意
- **WeCom bot の公開エンドポイント**（セルフホスト・F-7）
- **FAQ の鮮度**：所要日数や窓口変更が FAQ に反映されないと誤答になる → 月次更新の責任者を決める
