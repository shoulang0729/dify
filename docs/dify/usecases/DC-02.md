## 1. 業務シナリオ
- **トリガー**：定時（毎週月曜の生産会議後、当日中に配布）。③業務フィードでは `routine`。臨時会議では担当者が能動的に開く
- **登場人物**：記録者＝秘書・通訳、確認者＝議長（工場長）と各決定事項の担当者、受け手＝出席者（日本人駐在員・中国人管理職）
- **いまの手順（Before）**
  1. 会議中に手書き・PC でメモ（日中混在の発言を聞きながら）。録音は保険
  2. 会議後、録音を聞き直して決定事項・担当・期限を拾う（50 分の会議で 1.5〜2 時間）
  3. 日本語版を書き、中国語版に訳す（1 時間）。ホワイトボードの写真を見て抜けを補う
  4. 工場長に確認してもらい配布。当日中に出せないことが多い
- **エージェント導入後の手順（After）**
  1. 【入力】文字起こしテキスト（または録音）とホワイトボード写真をアップロード
  2. 【生成】決定事項・ToDo（担当／期限）・未決事項・次回論点の議事録が日中 2 言語で返る。発言者不明は「担当：要確認」
  3. 【確認】記録者が「要確認」を潰す（文字起こしの時刻を引いて「誰が言ったか」を対話で確認）。担当者名・期限の誤りを直す
  4. 【決める】議長（工場長）が決定事項の文言と次回論点を承認。**AI は配布しない**
  5. 【保存・配布】Outline「会議録 › 生産会議 › YYYY-MM-DD」に保存し、配布メール文（日中併記）を人が送る
- **成功の定義**：会議終了から配布まで 2 日 → 当日 2 時間以内。決定事項・期限の記載漏れ 0。日中版の内容一致

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 文字起こし | txt / docx（タイムスタンプ付き推奨） | ja / zh 混在（6:4 程度） | 週 1 回、50 分 ≒ 8,000〜12,000 字 | 「09:31 高橋：K 社の 10 月納入計画が…」 | 録音アプリ／`PC-03` の STT | Document Extractor で文字列化。話者ラベル・時刻を保持 |
| 録音（任意） | m4a / mp3 / wav | ja / zh 混在 | 50〜90 分 | — | 会議室の録音機 | STT：SiliconFlow `sense-voice-small` か自前 `models/funasr`（音声を外に出さない）。**Workflow 内で音声を直接 STT するノードは 0.6.0 で未確定** → `PC-03` 側で文字起こししてテキストを渡す |
| ホワイトボード写真 | jpg / png | ja / zh / 記号 | 1〜3 枚 | 「国庆 → 高桥 9/12」 | スマホ撮影 | Vision LLM（Qwen-VL 系）で文字化。読めない箇所は「[判読不能]」 |
| 前回議事録 | Markdown | ja / zh | 1 件 | 前回の ToDo・未決事項 | Outline「会議録」（`PC-05`） | ToDo 表だけをコンテキストに渡す（継続確認用） |
| 出席者リスト（任意） | テキスト | — | 5〜10 名 | 「小林（工場長）、李（製造二課）…」 | フォーム入力 | 話者名の正規化辞書に使う |

- **入力言語の扱い**：文字起こしは日中混在のまま渡す。**議事録は ja・zh の 2 版を必ず出す**（サービスの定義。§2-5 の「入力言語で返す」は対話部分に適用：記録者の質問が中国語なら中国語で答える）
- **入力の欠け・曖昧さ**：文字起こしが無いと生成しない（写真だけでは決定事項を組めない）。話者不明・期限不明は**推定せず「要確認」**。聞き返し文：「文字起こしテキストをアップロードしてください（録音のみの場合は先に文字起こしを実行します）」／「请上传会议转写文本（仅有录音时请先执行转写）」

## 3. 観点（LLM に守らせる業務ルール）
- 決定事項は**発言の根拠（時刻または話者）を引ける**ものだけ。推測で決定にしない。会議で「検討する」と言ったものは未決事項へ
- 担当者・期限は発言にあるものだけ。無ければ「担当：要確認」「期限：要確認」。日付は会議日を基準に絶対日付（9/12）へ正規化し、曖昧なら原文（「来週前半」）を併記
- 管理番号（CL-／ECR-／NC-／E-47 等）は原文どおり。数値（n=125、192,000 個）を丸めない
- 次回論点は **未決事項と ToDo の期限**から導く（4〜6 件）。会議で出ていない新規テーマを提案しない
- 日中 2 版は**同じ項目数・同じ順**。片方だけに項目を足さない
- 個人情報（`PC-10`）：出席者の氏名は姓＋部署で記載（社内配布物のため許容）。会議中に出た個人の処遇・残業超過者名は「人事と協議」に丸め、氏名を書かない。給与・評価の話題はドラフトに含めず「※記録対象外の議題あり」と注記
- 不確実時の定型：「この箇所は文字起こしから特定できませんでした（HH:MM 付近）。確認してください」／「该处无法从转写中确定（HH:MM 附近），请确认」
- 出力形式：Markdown 2 版（見出し固定：出席／決定事項／ToDo（担当／期限）／未決事項／次回論点）＋ §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（アップロード → 1 回実行）。「誰が言ったか」の追加質問は `PC-16` が同 Workflow に `question` を付けて再実行し、`transcript` を再度渡す
- **ノード列**
  1. `start`：`files`（file-list）、`meeting_date`、`attendees`（任意）、`question`（任意）、`prev_todos`（任意）
  2. `iteration`（files）→ `if-else`（拡張子）→ 文書は `document-extractor`／画像は `llm`（Vision、Qwen-VL 系）で文字化 → `variable-aggregator`
  3. `llm`（構造化）：発言→決定・ToDo・未決の JSON。根拠時刻を付ける
  4. `llm`（論点）：未決＋ToDo 期限 → 次回論点 4〜6 件
  5. `llm`（対訳）：JSON の各文を zh ⇄ ja に揃え、2 版の Markdown を生成（用語は `PC-06` の対応表を context に）
  6. `template-transform` → `end`：`minutes_ja`, `minutes_zh`, `minutes_json`, `open_points[]`
  - `question` がある場合は 3 の代わりに `llm`（QA）：transcript から該当発言を時刻付きで引用して回答
- **Knowledge**：原則不要（その場の入力のみ）。継続確認のため前回議事録の ToDo は `prev_todos` として渡す（`PC-05` が Outline から取得）
- **プラグイン／ツール**：`models/siliconflow`（LLM・Vision・STT）、`models/funasr`（音声を外部に出さない構成、任意）。配布メールは `tools/email` か `tools/wecom`（`PC-14`、任意）
- **モデル**：Qwen3-235B-A22B-Instruct（日中混在の構造化）。Vision は Qwen2.5-VL / Qwen3-VL（SiliconFlow）。中国語主体の会議で日本語版も出すため、日本語の自然さは評価セットで確認（`PC-08`）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（file-list → document-extractor の骨子）、`../templates/02-long-document-chunk-iteration-translate.yml`（長い文字起こしを分割する場合）。事例：dify-for-dsl 52「三步实现音视频转文字会议纪要」、火山引擎記事（`../plugins-and-references.md` §11）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `files` | file-list（txt/docx/jpg/png） | ✓ | 文字起こし・写真 |
| `meeting_date` | string | ✓ | 会議日（期限の絶対化に使う） |
| `attendees` | paragraph | — | 出席者（姓＋部署） |
| `prev_todos` | paragraph | — | 前回 ToDo（継続確認） |
| `question` | paragraph | — | 追加質問（「誰が確認すると言った？」） |
| `minutes_ja` / `minutes_zh` | string | 出力 | 議事録 2 版 |
| `minutes_json` | object | 出力 | §5-3 |
| `open_points` | array | 出力 | 「要確認」箇所（時刻付き） |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工（蘇州）の会議記録担当です。日本語と中国語が混在した会議の文字起こしとホワイトボードの文字から、議事録を作ります。
守るルール：
- 決定事項・ToDo・未決事項は、文字起こしに根拠（時刻 HH:MM か話者）があるものだけ。各項目に根拠時刻を付ける。
- 担当者・期限は発言に無ければ「要確認」。推測で埋めない。期限は会議日 {{meeting_date}} 基準で「9/12」のように絶対日付にし、曖昧なら原文を括弧で併記する。
- 管理番号・数値・条件（Vc 20／f 0.06、n=125 等）は原文どおり。丸めない。
- 「検討する」「後で決める」は決定ではなく未決事項。
- 次回論点は未決事項と ToDo の期限から 4〜6 件。会議に出ていないテーマを足さない。
- 個人の処遇・残業超過者の氏名・給与・評価は書かない。「人事と協議」に丸め、必要なら「※記録対象外の議題あり」と注記。
- 出席者は「姓（部署）」で書く。
- 日本語版と中国語版は同じ項目数・同じ順序。用語は {{glossary}} の対訳を使う。
- 追加質問 {{question}} があるときは、該当発言を時刻付きで引用して、質問の言語で答える（日本語なら日本語、中国語なら中国語）。
出力：JSON（指定スキーマ）→ 区切り線 → 日本語版 Markdown → 区切り線 → 中国語版 Markdown。
```

### 5-4. Few-shot
不要。決定／未決の区別は System のルール（「検討する」は未決）で足りる。実会議の文字起こしを few-shot に入れると個人情報の持ち込みになる（`PC-10`）

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | 決定事項・ToDo の根拠時刻が実際の発言と一致 ≥ 90% | 評価セット 10 会議を人手採点 |
| 網羅 | 人手議事録にある決定・ToDo の漏れ ≤ 1 件／会議 | 人手議事録との突合 |
| 担当・期限 | 誤った担当・期限 0（不明は「要確認」） | 人手 |
| 2 版一致 | ja/zh の項目数・順序一致 100% | JSON から自動 |
| 言語 | 追加質問への回答が質問の言語 100% | 自動判定（`PC-07`） |
| 形式 | JSON スキーマ準拠 100% | バリデータ |
| 速度 | p95 < 90 秒（50 分会議、写真 2 枚） | Langfuse（`PC-09`） |
| 安全 | 人事・処遇に関する氏名の混入 0 | 負例セット |

- **評価方法**：リリース前に過去会議 10 件（匿名化）を人手採点。運用後は記録者が「要確認」の件数と修正箇所を Langfuse に記録し月次で確認

## 8. 別出しが必要なもの
- `PC-03`：録音 → 文字起こし（`sense-voice-small` か自前 FunASR）。**音声を外に出さない**なら FunASR を GPU で自前運用
- `PC-05`：議事録の Outline 保存（`http-request`）と前回議事録 ToDo の取得
- `PC-13`：Markdown → A4 1 枚 docx（2 版）
- `PC-14`：配布メール／WeCom 投稿（文面は Dify が作り、送信は人。自動送信は第 2 段階）
- **無くても動く範囲**：txt をアップロード → 2 版 Markdown まで。録音・写真・Outline・docx は段階導入

## 9. Outline Wiki との関係
- **読む**：「会議録 › 生産会議」の前回議事録（ToDo の継続確認）。用語対訳は「用語集」（`PC-06`）
- **書く**：ドラフトを「会議録 › 生産会議 › YYYY-MM-DD（ドラフト）」に保存。**議長の承認後に人が「確定」へ**（タイトルの（ドラフト）を外す）。Outline のコメント機能で出席者の訂正を受ける
- 会議録コレクションの閲覧権限は出席者の部署に限定（`PC-02`）。人事系の会議は本サービスの対象外にする

## 10. 未確定・リスク
- **STT の配置**：Dify 内で音声を扱うか、`PC-03` で先に文字起こしするか。推奨：`PC-03` 先行（Workflow を音声形式に依存させない。0.6.0 での音声ノードの扱いが未確定）
- **話者分離**：STT に話者分離が無い場合、担当者の特定精度が落ちる。推奨：会議冒頭に出席者名を読み上げる運用と、ホワイトボードに担当を書く習慣を併用
- **議事録の法的位置づけ**：AI ドラフトを正式記録にするか。推奨：議長承認を経た版だけを正式記録とし、Outline の履歴で判別
- **配布の自動化**：`PC-14` で自動送信すると誤配布リスク。推奨：第 1 段階は文面生成のみ
