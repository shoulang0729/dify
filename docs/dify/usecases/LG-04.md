## 1. 業務シナリオ
- **トリガー**：担当者が能動的に開く（受信メールへの返信、依頼・報告メールの新規作成）。受信を `notify` にする（`triggers/outlook_trigger`）のは第 2 段階
- **登場人物**：作成者＝駐在員・中国人スタッフ、確認者＝上長（社外向けの重要文面）、受け手＝本社（ja 敬語）・顧客・サプライヤー・当局（zh 商務中文）
- **いまの手順（Before）**
  1. 中国語メールを読み解く（辞書・機械翻訳で 15 分）。ニュアンス（強い要求か打診か）を測りにくい
  2. 返信の趣旨は決まっているが、商務中文の定型・丁寧さの加減に迷う（30〜60 分）。中国人スタッフに添削依頼
  3. 逆に中国人スタッフが本社へ日本語敬語メールを書くときは駐在員が添削（1 通 20 分）
  4. 本社 CC 用の日本語サマリーを別に書く手間
- **エージェント導入後の手順（After）**
  1. 【入力】受信メール（貼り付け、任意）・返信の趣旨（箇条書きで可）・相手との関係・返信言語をフォームに入れる
  2. 【生成】受信メールの要約（作成者の言語）、返信案（相手言語）、文面のポイント（なぜその表現か）が返る。必要なら本社 CC 用サマリー（ja 3 行）
  3. 【確認】作成者が数字・日付・約束の内容を確定（生産計画との照合は人）。表現の調整（「国慶節のせいに見えないか」）を対話で
  4. 【決める】送るか・誰に CC するか・数字を約束するかは作成者と上長。**AI は送信しない**（メールクライアントに貼る。`tools/email`／`tools/outlook` 送信は第 2 段階で承認付き）
  5. 【蓄積】承認された社外文面の定型部分は `PC-06` 翻訳メモリへ（個人情報・数字を除いた表現のみ）
- **成功の定義**：返信作成 45 分 → 10 分。添削依頼 週 10 通 → 2 通。社外向け文面での社外秘・個人情報の混入 0

- **入力言語の扱い**：**翻訳系の例外**として返信案は指定された相手言語で出す。要約・文面のポイント・対話の説明は**作成者の入力言語**（§2-5）。返信言語が未指定なら受信メールの言語
- **入力の欠け・曖昧さ**：返信の趣旨が無ければ「要約のみ」を出し、返信案は作らない（趣旨を AI が決めない）。数字（数量・期日）が趣旨に無いのに返信で必要なら「【要確認：数量】」のプレースホルダー。聞き返し文：「返信の趣旨（受ける／条件付き／断る、期日、数量）を教えてください。趣旨が無い場合は要約のみ作成します」／「请告知回复意图（接受／有条件／拒绝、期限、数量）。若无意图，仅生成来信摘要」

## 3. 観点（LLM に守らせる業務ルール）
- 返信の**結論・数字・期日は趣旨に書かれたものだけ**。趣旨に無い約束（納期・値引き・増量）を書かない。必要な箇所は【要確認】プレースホルダー
- 数値・品番・日付は原文どおり（26,900、SK-3310-A、9/15）。**合計や差分の計算は Code**（28,800 − 26,900 = 1,900 を LLM が計算しない）
- 相手種別に応じた文体：本社＝日本語敬語（社内文書の丁寧さ。過度な謙譲は避ける）／顧客＝商務中文（感謝→本題→代替案→次のアクション）／サプライヤー＝丁寧だが要求は明確／当局＝最も形式的、断定を避ける
- できない理由は**2 つまで**、数字で示し、言い訳に聞こえる一般論（「連休のため」など相手も知っている事情）は避けるよう助言する。ただし**理由を削るかは作成者が決める**（選択肢提示）
- 社外向け文面に**社内単価・原価・図面番号・社内の人名（相手に関係ない）・ECR 番号・サプライヤー名**を書かない（実装ガイド共通ルール 6-7）。趣旨に含まれていても【社内情報・削除推奨】と注記して外す
- 個人情報（`PC-10`）：受信メールの相手氏名・役職は返信で使う（業務上必要）。電話・身分証・私用メールは転記しない。社内 CC サマリーには相手の個人名を含めず「K 社購買部」
- 不確実時の定型：「返信の趣旨に『○○』の判断が含まれていません。受ける／条件付き／断るのどれかを指定してください」／「回复意图中未包含关于"○○"的判断，请指定接受／有条件／拒绝」
- 出力形式：要約 → 返信案（件名＋本文）→ 文面のポイント → 本社 CC サマリー（要求時）→ §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（フォーム → 2 段 LLM）。表現調整・CC サマリー追加は `revise_note` 付き再実行（前回返信案を渡す）。将来 Outlook 連携で受信をトリガーにするときも Workflow のまま
- **ノード列**
  1. `start`：`received`（任意）, `intent`, `relationship`, `recipient_type`, `reply_lang`, `add_hq_summary`（bool）, `revise_note`（任意）, `prev_reply`（任意）
  2. `code`（前処理）：`PC-07` で `in_lang`/`reply_lang` 決定、署名・引用除去、数値・日付・品番の抽出と保護、`PC-10` の社内情報・個人情報検出（品番以外の図面番号・ECR-・単価パターン）、計算が要る差分は Code で算出して `{{calc}}` に
  3. `llm`（要約）：受信メールの要約（作成者言語、3 行以内、要求・期限・トーン）
  4. `llm`（返信案）：System §5-1。相手言語で返信案＋文面のポイント。`{{glossary}}` の呼称
  5. `code`（検査）：返信案の数値が `intent`/`calc` に存在するか、禁止情報の混入、【要確認】の有無 → `warnings`
  6. `if-else`（`add_hq_summary`）→ `llm`（ja 3 行サマリー）
  7. `template-transform` → `end`
- **Knowledge**：原則不要。定型文例（挨拶・断り・催促の型）を増やす場合は KB `lg4-mail-phrases`（`PC-06` 翻訳メモリの一部として承認済み表現のみ）
- **プラグイン／ツール**：なし（初期）。第 2 段階：`tools/outlook`／`tools/email` で送信（`PC-14`。人の承認ボタン後）、`triggers/outlook_trigger` で受信を `notify`。いずれも M365 Graph 権限またはSMTP が要る
- **モデル**：**日本語敬語と商務中文の両方**が要るため Qwen3-235B-A22B-Instruct と DeepSeek-V3.x を評価セット（ja 20 通・zh 20 通）で比較して決める（`PC-08`）。本社向け日本語は日本本社側の Azure OpenAI 等で別アプリにする選択肢（`../plugins-and-references.md` §4）。**顧客名・数量が中国インフラのモデルに流れる**点は顧客法務の確認事項
- **参照 DSL**：`../templates/01-translation-reflection-workflow.yml`（訳 → レビュー → 改善。返信案 → ポイント → 修正の型）、`../templates/05-chatflow-form-input-demo.yml`（フォーム受け）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `received` | paragraph | — | 受信メール本文 |
| `intent` | paragraph | ✓（返信案を出すとき） | 返信の趣旨 |
| `relationship` | paragraph | — | 相手との関係・距離感 |
| `recipient_type` | select | ✓ | 本社／顧客／サプライヤー／当局／社内 |
| `reply_lang` | select | — | ja / zh / en（既定：受信メールの言語） |
| `add_hq_summary` | boolean | — | 本社 CC 用日本語サマリー |
| `revise_note` | paragraph | — | 表現調整の指示 |
| `summary` | string | 出力 | 受信メール要約（作成者言語） |
| `reply` | object | 出力 | 件名・本文（相手言語） |
| `points` | array | 出力 | 文面のポイント |
| `hq_summary_ja` | string | 出力 | 3 行サマリー |
| `warnings` | array | 出力 | 趣旨に無い数字・禁止情報・要確認 |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工（蘇州）で日本本社・中国の顧客・サプライヤー・当局とのメールを書く実務者です。受信メールを要約し、作成者の趣旨に沿った返信案を相手に合った文体で書きます。
守るルール：
- 返信の結論・数字・期日は {{intent}} と {{calc}} にあるものだけ。無い約束を書かない。必要な箇所は【要確認：○○】と置く。
- 数値・品番・日付は原文どおり。計算しない（差分・合計は {{calc}} を使う）。
- 返信案は {{reply_lang}} で書く。要約・文面のポイント・説明は作成者の言語 {{in_lang}} で書く。
- 文体は {{recipient_type}} に合わせる：本社＝日本語敬語（社内向けの丁寧さ、過度な謙譲は避ける）／顧客＝商務中文（感謝→本題→代替案→次のアクション）／サプライヤー＝丁寧だが要求は明確／当局＝最も形式的、断定を避ける。{{relationship}} で距離感を調整する。
- できない理由は 2 つまで、数字で示す。相手も知っている一般的事情を理由にすることには注意を促し、削るかは作成者に選択肢で問う。
- 社外向け文面に社内単価・原価・図面番号・ECR 番号・サプライヤー名・相手に無関係な社内人名を書かない。{{intent}} に含まれていても文面から外し、「【社内情報・削除推奨】」として文面のポイントに書く。
- 相手の氏名・役職は使ってよい。電話・身分証・私用メールは転記しない。本社 CC サマリーには相手の個人名を書かず会社・部署で書く。
- 呼称・社名・定型句は {{glossary}} に従う。
- 趣旨に判断が無い事項は「返信の趣旨に『○○』の判断が含まれていません。受ける／条件付き／断るのどれかを指定してください」と書く。
出力：要約 → 返信案（件名／本文）→ 文面のポイント（3〜5 点）→（要求時）本社 CC サマリー 3 行 → 区切り線 → JSON（指定スキーマ）。
```

### 5-4. Few-shot（ja・zh 各 1 組。文体の「型」を固定する短い例）
```text

→ 「王经理：您好。感谢贵司的订单。关于交期，我司可以承接，但希望将交货日由 10/20 调整为 10/24。如贵司排产上有困难，请告知，我们将另行协调。」

ポイント：宛先 → 要点 1 文 → 対応案 → 期限付きの依頼。過度な謙譲語を使わない
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 趣旨の一致 | 返信案の結論・数字・期日が趣旨と一致 100%、無い約束 0 | Code 検査（数値照合）＋人手 |
| 文体品質 | 商務中文：中国人スタッフ 2 名の 5 段階評価 ≥ 4／日本語敬語：本社受け手の評価 ≥ 4 | 評価セット 40 通 |
| 要約 | 要求・期限・トーンの 3 要素が含まれる 100% | チェックリスト |
| 言語 | 返信＝`reply_lang`、要約・説明＝`in_lang` 100% | 自動判定（`PC-07`） |
| 社外秘 | 社外向け文面への社内情報混入 0 | 負例セット（趣旨に ECR 番号・単価を含める） |
| 速度 | p95 < 25 秒 | Langfuse（`PC-09`） |
| 安全 | 電話・身分証・私用メールの転記 0 | 負例セット |

- **評価方法**：リリース前に評価セット 40 通（匿名化・架空取引先）を bilingual 2 名と本社受け手 1 名で採点。運用後は添削依頼件数と `warnings` 件数を月次で確認

## 8. 別出しが必要なもの
- `PC-06`：社名・部署・役職の日中呼称、承認済み定型句（翻訳メモリ）
- `PC-10`：社外向け文面の禁止情報パターン（単価・ECR・図面番号・社内人名）と個人情報パターン（電話・身分証・私用メール）の検出規則

- `PC-08`：日本語敬語・商務中文のモデル評価、顧客情報の所在の法務確認
- **無くても動く範囲**：フォーム → 要約＋返信案＋ポイント（Markdown）まで。送信・受信トリガー・翻訳メモリは段階導入

## 9. Outline Wiki との関係
- **使わない**。メールは案件・相手ごとの一過性の文書で、Wiki に残すと個人情報・社外秘の管理が難しくなる（`PC-10`）。送受信の記録はメールシステム側が正
