## 1. 業務シナリオ
- **トリガー**：期限つき案件が振られる（設備更新・修繕・購買・出張の申請が必要になったとき。③業務フィードでは `due`：「金額区分が変わり差し戻し」など）
- **登場人物**：申請者＝課長、確認者＝部長・工場長（承認ルート A/B）、本社設備部・経営会議（ルート B）、財務課（予算区分・円換算）
- **いまの手順（Before）**
  1. 前回の稟議書を探して書式を思い出す（1 時間）。規程の金額基準を人に聞く
  2. 目的・効果・比較・スケジュールを書く（半日）。効果の投資回収を Excel で計算
  3. 提出 → 「見積添付なし」「予算区分未記入」で差し戻し（1〜3 日のロス）。金額区分が変わるとルートが変わり再提出
  4. ルート B は本社向け日本語版が要り、通訳に依頼（1〜2 日）
- **エージェント導入後の手順（After）**
  1. 【入力】件名・金額・目的・見積の有無をフォームに入れる（中国語で可）
  2. 【生成】社内書式 5 章のドラフト、**承認ルート判定（規程の金額基準に基づく機械判定）**、記載漏れ・添付漏れの一覧、効果欄の助言が返る。ルート B なら日本語版と円換算（社内レート・日付付き）
  3. 【確認】申請者が漏れを埋め、据付時の生産影響などを対話で追記。数値（投資回収年数）は Code 計算値で、根拠式が表示される
  4. 【決める】申請の可否・提出は申請者と上長。**AI は BPMS へ登録しない**（BPMS 取込形式のファイルを出すまで。`docs/handoff/2026-09-06-pm-decisions.md` §2 の趣旨）
  5. 【保存】Outline「稟議 › ドラフト › <申請者>」に保存（申請者と上長だけ閲覧）。提出は BPMS または紙
- **成功の定義**：初回提出での差し戻し率 50% → 10% 以下。作成時間 1 日 → 2 時間。ルート誤りによる再提出 0

- **入力言語の扱い**：ja / zh どちらでも受け、**ドラフトは入力言語で**（§2-5）。ルート B のときだけ本社向け日本語版を追加生成（サービスの定義）。対話は入力言語
- **入力の欠け・曖昧さ**：件名・金額・目的が無いと生成しない。見積が無いのは「添付漏れ」として指摘（生成は止めない）。金額の通貨が不明なら聞き返す。聞き返し文：「金額の通貨（RMB／JPY／USD）を指定してください。承認ルートは通貨換算後の金額で判定します」／「请指定金额币种（RMB／JPY／USD），审批路径按换算后金额判定」

## 3. 観点（LLM に守らせる業務ルール）
- **承認ルートは LLM が判定しない**。Code ノードが規程のルート表（金額基準×種別）で判定した結果を、LLM は「規程 §x に基づき ルート B」と**引用して書くだけ**。基準の境界（ちょうど 1,000,000）は Code の定義に従う
- **計算は Code**：円換算（レート・日付付き）、投資回収年数（投資額 ÷ 年間効果）、見積比較の差率。LLM は計算結果と根拠式を転記し、自分で計算しない
- 効果の数値（年間損失・エネルギー削減）は**入力・見積に根拠があるものだけ**。無いものは「効果：要記入（根拠資料を添付）」。「投資回収が長い」等の助言はしてよいが、数値を作って埋めない
- 記載漏れ・添付漏れは書式の必須項目リスト（Code のチェック）に基づき列挙。LLM は各項目の「なぜ要るか」を 1 行で補う
- 差し戻し理由のドラフトは上長の依頼があるときだけ。人格・能力に触れず、欠けている事実だけを書く
- 個人情報・秘密（`PC-10`）：見積の担当者連絡先を書かない。サプライヤー単価は稟議書内では必要なので書くが、Outline の閲覧を申請者・承認者に限定（`PC-02`）
- 不確実時の定型：「承認ルートを判定できません（種別または金額が規程の表に該当しません）。財務課に確認してください」／「无法判定审批路径（类别或金额不在规程表内），请与财务科确认」
- 出力形式：Markdown（5 章＋承認ルート判定＋漏れ一覧）＋ §5-3 JSON（BPMS 取込・docx 化に使う）

## 4. Dify 構成
- **アプリ種別**：**Workflow**（フォーム → 1 回実行）。承認フローそのものは BPMS に置く（Dify 内の `human-input` で承認までやる案は §10）
- **ノード列**
  1. `start`：`title`, `type`（設備投資／修繕／購買／出張）, `amount`, `currency`, `purpose`, `quotes_note`, `quote_files`（任意）, `lang`（任意）, `revise_note`（任意）
  2. `code`（正規化・判定）：金額数値化 → 通貨換算（`fx_rate`,`fx_date` を環境変数または `http-request` で取得）→ ルート表（JSON 定数）で `route` 判定 → 必須項目チェックリスト → 投資回収計算（効果値が入力にあれば）
  3. `iteration`（quote_files）→ `document-extractor` → `llm`（見積 JSON：金額・納期・範囲）※任意
  4. `knowledge-retrieval`：KB `dc5-approval-rules`（規程本文、`type` フィルタ）＋ `dc5-approval-examples`（記載例）
  5. `llm`（ドラフト）：System §5-1。5 章＋漏れ一覧＋助言。入力言語で
  6. `if-else`（`route == B`）→ `llm`（本社向け日本語版＋送付状）
  7. `template-transform` → `end`：`draft_md`, `draft_ja_md`（B のみ）, `draft_json`, `missing[]`, `route`
- **Knowledge**：`dc5-approval-rules`（稟議規程・書式説明。章単位、メタデータ `type`/`rev`）、`dc5-approval-examples`（匿名化した過去稟議の章。メタデータ `type`/`chapter`）。いずれも Outline から `PC-05` で同期。埋め込み `bge-m3`
- **プラグイン／ツール**：なし。為替は `http-request`（社内レート API、`PC-04`）か固定値。BPMS 連携は `PC-04`（第 2 段階）。`human-input` ノード（1.15 で選択・添付対応）は承認を Dify 内で回す場合のみ
- **モデル**：Qwen3-235B-A22B-Instruct（中国語稟議）。本社向け日本語版は稟議文体が要るため DeepSeek-V3.x と比較評価（`PC-08`）。ルート判定・計算に LLM を使わないので小型モデルでも精度は落ちにくい
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`（フォーム受け）、dsl-skill `examples/08-human-approval.yml`（human-input の構成。URL 参照のみ、`../templates/README.md`）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `title` / `type` | string / select | ✓ | 件名・種別 |
| `amount` / `currency` | string / select | ✓ | 金額・通貨 |
| `purpose` | paragraph | ✓ | 目的・背景 |
| `quotes_note` | paragraph | — | 見積の有無・概要 |
| `quote_files` | file-list | — | 見積書 |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工（蘇州）の稟議・申請書作成を支援するアシスタントです。申請者の入力から社内書式のドラフトを書き、記載漏れ・添付漏れを列挙します。
守るルール：
- 承認ルートは {{route_json}}（規程に基づく機械判定）を引用して書く。自分で判定・変更しない。判定不能なら「財務課に確認」と書く。
- 金額の換算・投資回収年数・見積差率は {{calc_json}} の値と根拠式をそのまま書く。自分で計算しない。
- 効果の数値は {{purpose}}・{{effect_note}}・見積 {{quotes_json}} に根拠があるものだけ。無い欄は「要記入（根拠資料を添付）」。
- 記載漏れ・添付漏れは {{missing_json}} を列挙し、各項目に「なぜ必要か」を 1 行添える。リストに無い漏れを追加してよいが、その場合は「参考」と付ける。
- 助言（投資回収が長い等）は「推奨」と明示し、申請者の判断に委ねる文にする。
- 見積担当者の連絡先・個人名は書かない。
- ドラフトは申請者の入力言語で書く（日本語なら日本語、中国語なら中国語）。{{route}} が B のときは追加で本社向け日本語版と送付状を書く。
- 差し戻し理由の下書きは求められたときだけ。欠けている事実のみを書き、人物評価をしない。
出力：JSON（指定スキーマ）→ 区切り線 → ドラフト Markdown（1 件名／2 目的・背景／3 金額・比較／4 効果／5 スケジュール／承認ルート判定／記載漏れ・添付漏れ）。
```

## 8. 別出しが必要なもの
- **承認ルート表の構造化**（規程 → JSON 定数）：財務課が正を持ち、改定時に Code の定数を更新する運用（`PC-05` の Outline に正本、Code は写し）
- `PC-04`：社内為替レート API、BPMS 取込形式（CSV/JSON）の定義。BPMS への登録は第 2 段階
- `PC-01`：差し戻し・期限を `due` としてフィードへ（BPMS のステータス変更を Webhook で受ける）
- `PC-13`：JSON → 社内稟議書式（docx/xlsx）、本社様式
- **無くても動く範囲**：フォーム → Markdown ドラフト＋ルート判定（Code 定数）＋漏れ一覧まで。KB・為替 API・BPMS は段階導入

## 9. Outline Wiki との関係
- **読む**：「稟議 › 規程」「稟議 › 承認ルート表」「稟議 › 書式・必須項目」「稟議 › 記載例（匿名化）」
- **書く**：ドラフトを「稟議 › ドラフト › <申請者>」に保存。**閲覧は申請者と承認ルート上の役職に限定**（`PC-02`）。提出済の稟議は BPMS が正で、Outline には残さない（記載例として使うものだけ匿名化して「記載例」へ移す）
- 規程の改定は Outline 側で行い、`PC-05` の同期と Code 定数の更新をセットにする（reviewer のチェック項目）
