## 1. 業務シナリオ
- **トリガー**：担当者が能動的に開く（相手方から契約書案文を受領したとき）。③業務フィードの `due`/`routine`/`notify` のいずれにも現状は連動しない
- **登場人物**：実施者＝契約実務の担当者（製造：管理部 財務・法務 駐在員／金融：審査部／IT：営業部）、確認者＝本社法務（製造・IT）または営業第一部（金融、審査部意見の宛先）、外部＝契約相手方（サプライヤー・顧客・借り手の代理人〈弁護士事務所〉など）
- **いまの手順（Before）**
  1. 相手方案文を読み、自社標準条項と条ごとに突き合わせる（半日〜1 日）。欠落条項（相手方案文に**書かれていないこと**）は読み流しやすい
  2. リスクの重さを個人の経験で判断し、修正文案を都度書く
  3. 関係部門（法務・営業）への報告文書を作成する（半日）
- **エージェント導入後の手順（After）**
  1. 【入力】相手方から届いた契約書ファイル（PDF・Word・スキャン）をアップロードする
  2. 【生成】自社標準条項（Knowledge Retrieval）と条文単位で突き合わせ、逸脱・欠落条項の一覧、リスク区分（要交渉／要確認／許容）、修正文案が返る
  3. 【確認】担当者が区分と修正文案を確認し、対話で「この数字の根拠」「他社／他案件とはどう扱ったか」を問える
  4. 【決める】**リスク区分の最終確定・修正文案の採否・締結の可否は本社法務（またはそれに準じるレビュー）が行う。AI は判断しない**
  5. 【伝える】要交渉事項を整理し、関係部門への報告文面（レビュー依頼メール・審査部意見など）を作る
- **成功の定義**：レビュー時間の短縮（半日〜1 日 → 1〜2 時間）。欠落条項の見落とし 0（法務・審査部の指摘との突合）。関係部門への報告作成が定型化される

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|

| 契約用語対訳 | 用語集 | ja／zh／en | 100〜200 語 | 需方／需要者、抵押／担保 | `PC-06` | context に注入 |

- **入力言語の扱い**：相手方案文は zh／ja のどちらでも受け付ける。**IT のように基本契約書（ja）と付属覚書（zh）が並行する場合は、言語をまたいで条項を突き合わせる**（`SCENARIOS.it.dc11` の再委託条項の食い違いが例）。対話・説明は依頼者の**入力言語**で返す（`CLAUDE.md` §2-5）。地の文は例外なく回答言語で書き、原語のまま出してよいのは条文の引用・文書名・記号（相手方コード・案件番号）だけ
- **入力の欠け・曖昧さ**：契約書ファイルが無ければ生成しない。自社標準条項が KB に無い類型（業種×契約類型の組み合わせが未整備）のときは「標準条項集に該当がありません。法務（審査部）にレビューの要否を確認してください」／「标准条款集中无对应条款，请与法务（审查部）确认是否需要审阅」と定型で返す

## 3. 観点（LLM に守らせる業務ルール）
- **自社の標準条項が正本**。標準条項に無い論点を勝手に作らない（標準に無い条は「※標準条項外・法務確認」と付ける）
- **条文単位で示す**（「全体的に不利です」のような総括で終わらせない）。第何条のどの文かを必ず引く
- **リスク区分は自社で決めた 3 段（要交渉・要確認・許容）に従う**。区分の定義は入力（標準条項集のメタデータ）で与え、LLM が独自の区分を作らない
- **欠落条項も出す**。相手方案文に**書かれていないこと**（標準条項にあるのに相手方案文に対応する条がない）が最大のリスクになるため、「一致」の判定だけでなく「欠落」を明示する
- **締結の可否を判定しない**。「有効です」「問題ありません」と書かない。判断が要る点は依頼者・法務・審査部への確認事項として列挙する（DC-07 と同じ歯止め）
- 相手方コード（T 社・甲社・碧洋銀行のような**顧客に見せてよい記号**）以外の担当者名・連絡先・単価を書かない（`PC-10`）
- 出力形式：`columns`＋`rows` の表（項目／相手方案文／自社標準条項／リスク区分／修正文案）。地の文の言語は依頼者の入力言語（§2）
- **BP（`ζ 社`）・ベンダ名・製品名は一切書かない**（本サービスの実現手段の議論は `../build-or-buy.md` 側の話であり、業務の出力に混ぜない）

## 4. Dify 構成
- **アプリ種別**：**Workflow**（アップロード → 抽出 → 差分 → 3 段 LLM）。対話での追加質問（根拠の深掘り・報告文面の作成）は `question` 付き再実行
- **ノード列**
  1. `start`：`contract_files`（相手方案文、必須）、`industry`（`mfg`/`fin`/`it`）、`contract_type`（select）、`question`（任意）
  2. `iteration`（`contract_files`）→ `document-extractor`／`tools/mineru`（スキャン）→ `code`（条番号で分割）→ `variable-aggregator`
  3. `knowledge-retrieval`（標準条項）：KB `dc11-standard-clauses`、メタデータ `industry = {{industry}}` AND `type = {{contract_type}}`、最新 `rev`
  4. `code`（差分下拵え）：相手方案文の条と自社標準条項を条番号・見出しで対応付け、対応が無い標準条項を「欠落」として検出（`PC-12` の `diff-core`）
  5. `llm`（逸脱・欠落・リスク区分・修正文案）：条ごとに事実として相違点を書き、標準条項のメタデータが持つリスク区分の初期値を踏まえて理由を添える
  6. `question` 時：`knowledge-retrieval`（過去の締結実績）→ `llm`（根拠の説明・報告文面の作成）
  7. `template-transform`（`columns`＋`rows` に整形）→ `end`
- **Knowledge**：`dc11-standard-clauses`（条単位、`industry`/`type`/`clause_no`/`rev`）、`dc11-past-contracts`（任意、匿名化要約、`industry`/`type`/`counterparty_code`/`year`）。KB の公開範囲は業種ごとの法務・審査帯に限定（`PC-02`）。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`
- **プラグイン／ツール**：`tools/mineru`（PDF スキャン抽出）。docx 化は `PC-13`
- **モデル**：Qwen3-235B-A22B-Instruct または DeepSeek-V3.x（法律文の中国語・日本語）。契約内容が中国インフラのモデルに流れるため、DC-07 と同様に顧客法務の確認が前提（`PC-08`）
- **参照 DSL**：`../templates/08-mineru-pdf-parse-demo.yml`（スキャン契約書の抽出）、`../templates/02-long-document-chunk-iteration-translate.yml`（長文の分割 → iteration、条文抽出に流用）、`../templates/04-trilingual-consistency-checker.yml`（言語をまたぐ条項の不一致列挙。IT の基本契約書〈ja〉× 付属覚書〈zh〉に使う）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `contract_files` | file-list | ✓ | 相手方契約書案（複数可。IT は基本契約書＋付属覚書の 2 通） |
| `industry` | select | ✓ | `mfg`/`fin`/`it` |
| `contract_type` | select | ✓ | 契約類型（取引基本契約／品質保証協定／金銭消費貸借契約／担保設定契約／業務委託基本契約 等） |
| `question` | paragraph | — | 追加質問（根拠照会・報告文面の作成依頼） |
| `diff_table` | string | 出力 | 逸脱・欠落条項の表（`columns`＋`rows`） |
| `risk_summary` | object | 出力 | 要交渉／要確認／許容の件数と一覧 |
| `diff_json` | object | 出力 | §5-3 |

## 5. プロンプト
### 5-1. System（差分・リスク区分用）
```text
あなたは契約書の条文単位レビューを支援するアシスタントです。相手方から届いた契約書案を、自社の標準条項（{{context}}）と条ごとに突き合わせ、逸脱している条項と欠落している条項を指摘します。あなたは法律の専門家ではなく、締結の可否は判断しません。
守るルール：
- 条文は {{context}}（標準条項集）を正本とし、相手方案文（{{contract_clauses}}）と条ごとに比較する。標準に対応する条が相手方案文に無いときは「欠落」として明示する。
- リスク区分は {{context}} のメタデータが持つ既定の 3 段（要交渉・要確認・許容）に従う。独自の区分名を作らない。
- 相違点は条ごとに事実で書く（相手方案：…／自社標準：…）。理由を 1 行添える。
- 締結の可否・条項の有効性・準拠法の妥当性を判断しない。「有効」「問題ない」と書かない。確認が必要な点は依頼者・法務・審査部への確認事項として列挙する。
- 相手方は顧客に見せてよい記号（例：T 社・甲社・碧洋銀行）で書く。担当者名・連絡先・単価を書かない。
- 質問・説明は依頼者の入力言語で書く（日本語なら日本語、中国語なら中国語）。基本契約書と付属覚書のように言語が異なる文書をまたいで比較するときも、地の文は依頼者の入力言語で統一する。
- 標準条項集に該当が無い場合は「標準条項集に該当がありません。法務（審査部）にレビューの要否を確認してください」と書く。
- 出力の末尾に必ず「本レビューは実務上の整理であり法的助言ではありません。締結の可否は法務のレビューに従ってください」を付ける（実装ガイド共通ルール 6-10）。
出力：JSON（指定スキーマ）→ 区切り線 → 逸脱・欠落条項の表（条ごと）→ リスク区分の内訳 → 確認事項リスト。
```

### 5-4. Few-shot
不要。条文の文言は標準条項集（KB）から取るため、few-shot に条文を置くと KB の改定と食い違う

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 逸脱検出 | 法務・審査部が指摘した相違点の再現 ≥ 95% | 過去案件（匿名化）で突合 |
| 欠落検出 | 標準条項にあり相手方案文に無い条の見落とし 0 | チェックリスト（標準条項の条番号を全件確認） |
| リスク区分 | 3 段（要交渉・要確認・許容）以外を出さない | 自動（スキーマ検証） |
| 断定禁止 | 締結可否・有効性の断定 0 | 負例セット（「これは有効？」「締結して大丈夫？」） |
| 言語 | 地の文は依頼者の入力言語 100%（言語混在文書でも統一） | 自動判定（`PC-07`）＋人手（IT の日中混在ケース） |
| 安全 | 担当者名・連絡先・単価の露出 0、相手方は記号のみ | 負例セット |
| 速度 | p95 < 150 秒（12 条・3 業種平均） | Langfuse（`PC-09`） |

- **評価方法**：リリース前に各業種の法務／審査担当が過去案件（匿名化）10 件で採点。運用後は指摘件数を案件ごとに記録し、標準条項集の改定に反映

## 8. 別出しが必要なもの
- **業種ごとの標準条項集の整備**（法務・審査部）：類型別・条単位・正本言語＋対訳・改定版管理。Outline に正本、KB は同期（`PC-05`）
- **過去の締結実績の匿名化要約**（法務・審査部、任意）：相手方コード化、条ごとの要点のみ。原契約全文は KB に入れない（`PC-10`）
- `PC-02`：アプリ・KB・Outline コレクションの閲覧を業種ごとの法務・審査帯に限定
- `PC-08`：契約文を扱うモデルの所在（中国インフラ／自前）の法務判断
- **無くても動く範囲**：業種×契約類型 1 組の標準条項集 ＋ アップロード → 逸脱・欠落の表まで。過去実績 KB・報告文面の自動生成は段階導入

## 9. Outline Wiki との関係
- **読む**：「法務／審査 › 標準条項集（業種別・類型別・改定版）」「法務／審査 › 締結実績（匿名化要約）」「用語集（法務）」
- **書く**：レビュー結果を「契約 › レビュー › <業種>/<相手方コード> › v1, v2 …」に保存し、関係部門への報告下書き（レビュー依頼メール・審査部意見）として使う。**閲覧は業種ごとの法務・審査帯のみ**（`PC-02`）。締結版は契約管理システム／紙が正
- 法務・審査部のコメントは Outline のコメント機能で受け、次回レビューの標準条項集改定に反映する運用
