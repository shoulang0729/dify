## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（与信・リスクレビューの前、定期ではなく都度）。③業務フィードでは `due`（次回レビュー期日が近いと促す）
- **登場人物**：審査部の主管・次長（レビュー資料を作る側）、担当セクターの発行体（丙社ほか同セクターの与信先）
- **いまの手順（Before）**：レビュー前に担当者が個別にニュース・開示・外部リサーチを見比べ、前回レビューから何が変わったかを頭の中で整理する。抜け漏れが起きやすく、議論すべき点が絞り込まれないまま会議に入る
- **エージェント導入後の手順（After）**：
  1. セクターと発行体（複数）、観点（原材料コスト・受注動向・規制変更など）、比較対象（前回レビュー）をフォームで設定する
  2. ニュース・開示・外部リサーチが突き合わされ、前回レビューからの変化が論点の形（3〜5 件）で返る
  3. 担当者が論点を確認し、**リスクレビュー資料に反映するかどうかを判断する**（AI は与信枠の変更を提案しない）
- **成功の定義**：レビュー前の情報整理にかかる時間が減り、「今回議論すべき点」が会議前に 3〜5 件に絞られている

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| モニタリング設定 | フォーム（セクター・発行体・観点・比較対象） | ja / zh | レビュー前 1 回 | セクター：自動車部品／発行体：丙社ほか5先／観点：原材料コスト・受注動向・規制変更／比較対象：前回リスクレビュー | フォーム（`PC-16`） | 発行体ごとに検索クエリを組み立てる |
| ニュース・開示・外部リサーチ | Web ページ・PDF | zh 主体（一部 ja/en） | セクターごと週次で数件〜十数件 | アルミ・鋼材価格の報道、丙社の直近開示 | 検索ツール（RS-01 と同じ枠組み）、コンプライアンス部の収集結果（`RS-01`） | 発行体ごとの分類、前回レビューとの突合 |

- **入力言語の扱い**：フォーム入力・追い質問は日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）
- **入力の欠け・曖昧さ**：前回のモニタリング結果が Outline に無い（初回）場合は「前回比較なし」と明示し、今回の状況整理のみを返す。発行体が未指定の場合はセクター全体の一般的な傾向のみを返し、個別発行体への言及はしない

## 3. 観点（LLM に守らせる業務ルール）

- **前回との差分を明示する**：新しく判明した事実・変わった数値・解消した論点を区別する。前回と同じ内容をそのまま繰り返さない
- **発行体固有の情報と、セクター共通の情報を分ける**：丙社固有の事実（価格転嫁の遅れ等）と、セクター全体に共通する要因（原材料コスト上昇）を混同しない
- **与信枠の変更を提案しない**：「個別の与信枠変更を要する事実は確認できていません」のように、判断材料の提示にとどめる。「与信枠を見直すべき」とは書かない
- **論点は 3〜5 件に絞る**：優先順位（影響の大きさ・確度）順に並べ、各論点に「次に何を確認するか」を 1 行添える
- **禁止**：確度の低い外部リサーチの推測を確定事実として書く／複数発行体の情報を混同する／数値の出所を明記せずに書く
- **不確実なとき**（入力言語で）：ja「前回のモニタリング結果が見つかりません。今回の状況整理のみお示しします。」／zh「未找到上次的监测结果。仅提供本次的情况梳理。」
- **出力の粒度**：観点ごとの整理（原材料コスト／受注動向／規制変更など）→ 与信枠への影響（判断材料のみ）→ 今回議論すべき点（3〜5 件）

## 4. Dify 構成

- **アプリ種別**：**Workflow**（フォーム入力 → 実行 → 結果）。追い質問は同じ Workflow を `follow_up` 付きで再実行する（Chatflow にしない理由：観点ごとの整理を固定順で出す必要があり、`Code` での並べ替え・件数調整を伴うため）
- **ノード列**：
  1. `Start`（セクター・発行体・観点・比較対象）
  2. `HTTP Request`（`PC-05` から前回のモニタリング結果を取得。無ければ空）
  3. 検索ツールで対象セクター・発行体のニュース・開示を収集（RS-01 と同じツール群を利用。§4 の検索ツール）
  4. `Code`（前回結果との突合・差分抽出・観点ごとの分類）
  5. `LLM`（論点整理。§5 のプロンプト）
  6. `Code`（論点数の検算：3〜5 件か、各論点に次アクションがあるか）
  7. `HTTP Request`（`PC-05` に今回の結果を「セクターモニタリング」コレクションへ下書きとして保存）
  8. `Answer`
- **Knowledge**：使わない（都度の外部情報を Code で突合するため。前回結果は Outline のドキュメントとして持つ）
- **プラグイン／ツール**：`tools/searxng` / `tools/google` / `tools/bing`（RS-01 と同じ。`../plugins-and-references.md` §2）、`Outline API`（`documents.info` で読む、`documents.create`（`publish: false`）で書く。`PC-05` の実現案どおり）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（論点整理）。日本語での議論資料としての読みやすさは評価セットで確認（`PC-08`）
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`、`../templates/04-trilingual-consistency-checker.yml`（前回との突合・差分表示の型）
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `sector` | string | ✓ | セクター名 |
  | `issuers` | string[] | ✓ | 発行体（`data/world/fin/clients.csv` の記号） |
  | `viewpoints` | string[] | ✓ | 観点（原材料コスト・受注動向・規制変更 等） |
  | `compare_to` | string | — | 比較対象（既定：前回リスクレビュー） |
  | `follow_up` | string | — | 追い質問 |
  | 出力 `points` | array[object] | ✓ | 議論すべき点（3〜5 件・根拠・次アクション） |
  | 出力 `outline_doc_url` | string | — | 今回の結果を保存した Outline ドキュメント |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 審査部のセクターモニタリング担当です。
指定されたセクターと発行体について、収集されたニュース・開示・外部リサーチと、前回のモニタリング結果（{{prev_result}}）を突き合わせ、
前回から何が変わったかを観点ごとに整理します。
守ること：
1. 発行体固有の情報とセクター共通の情報を分けて書く。
2. 与信枠の変更や取引継続の可否を提案しない。判断材料（事実）の提示にとどめる。
3. 議論すべき点は3〜5件に絞り、優先順位順に並べ、各点に「次に何を確認するか」を1行添える。
4. 数値には出所（自社の直近開示／外部リサーチ／公開情報）を明記する。
5. 前回のモニタリング結果が無いときは「前回のモニタリング結果が見つかりません。今回の状況整理のみお示しします。」と書く。
6. 言語：担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：観点ごとの整理 → 与信枠への影響（判断材料のみ）→ 今回議論すべき点（3〜5件）の順。
```

### 5-2. User テンプレート

```text
セクター={{sector}}／発行体={{issuers}}／観点={{viewpoints}}／比較対象={{compare_to}}
前回のモニタリング結果（Outline から取得。転記のみ）：{{prev_result}}
収集した記事・開示（転記のみ）：{{articles_json}}
追加の指示（無ければ空）：{{follow_up}}
```

### 5-3. 出力フォーマット

```json
{
  "sector": "自動車部品", "compared_to": "2026 年前四半期リスクレビュー",
  "viewpoints": [
    { "name": "原材料コスト", "finding": "アルミ・鋼材価格が前四半期比+6%", "source": "外部リサーチ", "affects": ["丙社ほかセクター全体"] }
  ],
  "credit_impact": "個別の与信枠変更を要する事実は確認できていません。",
  "points": [ { "rank": 1, "text": "原材料コスト上昇の価格転嫁進捗（丙社への確認要）", "next_action": "次回訪問時にヒアリング" } ],
  "outline_doc_url": null
}
```

### 5-4. Few-shot

**不要**。書式は System と JSON スキーマで固定する。セクター・発行体ごとに事実が異なるため few-shot は誤誘導になりうる。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 差分の正確性 | 前回結果との差分が実際の変化と一致 ≥ 90% | 評価セット（前回・今回のペア）15 組を人手採点 |
| 論点数 | 3〜5 件、各件に次アクションあり 100% | スキーマバリデータ |
| 越境なし | 与信枠変更・取引継続可否の断定表現 0 | 禁止語 + LLM-as-judge |
| 情報の分離 | 発行体固有とセクター共通の混同 0 | 人手（負例セット） |
| 言語 | 入力言語で返答 100% | 自動判定（`PC-07`） |
| 拒否 | 前回結果が無いとき定型文 100% | 自動 |
| 速度 | p95 < 30 秒 | Langfuse |

- **評価方法**：リリース前に審査部で 15 組（前回・今回セット）を人手採点。月次で Langfuse のスコア確認

## 8. 別出しが必要なもの

- `PC-05`：「セクターモニタリング」コレクションに前回結果を Markdown で保存し、次回はここを読んで差分を取る。承認フローは審査部内のレビュー担当が確認後に確定版とする
- `PC-13`：リスクレビュー資料への添付用ファイル（任意）
- RS-01 の収集結果（発行体単位のネガティブ情報）を突き合わせデータの一部として使う（台本参照）。RS-01 の出力形式と合わせる
- **無くても動く範囲**：Outline 連携が無くても「今回の状況整理」のみは動く（前回比較ができないだけ）

## 9. Outline Wiki との関係

- **読む**：「セクターモニタリング」コレクションの前回結果（`PC-05`）
- **書く**：今回の結果を同コレクションへドラフト（`publish: false`）として保存。確定は審査部内のレビュー担当が行う
- 発行体の個別与信情報（財務データそのもの）は書かない。論点整理のみを残す

## 10. 未確定・リスク

- **実現性を ○ とした理由**：フォーム入力・LLM 整理・Outline 読み書きは標準機能で足りるが、(1) 前回結果を Outline のどの粒度で残すか（セクター単位かセクター×期か）が未確定、(2) 外部リサーチの取得経路が RS-01 と共用かどうかが未確定、の 2 点で ◎ にしていない
- **RS-01 との関係**：発行体ごとのネガティブ情報監視は RS-01、セクター横断の論点整理は RS-02。両方が同じ検索基盤を使うため、検索クエリの重複実行を避ける仕組み（キャッシュ・共有）は次の設計で詰める
- **比較対象の粒度**：「前回リスクレビュー」が四半期単位か随時かは審査部の運用による。Outline のドキュメント命名規則（セクター＋期）を決める必要がある — PM／審査部確認
