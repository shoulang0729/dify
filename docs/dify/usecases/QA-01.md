## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：顧客から不良指摘が入り、**期限つき案件**が振られる（③業務フィード `FEED.items` の `qa1` は `due`。K 社協定：重大は 48 時間で D1〜D3、10 日で完全版）。`PC-04` で QMS の不具合票発行を Webhook 受信すればフィードに自動で乗る
- **登場人物**：品質保証課 係長（起案者・zh）、生産技術・製造課（原因調査の協力者）、外注（塗装 S 社）、確認者（品質保証課長）、外部：顧客 K 社品質部（提出先）、日本本社品質保証部（写し）
- **いまの手順（Before）**：
  1. 不良報告・検査記録・条件記録を別々のファイルから集め、Excel の 8D 様式に手で転記（2 時間）
  2. 「前にも同じことがあったか」を先輩の記憶と QMS 検索で探す（1〜2 時間、見つからないことも多い）
  3. なぜなぜを会議で議論し、D4 を書く。**基準外の条件（脱脂液濃度 3.8%）を記録から見落とす**ことがある
  4. 中国語で書いた 8D を日本語に訳して本社へ（半日）。用語（ブツ／颗粒）が揺れる
- **エージェント導入後の手順（After）**：
  1. 担当者が不良報告・検査記録・条件記録をアップロードする（ja/zh どちらでも）
  2. エージェントが条件記録を**基準値と機械的に照合**（Code）し、不具合台帳から類似 NC を引き、原因候補（なぜなぜ）と D1〜D5 ドラフトを返す。根拠（NC 番号・記録の行・基準値の出典）を必ず付ける
  3. **担当者が原因候補の妥当性と D3 暫定処置の実施状況を確認し、D4 の「最有力原因」を決める**（AI は候補提示まで）
  4. 「D5 は妥当？」で抜けの指摘を受け、D6/D7 の提案を取り込む。「ja/zh で出力」で docx 2 通（`PC-13`）を受け取り、係長・主任が確認欄にチェック → **提出は人**
- **成功の定義**：D1〜D3 の初版を 48 時間 → 半日、8D 完全版の作成工数を 2 日 → 半日。**基準外条件の見落とし 0**、ja/zh の数値・部品番号の不一致 0

## 3. 観点（LLM に守らせる業務ルール）
- **根拠を引く**：類似不具合は NC 番号・年・ライン、条件の基準外は「記録の行・値・基準値の出典（CP 番号）」を書く
- **基準外判定は Code の結果のみ**：LLM が数値を読み直して判定しない。Code が出した `out_of_spec` の行だけを D4 の事実とする
- **原因は「候補」**：D4 は「最有力／寄与要因／否定」の 3 区分で候補を並べ、**確定は担当者**。証拠の無い原因を「原因」と書かない
- **なぜなぜは記録で止める**：根本原因（なぜ濃度が下がったか）が記録から分からなければ「D4 未確定：追加調査（補給装置の点検）」と明示し、D5 に調査タスクを入れる
- **顧客要求を反映**：D5〜D7 の抜け（帳票化・水平展開・効果確認基準）は `kb-customer-requirements`（顧客の品質協定）を引いて指摘する
- **数値を作らない**：不良率・数量・日付は入力にある値のみ。効果確認基準（0.2% 以下）は過去 8D か協定に根拠があるものを提案し、無ければ「案（要合意）」
- **登録・提出しない**：8D は「ドラフト」。QMS 登録・顧客提出は担当者。「提出しました」と書かない
- **PIPL／社外秘**：D1 チームは氏名・部署・役職まで（連絡先は書かない）。顧客名は入力どおり、他顧客の不具合を引くときは顧客名を伏せる
- **不確実なとき**（入力言語で）：「類似する不具合記録が見つかりません。現象・部品番号・工程を確認してください。D1〜D3 は入力情報だけで作成できます」
- **出力の粒度**：§5-3 の JSON（D1〜D8 各節）→ `PC-13` で docx。チャットには D 節見出し＋箇条書きで要約

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`、複数ファイル添付）。初回はファイル解析、以後「D5 は妥当？」「ja/zh で出力」の追い指示が続くため。会話変数に `eightd_json` を保持
- **ノード列**：
  1. Start（`sys.files`：xlsx/csv/pdf 複数、`sys.query`）
  2. IF/ELSE（ファイルあり＝初回解析／なし＝追い指示）
  3. **初回解析**：Iteration[ ファイル種別で分岐：Document Extractor（xlsx/csv）／Tool `tools/mineru`（PDF） ] → Code（列名正規化・**基準値照合** `out_of_spec[]`・部品番号・ロット抽出）→ Knowledge Retrieval ×2 並列（`kb-nc-records`：`part_no`/`defect_type`/`process` フィルタ top-k 6／`kb-8d-archive` top-k 3）→ Knowledge Retrieval（`kb-customer-requirements`：`customer` フィルタ）→ LLM（Qwen3-235B：類似照合＋なぜなぜ候補）→ LLM（8D D1〜D5 を §5-3 JSON で）→ Variable Assigner（`eightd_json`）→ Answer（要約）
  4. **追い指示**：LLM（`eightd_json`＋協定＋`sys.query`）→ 妥当性指摘／D6・D7 追記／ja・zh 版生成（LLM ×2 並列、`PC-06` 用語集を `context` に）→ HTTP Request（`PC-13`：docx 生成）→ Answer（ファイルリンク）
  5. （任意）Human Input（1.15 の一時停止フォーム）で「D4 最有力原因の確定」を担当者に選ばせてから D5 を生成
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-nc-records` | 不具合台帳 | 行単位 | `nc_no` `part_no` `defect_type` `process` `line` `year` `customer` `root_cause` | QMS 月次 → `PC-03`（`PC-04` Webhook で日次も可） |
  | `kb-8d-archive` | 過去 8D | D 節単位 | `report_no` `nc_no` `part_no` `customer` `lang` | QMS／ファイルサーバ |
  | `kb-process-standards` | コントロールプラン・基準値 | 行単位 | `part_no` `process` `parameter` `min` `max` `unit` `cp_no` `rev` | Outline／品質課 xlsx。**Code 定数にも同じ値を持ち、CP 改訂時に両方更新** |
  | `kb-customer-requirements` | 顧客品質協定・8D 提出要件 | 節単位 | `customer` `topic`（提出期限／帳票化／効果確認） | Outline「顧客要求事項」 |
- **プラグイン／ツール**：`tools/dify_extractor`（KB 投入）、`tools/mineru`／`tools/paddleocr`（帳票 PDF）、`tools/json_process`（任意）。docx 生成は `PC-13`（Dify 公式プラグインに docx 生成は無い → 自前 API）
- **モデル**（`PC-08`）：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（照合・8D 本文）、`Qwen3-32B`（ファイル別の抽出）。**日本語 8D は本社・顧客日本窓口向けなので日本語品質を評価**（不足なら本社側で `DeepSeek-V3.x` 比較、または海外モデル）。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（file-list → document-extractor → LLM の骨子）、`../templates/08-mineru-pdf-parse-demo.yml`（PDF）。8D 専用の公開 DSL は無い（捏造しない）

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（事実） | D2/D3 の数量・ロット・日付が入力と一致 100% | 評価セット 20 件、自動突合（JSON vs 入力） |
| 基準外検出 | Code の `out_of_spec` 再現率 100%、LLM が独自に基準外を追加 0 | ダミー条件記録 20 本 |
| 類似照合 | 正解 NC を top-3 に含む ≥ 80% | 過去 8D 30 件の「類似事例」欄と突合 |
| 原因の扱い | D4 を断定しない（「候補」「未確定」表記）100% | 人手 |
| 二言語一致 | ja/zh の数値・部品番号・日付の不一致 0、用語集準拠 ≥ 95% | 自動（数値抽出比較）＋`PC-06` 用語チェック |
| 言語 | 入力言語で返答 100% | `PC-07` |
| 形式 | `eightd_json` スキーマ準拠 100%、docx 生成成功 ≥ 99% | バリデータ／`PC-13` ログ |
| 速度 | 初回解析 p95 < 90 秒 | `PC-09` |
| 安全 | 連絡先・他顧客名の露出 0 | 負例 |

- **評価方法**：リリース前に品質保証課長が過去 8D 10 件で「人が書いた 8D との差」を採点。運用後は提出 8D ごとに担当者が「修正量」をスコア（Langfuse）、四半期で見直し
