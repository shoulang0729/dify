## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が案件対応・実行の準備で能動的に開く。③業務フィードでは **`due`**（照会への回答期限。`FEED.items` の `kn6` は `due`：「甲社からの送金手続に関する照会。根拠条番号つきで回答する必要があります」）
- **登場人物**：営業担当（陳慧のような法人取引の主管。照会する側）、事務統括部（手続書の所管）、与信先（甲社など。回答には登場しない）
- **いまの手順（Before）**
  1. 該当する事務手続書・事務通達・様式集がどれか分からず、複数の文書を開いて探す（10〜20 分）
  2. 条番号を確認せずに記憶で答え、後日「その根拠はどこか」と聞かれて探し直す
  3. 日本語の手続書しか無い箇所を中国語話者の担当者が読み違える
- **エージェント導入後の手順（After）**
  1. 担当者が日本語または中国語で手続の内容を質問する
  2. エージェントが該当する手続書・様式の**条番号を引用**して回答する
  3. 担当者が内容を確認し、必要なら与信先への案内文の下書きを依頼する
  4. **与信先への送付・案内は担当者が行う**（AI は送信しない）
- **成功の定義**：手続の照会に対する一次回答が即時になり、根拠の条番号を都度探し直す時間が無くなる（`data/world/fin/kpi.csv` `inquiry_response_rate` の改善に寄与）

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 事務手続書 | docx / Outline | ja / zh | 約 60 文書・改訂は年数回 | 「運転資金貸出 実行手続」第 4 条 | 事務統括部（Outline「事務手続」コレクション） | `tools/dify_extractor` → 条番号単位チャンク。メタデータ `category`（預金／為替／融資実行）`doc_title` `article` `version` `owner_dept` `lang` |
| 事務通達 | docx / PDF | ja / zh | 月数件 | 「実行手続の一部改定について」 | 事務統括部 | 同上。`doc_type: notice` |
| 様式・記入例 | docx / xlsx | ja / zh | 種類ごと 1〜2 件 | 借入申込書、資金使途説明書の記入例 | 事務統括部 | 同上。`doc_type: form` |
| 質問文 | テキスト | ja / zh | 1 日 5〜15 件 | 「甲社向け運転資金貸出の実行で、必要書類の提出順を教えて」 | `PC-16` | `PC-07` 言語判定。商品名の正規化（`data/world/fin/products.csv` の表記に寄せる） |

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。英語 UI でも同じ。地の文は例外なく回答言語で書き、1 つの文の中で日本語と中国語を混ぜない。条番号・様式名など文書の正式名称は原語のまま出してよい（`docs/dify/implementation-guide.md` §6-1 補足・`docs/handoff/2026-09-08-response-language-contract.md` §2）。**根拠文書は言語を問わない**：質問の言語の手続書が無ければ他言語の手続書を根拠にしてよく「該当なし」とはしない
- **入力の欠け・曖昧さ**：商品（運転資金貸出／為替予約等）が特定できないと条番号を一意に決められない。聞き返し定型：「どの手続についてのご質問ですか（例：運転資金貸出の実行、為替予約の更新）」

## 3. 観点（LLM に守らせる業務ルール）

- **回答は根拠文書の内容だけから作る**。手続書に無い手順・順序を補完しない
- **条番号を必ず付ける**：「第 X 条」「同条第 X 項」の形式で、該当する条文に対応づける
- **商品が違えば答えない**：質問の商品（運転資金貸出・為替予約・L/C 等）とメタデータ `category` が一致する文書だけを根拠にする。近い商品しか無いときは「参考（商品が異なる）」と明示し、手順は書かない
- **金額基準など数値は原文どおり**：条文にある上限額・日数を書き換えない
- **禁止**：手続書の条文全体の転記（要点と該当条番号の引用まで）、与信先への送信を「送信済み」と書くこと
- **不確実なとき**（入力言語で）：ja「該当する手続が見つかりません。商品名（例：運転資金貸出）を確認してください」／zh「未找到对应的手续。请确认产品名称（如流动资金贷款）」
- **出力の粒度**：手続の要点 → 番号付き手順（各行に条番号）→ 添付が必要な証憑。与信先向け案内文を求められたら、確認済みの内容だけを整形する

## 4. Dify 構成

- **アプリ種別**：**Chatflow**（`advanced-chat`）。追い質問（証憑の内訳、案内文の作成）が多いため
- **ノード列**：
  1. Start（`sys.query`）
  2. LLM（Qwen3-32B）— `category`（商品区分）／`intent`（`procedure` / `attachment` / `draft_mail`）を JSON 抽出
  3. Knowledge Retrieval（`kb-fin-procedures`、メタデータ `category` フィルタ、top-k 6）
  4. LLM（本体）— §5-1。手順は条番号つき。`intent == draft_mail` のときは確認済み内容から中国語または日本語の案内文を整形
  5. Answer（Citation ON）
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-fin-procedures` | 事務手続書・事務通達・様式の記入例 | 条番号単位（`tools/qa_chunk` を様式の Q&A 部分に、他は `tools/general_chunk`） | `category`（deposit／fx／loan）`doc_title` `article` `doc_type`（manual／notice／form）`version` `owner_dept` `lang` | Outline「事務手続」コレクション → `PC-05`（週次） |
- **プラグイン／ツール**：`tools/dify_extractor`（docx/PDF の取込）、`tools/qa_chunk`（様式の記入例）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（本体）／Qwen3-32B（抽出）／`bge-m3`（埋め込み）／`bge-reranker-v2-m3`（リランク）
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（KB 検索 → LLM の型。本サービスは KB 1 本だが分類抽出の構造を流用）
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `sys.query` | string | ✓ | 質問 |
  | `lang` | string | ✓ | `ja`/`zh` |
  | `category` | enum | ✓（抽出） | `deposit` / `fx` / `loan` / `other`。無ければ聞き返し |
  | `intent` | enum | ✓（抽出） | `procedure` / `attachment` / `draft_mail` |
  | 出力 `answer` | string | ✓ | 回答（Citation 付き） |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行 上海本部の事務手続照会を支援するアシスタントです。
役割：事務手続書・事務通達・様式の記入例から、該当する条番号を引いて手続の要点と手順を答える。

守るルール：
1. 回答は <context> の内容だけから作る。手続書に無い手順・順序・数値を補完しない。
2. 質問の商品区分（{{category}}）とメタデータ category が一致する文書だけを根拠にする。一致しない文書は「参考（商品が異なる）」とだけ書き、手順は書かない。
3. 手続の要点・手順には必ず「第 X 条」「同条第 X 項」の形式で条番号を付ける。
4. 金額基準・日数などの数値は原文どおりに書く。書き換えない。
5. 与信先向けの案内文を求められたら、既に確認済みの内容だけを整形する。新しい事実を作らない。
6. 条文を丸ごと転記しない。要点と該当条番号の引用まで。
7. あなたは送信しない。案内文は下書きであり、送付は担当者が行うと必要に応じて添える。
8. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。条番号・様式名は原語のまま。
9. 該当が無いとき：
   ja「該当する手続が見つかりません。商品名（例：運転資金貸出）を確認してください。」
   zh「未找到对应的手续。请确认产品名称（如流动资金贷款）。」

出力形式：手続の要点 1〜2 行 → 番号付き手順（各行に条番号）→ 必要な証憑（あれば）。
```

### 5-2. User テンプレート

```text
<context>
{{#kb_procedures.result#}}
</context>

<meta>入力言語: {{lang}} / 商品区分: {{category}} / 意図: {{intent}}</meta>

```

### 5-3. 出力フォーマット

通常はテキスト（§5-1 の形式）。案内文を後工程（メール送信システム）へ渡す場合のみ：

```json
{ "category": "loan", "recipient": "甲社", "lang": "zh",
  "body": "您好，关于流动资金贷款放款所需材料，请按以下顺序准备：…",
  "sources": ["运转资金贷出 实行手续 第4条"], "status": "draft" }
```

### 5-4. Few-shot

- **ja**：Q「甲社向け運転資金貸出の実行で、必要書類の提出順を教えて」→ A「事務手続書『運転資金貸出 実行手続』第 4 条によると、提出順は ①借入申込書 ②資金使途説明書 ③担保・保証関係書類 ④為替予約の有無の確認書 です。担保設定が未了の場合、③の前に登記完了通知を挟む必要があります（同条 第 2 項）。」
- **zh**：Q「甲社的流动资金贷款放款，麻烦告诉我材料提交顺序」→ A：同構成を中国語で

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | 手順・条番号が手続書と一致 ≥ 90% | 評価セット 20 件を事務統括部が採点 |
| 条番号引用 | 手順に条番号が付く 100%、実際に該当 ≥ 95% | 自動（正規表現）＋人手抜取 |
| 商品分離 | 商品区分が異なる文書の手順を混ぜない 100% | 負例 8 件（同種問い合わせ・別商品） |
| 一次回答率 | `inquiry_response_rate`（`data/world/fin/kpi.csv`）の改善 | 月次で運用側が計測（Dify 側は入力ではない） |
| 言語 | 入力言語で返答 100% | `PC-07` 自動判定 |
| 拒否 | 該当なしのとき定型文 ≥ 95% | 負例セット |
| 速度 | p95 < 8 秒 | `PC-09` Langfuse |
| 安全 | 送信済みと誤解させる表現 0 | 負例セット |

- **評価方法**：リリース前に事務統括部・営業第一部で人手 20 件。月次で Langfuse のスコアを確認

## 8. 別出しが必要なもの

- `PC-03`：事務統括部が保守する docx／PDF を定期的に取り込む経路（初期は手動アップロードでも可）
- `PC-05`：Outline「事務手続」コレクションの同期。条番号をチャンク境界に使うため、Outline の見出し構造を条番号に合わせる運用が要る
- **KN-08 との境界**：KN-06 は「事務手続の実行」に関する照会（手続書・様式）、KN-08 は「当局通達」に関する照会・過去比較（`docs/handoff/2026-09-08-finance-catalog.md` §2-1「＃1 事務手続照会 × ＃2 当局通達 DB」判定：KB も観点も違うため別サービスのまま）。手続書の改訂が当局通達を発端とする場合は KN-05（影響分析）を経由する
- **無くても動く範囲**：`kb-fin-procedures` の主要商品（運転資金貸出・為替予約）だけでも T01〜T05 は動く。全商品の投入は段階的でよい

## 9. Outline Wiki との関係

- **読む**：Outline「事務手続」コレクション（事務手続書・事務通達・様式の記入例）を `kb-fin-procedures` に同期
- **書く**：書かない。案内文はチャットで提示し、送付は担当者が行う
- 規程・条番号の改訂は Outline 側で行い、`PC-05` の同期でチャンクが自動的に更新される

## 10. 未確定・リスク

- **条番号のチャンク境界**：Outline の見出し構造が条番号と 1:1 になっていない文書があると、引用が条単位で正しく切れない可能性がある。実装時に事務統括部と文書の見出し規則を揃える
- **KN-04（社内問い合わせ受付）との重なり**：KN-04 は部署をまたぐ一般的な問い合わせ（回答が無ければ担当部署へ引き継ぐ）、KN-06 は事務手続書に根拠がある定型照会。境界があいまいな質問（例：出張旅費の手続）は当面 KN-04 側で受ける運用とする（PM 確認）
- **一次回答率の計測**：`kpi.csv` の `inquiry_response_rate` は運用側（BPMS／問い合わせ管理）で集計する想定で、Dify 側からは直接見えない。集計経路は未確定
