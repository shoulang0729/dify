## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：月末（担当者が能動的に開く）。③業務フィードでは `routine`（月末のコスト配分作業の案内）
- **登場人物**：稼働集計・配分案の作成担当（次長クラス）、承認する上長、各案件の担当者
- **いまの手順（Before）**：各担当の稼働実績を Excel で集め、案件・組織単位に手作業で按分する。月報の記載と実績集計が食い違っていても気づきにくい
- **エージェント導入後の手順（After）**
  1. 稼働実績と案件一覧をアップロードする
  2. **案件別の稼働集計とコスト配分案**、前月からの偏りが返る
  3. **月報の記載と実績集計の食い違い**があれば指摘される（原因の推定は「候補」として示し、断定しない）
  4. 担当者が確認し、**配分の確定は人が行う**（AI は経理システムへ登録しない）
- **成功の定義**：按分の手作業が減り、前月比の偏りや月報との食い違いが早期に見つかる

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 稼働実績 | xlsx | ja / zh | 月次 | 担当者別の案件ごとの稼働時間 | 工数管理システムのエクスポート（`PC-04`） | Document Extractor で表を JSON 化 |
| 案件一覧 | xlsx | ja / zh | 月次 | 案件名・コストセンター・期間 | 案件管理システムのエクスポート | 稼働実績との突合キーに使う |
| コスト配分ルール | Markdown | ja / zh | 改定時 | 按分方法（工数比例／固定比率 等） | Outline「稼働配分 › ルール」（`PC-05`） | System へ埋め込み |
| 前月の配分実績（比較用・任意） | xlsx | ja / zh | 月次 | 前月の按分比率 | 前回の出力を保存したもの | 前月比の計算に使う |

- **入力言語の扱い**：ja / zh どちらのファイルでも受け、**結果は入力言語で**（`CLAUDE.md` §2-5）。列見出しが原語のままでも Code 側で正規化する
- **入力の欠け・曖昧さ**：案件一覧に無い案件名が稼働実績に出てくる場合は「未登録の案件」として一覧化し、按分対象から除外する（勝手に近い案件へ寄せない）。前月データが無ければ前月比は出さず「前月データなし」と明示する

## 3. 観点（LLM に守らせる業務ルール）

1. **集計・按分比率は Code の計算結果を転記する**。案件別の時間・比率を LLM が自分で計算しない
2. **月報の記載と実績集計の食い違いは事実として提示する**。原因は「候補」として書き、断定しない（例：「集計期間のズレが疑われます」）
3. **按分の確定・経理システムへの登録は行わない**。出力は常に「案」であることを明示する
4. **個人別の稼働時間は本人・直属の上長以外に見える形で書かない**。案件・組織単位の合計にとどめる（`PC-10`）
5. **禁止**：稼働が少ない担当者を名指しで評価する表現／案件一覧に無い案件を推測で按分対象に含める
6. **不確実なとき**：ja「案件一覧に無い案件があります。案件名を確認してください。」／zh「案件清单中没有该案件，请确认案件名称。」
7. **出力の粒度**：稼働集計（合計・案件別内訳）→ コスト配分案（比率・配分先）→ 前月からの偏り（データがあれば）→ 報告との食い違い（あれば）→ 確定前の確認事項

## 4. Dify 構成

- **アプリ種別**：**Workflow**（アップロード → 1 回実行）
- **ノード列**
  1. `Start`（`effort_file`, `case_list_file`, `prev_month_file` 任意）
  2. `Document Extractor`（xlsx → 表データ）
  3. `Code`（正規化・突合：担当者×案件×時間 → 合計・案件別内訳。案件一覧に無い案件を「未登録」として分離。前月データがあれば比率差分を計算）
  4. `Knowledge Retrieval`（KB `po4-allocation-rules`：配分ルール）
  5. `LLM`（配分案の説明・食い違いの指摘。§5-1）
  6. `Code`（出力 JSON の検算：比率の合計が 100% になっているか）
  7. `template-transform` → `End`（`allocation_md`, `allocation_json`, `unregistered_cases[]`）
- **Knowledge**：`po4-allocation-rules`（Outline 同期。按分方法・コストセンターの対応表）
- **プラグイン／ツール**：`http-request`（`PC-04` 工数・案件管理システムからの取得を自動化する場合。第 1 段階は手動アップロードで足りる）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（説明文の生成）。計算は LLM を使わない（Code）
- **参照 DSL**：`../templates/07-file-upload-extraction-workflow.yml`（アップロード抽出）、`../templates/06-text-to-sql-http-api-echarts.yml`（集計の型）
- **入出力変数**：`effort_file` file ✓／`case_list_file` file ✓／`prev_month_file` file（任意）／出力 `allocation_json` object・`unregistered_cases` array・`discrepancy` object（任意）

## 5. プロンプト

### 5-1. System

```text
あなたは組織の月次稼働集計とコスト配分案の作成を支援するアシスタントです。
守ること：
1. 稼働の合計・案件別内訳・配分比率は {{calc_json}} の値をそのまま書く。自分で計算しない。
2. 月報の記載と実績集計に食い違いがあれば事実として示し、原因は「候補」として書く。断定しない。
3. 配分の確定・システムへの登録は行わない。出力は常に「案」であることを明示する。
4. 個人別の稼働時間を、本人・直属の上長以外に分かる形で書かない。案件・組織単位の合計にとどめる。
5. 出力言語：利用者の入力言語。日本語なら日本語、中国語なら中国語。
6. 案件一覧に無い案件があれば「未登録の案件」として分けて示し、確認を求める。
```

```text

【配分ルール（検索結果）】{{context}}
【月報の記載（比較対象・任意）】{{report_note}}
```

不要。集計は Code の値の転記が中心で、書式は System と JSON スキーマで固定できる。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 集計の非捏造 | 合計・比率・件数が Code の値と完全一致 100% | 文字列一致の自動検査 |
| 按分比率の整合 | 比率の合計が 100%（丸め誤差は許容） | Code 単体テスト |
| 未登録案件の検出 | 案件一覧に無い案件の検出漏れ 0 | 評価セット |
| 個人情報 | 個人別稼働時間の非本人・非上長への開示 0 | 負例セット |
| 言語 | 入力言語で返答 100% | 自動判定 |
| 速度 | p95 < 30 秒 | Langfuse |

- **評価方法**：リリース前に過去 3 か月分の実績（匿名化）で按分比率の再現性を確認。月次で運用担当が抜き取りチェック

## 8. 別出しが必要なもの

- **工数・案件管理システムとの連携（`PC-04`）**：第 1 段階は手動アップロード。自動取得は API の有無を顧客ごとに確認
- **配分ルールの構造化**：Outline のルール文を Code の按分ロジックに落とす作業（財務・PMO 側が正を持つ）
- **無くても動く範囲**：システム連携が無くても「アップロード → 集計・配分案」までは動く

## 9. Outline Wiki との関係

- **読む**：「稼働配分 › ルール」コレクション（按分方法・コストセンター対応表）
- **書く**：確定した配分案を「稼働配分 › <対象月>」へ記録（人が確定した後）
- 稼働の生データは Outline に書かない（更新・集計ができないため。アップロードのたび再計算する運用）
