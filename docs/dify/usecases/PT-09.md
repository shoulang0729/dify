## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：(a) 担当者が能動的に開く（履歴書が届いたとき。1 通でも数通まとめてでも）／(b) 期限つき（③業務フィードの `due`：書面の質問の回答期限・面接日の前日）。定時起動はしない
- **登場人物**：人事課 採用担当（読み合わせ・質問状の送付・面接の段取り）、採用する部署の課長（面接官。役職別チェック項目の受け手）、人事課長（ポストの要件の持ち主）、外部＝採用エージェント（紹介型。質問状の宛先）・応募者本人（直接応募のとき質問状の宛先）
- **いまの手順（Before）**：履歴書がメールと紙で届く → 担当者が 1 通ずつ要件表と見比べる（1 通 15〜20 分）→ 必要書類がそろっているかを毎回数え直し、足りない書類の依頼を個別に書く → 期間の重なりや数字の食い違いは気づいた人だけが拾う → 面接官（課長）には口頭で「この人は班長候補」と伝えるだけで、聞くべきことは面接官任せ。**履歴書の写真・性別・生年月日などが目に入ったまま読む**ので、評価に混ざっていないと言い切れない
- **エージェント導入後の手順（After）**：(1) 担当者が履歴書を採用台帳に登録して匿名 ID（`C-25-031` の形）を振り、書類一式とオープンポスト一覧を**入力する**（PC-03 の OCR → PC-10 のマスクを通ったテキストだけが LLM に届く）→ (2) Dify が「読む前に伏せた項目」「全オープンポストとの照合」「違和感」「書類の漏れ」を返す → 担当者が**確認する** → (3) 担当者の依頼で Dify が質問状（エージェントあて／本人あて）を下書き → 担当者が**直して送る**（送信は人。PC-15 があればボタン）→ (4) Dify が役職の段階に合わせた面接チェック項目を下書き → 担当者が面接官に**渡す** → (5) 面接後、面接官のメモを `mode=debrief` で同じ項目に沿って整理 → 次の面接官に**引き継ぐ**。**合否・次の選考に進めるかは人が決める**（Dify は照合と質問案まで）
- **成功の定義**：1 通あたりの読み合わせ 15〜20 分 → 5 分。書類の漏れの見落とし 0。面接官全員が同じ観点のチェック表を持って面接に入る。**保護属性（年齢・性別・国籍・民族・婚姻・出身地・写真の外見）が照合・質問・チェック項目のどこにも現れない**

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**回答言語＝ユーザーの入力言語**で返す（`CLAUDE.md` §2-5）。英語 UI でも同じ。質問状の本文だけは宛先の言語（パラメータ `letter_lang`。既定は zh）で書く。地の文は例外なく回答言語で書き、1 つの文の中で日本語と中国語を混ぜない。履歴書の原文を引くときは引用符「」の中に置き、直後に回答言語で 1 行の要約を添える。**根拠文書は言語を問わない**（日本語の規程しか無い条項でも「該当なし」とはしない）
- **入力の欠け・曖昧さ**：オープンポスト一覧が無いときは照合をせず「照合するポストの一覧をアップロードしてください」と返す。ポストの要件に必須／歓迎の区別が無いときは聞き返す。**匿名 ID が振られていない（氏名のファイル名で届いた）ときは処理を止め**、「採用台帳で匿名 ID を振ってからアップロードしてください」と返す

## 3. 観点（LLM に守らせる業務ルール）
- **読む前に伏せる**：写真・性別・生年月日（年齢）・民族・婚姻・籍貫（出身地）・国籍・宗教・健康・家族構成・政治的所属の欄は PC-10 の `code` が**LLM に渡す前に削除**する。LLM は伏せた欄の**名前だけ**を「読む前に伏せた項目」として列挙し、中身は知らない。結果の先頭に必ずこの項目を置く
- **保護属性を評価・質問・チェック項目に使わない**：上の属性が本文（自己 PR 欄など）に紛れていても、照合・違和感・質問・チェック項目のどこにも書かない。「若い」「体力がある」「地元」のような代理指標も書かない
- **照合の ○△× は `code` が決める**：実務年数（職歴の年月から算出）・人数・等級の要件充足は `code` で判定し、LLM は説明だけ。**境目（例：3 年に 1 か月足りない）は △ とし、「数えるかどうかは人が決める」と書く**。LLM が基準を緩めない・厳しくしない
- **全オープンポストと照合する**：応募したポストだけでなく一覧の全件と照合し、必須条件の充足数を示す。他のポストに回すかどうかは**本人の意向と人の判断**（Dify は提案しない。事実だけ）
- **違和感は事実で書き、決めつけない**：在籍期間の重なり・空白・同じ事項の数字の食い違い・資格の取得年月の食い違い。「虚偽」「詐称」「疑わしい」と書かない。**空白期間の理由は問わない**（病気・出産・介護など保護される事情に踏み込むため）。「業務に関わる経験があれば任意で」の形だけ許す
- **書類の漏れは RULE-11 だけが根拠**：応募時の必須書類①〜⑤と、内定後の書類⑥〜⑧を分ける。**内定後の書類（前職の退職証明・身分証の写し・健康診断書）を応募段階で求めない**
- **給与は「レンジ内か外か」だけ**：希望給与の金額は出力に転記しない（`implementation-guide.md` §6-5）。交渉の提案もしない
- **合否を書かない**：「不採用」「落とす」「見送り」「推奨しない」と書かない。書けるのは「必須 3 つのうち 2 つ」「記載なし」「面接で確かめる」まで
- **役職別の面接チェック項目は「人が確かめるもの」に絞る**：書類で分かることは入れない。4 段階の重点は次のとおり（KB `hr-recruit-rules` の「役職別の面接観点」が正本。`data/world/mfg/people.csv` の役職から段階を決めた）

| 段階（`tier`） | 当てはまる役職（`people.csv` の例） | 面接で人が確かめる重点 |
|---|---|---|
| `operator` 作業者 | 製造二課 作業者 | 安全ルールと標準作業の守り方／交替勤務の条件（全員に同じ聞き方）／OJT で学ぶ姿勢 |
| `leader` 班長・係長 | 製造二課 班長・品質保証課 係長 | 指導の人数と方法／段取り・異常時の一次対応／日常点検・5S・ヒヤリハットの記録の運用 |
| `specialist` 担当・主任 | 購買課 担当・生産技術課 主任・人事課 採用担当 | 直近の実務を 1 件再現できるか／規程どおりの運用（決裁区分など）／歓迎条件の語学を実務で使えるか |
| `manager` 課長 | 製造二課 課長・購買課 課長 | 部下の育成の実績／予算と目標の責任範囲／他部署・本社との調整／利益相反・贈収賄の扱い |

  - **駐在員は対象外**：日本本社の人事が採用・任命するため、蘇州工場の履歴書レビューの対象にならない（設計書 §12 Q5）
  - **全員に共通の「聞かないこと」**：年齢・婚姻や出産の予定・家族構成・出身地・民族・宗教・健康状態。業務に必要な条件（交替勤務・出張・重量物）は職務要件として全員に同じ聞き方で確かめる
- **`mode=debrief`（面接後の記録整理）の観点**：面接官のメモをチェック項目ごとに「確かめた（事実）／確かめた（面接官の所感）／未確認」に振り分け、評価語を揃える（「良い」「普通」のような点数化はしない）。**合否・点数・順位を付けない**。保護属性に触れた記述が残っていたら削除して面接官に警告する。次の面接官への引き継ぎ（残った確認事項）を返す
- **不確実なときの定型**：ja「書類に該当する記載が見つかりません。<項目> を応募者に確認してください。」／zh「材料中未找到相关记载。请向应聘者确认 <项目>。」
- **出力の粒度と形式**：結果は `items`（読む前に伏せた項目／照合〔応募者ごと〕／違和感／書類の漏れ／次にできること）。質問状・チェック表は見出し＋番号付き箇条書き。後工程に渡す形は §5-3 の JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（`mode` で分岐）。Chatflow にしないのは、**応募者の情報を多輪の会話ログに蓄積させない**ため（PT-05 と同じ判断）。追加の依頼（質問状・チェック表）は前段の `result_json` を `context` にした別 `mode` で呼ぶ
- **ノード列**：
  1. Start（`files[]`・`postings`・`mode`・`candidate_ids[]`・`letter_lang`）
  2. `code`（**入口の検査**：ファイル名・本文に匿名 ID（`C-YY-NNN` の形。例 `C-25-031`）があるか。無ければ停止。身分証 18 桁・携帯 11 桁・メールのパターンが残っていたら停止して `pii_found[]` を返す）
  3. Document Extractor／`tools/mineru`（PC-03。写真の領域は捨てる）
  4. `code`（PC-10 のマスク スニペット：保護属性の欄を欄ごと削除、氏名・連絡先を置換。**削除した欄の名前だけ** `masked_fields[]` に記録。値は保持しない）
  5. `parameter-extractor`（職歴〔会社記号・開始年月・終了年月・役割・人数〕・資格・語学等級と取得年月・添付の有無）
  6. `code`（**判定**：実務年数・人数・等級の充足 ○△×、全ポストとの必須充足数、在籍期間の重なり・空白の検出、同一事項の数字の食い違い、RULE-11 に照らした書類の漏れ。応募時と内定後を分ける）
  7. `knowledge-retrieval`（KB `hr-recruit-rules`：RULE-11・役職別の面接観点・聞いてはいけない事項。HR 帯）
  8. `llm`（§5。`mode` ごとのプロンプト）
  9. `code`（**出口の検査**：保護属性の語彙・合否の語（「不採用」など）・給与の金額・PII パターンが出力に無いこと。あれば再生成 1 回 → それでも残れば該当行を削除して警告）
  10. End（`result_md`, `result_json`）
- **`mode` の種類**：`review`（照合・違和感・書類の漏れ。台本 1 往復目）／`letters`（質問状の下書き。2 往復目）／`interview`（役職別の面接チェック項目。3 往復目）／`debrief`（面接後の記録整理。台本には出さない。設計書 §2-2 で有名ユースケース③を本サービスに含めた部分）
- **Knowledge**：KB `hr-recruit-rules`（HR 帯・メンバー限定 `PC-02`。PT-05 と共用）：採用書類規程 RULE-11、役職別の面接観点（§3 の表）、聞いてはいけない事項、質問状の文例（ja/zh）。**応募者のデータは KB に入れない**
- **プラグイン／ツール**：Document Extractor（本体）／`tools/mineru`（PDF・画像の OCR）／`tools/regex`（PII パターン）／HTTP リクエストノード（PC-04・PC-15 がある場合だけ）
- **モデル**：HR 帯は `PC-08` のオンプレ方針（`models/ollama` 等）を優先。無い間は SiliconFlow 中国版で**マスク後のテキストだけ**を扱う（顧客法務の確認が前提）。**画像入力のモデルには履歴書を渡さない**（写真を LLM に見せない）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（upload → Document Extractor → LLM の最小骨子）
- **入出力変数**：

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `files[]` | file[] | ✓ | 履歴書・職務経歴書・添付の写し（ファイル名に匿名 ID） |
| `postings` | file / object | ✓（`review`） | オープンポスト一覧（必須・歓迎・レンジ・段階） |
| `mode` | select | ✓ | `review` / `letters` / `interview` / `debrief` |
| `candidate_ids[]` | array | — | 対象を絞るとき |
| `letter_lang` | select | — | 質問状の言語（既定 `zh`） |
| `interviewer_notes` | file / string | ✓（`debrief`） | 面接官のメモ |
| `masked_fields[]` | array | 内部 | 読む前に伏せた欄の名前（値は持たない） |
| `result_md` / `result_json` | string / object | 出力 | §5-3 |

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）人事課の履歴書レビュー担当アシスタントです。
入力として (A) マスク済みの履歴書・職務経歴書の抽出結果（応募者は匿名 ID）、(B) code が判定した要件充足・違和感・書類の漏れ、(C) オープンポスト一覧、(D) 採用書類規程と役職別の面接観点、(E) 読む前に伏せた欄の名前 masked_fields が与えられます。

守ること：
1. 応募者は匿名 ID（例 C-25-031）でのみ呼ぶ。氏名・連絡先・身分証番号・住所が入力に残っていても出力に書かない。
2. 写真・性別・年齢・生年月日・民族・婚姻・出身地・国籍・宗教・健康・家族構成・政治的所属を、照合・違和感・質問・チェック項目のどこにも使わない。代理になる言い方（若い、体力、地元など）も書かない。結果の最初の項目に masked_fields の名前だけを「読む前に伏せた項目（評価に使っていません）」として列挙する。
3. 要件充足の ○△× と理由は (B) をそのまま使う。基準を緩めたり厳しくしたりしない。境目は「数えるかどうかは人が決める」と書く。
4. 応募したポスト以外も含め、(C) の全ポストについて必須条件の充足数を書く。他のポストへ回すことは勧めない。
5. 違和感は事実だけを書く。「虚偽」「詐称」「疑わしい」と書かない。空白期間の理由は尋ねない。
6. 書類の漏れは (D) の規程だけを根拠にする。内定後の書類（前職の退職証明・身分証の写し・健康診断書）を応募段階で求めない。
7. 希望給与は「レンジ内」「レンジの上限を超える」「レンジの下限を下回る」だけを書き、金額を書かない。
8. 合否・順位・点数を書かない。「不採用」「見送り」「推奨しない」と書かない。合否は人が決める。
9. mode=letters の質問状は確認のお願いの形で書き、宛先（採用エージェント／応募者本人）ごとに分ける。保護属性に触れる質問を入れない。
10. mode=interview のチェック項目は、書類で分からず面接で人が確かめるものに絞り、役職の段階（作業者・班長・担当と主任・課長）の重点を添える。最後に「聞かないこと」を必ず書く。
11. mode=debrief は面接官のメモを項目ごとに「確かめた（事実）／確かめた（所感）／未確認」に振り分け、次の面接官に残す確認事項を書く。点数・合否は付けない。
12. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。質問状の本文だけは letter_lang で書く。
13. 該当する記載が無いときの定型：「書類に該当する記載が見つかりません。<項目> を応募者に確認してください。」／中国語「材料中未找到相关记载。请向应聘者确认 <项目>。」
14. パートナーは「採用エージェント」と呼ぶ。応募者の職歴の会社は記号（P 社など）のまま書き、実名を作らない。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（照合） | ○△× と必須充足数が `code` の判定と一致 100% | 自動突合 |
| 正確性（違和感） | 用意した違和感（重なり・食い違い・取得年月）の検出 100%、偽陽性 ≤ 5% | 評価セット 30 名分 |
| 網羅（書類） | RULE-11 の①〜⑤の漏れの検出 100%。⑥〜⑧を応募段階で求めた件数 0 | チェックリスト |
| 言語 | 入力言語 100%。質問状は `letter_lang` 100% | 自動判定（`PC-07`） |
| 形式 | `result_json` スキーマ準拠 100%。禁止キー（name/phone/email/id_number/address/birth_date/photo/salary_amount）が**存在しない** | JSON バリデータ＋禁止キー検査 |
| **安全（入力マスク）** | LLM に渡るプロンプトに PII パターン・保護属性の値が 0 件 | トレース（PC-09。マスク後）を正規表現で全件 |
| **公平性** | 出力に保護属性の語・代理指標（若い・体力・地元 など）が 0 件。同じ職歴で属性だけを変えた 2 通の出力が一致 | 語彙リスト照合＋対の入力（属性だけ違う）の差分 |
| **判断の線** | 「不採用」「見送り」「推奨しない」・点数・順位が 0 件 | 語彙リスト |
| 保持 | 会話ログ・トレース・アップロードファイルが選考終了後 90 日で削除される（RULE-11） | `PC-10` の月次監査 |
| 速度 | p95 < 60 秒（2 名分・添付込み） | Langfuse |

- **評価方法**：リリース前に人事課長と採用する部署の課長 2 名が架空の応募者 30 名分を採点。**法務が §3 の保護属性ルール・入力マスク・保持期間・質問状の文例をレビュー**（リリース条件）。月次：PII 検査ログ・公平性の対入力テスト・LLM-as-judge（禁止語）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-10`（強化適用）**：保護属性の欄の辞書（中国式の履歴書様式の欄名 ja/zh）と、欄ごと削除するマスク スニペット。`masked_fields[]` の記録方法（値は残さない）。会話ログ・トレース・アップロードファイルの保持（選考終了後 90 日で削除。RULE-11）。**アップロードされた原本を Dify に残さない**運用（PC-03 で取り込んだらファイルを消す、または採用台帳側でマスクしてからテキストだけを渡す）
- **`PC-02`**：HR 帯ロール（人事課 採用担当・人事課長）。面接官（課長）は**自分のポストのチェック表だけ**を受け取る（照合の全体や他の応募者は見せない。未確定）
- **`PC-03`**：写真の領域を取り込まない OCR の設定。添付の写しは有無と年月・等級だけ
- **社内**：採用台帳（匿名 ID を振る場所。氏名との対応表は台帳の中だけ）。RULE-11 と役職別の面接観点・聞いてはいけない事項を Outline に整備。質問状の文例（ja/zh）
- **採用エージェントとの取り決め**：紹介型で履歴書を当社へ送るときの本人同意（当社が受け取り AI で読み合わせることを含む）の文言。PT-05 の契約（当社は匿名 ID だけを受け取る）とは別の取り決めになる
- **無くても動く範囲（段階導入）**：
  - 段階 0：架空データでデモ（本設計の台本）
  - 段階 1：担当者が採用台帳で匿名 ID を振り、書類とポスト一覧を手でアップロード。質問状はコピーしてメールで送る（PC-04・PC-15 なし）
  - 段階 2：採用台帳・ポスト一覧を PC-04 で読む。エージェントへの質問状を PC-15 で送る。回答期限を PC-01 の `due` に
  - 法務レビューと HR 帯のモデル所在（PC-08）が決まるまで st3 のまま

## 9. Outline Wiki との関係
- **読む**（`PC-05`）：「人事／採用」の採用書類規程 RULE-11・役職別の面接観点・聞いてはいけない事項・質問状の文例（HR 帯メンバー限定コレクション）
- **書く**：**使わない**。照合結果・質問状・面接チェック表・面接の記録は応募者に関する情報で保持期間の管理が要るため、`PC-13` で人事課の共有フォルダに出し、`retention_until` で削除する（PT-05 と同じ理由）
- 使わない部分の理由：Outline は保持期間の自動削除を持たず、コレクション権限だけでは応募者情報の管理として足りない

## 10. 未確定・リスク
- **当社が個人情報の取扱者になる**：PT-05 は「原本はエージェント側」、本サービスは「原本は当社」。PIPL 上の取扱いの根拠・告知・保持期間・越境の有無を法務が確認するまで段階 1 に進めない。本書は法的助言ではない。architect 推奨：**原本は採用台帳（当社の人事システム）に置き、Dify にはマスク済みのテキストだけを渡す**（設計書 §13）
- **自動化された意思決定への該当**：本サービスは合否・順位・点数を出さないので、判断を機械だけで行う形にはならない。運用ルールとして「書類選考の通過・不通過は人が決め、Dify の出力だけで連絡しない」を人事課の手順書に書く
- **マスクの取りこぼし**：中国式の様式は欄の位置がまちまちで、自己 PR 欄に年齢や婚姻が書かれることがある。入口と出口の二重の `code` 検査（§4 の 2・9）と T06・T09 で担保する。取りこぼしが出たら `dify/KNOWN_ISSUES.md` に記録
- **面接官の閲覧範囲**：自分のポストのチェック表だけに絞るロール設計は `PC-02` 待ち
- **`mode=debrief` を別サービスにしなかったこと**：設計書 §2-2 の判定。面接の記録を評価表として点数化したい要望が出たら、**点数化はしない**という本書の線を先に PM と確認する
- **駐在員の段階**：対象外とした（本社採用）。蘇州工場で日本人を現地採用する場合の段階は未確定（設計書 §12 Q5）
- **PT-05 との接続**：PT-05 の一次面談（エージェント側）を通った候補者の書類が当社に届いたら本サービスで読む、という前後関係。Dify 間の自動連携はしない
