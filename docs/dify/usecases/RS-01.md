## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に監視対象を設定して開く（初回）。以後は `PC-11` の定期実行（既定：週次）。③業務フィードでは `routine`（定期配信）または `notify`（ネガティブ情報の該当あり）
- **登場人物**：コンプライアンス・審査・営業の担当者（監視対象を設定する側）、監視対象の取引先（丙社など）、共有先の部門（審査部など）
- **いまの手順（Before）**：取引継続審査や与信レビューの前に、担当者が検索エンジンや業界ニュースサイトを手作業で見て回る。見落とし・検索漏れが起きやすく、誰が何をいつ確認したかの記録も残らない
- **エージェント導入後の手順（After）**：
  1. 対象先・業界・キーワードと収集モード（一般／ネガティブ情報のみ）、配信頻度・配信先をフォームで設定する
  2. 定期実行が公開情報を集め、日本語要約付きで配信する。取引先ごとのファイルも出力される
  3. 該当する記事が見つかったら、担当者が内容を確認し、**共有可否・エスカレーション先を判断する**（AI は共有しない）
- **成功の定義**：取引継続審査・与信レビュー前のネガティブ情報チェックが手作業の巡回から定期配信に変わり、確認漏れが無くなる

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 監視設定 | フォーム（対象先・業界・キーワード・収集モード・配信頻度・配信先） | ja / zh | 対象ごと 1 回（変更は随時） | 対象：丙社／業界：自動車部品／キーワード：訴訟・行政処罰・資金繰り・環境事故／モード：ネガティブ情報のみ | フォーム（`PC-16`） | §8 の監視設定ストアに保存。次回以降の定期実行はここを読む |
| 公開情報（ニュース・当局公表等） | Web ページ・記事 | zh 主体（一部 ja/en） | 対象ごと週次で数件〜数十件 | 地方紙報道（環境規制に関する行政指導） | 検索ツール（§4） | 重複記事の除去、対象期間（既定 4 週間）での絞り込み、日本語要約の生成 |

- **入力言語の扱い**：フォーム入力・チャットでの追い質問は日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。ただし配信物（日本語要約）は**常に日本語**が既定（元記事は中国語が多く、配信先はコンプライアンス部・審査部が主体のため）。中国語配信が必要な場合はフォームの出力言語で切り替える
- **入力の欠け・曖昧さ**：対象先・キーワードが未入力だと収集できない旨を返す。収集モード未選択は「一般」を既定にする。該当記事が 0 件でも「該当なし」を明示し、収集自体が失敗したのか区別する

## 3. 観点（LLM に守らせる業務ルール）

- **原文と要約を対応付ける**：要約には必ず原文リンク（または原文の掲載媒体名・日付）を添える。要約から作った推測を記事の事実として書かない
- **重大度を勝手に判定しない**：「重大な訴訟・行政処罰の該当はありません」のような判定は、記事に書かれている事実（罰金の有無・是正の有無・報道の系統数）から言えることだけを書く。単独の情報源しか無い場合はその旨を明記する
- **審査・与信の可否を出力しない**：ネガティブ情報の有無を伝えるところまでで、「取引を続けてよいか」の判断はしない。「この 1 件をもって取引継続の可否を判断せず、他の与信情報と合わせて評価する」ことを促す
- **配信先の追加は都度確認**：既定の配信先（設定時に選んだ部門）以外への共有は、担当者の明示的な指示があるときだけ行い、共有してよいか確認を返す
- **禁止**：記事に無い事実を推測で補う／個人名を不要に強調する／収集モードで除外したはずの一般ニュースを紛れ込ませる
- **不確実なとき**（入力言語で）：ja「該当する記事が見つかりませんでした。対象先・キーワードを確認してください。」／zh「未找到相关报道。请确认对象与关键词。」
- **出力の粒度**：設定内容の確認 → 直近の収集結果（該当件数・要旨・情報源の数）→ 出力ファイル名 → 確定前の確認（共有可否など）

## 4. Dify 構成

- **アプリ種別**：**Workflow**（フォーム入力 → 実行 → 結果）。定期実行は `PC-11` から同じ Workflow を呼ぶ
- **ノード列**：
  1. `Start`（監視設定 6 項目。§2）
  2. `Code`（監視設定の保存・読込。§8 のストアへ）
  3. `LLM`（軽量）— 対象先・業界・キーワードから検索クエリを組み立てる（zh 主体の記事を拾うため中国語クエリも生成）
  4. 検索ツール（§4 プラグイン）で対象期間（既定 4 週間）の記事を収集
  5. `Code`（重複除去・対象期間での絞り込み）
  6. `LLM`（要約・ネガティブ判定）— 記事ごとに日本語要約、収集モードに応じてネガティブ情報の該当を判定。§5 のプロンプト
  7. `Code`（件数集計・出力ファイルの組み立て）
  8. `HTTP Request`（`PC-13` `POST /render` でファイル出力）
  9. `Answer`（設定内容・収集結果・出力ファイル・確定前の確認）
- **Knowledge**：使わない（KB 化するのは社内文書ではなく都度取得する公開情報のため。過去の収集結果は §8 のストアに構造化データとして残す）
- **プラグイン／ツール**：`tools/searxng` または `tools/google`／`tools/bing`（`../plugins-and-references.md` §2。KN-05・NM-02 で使われているものと同じ）。`Code` ノード（重複除去・期間絞り込み・集計）。`PC-13` へは `http-request`
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（要約・判定）／Qwen3-32B（クエリ組み立て）。中国語記事の要約品質は評価セットで確認する（`PC-08`）
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`（フォーム入力の型）、`../templates/06-text-to-sql-http-api-echarts.yml`（外部取得と集計の型）
- **入出力変数**：

  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `target` | string | ✓ | 対象先（`data/world/fin/clients.csv` の記号または自由入力） |
  | `industry` | string | ✓ | 業界 |
  | `keywords` | string | ✓ | キーワード（複数、区切り文字） |
  | `mode` | select | ✓ | `general` / `adverse_only` |
  | `frequency` | select | ✓ | `weekly` / `monthly` |
  | `distribution` | string[] | ✓ | 配信先部門（`data/world/fin/org.csv` の `dept_id`） |
  | 出力 `summary_ja` | string | ✓ | 日本語要約 |
  | 出力 `hits` | array[object] | ✓ | 該当記事（媒体・日付・要旨・原文リンク） |
  | 出力 `file_url` | string | — | `PC-13` が生成した取引先ごとのファイル |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行の企業・業界ニュース収集アシスタントです。
指定された対象先・業界・キーワードに基づき、収集された公開情報の記事を日本語で要約します。
守ること：
1. 要約は与えられた記事本文からのみ作る。記事に無い事実・数値を作らない。
2. 収集モードが「ネガティブ情報のみ」のときは、訴訟・行政処罰・資金繰り悪化・環境事故など、指定されたキーワードに関連する記事だけを扱う。一般的な好意的な記事は除外する。
3. 重大度は記事に書かれている事実（罰金の有無・是正の有無・情報源の数）からのみ述べる。自分で重大性を格付けしない。
4. 情報源が1系統のみのときは、その旨を必ず明記する。
5. 取引継続の可否・与信の判断はしない。「この情報だけで判断せず、他の与信情報と合わせて評価する」ことを促す。
6. 既定の配信先以外への共有は、担当者の指示があるときだけ行い、共有してよいかを確認する。
7. 該当記事が無いときは「該当する記事が見つかりませんでした。対象先・キーワードを確認してください。」と書く。
8. 言語：要約は日本語が既定。担当者とのやり取りは入力言語（日本語なら日本語、中国語なら中国語）で答える。
出力：見出し（設定内容／直近の収集結果／出力ファイル／確定前の確認）の順で書く。
```

### 5-2. User テンプレート

```text
監視設定：対象={{target}}／業界={{industry}}／キーワード={{keywords}}／モード={{mode}}／頻度={{frequency}}／配信先={{distribution}}
収集した記事（重複除去・期間絞り込み済み。転記のみ）：{{articles_json}}
```

### 5-3. 出力フォーマット（後工程・ファイル出力向け）

```json
{
  "target": "丙社", "mode": "adverse_only", "period_weeks": 4,
  "hits": [ { "source": "地方紙", "date": "2026-06", "summary": "環境規制に関する軽微な行政指導。是正済みと報道", "single_source": true, "url_or_ref": "…" } ],
  "summary_ja": "過去4週間で該当1件。地方紙報道（2026年6月、環境規制に関する軽微な行政指導・是正済み）。重大な訴訟・行政処罰の該当はありません。",
  "file_name": "丙社_ネガティブ情報_週次.pdf",
  "confirm_required": ["配信先の追加（審査部）を含めるか"]
}
```

### 5-4. Few-shot

**不要**。要約対象の記事は毎回異なり、few-shot の文例をそのまま流用すると事実の混入事故が起きる。書式は System と JSON スキーマで固定する。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | 要約が記事本文の事実と一致 ≥ 90% | 評価セット 20 件を人手採点 |
| モード遵守 | `adverse_only` で一般記事が混入 0 件 | 負例セット |
| 単一情報源の明記 | 情報源 1 系統の記事に注記が付く 100% | 自動（フィールド突合） |
| 判断の越境なし | 「取引継続可否」を断定する表現の出現 0 | 禁止語 + LLM-as-judge |
| 言語 | 要約は日本語、やり取りは入力言語 100% | 自動判定（`PC-07`） |
| 拒否 | 該当なしのとき定型文 ≥ 95% | 負例セット |
| 速度 | p95 < 30 秒 | Langfuse（`PC-09`） |

- **評価方法**：リリース前に人手 20 件（うち負例 5 件）。月次で Langfuse のスコアを確認

## 8. 別出しが必要なもの

- **監視設定ストア**（本サービス固有・最優先）：`rs1_watchlist` テーブル（`id`／`target`／`industry`／`keywords`／`mode`／`frequency`／`distribution`／`owner_id`／`updated_at`）。`PC-11` の定期実行はここを読んで対象ごとに Workflow を回す。第 1 段階は `tools/jiandaoyun`／`tools/microsoft_excel_365` の表でも代替できる
- `PC-11`：週次・月次の定期実行。祝日・営業日の考慮は不要（当局報告のような期日制約が無いため）
- `PC-13`：取引先ごとのファイル（PDF）出力
- `PC-14`：社内チャットへの通知（該当ありのときのみ。実在のチャットツール名は使わず一般名で扱う。`docs/handoff/2026-09-08-finance-catalog.md` §7-3）
- **無くても動く範囲**：監視設定ストアが無くても、都度フォームに条件を入れて単発実行すれば動く（定期配信ができないだけ）。`PC-14` が無ければ結果は画面表示のみ

## 9. Outline Wiki との関係

- 使わない。監視設定・収集結果は §8 のストアに構造化データとして持ち、Outline には書かない（個人・取引先の負面情報を Wiki に残すと閲覧範囲の統制が難しくなるため）

## 10. 未確定・リスク

- **実現性を ○ とした理由**：フォーム入力・要約・ファイル出力は Dify 標準機能で足りるが、(1) 監視設定を保存する専用ストアが新規に要る、(2) 検索ツールの中国語ニュースに対する精度・到達性が未検証、の 2 点で ◎ にしていない
- **検索ツールの選定**：`tools/searxng`（自前運用）か `tools/google`／`tools/bing`（SaaS、中国本土からの到達性を要確認）かは実装時に決める。中国国内のニュースサイトへの直接クロールが必要なら `datasources` 系（Knowledge Pipeline 経由）への切り替えも検討
- **配信先の追加運用**：既定の配信先以外への共有を「都度確認」にしているため、頻繁に共有する部門は監視設定自体に追加してもらう運用にすべきか — PM 確認
- **CV-04（KYC）との関係**：CV-04 は本サービスの収集結果（`rs1_ネガティブ情報_丙社.pdf` 相当）を入力の一部として使う（台本参照）。両サービスの出力ファイル形式を合わせる必要がある
