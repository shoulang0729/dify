## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：担当者が能動的に開く。年次の給与改定（10〜12 月）、離職増加の報告があったとき、採用オファー額を決めるとき（PT-05 から）。③業務フィードでは `due`（給与改定の起案期限）
- **登場人物**：管理部 総務・人事 駐在員（照会・改定案の起案）、管理部長（確認）、本社人事（承認）、人事課（等級別集計の提供者）、外部＝人事情報サービス（市場データの提供のみ。当社の個人データは受け取らない）
- **いまの手順（Before）**：現場から「CNC オペレーターの離職が増えている」→ 人事課に等級 G3 の給与一覧（**個人単位**）を出してもらい Excel で中央値を計算（30 分）→ 人事情報サービスのポータルで職種・地域・規模を選び画面を転記（1 時間）→ 位置づけ・改定シミュレーション・費用を Excel で手計算（1 時間）→ 本社人事向けの日本語説明を書く（1 時間）。個人の給与一覧が Excel・メールで出回る
- **エージェント導入後の手順（After）**：(1) 担当者が職種・経験帯・地域・企業規模（＋当社等級）を**入力**する → (2) Dify が `PC-15` 経由で市場水準・手当相場・法定変更を取得し、同時に `PC-04` の**集計専用 API** から当社等級の中央値・人数（n≥5 のみ）を取得 → `code` で位置づけ（P 値）・改定シミュレーション・費用を計算 → KN-03 の KB（給与改定規程）を参照して表と説明を返す → (3) 担当者が**改定率の案を選び**、費用と規程手順を確認する → (4) 担当者が本社人事向け説明文を**確認・修正して送る**（AI は給与マスタに書かない、送らない）
- **成功の定義**：照会〜説明文まで 3.5 時間 → 20 分。**個人の給与データが Dify・Excel・メールのどこにも現れない**。改定案に市場データの出典（更新月・サンプル n）が必ず付く

## 3. 観点（LLM に守らせる業務ルール）
- **個人単位の数値を扱わない・作らない**：当社側は「等級別の中央値・人数・賞与月数・手当額」のみ。個人名・従業員番号・個人の給与が入力に紛れても**出力に転記しない**。「〇さんの給与は」と聞かれたら答えない（定型：「個人の給与は本サービスでは扱いません。人事課の権限者が人事システムで確認してください」）
- **n を必ず表示する**：市場データ（サンプル n、日系サブセット n）と当社集計（n=46）を表に出し、n が小さい比較は「参考値」と書く
- **計算は `code`**：P 値・改定後の位置・費用（基本給×率×人数×12、社保会社負担率）・回収額は `code` の値を転記。LLM が暗算しない
- **法定変更の「解説」は法的助言ではない**：「人事情報サービスの解説」として引用し、「適用の判断は法務・社保代理機構に確認」を添える
- **市場データを過信しない**：日系サブセットが 23 社など小さい場合、偏りの注記
- **改定案は複数提示、決定は人**：「+5%」「+13%（中央値到達）」「折衷（基本給 +5%＋手当是正）」のように並べ、推奨は書いてよいが決定は担当者・本社人事
- **送っていないものを明示**：表の最終行「連携」に「外部へ送信：職種・経験帯・地域・企業規模・等級別中央値（集計値）のみ。**個人の給与・氏名・従業員番号は送信していない**」を必ず書く（PM 決定 PT-10）
- **不確実なときの定型**：ja「人事情報サービスに該当する職種・地域の水準がありません。近い分類（候補）で照会し直すか、条件を広げてください」／zh「人事信息服务中没有对应职种・地区的水平。请用相近分类重新查询或放宽条件」
- **出力の粒度と形式**：表（項目／市場／当社（等級中央値）／位置づけ・備考）9 行＋連携行。改定シミュレーション・説明文は §5-3 の JSON を経て Markdown

## 4. Dify 構成
- **アプリ種別**：**Workflow**（lookup。1 回実行）。追加質問（改定シミュレーション・説明文）は `mode` で分岐した再実行。Chatflow にしないのは、**会話ログに給与関連の数値を多輪で蓄積させない**ため（保持期間管理を単純にする）
- **ノード列**：
  1. Start（`role`, `experience_band`, `region`, `company_size`, `internal_grade`, `mode`, `raise_rate`（`simulate` 時））
  2. `code`（入力の**個人情報スクリーニング**：氏名・従業員番号・個人金額らしき記述を検出したら除去して `pii_flag` を立てる。職種をマッピング表で給与 DB 分類へ変換）
  3. `if-else`（マッピング不可 → 候補提示で終了）
  4. `http-request` ①（`PC-15` 経由：人事情報サービスの水準・手当・昇給率・離職率推定・法定変更解説。送るのは**分類コード・経験帯・地域・規模**のみ）
  5. `http-request` ②（`PC-04`：人事給与システムの**集計専用 API**。`grade` を渡し `{median, n, bonus_months, allowances}` を受ける。n<5 なら null）
  6. `code`（Python）：市場 P 値の位置づけ、改定後位置（市場昇給率織り込み）、中央値到達に要する率、費用（基本給・手当・社保会社負担）、回収額（離職率差×採用コスト）。`calc_json`
  7. `knowledge-retrieval`（KB `hr-rules`＝KN-03 の HR 帯 dataset。フィルタ `doc = 給与改定規程`）
  8. `llm`（§5。表と説明。入力言語）
  9. （`mode=hq_note`）`llm`（日本語の本社向け 1 段落。日本語品質モデル）
  10. `template-transform`（「連携」行の付与）
  11. End（`result_md`, `result_json`）
- **Knowledge**：KB `hr-rules`（KN-03 と共用。HR 帯・メンバー限定 `PC-02`）。**市場データ・当社集計は KB に入れない**（毎回照会。ライセンスと個人情報保護）。等級表は集計 API 側が正
- **プラグイン／ツール**：HTTP リクエストノード（本体）／Code ノード／`tools/regex`（個人情報パターン検出の補助）。通知系は不要
- **モデル**：HR 帯は **越境ゼロ**を優先し `models/ollama` 等のオンプレ Qwen（`PC-08` の HR 帯方針）。オンプレが無い間は SiliconFlow 中国版で**集計値のみ**を扱う前提（個人行は元から載せないため許容範囲だが顧客法務確認）。日本語説明文は DeepSeek-V3.x 等と評価
- **参照 DSL**：`../templates/06-text-to-sql-http-api-echarts.yml`（`http-request` で自前 API を叩く lookup 骨格。SQL 生成部は使わず、集計 API 呼び出しに置き換える）
- **入出力変数**：

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `role` | string | ✓ | 職種（自由記述 → マッピング） |
| `experience_band` | select | ✓ | `0-2` / `3-5` / `6-10` / `10+` |
| `region` | string | ✓ | 地域（蘇州 等） |
| `company_size` | select | ✓ | 従業員規模帯 |
| `internal_grade` | string | — | 当社等級（無ければ当社列を出さない） |
| `mode` | select | ✓ | `lookup` / `simulate` / `hq_note` |
| `raise_rate` | number | — | `simulate` 時の改定率 |
| `pii_flag` | bool | 内部 | 入力に個人情報らしき記述があった |
| `result_md` / `result_json` | string / object | 出力 | 表＋連携行／§5-3 |

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）管理部の給与水準照会アシスタントです。
入力として (A) 人事情報サービスから取得した市場データ（中央値・四分位・サンプル数・手当相場・昇給率・離職率推定・法定変更の解説）、(B) 当社の等級別集計値（中央値・人数・賞与月数・手当。個人の行は含まれない）、(C) code が計算した位置づけ・シミュレーション・費用、(D) 社内規程「給与改定規程」の該当条項、が与えられます。

守ること：
1. 個人単位の情報を扱わない。入力や会話に氏名・従業員番号・個人の金額があっても出力に書かない。個人の給与を尋ねられたら「個人の給与は本サービスでは扱いません。人事課の権限者が人事システムで確認してください」と答える。
2. 数値は (A)(B)(C) にあるものだけを転記する。計算し直さない・丸めない。無いものは「データなし」。(B) が null（人数が少ない）なら当社列を出さず、その理由（個人が特定され得る）を書く。
3. 表は「項目｜市場（人事情報サービス）｜当社（等級 {{internal_grade}} 中央値）｜位置づけ・備考」の 4 列。市場と当社の両方にサンプル数 n を書く。n が小さい比較は「参考値」と書く。
4. 最終行は必ず「連携」行：取得元・更新月・「外部へ送信したのは職種・経験帯・地域・企業規模・等級別中央値の集計値のみ。個人の給与・氏名・従業員番号は送信していない」・当社集計の対象人数・参照した規程条項。
5. 法定変更は「人事情報サービスの解説」として引用し、「適用判断は法務・社保代理機構に確認」を添える。法的助言をしない。
6. 改定案は複数（例：一律 +N%／中央値到達／基本給＋手当是正の折衷）を並べ、費用と位置づけを (C) から転記する。推奨は書いてよいが「決定は担当者と本社人事」の文体。改定手順は (D) の条項番号を引く。
7. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。本社人事向け説明文（mode=hq_note）だけは常に日本語・敬体・1 段落・数値に出典（人事情報サービス、更新月）と「個人データは社外に出していない」旨を含める。
8. 該当なしの定型：「人事情報サービスに該当する職種・地域の水準がありません。近い分類（候補）で照会し直すか、条件を広げてください」／中国語「人事信息服务中没有对应职种・地区的水平。请用相近分类重新查询或放宽条件」。
9. パートナーは「人事情報サービス」（給与 DB）と呼ぶ。実名・製品名を作らない。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（転記） | 表・シミュレーションの数値が `calc_json`／API 応答と一致 100% | 自動突合 |
| 網羅 | 表 9 行＋連携行、n の表示、規程条項の引用 100% | チェックリスト |
| 言語 | 入力言語で返答 100%、`hq_note` は日本語 100% | 自動判定（`PC-07`） |
| 形式 | `result_json` スキーマ準拠 100%。個人識別子フィールドが**存在しない** | JSON バリデータ＋スキーマ禁止キー検査 |
| 拒否 | 個人給与の質問を 100% 拒否。n<5 で当社列を出さない 100% | 負例セット 20 件 |
| **安全（送信最小化）** | `PC-15` 送信ログに個人名・従業員番号・個人金額 0 件。送信キーが分類コード・経験帯・地域・規模・（集計中央値）に限られる 100% | 送信ログ監査（自動・毎実行） |

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-15`**：人事情報サービスとの契約（データ利用範囲、更新頻度、課金）。送信**ホワイトリスト＝職種分類コード・経験帯・地域・企業規模（＋任意で等級中央値）**。それ以外のキーは`PC-15` で落として監査ログに記録。海外事業者なら**越境提供評価**（集計値が個人情報に該当しないことの法務確認。PIPL 第 38 条）。中国国内事業者を優先
- **`PC-10`**：社内給与は**敏感個人情報に準ずる扱い**（PIPL 第 28 条の趣旨）。方針：Dify に個人行を載せない設計を第一とし、ログ（会話・ノード入出力・Langfuse）に集計値以外が残らないマスク設定、保持期間（例 90 日）、HR 帯限定。**従業員への告知**（就業規則・個人情報告知書に「給与水準の集計値を外部ベンチマークと比較する」旨があるか）を法務が確認
- **`PC-04`**：人事給与システムの**集計専用 API**（等級・職種で中央値・人数・賞与月数・手当額を返す。n<5 は null。個人行を返すエンドポイントを**持たない**）。無い場合は人事課が月次で集計表（CSV、集計値のみ）を出し `code` で読む暫定案
- **`PC-02`**：HR 帯ロール（管理部 総務・人事、人事課長、管理部長）。SSO 属性
- **職種マッピング表**：当社職種・等級 ⇄ 人事情報サービスの職種分類。人事課が作成（`PC-06` に載せるか専用表かは未確定）
- **無くても動く範囲（段階導入）**：
  - 段階 0（契約前・集計 API 前）：`PC-15` モック＋集計 API モック。表・計算・PII スクリーニング・連携行の確認とデモ。**実データは触らない**
  - 段階 1：人事情報サービス接続。当社側は人事課の月次集計 CSV（集計値のみ）
  - 段階 2：集計専用 API 接続、`hq_note`、PT-05（採用オファー額）からの参照
  - 段階 2 まで到達し法務レビューを通るまで成熟度は st3 のまま

## 9. Outline Wiki との関係
- **読む**（`PC-05`）：「人事／規程」の給与改定規程・等級表・手当規程（KN-03 の HR 帯 dataset と共用。メンバー限定コレクション）。離職・採用コストの社内試算表（あれば）
- **書く**：**書かない**。市場データはライセンス上、当社集計値は個人情報に近いため Outline に残さない。本社人事向け説明文は `PC-13` で人事共有フォルダ（アクセス制御あり）に出力し、保存の実行は担当者
- 使わない理由の補足：Outline のコレクション権限は KB 同期の単位としては十分だが、給与関連の「結果」を蓄積する場所としては監査・保持期間の管理がしにくい

## 10. 未確定・リスク
- **人事情報サービスの API と契約**：未確定。日系サブセット等のサンプル偏りは表に n を出して対処
- **集計専用 API の有無**：顧客の人事給与システム次第。無ければ暫定 CSV。architect 推奨：**API ができるまで段階 1 で止め、st3 を維持**
- **越境**：海外事業者の場合、集計値でも「個人情報に該当しない」ことの法務確認が要る（PM／顧客法務）。中国国内事業者なら評価は軽い
- **モデルの所在**：HR 帯は `PC-08` のオンプレ方針待ち。集計値のみなら SiliconFlow 中国版でも許容範囲だが、顧客法務の確認事項として明示
- **従業員への告知・同意**：就業規則・告知書の文言確認（顧客人事・法務）。無ければ告知文の追加が先
- **PT-05 との接続**：採用オファー額の妥当性確認に PT-04 の市場中央値を使う。個人（候補者）の希望給与を PT-04 に渡すのではなく、**PT-05 側で市場中央値を参照する**方向にする（PT-04 に個人データを近づけない）
- **KN-03 との重なり**：規程 QA は KN-03。PT-04 は市場比較と改定シミュレーションに限定し、規程の解釈質問は KN-03 へ誘導
