## 1. 業務シナリオ
- **トリガー**：担当者が能動的に開く（本社文書の現地展開、現場報告の本社共有、チャットの即時翻訳）。②ダッシュボードで「よく使う」筆頭（利用件数最多）
- **登場人物**：依頼者＝翻訳を必要とする全員、確認者＝用途による（現場掲示なら班長、本社送付なら駐在員）、**用語集管理者**（生産技術 王 磊。登録候補の承認）
- **いまの手順（Before）**
  1. 通訳（秘書）に依頼が集中。技術文書 1 枚に 30〜60 分。順番待ちで半日遅れることも
  2. 汎用の機械翻訳を使うと「治具→夹具」「赤札→红牌」のように社内の別物と混同する訳が出る
  3. 同じ語を人によって違う訳で出し、LG-02 の「呼称の揺れ」を増やしている
  4. 新しい社内語（「技術連絡書」）の訳が決まらないまま各自が訳す
- **エージェント導入後の手順（After）**
  1. 【入力】方向（自動判定可）・用途（掲示／メール／技術文書／チャット）・原文をフォームに入れる
  2. 【生成】用語集に揃えた訳文、用語対応表（用語 ID 付き）、訳語候補が複数ある語の根拠付き併記、**用語集未登録語の登録候補（登録形式）**が返る
  3. 【確認】依頼者が訳文を確認。用途変更（掲示 → 朝礼読み上げの口語版）は対話で
  4. 【決める】訳文の採用は依頼者。**用語集への登録は用語集管理者が承認**（AI は登録しない。`docs/handoff/2026-09-06-pm-decisions.md` §2）
  5. 【蓄積】承認済み訳文ペアは `PC-06` の翻訳メモリへ（人が承認したものだけ）
- **成功の定義**：技術文書 1 枚 30〜60 分 → 5 分＋確認。用語集違反の訳 0（自動照合）。通訳への依頼の 6 割が本サービスへ移る

## 3. 観点（LLM に守らせる業務ルール）
- **用語集の承認済み訳語を必ず使う**。`avoid` 欄にある訳語（夹具・红牌・半成品）は使わない。用語対応表に `term_id` を付ける
- 用語集に無い専門語は**翻訳メモリの訳**を優先し、それも無ければ一般訳を出して**「用語集未登録」として登録候補に挙げる**（ja/zh/en・分類・備考・出典の登録形式）。AI は登録しない
- 訳語候補が複数あるときは併記し、用途に応じた採用理由を 1 行（規定文向き／口語）。**黙って一つに決めない**
- 品番・管理番号・数値・単位・日付は訳さない・変えない（SK-3310-A、TN-25-031、30 分）
- 文体は用途に従う：掲示＝短文・命令形、朝礼＝口語、メール＝敬体／商務中文、技術文書＝規定文。用語は用途が変わっても**同じ**にする
- 原文に無い情報を足さない（「安全のため」等の補足を勝手に入れない）。原文の誤りに気づいたら訳文は原文どおりにし、「※原文確認」を付ける
- 個人情報（`PC-10`）：原文に含まれる氏名・電話・メールは訳文でもそのまま**転記せず**「[氏名]」等に置換するかを用途で判定（社内チャットは保持可、掲示・社外メールは置換）。Code のマスク結果 `{{masked}}` に従う
- 不確実時の定型：「この語の社内訳が確定していません。候補を併記しました。用語集管理者に確認してください」／「该词的公司内部译法尚未确定，已并列候选，请与术语表管理者确认」
- 出力形式：訳文 → 用語対応表 → 複数候補 → 登録候補（登録形式）→ §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（フォーム → 2 段 LLM → 構造化出力）。口語版などの再依頼は `question` 付き再実行（前回訳文を渡す）。チャット即時翻訳の入口（WeCom bot）は第 2 段階で Chatflow 版を追加
- **ノード列**
  1. `start`：`source`, `direction`（auto/ja2zh/zh2ja）, `purpose`, `question`（任意）, `prev_translation`（任意）
  2. `code`（前処理）：`PC-07` の言語判定 → `in_lang`/`out_lang`。品番・番号・数値の保護トークン化。`PC-10` マスク。原文の語を用語集 CSV と照合し出現語だけ `{{glossary}}` に整形
  3. `knowledge-retrieval`：KB `lg1-translation-memory`（原文の文単位で類似検索、top 5）
  4. `llm`（翻訳）：System §5-1。用語集・翻訳メモリを context に。保護トークンを維持
  5. `llm`（用語チェック）：訳文を用語集と再照合、`avoid` 語の検出、複数候補の併記、未登録語の抽出 → 登録形式
  6. `code`（後処理）：保護トークンを戻す、用語集違反の機械チェック（`avoid` 語の有無）、JSON 整形
  7. `end`：`translation`, `term_table`, `alternatives`, `glossary_candidates`, `result_json`
- **Knowledge**：`lg1-translation-memory`（承認済み訳文ペア。`PC-06` が投入。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`）。用語集は KB ではなく **CSV 注入**（`PC-06` の (2)。検索漏れを避けるため）
- **プラグイン／ツール**：なし（本体ノードのみ）。トークン節約に `tools/baidu_translate`／`deepl` を 1 段目に置き LLM で用語統一する 2 段構成も可（Awesome「DuckDuckGo翻译+LLM二次翻译」方式。原文が外部に出る点は `PC-08` で判断）。用語集への書き込み（Knowledge API を `http-request` で）は**初期構成に含めない**
- **モデル**：Qwen3-235B-A22B-Instruct（日中双方向）。zh→ja の本社向け敬体は DeepSeek-V3.x と比較評価（`PC-08`）
- **参照 DSL**：**`../templates/01-translation-reflection-workflow.yml`**（直訳 → 専門家提案 → 改善訳。段 4→5 の型）、`../templates/04-trilingual-consistency-checker.yml`（用語一致チェック）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `source` | paragraph | ✓ | 原文 |
| `direction` | select | ✓ | auto / ja2zh / zh2ja |
| `purpose` | select | ✓ | 掲示／朝礼／メール／技術文書／チャット |
| `question` | paragraph | — | 再依頼（口語版・登録形式で出す 等） |
| `prev_translation` | string | — | 前回訳文 |
| `translation` | string | 出力 | 訳文（`out_lang`） |
| `term_table` | array | 出力 | 用語対応（`term_id` 付き） |
| `alternatives` | array | 出力 | 複数候補と採用理由 |
| `glossary_candidates` | array | 出力 | 登録形式の候補 |
| `result_json` | object | 出力 | §5-3 |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工（蘇州）の社内翻訳者です。日本語と中国語を双方向に翻訳し、社内用語集の言い方に揃えます。
守るルール：
- 訳文は {{out_lang}} で書く（ja2zh なら中国語、zh2ja なら日本語）。説明・用語対応・候補の解説は原文の言語 {{in_lang}} で書く。
- 用語は {{glossary}}（term_id, ja, zh, en, avoid）の承認済み訳語を必ず使う。avoid にある語は使わない。用語対応表に term_id を付ける。
- 用語集に無い専門語は {{context}}（翻訳メモリ）の訳を優先。無ければ一般訳を出し、「用語集未登録」として登録候補に挙げる（登録形式：ja／zh／en／分類／備考（使わない訳語）／出典）。登録は行わない。
- 訳語候補が複数あるときは併記し、用途 {{purpose}} に応じた採用理由を 1 行書く。
- 保護トークン（⟦P1⟧ 等）はそのまま残す。数値・単位・日付は変えない。
- 文体は用途に従う（掲示＝短文・命令形／朝礼＝口語／メール＝敬体・商務中文／技術文書＝規定文／チャット＝平易）。用途が変わっても用語は変えない。
- 原文に無い情報を足さない。原文の誤りは訳文で直さず「※原文確認」を付ける。
- {{masked}} に置換指示がある個人情報は訳文でも置換のまま。
- 社内訳が確定しない語は「この語の社内訳が確定していません。候補を併記しました。用語集管理者に確認してください」と書く。
出力：訳文 → 用語対応表 → 複数候補 → 登録候補 → 区切り線 → JSON（指定スキーマ）。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 用語準拠 | 用語集の承認語の使用率 100%、`avoid` 語の出現 0 | Code の自動照合（`violations`） |
| 訳の正確性 | 意味の誤り 0、抜け・付け足し 0 | 評価セット 40 文（ja→zh 20・zh→ja 20）をバイリンガル 2 名が採点 |
| 保護 | 品番・番号・数値の改変 0 | 自動（保護トークン照合） |
| 言語 | 訳文＝`out_lang`、説明＝`in_lang` 100% | 自動判定（`PC-07`） |
| 候補提示 | 多義語で候補併記 ≥ 90% | 多義語 20 件のセット |
| 登録候補 | 未登録専門語の抽出率 ≥ 90%、誤抽出 ≤ 10% | 人手 |
| 速度 | p95 < 20 秒（500 字） | Langfuse（`PC-09`） |
| 安全 | 掲示・社外用途での個人情報転記 0 | 負例セット |

- **評価方法**：リリース前に評価セット 40 文で人手採点。運用後は `violations` 件数と用語集管理者の候補承認率を月次で確認（`PC-09`）

## 8. 別出しが必要なもの
- `PC-06`：用語テーブル（`approved`/`candidate`）と注入 CSV 生成、翻訳メモリ KB。**正本は用語集管理者（生産技術）が Outline「用語集」で持つ**（LG-02 §9 と同じ）
- `PC-07`：言語判定・方向決定・保護トークン化の共通 Code
- `PC-10`：用途別のマスク規則（掲示・社外は置換、社内チャットは保持）
- `PC-05`：登録候補を「用語集 › 候補」に下書き（`publish: false`）
- **無くても動く範囲**：System に用語 30〜50 語を直書き → 訳文＋用語対応まで。翻訳メモリ・候補の Outline 下書き・WeCom 入口は段階導入

## 9. Outline Wiki との関係
- **読む**：「用語集」コレクション（`PC-06` の正本。承認済み用語 → 注入 CSV）。用途別の文例（「本社向けメール定型」）を置くなら「翻訳 › 文例」
- **書く**：`glossary_candidates` を「用語集 › 候補 › YYYY-MM」に**下書き**（`PC-05`。publish は用語集管理者）。**訳文そのものは Outline に書かない**（依頼者が用途先に貼る）。Outline ページの日中同期（OW-04）は本サービスの入口追加として扱う（`../outline-wiki-usecases.md` O-7 推奨案 (c)）
- 用語集の更新 → Webhook → 注入 CSV 再生成（`PC-05`＋`PC-06`）
