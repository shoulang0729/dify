## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：月末〜月初の精算締め（③業務フィードの `routine`）。個別申請の随時チェックも同じアプリ
- **登場人物**：財務経費担当（照合結果の確認・差し戻し送信・承認）、財務課長（例外承認）、申請者（差し戻し対応）、所属長（事前承認）
- **いまの手順（Before）**：60 件の申請一覧（Excel）と発票（PDF 束）を 1 件ずつ目で照合：抬頭・税号・金額・日付・規程上限・事前承認（1 件 5〜10 分＝合計 1 日）→ 見落としが監査で指摘 → 差し戻し文を個別に書く（非定型で時間がかかる）
- **エージェント導入後の手順（After）**：
  1. 担当者が**精算申請一覧（xlsx）と発票 PDF 束をアップロード**
  2. `PC-03` が発票を 1 枚ずつ OCR（抬頭・税号・金額・日付・品目）→ **`PC-10` で身分証・電話・口座をマスク** → 抽出 JSON
  3. **Code ノードで**申請と照合：金額一致・抬頭一致・税号一致・日付整合・**規程ルール（コード化済み）**：接待 1 人上限・事前承認閾値・外貨の社内レート換算・回数上限
  4. LLM が検出事項を**規程 KB の条文番号を引いて**説明し、差し戻し文（申請者の言語）をドラフト
  5. **人が決める場所**：差し戻し／承認／例外承認は財務担当・課長。**エージェントは承認しない・送信しない**（送信は人がボタン）
  6. 結果一覧を `PC-13` で xlsx 出力
- **成功の定義**：60 件の一次チェック 1 日 → 1 時間（確認のみ）。抬頭・税号・上限超過の見落とし 0。差し戻し文が規程条文付きで統一される

## 3. 観点（LLM に守らせる業務ルール）
- **判定は Code**：金額一致・上限超過・換算・回数はコード化ルールの結果。LLM は結果の説明と文面作成のみ。金額・差額を計算しない
- **規程を引くときは条文番号と原文**（「規程 §6.2：接待費は 1 人 RMB 300 を上限」）。KB に無い規程を作らない
- **個人情報**（`PC-10`）：出力には**社員 ID と姓のみ**（「李 課長」可、フルネーム・身分証・電話・口座・住所は出さない）。発票の個人名抬頭は「個人名」と記し氏名を転記しない
- **税務・法的助言をしない**：「発票の真偽」「税務上の可否」は判定せず「税務総局の照会または税理士確認」と案内
- **差し戻し文は丁寧・定型**：事実（何が・規程のどこに）→ 依頼（何を提出）→ 期限。責める表現なし
- **禁止**：承認・却下を決定したと書く／申請者の傾向を評価する（「よく間違える人」）／規程の閾値を推定する
- **不確実時の定型文**：「この申請は規程の該当条文が特定できません。財務課長の判断をお願いします」
- **出力形式**：結果一覧（申請番号／申請者（ID・姓）／内容／金額／検出事項（条文）／判定候補）＋差し戻し文ドラフト。後工程は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（月次一括）。台本 Q1（差し戻し文）Q2（履歴の傾向）は結果 JSON を会話変数に持つ **Chatflow** 版で第 2 段階（Q2 は精算履歴 API が前提・st2 相当）
- **ノード列**：
  1. Start（`claims` file（xlsx）必須／`receipts` file-list（pdf/jpg）必須／`period` text／`fx_month` text 任意）
  2. Document Extractor（claims → 行 JSON）→ **Code（`mask`、`PC-10`）**：氏名→姓＋ID、身分証 18 桁・電話 11 桁・口座を `[ID]`/`[TEL]`/`[ACCT]` に置換
  3. Iteration（receipts）→ If/Else（電子発票 PDF はテキスト抽出／画像は `tools/paddleocr`）→ LLM（`extract_receipt`、小型）：抬頭・税号・金額・税率・日付・品目 JSON。マスク適用
  4. **Code（`match_and_check`）**：申請⇄発票の対応（申請番号／金額＋日付）、金額一致、抬頭＝会社名一致、税号一致、日付整合、外貨換算（社内レート）、規程ルール JSON（上限・閾値・回数）で判定 → `findings[]`
  5. Knowledge Retrieval（KB `gn-expense-rules`、クエリ＝finding の rule_id／キーワード。Iteration 内）
  6. LLM（`explain`）：検出事項の説明（条文引用）・判定候補・差し戻し文ドラフト（申請者言語）（§5）
  7. Code → xlsx/CSV（`PC-13`）／End（`results` JSON・`report_md`）
- **Knowledge**：`gn-expense-rules`（Outline「経費規程」「出張規程」「発票要件」同期。条文単位チャンク、メタ `section`）。申請・発票データは **KB に入れない**（個人情報・一過性）
- **プラグイン／ツール**：`tools/paddleocr`（Baidu AI Studio トークン。**発票画像が Baidu に出る**→ 顧客法務確認。回避は `tools/mineru` 自前デプロイ）／Document Extractor・Code（本体）／`tools/json_process`（任意）／`tools/microsoft_excel_365`（結果保存、任意）／`tools/jiandaoyun`（精算台帳が简道云なら）／`tools/email`（差し戻し送信：**人が確認後にボタン**、任意）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（説明・文面）、`extract_receipt` は Qwen3-32B（60〜120 回呼ぶ）。**人事・経費データは越境ゼロ構成（`models/ollama` Qwen）が選択肢**（`PC-08`、F-4）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（xlsx→Code→LLM）、`../templates/08-mineru-pdf-parse-demo.yml`（PDF 解析 tool＋iteration）。URL 参照：dify-for-dsl 61（発票批量→Excel）、difyhub `smart-recipe-recognition`（OCR→JSON→Excel の型）
- **入出力変数**：`claims` file 必須／`receipts` file-list 必須／`period` string／`fx_month` string 任意／出力 `results` object・`report_md` string・`return_drafts` array

## 5. プロンプト
### 5-1. System（`explain`）
```text
あなたは青嶺精工 蘇州工場 財務課の経費精算チェック補助です。Code ノードが判定した検出事項（findings）と規程 KB の条文を使い、担当者向けの説明と、申請者への差し戻し文ドラフトを作ります。
守ること：
1. 金額・差額・換算・回数は findings の値をそのまま転記する。自分で計算しない。
2. 規程は KB の条文番号と原文を引用する。KB に無い規程・閾値を書かない。該当条文が無ければ「規程に該当条文なし。財務課長の判断」と書く。
3. 個人情報：申請者は「姓＋役職」または社員 ID で書く。フルネーム・身分証番号・電話・口座・住所・個人名の抬頭の氏名を書かない（入力に [ID] [TEL] 等のマスクがあればそのまま残す）。
4. 発票の真偽・税務上の可否を判定しない。必要なら「税務総局の発票査験または税理士確認」と案内する。
5. 「承認」「却下」を決定しない。「判定候補：差し戻し／確認／問題なし」と書く。
6. 差し戻し文は申請者の言語（applicant_lang）で、事実→規程条文→依頼（提出物）→期限の順。丁寧に、責めない。
7. 申請者の傾向や人物評価を書かない。
8. 出力言語（説明部分）：担当者の質問言語。日本語なら日本語、中国語なら中国語。
出力形式：「結果一覧」表（申請番号｜申請者｜内容｜金額｜検出事項（条文）｜判定候補）→「差し戻し文ドラフト」（申請番号ごと）→「要判断（課長）」。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| OCR 抽出 | 抬頭・税号・金額・日付の抽出一致 ≥ 95% | ダミー発票 60 枚を人手採点 |
| 判定の正確性 | Code の findings が正解ラベルと一致 100%（ルール判定は決定的） | 評価セット 60 件 |
| 規程引用 | 条文番号が KB に存在 100%、閾値の捏造 0 | 自動（KB 照合）＋負例 |
| 個人情報 | フルネーム・身分証・電話・口座の出力 0 | 負例（架空値混入）で文字列検査 |
| 転記の忠実性 | 説明の数値が findings と一致 | 自動 |
| 言語 | 説明＝担当者言語、差し戻し文＝申請者言語 100% | 自動判定 |
| 法的助言の抑制 | 発票真偽・税務可否の断定 0 | LLM-as-judge |
| 速度 | 60 件で p95 < 6 分 | Langfuse |

- **評価方法**：リリース前に財務 2 名で 60 件（ダミー）。月次で Langfuse データセット（個人情報は自動、規程引用は自動、文面は人手抜取）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **規程ルールのコード化**（財務＋implementer）：上限・閾値・回数・費目分類を JSON に。Outline の条文と 1:1 で `rule_id` を対応（`PC-05`）
- **OCR 基盤の越境判断**（`PC-10`／`PC-03`）：`tools/paddleocr`（Baidu）に発票画像を送ってよいか。NG なら `tools/mineru` 自前
- **マスク共通スニペット**（`PC-10`）：氏名リストは人事マスタから（`PC-04`）
- **社内為替レート・精算履歴 API**（`PC-04`、任意）：履歴分析（台本 Q2）は財務ロール限定（`PC-02`）
- **差し戻し送信**（`PC-14`）：`tools/email` or WeCom。人が確認後にボタン
- **無くても動く範囲**：規程 JSON（上限 5 項目）＋OCR＋Code 照合＋説明 で **単票〜月次チェックは動く**（st1 の中身）。履歴分析・自動送信は後付け
