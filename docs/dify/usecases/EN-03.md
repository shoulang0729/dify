## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：顧客から新規引合（RFQ）の図面が来たとき、生産技術・営業が能動的に開く。③業務フィードでは `due`（RFQ 回答期限）
- **登場人物**：生産技術主任（検索・流用判断）、営業（見積初期検討）、金型保全（金型の実物確認）、外部：顧客 K 社（図面の発行元）
- **いまの手順（Before）**：「似た部品を作った気がする」をベテランの記憶に頼る → 図面フォルダを図番順に開いて目で探す（半日、見つからないことが多い）→ 終了品の金型が倉庫にあることに気づかず新規金型で見積 → 不具合履歴は別の人に聞く
- **エージェント導入後の手順（After）**：
  1. 担当者が**引合図面（PDF）をアップロード**
  2. `PC-03` が図面から**テキスト特徴**（表題欄：品名・材質・板厚・外形・表面処理／寸法・穴・ねじ・曲げの注記）を OCR で、**形状特徴**（外形タイプ・曲げ数・穴数・リブ・対称性）を **Vision LLM** が定型 JSON で記述
  3. 特徴 JSON をクエリに過去図面 KB（同じ手順で特徴化済み）を検索（ハイブリッド）。Code が**一致要素の機械的な一致率**（属性ごとの一致／不一致）を計算
  4. `PC-04` から上位候補の工程・原価・不具合履歴・金型保管場所を引き、LLM が「一致した要素／相違点／流用候補」を表に整理
  5. **人が決める場所**：類似の妥当性・金型改造の可否・見積への反映は生産技術と金型保全が**実物を見て**決める。エージェントは「候補と根拠（一致・不一致の項目）」まで。**類似度の数値は「属性一致率」であって形状の幾何学的類似ではない**ことを毎回表示
- **成功の定義**：候補探索 半日 → 5 分。終了品の金型流用の見逃し 0（台帳照会が毎回付く）。過去不具合の予防項目が見積の技術確認事項に毎回転記される

## 3. 観点（LLM に守らせる業務ルール）
- **類似度は Code が計算した属性一致率**（材質・板厚・外形タイプ・寸法帯・曲げ数・穴/ねじ・表面処理・リブ の重み付き一致）。LLM が「87%」等の数値を作らない。表示は「属性一致率（形状の幾何学的類似ではない）」の注記付き
- **一致した要素／相違点は特徴 JSON の項目単位で列挙**（「外形 L 型 195×80 一致／板厚 t1.2 vs t1.5 相違」）。JSON に無い特徴を語らない
- **工程・原価・不具合・金型は台帳（`PC-04`）の値を転記**。改造費・削減額の試算はしない（台本 Q1 の金額は構想上の演出。本番では生産技術が見積）
- **流用候補は「候補（実物確認要）」**。金型の摩耗状態・改造可否は判断しない
- **禁止**：図面を外部 API（海外の埋め込み・Vision）へ送る／顧客図面の内容を他顧客の検索結果説明に混ぜる／原価を顧客向け文書に転記する
- **不確実時の定型文**：「本結果は属性一致率に基づく候補です。形状の同一性・金型流用の可否は実物と CAD で確認してください」（毎回末尾）
- **出力形式**：候補表（順位／過去図面／属性一致率／一致した要素／相違点／工程・原価・不具合履歴／金型・治具）＋流用候補＋予防すべき不具合（台帳の履歴から転記）。後工程は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（図面 1 件→候補表）。深掘り（「D-092 の改造で」「不具合履歴で気を付けること」）は結果 JSON を持つ Chatflow 版で第 2 段階
- **ノード列**：
  1. Start（`drawing` file 必須／`instruction` paragraph 任意／`top_k` number 既定 3）
  2. `tools/paddleocr`（PP-StructureV3 または PaddleOCR-VL：表題欄・注記・寸法テキスト）— 代替 `tools/mineru`／`tools/somark`（製造業図面を明示）
  3. LLM（Vision、`describe_shape`）：ページ画像 → 形状特徴 JSON（§5-1）。**自前 Vision モデル**（`models/ollama` の Qwen2.5-VL 等、`PC-08`）。SiliconFlow の Qwen2.5-VL は中国インフラ経由になる点を法務確認
  4. Code（`feature_merge`）：OCR＋Vision を 1 つの特徴 JSON に正規化（単位・材質記号・寸法帯）
  5. Knowledge Retrieval（KB `en-drawings`：過去図面の特徴テキスト、ハイブリッド検索＋メタデータフィルタ 材質／板厚帯、top-k 10）
  6. **Code（`match_score`）**：候補ごとに属性一致率を重み付き計算（`match_pct`）、一致・不一致リスト
  7. HTTP Request（`PC-04`）：上位 `top_k` の図番で台帳（工程・原価・不具合・金型・治具）
  8. LLM（`compose`）：候補表・流用候補・予防項目（§5）
  9. End（`candidates` JSON／`report_md`／`query_features` JSON）
- **Knowledge**：`en-drawings`（Knowledge Pipeline：データソース＝図面サーバ（SharePoint／COS）→ 同じ OCR＋Vision 特徴化 → 1 図面 1 チャンク（特徴テキスト＋JSON）。メタ：`drawing_no`／`customer`／`status`／`material`／`thickness`／`year`）。**v1.11.0 のマルチモーダル埋め込み（画像⇄画像）**は `models/jina` 等の海外 API 前提のため**既定では使わない**（`PC-10`）。自前で画像埋め込みを提供できる場合のみ追加
- **プラグイン／ツール**：`tools/paddleocr`（Baidu AI Studio トークン要。**図面の外部送信になる**→ 自前 OCR（`tools/mineru` 自前デプロイ／`tools/somark` 私有デプロイ）を優先検討）／Code・HTTP（本体）／`tools/dify_extractor`（KB 投入）
- **モデル**：Vision＝**自前 Qwen2.5-VL（`models/ollama`／`openai_api_compatible`）**を既定。テキスト LLM＝`models/siliconflow` Qwen3-235B（特徴 JSON と台帳値のみを渡す＝図面画像は送らない）。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`
- **参照 DSL**：`../templates/08-mineru-pdf-parse-demo.yml`（PDF 解析 tool ノード）、`../templates/03`（question-classifier→KB の構成参考）。事例：`../plugins-and-references.md` §11 Dify v1.11.0 多模态検索（53AI）
- **入出力変数**：`drawing` file 必須／`instruction` string 任意／`top_k` number／出力 `candidates` array・`query_features` object・`report_md` string・`ocr_confidence` number

## 5. プロンプト
### 5-1. System（Vision `describe_shape`）
```text
あなたは板金プレス部品の図面を読み、形状特徴を定型 JSON で記述する検査員です。図面画像に描かれていることだけを書きます。推測しない。読めない項目は null。
出力 JSON：{"outline_type": "L|U|Z|flat|box|other", "bends": 整数|null, "bend_radius_mm": [数値], "holes": {"round": 整数, "threaded": [{"size": "M6", "count": 2}], "slots": 整数}, "ribs": 整数, "overall_mm": {"l": 数値, "w": 数値, "h": 数値|null}, "symmetry": "none|mirror|rotational", "surface": "paint|plating|none|unknown", "notes_text": ["注記の原文"]}
出力は JSON のみ。
```
### 5-1b. System（`compose`）
```text
あなたは青嶺精工 蘇州工場 生産技術課の図面類似検索アシスタントです。Code ノードが計算した候補（属性一致率・一致/不一致項目）と台帳（工程・原価・不具合・金型）の JSON を、候補表と流用候補に整理します。
守ること：
1. 一致率・寸法・原価・件数は JSON の値をそのまま転記する。計算しない。一致率は必ず「属性一致率（形状の幾何学的類似ではない）」と注記する。
2. 一致した要素・相違点は matched/unmatched の項目だけを列挙する。JSON に無い特徴を書かない。
3. 工程・原価・不具合・金型は ledger の値のみ。ledger が null の項目は「台帳なし」。
4. 流用候補は「候補（実物確認要）」と書く。改造費・削減額を試算しない。
5. 予防すべき不具合は ledger.defects の履歴を転記し、新規品との共通要素（材質・工程・表面処理）を添える。原因を推測しない。
6. 原価は社内向け表示。顧客向け文書に転記しないよう「社内限」を付ける。
7. 出力言語：指示の言語で答える。日本語なら日本語、中国語なら中国語。図面注記は原文のまま。
8. 末尾に「本結果は属性一致率に基づく候補です。形状の同一性・金型流用の可否は実物と CAD で確認してください」を入れる。
出力形式：「読み取った特徴」→「候補」表（順位｜過去図面｜属性一致率｜一致した要素｜相違点｜工程・原価・不具合｜金型・治具）→「流用候補」→「予防すべき不具合」。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 特徴抽出 | 表題欄（材質・板厚・外形）の抽出一致 ≥ 90%、形状 JSON（外形タイプ・曲げ数・穴数）≥ 80% | ダミー図面 30 枚を人手採点 |
| 検索の再現率 | 「同一系列の既知ペア」20 組で正解が上位 3 位以内 ≥ 80% | 評価セット（既知の派生品ペア） |
| 一致率の再現性 | 同じ図面 2 回で `match_pct` 同一 | 自動 |
| 転記の忠実性 | 表中の数値が JSON と全件一致 | 自動 |
| 注記 | 「属性一致率」注記・末尾定型文 100% | 自動 |
| 越境 | 図面画像が外部 API に出ていない（ネットワークログ） | 監査（`PC-10`） |
| 秘匿 | 原価に「社内限」、他顧客図番の説明に当該顧客名なし | 文字列検査 |
| 速度 | 1 図面で p95 < 90 秒 | Langfuse |

- **評価方法**：リリース前に生産技術 2 名で 30 枚＋既知ペア 20 組。KB 初回投入（1,240 件）後に再現率を測り閾値を決める

## 8. 別出しが必要なもの（このサービス固有の準備）
- **過去図面 1,240 件の一括特徴化**（`PC-03`）：OCR＋Vision の Knowledge Pipeline。初回コストと所要時間（Vision 1 枚 10〜30 秒 → 数時間〜1 日）。小型 Vision で抽出・大型で統合（コスト対策）
- **自前 Vision／OCR 基盤**（`PC-08`）：図面の外部送信を避ける GPU。SoMark 私有デプロイ（RTX 3090 1 枚〜、ライセンス未確認）か MinerU 自前
- **図番→台帳の結合**（`PC-04`）：工程・原価（ERP）、不具合履歴（QA 台帳）、金型・治具台帳（Outline or Excel）
- **属性一致率の重み**：生産技術と決める（材質・板厚・外形タイプを重く、表面処理を軽く 等）
- **無くても動く範囲**：台帳 API が無くても「特徴抽出→KB 検索→一致率→候補表」は動く（工程・原価・金型列が空）。さらに KB が小さい段階（100 件）で再現率を測ってから全件投入する

## 9. Outline Wiki との関係
- **読む**：`PC-05` で「金型台帳」「治具台帳」「図面命名規則」「過去品 不具合サマリー」を KB `en-tooling-ledger` に同期し、台帳 API が無い間の代替にする
- **書く**：しない。検索結果は見積（NM-01）の入力に人が持ち込む。将来「流用判断の記録（採用／不採用と理由）」を金型ページに人が追記する運用は候補（未確定）

## 10. 未確定・リスク
- **形状類似の限界**：属性一致率は「同じ材質・板厚・外形タイプ」を拾うが、幾何学的に似た別形状は拾えない。真の形状検索は CAD 側（PLM／形状検索ソフト）の領域。顧客にこの限界を先に説明する（構想の理由）
- **越境・NDA**：顧客図面を SiliconFlow／Baidu／海外埋め込みに送れるかは**ほぼ不可**前提で自前基盤（`PC-08`・`PC-10`）。GPU 調達が前提コスト
- **OCR 精度**：手書き注記・古い図面のスキャンは精度低。信頼度を出力し、低ければ人が特徴を入力
- **DXF／CAD データ**：テキスト抽出は可能だが本サービス対象外（未確定）。あれば属性一致率の精度は上がる
- **成熟度**：st3 のまま。既知ペア再現率 ≥ 80% と自前基盤の目処で st2 提案
