## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：担当者が能動的に開く。典型は**夜勤中の設備アラーム停止**（日本人駐在員不在、日本語マニュアルしか無い）。③業務フィードの項目にはならない
- **登場人物**：保全技師・オペレーター（中国語母語、スマホ／現場端末）、保全課長（再発時の連絡先）、設備メーカー（マニュアルの著作者。回答には登場しない）
- **いまの手順（Before）**：
  1. 操作パネルのアラームコードを見て、紙の日本語マニュアル（数百ページ）を棚から探す（10 分）
  2. コード表のページを目視で探し、日本語を翻訳アプリで読む（15〜30 分。図番号や手順の読み違いが起きる）
  3. 判断できなければ保全課長に電話。夜間はつながらず**翌朝まで停止**
  4. 同じアラームが月に何回出たかは、後日 MES の記録を Excel で集計しないと分からない
- **エージェント導入後の手順（After）**：
  1. 担当者が WeCom または `PC-16` から**設備型式とアラームコードを中国語で入力**
  2. エージェントがマニュアルの該当ページ（章・ページ番号）と復旧手順の要約を中国語で返す。安全注意（非常停止・両手操作）を必ず添える
  3. 追い質問（ボタンの位置、原点復帰）に図番号付きで答える。**復旧作業を実施するか、上長に連絡するかは担当者が決める**
  4. 「今月何回出た？」は稼働記録 KB から件数と傾向を返す。保全依頼票は**ドラフト提示まで**（起票は担当者）
- **成功の定義**：アラーム停止から復旧着手までを 30〜60 分 → 10 分以内。夜勤の初動を日本語マニュアルに依存しない

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|

| 質問文 | テキスト | zh 主体・ja | 1 日 5〜15 件（夜間多い） | 「冲床 PX-200 出现报警 E-47 停机了，该怎么处理？」 | WeCom bot／`PC-16` | `PC-07` 言語判定。型式・コードの正規化（`E47`→`E-47`、全角→半角） |

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。マニュアルが日本語でも中国語で要約し、ページ番号・図番号・ボタン名（パネル表記）は原語のまま添える
- **入力の欠け・曖昧さ**：設備型式が無いとコードは一意に決まらない（同じ `E-47` が別型式で別意味）。聞き返し定型：「設備の型式（例：PX-200）を教えてください。同じコードでも型式により意味が異なります」

## 3. 観点（LLM に守らせる業務ルール）
- **型式一致**：質問の型式とメタデータ `model` が一致する文書だけを根拠にする。**型式が違うマニュアルの手順を答えない**（類似型式は「参考・型式が異なる」と明示し、手順は書かない）
- **ページ引用**：手順・意味には必ず「第 X 章 X-XX ページ（図 X-X）」を付ける
- **安全最優先**：非常停止・両手操作・電源遮断・金型内確認など、マニュアルの安全注意は要約で省かない。手順の先頭に置く
- **手順を作らない**：マニュアルに無い手順・ボタン操作を補完しない。復旧できないときは「センサー交換等はメーカー／保全課長」と手順書どおりに案内
- **件数は記録から**：「何回出た」は稼働記録 KB の件数のみ。記録が無い期間は「記録なし」と言う。推測で回数を出さない
- **起票しない**：保全依頼票は「ドラフト」と明記し、起票は担当者
- **禁止**：メーカーマニュアルの章全体の転記（NDA・著作権）。要約と該当箇所の短い引用まで
- **不確実なとき**（入力言語で）：「該当するアラームコードが見つかりません。設備型式とコードを確認してください。パネル表示の写真があれば添えてください」
- **出力の粒度**：コードの意味 1 行 → 番号付き手順（各 1 行、ページ参照）→ 再発時の連絡先。件数質問は表または箇条書き

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`）。追い質問・Citation・WeCom bot 接続のため
- **ノード列**：
  1. Start（`sys.query`。WeCom 経由も同じ入口）
  2. LLM（Qwen3-32B）— `model` / `alarm_code` / `intent`（`procedure` | `location` | `count` | `other`）を JSON 抽出。型式・コードの正規化
  3. IF/ELSE（`intent == count`）
     - **count 分岐**：Knowledge Retrieval（`kb-equip-logs`、メタデータ `model`・`alarm_code` フィルタ、top-k 50）→ Code（当月件数・金型別集計）→ LLM（要約）
     - **それ以外**：Knowledge Retrieval ×2 並列（`kb-equip-manuals` メタデータ `model` フィルタ／`kb-alarm-codes`）＋ Knowledge Retrieval（`kb-maint-procedures`：連絡先）→ LLM（本体）
  4. Answer（Citation ON）
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-equip-manuals` | メーカー取扱説明書 | ページ単位（MinerU 出力）。表は HTML 保持 | `model` `maker` `chapter` `page` `edition` `lang` | `PC-03`：ファイルサーバ → MinerU（自前デプロイ推奨）→ 投入。年数回 |
  | `kb-alarm-codes` | アラームコード表 | Q&A チャンク | `model` `alarm_code` `page` | 保全課 Excel → `tools/qa_chunk` |
  | `kb-maint-procedures` | 社内保全手順・連絡先 | 一般チャンク | `equipment_group` `lang` `version_date` | Outline → `PC-05`（週次） |
  | `kb-equip-logs` | MES 稼働・アラーム記録 | 行単位 | `model` `alarm_code` `date` `shift` `die_no` | MES CSV → `PC-11` 月次（台本の前提） |
- **プラグイン／ツール**：`tools/mineru`（既定。自前デプロイなら越境なし）／`tools/paddleocr`（中国語帳票寄りの代替）、`tools/dify_extractor`、`tools/qa_chunk`、`tools/general_chunk`、**`extensions/wecom_bot`**（スマホ入口。Dify に公開 URL が要る → セルフホスト）
- **モデル**（`PC-08`）：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（本体）／`Qwen3-32B`（抽出）／`bge-m3`／`bge-reranker-v2-m3`。代替 `DeepSeek-V3.x`
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（複数 KB）、`../templates/08-mineru-pdf-parse-demo.yml`（MinerU tool ノード）
- **入出力変数**：
  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `sys.query` | string | ✓ | 質問 |
  | `lang` | string | ✓ | `ja`/`zh` |
  | `model` | string | ✓（抽出） | 設備型式。無ければ聞き返し |
  | `alarm_code` | string | — | 正規化済みコード |
  | `intent` | enum | ✓（抽出） | `procedure` / `location` / `count` / `other` |
  | 出力 `answer` | string | ✓ | 回答（Citation 付き） |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工 蘇州工場の設備保全を支援する「設備マニュアル検索」です。
役割：設備メーカーの取扱説明書・アラームコード表・社内保全手順・設備稼働記録から、該当ページを引いて復旧手順を要約する。

守るルール：
1. 回答は <context> の内容だけから作る。マニュアルに無い手順・ボタン操作・数値を補完しない。
2. 質問の設備型式（{{model}}）とメタデータ model が一致する文書だけを根拠にする。型式が異なる文書は「参考（型式が異なる）」とだけ書き、手順は書かない。
3. 手順・意味には必ず「第 X 章 X-XX ページ（図 X-X）」を付ける。
4. 安全注意（非常停止・両手操作・電源遮断・金型内の確認）は省略せず、手順の先頭に置く。
5. 「何回出た」など件数の質問は設備稼働記録の行だけから数える。記録に無い期間は「記録なし」と書く。
6. 保全依頼票・報告書を求められたら「ドラフト」と明記し、起票は担当者が行うと 1 行添える。
7. マニュアルの章を丸ごと転記しない。要約と該当箇所の短い引用まで。
8. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。ページ番号・図番号・パネル表記（ORG、MODE 等）は原語のまま。
9. 該当が無いとき：
   ja「該当するアラームコードが見つかりません。設備型式とコードを確認してください。パネル表示の写真があれば添えてください。」
   zh「未找到对应的报警代码。请确认设备型号与代码。如有面板显示的照片请一并提供。」

出力形式：1 行目にコードの意味（ページ付き）→ 番号付き復旧手順 → 再発時の連絡先（社内手順から）。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | コードの意味・手順がマニュアル該当ページと一致 ≥ 90% | 評価セット 30 件（型式 5 種）を保全課長が採点 |
| ページ引用 | 手順にページ番号が付く 100%、ページが実際に該当 ≥ 95% | 自動（正規表現）＋人手抜取 |
| 型式分離 | 別型式の手順を混ぜない 100% | 負例 10 件（同コード・別型式） |
| 安全 | 安全注意の欠落 0 | チェックリスト（型式ごとの必須注意） |
| 言語 | 入力言語で返答 100% | `PC-07` 自動判定 |
| 件数 | 稼働記録の件数と一致 100% | CSV で突合 |
| 速度 | p95 < 12 秒（夜勤の初動） | `PC-09` Langfuse |

- **評価方法**：リリース前に人手（保全課長＋技師 2 名）。月次で Langfuse データセットの回帰と、WeCom 経由の「役に立った／立たなかった」ボタン集計

## 8. 別出しが必要なもの
- `PC-03`：スキャン PDF の OCR 経路（MinerU 自前デプロイ or API。API はデータが MinerU 側に出る）。ページ番号を落とさない設定
- `PC-14`：`extensions/wecom_bot` の登録（WeCom 管理者権限、Token / EncodingAESKey、公開 URL）
- `PC-11`：MES 稼働記録の月次エクスポート → `kb-equip-logs` 投入（台本 Q3 の前提）
- `PC-05`：Outline「設備保全」コレクション（社内手順・連絡先）の同期
- **無くても動く範囲**：`kb-equip-manuals` ＋ `kb-alarm-codes` だけで T01〜T03 は動く。`kb-equip-logs` が無い間は「件数」質問に「稼働記録は未接続」と定型で返す（FEED 前提と食い違うので初回デモ前に接続推奨）。WeCom 無しなら `PC-16` から
