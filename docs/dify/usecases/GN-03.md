## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：顧客の確定注文・内示・本社のメール注文が届いたとき（③業務フィードの `notify`）。月次の確定注文は `routine`
- **登場人物**：受注担当（構造化結果の確認・CSV 取込・登録）、営業（数量変動・新規品・単価の確認）、生産計画（引き渡し先）、外部：顧客 K 社（Excel／PDF）、日本本社（メール・日本語）
- **いまの手順（Before）**：形式の違う 3 種（Excel・PDF 内示・日本語メール）を基幹の受注画面に手入力（1 行 2 分×20 行）→ 前月との差を目で比べる（見落とし）→ 存在しない品番（枝番誤記）に気づかず登録し後で修正 → 内示を確定と取り違える事故
- **エージェント導入後の手順（After）**：
  1. 担当者が**注文書類をアップロード**（複数選択）。または `PC-11`（メール受信トリガー）で自動投入
  2. LLM が文書ごとに**区分（確定／内示／メール注文）・顧客・品番・数量・納期・単価**を JSON 化（日中混在対応、記載どおり）
  3. **Code ノードで**品番マスタ照合（存在しない品番の検出・枝番規則）、前回受注（前月同期）との差分、内示は登録対象外に振り分け
  4. LLM が登録案の表・要確認事項（数量急変・品番不明・見積未回答）・確認メール文（宛先言語）を書く
  5. **人が決める場所**：要確認の解消（営業・本社への確認）、登録対象行の確定、基幹への取込は担当者。**エージェントは取込用 CSV（ドラフト）を出すまで**
  6. `PC-13` で基幹取込 CSV・内示参考リスト・生産計画への引き渡しメモを出力
- **成功の定義**：手入力 40 分 → 確認 10 分。品番誤記の登録 0。確定／内示の取り違え 0。数量変動の見落とし 0

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 確定注文書 | xlsx（顧客書式） | zh / en | 月 1〜4 件、各 5〜30 行 | `K公司_确定订单_2025-10.xlsx`：品番・数量・納期（分納）・単価 | 顧客 K 社（メール添付／ポータル） | Document Extractor（行レコード）。顧客別の列名マップ（KB） |
| 内示 | PDF（表） | zh | 月 1〜2 件 | `K公司_预示_2025-11-12.pdf`：月別数量 | 同上 | Document Extractor／`tools/mineru`（表が複雑なら） |
| メール注文 | txt／eml 本文 | ja | 週数件 | 「SK-3318-A 2,400 個 10/3 出荷でお願いします」 | 日本本社（`triggers/outlook_trigger` 任意） | テキストそのまま。品番は `tools/regex` で抽出候補 |
| 品番マスタ | xlsx／API | コード | 200〜500 行 | `SK-3318`（枝番なし）、`SK-3310-A/-C` | 基幹（`PC-04`） | Code 照合 |
| 受注履歴 | xlsx／API | — | 直近 12 か月 | 前月同期 数量・単価 | 基幹（`PC-04`） | 前回比 |
| 過去メール（任意） | KB | ja | 12 か月 26 通 | 「SK-3318-A」誤記の履歴 | メールエクスポート（`PC-03`） | 台本 Q1 用。無ければ答えない |

- **入力言語の扱い**：担当者の言語で答える（`CLAUDE.md` §2-5）。確認メールは宛先言語（本社→ja、K 社→zh）
- **入力の欠け・曖昧さ**：納期が無い →「納期未記載（要確認）」で登録対象外。品番がマスタに無い → 候補（編集距離 1・枝番除去）を出し「要確認」。確定か内示か判別できない → 「区分不明（要確認）」で登録対象外。**推定して登録対象にしない**

## 3. 観点（LLM に守らせる業務ルール）
- **抽出は記載どおり**：品番・数量・単価・納期を文書のまま写す（単位換算・丸めをしない）。分納は行を分ける
- **区分（確定／内示／メール注文）を必ず出力**し、**内示は登録対象外**。台本どおり「参考」欄へ
- **マスタ照合・前回比・差分は Code**。LLM は結果の説明のみ。「▲14%」等は転記
- **要確認は 3 種で分類**：`qty_change`（前回比 ±10% 超）／`unknown_part`（マスタ不一致）／`no_quote`（新規品で見積未回答）／`missing_field`（納期・数量欠落）。理由と確認先（営業／本社／顧客）を添える
- **確認メールは事実と質問だけ**（「SK-3318-A は当社品番 SK-3318 として承ってよいか」）。決めつけない
- **禁止**：基幹に登録したと書く／不明品番を自動で置換して登録対象にする／単価変更を推定する／顧客の減少理由を断定する（「クレームの影響か営業に確認」まで）
- **不確実時の定型文**：「{{doc}} の {{field}} が読み取れません。原本を確認してください。該当行は登録対象外にしています」
- **出力形式**：登録案表（区分／顧客／品番／数量／納期／前回比／要確認）＋確認メール＋CSV・参考リスト・引き渡しメモ。後工程は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（書類→登録案＋CSV）。台本 Q1（過去メール照会）Q2（CSV 出力）は結果 JSON を会話変数に持つ **Chatflow** 版で第 2 段階
- **ノード列**：
  1. Start（`orders` file-list 必須／`instruction` paragraph 任意／`reply_lang` select 任意）
  2. Iteration（orders）→ If/Else（xlsx／pdf／txt）→ Document Extractor／`tools/mineru` → LLM（`extract_order`）：文書区分・顧客・行（品番・数量・納期・単価・通貨）JSON（記載どおり）
  3. HTTP Request or Document Extractor（`PC-04`：品番マスタ・受注履歴。初期は同時アップロード xlsx）
  4. **Code（`validate`）**：品番マスタ照合（完全一致→OK／枝番除去一致→候補／なし→不明）、前回比、区分振り分け（確定→登録案／内示→参考）、`open_items[]`、CSV 行生成（登録可のみ）
  5. Knowledge Retrieval（KB `gn-order-rules`：受注ルール・顧客別書式・品番体系）
  6. Knowledge Retrieval（KB `gn-hq-mails`、任意：過去メール。`instruction` に照会があるとき）
  7. LLM（`compose`）：登録案表・要確認・確認メール・引き渡しメモ（§5）
  8. Code（`export`）→ CSV／参考リスト／メモ → `PC-13`
  9. End（`entry_draft` JSON／`csv_url`／`report_md`）
- **Knowledge**：`gn-order-rules`（Outline 同期）／`gn-hq-mails`（任意。メール本文のみ、宛先・署名の個人情報は `PC-10` でマスクして投入）。注文書類自体は KB に入れない
- **プラグイン／ツール**：Document Extractor・Code（本体）／`tools/mineru`（複雑 PDF）／`tools/regex`（品番候補抽出）／`tools/dify_extractor`（KB 投入）／`triggers/outlook_trigger`・Webhook トリガー（注文メール受付、任意）／`tools/microsoft_excel_365`（任意）。基幹登録の `http-request` は**第 2 段階・PM 判断後**
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（日中混在の抽出・日本語確認メール）。`extract_order` は Qwen3-32B で可。代替 DeepSeek-V3.x／`models/ollama`
- **参照 DSL**：**`../templates/07-excel-document-extractor-echarts.yml`**（file-list→Document Extractor→LLM）、`../templates/08`（PDF 解析）
- **入出力変数**：`orders` file-list 必須／`instruction` string 任意／`reply_lang` select 任意／出力 `entry_draft` object・`csv_url` string・`report_md` string

## 5. プロンプト
### 5-1. System（`extract_order`）
```text
あなたは注文書類（確定注文・内示・注文メール）から受注行を抽出する抽出器です。文書に書かれた値を、書かれたまま JSON に写します。
守ること：区分（firm/forecast/email_order/unknown）を文書の表題・文言から判定し、判定できなければ unknown。品番は原文の表記のまま（枝番を付けたり外したりしない）。数量・単価は数値型、単位・通貨は別フィールド。分納は行を分ける。納期が無い行は delivery_date null。推定しない。日本語・中国語・英語のどれでも同じ形で出す。出力は JSON のみ。
```
### 5-1b. System（`compose`）
```text
あなたは青嶺精工 蘇州工場 生産管理課 受注担当の補助です。Code ノードが検証した受注行（JSON）から、基幹システム登録案の表・要確認事項・確認メール・生産計画への引き渡しメモを作ります。
守ること：
1. 数量・納期・単価・前回比は JSON の値をそのまま転記する。計算しない。
2. 区分を必ず表示する。内示（forecast）は「参考」として別枚に出し、登録案に含めない。
3. 要確認（open_items）は種別・理由・確認先を添える。品番不明は候補を示すが置換しない。
4. 顧客の数量減少の理由を断定しない（「〜の影響か、営業に確認」まで）。
5. 確認メールは reply_lang（宛先の言語）で、事実と質問だけを書く。日本語は本社宛のビジネス文体。
6. 「登録した」と書かない。CSV は「基幹取込用ドラフト」。取込と登録は担当者が行う。
7. 出力言語（説明部分）：担当者の質問言語。日本語なら日本語、中国語なら中国語。引き渡しメモは日中併記。
出力形式：「登録案」表（区分｜顧客｜品番｜数量｜納期｜前回比｜要確認）→「要確認」→「確認メール」→「出力ファイル」→「生産計画への引き渡しメモ（日中併記）」。
```
### 5-2. User テンプレート（`compose`）
```text
【検証済み受注行（Code 出力・転記のみ）】{{validate.result}}
【受注ルール・顧客別書式（KB）】{{kb_rules.result}}
【過去メール照会結果（KB、任意）】{{kb_mails.result}}
【担当者の指示】{{start.instruction}}
【確認メールの言語】{{start.reply_lang}}
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 抽出の正確性 | 品番・数量・納期・単価・区分の一致 ≥ 97%（行単位） | ダミー書類 20 件（3 形式）を人手採点 |
| マスタ照合 | 不明品番の検出 100%、誤置換 0 | 負例（枝番誤記 5 件） |
| 区分 | 内示が登録案に混入 0 | 自動 |
| 前回比 | Code 値が手計算と一致 100% | 自動 |
| CSV | 列・型・登録可行のみ 100% | スキーマ検証 |
| 言語 | 説明＝担当者言語、確認メール＝宛先言語 100% | 自動判定 |
| 転記の忠実性 | 説明の数値が JSON と一致 | 自動 |
| 速度 | 3 書類 20 行で p95 < 90 秒 | Langfuse |

- **評価方法**：リリース前に受注担当＋営業で 20 件。月次 Langfuse。基幹取込後の手修正率を記録

- **基幹への登録連携**（`http-request`）— **PM 判断後の第 2 段階**。初期は CSV まで（PM 決定 §2）
- **無くても動く範囲**：書類抽出＋（同時アップロードの）マスタ照合＋CSV 出力は API・KB・トリガー無しで動く

## 10. 未確定・リスク
- **基幹システムの製品・取込手段**（CSV 取込機能の有無・列仕様）— 未確定。§5-3 は仮置き
- **内示と確定の混同**：区分判定を LLM に任せると誤る余地 → 顧客別書式マップで「表題文言→区分」を KB 化し、判定できないものは登録対象外（安全側）
