## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：(a) 担当者が能動的に開く（欠員補充の起案：求人票の起草）／(b) 監視対象の変化（③業務フィードの `notify`：採用エージェントから「一次面談完了（候補者 N 名）」の Webhook）／(c) 期限つき（`due`：二次面談日・内定回答期限）
- **登場人物**：人事課 採用担当（起草・比較・稟議起案）、設備課長（要件の確認・二次面談）、管理部・本社（承認）、外部＝採用エージェント（媒体掲載・スクリーニング・AI 一次面談・日程調整。応募者の同意取得と原本保管）、応募者（**当社は匿名 ID でしか扱わない**）
- **いまの手順（Before）**：設備保全技師 1 名の欠員 → 担当者が過去の求人票を修正して媒体に出す（1 時間）→ 応募 27 名の履歴書（氏名・連絡先・写真つき）がメールで届き Excel で管理 → 電話で一次面談 27 回（1 人 20 分＝9 時間）→ 上位 4 名を設備課長に口頭で説明 → 本社向け稟議は駐在員が日本語で書き直す（1 時間）。**履歴書原本が社内メールに散在**し、不採用者の分を消す運用がない
- **エージェント導入後の手順（After）**：(1) 担当者が求人要件を**入力**し、Dify が求人票を起草 → 担当者が**確認・修正して**エージェントへの掲載依頼を**ボタンで送る**（`PC-15`）→ (2) エージェント側でスクリーニング・AI 一次面談（応募者同意はエージェントが取得）→ 完了 Webhook で当社へ**匿名 ID・評価・面談要約のみ**が届く（または担当者がレポート PDF をアップロード）→ (3) Dify が求人要件との照合表と推奨を返す → 担当者と設備課長が**二次面談に呼ぶ候補を決め**、エージェントへ日程調整を**依頼する**（送信は人のボタン）→ (4) Dify が本社承認用の日本語サマリ（匿名 ID・最小情報）を起草 → 担当者が**確認して**稟議へ → (5) 内定後、本人同意のうえ氏名等をエージェントから受領（**Dify の外**）。入社手続きは KN-04 へ引き継ぐ
- **成功の定義**：一次面談 9 時間 → 0（エージェント側）、比較・稟議 2 時間 → 20 分。**当社の Dify・メール・Excel に応募者の氏名・連絡先・履歴書原本が存在しない**。採否は必ず人の二次面談を経る

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。本社承認用サマリを頼まれたときだけ**日本語**（台本の zh 側もそう）。エージェントの要約が中国語でも、日本語の照合表では要約を日本語に訳す（原文は保持しない）
- **入力の欠け・曖昧さ**：求人要件に「必須／歓迎」の区別が無いときは聞き返す（「必須条件と歓迎条件を分けてください」）。レポートに候補者 ID が無い（氏名で来た）場合は**処理を止めて**「氏名で届いています。エージェントに匿名 ID 形式での再送を依頼してください」と返す。給与レンジが無ければ「希望給与の妥当性は判定しません」

## 3. 観点（LLM に守らせる業務ルール）
- **候補者は匿名 ID でのみ呼ぶ**：氏名・連絡先・生年月日・住所・写真・身分証番号・SNS は**入力に紛れても出力しない**。出てきたら「（エージェント側保管情報のため省略）」に置換
- **差別的属性を評価に使わない**：年齢・性別・出身地・婚姻・妊娠・宗教・民族・健康状態を照合表・所見・推奨のどこにも書かない。要件にあれば除去し警告
- **AI 評価は単独で採否判断にしない**：推奨は「二次面談に呼ぶか」の優先順位であって採否ではない。「不採用」と書かない（「今回の要件とはズレ」「経験が要件未満」まで）
- **自己申告と確認済みを区別**：語学等級・資格は「N1（証明書確認済：エージェント）」「N3 相当（自己申告）」と明記
- **要件充足は `code` が判定**：経験年数・語学等級・給与上限は `code` で ○△× を決め、LLM は所見の要約と説明。LLM が基準を緩めない
- **給与は「要件レンジ内か」だけ**：市場中央値は参考表示。値切り交渉の提案はしない
- **送っていない・受け取っていないものを明示**：表の最終行「連携」に「当社が受け取ったのは候補者 ID・評価・面談要約のみ。氏名・連絡先・履歴書原本はエージェント側に保管（採用決定後、本人同意のうえ提供）」を必ず書く（PM 決定 PT-10）
- **不確実なときの定型**：ja「一次面談レポートに該当項目がありません。エージェントに確認を依頼してください」／zh「初面报告中没有该项目。请向招聘代理确认」
- **出力の粒度と形式**：照合表（候補者 ID／経験／日本語／設備・保全／一次面談所見／希望月給／推奨）＋連携行。稟議サマリは §5-3 の JSON を経て Markdown（匿名 ID・最小情報）

## 4. Dify 構成
- **アプリ種別**：**Workflow ×2 ＋ Webhook Trigger**。(A) 求人票起草（form → `llm` → 担当者確認 → `http-request` 掲載依頼）、(B) 候補者サマリ（Webhook Trigger または upload → 抽出 → 照合 → サマリ）。Chatflow にしないのは、**応募者情報を多輪の会話ログに蓄積させない**ため。追加質問（「B の N1 は本当？」）は (B) の結果 JSON を `context` にした `mode=followup`
- **ノード列 (B)**：
  1. Webhook Trigger（`PC-15` から `{case_id, candidates[]}`）／または Start（`sys.files`：PDF・docx・xlsx）
  2. `code`（**受信データのホワイトリスト適用**：許可キー以外を削除。氏名・電話・メール・身分証・生年月日・URL のパターン検出 → 削除＋`pii_dropped[]` に記録。候補者 ID 形式 `C-YYMM-X` の検証。無ければ停止）
  3. （アップロード時）Document Extractor／`tools/mineru`（PDF レポート）→ `llm`（レポートを候補者ごとの JSON に構造化。**個人情報フィールドを出力スキーマに持たせない**）
  4. `knowledge-retrieval`（KB `hr-recruit-rules`：採用規程・求人要件テンプレート・語学等級の扱い。HR 帯）
  5. `code`（要件充足判定：経験年数≧N・分野一致・語学等級≧N2・希望給与≦上限 → ○△×。自己申告／確認済フラグ）
  6. `llm`（§5。照合表＋推奨。入力言語）
  7. （`mode=hq_summary`）`llm`（日本語稟議サマリ。日本語品質モデル）
  8. `template-transform`（「連携」行）
  9. `http-request`（`PC-01` フィードに `notify`「一次面談完了 N 名」／`due`「二次面談 9/15」を書く）＋ `tools/wecom`（`PC-14`。担当者へ通知。**内容は件数のみ**）
  10. End（`result_md`, `result_json`）
- **ノード列 (A)**：Start（要件フォーム）→ `code`（差別的属性の検出・除去）→ `knowledge-retrieval`（求人票テンプレート）→ `llm`（求人票 ja/zh）→ End。掲載依頼は**別 Workflow**（担当者のボタン → `http-request` → `PC-15` → エージェント API）。二次面談依頼も同型（送るのは候補者 ID・希望日時枠・面接官の役職のみ）
- **Knowledge**：KB `hr-recruit-rules`（HR 帯・メンバー限定 `PC-02`）：採用規程、求人票テンプレート、語学・資格の確認ルール、面接評価の観点（差別禁止項目を含む）。**候補者データは KB に入れない**
- **プラグイン／ツール**：Webhook Trigger（本体、1.10.0〜）／Document Extractor（本体）／`tools/mineru`（PDF レポート）／`tools/regex`（PII パターン）／`tools/wecom`・`tools/email`（通知。件数のみ）／HTTP リクエストノード
- **モデル**：HR 帯は `PC-08` のオンプレ方針（`models/ollama` 等）を優先。無い間は SiliconFlow 中国版で**匿名 ID データのみ**（顧客法務確認）。日本語サマリは DeepSeek-V3.x 等と評価
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（upload → Document Extractor → LLM の最小骨子）。Webhook Trigger の保存 DSL は無いため dsl-skill `--target-version 0.6.0` で生成。人の確認を挟む箇所は Dify 1.15 の Human-in-the-loop（`human-input`）を使ってもよいが、本書は「担当者のボタン＝別 Workflow の起動」で十分としている
- **入出力変数**：

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `case_id` | string | ✓ | 求人案件 ID（エージェント側の番号） |
| `requirements` | object | ✓ | 必須／歓迎要件・給与上限（(A) の出力） |
| `candidates[]` | array | ✓ | ホワイトリスト適用後の候補者（匿名 ID） |
| `mode` | select | ✓ | `compare` / `followup` / `hq_summary` |
| `pii_dropped[]` | array | 内部 | 落とした項目名（値は保持しない） |
| `market_median` | number | — | PT-04 由来（任意） |
| `result_md` / `result_json` | string / object | 出力 | 照合表＋連携行／§5-3 |

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）人事課の採用支援アシスタントです。
入力として (A) 求人要件（必須／歓迎・給与上限）、(B) 採用エージェントの一次面談レポート（候補者は匿名 ID。経験・分野・語学〔等級と確認状況〕・AI 所見・希望月給・推薦度）、(C) code が判定した要件充足（○△×）、(D) 社内の採用規程・評価観点、が与えられます。

守ること：
1. 候補者は匿名 ID（例 C-2609-A）でのみ呼ぶ。氏名・連絡先・生年月日・住所・写真・身分証番号・SNS・録画リンクが入力に含まれていても出力に書かない。「（エージェント側保管情報のため省略）」と置く。
2. 年齢・性別・出身地・婚姻・妊娠・宗教・民族・健康状態を評価・所見・推奨のどこにも書かない。要件にそれらがあれば無視し、末尾に「要件から除外した属性: …」と警告する。
3. 要件充足の ○△× と理由は (C) をそのまま使う。基準を緩めたり厳しくしたりしない。
4. 語学・資格は「等級（確認済：エージェント）」か「等級相当（自己申告）」を必ず区別して書く。
5. 推奨は「二次面談に呼ぶ優先順位」であり採否ではない。「不採用」「落とす」と書かない。「今回の要件とはズレ」「経験年数が要件未満」のように事実で書く。採否は人の面談を経て当社が決める。
6. 表は「候補者 ID｜経験｜日本語｜設備・保全｜一次面談（AI）所見｜希望月給｜推奨」。最終行は必ず「連携」行：受領経路・「当社が受け取ったのは候補者 ID・評価・面談要約のみ。氏名・連絡先・履歴書原本はエージェント側に保管（採用決定後、本人同意のうえ提供）」・日程調整の担当・入社手続きの引き継ぎ先（労務・総務の社内問い合わせ対応）。
7. 希望月給は「要件レンジ内か」だけを書く。参考の市場中央値があれば添える。交渉の提案はしない。
8. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。本社承認用サマリ（mode=hq_summary）だけは常に日本語。稟議サマリには候補者の匿名 ID・経験年数・語学等級・分野・希望給与レンジ・推奨のみを書き、面談所見の詳細は書かない。
9. 該当項目なしの定型：「一次面談レポートに該当項目がありません。エージェントに確認を依頼してください」／中国語「初面报告中没有该项目。请向招聘代理确认」。
10. パートナーは「採用エージェント」と呼ぶ。実名・媒体名を作らない。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（転記） | 表の経験・等級・給与がレポート JSON と一致 100%。○△× が `fit_json` と一致 100% | 自動突合 |
| 網羅 | 7 列＋連携行、語学の確認状況表記、二次面談の確認点 3 つ | チェックリスト |
| 言語 | 入力言語 100%、`hq_summary` は日本語 100% | 自動判定（`PC-07`） |
| 形式 | `result_json` スキーマ準拠 100%。禁止キー（name/phone/email/birth/id_number/photo/address）が**存在しない** | JSON バリデータ＋禁止キー検査 |
| 拒否 | 氏名で届いたレポートを処理停止 100%。差別的属性を含む要件で警告 100% | 負例セット 20 件 |
| **安全（受信最小化）** | ホワイトリスト外のキーが `candidates[]` に残らない 0 件。PII パターン（電話・メール・身分証 18 桁）が出力・トレースに 0 件 | 自動（正規表現）毎実行 |
| **安全（送信最小化）** | 掲載依頼・二次面談依頼で `PC-15` に送るのは求人票・候補者 ID・日時枠・面接官役職のみ | 送信ログ監査 |
| **公平性** | 所見・推奨に年齢・性別・出身地等の語が 0 件 | 語彙リスト照合＋人手 |
| 保持 | 会話ログ・トレースが `retention_until`（採用終了後 90 日）で削除される | `PC-09`／`PC-10` の月次監査 |
| 速度 | p95 < 60 秒（PDF 4 名分） | Langfuse |

- **評価方法**：リリース前に人事課長・設備課長が 10 案件分（架空データ）を採点。**法務が §3 の個人情報・公平性ルール、`PC-15` の受信／送信ホワイトリスト、エージェント契約（同意取得・保持期間・AI 面談の告知）をレビュー**（リリース条件）。月次：PII 検査ログ・保持期間削除の確認・LLM-as-judge（連携行・禁止語）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-15`**：採用エージェントとの契約と API（求人掲載・案件状態・一次面談完了 Webhook・二次面談依頼・候補者 ID 体系）。**受信ホワイトリスト**（候補者 ID・経験・分野・語学等級＋確認状況・面談要約・希望条件・推薦度）と**送信ホワイトリスト**（求人票・候補者 ID・日時枠・面接官役職）。契約に明記：応募者への**告知と同意**（AI 面談の実施・評価の当社提供・保持期間）はエージェント責任、差別的属性を評価に含めない API 仕様、当社への氏名等の提供は内定時・本人同意後・Dify の外（`PC-15` を通さない経路）
- **`PC-10`**：匿名 ID 原則。Dify ログ・Langfuse の保持期間（採用終了後 90 日で削除）、PII パターン検査、HR 帯限定。越境：海外エージェントなら越境提供評価（PIPL 第 38 条）。**中国国内のエージェントを前提**にするのが現実的（設計書 §5-2 pt5）
- **`PC-02`**：HR 帯ロール（人事課 採用担当・人事課長・管理部）。設備課長は「自分の求人の照合表」だけ閲覧（ロール属性で絞る。未確定）
- **`PC-01` / `PC-14`**：`notify`（一次面談完了。件数のみ）・`due`（二次面談・内定回答期限）。通知本文に候補者情報を入れない
- **社内**：求人票テンプレート・採用規程・評価観点（差別禁止項目）の Outline 整備。PT-04 の市場中央値（任意）。KN-04 への入社手続き引き継ぎ（リンクのみ）
- **無くても動く範囲（段階導入）**：
  - 段階 0（契約前）：`PC-15` モック。求人票起草（A）とアップロード版（B）の動作・PII 検査・公平性検査の確認とデモ
  - 段階 1：求人票起草＋担当者がエージェントのレポート PDF を手動アップロード（Webhook なし。エージェントは既存の人手運用でも可）
  - 段階 2：Webhook・掲載依頼・二次面談依頼の API 化、フィード連携
  - 法務レビューを通り段階 2 に到達するまで st3 のまま

## 9. Outline Wiki との関係
- **読む**（`PC-05`）：「人事／採用」の求人票テンプレート・採用規程・評価観点（HR 帯メンバー限定コレクション）
- **書く**：求人票ドラフト（(A) の出力）を「人事／採用／求人票」にドラフト保存（担当者のボタン）。**候補者の照合表・所見・稟議サマリは Outline に書かない**（個人情報に近く、保持期間管理が要るため。`PC-13` で人事共有フォルダへ出力し、`retention_until` で削除）
- 使わない部分の理由：Outline は保持期間の自動削除が無く、コレクション権限だけでは応募者情報の管理として不足

## 10. 未確定・リスク
- **採用エージェントの API・候補者 ID 体系・同意フロー**：未確定。契約前に**同意文言と保持期間**を法務が確認する必要（PM／顧客法務）
- **AI 一次面談の評価の扱い**：中国の関連規制（アルゴリズム推薦・自動化意思決定に関する説明・拒否権）への該当性はエージェント側の責任として契約に書くが、当社側も「単独で採否判断に使わない」を運用ルールに明文化する。architect 推奨：**二次面談を必須工程として稟議テンプレートに固定**
- **氏名等の受領経路**：内定時の本人情報は Dify を通さない別経路（エージェントのポータル→人事システム）とする。Dify に「内定者の氏名」を入れる誘惑を UI（`PC-16`）で防ぐ
- **設備課長の閲覧範囲**：自分の求人だけに絞るロール設計は `PC-02` 待ち
- **モデル所在**：匿名 ID データでも面談所見は個人関連情報。`PC-08` のオンプレ方針を HR 帯で優先
- **KN-04 / DC-03 との接続**：入社手続きは KN-04、育成前提の候補者には DC-03 で教材準備。いずれも「言及止まり」で、Dify 間の自動連携はしない
- 実現手段の候補として BP（`ζ 社`）の既製品がある。比較は `docs/dify/build-or-buy.md` §2-8
- **BP 製品で実現する場合の PIPL 上の論点**：BP 製品は履歴書そのものを自社側で解析するため、本サービスの「氏名・連絡先はエージェント側に留め、匿名化された候補者 ID だけを受け取る」前提は採れない（自社が個人情報の取扱者になり、`PC-15` の `not_sent` 表示が成り立たなくなる）。PIPL 評価と保管・削除の経路（`PC-10`）を先に決める。`SVCS.pt5.desc` は 1 文字も変えない（現行の設計が正しい。BP 製品を採るかどうかは未決）
