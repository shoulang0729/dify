## 1. 業務シナリオ
- **トリガー**：期限つき案件が振られる（`due`）。承認ワークフローで自分のところに回ってきたとき
- **登場人物**：実施者＝承認者（購買課長・部長・駐在員）。申請者＝各課の班長・担当。後工程＝承認ワークフロー（BPMS）、差し戻し時は申請者
- **いまの手順（Before）**
  1. 承認待ちが 5〜10 件たまる。1 件ずつ本文と添付を開く
  2. 「前に似た申請があったはず」を**記憶とメールの検索**で探す（見つからないことが多い）
  3. 規程の金額区分・相見積の要否は**覚えている範囲**で判断する。境目の近くほど間違えやすい
  4. 忙しいと**内容を読まずに承認する**か、逆に**全部差し戻して**申請者の手戻りを増やす
  5. 差し戻しの理由を書くのに 10 分かかり、書き方次第で角が立つ
- **エージェント導入後の手順（After）**
  1. 申請の種別と本文を貼る（または承認ワークフローの行からボタンで呼ぶ。**入力する場所**）
  2. 要点 3 行が返り、**過去の同種申請との違い**（金額・相手先・頻度）が並ぶ
  3. **該当する規程の条文**と、その申請が境目のどちら側にあるかが示される（**確認する場所**）
  4. 判断に効く点が ❗／⚠／✅ で分かれ、社内で確かめられないこと（市況など）は**未確認**と明示される
  5. 差し戻すなら理由の下書き、差し戻さない選択肢（単価契約など）が並ぶ。**承認も差し戻しも人が押す**（決める場所）
- **成功の定義**：1 件あたりの確認が 10 分から 2 分になる。かつ**境目（金額区分・相見積の要否）の見落としがゼロになる**

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 申請 | フォーム（テキスト）／BPMS のレコード | zh 主体・ja 併記 | 1 日 3〜10 件 | `PR-25-0417`（`SK-T-0812` 120 本・RMB 10,320） | 承認ワークフロー（`PC-04`） | 種別・金額・数量・相手先・添付の有無を抽出 |
| 過去の同種申請 | 構造化データ | zh | 過去 24 か月 | `PR-25-0362` `PR-25-0208` | 申請台帳（`PC-04`） | 品目・相手先・金額・日付でインデックス |
| 社内規程 | Markdown / PDF | ja / zh | 数本 | `RULE-10` 購買管理規程、`RULE-07` 費用管理規程、`FIN-TRV-01` 経費規程 | Outline（`PC-05`） | 条文単位でチャンク。**金額のしきい値をメタデータに持つ** |
| 添付 | PDF / 画像 | zh | 申請ごと 0〜3 件 | 見積書（X 社） | 申請台帳 | 有無と件数だけを見る（中身の読み取りは任意） |

- **入力言語の扱い**：**回答言語＝利用者の入力言語**（承認者の言語）。差し戻し理由の下書きだけは**申請者の言語**で書いてよく、その場合は地の文で「以下は申請者向けの文面です」と断る。金額・番号・品番は原文のまま
- **入力の欠け・曖昧さ**：①金額が本文に無い → 「金額が読み取れません。合計金額（税込・通貨）を教えてください。規程の区分が金額で決まるためです」。②過去申請が未接続 → 比較を行わず「過去の同種申請は照会できません（台帳が未接続）」。③種別が不明 → 規程を特定せず、種別を選ばせる

## 3. 観点（LLM に守らせる業務ルール）
1. **要点は 3 行に固定**（何を・いくらで・どうしたいか）。4 行以上にしない
2. **過去の同種申請は数量・単価・合計・相手先・発注間隔の 5 項目で並べる**。項目を増やさない（承認者が横に読めなくなる）
3. **規程は条文を引用し、しきい値（金額区分・相見積の要否・単価契約の対象）に対して申請がどちら側かを明示する**。規程に無いしきい値を作らない
4. **判断に効く点は ❗（規程上の不備）／⚠（確認が要る）／✅（事実として妥当）の 3 段**に分ける
5. **社内の情報で確かめられないこと（市況・相場・他社価格）は「未確認」と書き、妥当か否かを断定しない**。確かめる手（相手先への確認事項）を示すにとどめる
6. **承認も差し戻しもしない**。差し戻し理由は下書きとして示し、「押すのは人」と明記する
7. 差し戻し理由の下書きは**理由を規程に寄せる**（申請者の判断を責めない）・**こちらが引き取る作業を書く**・**期限を先に置く**の 3 点を含める
8. **DC-05 の領域（申請者向けの記載漏れ検出）に踏み込まない**。書き直し案そのものは出さず、差し戻しの理由と依頼事項までにとどめる

- **不確実なときの定型**：ja「この値上げが妥当かどうかは社内の情報では判断できません（未確認）。相手先に値上げ通知の有無と根拠を確認するのが最短です。」／zh「涨价是否合理，用公司内部的信息无法判断（未确认）。最快的做法是向对方确认是否有涨价通知及其依据。」
- **出力の粒度と形式**：見出し 6 つ（要点 3 行・過去の同種申請との違い・該当規程の該当箇所・判断に効く点・差し戻すなら理由・差し戻さない選択肢）。`PC-01`／BPMS へ渡す分は §5-3 の JSON

## 4. Dify 構成
- **アプリ種別**：**Chatflow**。承認者は必ず追い質問をする（「値上げは妥当か」「角が立たない書き方で」＝台本 ja#2・ja#3）。文脈を保つ必要がある
- **ノード列**
  ```
  Start（request_type・request_body・request_id・attachments_count）
    → 言語判定（PC-07）
    → Code（金額・数量・相手先・品目の抽出。正規化）
    → HTTP Request（PC-04：申請台帳 → 同一品目・同一相手先の過去 24 か月の申請）
    → Knowledge Retrieval（DC-12 規程 KB：種別でメタデータフィルタ → 該当条文）
    → Code（しきい値判定：金額区分・相見積の要否・単価契約の対象。LLM に判定させない）
    → LLM 1（要点 3 行・過去との違い・判断に効く点の 3 段分け）
    → LLM 2（差し戻し理由の下書き・差し戻さない選択肢）
    → Template（6 ブロック）／Code（JSON）
    → Answer
  ```
- **Knowledge**：KB 名 `DC-12 社内規程`（DC-05・KN-03 の KB を共用してよい）。投入＝`RULE-10` 購買管理規程、`RULE-07` 費用管理規程、`FIN-TRV-01`／`FIN-ENT-01` 経費規程。チャンクは条文単位。**メタデータに `threshold_amount` `threshold_kind` を持たせ、Code ノードの判定に使う**。更新経路は Outline（`PC-05`）
- **プラグイン／ツール**：`http-request`（申請台帳・BPMS の読み取り）
- **モデル**：既定 chat モデル。しきい値判定は Code ノードで行い、LLM に金額比較をさせない（`../implementation-guide.md` §6）
- **参照 DSL**：`DC-05` の DSL を雛形にする（規程 KB とメタデータフィルタが共通）。DC-05 が未投入の場合は `KN-03` の DSL
- **入出力変数**

| 名前 | 型 | 必須 | 説明 |
|---|---|---|---|
| `request_type` | string | ✓ | 申請の種別（`purchase`／`capex`／`expense`／`travel`／`other`） |
| `request_body` | string | ✓ | 申請本文 |
| `request_id` | string | | 申請番号（例 `PR-25-0417`） |
| `attachments_count` | number | | 添付件数（見積の社数の判定に使う） |
| `approver_role` | string | | 承認者の役職（承認ルートの判定に使う） |
| `lang` | string | | 出力言語 |

## 5. プロンプト
### 5-1. System
```text
あなたは製造業の工場で申請を承認する立場の人の補助です。
回ってきた申請を承認者の側から読み、要点・過去の同種申請との違い・該当規程を示します。

守ること:
1. 要点は 3 行に固定する（何を・いくらで・どうしたいか）。4 行以上にしない。
2. 過去の同種申請は、数量・単価・合計・相手先・発注間隔の 5 項目だけで並べる。項目を増やさない。
3. 規程は条文を引用し、申請がしきい値のどちら側にあるかを明示する。規程に無いしきい値を作らない。
   しきい値の判定結果は与えられた値をそのまま使い、自分で金額を比較し直さない。
4. 判断に効く点は ❗（規程上の不備）／⚠（確認が要る）／✅（事実として妥当）の 3 段に分ける。
5. 社内の情報で確かめられないこと（市況・相場・他社価格）は「未確認」と書き、妥当か否かを断定しない。
   確かめる手（相手先への確認事項）を示すにとどめる。
6. 承認も差し戻しもしない。差し戻し理由は下書きとして示し、押すのは人だと明記する。
7. 差し戻し理由の下書きには次の 3 点を必ず含める。
   (a) 理由を規程に寄せる（申請者の判断を責めない）
   (b) こちらが引き取る作業を書く（申請者に丸投げしない）
   (c) 期限を先に置く（相手の納期の逼迫を理解している姿勢を示す）
8. 申請の書き直し案そのものは出さない（それは申請者向けの別サービスの役目）。
9. 回答はユーザーの入力言語で書く。差し戻し理由の下書きだけは申請者の言語で書いてよいが、
   その場合は地の文で「以下は申請者向けの文面です」と断る。地の文で 2 つの言語を混ぜない。

判断できないときの定型:
ja「この値上げが妥当かどうかは社内の情報では判断できません（未確認）。相手先に値上げ通知の有無と根拠を確認するのが最短です。」
zh「涨价是否合理，用公司内部的信息无法判断（未确认）。最快的做法是向对方确认是否有涨价通知及其依据。」
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| しきい値 | Code ノードの判定と本文が一致 100%（LLM が判定し直さない） | 自動（突合） |
| 規程の引用 | 引用条文が実在し `doc_id` が正しい ≥ 98% | 自動＋人手 |
| 3 行 | 要点が 3 行 100% | 自動 |
| 未確認 | 社内に根拠の無い事項を断定しない 100% | 負例セット 8 件（市況・他社価格） |
| 判断の非代行 | `decision` が null 100%・本文に「承認しました／差し戻しました」が無い 100% | 自動＋負例 |
| 差し戻し文 | (a)(b)(c) の 3 点が含まれる ≥ 95% | 人手 20 件 |
| 領域の分離 | 申請の書き直し案を出さない 100%（DC-05 の領域） | 負例 5 件 |
| 言語 | 入力言語で返答 100%。申請者言語の下書きには断り書き 100% | 人手 |
| 速度 | p95 < 25 秒 | Langfuse |

## 8. 別出しが必要なもの
- **申請台帳の照会**（`PC-04`）。過去 24 か月の同種申請が引けないと本サービスの価値の半分が出ない。既存の承認ワークフロー／ノーコード業務 DB の申請アプリを読み取り先にできる（設計書 `docs/handoff/2026-09-21-kintone-derived-usecases.md` §11）
- **規程のしきい値のメタデータ化**（`threshold_amount` `threshold_kind`）。条文をただ検索するだけでは「どちら側か」を安定して出せない。**規程 KB の投入時に人が付与する**（自動抽出はしない）
- **承認ルートの定義**（金額 → 役職の対応表）。`RULE-10` から人が書き写して `PC-06` に置く
- **無くても動く範囲**：規程 KB だけでも「要点 3 行＋該当条文」は出る。**過去との比較と、境目のどちら側かの判定が落ちる**（第 1 段はここ、第 2 段で申請台帳、第 3 段でしきい値メタデータ）

## 9. Outline Wiki との関係
- **読む**：`社内規程` コレクション（購買・稟議・経費・出張）を KB へ同期（`PC-05`）。DC-05・KN-03 と同じソース
- **書く**：使わない。承認・差し戻しの記録は承認ワークフロー（BPMS）が正本で、Outline に二重に残さない
