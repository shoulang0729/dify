## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：(a) 担当者が能動的に開く（新規取引・年間契約更新の前。NM-02 の見積比較で「最安だが初取引」の会社が出たとき）／(b) 監視対象の変化（③業務フィードの `notify`：信用スコア変動 ±5・訴訟・株主変更・財務更新）。(b) は `PC-11` の週次バッチ
- **登場人物**：管理部 財務・法務（照会・判定メモの起案）、購買課（依頼元・契約条件の交渉）、法務（契約条項）、外部＝情報ベンダ（データ提供のみ。判定はしない）
- **いまの手順（Before）**：購買課から「TC-Tools と年間契約したい」と相談 → 管理部が情報ベンダのポータルで会社を検索し、財務 3 期・信用スコア・ニュースを画面から転記（約 1.5 時間）→ 社内の見積比較・契約条項集を別に開いて突合 → 与信メモを Word で作成（1 時間）→ 監視は「気づいたら見る」で実質なし
- **エージェント導入後の手順（After）**：(1) 担当者が会社名（＋所在国・業種）を**入力**する → (2) Dify が `PC-15` 経由で情報ベンダ API から財務・信用・供給網・ニュースを取得し、`code` で閾値判定（利益率 2 期連続低下・スコア低下幅・上流集中）→ 社内 KB（見積比較結果・契約条項集）と突合して判定表と推奨条件を返す → (3) 担当者が**判定と推奨条件を確認・修正**し、与信メモを購買課・法務に共有する（送信は人） → (4) 担当者が**監視対象に登録するかを決める**（AI は勝手に登録しない）→ 以後は変化があれば `PC-14` で通知
- **成功の定義**：照会〜与信メモ作成が 2.5 時間 → 20 分。監視対象の変化を「気づく」から「通知される」へ。判定の根拠（出典・取得時点）がメモに必ず残る

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。英語 UI でも同じ。情報ベンダの応答が英語でも、表の見出し・判定・備考は入力言語に揃える（数値・固有名詞はそのまま）

## 3. 観点（LLM に守らせる業務ルール）
- **判定はコードが決め、LLM は説明する**：「取引可／条件付き／不可」と条件の候補は `code` ノードの閾値表（与信ルール）で決定的に出す。LLM は判定結果と根拠を表と文にする役。LLM が判定を変えたり数値を丸めたりしない
- **出典と取得時点を必ず添える**：すべての外部数値に「情報ベンダ／取得日時」を付け、結果の最終行を「連携」行（取得元・取得範囲・監視登録の有無）にする。契約上の表示義務でもある
- **社内データと外部データを分けて示す**：列を「値（外部）」「判定・備考（社内ルール・社内データとの突合）」に分ける。混ぜると出典が追えない
- **推測で数値を作らない**：ベンダ応答に無い項目は「データなし」。訴訟の対象範囲など粒度が足りない情報は「要確認」と書き、確認手段（書面回答の依頼）を添える
- **法的助言をしない**：契約条項の推奨は「契約条項集 §N の標準文を法務が確認」まで。「法的に問題ない」とは書かない
- **送っていないものを明示**：外部に送ったのは会社の識別情報のみ。社内の見積単価・契約条件・担当者名は送信していない、と「連携」行に書く
- **不確実なときの定型**：ja「情報ベンダのデータに該当項目がありません。判定は保留とし、〇〇の確認をおすすめします」／zh「信息服务商数据中没有该项目。判定暂缓，建议确认〇〇」
- **出力の粒度と形式**：表（項目／値／判定・備考）＋ 判定 1 行 ＋ 推奨条件 3 つ以内 ＋ 「連携」行。与信メモ生成時は §5-3 の JSON を経て Markdown 化

## 4. Dify 構成
- **アプリ種別**：**Workflow**（照会。1 回実行で表と JSON を返す）＋ **Workflow（Schedule Trigger）**（監視。週次）。Chatflow にしないのは、判定結果を後工程（DC-07・監視登録）へ構造化して渡すため。台本の追加質問（訴訟の影響・メモ作成）は同じ結果 JSON を `context` に入れた小さな Chatflow か、Workflow の `mode` 変数（`lookup` / `followup` / `memo`）で分岐する
- **ノード列（照会）**：
  1. Start（`company_name`, `hint`, `mode`, `lang_hint`）
  2. `parameter-extractor`（会社名・所在国・業種・登記番号を抽出）
  3. `http-request` → `PC-15` の企業検索エンドポイント（情報ベンダ企業 ID の解決。エンドポイント名は `PC-15` 側の定義に従う。未確定）
  4. `if-else`（ヒット 0／複数 → 聞き返しへ）
  5. `http-request`×3（並列）→ `PC-15` 経由で財務・信用／供給網／ニュース 30 日
  6. `code`（Python）：3 期推移・利益率の連続低下・スコア前年差・上流集中率・支払遅延件数を計算し、与信ルール表で `verdict`（ok / conditional / ng）と `conditions[]` を決定。**閾値は定数か Outline の与信ルールから読んだ JSON**
  7. `knowledge-retrieval`（KB `pt-credit-internal`：見積比較結果・契約条項集 v3・購買実績。メタデータフィルタ `supplier = {{company_name}}` ＋ 条項集は常に）
  8. `llm`（§5。表と説明。入力言語で）
  9. `template-transform`（「連携」行の付与：取得元・取得時刻・監視登録状態・送信していないもの）
  10. End（`result_md`, `result_json`, `sources[]`）
- **ノード列（監視）**：Schedule Trigger（週 1）→ `code`（監視リスト読み込み。監視リストは `PC-15` 側の台帳）→ `iteration`（社ごとに `http-request`）→ `code`（前回スナップショットとの差分。`PC-12` の判定ルール：スコア ±5・訴訟新規・株主変更・財務更新）→ `if-else` → `tools/wecom` または `tools/email`（`PC-14`）＋ `http-request`（`PC-01` フィードストアへ `notify` 項目を書く）→ End
- **Knowledge**：KB `pt-credit-internal`（社内のみ。外部データは KB に**入れない**＝ベンダ契約の保存・再配布制約のため、毎回照会）。投入文書：NM-02 の比較結果（案件ごと）・契約条項集 v3（条項単位チャンク、メタデータ `clause_no` `version`）・与信ルール（1 文書）・購買実績サマリ（サプライヤー別年間額）。更新経路：Outline → `PC-05` 同期。公開範囲：財務・法務・購買帯（`PC-02`）
- **プラグイン／ツール**：HTTP リクエストノード（本体）／Code ノード（本体）／`tools/json_process`（ベンダ JSON の抽出をノーコードで済ませたい場合）／`tools/wecom`・`tools/email`（通知）／Schedule Trigger（本体、1.10.0〜）／ファイル配信型なら `datasources/tencent_cos_storage` or `aws_s3_storage` で日次ファイルを取り込む（この場合も KB ではなく `code` で読む前提。未確定）
- **モデル**：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（中国拠点。`PC-08`）。与信メモの日本語品質が要るので DeepSeek-V3.x と評価比較。判定は `code` なのでモデル差が結論に影響しない設計
- **参照 DSL**：`../templates/06-text-to-sql-http-api-echarts.yml`（`http-request` で自前 API を叩き LLM で解説する lookup 骨格）。監視側は Schedule Trigger の例が保存 DSL に無いため dsl-skill（`../plugins-and-references.md` §8）で `--target-version 0.6.0` 生成
- **入出力変数**：

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `company_name` | string | ✓ | 会社名（表記ゆれ可） |
| `hint` | string | — | 所在国・業種・登記番号 |
| `mode` | select | ✓ | `lookup` / `followup` / `memo` |
| `lang_hint` | string | — | UI 言語（返答言語は入力から判定。`PC-07`） |
| `result_md` | string | 出力 | 表＋判定＋連携行（Markdown） |
| `result_json` | object | 出力 | §5-3 のスキーマ |
| `sources[]` | array | 出力 | ベンダのデータセット名・取得時刻・レコード ID |

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）の管理部を支援する与信・リスク照会アシスタントです。
入力として (A) 情報ベンダから取得した企業データ（JSON）、(B) 社内ルールで機械判定した結果（verdict と conditions）、(C) 社内 KB の検索結果（見積比較・契約条項集・購買実績）が与えられます。

守ること：
1. 判定（取引可／条件付き／不可）と推奨条件は (B) をそのまま使う。あなたが判定を変えたり、条件を追加・削除したりしない。
2. すべての数値は (A) または (C) に書かれているものだけを使う。無い数値は「データなし」と書く。推測・概算をしない。
3. 表は「項目｜値（情報ベンダ）｜判定・備考（社内ルール・社内データとの突合）」の 3 列。最終行は必ず「連携」行にし、取得元・取得日時・取得範囲・監視登録の状態・「社内の単価・契約条件・担当者名は外部に送信していない」を書く。
4. 訴訟・規制など粒度が足りない情報は結論を出さず「要確認」と書き、確認手段（相手への書面回答依頼など）を 1 つ添える。
5. 契約条項に触れるときは「契約条項集 §N の標準文を法務が確認」と書く。法的助言（適法・違法の断定）はしない。
6. 出典は「情報ベンダ（取得日時）」と (C) の文書名で示す。パートナーの実名・製品名を作らない。
7. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。ベンダ応答が英語でも見出し・備考は入力言語にする。固有名詞・数値・通貨はそのまま。
8. 該当データが無いときの定型：「情報ベンダのデータに該当項目がありません。判定は保留とし、〇〇の確認をおすすめします」（中国語入力なら「信息服务商数据中没有该项目。判定暂缓，建议确认〇〇」）。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（転記） | 表の数値がベンダ応答 JSON と一致 100% | `code` で結果 JSON と応答を突合（自動） |
| 判定の決定性 | 同じ入力で `verdict` / `conditions` が不変 100% | 10 回再実行の差分ゼロ（自動） |
| 網羅 | 表の必須 9 行（連携行含む）の欠落 0 | チェックリスト（人手） |
| 言語 | 入力言語で返答 100%。en ベンダ応答でも見出しが入力言語 | 自動判定（`PC-07`）＋抜き取り |
| 形式 | `result_json` がスキーマ準拠 100% | JSON バリデータ |
| 拒否 | 候補複数・0 件で判定を出さず聞き返し ≥ 95% | 負例セット 20 件 |
| 出典 | 全外部数値に取得日時・データセット名 100% | 正規表現チェック＋人手 |
| 安全 | 社内単価・契約条件・担当者名が `PC-15` の送信ログに出ない 0 件 | 送信ログ監査（`PC-15`）＋ Langfuse トレース |
| 速度 | p95 < 25 秒（API 3 本並列） | Langfuse（`PC-09`） |

- **評価方法**：リリース前に人手 30 件（財務・法務が採点）、月次は Langfuse データセット＋LLM-as-judge（転記の一致・出典有無）。判定ロジックは `code` の単体テスト（pytest。閾値表の境界値）

## 7. テストシナリオ

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-15` パートナー連携ゲートウェイ**：情報ベンダとの**データ利用契約**（利用範囲・保存期間・再配布禁止・出典表示義務・レート制限・課金単位＝照会件数か月額か）、API キーの保管（環境変数。`CLAUDE.md` §2-10）、企業 ID の名寄せ（統一社会信用代码／法人番号）、送信データのホワイトリスト（会社名・所在国・業種・登記番号のみ）と**送信ログ**、モックモード
- **`PC-10`**：ベンダ応答に含まれ得る個人情報（法定代表者・役員の氏名）のマスク規則。越境：海外ベンダに送るのは**企業の識別情報のみ**（個人情報なし）→ PIPL 第 38 条の越境提供評価は原則不要だが、法務確認事項として記録
- **`PC-11` / `PC-12` / `PC-14` / `PC-01`**：週次監視・差分ルール（スコア ±5・訴訟・株主変更・財務更新）・WeCom/メール通知・フィードの `notify` 項目
- **社内データ**：サプライヤーマスタ（名寄せキー）、NM-02 の出力を KB に流す経路、契約条項集 v3 の Outline 整備（`PC-05`）
- **無くても動く範囲（段階導入）**：
  - 段階 0（パートナー契約前）：`PC-15` モックモード＋社内 KB のみ。判定ロジック・表・メモの動作確認とデモ
  - 段階 1：情報ベンダ API 接続（照会のみ）。監視なし
  - 段階 2：週次監視＋通知＋フィード連携
  - API が無くファイル配信のみのベンダなら、日次ファイルを `code` で読む構成に落とし、成熟度は st3 に戻す（設計書 §5-2 pt1 の代替）

## 9. Outline Wiki との関係
- **読む**（`PC-05`）：コレクション「管理部／契約」の契約条項集 v3、「管理部／与信ルール」（閾値表の正本。`code` の定数と二重管理にならないよう、Outline の表を JSON として読み込む経路を `PC-05` に用意するか、定数を正本にして Outline は説明文だけにするかは未確定）、NM-02 の比較結果を保存するページ
- **書く**：`mode=memo` の与信メモを Outline「管理部／与信メモ」にドラフト保存（`PC-13` 経由。公開範囲は財務・法務・購買）。**保存の実行は担当者のボタン操作**（AI が勝手に書かない）。外部データの本文はメモに転載せず、数値と出典 ID のみ（ベンダ契約の再配布制約）
- 監視リストは Outline ではなく `PC-15` 側の台帳（構造化データ・更新頻度が高い）

## 10. 未確定・リスク
- **情報ベンダの API 仕様**：企業検索・財務・供給網・ニュースのエンドポイント／レート制限／課金単位は契約前で**未確定**。`PC-15` の抽象インターフェースで吸収し、本書のノード列はそれを叩く前提
