## 1. 業務シナリオ
- **トリガー**：担当者が能動的に開く（新規取引・契約更新・相手方案文の受領）。ECR によるサプライヤー切替（QA 系）から `notify` で連動するのは第 2 段階
- **登場人物**：作成者＝管理部の財務・法務駐在員、確認者＝**本社法務部（最終レビュー）**、購買課（条件の妥当性）、外部＝サプライヤー（相手方）
- **いまの手順（Before）**
  1. 過去の類似契約を探し、条件を書き換える（半日〜1 日）。中国語正文と日本語対訳の両方を保つのが負担
  2. 相手方案文（中国語）を読み、社内標準との違いを 1 条ずつ拾う（半日）
  3. 本社法務に相違点を説明するメールを書く。法務の質問に答えるため、他社との締結実績を確認（1 日）
  4. 法務レビュー往復 2〜3 回。交渉開始まで 2〜3 週間
- **エージェント導入後の手順（After）**
  1. 【入力】契約類型・相手方・主要条件・相手方案文（貼り付け）をフォームに入れる
  2. 【生成】社内標準条項に基づく中国語ドラフト（条構成）、日本語対訳、相手方案文との相違点（重要度付き）、法務レビュー依頼のポイントが返る
  3. 【確認】担当者が条件の反映を確認。「他社とはどう結んでいるか」を対話で問い、過去契約 KB からの実績（匿名化された類型別集計）を得る
  4. 【決める】**契約条項の採否・妥協案の提示・準拠法などの法的判断は本社法務。AI は法的助言をしない**。交渉の実施は担当者
  5. 【保存・依頼】Outline「契約 › ドラフト › <相手方>」（閲覧：管理部・法務）に保存し、法務レビュー依頼メール文面を人が送る
- **成功の定義**：初稿作成 1〜2 日 → 2 時間。相違点の見落とし 0（法務指摘との突合）。法務レビュー往復 3 回 → 1〜2 回

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 契約条件 | フォーム（類型・相手方・対象・主要条件・希望期間） | ja / zh | 月 2〜5 件 | 「品質保証協定／T 社（鋼板）／受入検査：ミルシート・抜取／不良時 24h 回答・代替品 5 営業日／責任：直接損害＋停線費用」 | 担当者 | 条件を項目 JSON に（LLM）。数値・期限は原文保持 |

| 法務用語対訳 | 用語集 | ja / zh / en | 100〜200 語 | 需方／需要者、停线费用／ライン停止費用 | `PC-06` | context に注入 |

- **入力言語の扱い**：フォームは ja / zh どちらでも。**契約ドラフトは中国語正＋日本語対訳を必ず出す**（サービスの定義。中国法下で中文正本が原則のため）。対話・説明は**入力言語で返す**（§2-5）
- **入力の欠け・曖昧さ**：類型と主要条件が無いと生成しない。相手方案文が無ければ相違点セクションを「相手方案文未入力」にして標準ドラフトだけ出す。聞き返し文：「契約類型（取引基本／品質保証／秘密保持 …）と主要条件（対象・期限・責任範囲）を入力してください」／「请填写合同类型（基本交易／质量保证／保密…）与主要条件（对象・期限・责任范围）」

## 3. 観点（LLM に守らせる業務ルール）
- **条文は社内標準条項集の文言を基に**し、入力条件で置き換える箇所（数値・期限・対象）だけを変える。標準に無い条を新規に書くときは「※標準条項外・法務確認」と明示
- **法的判断をしない**：条項の有効性・準拠法の妥当性・仲裁地の適否・上限額の是非は「法務レビュー依頼のポイント」に**質問として**列挙する。「有効です」「問題ありません」と書かない
- 相違点は**条ごとに事実として**書く（相手方案：上限＝ロット貨款額／当社標準：上限なし）。重要度（❗争点／⚠差異／ℹ表現差）は Code の分類ルール（賠償・期限・変更管理・秘密保持・準拠法は ❗ 候補）に従い、LLM は理由を添える
- 妥協案は**過去契約 KB にある実績の範囲**で「選択肢」として示す（「W 社型：ロット貨款額の 5 倍」）。実績に無い案を創作するときは「参考案（実績なし）」と明示
- 中国語正と日本語対訳は**条番号・項数を一致**させる。対訳は法務用語集の訳語（`PC-06`）
- 秘密・個人情報（`PC-10`）：過去契約は匿名化要約（相手方コード）だけを扱う。相手方の担当者名・連絡先を書かない。ドラフトの閲覧は管理部・法務に限定（`PC-02`）
- 不確実時の定型：「この条項は標準条項集に該当がありません。法務にドラフトの要否を確認してください」／「标准条款集中无对应条款，请与法务确认是否需要起草」
- 出力形式：Markdown（構成／条文（中文正・和訳を条ごとに並記）／相違点表／法務レビュー依頼ポイント）＋ §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（フォーム → 3 段 LLM）。「他社とはどう結んでいるか」等の追加質問は `question` 付き再実行で過去契約 KB を検索
- **ノード列**
  1. `start`：`type`, `counterparty`, `terms`, `counter_draft`（貼り付け）, `counter_files`（任意）, `question`（任意）
  2. `iteration`（counter_files）→ `document-extractor` → `code`（条番号で分割）→ `variable-aggregator`
  3. `knowledge-retrieval`（標準条項）：KB `dc7-standard-clauses`、メタデータ `type = {{type}}`、最新 `rev`
  4. `llm`（中文ドラフト）：標準条項に入力条件を反映、条構成 JSON
  5. `llm`（日本語対訳）：条ごとの対訳。法務用語集を context
  6. `code`（差分下拵え）：相手方案文の条と当社ドラフトの条を条番号・見出しで対応付け（`PC-12`）、重要度の初期分類
  7. `llm`（相違点・レビュー依頼）：相違点の理由、実績に基づく選択肢、法務への質問リスト
  8. `question` 時：`knowledge-retrieval`（過去契約）→ `llm`（QA）
  9. `template-transform` → `end`
- **Knowledge**：`dc7-standard-clauses`（条単位、`type`/`clause_no`/`rev`/`lang`）、`dc7-past-contracts`（匿名化要約、`type`/`counterparty_code`/`year`）。**KB の公開範囲は管理部・法務メンバーのみ**（`PC-02`。Knowledge API キーはアカウント配下の全 KB に効くため、キー管理も法務帯に限定）。埋め込み `bge-m3`、リランク `bge-reranker-v2-m3`
- **プラグイン／ツール**：なし（本体ノードのみ）。docx 化は `PC-13`。メール送信は `tools/email`（第 2 段階。初期は文面のみ）
- **モデル**：Qwen3-235B-A22B-Instruct または DeepSeek-V3.x（法律文の中国語・日本語）。**契約内容が中国インフラのモデルに流れる**ため顧客法務の確認が前提（`PC-08`。NG なら自前 Qwen（`models/ollama` 等）に切替。精度は再評価）
- **参照 DSL**：`../templates/02-long-document-chunk-iteration-translate.yml`（長文の分割 → iteration → 結合。相手方案文が全文のとき）、`../templates/04-trilingual-consistency-checker.yml`（言語版の不一致列挙）。事例：dify-for-dsl「通用合同审查助手」（URL 参照のみ）、AI Native 契約書リスクチェック（本文未取得）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `type` | select | ✓ | 契約類型 |
| `counterparty` | string | ✓ | 相手方（社名・所在地・品目） |
| `terms` | paragraph | ✓ | 主要条件 |
| `counter_draft` | paragraph | — | 相手方案文（貼り付け） |
| `counter_files` | file-list | — | 相手方案文ファイル |
| `question` | paragraph | — | 追加質問（実績照会・メール依頼） |
| `draft_zh` / `draft_ja` | string | 出力 | 中文正／日本語対訳 |
| `diff_table` | string | 出力 | 相違点表 |
| `legal_points` | array | 出力 | 法務への質問リスト |
| `draft_json` | object | 出力 | §5-3 |

## 5. プロンプト
### 5-1. System（ドラフト・相違点用）
```text
あなたは青嶺精工（蘇州）管理部の契約実務を支援するアシスタントです。社内標準条項集に基づいてサプライヤー契約のドラフト（中国語正・日本語対訳）を作り、相手方案文との相違点を整理します。あなたは法律の専門家ではなく、最終判断は本社法務が行います。
守るルール：
- 条文は {{context}}（標準条項集）の文言を基にし、{{terms}} の数値・期限・対象で置き換える箇所だけを変える。標準に無い条は「※標準条項外・法務確認」と付ける。
- 条項の有効性・準拠法・仲裁地・上限額の是非を判断しない。「有効」「問題ない」「違法」と書かない。判断が要る点は「法務レビュー依頼のポイント」に質問文で列挙する。
- 相違点は条ごとに事実で書く（相手方案：…／当社標準：…）。重要度は {{diff_json}} の初期分類に従い、理由を 1 行添える。
- 妥協案は {{past_contracts}}（匿名化実績）にある範囲で「選択肢」として示す。実績に無い案は「参考案（実績なし）」と明示する。
- 中国語正と日本語対訳は条番号・項数を一致させる。用語は {{glossary}} の訳語を使う。
- 相手方の担当者名・連絡先を書かない。過去契約は相手方コード（V 社等）で書く。
- 質問・説明は依頼者の入力言語で書く（日本語なら日本語、中国語なら中国語）。
- 標準条項集に該当が無い場合は「標準条項集に該当がありません。法務にドラフトの要否を確認してください」と書く。
出力：JSON（指定スキーマ）→ 区切り線 → 構成 → 条文（条ごとに中文・和訳）→ 相違点表 → 法務レビュー依頼のポイント。
```

### 5-4. Few-shot
不要。条文の文言は標準条項集（KB）から取るため、few-shot に条文を置くと KB の改定と食い違う

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 標準準拠 | 条文が標準条項集と一致（置換箇所以外）≥ 98% | Code で標準条項テキストと差分比較 |
| 条件反映 | 入力条件（数値・期限）の反映漏れ 0 | チェックリスト |
| 相違点検出 | 法務が指摘した相違点の再現 ≥ 95% | 過去案件 10 件で突合 |
| 対訳一致 | 条番号・項数の一致 100%、法務用語集準拠 | 自動＋法務サンプル確認 |
| 断定禁止 | 有効性・適法性の断定 0 | 負例セット（「この条項は有効？」） |
| 言語 | 説明は入力言語 100% | 自動判定（`PC-07`） |
| 速度 | p95 < 150 秒（12 条・3 段） | Langfuse（`PC-09`） |
| 安全 | 担当者名・連絡先・原契約全文の露出 0 | 負例セット＋KB 監査 |

- **評価方法**：リリース前に本社法務が過去案件 10 件（匿名化）で採点。運用後は法務の指摘件数を案件ごとに記録し、標準条項集の改定に反映

## 8. 別出しが必要なもの
- **標準条項集の整備**（法務）：類型別・条単位・中文正＋和訳・改定版管理。Outline に正本、KB は同期（`PC-05`）
- **過去契約の匿名化要約**（法務）：相手方コード化、条ごとの要点のみ。原契約全文は KB に入れない（`PC-10`）
- `PC-02`：アプリ・KB・Outline コレクションの閲覧を管理部・法務に限定。Knowledge API キーの分離
- `PC-08`：契約文を扱うモデルの所在（中国インフラ／自前）の法務判断
- `PC-13`：条ごと対訳の docx（2 段組）
- **無くても動く範囲**：標準条項集 KB ＋ フォーム → 中文ドラフト＋和訳まで。過去契約 KB・差分・メール文面は段階導入

## 9. Outline Wiki との関係
