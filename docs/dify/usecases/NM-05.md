## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：本社から「なぜ」を問われたとき、月次報告の前に、工場長・課長が能動的に開く。③業務フィードでは `notify`（本社からの質問）
- **登場人物**：工場長（質問・示唆の採否）、製造課長（現場事実の裏取り）、情シス（DWH・スキーマの正）、人事（残業データの開示範囲）
- **いまの手順（Before）**：情シスに「ライン別・月別の残業と不良率を出して」と依頼（2〜3 日待ち）→ Excel で結合・散布図（1 時間）→ 相関の解釈は工場長の経験 → 本社報告までに 1 週間。深掘り（夜勤／昼勤）はもう一往復
- **エージェント導入後の手順（After）**：
  1. 工場長が**自然言語で質問**（ja/zh）：「ライン別に直近 6 か月の残業時間と不良率の関係を見せて」
  2. エージェントがスキーマ辞書（KB）を参照し **SELECT 文を生成** → `PC-04` の**読み取り専用 SQL API**で実行（許可テーブル・行数上限・タイムアウト）
  3. **Code ノードで**集計・相関係数・昼夜比較などの統計量を計算。**LLM は統計値を計算しない**
  4. LLM が結果表・示唆コメント（「相関は L2 だけ」）・次の深掘り候補を書き、`tools/echarts` でグラフを描く
  5. **人が決める場所**：示唆の採用・対策・本社への説明は工場長。エージェントは「データが示す事実」と「仮説」を分けて出す
- **成功の定義**：質問→表とグラフまで 1 週間 → 5 分。SQL による誤集計 0（定型クエリと一致）。示唆に必ず数値根拠が付く

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 質問文 | テキスト（`sys.query`） | ja / zh | 週 5〜10 件 | 「残業時間と不良の相関は？」 | 入力欄 | 言語判定、指標名の正規化（`PC-06`：不良率／不良率／defect rate） |
| DWH テーブル | SQL（読み取り専用ビュー） | 列名 en/zh | 生産・品質・勤怠・設備の月次〜日次 | `v_prod_daily(line, date, shift, output, defects)`、`v_overtime_monthly(line, month, ot_hours_per_person)` | DWH／各システムの ETL（`PC-04`） | **個人単位の勤怠はビューに含めない**（ライン×月に集約） |
| スキーマ辞書 | md | ja / zh | 年数回改定 | 列の意味・単位・結合キー・注意点 | Outline（`PC-05`）→ KB | チャンク（テーブル単位） |
| 定型クエリ集 | md（SQL 付き） | — | 10〜20 本 | 「ライン別月次 不良率」 | Outline → KB | few-shot として retrieval |
| 指標定義 | md | ja / zh | 年 1 回 | 不良率＝不良数÷生産数、稼働率の定義 | Outline → KB（NM-03 と共用 `nm-kpi-def`） | — |

- **入力言語の扱い**：質問の言語で答える（`CLAUDE.md` §2-5）。グラフのラベルも同言語。本社報告用に `report_lang` で日本語指定可
- **入力の欠け・曖昧さ**：期間が無い → 既定「直近 6 か月」を明示して実行。指標がスキーマ辞書に無い → 「{{metric}} に対応するデータがありません。定義済み指標：…」。結合できない組み合わせ → 「{{a}} と {{b}} は結合キーがありません」（**推定 SQL を実行しない**）

## 3. 観点（LLM に守らせる業務ルール）
- **SQL は SELECT のみ**。`INSERT/UPDATE/DELETE/DROP/ALTER`・複文・コメント・`;` 連結を生成しない。許可テーブル（ビュー）以外を参照しない。`LIMIT` を必ず付ける（既定 5,000 行）。Code ノードで**実行前に静的検査**（dsl-skill `database-tools.md` の方針）
- **統計量（平均・率・相関係数・差）は Code の出力を転記**。LLM は解釈のみ
- **相関≠因果**：「相関 +0.78」を「原因」と書かない。「関係が強い／弱い」＋「考えられる要因（仮説）」＋「確認方法」の 3 段で書く
- **個人を特定する出力をしない**（`PC-10`）：残業は「ライン×月の平均 h/人」まで。個人名・工号・「入社 1 年未満の 2 名」のような小集団の属性は出さない（n < 5 の集団は集約）
- **データの範囲・欠損を明示**：期間・件数・除外条件・欠損月
- **禁止**：データに無い事実（フィルター差圧・脱脂液濃度など、テーブルに無い項目）を書く／対策を決めたと書く
- **不確実時の定型文**：「このデータだけでは判断できません。{{missing}} を追加すれば確認できます」
- **出力形式**：結果表（Markdown）＋要点 3 行（事実／仮説／次の一手）＋グラフ（ECharts）。後工程用は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（多輪の深掘りが本質。会話変数に前回の結果 JSON を保持）
- **ノード列**：
  1. Start（`sys.query`／`report_lang` select 任意）
  2. Knowledge Retrieval ×2（`nm-schema-dict`：スキーマ辞書＋定型クエリ／`nm-kpi-def`：指標定義）
  3. LLM（`text2sql`）：スキーマ辞書と定型クエリを context に、SELECT 文と「使用テーブル・期間・集計単位」を JSON で出力（§5）
  4. **Code（`sql_guard`）**：静的検査（SELECT 単文・許可テーブル・LIMIT・禁止語）。NG → Answer（実行拒否の定型文）
  5. **HTTP Request**（`PC-04` 読み取り専用 SQL API：`{sql, timeout, max_rows}` → rows）。失敗 → Answer（接続失敗）
  6. **Code（`stats`）**：pandas 不使用でも可（標準ライブラリで平均・率・Pearson 相関・グループ比較）。n < 5 の集団を集約（`PC-10`）。ECharts オプション JSON も組み立て
  7. LLM（`insight`）：表・要点・仮説・次の一手（§5）
  8. `tools/echarts`（bar/line/pie）。散布図は LLM が ECharts JSON を書き Answer 内で描画（`templates/06` の方式）
  9. Answer（会話変数 `last_result` に §5-3 を保存）
- **Knowledge**：`nm-schema-dict`（Outline「DWH テーブル辞書」「定型クエリ集」を `PC-05` で同期。チャンクはテーブル単位）／`nm-kpi-def`（NM-03 と共用）
- **プラグイン／ツール**：HTTP リクエストノード・Code（本体）／`tools/echarts`／`tools/chart`（静止画）。`tools/vanna`（SaaS Text-to-SQL）は**使わない**（DB 接続情報が SaaS に出る）。DB 直結は顧客 DWH 製品に応じて `tools/snowflake`／`oracle_ai_db`／`supabase` 等。MySQL/PostgreSQL の公式汎用プラグインは無いため**自前 SQL API**（`templates/06` の Flask 方式）を既定
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（`text2sql`・`insight` とも）。DeepSeek-V3.x を SQL 精度で比較。労務データを含むため越境ゼロ要件なら `models/ollama`（`PC-08`）
- **参照 DSL**：**`../templates/06-text-to-sql-http-api-echarts.yml`**（自然言語→SQL→`http-request`→LLM→ECharts）、`../templates/07`（Excel 版フォールバック）
- **入出力変数**：`sys.query` string 必須／`report_lang` select 任意／会話変数 `last_result` object・`last_sql` string／出力 `answer` string・`chart` ECharts JSON

## 5. プロンプト
### 5-1. System（`text2sql`）
```text
あなたは製造 DWH に対する SQL 生成器です。与えられたテーブル辞書（許可されたビューのみ）と定型クエリを参考に、質問に答えるための SELECT 文を 1 本だけ生成します。
守ること：SELECT 単文のみ。辞書に無いテーブル・列を使わない。LIMIT 5000 を付ける。期間が無ければ直近 6 か月（辞書の date 列で）。個人単位の列（employee_id, name）は決して選択しない。結合キーが辞書に無い組み合わせは SQL を出さず、reason に理由を書く。
出力は JSON のみ：{"sql": "...", "tables": [...], "period": {"from": "...", "to": "..."}, "granularity": "line×month", "reason": null}
```
### 5-1b. System（`insight`）
```text
あなたは青嶺精工 蘇州工場 工場長のデータ分析アシスタントです。Code ノードが計算した統計結果（JSON）を読み、事実・仮説・次の一手に分けて説明します。
守ること：
1. 数値は JSON の値をそのまま転記する。相関係数・平均・率を自分で計算しない。
2. 「相関」を「原因」と書かない。事実（データが示すこと）→ 仮説（考えられる要因、データには無い）→ 確認方法（追加で見るデータ）の順。
3. データに無い項目（設備の状態、作業者の経験など）は仮説として明示し、事実と混ぜない。
4. 個人を特定できる記述をしない。n<5 の集団の属性を書かない。
5. 期間・件数・欠損（meta）を冒頭に 1 行で書く。
6. 出力言語：質問の言語で答える。日本語なら日本語、中国語なら中国語。report_lang があればそれに従う。
7. 対策を「決定」しない。「候補」として書く。
出力形式：「データ範囲」1 行 →「結果」表 →「要点」3 行（事実／仮説／次の一手）→「グラフ」（chart_spec に従う）。
```
### 5-2. User テンプレート（`insight`）
```text
【質問】{{sys.query}}
【実行 SQL（参考）】{{text2sql.sql}}
【統計結果（Code 出力・転記のみ）】{{stats.result}}
【指標定義（KB）】{{kb_kpi.result}}
【前回の結果（多輪）】{{conversation.last_result}}
```
### 5-3. 出力フォーマット（Code `stats` の JSON。会話変数・グラフ・DC-01 への引き渡し）
```json
{
  "meta": {"period": {"from": "2025-03", "to": "2025-08"}, "rows": 18, "granularity": "line×month", "excluded": [], "missing_months": []},
  "table": [{"line": "L2", "ot_hours_per_person_avg": 31.5, "defect_rate_pct_avg": 0.46, "pearson_r": 0.78, "n": 6, "max_month": {"month": "2025-07", "defect_rate_pct": 0.58}}],
  "comparisons": [{"line": "L2", "dim": "shift", "groups": [{"name": "day", "defect_rate_pct": 0.34}, {"name": "night", "defect_rate_pct": 0.61}]}],
  "chart_spec": {"type": "scatter|bar|line|pie", "x": "ot_hours_per_person", "y": "defect_rate_pct", "series": "line"},
  "privacy": {"aggregated_small_groups": true, "min_group_size": 5}
}
```
### 5-4. Few-shot
- **ja**：質問「ライン別に残業と不良率の関係」＋ JSON（L2 r=0.78、他 0.21／0.12）→ 要点：「事実：関係が強いのは L2 のみ（r=+0.78、月次 6 点）。L1・L3 は弱い。仮説：L2 は夜勤の不良率が昼勤の約 1.8 倍（0.61% vs 0.34%）で、夜勤帯の条件差が関係している可能性。次の一手：L2 夜勤の不良分類内訳と設備停止記録を月別に見る」
- **zh**：質問「L2 夜班发生了什么？」＋ JSON（不良分類内訳あり、設備・人員データなし）→ 「事实：L2 夜班不良 412 件中涂装颗粒 46%、涂膜厚度不足 22%（数据）。假设：与喷房过滤器状态或夜班检查频率有关——**本数据中无此项**，需另行确认。下一步：调取设备保全记录（过滤器更换日）与作业指导书的检查频率」

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| SQL 正確性 | 定型 20 問で生成 SQL の結果が正解クエリと一致 ≥ 90% | 評価セット（ダミー DB） |
| SQL 安全 | 禁止語・非許可テーブル・LIMIT 欠落の通過 0 | 負例 30 本を `sql_guard` に流す |
| 統計の正確性 | Code の相関・平均が pandas/Excel と一致（±0.01） | 単体テスト |
| 転記の忠実性 | 回答中の数値が JSON と全件一致 | 自動 |
| 因果表現 | 「原因は」等の断定 0 | LLM-as-judge＋人手 |
| 個人情報 | 個人名・工号・n<5 属性の出力 0 | 負例セット（`PC-10`） |
| 言語 | 質問言語で回答 100% | 自動判定 |
| 速度 | p95 < 30 秒（SQL 10 秒上限含む） | Langfuse |

- **評価方法**：リリース前に情シス＋工場長で 20 問。月次で Langfuse データセット（SQL 一致は自動、表現は LLM-as-judge）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **結合可能な DWH／ビュー**（`PC-04`）：生産・品質・勤怠（ライン×月集約）・設備停止。読み取り専用ユーザー・許可ビューのみ・タイムアウト・行数上限。**これが本体（△ の理由）**
- **読み取り専用 SQL API**（`PC-04`）：`templates/06` の Flask 方式。SQL 静的検査を API 側でも二重に
- **スキーマ辞書・定型クエリ集**（Outline → `PC-05` → KB）：Text-to-SQL の精度はここで決まる
- **労務データの開示範囲**（`PC-02`／`PC-10`）：残業は集約のみ。閲覧ロールは工場長・課長・人事
- **無くても動く範囲**：DWH が無い段階は **NM-03 の集計 JSON（xlsx）をアップロードして Code で統計→示唆**を出す「upload 版」で表現・示唆の品質を先に検証。Text-to-SQL 部分は後付け

## 9. Outline Wiki との関係
- **読む**：`PC-05` で「DWH テーブル辞書」「定型クエリ集」「指標定義」を KB に同期。辞書の改訂＝Text-to-SQL の精度改善なので、情シスが Outline を更新する運用を先に決める
- **書く**：しない。分析結果は工場長が DC-01（本社報告）に持ち込む。「よく使う質問と SQL」を定型クエリ集に人が追記するループは推奨（未確定）
