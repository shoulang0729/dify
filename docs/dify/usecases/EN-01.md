## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：顧客（K 社）から要求仕様書・作業標準書の改訂版が届いたとき（③業務フィードの `notify`）。適用開始日が期限（`due`）
- **登場人物**：顧客仕様担当（比較・影響判定・起票）、生産技術（工程への影響）、文書管理（社内文書の改訂）、営業（顧客への確認）、外部：K 社（発行元）、塗装外注 S 社（条件変更の相手）
- **いまの手順（Before）**：42 ページを Rev.C と並べて目で読む（半日〜1 日）→ 変更に気づけない箇所が残る → K 社用語（涂层厚度／限度样件）を社内呼称に頭で変換 → 影響する社内文書を記憶で探す → 起票漏れが監査で指摘される
- **エージェント導入後の手順（After）**：
  1. 担当者が**旧版と新版の PDF を指定**（Rev.C／Rev.D）
  2. `PC-03` が両版を Markdown 化（表・図番を保持）、**`PC-12` が章単位に正規化して機械的に差分**を取る（追加／削除／変更、章番号・ページ付き）
  3. LLM が各差分に**意味づけ**（管理項目／検査方法／記録様式／トレーサビリティ等への影響区分）と、用語集（`PC-06`）による**K 社用語→社内呼称**の対応を付ける
  4. 社内文書一覧 KB から**対応文書の候補**（検査基準書 QS-xxxx 等）を引く
  5. **人が決める場所**：影響の大小・工程変更の要否・起票する文書と担当・期限は担当者と生産技術が決める。エージェントは「差分＋影響区分＋候補文書」まで。**起票そのものはしない**（ドラフトリスト出力）
- **成功の定義**：差分抽出の見落とし 0（機械差分）。42 ページの初期整理 1 日 → 30 分。起票リストに顧客条項番号が 100% 付く

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |

| 旧版仕様書 | PDF（電子中心、図表あり） | zh（K 社中国）／ja（本社経由） | 20〜60 ページ。改訂は年数回×顧客数 | `K社 要求規格書 SK-3310系 Rev.C（2024-11）` | 顧客ポータル／メール／文書管理 | `tools/mineru`（表は HTML、章見出し保持）→ Code で章単位に分割・空白/改行/全角半角を正規化 |

| 用語対応表 | csv / md | zh→ja（→en） | 顧客ごと 100〜300 語 | `涂层厚度 → 塗膜厚`、`限度样件 → 限度見本`、`首件 → 初品` | Outline／LG-02 の用語集（`PC-06`） | KB `en-glossary-<customer>` |

- **入力言語の扱い**：質問・指示の言語で答える（`CLAUDE.md` §2-5）。差分本文は原文言語のまま引用し、説明は入力言語。用語対応は「K 社用語（原文）→ 社内呼称（ja）」を必ず併記
- **入力の欠け・曖昧さ**：片方しか無い →「比較には 2 版が必要です」。版が同じ／順序が逆（日付で判定）→ 確認を求める。スキャン PDF で OCR 品質が低い（文字化け率 > 5%）→ 「OCR 品質が低く差分の信頼性が下がります。原本 PDF を入手してください」

## 3. 観点（LLM に守らせる業務ルール）
- **差分の抽出は機械（`PC-12`）が正**。LLM は差分を増やしたり減らしたりしない。「変更なし」の章について言及しない
- **影響区分は定義済みの語彙から選ぶ**：`control_item`（管理項目）／`inspection_method`（検査方法）／`record_form`（記録様式）／`traceability`／`change_management`／`retention`／`terminology`／`other`。根拠は新旧の原文引用
- **用語対応は用語集にある語だけ**。用語集に無い語は「（対応語なし・要登録）」とし、LLM が訳語を作らない
- **数値変更は原文どおり転記**（15 µm → 20 µm）。「何%が外れる」等の計算は SPC データがあり Code が計算した場合だけ
- **対応文書は KB にある文書番号だけ**。候補であり確定ではない（「候補：QS-3310」）
- **禁止**：K 社仕様の要求を緩めて解釈する／適用日を推定する（表紙・改訂履歴に書かれた日付のみ）／起票済みと書く
- **不確実時の定型文**：「§{{sec}} の変更は原文の表現が曖昧です。K 社への確認事項として挙げます」
- **出力形式**：差分一覧表（#／箇所／Rev.C→Rev.D／用語対応／影響区分／対応文書候補）＋要確認＋起票ドラフトリスト。後工程は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（2 ファイル→差分一覧）。台本 Q1（規格外率）Q2（起票リスト）は結果 JSON を会話変数に持つ **Chatflow** 版で第 2 段階
- **ノード列**：
  1. Start（`old_doc` file 必須／`new_doc` file 必須／`customer` select／`instruction` paragraph 任意／`spc_file` file 任意）
  2. `tools/mineru` ×2（旧・新。Markdown＋ページ番号）— 電子 PDF で表が単純なら Document Extractor でも可（**両版同じ手段**）
  3. **Code（`normalize_split`）**：章見出し（§n.n／第 n 章／附录）で分割、空白・全角半角・句読点を正規化、章 id をキーに dict
  4. **Code（`diff`、`PC-12`）**：章 id ごとに `difflib.SequenceMatcher`／`unified_diff`。追加／削除／変更を JSON（章・ページ・旧文・新文）。数値変更は正規表現で抽出（`15 µm → 20 µm`）
  5. Knowledge Retrieval ×2（`en-glossary-<customer>`／`en-doc-index`、クエリは差分ごとの章タイトル＋キーワード。Iteration 内）
  6. Iteration（差分ごと）→ LLM（`classify`）：影響区分・要約・用語対応・対応文書候補を JSON（§5）
  7. Code（`spc`、`spc_file` があるとき）：規格値に対する実測の規格外率・正規近似
  8. LLM（`compose`）：一覧表＋要確認＋起票ドラフトリスト
  9. Code → xlsx/CSV（`PC-13`）／End（`diff_report` JSON・`report_md`）
- **Knowledge**：`en-glossary-<customer>`（用語対応表、Q&A チャンク `tools/qa_chunk` が向く）／`en-doc-index`（社内文書一覧、メタ `doc_no`・`owner`・`spec_sections`）。仕様書本文は KB に入れない（版ごとの比較は Code）
- **プラグイン／ツール**：`tools/mineru`（自前デプロイ推奨、`PC-03`）／Document Extractor（本体）／Code（本体、`difflib` は標準ライブラリ）／`tools/dify_extractor`・`tools/qa_chunk`（KB 投入）／`tools/microsoft_excel_365`（任意）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（中国語仕様書の読解）。`classify` は Qwen3-32B で可（差分数×呼び出し）。代替 DeepSeek-V3.x／`models/ollama`
- **参照 DSL**：`../templates/04-trilingual-consistency-checker.yml`（複数版の LLM 不一致列挙。URL 取得を file 入力に置換）、`../templates/08-mineru-pdf-parse-demo.yml`（MinerU tool ノード＋iteration）、`../templates/02`（章分割→iteration の型）
- **入出力変数**：`old_doc`/`new_doc` file 必須／`customer` select 必須／`instruction` string 任意／`spc_file` file 任意／出力 `diff_report` object・`report_md` string・`ocr_quality` number

## 5. プロンプト
### 5-1. System（`classify`、差分 1 件ごと）
```text
あなたは自動車部品メーカー（青嶺精工）の品質保証担当を補助し、顧客要求仕様書の新旧差分 1 件に意味づけをするアシスタントです。
守ること：
1. 差分の内容は与えられた旧文・新文の引用に限る。差分を増やしたり要約で消したりしない。
2. 影響区分は次から 1〜2 個選ぶ：control_item / inspection_method / record_form / traceability / change_management / retention / terminology / other。
3. 用語対応は glossary にある語だけ使う。無い語は "term_map": [{"src": "...", "dst": null}] とし、訳語を作らない。
4. 数値は原文どおり転記する。計算しない。
5. 対応文書候補は doc_index にある文書番号だけ。無ければ空配列。
6. 原文の表現が曖昧なら "open_question" に顧客への確認事項を書く。
7. summary は request_lang（日本語または中国語）で書く。
出力は JSON のみ。
```

【社内文書一覧（KB）】{{kb_docs.result}}

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 差分の再現率 | 意図的に仕込んだ変更の検出 100%（機械差分） | 評価セット：ダミー仕様書に 10 か所変更を入れた 5 組 |
| 差分の適合率 | 抽出揺れによる誤検出 ≤ 5% | 同上（同一文書 2 回抽出の差分が 0 であること） |
| 影響区分 | 人手ラベルと一致 ≥ 85% | 30 差分を品質保証が採点 |
| 用語対応 | 用語集外の訳語生成 0 | 負例（用語集に無い語） |
| 対応文書 | KB 外の文書番号 0、候補の妥当性 ≥ 80% | 人手 |
| 言語 | 指示言語で説明 100%、原文引用は原語 | 自動判定 |
| 形式 | `diff_report` スキーマ準拠 100% | JSON バリデータ |
| 速度 | 42 ページ×2 で p95 < 4 分 | Langfuse |

- **評価方法**：リリース前に品質保証 2 名で 5 組。顧客ごとの初回は全件人手確認。月次 Langfuse

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-12` 差分検出エンジン**：章分割ルール（顧客ごとの見出し様式）と正規化の共通実装。QA-02（4M）・DC-06 と共用
- **顧客別用語対応表**（`PC-06`）：LG-02 用語統一の成果物を顧客別に切り出す。初期 100 語は人手
- **社内文書一覧 KB**（Outline → `PC-05`）：文書番号・所管・対応する顧客条項。これが無いと「対応文書」列が空
- **MinerU 自前デプロイ**（`PC-03`）：顧客仕様書は NDA 文書のため API 版は避ける
- **SPC データの取得**（`PC-04`、任意）
- **無くても動く範囲**：用語集・文書一覧が無くても「機械差分＋影響区分＋要約」は動く（用語・文書列が空）。ここから始め、顧客 1 社分の用語集を育てる

## 9. Outline Wiki との関係
- **読む**：`PC-05` で「顧客仕様 文書管理」コレクション（社内文書一覧・対応条項）と「用語集」を KB に同期
- **書く**：差分一覧（§5-3）を顧客仕様ページの「改訂メモ Rev.C→D」として**ドラフト保存**し、担当者が確認後に公開する運用は有用（監査対応の証跡になる）。Outline API を `http-request` で呼ぶ経路は `PC-05` の定義待ち — **未確定**

## 10. 未確定・リスク
- **PDF→Markdown の揺れ**が差分として出る問題：同一抽出器・同一正規化・章単位比較で抑える。表内の差分（HTML 表）は行単位比較に落とす — 実装で要検証
- **顧客ごとの章見出し様式**：K 社以外は分割ルールを追加。推奨：見出し正規表現を顧客設定として `PC-12` に持つ
- **図面・図の変更**は本サービスの対象外（テキスト差分のみ）。図の差し替えは「図番の変更」としてのみ検出
- **起票の自動化**（変更管理システムへの書き込み）は QA-02 と同じく第 2 段階（`PC-04`）。初期はドラフトリスト
- **越境**：顧客仕様書は NDA。MinerU・モデルとも自前／中国国内で完結させる（`PC-08`）
