## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：(a) 担当者が能動的に開く（PT-06 の戦略購買案の第 1 弾、または通常の見積依頼で配布・回収を外部化したいとき）／(b) 期限つき（③業務フィードの `due`：図面開示承認 9/9・NDA 9/12・回答締切 9/26。`PC-11` が前日リマインド）／(c) 監視対象の変化（`notify`：見積到着 n/5・比較表提出・状態遷移の Webhook）
- **登場人物**：購買課担当（起草・引き継ぎ・進捗確認）、購買課長（発注判断）、生産技術課長（図面の社外開示承認）、法務（NDA）、本社購買部（同等性・数量確定）、外部＝購買代行（配布〜一次交渉）、サプライヤー 5 社（**当社は直接やり取りしない**）
- **いまの手順（Before）**：担当者が過去 RFQ を修正（1 時間）→ 5 社にメール配布 → 質問対応・催促（2 週間で延べ 4 時間）→ 5 通の見積が形式バラバラで届き Excel で揃える（半日）→ 一次交渉（延べ 3 時間）→ 比較表を課長へ。図面は都度メール添付で送り、**誰に何を送ったかの記録が残らない**
- **エージェント導入後の手順（After）**：(1) 担当者が品目・数量・納期・条件・**代行範囲**をフォームに入力 → (2) Dify が RFQ 雛形・評価基準・図面メタを KB から引いて RFQ を起草 → 担当者が**確認・修正** → (3) 図面を添えるなら `human-input` で**生産技術課長が社外開示を承認**（承認者以外は進めない）→ (4) 担当者の**送信ボタン**で `PC-15` 経由の案件作成 API へ（RFQ 本文・**期限付き URL の図面〔NDA 先のみ〕**・評価基準・期限。**現行単価・現行契約先名は送らない**）→ 案件番号・配布先候補・スケジュールが返る → (5) 進捗は Webhook で `PC-01` に `notify`、担当者は案件番号で照会 → (6) 見積が揃うと比較表 JSON が届き、`code` が NM-02 の正規化ルールに変換して**NM-02 へ渡せる形**にする → (7) **発注判断・発注実行は当社**（課長 → GN-03）、契約は DC-07
- **成功の定義**：起草〜配布 1 日 → 1 時間（承認待ちを除く）、質問対応・催促・条件揃え 延べ 8 時間 → 0（代行側）。図面の開示先・期限・承認者が**記録に残る**。回収見積は NM-02 で自動比較できる

## 3. 観点（LLM に守らせる業務ルール）
- **RFQ に書くもの／書かないもの**：書く＝仕様（図番・要求性能）・数量・納期・価格の提示形式・条件・提出物・期限・評価基準の項目。**書かない＝現行単価・目標単価・現行契約先名・他社見積・社内の落としどころ**。入力に紛れても除去して警告
- **図面は URL 参照のみ**：図面本体を RFQ 本文に貼らない。「NDA 締結先のみ閲覧・期限付き」を本文に明記。開示承認の有無を `code` が確認し、未承認なら送信ボタンを出さない
- **状態はパートナー側が正**：進捗の質問には案件番号で照会した最新状態（5 段階：配布済／質問受付中／回答受領 n/N／条件揃え中／比較表提出）を答え、Dify の記憶で答えない
- **代行範囲を明示**：「発注実行と検収は当社」など範囲外の工程を結果に必ず書く。代行が交渉した内容も「一次交渉（購買代行）」と出典を付け、決定は当社
- **期限と当社残タスクを先頭に**：結果の先頭「連携」行に案件番号・引き継ぎ時刻・回答期限・送信したもの・**送信していないもの**。当社側の残タスク（開示承認・NDA・同等性確認）を ❗ で列挙
- **配布先候補は提案として**：パートナー DB からの候補は「購買代行の推奨」と書き、最終配布先は担当者が確定
- **不確実なときの定型**：ja「案件 {{case_id}} の最新状態を購買代行から取得できませんでした。案件番号でポータルを確認するか、時間をおいて再照会してください」／zh「无法从采购代理获取案件 {{case_id}} 的最新状态。请凭案件编号查看门户或稍后重试」
- **出力の粒度と形式**：items 6 行（連携／RFQ ドラフト要旨／配布先候補／評価基準／当社残タスク／スケジュール）。RFQ 全文は `PC-13` でファイル出力。比較表は §5-3 の JSON（NM-02 入力形式）

## 4. Dify 構成
- **アプリ種別**：**Workflow（form → 起草 → 承認 → 引き継ぎ）＋ Webhook Trigger（状態遷移・成果物）＋ 小さな Workflow（進捗照会・Addendum）**。Human-in-the-loop（Dify 1.15）を図面開示承認に使う
- **ノード列（起草・引き継ぎ）**：
  1. Start（`item`, `drawing_no`, `qty_period`, `delivery_terms`, `agency_scope`, `weights`（任意）, `attach_drawing`（bool）, `rfq_lang`）
  2. `parameter-extractor` → `code`（機密スクリーニング：現行単価・契約先名・他社見積のパターン検出 → 除去＋警告。図番を `PC-06` で本社図番に対応）
  3. `knowledge-retrieval`（KB `pt-rfq-internal`：RFQ 雛形・評価基準・図面メタ・開示ルール。フィルタ `drawing_no`）
  4. `llm`（§5。RFQ 本文〔`rfq_lang`〕＋要旨〔入力言語〕＋評価基準表）
  5. `if-else`（`attach_drawing` かつ開示区分 B → 承認へ／それ以外 → 6 へ）
  5a. `human-input`（生産技術課長：RFQ 要旨・図番・開示先の条件〔NDA 先のみ・期限付き〕を表示し **承認／却下**。`PC-02` のロールで承認者を限定）
  5b. `http-request`（`PC-04`：図面の**期限付き URL**を発行。NDA 先のみアクセス可の属性つき。未確定）
  6. `human-input` または担当者ボタン（送信内容プレビュー：RFQ・URL・評価基準・期限。**現行単価・契約先が無いこと**を表示）
  7. `http-request`（`PC-15` 経由：購買代行の案件作成 API → `case_id`・配布先候補・スケジュール）
  8. `http-request`（`PC-01`：`due`（回答期限・当社残タスク 3 件）と `notify`（引き継ぎ済））
  9. `template-transform`（items 6 行。先頭「連携」）→ End（`result_md`, `result_json`, `rfq_text`）
- **ノード列（戻り）**：Webhook Trigger（`{case_id, state, quotes_received, deliverable?}`）→ `code`（状態の正規化。比較表が来たら NM-02 入力形式へ変換：通貨・箱単位・寿命換算・支払条件の現在価値化）→ `http-request`（`PC-01` に `notify`）→ `tools/wecom`（`PC-14`：担当者へ「回答受領 3/5」）→ End（`nm2_input_json`）
- **ノード列（進捗・Addendum）**：Start（`case_id`, `mode`=`status`/`addendum`, `change_text`）→ `http-request`（`PC-15`：状態照会／Addendum 作成。締切 1 週間前を過ぎていれば延長要否を応答）→ `llm`（説明。入力言語）→ End
- **Knowledge**：KB `pt-rfq-internal`（購買帯＋生産技術 `PC-02`）：RFQ 雛形 v2、評価基準（既定の重み）、図面メタ・開示区分・承認者、NM-02 の正規化ルール、DC-07 の NDA 標準版へのリンク。**図面本体・現行単価・見積は KB に入れない**
- **プラグイン／ツール**：`human-input`（本体 1.15）／HTTP リクエストノード／Webhook Trigger／Code ノード／`tools/wecom`・`tools/email`（`PC-14`）／`tools/regex`（機密パターン）／`tools/microsoft_excel_365`（任意：比較表を Excel に）

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）購買課の RFQ 起草・引き継ぎアシスタントです。
入力として (A) フォーム（品目・図番・数量・納期・条件・代行範囲・評価基準の重み）、(B) 社内 KB（RFQ 雛形・評価基準の既定・図面メタと開示区分・NM-02 の正規化ルール）、(C) 購買代行からの応答（案件番号・配布先候補・スケジュール・状態）、(D) 開示承認の記録、が与えられます。

守ること：
1. RFQ 本文に書くもの：仕様（図番・要求性能・コーティング等）、数量と期間、納入先と納期、価格の提示形式（通貨・単位・税）、条件（支払・MOQ・保証・再研磨）、提出物、回答期限、評価基準の項目。書かないもの：現行単価、目標単価、現行契約先名、他社見積、社内の交渉方針。入力にこれらが含まれていても本文に入れず、末尾に「RFQ から除外した項目: …」と警告する。
2. 図面は本文に貼らず「図面 {{drawing_no}} は NDA 締結先のみ、期限付き URL で閲覧」と書く。(D) に承認記録が無いときは「図面開示は未承認。承認後に送信可」と明示する。
3. 結果の先頭は必ず「連携」行：引き継ぎ状態・案件番号・引き継ぎ時刻・回答期限（時刻とタイムゾーン）・送信したもの（RFQ 本文・図面 URL〔NDA 先のみ〕・評価基準）・送信していないもの（現行単価・現行契約先名）・進捗の照会方法。
4. 続けて「RFQ ドラフト（要旨）」「配布先候補（購買代行の推奨。最終確定は担当者）」「評価基準（購買見積の比較へ引き渡す）」「当社側の残タスク（❗ 期限つき）」「スケジュール」の順。
5. 代行範囲外の工程（発注判断・発注実行・検収）は当社が行うと必ず書く。代行の交渉結果には「一次交渉（購買代行）」と出典を付ける。
6. 進捗を聞かれたら (C) の最新状態だけを答える。自分の記憶や前回の状態で答えない。取得できなければ定型：「案件 {{case_id}} の最新状態を購買代行から取得できませんでした。案件番号でポータルを確認するか、時間をおいて再照会してください」／中国語「无法从采购代理获取案件 {{case_id}} 的最新状态。请凭案件编号查看门户或稍后重试」。
7. 言語：要旨・説明はユーザーの入力言語（日本語なら日本語、中国語なら中国語）。RFQ 本文は {{rfq_lang}} で書く（既定：中国語＋英語併記）。
8. パートナーは「購買代行」「購買エージェント会社」と呼ぶ。実名を作らない。サプライヤー名は当社が既に知るもの（現行取引先・与信照会済の候補）だけ書き、代行 DB の新規候補は「国内大手 2 社（購買代行の推奨）」のように属性で書く。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| RFQ の網羅 | 雛形の必須 8 項目（仕様・数量・納期・価格形式・条件・提出物・期限・評価項目）欠落 0 | チェックリスト（自動：見出し検出） |
| **機密除外** | RFQ 本文・送信データに現行単価・目標単価・現行契約先名・他社見積 0 件 | `PC-15` 送信ログ監査（正規表現）＋人手 |
| **開示ゲート** | 開示区分 B の図面が承認なしに URL 発行・送信されない 100%。URL に期限と NDA 先限定 | トレース確認＋`PC-04` ログ |
| 状態の正しさ | `mode=status` の状態が API 応答と一致 100%（記憶で答えない） | 自動突合 |
| 変換 | 比較表 → `nm2_input_json` の単価正規化が NM-02 のテストケースと一致 100% | pytest |
| 言語 | 要旨は入力言語 100%、RFQ 本文は `rfq_lang` 100% | 自動判定（`PC-07`） |
| 形式 | `result_json` スキーマ準拠 100% | JSON バリデータ |
| 期限管理 | `due` が `PC-01` に登録され、前日リマインドが届く | `PC-11` テスト |
| 速度 | 起草 p95 < 30 秒。承認待ちは除く | Langfuse |

- **評価方法**：リリース前に購買課長・生産技術課長・法務が架空 3 案件でレビュー（RFQ 品質・開示ゲート・NDA 文言）。月次：送信ログ監査・LLM-as-judge（除外項目の有無・出典付き）。`code` は pytest（機密パターン・正規化）

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-15`**：購買代行との**業務委託契約**（代行範囲の選択肢、成果連動手数料の定義＝「削減額」の基準、NDA、サプライヤー DB の利用、当社データの保存期間）、案件 API（作成・状態・Addendum・成果物）、送信ホワイトリスト（RFQ 本文・図面 URL・評価基準・期限。**現行単価・契約先名は禁止**）、送信ログ、モックモード
- **`PC-10`**：図面・仕様の機密区分と開示ルール（区分 B＝NDA 必須・承認者＝生産技術課長）、期限付き URL の期限（既定 30 日。未確定）、機密パターン検出。個人情報：原則なし（サプライヤー担当者名は代行側で保持）
- **`PC-04`**：社内ファイルサーバの期限付き URL 発行（NDA 先限定の属性つき）。無ければ暫定として代行のポータルへ**担当者が手動アップロード**（Dify は URL を持たない）
- **`PC-01` / `PC-11` / `PC-14`**：`due`（3 件の残タスク＋回答期限）・前日リマインド・見積到着通知
- **`PC-02`**：開示承認者ロール、代理承認ルール
- **社内**：RFQ 雛形 v2・評価基準の既定重み・図面メタと開示区分の Outline 整備、NM-02 の正規化ルールの版管理、DC-07 の NDA 標準版
- **無くても動く範囲（段階導入）**：
  - 段階 0（契約前）：起草・機密除外・開示ゲート・プレビューまで。`PC-15` モックが案件番号と状態遷移を返す。デモと法務レビュー
  - 段階 1：RFQ 起草＋担当者が代行のポータルへ手動で引き継ぎ（API なし）。進捗は手動入力
  - 段階 2：案件 API・Webhook・`nm2_input_json`・期限付き URL
  - 段階 3（任意）：代行範囲「発注実行まで」。ただし GN-03 の登録は当社に残す
