## 1. 業務シナリオ
- **トリガー**：定時（`routine`。四半期棚卸の締め）。差異が残ったまま締めが近づくと `due`
- **登場人物**：実施者＝物流課 出荷・在庫担当（部品・製品）／財務課（固定資産）。確認者＝物流課長。後工程＝財務課（帳簿修正の受け手）
- **いまの手順（Before）**
  1. 棚卸の実数と帳簿が合わない行が数件〜十数件残る
  2. 担当者が入出庫履歴を Excel で開き、**差異の数だけ伝票を目で追う**（1 行 30 分〜）
  3. 「前回も同じ品番で出ていたか」は**前回ファイルを開いて目視**。2 期前まで遡ることはまずない
  4. 原因が分からない行は「棚卸差異」として一括で帳簿修正し、**同じ差異が翌期も出る**
  5. 締めまでの残日数の中で、どの行から手を付けるかの優先順位が立てられない
- **エージェント導入後の手順（After）**
  1. 差異一覧・入出庫履歴・前回差異をアップロードする（**入力する場所**）
  2. 行ごとに原因仮説が**根拠の伝票番号つきで**返る（どの出庫・どの返品・どの不良処置に紐づくか）
  3. 前回・前々回と**同じ品番かつ同じ向き（プラス／マイナス）**の差異が続いていれば、単発のミスではなく**計上の型**として示される（**確認する場所**）
  4. 確認手順が所要時間つきで並ぶ。差異の大きい行から着手できる
  5. 処理案が「再調査／帳簿修正／廃棄処理」に分かれて返る。**伝票は起票されない。承認は課長と財務課**（決める場所）
- **成功の定義**：差異 1 行あたりの調査時間が 30 分から 5 分になる。かつ**2 期連続の同じ型の差異が「棚卸差異」で流されず、計上ルールの是正につながる**

## 2. 想定インプット
| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 棚卸差異一覧 | Excel / CSV | zh（品番は英数） | 四半期 1 回・3〜15 行 | `ST-25-Q3`：`SK-3310-A` 帳簿 1,240／実数 1,198 | 棚卸システム／業務台帳 | 表の正規化（品番・帳簿数・実数・差異・単位） |
| 入出庫履歴 | CSV | zh | 四半期分（数千行） | 出庫 `INV-2025-0906`、返品 `RT-2508-04` | 業務システム（`PC-04`） | 品番・日付・区分（入庫／出庫／返品／廃棄／仕掛）で集計 |
| 前回・前々回の棚卸差異 | Excel / CSV | zh | 各 1 ファイル | `ST-25-Q2`：`SK-2207-B` ＋18 | 棚卸システム | 品番・向きでインデックス |
| 品質処置の記録 | 構造化データ | ja / zh | 随時 | `NC-2025-0912` の D3（640 個全数目視・不良 9 個） | QMS／業務台帳（`PC-04`） | 抜き取り数・廃棄予定数の抽出 |

- **入力言語の扱い**：入力は中国語、財務課あての連絡文は相手に合わせる（**回答言語＝利用者の入力言語**、連絡文だけは宛先の言語で書き分けてよい。その場合は「以下は宛先言語の文面です」と地の文で断る）。品番・伝票番号は原文のまま
- **入力の欠け・曖昧さ**：①入出庫履歴が未接続 → **原因仮説を出さず**「履歴が接続されていないため、原因の推定はできません。差異の一覧と前回との比較までを返します」。②前回差異が無い → 型の判定を行わず、その旨を書く。③単位が混在（本／箱） → 換算せず、**単位を揃えてから再実行してください**と返す

## 3. 観点（LLM に守らせる業務ルール）
1. **原因仮説には必ず根拠の伝票番号を添える**。番号を出せない仮説は「根拠なし（要調査）」と明示する。数字を作らない
2. **差異の向き（プラス／マイナス）と仮説の向きが一致していること**を確かめる。実数が多いのに「出庫の計上漏れ」のような逆向きの仮説を出さない
3. **前回・前々回と同じ品番かつ同じ向きなら「型」として示す**。ただし**2 期では型と断定せず**「3 期目を見ないと言い切れない」と書く
4. **処理案は再調査／帳簿修正／廃棄処理のどれかに分類し、順序に依存関係があるときは順序を明示する**（例：廃棄伝票が未起票なら廃棄処理が先。逆にすると抜いた現物が帳簿からも台帳からも消える）
5. **伝票を起票しない。帳簿修正の承認は人**。出力は「〜を起票してください」の形にする
6. 再出荷可否が未判定の現物（返品など）は、**良品在庫に計上しない**処理案にする
7. 確認手順は**所要時間つき**で、差異の大きい行から並べる

- **不確実なときの定型**：ja「この差異の原因は推定できません。入出庫履歴が接続されていないためです。差異の一覧と前回との比較までを返します。」／zh「无法推定该差异的原因。原因是出入库履历未接入。仅返回差异一览与同上次的比较。」
- **出力の粒度と形式**：見出しは「差異の全体」＋差異行ごとに 1 見出し＋「確認手順」「処理案」「財務課あて連絡文」。後工程へ渡す分は §5-3 の JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**。入力がファイル 3 種で出力が定型。対話は必須でない（追い質問は再実行で足りる）
- **ノード列**
  ```
  Start（variance_file・movement_file・prev_variance_file・period）
    → Doc Extractor（表の読み取り。Excel/CSV は Code ノードで直接パース）
    → Code（差異行の正規化：品番・帳簿数・実数・差異・向き）
    → HTTP Request（PC-04：品質処置の記録 — 抜き取り・廃棄予定数）
    → Code（入出庫履歴を品番・区分で集計し、差異に近い数量の動きを候補として抽出）
    → LLM 1（行ごとの原因仮説＋根拠の伝票番号。向きの整合を検査）
    → Code（前回・前々回との向き一致の判定 → repeat_pattern フラグ）
    → LLM 2（確認手順・処理案・連絡文）
    → Template（本文）／Code（JSON）
    → End
  ```
- **Knowledge**：**使わない**（規程照会ではなく数字の突き合わせ。KB を持たせると根拠が曖昧になる）。棚卸の社内ルール（区分の定義）は `PC-06` の用語集で持つ
- **プラグイン／ツール**：`http-request`（業務システム）。Excel は Code ノードで扱い、`tools/mineru` は紙の棚卸票が混じる場合のみ
- **モデル**：既定 chat モデル。数量の一致判定は LLM ではなく **Code ノードで行う**（LLM に足し算をさせない。`../implementation-guide.md` §6 の原則）
- **参照 DSL**：未確定（`../templates/` に該当なし）
- **入出力変数**

| 名前 | 型 | 必須 | 説明 |
|---|---|---|---|
| `variance_file` | file | ✓ | 棚卸差異一覧 |
| `movement_file` | file | | 入出庫履歴。無ければ仮説を出さない |
| `prev_variance_file` | file | | 前回（可能なら前々回）の差異 |

## 5. プロンプト
### 5-1. System
```text
あなたは製造業の工場で棚卸を担当する担当者の補助です。
棚卸の差異行について、入出庫履歴と前回の差異を突き合わせ、原因仮説・確認手順・処理案を示します。

守ること:
1. 原因仮説には必ず根拠となる伝票番号を添える。番号を出せないものは「根拠なし（要調査）」と書く。
   数量や金額を自分で作らない。
2. 差異の向き（実数が多い／少ない）と仮説の向きが一致していることを確かめる。逆向きの仮説を出さない。
3. 前回・前々回と同じ品番かつ同じ向きの差異が続いていれば「型」として示す。
   ただし 2 期では断定せず、3 期目を見ないと言い切れないと書く。
4. 処理案は「再調査」「帳簿修正」「廃棄処理」のどれかに分類する。
   順序に依存関係があるときは順序を明示する（例: 廃棄伝票が未起票なら廃棄処理が先）。
5. 伝票を起票しない。帳簿修正の承認は人が行う。出力は「〜を起票してください」の形にする。
6. 再出荷可否が未判定の現物は良品在庫に計上しない処理案にする。
7. 確認手順は所要時間を添え、差異の大きい行から並べる。
8. 回答はユーザーの入力言語で書く。地の文で 2 つの言語を混ぜない。品番・伝票番号は原文のまま。

履歴が無いときの定型:
ja「この差異の原因は推定できません。入出庫履歴が接続されていないためです。差異の一覧と前回との比較までを返します。」
zh「无法推定该差异的原因。原因是出入库履历未接入。仅返回差异一览与同上次的比较。」
```

3. 確認手順（所要時間つき・差異の大きい行から） 4. 処理案（再調査／帳簿修正／廃棄処理）

### 5-3. 出力フォーマット（後工程へ渡す JSON）
```json
{
  "period": "ST-25-Q3",
  "scope": "parts",
  "lines": [
    { "part_no": "SK-2207-B", "book": 860, "counted": 884, "variance": 24, "direction": "plus",
      "hypotheses": [{ "text": "返品受入の入庫計上漏れ", "evidence": ["RT-2508-04"], "direction_ok": true }],
      "repeat_pattern": { "prev_periods": ["ST-25-Q2"], "same_direction": true, "confirmed": false },
      "disposition": "book_adjustment", "book_to": "on_hold", "voucher_created": false }
  ],
  "unexplained": [],
  "approval_required": ["section_manager", "finance"]
}
```
- **`voucher_created` は常に false**（AI は伝票を起票しない。§3-5 の機械化）
- `repeat_pattern.confirmed` は 3 期連続で初めて true。2 期では false のまま

### 5-4. Few-shot
ja・zh 各 1 組（「実数が帳簿より多い ＝ 入庫の計上漏れ」という**向きの整合**の例）。向きの取り違えがいちばん起きやすい誤りのため。

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 根拠 | 原因仮説に伝票番号が付く ≥ 95%（付かないものは「根拠なし」と明示 100%） | 自動（JSON の `evidence`） |
| 向きの整合 | `direction_ok` が false の仮説を本文に出さない 100% | 自動 |
| 型の判定 | 2 期連続で `confirmed` を true にしない 100% | 自動 |
| 数量 | LLM が数量を計算しない（Code ノード出力と本文が一致）100% | 自動（突合） |
| 起票の非代行 | `voucher_created` が false 100%・本文に「起票しました」が無い 100% | 自動＋負例 |
| 順序依存 | 廃棄伝票未起票のとき廃棄処理を先に置く 100% | 該当パターン 5 件 |
| 言語 | 入力言語で返答 100%（連絡文の書き分けは断り書きつき） | 人手 |
| 速度 | p95 < 90 秒（履歴 5,000 行まで） | Langfuse |

## 8. 別出しが必要なもの
- **入出庫履歴の API 化**（`PC-04`）。Excel の手渡しでも動くが、**四半期分を毎回手で出す運用だと定着しない**。既存の業務台帳（ノーコード業務 DB の WMS・在庫アプリを含む。設計書 `docs/handoff/2026-09-21-kintone-derived-usecases.md` §11）を読み取り先にできる
- **区分の定義の統一**（入庫／出庫／返品／廃棄／仕掛／移動）。ここが揺れると向きの整合検査が効かない。`PC-06` の用語集に置く
- **品質処置（抜き取り・廃棄予定）の参照**。QMS 側に持つか業務台帳に持つかは未確定（§10 R-3）
- **無くても動く範囲**：差異一覧だけでも「差異の全体・前回との比較・確認手順の雛形」は出る。**原因仮説と処理案が落ちる**（第 1 段はここ、第 2 段で入出庫履歴、第 3 段で品質処置）
