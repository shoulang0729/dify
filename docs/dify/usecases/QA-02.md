## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：4M（材料・工程・人・設備）の変更を申請したい担当者が能動的に開く。または**期限つき案件**（③業務フィード `FEED.items` の `qa2` は `due`：サプライヤー値上げ通告への回答期限・顧客承認の逆算期限）
- **登場人物**：申請者（製造課長・生産技術。zh 主体）、確認者（品質保証課長・工場長＝材料変更の決裁者）、外部：顧客 K 社（PPAP 承認）、サプライヤー S 社／T 社
- **いまの手順（Before）**：
  1. 変更の影響を申請者の経験で書く。「前に同じ変更で何が起きたか」は QMS を部品番号で検索しても ECR と不具合記録が別システムで紐づかない（半日）
  2. 顧客承認の要否を品質保証課に聞き、PPAP 提出レベル表を人が読む（1 日待ち）
  3. **切替時期の逆算（承認 6 週間・在庫消化）を忘れて、承認前に在庫が切れる／承認遅れで二重在庫**が起きる
  4. ECR 申請書に手で転記
- **エージェント導入後の手順（After）**：
  1. 申請者が変更前・変更後の条件を入力言語（zh/ja）で入力（diff 画面）
  2. エージェントが差分を項目化（`PC-12`）→ ECR 履歴・不具合記録から「同種の変更で起きたこと」を引き、影響項目・今回の予測（高／中／低）・**顧客承認の要否（PPAP レベル表の該当行を引用）**を表で返す
  3. **申請者が影響の見立てと検証計画を決める**（AI は過去事例と要否ルールの提示まで。「予測」は根拠のある範囲）
  4. 「切替はいつから？」で逆算案、「ECR のドラフトを」で申請書ドラフト（`PC-13`）を受け取り、**変更管理システムへの起票は人**
- **成功の定義**：影響評価の初版を 1〜2 日 → 30 分。**顧客承認要否の見落とし 0**、過去の同種変更事例の参照率 100%（記録がある限り）

## 3. 観点（LLM に守らせる業務ルール）
- **差分だけを対象にする**：`PC-12` が出した変更項目（サプライヤー・幅）だけを影響評価の起点にし、変わっていない項目（材質・板厚）を「変更」と書かない
- **過去事例は番号付きで**：ECR 番号・年・結果（何が起きたか）を引く。事例が無い影響項目は「過去事例なし（一般的な留意点）」と区別する
- **「予測」の表現を抑える**：今回の予測は「高／中／低」＋根拠（サプライヤー提示値との差、過去事例の有無）。**確率・不良率を数値で作らない**
- **顧客承認要否は表を引く**：PPAP 提出レベル表・協定の該当行を引用して「要／不要／要確認」。表に無い変更種別は「要確認」
- **逆算は入力値から**：承認リードタイム（表の値）・在庫（入力値）・検証期間（入力または過去 ECR の実績）から日付を積む。無い値は仮定を明示（「検証 2 週間と仮定」）
- **起票しない**：ECR は「ドラフト」。承認ルート（製造二課長 → 品質保証課長 → 工場長）は変更管理規程を引き、**申請・承認・登録は人**
- **禁止**：サプライヤーの機密（単価・原価差）を他サプライヤーの文脈に転記しない。コスト差は申請者が入力した値のみ
- **不確実なとき**（入力言語で）：「この部品・変更種別の過去事例が見つかりません。一般的な留意点と顧客承認ルールのみ示します。影響評価は工程担当と協議してください」
- **出力の粒度**：影響表（#／影響項目／過去事例／今回の予測／対応）→ 承認要否 → 逆算（任意）。ECR ドラフトは §5-3 JSON → `PC-13`

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`）。diff 入力後に「いつから？」「ECR ドラフトを」の追い指示が続くため。会話変数 `impact_json`
- **ノード列**：
  1. Start（`before`、`after`、`customer`、`part_no`（任意）、`sys.query`）
  2. LLM（Qwen3-32B）— before/after を `{category, part_no, supplier, items[]}` に構造化（JSON）
  3. **HTTP Request（`PC-12`）**または Code — 項目差分 `changed_items[]`（`PC-12` 未整備時は Code で辞書比較）
  4. Knowledge Retrieval ×3 並列 — `kb-ecr-history`（`part_no` or `change_type`＋`supplier` フィルタ、top-k 6）／`kb-nc-records`（`part_no` フィルタ、top-k 4）／`kb-customer-rules`（`customer`＋`change_type` フィルタ、top-k 3）
  5. LLM（Qwen3-235B）— 影響表・承認要否を §5-3 JSON＋表で出力 → Variable Assigner（`impact_json`）→ Answer
  6. 追い指示：LLM（`impact_json`＋`sys.query`）→ 逆算／ECR ドラフト → HTTP Request（`PC-13`：docx/xlsx）→ Answer
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-ecr-history` | ECR 履歴 | 行単位（1 ECR 1 チャンク。長い評価欄は親子） | `ecr_no` `part_no` `change_type`（material/method/man/machine）`supplier` `customer` `year` `outcome` `approval_level` | `PC-04` 変更管理システム → 月次 → `PC-03` |
  | `kb-nc-records` | 不具合記録（QA-01 と共用） | 行単位 | `nc_no` `part_no` `related_ecr` `process` `year` | QMS 月次 |
  | `kb-customer-rules` | PPAP 提出レベル表・顧客協定・変更管理規程・承認ルート | 節／行単位 | `customer` `change_type` `level` `lead_time_weeks` `approver_route` | Outline → `PC-05` |
- **プラグイン／ツール**：標準ノードのみ（`tools/dify_extractor` は KB 投入）。ミルシート読み取りは `tools/mineru`（任意）。起票連携は第 2 段階で `http-request`／`tools/jiandaoyun`

- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（複数 KB → LLM）。差分比較の Dify 公開事例は無し（`../plugins-and-references.md` §11「該当なし」）。`../templates/04` の「突合して不一致を列挙」の発想を before/after に適用
- **入出力変数**：
  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `before` / `after` | string | ✓ | 変更前／後（diff 2 欄） |
  | `customer` | string | ✓ | 納入先（承認要否） |
  | `part_no` | string | — | 無ければ抽出 |
  | `stock_qty` / `monthly_usage` | number | — | 逆算用（任意） |
  | `lang` | string | ✓ | 入力言語 |
  | `changed_items` | array | ✓ | `PC-12` 出力 |
  | `impact_json`（会話変数） | object | ✓ | §5-3 |
  | 出力 `answer` / `ecr_draft` | string / object | ✓ / — | 影響表／ECR ドラフト |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工 蘇州工場の 4M 変更管理を支援する「変更点影響評価アシスタント」です。
役割：変更前後の差分と、ECR 履歴・不具合記録・顧客承認ルールから、影響項目・過去事例・顧客承認の要否を整理し、ECR 申請書のドラフトを作る。

守るルール：
1. 影響評価の起点は <changed_items>（実際に変わった項目）だけ。変わっていない項目を変更として扱わない。
2. 過去事例は ECR 番号・年・結果を付けて引く。事例が無い項目は「過去事例なし（一般的な留意点）」と区別する。
3. 今回の予測は「高／中／低」と根拠（提示値の差、過去事例の有無）で書く。確率・不良率などの数値を作らない。
4. 顧客承認の要否は <customer_rules> の該当行（提出レベル表・協定）を引用して「要／不要／要確認」。表に無い変更種別は「要確認」。
5. 切替時期の逆算は、承認リードタイム（表の値）・在庫と使用量（入力値）・検証期間（入力または過去 ECR 実績）から積む。無い値は「〜と仮定」と明示する。
6. ECR は「ドラフト」。申請・承認・変更管理システムへの登録は行わない。承認ルートは変更管理規程の記載どおりに書く。
7. サプライヤーの単価・機密を別のサプライヤーの文脈に書かない。コスト差は入力された値のみ。
8. 言語：ユーザーの入力言語で答える。中国語なら中国語、日本語なら日本語。ECR 番号・部品番号・材質記号は原文のまま。
9. 過去事例が無いとき：
   zh「未找到该零件・变更类别的历史案例。仅提供一般注意事项与客户承认规则。影响评价请与工序负责人协商。」
   ja「この部品・変更種別の過去事例が見つかりません。一般的な留意点と顧客承認ルールのみ示します。影響評価は工程担当と協議してください。」

```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 差分検出 | `changed_items` が人手判定と一致 100% | ダミー 20 組 |
| 事例照合 | 正解 ECR を top-3 に含む ≥ 80% | 過去 ECR 30 件（部品・種別が近い正解付き） |
| 承認要否 | レベル表と一致 100%（見落とし 0） | 顧客×変更種別 40 組 |
| 予測の表現 | 数値確率・不良率の生成 0、「高／中／低」＋根拠 100% | 自動（数値パターン）＋人手 |
| 逆算 | 入力値からの日付計算が正しい 100%、仮定の明示 100% | 10 ケース |
| 言語 | 入力言語で返答 100% | `PC-07` |
| 形式 | `impact_json` スキーマ準拠 100% | バリデータ |
| 速度 | p95 < 30 秒 | `PC-09` |
| 安全 | 起票済み・承認済みの虚偽記述 0、他社機密転記 0 | 負例 |

- **評価方法**：リリース前は品質保証課長が 20 ケース採点。運用後は ECR ごとに「AI の影響表に無かった影響が後で出たか」を記録（四半期レビュー）。**st3 → st2 への昇格判断材料**にする

## 8. 別出しが必要なもの
- **`PC-12`**：before/after の項目差分（初期は Code 代替可）。EN-01 仕様差分と共用

- **読む**：Outline「顧客要求事項」（PPAP 提出レベル表・協定）、「変更管理規程」（承認ルート・4M 定義）→ `kb-customer-rules`
