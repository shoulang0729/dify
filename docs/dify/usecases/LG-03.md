## 1. 業務シナリオ
- **トリガー**：定時（③業務フィード `routine`：毎週月曜「今週の作業変更点を現場向けの中国語に」）と、担当者が能動的に開く（口頭指示が伝わらなかった翌日、段取り変更・条件変更のたび）
- **登場人物**：指示者＝日本人駐在員（部長・課長・技術者）、受け手＝中国人班長・作業者（日本語は日常会話レベル）、確認者＝通訳（任意）、夜勤班長（伝達先）
- **いまの手順（Before）**
  1. 口頭または日本語メモで班長に伝える（5 分）。班長は日本語を「だいたい」理解して現場に展開
  2. 翌日、意図と違うやり方になっている（「今までと逆」が何と何か曖昧、「3 個測る」を「3 個作ってから測る」と解釈）
  3. 通訳を呼んで再説明（30 分〜1 時間）。夜勤には伝わっていない
  4. 基準値（予熱温度など）を指示者が覚えていず、班長も判断できない
- **エージェント導入後の手順（After）**
  1. 【入力】相手（役職・日本語レベル）・伝えたい指示（日本語のまま。口語・箇条書き可）・背景をフォームに入れる
  2. 【生成】番号付きの中国語指示文、伝える側の確認チェック（口頭で抜けやすい点）、よくある誤解と具体化した書き方、理解確認の質問 3 問（正答付き）が返る。**指示に無い数値を KB から補った箇所は「補足」と明示し、採用するか選択肢で問う**
  3. 【確認】指示者が「勝手に足していいのか」を判断（(a) 基準の所管に確認して載せる／(b) 「所管の基準に従う」と書く）。自分の意図と違う項目を直す
  4. 【決める】指示の内容・数値・伝達ルート（夜勤へ誰が伝えるか）は指示者。AI は現場に配信しない
  5. 【渡す】A4 1 枚（上段：指示 5 項・下段：確認質問＋サイン欄、裏面：日本語原文）を `PC-13` で出力し、班長に渡して確認質問で理解を確かめる。控えを Outline に下書き
- **成功の定義**：口頭指示の「翌日違うやり方」再発 0（ラインごとに記録）。再説明の通訳時間 週 2 時間 → 0.5 時間。夜勤への未伝達 0（伝達ルートが指示書に書かれる）

- **入力言語の扱い**：指示文は**受け手の言語**で出す（既定 zh。中国人管理職 → 日本人技術者のときは ja。翻訳系の例外扱い）。伝える側の確認チェック・よくある誤解・選択肢の説明は**指示者の入力言語**（§2-5）。理解確認の質問は受け手の言語（正答も）
- **入力の欠け・曖昧さ**：指示が無いと動かない。相手が無ければ「班長（中国語母語）」を既定にし明示。日付が相対（「来週から」）で基準日が無ければ聞き返す。聞き返し文：「『来週から』の起点日を指定してください（例：9/15）。指示書には絶対日付で書きます」／「请指定"下周起"的起始日期（例：9/15），指示书中将写为具体日期」

## 3. 観点（LLM に守らせる業務ルール）
- **指示に無い数値・条件を黙って足さない**。KB から補える基準（温度・回数・時間）は**「補足（出典：○○基準 YYYY-MM）」と明示**し、指示者に採用可否を (a)/(b) の選択肢で問う（台本 Q1 のルールを System に固定）
- 曖昧語を具体化する：「今までと逆」→ 2 手順を明記、「3 個測る」→「首件 3 件（作ってから 3 個ではない）」、「連絡」→「停机 → 联系」の順序。**具体化は言い換えであり、内容の追加ではない**ことを確認チェックに書く
- 各項目は 1 文 1 動作、番号付き、受け手の日本語レベルに合わせた平易な中国語。用語は用語集（`PC-06`）
- 「止める」「連絡する」など安全・品質に関わる動作は**主語と順序**を明確に（誰が・何を先に）。「自分で調整して続行しない」の禁止文を添える
- 伝達ルート（夜勤・他班）が指示に含まれていれば項目化し、無ければ確認チェックで問う（勝手に決めない）
- 理解確認の質問 3 問は指示文の中の**数値・順序・連絡先**を問うもの。正答は指示文に書いたことだけから作る
- 個人情報（`PC-10`）：受け手・連絡先の氏名は姓＋役職まで（社内文書なので可）。電話番号は指示者が入力した場合のみ、A4 の表面ではなく裏面に
- 不確実時の定型：「この指示の『○○』が何を指すか特定できませんでした。具体的な工程・部品を教えてください」／「无法确定指示中的"○○"具体指什么，请告知具体工序或零件」
- 出力形式：Markdown（指示文／確認チェック／よくある誤解／確認質問）＋ §5-3 JSON（`PC-13` の A4 テンプレへ）

## 4. Dify 構成
- **アプリ種別**：**Workflow**（フォーム → 1 回生成。(a)/(b) の選択・差し替えは `revise_note` 付き再実行）
- **ノード列**
  1. `start`：`recipient`, `instruction`, `background`, `base_date`, `line`（任意）, `revise_note`（任意）, `prev_result`（任意）
  2. `code`（前処理）：`PC-07` で `in_lang`/`out_lang`（受け手言語）、相対日付の絶対化、品番・型式の保護、用語集の出現語抽出
  3. `knowledge-retrieval`（任意）：KB `lg3-procedures`、メタデータ `line`/`equipment`。指示に出る設備・工程名で検索
  4. `llm`（書き下し）：System §5-1。指示 5〜8 項目、補足の明示、確認チェック、誤解、質問 3 問
  5. `code`（検査）：指示文中の数値が入力に存在するか照合 → 無い数値は `supplements[]` に無ければ `warnings`
  6. `template-transform` → `end`：`instruction_md`, `result_json`, `supplements`, `warnings`
- **Knowledge**：`lg3-procedures`（作業手順書・設備基準・復旧手順。Outline「手順書」「設備保全 › 基準」を `PC-05` 同期。章単位チャンク、メタデータ `line`/`equipment`/`rev`/`owner_dept`。埋め込み `bge-m3`）。**無くても動く**（補足なしで生成）

- 理解確認の質問は 3 問、指示文の数値・順序・連絡先を問い、正答は指示文に書いたことだけから作る。

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 内容保持 | 指示の意図が欠落・変質した項目 0 | 指示者 5 名による評価セット 20 件の採点 |
| 無断補足 | 入力に無い数値が「補足」表示なしで出る 0 | Code 検査（§4 ノード 5）＋負例セット |
| 具体化 | 曖昧語 3 種（逆・測る・連絡）が具体化 ≥ 95% | 曖昧語セット 15 件 |
| 受け手理解 | 班長が確認質問 3 問に正答 ≥ 90%（試行時） | 現場トライアル 4 週 |
| 言語 | 指示文＝受け手言語、説明＝指示者言語 100% | 自動判定（`PC-07`） |
| 形式 | JSON 準拠、A4 1 枚に収まる項目数（≤ 8） | バリデータ |
| 速度 | p95 < 25 秒 | Langfuse（`PC-09`） |
| 安全 | 電話番号の表面掲載 0 | 負例セット |

- **評価方法**：リリース前に過去の「伝わらなかった指示」10 件を再現し、指示者と班長の双方で採点。運用後は「翌日違うやり方」の件数をラインごとに月次で記録

## 9. Outline Wiki との関係
- **読む**：「手順書 › ライン別」「設備保全 › 基準（予熱・復旧）」「用語集」。補足の出典として文書名・版を指示書に書く
- **書く**：確定した指示書を「現場指示 › ライン別 › YYYY-MM-DD（下書き）」に保存（`PC-05`。publish は指示者）。手順書の恒久変更が要る場合は、指示書ではなく手順書の改訂として人が Outline を更新する（OW-04 の日中同期は LG-01 側）
- 繰り返し出る指示（段取り順など）は手順書に昇格させる判断を管理者に促す（第 2 段階：同一ライン・同一内容の指示が 3 回出たら `notify`）
