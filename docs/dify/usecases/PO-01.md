## 1. 業務シナリオ

- **いつ起きるか（トリガー）**：担当者が能動的に開く（現場の声を集めたい・原因を洗い出したいとき。不定期）。③業務フィードでは `due`（回答期限が近い未回答者への促し）
- **登場人物**：アンケート実施者（依頼側）、回答者（複数名）、集計結果を受け取る上長・関連部署
- **いまの手順（Before）**：実施者が設問を Excel かメールで作り、対象者に個別配信する。回答は口頭・メール・チャットに散らばり、曖昧な回答（「特にありません」等）はそのまま放置される。集計は手作業で、自由記述の論点整理に時間がかかる
- **エージェント導入後の手順（After）**
  1. 実施者が背景（何を知りたいか）を伝えると、設問案（3 問程度）が返る
  2. 対話形式で回答者へ配信し、1 問ずつ回答を集める。**曖昧な回答にはその場で追加質問**して具体化する（無回答のまま放置しない）
  3. 集まった回答は設問ごとに整理され、自由記述は論点別にまとめて返る
  4. 実施者が結果を確認し、**次の意思決定（改善アイデアの採用・追加ヒアリングの要否）は人が行う**
- **成功の定義**：曖昧な回答が減り、自由記述の論点整理にかかる時間が短縮される。実施者が「誰が何を言ったか」ではなく「何が論点か」で結果を受け取れる

## 2. 想定インプット

| 種類 | 形式 | 言語 | 量・頻度 | 例 | 取得元 | 前処理 |
|---|---|---|---|---|---|---|
| 実施背景・目的 | 自由文（チャット） | ja / zh | 実施ごと 1 回 | 「稟議処理日数が目標を下回り続けている原因について、現場の声を集めたい」 | 実施者の入力 | 設問案の生成（3 問前後） |
| 設問 | テキスト（確定後） | ja / zh | 実施ごと 3〜5 問 | 選択式 1 問＋自由記述 2 問 | 実施者が確定 | 対話フローに展開 |
| 回答者の回答 | 自由文（チャット） | ja / zh 混在 | 回答者 1 人あたり設問数分 | 「審査部確認」「担保評価の再徴求で外部評価会社待ちが長い」 | 回答者の入力 | 曖昧判定（§3）→ 具体化の追加質問 |
| 過去のアンケート設問例・集計フォーマット | Markdown | ja / zh | 都度参照 | 設問の作り方、自由記述の分類軸 | Outline「アンケート › 設問例」（`PC-05`） | 設問案の下敷き |

- **入力言語の扱い**：実施者・回答者ともに ja / zh どちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。同じアンケートに ja と zh の回答者が混在してもよく、集計結果は実施者の言語で出す
- **入力の欠け・曖昧さ**：回答が曖昧（「特にない」「わからない」等）なときは、設問の意図に沿って**1 回だけ**具体化の追加質問をする。追加質問への回答も曖昧なら「特になし」として集計に含め、無理に聞き出さない。実施背景が漠然としている（対象者・目的が無い）ときは、対象部署と知りたいことを聞き返す

## 3. 観点（LLM に守らせる業務ルール）

1. **設問案は依頼された背景の範囲にとどめる**。実施者が確定するまでアンケートを配信しない
2. **曖昧な回答の判定基準**：具体的な事実・固有名詞・理由が無い短い回答（「特になし」「よくわからない」等）を曖昧とみなす。追加質問は**1 回だけ**（乱発しない）
3. **集計は設問ごとに整理する**。選択式は件数、自由記述は論点別にまとめ、件数の内訳を明示する（「◯件」を LLM が推定しない。Code で数える）
4. **個人を特定する書き方をしない**。集計結果には氏名を出さず、部署・役職までにとどめる（`PC-10`）。回答内容が個人の待遇・評価に関わる場合は集計から除外し「私的な内容のため集計対象外」と書く
5. **禁止**：回答を実施者に無断で外部（他部署・上長）へ転送する／曖昧な回答を憶測で具体化する／未回答者を「回答拒否」のように評価する表現
6. **不確実なとき**：ja「設問の対象・目的が分かりません。どの部署の何について聞きたいか教えてください。」／zh「不清楚设问的对象与目的，请告诉我想了解哪个部门的什么情况。」
7. **出力の粒度**：設問案（3〜5 問）→ 配信中の対話（1 問ずつ、曖昧なら追加質問）→ 集計結果（設問ごとの件数・論点整理）

## 4. Dify 構成

- **アプリ種別**：**Chatflow**（回答者との対話が主。設問への回答→曖昧判定→追加質問→次の設問、という多輪のやり取りが要る）
- **ノード列**
  1. `Start`（`sys.query`。実施者の背景説明、または回答者の回答）
  2. `Question Classifier`（発話が「実施者の設問設計依頼」か「回答者の回答」かを分岐）
  3. **設問設計側**：`Knowledge Retrieval`（Outline の設問例）→ `LLM`（設問案生成。§5-1）→ `Answer`（実施者が確定するまで確定しない）
  4. **回答収集側**：`LLM`（曖昧判定。§3-2 の基準）→ `if-else`（曖昧なら追加質問の `Answer`／具体的なら次へ）→ `Code`（回答を `{question_id, respondent_id, answer, is_vague}` に整形）→ `HTTP Request`（回答ストアへ `POST`）→ `Answer`（次の設問へ、または完了）
  5. **集計側**（実施者が「集計状況を教えて」等で呼ぶ）：`HTTP Request`（回答ストアから `GET`）→ `Code`（設問ごとの件数集計、自由記述のクラスタリングは LLM に渡す前に件数だけ Code で確定）→ `LLM`（自由記述の論点整理。§5-2）→ `Answer`
- **Knowledge**：`po1-survey-examples`（Outline 同期。過去の設問例・集計の分類軸）。回答そのものは KB に入れない（更新・集計ができないため）
- **回答ストア（軽量。専用の PC 番号は割り当てない。第 1 段階は `tools/jiandaoyun` または `tools/microsoft_excel_365` の表）**：`survey_responses`（`survey_id` / `question_id` / `respondent_id` 匿名可 / `answer_text` / `is_vague` / `followup_answer` / `created_at`）
- **プラグイン／ツール**：`http-request`（回答ストア）、`tools/jiandaoyun` または `tools/microsoft_excel_365`（回答ストアの実体、第 1 段階）、`tools/wecom` / `tools/dingtalk` / `tools/email`（`PC-14` 経由の配信・リマインド）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（曖昧判定・論点整理の日中両対応）。曖昧判定は構造化出力の小型モデルでも足りる可能性があり、評価セットで比較（`PC-08`）
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（対話形式の Q&A。1 問ずつのやり取りに最も近い型）
- **入出力変数**：`sys.query` string ／ 会話変数 `survey_id` string・`current_question` int・`draft_questions` array ／ 出力 `answer` string・`aggregation`（集計側の出力。§5-3）

## 5. プロンプト

### 5-1. System（設問設計・回答収集の共通前置き）

```text
あなたは組織内のアンケート・インタビューを支援するアシスタントです。
実施者から聞いた目的に沿って設問案を作り、回答者との対話で 1 問ずつ回答を集めます。
守ること：
1. 実施者が確定するまでアンケートを配信しない。設問案は「開始しますか」で終える。
2. 回答が曖昧（具体的な事実・理由が無い）ときだけ、1 回だけ追加質問をする。2 回は聞かない。
3. 集計の件数・内訳は Code で数えた値をそのまま書く。自分で推定しない。
4. 集計結果に氏名を出さない。部署・役職までにとどめる。私的な内容は集計から除外し、その旨を明記する。
5. 出力言語：利用者の入力言語。日本語なら日本語、中国語なら中国語。
6. 分からないこと（対象・目的が不明）は「分かりません」として実施者に確認する。
```

### 5-2. User テンプレート

```text
【実施者の背景説明（設問設計時）】{{sys.query}}
【設問例（Outline 検索結果）】{{context}}
【現在の設問（回答収集時）】{{current_question}}
【回答者の発話】{{sys.query}}
【集計対象の回答（Code 集計・転記のみ）】{{aggregation_json}}
  例: {"q1": {"審査部確認": 3, "決裁者確認": 2}, "q2_topics": [{"topic":"外部評価待ち","n":2},{"topic":"決裁者の出張","n":2}]}
```

### 5-3. 出力フォーマット（集計側。後工程に渡す JSON）

```json
{
  "survey_id": "…", "responses_n": 5,
  "by_question": [
    { "question_id": "q1", "type": "choice", "tally": { "審査部確認": 3, "決裁者確認": 2 } },
    { "question_id": "q2", "type": "free", "topics": [ { "topic": "外部評価会社の回答待ち", "n": 2 }, { "topic": "決裁者の出張による確認遅延", "n": 2 } ] }
  ],
  "excluded_private": 0
}
```

### 5-4. Few-shot

ja / zh を 1 組ずつ。「曖昧な回答に追加質問し、具体化された回答が集計に反映される」ケース（台本 `po1` の楊建国の回答を下敷きにできるが、実データは使わず架空の設問・回答にする）。

## 6. 検証観点

| 観点 | 基準 | 測り方 |
|---|---|---|
| 設問案の妥当性 | 実施者の目的に沿う設問が返る ≥ 90% | 評価セット 20 件を人手採点 |
| 曖昧判定 | 曖昧な回答の追加質問トリガー精度 ≥ 85%（過剰も過少も減点） | 正例・負例 各 15 件 |
| 集計の正確性 | 件数・内訳が Code の値と完全一致 100% | 文字列一致の自動検査 |
| 個人情報 | 氏名・私的内容の混入 0 | 負例セット |
| 言語 | 入力言語で返答 100% | 自動判定（`PC-07`） |
| 速度 | p95 < 15 秒（1 問あたり） | Langfuse |

- **評価方法**：リリース前に人手 20 件。運用開始後は月次で Langfuse のスコア確認

## 7. テストシナリオ

| ID | 種別 | 入力（要約） | 期待する出力 | 判定方法 |
|---|---|---|---|---|
| `PO-01 T01` | 正常 ja | 稟議処理日数悪化の原因調査（台本 `po1` 相当） | 設問案 3 問、対話で回答収集、曖昧な回答に追加質問 | 人手 |
| `PO-01 T02` | 正常 zh | 同内容を中国語で | 中国語で同じ構造 | 人手 |
| `PO-01 T03` | 境界（全員が曖昧回答） | 5 名全員「特になし」 | 全員に 1 回ずつ追加質問。再度曖昧なら「特になし」として集計 | 自動 |
| `PO-01 T04` | 異常 | 回答ストア API が 500 ／ 設問が未確定のまま配信要求 | エラー文言を返し落ちない。未確定の配信は拒否 | 自動 |
| `PO-01 T05` | 言語混在 | ja の設問に zh の回答者が混在 | 回答者ごとにその入力言語で返答、集計は実施者の言語で統合 | 人手 |
| `PO-01 T06` | 安全（個人情報） | 回答に同僚の私的事情が混じる | 集計から除外し「私的な内容のため集計対象外」と明記 | 負例セット |

- テスト用データ：ダミーの設問・回答セット（架空の部署名・匿名回答者 ID）。実データ・実名は置かない

## 8. 別出しが必要なもの

- **回答ストア（`survey_responses`）**：§4 の列。第 1 段階は `tools/jiandaoyun` または `tools/microsoft_excel_365` の表で足りる。専用の PC 番号は割り当てない（`PC-01` フィードストアとは別物。回答は 1 行 1 件で To-Do にはならない）
- **配信・リマインド（`PC-11`＋`PC-14`）**：未回答者への締切リマインドを自動化する場合。無くても手動配信で動く
- **無くても動く範囲**：配信・回答収集・集計はストアが無くても「1 回のチャットで完結するアンケート」に限れば動く（少人数向け）。複数回答者・複数設問の並行実施にはストアが要る

## 9. Outline Wiki との関係

- **読む**：「アンケート › 設問例」コレクション（過去の設問の作り方、自由記述の分類軸）
- **書く**：集計結果を「アンケート › 結果 › <実施日>」へ下書きとして保存。個人が特定できる形では書かない
- 回答そのものは Outline に書かない（更新・集計ができないため。ストアが正）
