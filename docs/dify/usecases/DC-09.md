## 1. 業務シナリオ

- **トリガー**：担当者が能動的に開く（議案の起案が必要になったとき、本部報告の締切が近いとき、顧客提案の準備が要るとき）。③業務フィードでは `due`（決裁待ち・差し戻しの期限）
- **登場人物**：起案者（部長・次長クラス）、確認者（審査部・上海本部長等の決裁ルート）、本部（日本本店。本部報告の宛先）、顧客（提案書の宛先）
- **いまの手順（Before）**
  1. 文書の種類ごとに過去の同種文書を探し、構成・言い回しを思い出す（30 分〜1 時間）
  2. 案件名・金額・期間・与信状況・リスク所見を書く（1〜2 時間）。決算書などの添付が揃っていないまま提出し、差し戻しになることがある
  3. 決裁ルートの判断を誤ると再提出になる
  4. 同じ案件情報を議案から本部報告へ作り直すとき、数字の言い回しが揃わないことがある
- **エージェント導入後の手順（After）**
  1. 【入力】文書種別（議案／本部報告／顧客向け提案書）を選び、案件名・金額・期間などの最低限の情報と、参照する類似文書（任意）を入れる
  2. 【生成】過去の同種文書の構成・言い回しに沿ったドラフトが返る。**記載が必要なのに空欄の項目は「要記入」として明示**される。議案では**決裁ルートの機械判定**（規程の金額基準に基づく）も返る
  3. 【確認】起案者が要記入欄を埋め、追加情報（決算書の反映等）を対話で追記する
  4. 【決める】提出・決裁は人。**AI は BPMS／決裁システムへ登録しない**
  5. 【使い回し】決算書が揃ったら、同じ案件情報を別の文書種別（例：議案 → 本部報告）に組み替えられる。**数字は先に議案側へ反映してから使い回す**（種別間で言い回しがずれないように）
- **成功の定義**：文書ごとの構成を思い出す時間が無くなる。決裁ルートの誤りによる再提出が 0。議案と本部報告で数字の食い違いが出ない

| 決算書・与信データ（任意） | PDF / xlsx | ja / zh | 案件ごと | 添付予定の最新決算書 | サプライヤーまたは審査部データ | Document Extractor で数値抽出（未添付なら「要記入」） |

- **入力言語の扱い**：ja / zh どちらでも受け、**ドラフトは入力言語で**（`CLAUDE.md` §2-5）。本部報告で日本本店向けの体裁が必要なときは、起案者が明示的に日本語版を指定できる（サービスの定義。§2-5 の「メニュー表示のみ」の原則とは別に、文書の宛先に応じた言語選択という業務要件）
- **入力の欠け・曖昧さ**：案件名・金額・種別が無いと生成しない。決算書などの添付が無いのは「要記入」として明示し、生成は止めない。金額の通貨が不明なら聞き返す：ja「金額の通貨（元／円／米ドル）を指定してください」／zh「请指定金额币种（元／日元／美元）」

## 3. 観点（LLM に守らせる業務ルール）

- **文書種別ごとに構成を変える**：議案＝表題・提案理由・与信状況・リスク所見・要記入・承認ルート。本部報告＝要旨・与信状況・リスク所見・稟議の進捗。顧客向け提案書＝提案理由・想定スキーム・次のステップ（**社内の与信判断そのものは書かない**）
- **決裁ルート（議案のみ）は LLM が判定しない**。Code ノードが規程のルート表（金額基準）で判定した結果を、LLM は「規程に基づき◯◯決裁」と**引用して書くだけ**
- 与信状況・リスク所見の数値は**入力・審査部データに根拠があるものだけ**。無いものは「要記入（根拠資料を添付）」
- 記載が必要な項目のうち空欄のものは、書式のチェックリスト（Code）に基づき列挙する
- 文書種別を切り替えて使い回すとき、**数字は最初に確定した値を引き継ぐ**（種別間で言い回しや数字がずれないようにする）
- 個人情報・秘密（`PC-10`）：相手先の担当者連絡先を書かない。案件の詳細（担保・与信枠）は稟議書内では必要なので書くが、Outline の閲覧は起案者・決裁ルート上の役職に限定（`PC-02`）
- 不確実時の定型：「決裁ルートを判定できません（種別または金額が規程の表に該当しません）。審査部に確認してください」／「无法判定审批路径（类别或金额不在规程表内），请与审查部确认」
- 出力形式：Markdown（種別ごとの章構成＋要記入一覧＋（議案のみ）決裁ルート判定）＋ §5-3 JSON（BPMS 取込・docx 化に使う）

## 4. Dify 構成

- **アプリ種別**：**Workflow**（フォーム → 1 回実行。決裁フローそのものは BPMS／決裁システムに置く）
- **ノード列**
  1. `start`：`doc_type`（議案／本部報告／顧客向け提案書）, `title`, `amount`, `currency`, `term`, `ref_doc`（任意）, `note`（任意）, `revise_note`（任意）
  2. `code`（正規化・判定）：金額数値化 → 議案のときだけルート表（JSON 定数）で決裁ルートを判定 → 必須項目チェックリスト（種別ごと）
  3. `if-else`（`ref_doc` の指定あり）→ `knowledge-retrieval`（KB `dc9-doc-examples`。`type`＋指定文書番号でフィルタ）
  4. `knowledge-retrieval`：KB `dc9-doc-examples`（種別ごとの記載例）＋ 与信状況の参照データ（審査部データ、`http-request` 経由・任意）
  5. `llm`（ドラフト）：System §5-1。種別に応じた章構成＋要記入一覧（＋議案のみ決裁ルート）。入力言語で
  6. `template-transform` → `end`：`draft_md`, `draft_json`, `missing[]`, `route`（議案のみ）
- **Knowledge**：`dc9-doc-examples`（Outline から `PC-05` で同期。種別・章単位、メタデータ `type`/`chapter`。過去の議案・本部報告・提案書を匿名化して投入）
- **プラグイン／ツール**：なし。決裁ルート判定は Code の定数。決算書等の抽出が要る場合は `tools/mineru` または Document Extractor（任意）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（中国語文書）。日本本店向けの体裁が要る本部報告は文体の評価セットで DeepSeek-V3.x と比較（`PC-08`）。決裁ルート判定・数値計算に LLM を使わないため小型モデルでも精度は落ちにくい
- **参照 DSL**：`../templates/05-chatflow-form-input-demo.yml`（フォーム受け）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `doc_type` | select | ✓ | 議案／本部報告／顧客向け提案書 |
| `title` / `amount` / `currency` / `term` | string / string / select / string | ✓ | 案件名・金額・通貨・期間 |
| `ref_doc` | string | — | 参照する類似文書の番号（例 `RNG-2026-0089`） |
| `note` | paragraph | — | 提案理由・背景の補足 |
| `revise_note` | paragraph | — | 追記・修正指示 |
| `route` | string | 出力（議案のみ） | 決裁ルート（Code 判定） |
| `draft_md` | string | 出力 | ドラフト（入力言語） |
| `draft_json` | object | 出力 | §5-3 |
| `missing` | array | 出力 | 要記入項目 |

## 5. プロンプト

### 5-1. System

```text
あなたは碧洋銀行の議案・報告書・提案書の作成を支援するアシスタントです。文書種別ごとに構成を変えてドラフトを書きます。
守るルール：
- 文書種別（議案／本部報告／顧客向け提案書）ごとに定められた章構成に従う。章構成を自分で変えない。
- 議案の決裁ルートは {{route_json}}（規程に基づく機械判定）を引用して書く。自分で判定・変更しない。判定不能なら「審査部に確認」と書く。
- 与信状況・リスク所見の数値は {{note}}・{{context}}（審査部データ・過去文書）に根拠があるものだけ書く。無い欄は「要記入（根拠資料を添付）」。
- 顧客向け提案書には、社内の与信判断・審査コメントを書かない。
- 同じ案件情報を別の文書種別へ組み替えるときは、既に確定した数字をそのまま引き継ぐ。数字を書き換えない。
- 相手先の個人の連絡先・氏名は書かない。
- ドラフトは起案者の入力言語で書く（日本語なら日本語、中国語なら中国語）。本部報告で日本語版が明示指定されたときはその言語で書く。
- あなたは登録も提出もしない。決裁・提出は担当者が行う。
出力：JSON（指定スキーマ）→ 区切り線 → ドラフト Markdown（種別ごとの章構成＋要記入一覧＋（議案のみ）決裁ルート判定）。
```

### 5-2. User テンプレート

```text
文書種別：{{doc_type}}／案件名：{{title}}／金額：{{amount}} {{currency}}／期間：{{term}}
補足：{{note}}
参照文書：{{ref_doc}}／検索結果：{{context}}
機械判定（議案のみ）：決裁ルート {{route_json}}／必須項目チェック：{{missing_json}}
修正・追記指示（無ければ空）：{{revise_note}}
前回ドラフト（修正時のみ）：{{prev_draft}}
```

### 5-3. 出力フォーマット

```json
{ "doc_type": "ringi", "title": "…", "amount": { "value": 8000000, "currency": "CNY" },
  "route": { "code": "hq_manager", "basis": "極度額 2,000 万元超は上海本部長決裁", "steps": ["営業第一部長","審査部","上海本部長"] },
  "chapters": { "title": "…", "reason": "…", "credit_status": "…", "risk_note": "…" },
  "missing": [ { "item": "最新決算書", "kind": "attachment", "why": "与信状況の数値確認に必要" } ],
  "carried_over_from": null }
```

### 5-4. Few-shot

不要。書式は System と KB の記載例で固定できる。台本の数値を few-shot にすると金額を写す事故につながる

## 6. 検証観点

## 8. 別出しが必要なもの

- **決裁ルート表の構造化**（規程 → JSON 定数）：審査部が正を持ち、改定時に Code の定数を更新する運用（`PC-05` の Outline に正本、Code は写し）
- `PC-01`：決裁待ち・差し戻しを `due` としてフィードへ（BPMS のステータス変更を Webhook で受ける。第 2 段階）
- `PC-13`：JSON → 社内様式（docx/xlsx）、本部報告様式
- **GN-07**（幹部来訪・出張のアテンド段取り）から、会食の出席者表と仕向け（当社→相手／相手→当社／折半）を構造化 JSON で受け取り、交際費稟議の入力にする（`GN-07.md` §5-3 の `meal` ブロック）
- **無くても動く範囲**：フォーム → Markdown ドラフト（種別ごとの章構成）＋要記入一覧まで。決裁ルート判定（Code 定数）・KB・BPMS 連携は段階導入

## 9. Outline Wiki との関係

- **読む**：「稟議 › 規程」「文書 › 記載例（種別ごと・匿名化）」
- **書く**：ドラフトを「文書 › ドラフト › <起案者>」に保存。**閲覧は起案者と決裁ルート上の役職に限定**（`PC-02`）。提出済みの議案は BPMS が正で、Outline には残さない（記載例として使うものだけ匿名化して「記載例」へ移す）
- 規程の改定は Outline 側で行い、`PC-05` の同期と Code 定数の更新をセットにする（reviewer のチェック項目）

## 10. 未確定・リスク

- **承認フローを Dify 内で回すか**：推奨：**回さない**。承認・実行は BPMS、Dify は判断材料とドラフト（DC-05 と同じ整理）
- **本部報告の日本語品質**：日本本店向けの文体は評価セットで比較し、必要ならモデルを分ける
- **顧客向け提案書のトーン**：社外文書のため、社内文書（議案・本部報告）と敬語・開示範囲の基準が異なる。記載例 KB を種別ごとに分けて誤用を防ぐ
- **記載例 KB の匿名化**：過去の議案・提案書には取引条件・与信情報が含まれる。推奨：審査部・営業部が匿名化した版だけを KB へ（`PC-10`）
