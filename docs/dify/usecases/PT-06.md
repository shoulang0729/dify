## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：(a) 担当者が能動的に開く（年度の購買方針策定、本社からの削減要求）／(b) 監視対象の変化（③業務フィードの `notify`：購買エージェント AI から提案が届いた Webhook）。年 1〜2 回の大きな案件＋カテゴリ単位の追加依頼
- **登場人物**：購買課長（依頼・判断・本社合意）、購買課担当（データ準備、PT-07 へ続く）、本社購買部（共同購買の相手・合意先）、法務（契約条項＝DC-07）、外部＝購買代行の AI エージェント（提案の作成。**発注や交渉はしない**）
- **いまの手順（Before）**：本社から「買い方を変えて 8% 削減」→ 課長が ERP から発注実績 14 か月（3,860 行）を出し Excel でカテゴリ集計（半日）→ 契約一覧 36 件を突合（半日）→ 集約・複数年・代替の案を経験で書く（2 日）→ 本社と往復（数週間）。毎年の見積比較（NM-02）では 2〜3% しか下がらず「買い方」の見直しまで手が回らない
- **エージェント導入後の手順（After）**：(1) 担当者が発注実績・現行契約一覧・本社共通品目を**アップロード**する → (2) Dify が `code` で品目コード名寄せ・カテゴリ集計・**サプライヤー名の ID 化**・顧客固有仕様の除去を行い、担当者が**送信内容のプレビューを確認して送信ボタン**を押す → `PC-15` 経由で購買エージェント AI の提案 API へ送り、案件番号を受領 → (3) 提案が Webhook で戻る（同期 API なら即時）→ Dify が社内 KB（見積比較・契約条項集）と整合を確認し、カテゴリ別の表・削減額・リスク・本社向け説明を返す → (4) 課長が**採用するカテゴリ・順序を決め**、本社購買部と合意 → (5) 契約条項は DC-07 へ、最初の RFQ は PT-07 へ**担当者が引き継ぐ**（AI は発注も契約もしない）
- **成功の定義**：データ整理〜案作成 3 日 → 半日（提案待ち時間を除く）。削減額・リスクに前提（市況・数量）が付き、本社と同じ表で議論できる。**サプライヤー名・顧客仕様が社外に出ない**

## 3. 観点（LLM に守らせる業務ルール）
- **送信前プレビューを必ず通す**：外部へ送るデータの列名・行数・ID 化の結果・除去した項目を表示し、**担当者が承認してから**送る。AI は勝手に送らない
- **パートナー AI の数値を転記し、当社集計で照合する**：削減率・削減額は提案 JSON の値をそのまま表に出し、`code` が当社の実績集計から再計算した値と差があれば「差分」列に出す。LLM が数値を言い換えない・平均しない
- **推奨は提案として扱う**：「購買エージェント（AI）の提案」と出典を明示し、当社の判断責任を書く（「採用の判断は購買課長と本社購買部」）。「すべき」と書かない
- **顧客固有仕様は動かさない**：K 社向け仕様など顧客承認品は「変更不可」と明示（提案が共通化を勧めても当社側の制約として残す）
- **サプライヤーは ID で語る**：表・説明ではサプライヤー ID を社内対応表で名前に**戻して表示**してよい（社内向け）。ただし `PC-15` へ送る側は ID のまま。代替候補はパートナー DB の ID で受け取り、与信は PT-01 で別途照会と書く
- **契約条項は DC-07 の形式で出す**：価格調整条項案は「契約条項集 §7 に差し込める形」で、法務レビュー前提
- **送っていないものを明示**：「連携」行に「送信：発注実績（品目コード・数量・単価・サプライヤー ID）・契約条件の要約・本社共通品目。**送信していない：サプライヤー名・顧客名・顧客向け図面／仕様・担当者名**」を必ず書く
- **不確実なときの定型**：ja「購買エージェントの提案にこのカテゴリの根拠（市況前提・代替候補）が含まれていません。提案の補足を依頼するか、当社判断で保留してください」／zh「采购代理的方案中没有该品类的依据（行情前提・替代候选）。请要求补充或由本公司暂缓」
- **出力の粒度と形式**：表（カテゴリ／現状／戦略案／期待削減／リスク・条件）＋合計行＋連携行。条項案・本社向け 1 枚・進め方は §5-3 の JSON を経て Markdown

## 4. Dify 構成
- **アプリ種別**：**Workflow（upload → 匿名化 → 送信）＋ Webhook Trigger（提案の戻り → 整合確認 → 表）**。同期 API なら 1 本の Workflow。追加質問（条項の入れ方・次の進め方）は結果 JSON を `context` にした `mode=followup`
- **ノード列（送信側）**：
  1. Start（`sys.files`：CSV・xlsx ×3、`scope`（対象カテゴリ）、`target_saving`）
  2. Document Extractor（xlsx）／`code`（CSV 読み込み。pandas は sandbox に追加要）
  3. `code`（名寄せ・カテゴリ集計・通貨統一・**サプライヤー ID 化**・顧客固有仕様行の除外・本社単価列の除外。`preview_json`＝送信予定データの要約と `removed[]`）
  4. `human-input`（Dify 1.15 Human-in-the-loop：送信プレビューを表示し購買課長が**承認／中止**。承認なしで先に進まない）
  5. `http-request`（`PC-15` 経由：購買エージェント AI の提案 API。応答に `case_id`）
  6. `http-request`（`PC-01` フィードに `notify`「送信済・提案待ち（PA-…）」）
  7. End（`case_id`, `preview_json`）
- **ノード列（受領側）**：Webhook Trigger（`PC-15` から `{case_id, proposal}`）→ `code`（スキーマ検証・**削減額の当社再計算と差分**・サプライヤー ID を社内名に復元〔表示用〕）→ `knowledge-retrieval`（KB `pt-sourcing-internal`：見積比較結果・契約条項集 §7・NM-05 の発注頻度分析）→ `llm`（§5。表・説明。入力言語）→ （`mode=hq_note`）`llm`（日本語 1 枚）→ `template-transform`（連携行）→ `tools/wecom`（`PC-14`：課長へ「提案到着」件数のみ）→ End（`result_md`, `result_json`）
- **Knowledge**：KB `pt-sourcing-internal`（購買帯 `PC-02`）：NM-02 の比較結果、契約条項集 v3（§7 価格改定・§12 知財 等）、NM-05 の分析結果（発注頻度）、品目カテゴリ定義。**発注実績の生データと提案 JSON は KB に入れない**（ファイル／DB で保持。`PC-13`）
- **プラグイン／ツール**：Document Extractor（本体）／Code ノード（pandas。`../plugins-and-references.md` §7 の sandbox 依存追加）／`human-input`（本体 1.15）／HTTP リクエストノード／Webhook Trigger／`tools/wecom`／`tools/echarts`（任意：カテゴリ別削減額の bar）／`tools/microsoft_excel_365`（任意：表を Excel に出す）
- **モデル**：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（説明・zh）。本社向け日本語は DeepSeek-V3.x 等と評価（`PC-08`）。数値は `code` なのでモデル差が結論に影響しない
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（upload → Document Extractor → LLM）、`../templates/06-text-to-sql-http-api-echarts.yml`（`http-request` の呼び方）。`human-input` の DSL 例は dsl-skill の `examples/…/08-human-approval.yml`（URL 参照のみ。`../templates/README.md`）を構成の参考にし、0.6.0 で生成
- **入出力変数**：

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `sys.files` | file-list | ✓ | 発注実績 CSV・契約一覧 xlsx・本社共通品目 xlsx |
| `scope` | string | — | 対象カテゴリ（空なら全部） |
| `target_saving` | number | — | 目標削減率（本社要求 8% 等） |
| `preview_json` | object | 内部 | 送信予定データの要約・`removed[]`・行数 |
| `approved` | bool | 内部 | `human-input` の結果 |
| `case_id` | string | 出力 | 購買エージェントの案件番号 |
| `proposal_json` | object | 内部 | 受領した提案（スキーマ検証済） |
| `mode` | select | ✓ | `send` / `review` / `followup` / `hq_note` |
| `result_md` / `result_json` | string / object | 出力 | 表＋連携行／§5-3 |

## 5. プロンプト
### 5-1. System
```text
あなたは在中日系メーカー（青嶺精工 蘇州工場）購買課の戦略購買アシスタントです。
入力として (A) 購買エージェント（AI）から受領した提案 JSON（カテゴリ別の現状・戦略案・期待削減・リスク・代替候補 ID・条項案・市況前提）、(B) code が当社の発注実績から再計算した集計と、提案値との差分、(C) 社内 KB（見積比較結果・契約条項集・発注頻度分析）、(D) サプライヤー ID と社内名の対応（表示用）、が与えられます。

守ること：
1. 数値は (A)(B) にあるものだけを転記する。削減率・削減額を再計算・言い換え・平均しない。(B) に差分があれば「差分」列に出し、理由を推測せず「要確認」と書く。
2. 提案は「購買エージェント（AI）の提案」と出典を明示し、採用の判断は購買課長と本社購買部にあると書く。「すべき」「必ず」と書かない。
3. 顧客承認品（顧客向け図面・仕様）は「変更不可」と明示し、提案が共通化を勧めていても当社の制約として残す。
4. 表は「カテゴリ｜現状（サプライヤー数／年間額／契約）｜戦略案｜期待削減｜リスク・条件」。合計行の次に必ず「連携」行：送信したもの（発注実績の品目コード・数量・単価・サプライヤー ID・契約条件の要約・本社共通品目）／送信していないもの（サプライヤー名・顧客名・顧客向け図面／仕様・担当者名）／案件番号／整合を取った社内データ／契約条項は「サプライヤー契約書ドラフト支援」へ、と書く。
5. 代替サプライヤー候補は ID で受け取ったものとして扱い、与信は「取引先・サプライヤーの与信・リスク監視」で別途照会が要ると添える。
6. 価格調整条項案は契約条項集 §7 に差し込める形（基準指数・調整ルール・上限・対称性）で書き、法務レビュー前提と添える。
7. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。本社向け 1 枚（mode=hq_note）だけは常に日本語・敬体。
8. 根拠が無いカテゴリの定型：「購買エージェントの提案にこのカテゴリの根拠（市況前提・代替候補）が含まれていません。提案の補足を依頼するか、当社判断で保留してください」／中国語「采购代理的方案中没有该品类的依据（行情前提・替代候选）。请要求补充或由本公司暂缓」。
9. パートナーは「購買エージェント（AI）」「購買代行」と呼ぶ。実名を作らない。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性（転記） | 表の削減率・額が提案 JSON と一致 100%。差分列が `recalc_json` と一致 100% | 自動突合 |
| 匿名化 | 送信データにサプライヤー名・顧客名・図面／仕様・担当者名が 0 件。ID 化の対応表が社内のみ | `PC-15` 送信ログ監査（自動）＋対応表の所在確認 |
| 承認ゲート | `human-input` の承認なしに `http-request` が実行されない 100% | エラー注入（承認スキップ）・トレース確認 |
| 網羅 | 表＋合計＋連携行、代替候補の与信注記、条項案の法務前提 | チェックリスト |
| 言語 | 入力言語 100%、`hq_note` は日本語 100% | 自動判定（`PC-07`） |
| 形式 | `result_json` スキーマ準拠 100%。提案 JSON のスキーマ違反を検出 100% | JSON バリデータ |
| 拒否 | 根拠なしカテゴリで定型文 ≥ 95%。「すべき」等の断定語 0 | 負例セット＋語彙照合 |
| 安全（顧客仕様） | 顧客承認品カテゴリに「変更不可」100% | チェックリスト |
| 速度 | 送信側 p95 < 90 秒（5,000 行）、受領側 p95 < 40 秒 | Langfuse |

## 8. 別出しが必要なもの（このサービス固有の準備）
- **`PC-15`**：購買代行との**契約（NDA・データ利用範囲・保存期間・提案の帰属・成果連動報酬の定義）**、提案 API 仕様（同期／非同期、案件番号、スキーマ）、送信**ホワイトリスト**（品目コード・数量・単価・サプライヤー ID・契約条件要約・本社共通品目コードと数量）、送信ログ、モックモード。**単価を送るか**は交渉事項（送らないと提案精度が落ちる。NDA 前提で送る案を推奨。未確定）
- **`PC-10`**：購買機密（単価・サプライヤー名・契約先・顧客仕様）の分類と扱い。サプライヤー ID 対応表の保管（社内 DB。`PC-15` に渡さない）。個人情報は原則なし（担当者名列の除去）。越境：海外パートナーなら送信データが**企業機密のみ**でも輸出管理・NDA を法務確認
- **`PC-04`**：ERP からの発注実績エクスポート（当面手動。将来は API）。Webhook 受信 URL の公開（セルフホスト前提 F-7）
- **`PC-06`**：品目コードの日中マッピング（当社 `SK-` ⇄ 本社 `HT-`）、カテゴリ定義
- **本社側**：本社共通品目の提供と、本社単価を送るかの判断（本社購買部）
- **無くても動く範囲（段階導入）**：
  - 段階 0（契約前）：送信側の匿名化・集計・プレビュー・承認ゲートまでを実装し、`PC-15` モックが固定提案を返す。デモと法務レビュー
  - 段階 1：購買代行 AI の提案 API（同期）接続。1 カテゴリ（切削工具）で試行
  - 段階 2：Webhook 非同期・全カテゴリ・`hq_note`・NM-05 の分析結果との整合
  - 匿名化なしで送りたい要望が出ても**段階 0 のゲートを外さない**

## 9. Outline Wiki との関係
- **読む**（`PC-05`）：「購買／契約」契約条項集 v3、「購買／見積比較」NM-02 結果、「購買／品目マッピング」、NM-05 の分析メモ

## 10. 未確定・リスク
- **購買代行 AI の提案 API 仕様**：未確定。Agent-to-Agent の標準プロトコルは前提にせず `http-request`＋Webhook（設計書 §5-2 pt6）
- **単価の送信可否**：NDA 前提で送る／送らない。architect 推奨：**段階 1 は単価を送らずカテゴリ集計額のみで試行**し、提案精度を見てから NDA を結んで単価を送る
- **本社単価・本社データの扱い**：別法人のデータをパートナーに送る判断は本社購買部（PM 経由で確認）
- **判断責任**：パートナー AI の提案を採用した結果（PPAP 再取得の遅延・代替品の品質）は当社の責任。表とサマリに「提案」「当社判断」を分けて書く運用を守る
- **NM-02 / NM-05 との重なり**：NM-02 は単年の見積正規化比較、NM-05 は実績の可視化。PT-06 は両者の出力を**入力**として「買い方」を変える提案を受ける位置。PT-06 → PT-07（RFQ）→ NM-02（回収見積の比較）→ GN-03（発注登録）という一方向の流れを崩さない
- **`human-input` の運用**：承認者（購買課長）が不在のときの代理承認ルールは `PC-02` のロールで決める
