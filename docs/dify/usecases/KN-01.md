## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：担当者が能動的に開く（③業務フィードの項目にはならない）。典型は「新材質・新工程の条件が決まらない」「ライン停止の原因に見覚えがある」瞬間
- **登場人物**：質問者（生産技術・製造の主任〜担当者、多くは中国語母語）、根拠文書の作者（過去の日本人駐在員・現地技術者）、確認者（生産技術課長）。外部は関与しない
- **いまの手順（Before）**：
  1. ファイルサーバの `技術報告/` 配下を年度フォルダごとに開き、ファイル名で当たりをつける（30〜60 分）
  2. 日本語の報告書を読み、必要箇所を自分で翻訳する（中国語母語者は 1 件 20〜30 分）
  3. 知っていそうな先輩に WeCom で聞く。不在なら翌日以降。**ノウハウが人に付いている**
  4. 条件表は Excel に手で転記。根拠文書番号は書かれないことが多い
- **エージェント導入後の手順（After）**：
  1. 担当者が材質・寸法・加工内容を**入力言語（zh/ja どちらでも）で質問する**
  2. エージェントが技術報告 KB・トラブル記録 KB から根拠付きで推奨条件を返す（文書番号・拠点・ラインを必ず併記）
  3. 担当者が追い質問で失敗事例を確認する（**ここで「この根拠は信用できるか」を人が判断**）
  4. 「条件表の形にして」でドラフトを受け取る。**条件表の正式登録（工程条件マスタ・作業標準書）は担当者が行う**。AI は登録しない
- **成功の定義**：初回回答までの時間を 30〜60 分 → 5 分以内。回答に**根拠文書番号が 100% 付く**ことで、退職・帰任による属人化を減らす

| 工程条件表（現行） | xlsx | ja | 約 150 品目 | `条件表_SK-3310-A_RevC` | 生産技術課共有フォルダ | 行単位。品目・工程・改訂のメタデータ |
| 質問文 | テキスト | ja / zh 混在（型式・材質記号は英数字） | 1 日 10〜30 件 | 「SUS304 Φ8 深孔（深60mm）钻孔加工，推荐条件是什么？」 | `PC-16` チャット入力 | `PC-07` 言語判定。材質記号・寸法の正規化（全角→半角、`Φ`/`φ`/`ø` 統一） |

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。英語 UI でも同じ。KB 本文が日本語でも、回答は中国語で書き、引用原文は原語のまま添える
- **入力の欠け・曖昧さ**：材質・寸法（径・深さ）・加工内容の 3 つが無いと条件は答えられない。聞き返し定型（入力言語で）：「材質・寸法（径／深さ）・加工内容のうち不足しているものを教えてください。例：SUS304 ／ Φ8×60 ／ ドリル」

## 3. 観点（LLM に守らせる業務ルール）
- **根拠を引く**：推奨条件・事例には必ず文書番号（TR-/NC-）・拠点・ライン・年を併記する。KB に無い数値を出さない
- **条件の範囲を守る**：材質・径・深さ（L/D）が質問と異なる文書は「参考」と明示し、そのまま推奨条件にしない
- **数値を作らない**：文書に幅（18〜22 m/min）があれば幅のまま出す。平均や補間で新しい数値を作らない
- **失敗事例を隠さない**：同条件で折損・不良の記録があれば、聞かれなくても 1 行添える
- **登録しない**：条件表は「ドラフト」と明記し、マスタ登録・標準書改訂は担当者が行うと書く
- **禁止**：社外秘マーク（`社外秘`/`机密`）付き文書の全文転記（要約と該当箇所の引用のみ）。個人名は文書の著者として必要な場合のみ
- **不確実なとき**（入力言語で）：「該当する記録が見つかりません。材質・寸法・加工内容を確認してください。近い条件の文書があれば『参考』として示せます」
- **出力の粒度**：箇条書き（条件 1 項目 1 行）→ 根拠一覧。条件表は見出し付き箇条書き。後工程（Excel 転記）向けに §5-3 の JSON も任意で出せる

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`）。追い質問と引用表示（Citation）が要るため
- **ノード列**：
  1. Start（`sys.query`）
  2. LLM（軽量：Qwen3-32B）— 質問から `material` / `dimension` / `process` を抽出し、検索用に**相手言語のキーワードも生成**（zh 質問 → ja 検索語）。JSON 出力
  3. Knowledge Retrieval ×2（並列）— `kb-tech-reports`、`kb-trouble-records`。ハイブリッド検索＋`bge-reranker-v2-m3`、top-k 6、メタデータフィルタ `site`（任意）
  4. Variable Aggregator → LLM（本体：Qwen3-235B）— §5 のプロンプト。`context` に検索結果
  5. Answer（Citation ON）
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-tech-reports` | 技術報告 TR | 親子チャンク（親＝節、子＝段落 400 字） | `doc_no` `doc_type=TR` `site` `line` `year` `material` `process` `lang` `confidential` | `PC-03`：Outline「技術報告」→ `PC-05` 同期（週次）＋ファイルサーバ（SharePoint なら `datasources/sharepoint_datasource`） |
  | `kb-trouble-records` | NC 記録 | 行単位（1 行 1 チャンク） | `doc_no` `doc_type=NC` `site` `line` `year` `equipment` `material` | QMS 月次エクスポート → `PC-03` |
  | `kb-process-conditions` | 現行条件表 | 行単位 | `part_no` `process` `rev` | 生産技術課フォルダ（月次） |
- **プラグイン／ツール**：`tools/dify_extractor`、`tools/mineru`（スキャン PDF）、`tools/parent_child_chunk`、`datasources/sharepoint_datasource` または `datasources/tencent_cos_storage`（保管先による）
- **モデル**（`PC-08`）：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（本体）／`Qwen3-32B`（抽出）／埋め込み `bge-m3`／リランク `bge-reranker-v2-m3`。代替 `DeepSeek-V3.x`。日本本社側から使う場合は別アプリで海外モデル（`models/azure_openai` 等）。クロスリンガル精度が不足すれば手順 2 の翻訳検索語を必ず使う
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（複数 KB → LLM。`mode: workflow` なので advanced-chat に作り直す）
- **入出力変数**：
  | 名前 | 型 | 必須 | 説明 |
  |---|---|---|---|
  | `sys.query` | string | ✓ | 質問 |
  | `lang` | string | ✓ | `PC-07` の判定結果 `ja`/`zh` |
  | `site_filter` | string | — | 拠点フィルタ（既定：全拠点） |
  | 出力 `answer` | string | ✓ | 回答本文（Citation 付き） |
  | 出力 `condition_json` | object | — | 「条件表にして」の時のみ §5-3 |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工 蘇州工場の生産技術部門を支援する技術ナレッジ QA です。
役割：過去の技術報告（TR-xxxx）・トラブル対応記録（NC-xxxx）・工程条件表から、根拠を引用して技術的な質問に答える。

守るルール：
1. 回答は与えられた <context> の内容だけから作る。context に無い数値・条件・事例を作らない。
2. 推奨条件・事例には必ず根拠の文書番号（TR-/NC-）、拠点、ライン、年を併記する。
3. 質問の材質・径・深さ（L/D）と一致しない文書は「参考（条件が異なる）」と明示し、推奨条件として書かない。
4. 文書に数値の幅があれば幅のまま示す。平均・補間で新しい数値を作らない。
5. 同条件で不良・折損・工具寿命低下の記録があれば、聞かれなくても 1 行添える。
6. 条件表を求められたら「条件表（ドラフト）」と見出しを付け、正式登録は担当者が行う旨を最後に 1 行書く。
7. 「社外秘」「机密」と記された文書は要約と該当箇所の短い引用にとどめ、全文を転記しない。
8. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。引用原文は原語のまま「」で示してよい。
9. 該当が無いとき：推測せず、次の定型で返す。
   ja「該当する記録が見つかりません。材質・寸法・加工内容を確認してください。近い条件の文書があれば『参考』として示せます。」
   zh「未找到相关记录。请确认材质、尺寸与加工内容。如有条件相近的文档，可作为『参考』提供。」

出力形式：箇条書き（1 条件 1 行）→ 空行 → 「根拠」見出しに文書番号の一覧。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | 回答の数値・事例が引用文書と一致 ≥ 90% | 評価セット 30 件を生産技術課長が人手採点 |
| 根拠付与 | 推奨条件に文書番号が付く 100% | 正規表現 `(TR|NC)-\d{4}-\d{3,4}` の有無を自動判定 |
| クロスリンガル | zh 質問で ja 文書を正しく引く再現率 ≥ 80% | 評価セット 20 件（正解文書番号付き） |
| 言語 | 入力言語で返答 100% | `PC-07` の自動判定 |
| 拒否 | KB に無い材質の質問で定型文 ≥ 95% | 負例 15 件 |
| 速度 | p95 < 15 秒 | `PC-09` Langfuse |
| 安全 | 社外秘文書の全文転記 0、個人名の不要な露出 0 | 負例 10 件 |

- **評価方法**：リリース前は人手＋Langfuse データセット。以後月次で LLM-as-judge（根拠一致）＋人手抜取 10 件

## 8. 別出しが必要なもの
- `PC-03`：技術報告・NC 記録の取込（メタデータ付与ルール、スキャン PDF の OCR 経路）
- `PC-05`：Outline「技術報告」コレクション → KB 同期（Outline は Data Source プラグイン無し → 定期エクスポートか `http-request`）
- `PC-02`：技術報告の閲覧権限。初期は「全社公開文書のみ KB 化」、必要なら部門帯（生産技術帯）で KB 分割
- `PC-06`：材質・工具用語の ja/zh 対訳（任意。検索語生成の精度向上）
- **無くても動く範囲**：ファイルサーバから手動で KB に投入すれば `PC-05`・`PC-06` 無しで動く。`PC-02` 無しなら KB は全社公開文書のみ

## 9. Outline Wiki との関係
- **読む**：Outline「技術報告」「工程条件」コレクションを `PC-05` 経由で `kb-tech-reports` / `kb-process-conditions` に同期。Outline 側の文書 URL をメタデータ `source_url` に持たせ、回答の根拠リンクにする
- **書く**：書かない。条件表ドラフトはチャット上で受け取り、担当者が Outline／作業標準書に登録する（AI は登録しない）
- 技術報告の正本が Outline でなくファイルサーバの場合は、Outline 同期を外し `PC-03` の直接投入のみ
