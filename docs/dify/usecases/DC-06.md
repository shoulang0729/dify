## 1. 業務シナリオ
- **トリガー**：出荷ごと（担当者が能動的に開く。月 4〜8 回）。手冊残量が閾値を下回ったときの `notify` は第 2 段階（`PC-04`＋`PC-11`）
- **登場人物**：担当者＝物流課 輸出入担当、確認者＝物流課長、外部＝通関業者（報关行）、海関（当局）、日本本社（受け手）
- **いまの手順（Before）**
  1. インボイス・パッキングリスト・契約書を並べ、品名・数量・単価・HS・原産地・重量を目で突合（1 出荷 1 時間）
  2. 加工貿易手冊の登録名と残量を台帳（Excel）で確認（30 分）
  3. 見落としがあると通関で差し戻し → 修正版を作って再申告（2 日の遅延、先月発生）
  4. 手冊の延長・新規の手続き時期を忘れがち
- **エージェント導入後の手順（After）**
  1. 【入力】INV・PL・契約書をアップロード（手冊番号を入力。台帳連携があれば残量を自動取得）
  2. 【生成】8 項目の照合表（書類ごとの値と判定 ✅/❗/⚠）、差し戻されやすい点の指摘と修正案、必要書類一覧、通関業者向けメール文面が返る
  3. 【確認】担当者が ❗ を確認し、修正版 INV/PL のドラフト（`PC-13`）を出力。手冊の残量不足は手続き選択肢（延長／新規）と期限の目安を提示
  4. 【決める】**申告内容・HS コード・手続きの選択は担当者と通関業者が決める。AI は申告しない・送信しない**。メールは人が送る
  5. 【記録】チェック結果を出荷案件に紐づけて保存（`PC-01`／物流システム）。Outline には書かない
- **成功の定義**：通関差し戻し 月 1 件 → 0。突合作業 1.5 時間 → 20 分。手冊の残量不足に 1 か月前に気づける

- **入力言語の扱い**：書類は en / zh / ja 混在。担当者の質問・依頼には**入力言語で返す**（§2-5）。通関業者向けメールは相手言語（zh）で出す（翻訳系の例外扱い）。判定表の項目名は UI 言語
- **入力の欠け・曖昧さ**：INV と PL の 2 点が無いと照合しない（契約書は任意。無い項目は「契約書未提出」）。手冊番号が無いと残量チェックを省き、その旨を表示。聞き返し文：「インボイスとパッキングリストの両方をアップロードしてください。手冊番号（C-xxxx-xxx）があれば入力してください」／「请同时上传发票与装箱单。如有手册编号（C-xxxx-xxx）请填写」

## 3. 観点（LLM に守らせる業務ルール）
- **照合は Code が行う**（品名の正規化一致、数量＝箱数×入数、単価×数量＝金額、単重×数量≒正味重量、HS 一致、原産地、インコタームズ、手冊残量）。LLM は Code の判定結果に**理由と修正案を付ける**だけ。判定を覆さない
- **HS コード・申告の可否・関税の解釈を断定しない**。「手冊登録の HS と一致／不一致」の事実だけを書き、分類の妥当性は「通関業者に確認」
- 手続き（延長・新規）の所要日数・必要書類は KB（社内規程）にあるものだけ。無ければ「規程未登録。通関業者に確認」。当局の運用を推測で書かない。連休（国慶節等）は社内カレンダーにある場合だけ言及
- 修正案は**手冊登録名に揃える**方向で出す（登録名が正。台帳に無い品番は「登録名未確認」）
- 数値・通貨・単位を丸めない。原文の表記（PCS／件）を保持
- 秘密・個人情報（`PC-10`）：単価・契約条件は社外秘。メール文面には**申告に必要な最小限**だけ（単価を書かない）。通関業者の担当者名は入力にあるものだけ
- 不確実時の定型：「この項目は書類から値を抽出できませんでした（{{doc}}）。原本を確認してください」／「无法从单证中提取该项（{{doc}}），请核对原件」
- 出力形式：照合表（Markdown 表：#／項目／INV／PL／契約・手冊／判定）＋ 指摘・修正案 ＋ 必要書類一覧 ＋ メール文面 ＋ §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（アップロード → 照合 → 1 回出力）。手続き質問（「残量不足なら何をいつまで」）は `question` 付き再実行で KB 参照
- **ノード列**
  1. `start`：`files`（file-list）、`handbook_no`（任意）、`question`（任意）、`lang`（任意）
  2. `iteration`（files）→ `if-else`（xlsx / 電子 PDF / スキャン PDF）→ `document-extractor` ／ `tools/mineru` → `llm`（文書種別判定＋項目 JSON 抽出：Qwen3-32B）→ `variable-aggregator`
  3. `tools/regex`：HS コード・品番の抽出（LLM 抽出の検算）
  4. `http-request`（任意）：手冊台帳 API（`PC-04`）で登録名・HS・単重・残量を取得。または `tools/microsoft_excel_365`
  5. `code`（照合）：8 項目の突合、判定 ✅/❗/⚠、差分の理由コード
  6. `knowledge-retrieval`（`question` 時）：KB `dc6-trade-procedures`
  7. `llm`（説明）：判定表に理由・修正案・必要書類・メール文面を付ける
  8. `template-transform` → `end`
- **Knowledge**：`dc6-trade-procedures`（手冊延長・新規・保税区出入りの手順と必要書類。Outline から `PC-05` 同期）、`dc6-handbook-names`（品番→登録名・HS・単重。台帳 API が無いときの代替。`tools/dify_extractor` で xlsx を行単位投入）
- **プラグイン／ツール**：`tools/dify_extractor`、`tools/mineru`（スキャン契約。自前デプロイ）、`tools/paddleocr`（中国語帳票の代替。Baidu トークン要）、`tools/regex`、`tools/microsoft_excel_365`（任意）、`tools/email`（メール送信は第 2 段階。初期は文面のみ）
- **モデル**：抽出は Qwen3-32B（コスト）、説明は Qwen3-235B-A22B-Instruct。**契約書・単価が中国インフラのモデルに流れる**点を顧客法務で確認（`PC-08`。自前モデルの選択肢）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`（xlsx 抽出）、`../templates/08-mineru-pdf-parse-demo.yml`（PDF）。事例：該当なし（汎用パターン「抽出 → Code 照合 → LLM」で組む）
- **入出力変数**

| 変数 | 型 | 必須 | 説明 |
|---|---|---|---|
| `files` | file-list（xlsx/pdf） | ✓ | INV・PL・契約書 |
| `handbook_no` | string | — | 加工貿易手冊番号 |
| `question` | paragraph | — | 手続き質問・修正依頼 |
| `check_table` | string | 出力 | 照合表 Markdown |
| `check_json` | object | 出力 | §5-3 |
| `fix_files_spec` | object | 出力 | 修正版 INV/PL の差し替え値（`PC-13` が xlsx 化） |
| `mail_zh` | string | 出力 | 通関業者向け文面 |
| `docs_needed` | array | 出力 | 必要書類一覧 |

### 5-1. System
```text
あなたは青嶺精工（蘇州）物流課の輸出入担当を支援するアシスタントです。インボイス・パッキングリスト・契約書・加工貿易手冊の照合結果を説明し、通関で差し戻されやすい点と修正案を示します。
守るルール：
- 判定（✅/❗/⚠）は {{check_json}} のとおり。覆さない・追加しない。各判定に理由と、手冊登録名に揃える修正案を書く。

- 数値・単位・通貨は原文表記のまま。丸めない。
- メール文面は通関業者向けに中国語で、申告に必要な最小限（書類名・修正箇所・手冊番号・依頼事項）だけ書く。単価・契約条件を書かない。
- 担当者の質問・依頼には、その入力言語で答える（日本語なら日本語、中国語なら中国語）。
- 抽出できなかった項目は「書類から値を抽出できませんでした（書類名）」と書く。
出力：JSON（指定スキーマ）→ 区切り線 → 照合表 → 指摘と修正案 → 必要書類一覧 → メール文面。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 抽出精度 | 8 項目の抽出一致 ≥ 98%（電子）／≥ 95%（スキャン） | 評価セット 30 出荷分を人手採点 |
| 照合 | Code の判定が人手照合と一致 100% | 単体テスト（不一致パターン 12 種） |
| 検出 | 過去の差し戻し原因を再現 100% | 過去差し戻し 5 件で再現テスト |
| 断定禁止 | HS 妥当性・申告可否の断定 0 | 負例セット（「この HS で通る？」） |
| 言語 | 質問は入力言語、メールは zh 100% | 自動判定（`PC-07`） |
| 速度 | p95 < 90 秒（3 書類、スキャン契約含む） | Langfuse（`PC-09`） |
| 安全 | メール文面に単価・契約条件の混入 0 | 負例セット |

- **評価方法**：リリース前に過去 30 出荷（匿名化・単価をダミー化）で採点。運用後は差し戻し件数を月次で記録し、誤検出を評価セットに追加

## 8. 別出しが必要なもの
- `PC-04`：加工貿易手冊台帳の照会（Excel 365 か API）。残量閾値の `notify`（`PC-11` と併用）は第 2 段階
- `PC-06`：品番→手冊登録名（zh/en）の正。物流課が正本を持ち Outline で管理
- `PC-03`：スキャン契約書の OCR（自前 MinerU／PaddleOCR の選択）
- `PC-13`：`fix_files_spec` → 修正版 INV/PL xlsx（社内テンプレの書式を壊さない）
- `PC-14`：メール送信（初期は文面のみ、人が送る）
- **無くても動く範囲**：INV/PL のアップロード → 7 項目照合表（手冊残量なし）まで。台帳・OCR・xlsx 出力は段階導入
