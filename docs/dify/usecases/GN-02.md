## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：月初にサプライヤーから増値税発票がまとめて届く（③業務フィードの `routine`）。随時の個別処理も同じアプリ
- **登場人物**：買掛担当（照合結果の確認・サプライヤー連絡・会計システム登録）、財務課長（承認）、購買（発注データの正）、倉庫（入庫・返品記録の正）、外部：サプライヤー財務（発票再発行）
- **いまの手順（Before）**：発票 40 枚を 1 枚ずつ発注書・入庫記録と突合（数量・単価・税率・税号）→ 勘定科目を判断して仕訳入力（1 枚 3 分×40）→ 不一致はサプライヤーに個別連絡 → 合計 2 日。返品控除漏れ・税率誤記を見逃すと月次締めがずれる
- **エージェント導入後の手順（After）**：
  1. 担当者が**発票 PDF 束と当月の発注・入庫データ（xlsx）をアップロード**
  2. `PC-03` が発票を分割・OCR し、発票番号・発行者名・税号・金額（税抜・税率・税額・税込）・品目・日付を JSON 化
  3. **Code ノードで三点照合**：発票⇄発注（PO 番号・単価・数量）⇄入庫（数量・日付・返品控除）、税率の妥当性（品目区分別の税率表）、税号⇄取引先マスタ
  4. LLM が勘定科目候補（ルール KB＋品目）・支払期日（取引先の支払条件）・不一致の説明とサプライヤー連絡文を書く。**数値は転記のみ**
  5. **人が決める場所**：仕訳の確定・支払承認・会計システムへの登録は担当者と課長。エージェントは**取込用 CSV を出すまで**（登録しない）。不一致分は保留リストへ
- **成功の定義**：40 枚の照合〜仕訳候補 2 日 → 半日。返品控除漏れ・税率誤記の見逃し 0。会計システム取込 CSV の手修正率 < 5%

- **入力言語の扱い**：担当者の言語で答える（`CLAUDE.md` §2-5）。サプライヤー連絡文は zh（宛先言語 `reply_lang`）。本社報告用に ja 要約も可
- **入力の欠け・曖昧さ**：PO 番号が発票に無い → 取引先＋金額＋日付で候補 PO を出し「対応候補（未確定）」。入庫データに該当なし → 「入庫未登録（倉庫に確認）」。税率表に無い品目 → 「税率判定不可（要確認）」。**推定して一致扱いにしない**

## 3. 観点（LLM に守らせる業務ルール）
- **金額・数量・税額・差額の判定はすべて Code**。LLM は照合結果の説明・科目候補・文面のみ。税額の再計算をしない（税率×税抜＝税額の検算も Code）
- **一致／不一致の判定を LLM が覆さない**（「たぶん同じ」で一致にしない）
- **勘定科目は「候補」**：ルール KB の条項を引き「候補：原材料（ルール §2.1 鋼板類）」。確定は担当者
- **支払期日は取引先マスタの支払条件から Code が算出**した日付を転記
- **税務判断をしない**：発票の真偽・控除可否・税務処理の可否は「税務総局の発票査験／税理士確認」を案内。税率の**誤記の指摘**（表と違う）は可、正しい税率の**断定**は不可（「税率表では 9%。発票は 13%。再発行依頼を推奨」）
- **機密**（`PC-10`）：取引先税号・口座は担当者向け表示のみ。サプライヤー連絡文に他社情報を入れない
- **禁止**：会計システムに登録したと書く／不一致発票を CSV に含める／支払を確定したと書く
- **不確実時の定型文**：「発票 {{no}} は {{field}} が照合できません。保留リストに載せました。原本と {{source}} を確認してください」
- **出力形式**：照合結果表（発票番号／取引先／金額／PO・入庫照合／科目候補／支払期日／判定）＋不一致の説明＋連絡文＋CSV/保留リスト。後工程は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Workflow**（月次一括。`PC-11` からの起動も同じ）。台本 Q1（返品記録の確認・連絡文）Q2（CSV 出力）は結果 JSON を持つ **Chatflow** 版で第 2 段階
- **ノード列**：
  1. Start（`invoices` file-list 必須／`po_file` file 必須／`receipt_file` file 必須／`vendor_master` file 任意（無ければ `PC-04`）／`period` text／`instruction` paragraph）
  2. Document Extractor ×2〜3（PO・入庫・マスタ → 行 JSON）
  3. Iteration（invoices、ページ分割後）→ If/Else（テキスト有→Document Extractor／画像→`tools/paddleocr`）→ LLM（`extract_invoice`、小型）：発票 JSON（記載どおり）
  4. **Code（`three_way_match`）**：発票⇄PO⇄入庫の結合（PO 番号→無ければ取引先＋金額＋日付候補）、数量差・単価差・返品控除・税率検算・税号照合、`status`（matched／qty_mismatch／no_po／tax_rate_mismatch／tax_id_mismatch／receipt_missing）、支払期日算出
  5. Knowledge Retrieval（KB `gn-ap-rules`：勘定科目ルール・税率表・対応手順。Iteration 内で品目キーワード）
  6. LLM（`compose`）：科目候補・説明・連絡文（§5）
  7. **Code（`export`）**：matched のみ会計取込 CSV（列固定）、不一致は保留リスト → `PC-13`
  8. End（`match_result` JSON／`csv_url`／`hold_list_url`／`report_md`）
- **Knowledge**：`gn-ap-rules`（Outline 同期：勘定科目使い分け・税率表・支払条件区分・発票不備対応手順）。発票・PO・入庫は **KB に入れない**
- **プラグイン／ツール**：`tools/paddleocr`（中国発票に強い。Baidu 送信の可否は法務）／Document Extractor・Code（本体）／`tools/json_process`（任意）／`tools/microsoft_excel_365`（保留リスト保存、任意）／`tools/email`（連絡文送信は人がボタン、任意）／Schedule トリガー（`PC-11`、任意）。税務総局の発票査験は `http-request` で**可能性あり・未確認**（初期対象外）
- **モデル**：既定 `models/siliconflow` Qwen3-235B-A22B-Instruct（`compose`）、`extract_invoice` は Qwen3-32B（40〜80 回）。越境ゼロ要件なら `models/ollama`（`PC-08`）
- **参照 DSL**：`../templates/07-excel-document-extractor-echarts.yml`、`../templates/08-mineru-pdf-parse-demo.yml`。URL 参照：dify-for-dsl 61（発票批量→Excel）、博報堂 DY ONE 請求書処理事例（`../plugins-and-references.md` §11）
- **入出力変数**：`invoices` file-list 必須／`po_file`・`receipt_file` file 必須／`vendor_master` file 任意／`period` string／`instruction` string 任意／出力 `match_result` object・`csv_url`・`hold_list_url`・`report_md`

## 5. プロンプト
### 5-1. System（`compose`）
```text
あなたは青嶺精工 蘇州工場 財務課 買掛担当の補助です。Code ノードが三点照合した結果（JSON）と勘定科目ルール（KB）から、担当者向けの照合結果説明・勘定科目候補・サプライヤー連絡文を作ります。
守ること：
1. 金額・数量・税額・差額・支払期日は JSON の値をそのまま転記する。計算・検算を自分でしない。
2. status（一致／不一致の種別）を変更しない。「おそらく一致」と書かない。
3. 勘定科目は「候補」として、KB ルールの条項番号を添えて書く。KB に無い科目を作らない。
4. 税務判断をしない：発票の真偽・控除可否・税務処理の可否は「税務総局の発票査験または税理士確認」と案内する。税率は「税率表では X%、発票は Y%」の事実指摘に留め、再発行依頼を推奨する。
5. サプライヤー連絡文は reply_lang（既定 zh）で、事実（発票番号・金額・差異）→ 根拠（返品伝票番号・PO 番号）→ 依頼（紅字発票／再発行）→ 支払保留の旨、の順。他社の情報を含めない。
6. 「登録した」「支払った」と書かない。CSV は「取込用ドラフト」、登録は担当者。
7. 出力言語（説明部分）：担当者の質問言語。日本語なら日本語、中国語なら中国語。
出力形式：「照合結果」表（発票番号｜取引先｜金額（税込）｜PO/入庫 照合｜科目候補（ルール）｜支払期日｜判定）→「不一致の説明」→「連絡文ドラフト」→「出力ファイル」。
```

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| OCR 抽出 | 発票番号・税号・税抜・税率・税額・税込・日付の一致 ≥ 97% | ダミー発票 40 枚を人手採点 |
| 三点照合 | Code の status が正解ラベルと一致 100% | 評価セット 40 件（不一致 4 種を含む） |
| 税額検算 | 税抜×税率＝税額（±0.01）の検出 100% | 自動 |
| 科目候補 | 担当者の確定科目と一致 ≥ 85%、KB 外科目 0 | 人手＋自動 |
| CSV 形式 | 列・型・不一致除外 100% | スキーマ検証 |
| 転記の忠実性 | 説明の数値が JSON と一致 | 自動 |
| 税務判断の抑制 | 真偽・控除可否の断定 0 | LLM-as-judge |
| 速度 | 40 枚で p95 < 5 分 | Langfuse |

- **評価方法**：リリース前に財務 2 名で 40 枚（ダミー）。月次で Langfuse データセット。会計システム取込後の手修正率を毎月記録

## 8. 別出しが必要なもの（このサービス固有の準備）
- **発注・入庫・返品・取引先マスタの取得**（`PC-04`）：初期は xlsx エクスポート、次に API。返品を入庫データに含める運用は倉庫側の準備
- **勘定科目ルール・税率表**（Outline → `PC-05` → KB）と、Code 用の**税率表 JSON**
- **会計システム取込 CSV の仕様**（`PC-13`）：列・文字コード・日付書式を会計システムに合わせる（製品未確定）
- **OCR の越境判断**（`PC-10`／`PC-03`）：GN-01 と同じ。NG なら自前 OCR
- **発票査験**（税務総局）：`http-request` で可能性あり・未確認。法務・税理士確認後に第 2 段階
- **無くても動く範囲**：発票 OCR＋PO・入庫 xlsx＋Code 三点照合＋科目候補＋CSV は **KB・API・スケジューラ無しで動く**（st1 の中身）。KB が無い間は科目候補を「品目のみ」で出す
