## 1. 業務シナリオ
- **いつ起きるか（トリガー）**：担当者が能動的に開く。典型は現地スタッフから労務条件の質問を受けた駐在員が、**中国語版規程の条文を確認したい**とき。③業務フィードの項目にはならない
- **登場人物**：質問者（総務・人事の駐在員＝日本語母語、または現地人事担当＝中国語母語）、最終回答を受けるスタッフ、確認者（管理部長）。当局は関与しない（労働契約法の解釈は本サービスの範囲外）
- **いまの手順（Before）**：
  1. 就業規則の ja 版と zh 版（別ファイル）を開き、条番号を突き合わせる（20 分）
  2. 中国語版の条文を翻訳して読み、細則（休暇管理細則等）も辿る（20 分）
  3. **ja 版と zh 版で内容が違う**ことに気づかず、日本語版を根拠に回答して現地スタッフと食い違う事故が年数回
  4. 回答文を中国語で書き、現地人事にチェックを頼む
- **エージェント導入後の手順（After）**：
  1. 駐在員が日本語で質問する（現地担当は中国語で）
  2. エージェントが **ja 版・zh 版の該当条文を両方引用**し、版日付が異なれば「版ズレ」を明示し、**どちらを正とすべきか（現地スタッフ向けは中国語版）を根拠付きで示す**
  3. 担当者が回答内容を確認する（**規程の解釈・例外適用は人が決める**）
  4. 「スタッフへの回答を中国語で」でドラフトを受け取り、担当者が送る。日本語版の改定起票メモもドラフトで受け取れる（起票は人）
- **成功の定義**：条文確認を 40 分 → 5 分。**版ズレによる誤回答 0**。個別の休暇残日数等は答えない（PIPL・ACL）

- **入力言語の扱い**：日本語・中国語のどちらでも受け、**入力言語で返す**（`CLAUDE.md` §2-5）。引用条文は ja 版・zh 版の原文をそれぞれ原語で併記し、要約と結論は入力言語で書く
- **入力の欠け・曖昧さ**：規程名が特定できない（「規則で決まってる？」）ときは候補規程を 2〜3 提示して選ばせる。個人の事情（「私の残日数は？」）には答えず、人事窓口を案内

## 3. 観点（LLM に守らせる業務ルール）
- **条文を引く**：回答の根拠は「規程名・版日付・条・項」まで書く。条文の原文を「」で引用する
- **両版を必ず見る**：ja 版・zh 版の両方に該当条があるか確認し、**内容・数値・版日付が異なれば「版ズレ」と明示**する。どちらを正とするかは規程の定め（通常「現地スタッフ向けは中国語版が正」）を引いて示す。定めが無ければ「要確認」
- **解釈しない**：規程に書かれていない例外・運用は「規程に記載なし。管理部に確認」。法律（労働契約法等）の解釈は行わない（当局通達は KN-05 の範囲）
- **数値を作らない**：日数・割合・金額は条文の数値のみ。ja 版と zh 版で数値が違うときは両方書く
- **PIPL**（`PC-10`）：個人の休暇残・給与・処分歴など個人データは KB に入っていないし答えない。質問に身分証番号・氏名が含まれても回答に繰り返さない
- **登録しない**：改定起票メモ・回答文は「ドラフト」。送信・起票は担当者
- **不確実なとき**（入力言語で）：「該当する条文が見つかりません。規程名（例：就業規則／休暇管理細則）を確認してください」
- **出力の粒度**：結論 1〜2 行 → 引用（ja 版／zh 版）→ 版ズレ注記 → 関連細則。後工程（改定起票）は §5-3 JSON

## 4. Dify 構成
- **アプリ種別**：**Chatflow**（`advanced-chat`）。追い質問と Citation のため
- **ノード列**：
  1. Start（`sys.query`）
  2. LLM（Qwen3-32B）— `topic`（休暇／経費／出張／勤務時間／懲戒／その他）と検索語（ja・zh 両方）を JSON 抽出
  3. Knowledge Retrieval ×2 並列 — `kb-rules`（メタデータ `lang=ja`）、`kb-rules`（`lang=zh`）。top-k 各 5、リランク ON
  4. Code — 両検索結果の `doc_id`・`article_no` を突き合わせ、`version_date` を比較して `version_gap`（true/false）と対応表を生成（`PC-12` の軽量版。条単位のテキスト差分は `difflib`）
  5. LLM（本体：Qwen3-235B）— §5 プロンプト。`context` に両版＋`version_gap`
  6. Answer（Citation ON）
- **Knowledge**：
  | KB 名 | 文書 | チャンク | メタデータ | 更新経路 |
  |---|---|---|---|---|
  | `kb-rules` | 規程・就業規則・細則（ja/zh 両版） | **条単位**（1 条 1 チャンク。長い条は項で分割） | `doc_id` `title` `lang` `version_date` `article_no` `category` `audience`（全社／管理職） | `PC-03` ← `PC-05`（Outline 規程コレクション、週次）。改定時は旧版を `archived=true` にして残す（履歴質問用） |
  | `kb-rules-map` | 規程対応表 CSV | 行単位 | `doc_id` | 管理部が更新 |
  - 1 KB でメタデータ `lang` を分ける方式を採る（KB を 2 つに割る方式でも可。ACL 上は同じ「全社公開・HR 帯」）
- **プラグイン／ツール**：`tools/dify_extractor`、`tools/general_chunk`（条分割は Code ノードで前処理する方が確実）
- **モデル**（`PC-08`）：既定 SiliconFlow `Qwen3-235B-A22B-Instruct`（条文読解・日本語品質）／`Qwen3-32B`（抽出）／`bge-m3`／`bge-reranker-v2-m3`。代替 `DeepSeek-V3.x`。**人事規程は越境ゼロ構成（`models/ollama` Qwen）も選択肢**（F-4 (c)）
- **参照 DSL**：`../templates/03-document-chat-classifier-multi-kb.yml`（複数 KB）、`../templates/04-trilingual-consistency-checker.yml`（言語版突合の発想。URL 取得を KB 検索に置き換える）
- **入出力変数**：
  | 名前 | 型 | 必須 | 説明 |

  | `sys.query` | string | ✓ | 質問 |

## 5. プロンプト
### 5-1. System
```text
あなたは青嶺精工 蘇州工場 管理部の社内規程 QA です。
役割：就業規則・社内規程・運用細則の日本語版と中国語版から、根拠条文を引用して質問に答える。

守るルール：
1. 回答は <context> の条文だけから作る。書かれていない例外・運用・法解釈は「規程に記載なし。管理部に確認してください」と書く。
2. 根拠は「規程名（版日付）第 X 条 X 項」まで書き、条文原文を「」で引用する。日本語版・中国語版の両方を引く。
3. <meta> の version_gap が true、または両版の数値・内容が異なるときは、必ず「版ズレ」と見出しを付け、両版の版日付と差を書く。現地スタッフへの回答は中国語版を正とする（規程に別の定めがあればそれに従う）。
4. 日数・割合・金額は条文の数値のみ。作らない。両版で異なれば両方書く。
5. 個人の休暇残日数・給与・処分歴などは答えない。「個別の状況は人事窓口へ」と案内する。質問に含まれる氏名・身分証番号は回答に繰り返さない。
6. 回答文・改定起票メモを求められたら「ドラフト」と明記する。送信・起票は担当者が行う。
7. 言語：ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。引用原文は原語のまま。
8. 該当が無いとき：
   ja「該当する条文が見つかりません。規程名（例：就業規則／休暇管理細則）を確認してください。」
   zh「未找到相关条款。请确认规章名称（例如：员工手册／休假管理细则）。」

出力形式：結論（1〜2 行）→「根拠」（ja 版／zh 版の引用）→ 必要なら「版ズレ」→「関連細則」。
```

### 5-4. Few-shot
- **ja**：Q「年次有給休暇の翌年繰越は何日まで認められる？」→ A：結論「中国語版（2025 年 1 月改定）第 23 条 3 項：上限 5 日」→ 根拠 ja/zh 引用 → 「版ズレ：日本語版（2023 年 7 月版）は上限 3 日のまま。現地スタッフへは中国語版が正」
- **zh**：Q「年假最多可以结转到下一年多少天？」→ A：同構成を中国語で。「版本差异：日文版（2023年7月版）仍为3天」

## 6. 検証観点
| 観点 | 基準 | 測り方 |
|---|---|---|
| 正確性 | 引用条・項・数値が原文と一致 ≥ 95% | 評価セット 30 件を管理部が採点 |
| 版ズレ検出 | 意図的に差を入れた条で「版ズレ」表示 100%、差が無い条で誤検出 ≤ 5% | 正例 10・負例 10 |
| 両版引用 | ja/zh 両方の引用がある ≥ 95% | 自動（`[ja]`/`[zh]` の存在） |
| 言語 | 入力言語で返答 100% | `PC-07` |
| 拒否 | 規程外の解釈・個人データ質問で定型 ≥ 95% | 負例 15 件 |
| 安全 | 個人情報の繰り返し 0 | 負例 10 件 |
| 速度 | p95 < 15 秒 | `PC-09` |

- **評価方法**：リリース前は人手。改定のたび（年数回）に評価セットを更新して回帰。月次で Langfuse の低評価会話を管理部がレビュー

## 8. 別出しが必要なもの
- `PC-03`／`PC-05`：Outline 規程コレクション（ja/zh）→ 条単位チャンク・版日付メタデータ付きで KB 化。旧版のアーカイブ保持
- `PC-02`：HR 帯の閲覧権限（一般公開規程／管理職限定規程）。初期は「全社公開規程のみ KB 化」（F-5 (a)）
- `PC-12`：版ズレ検出（初期は Code ノードの版日付比較＋`difflib`。全規程横断の定期差分検査は `PC-12` 本体へ）
- `PC-10`：会話ログの個人情報マスキング（身分証番号・氏名）
- **無くても動く範囲**：規程を手動投入し、対応表 CSV があれば `PC-05`・`PC-12` 無しで T01〜T07 は動く。`PC-02` 無しなら管理職限定規程を KB に入れない

## 9. Outline Wiki との関係
- **読む**：Outline「規程（日本語）」「规章（中文）」コレクションを正本とし、`PC-05` で `kb-rules` へ同期。文書 URL を `source_url` に持たせ根拠リンクにする
- **書く**：任意。改定起票メモ（§5-3）を Outline「規程改定ドラフト」コレクションに**ドラフトとして**作成（`http-request` で Outline API）。公開・版上げは管理部が行う
- Outline を使わない場合：管理部フォルダの docx を `PC-03` へ直接投入。版日付はファイル名規約から取る

## 10. 未確定・リスク
- **規程の正本**（Outline か管理部フォルダか）と ja/zh の 1:1 対応の有無 — 顧客確認。対応が崩れている規程は対応表で明示
- **「どちらが正か」の定め**（規程に「中国語版を正とする」条項があるか）— 顧客確認。無ければ回答は「要確認」止まり
- **人事データの越境**：規程本文は全社公開でも、質問文に個人事情が入り得る → `PC-10` マスキングか `models/ollama` 構成（F-4 (c)）を顧客法務と決める
- **条分割の精度**：中国語版の「第 X 条」と日本語版の条番号がずれている規程がある可能性 → 対応表で吸収
- 労働法解釈への期待（顧客が「法律も答えてほしい」と言う可能性）— 範囲外と明示。当局通達は KN-05
