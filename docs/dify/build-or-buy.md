## 2. 各行の詳細（8 節）

### 2-1. 翻訳 → LG-01（＋ LG-02 は別途）

BP 翻訳製品が埋めるもの：レイアウト復元（元の体裁のまま訳文を返す）・用語集の運用 UI・オンライン編集・権限管理。**LG-01（PC-13・PC-06・PC-02 の代替候補）** として記録する。

**LG-02（用語集）との関係**：BP 翻訳製品の「用語集」は訳出時に参照する辞書機能であって、LG-02 の「呼称の揺れを検出し、用語集への登録候補を作る」ではない。**LG-02 は別サービスのまま。** LG-01 を買う場合、LG-02 の登録候補づくりは別途必要。

### 2-2. ChatBI → NM-05（＋ RS-05 は入力が違う）

BP ChatBI 製品が埋めるもの：DB 構造と BI 知識の自動校正・サンプル庫・SQL 自己修復・結果表示の推奨・質問の曖昧さ識別。**NM-05（PC-04 の読み取り側の代替候補）** として記録する。

**RS-05 との関係**：RS-05（ダッシュボード出力からの気づき分析）は入力が BI のエクスポート（PDF・CSV）で、DB に接続しない。ChatBI 製品は DB 直結のため一致は低く、**統合しない**。ただし、BI に直結できる環境なら RS-05 は NM-05 と同じ手段で足りる。

### 2-3. 契約レビュー → DC-11（新規。設計書 §4）

一致 3/5（テンプレートが違う＝画面が違う）のため**目的別分割＝新規採番**。仕様は設計書 §4（DC-11 契約書レビュー〔逸脱条項の検出と修正案〕）。データ層への反映は別 PR（PR-B）。

### 2-4. チーム知識ベース → DC-02 / KN-09 / PC-13

BP チーム知識ベース製品が埋めるもの：個人 KB → チーム KB のワンクリック変換（**KN-09**）・議事録自動生成（**DC-02**）。

**PPT 自動生成をサービスにしない理由**：DC-01・DC-09 は「何を書くか」を決めるサービスで、出力が Markdown か Word か PPTX かは出口の形式にすぎない。形式ごとにサービスを増やすと同じ業務が並んでしまう（統廃合ルール違反）。**PC-13（ファイル出力）の実現手段候補**として記録する。

**`usecases/KN-09.md` はまだ存在しない**（IT 固有の実装リファレンスは未着手）ので、本行だけで参照先ファイルは無い。

### 2-5. アパレルデザイン → 対象外（PM 判断 2026-09-11）

架空世界は 3 つ（製造＝青嶺精工、金融＝碧洋銀行、IT＝翠雲システムズ）。アパレルはどれにも当たらず、5 軸すべて 0。**対象外。アパレル業種の顧客が現れたら、まず `data/world/<新業種>/` を立てるところから。**

### 2-6. 採点 → 対象外（PM 判断 2026-09-11）

教育向けの製品で、3 つの世界のどの業務にも主用途が無い。研修の理解度テストは PO-03 の範囲で足りる。**対象外。**（`PO-03` の `tags`・`desc`・台本は 1 文字も変えない）

### 2-7. AI ポータル → カタログ対象外。ポータルに取り込む（設計書 §7。`portal-nocobase` rev4 の入力）

複数プラットフォームのエージェント統合管理・統合 ID 認証・コンテンツ監査・LLM ゲートウェイ・IM 連携・プリセットのエージェントは、カタログのサービスではなく**基盤**の話。詳細は `docs/handoff/2026-09-11-bp-usecases.md` §7（`docs/handoff/2026-09-10-portal-nocobase.md` rev4 に反映すべき差分。同設計書は本書からは 1 文字も変えない）。⚠️ Dify Enterprise を入れるかどうかは保留（同設計書 §13-2）。

### 2-8. 履歴書スクリーニング → PT-05（PIPL の但し書きが本体。設計書 §2-7）

BP 履歴書スクリーニング製品が埋めるもの：履歴書の一括解析・評価軸のカスタマイズ・多軸スコア・面接レポート。**PT-05** として記録する。

**重大な但し書き**：PT-05 は「氏名・連絡先はエージェント側に留め、匿名化された候補者 ID だけを受け取る」設計（`SVCS.pt5.desc` に明記。PC-10 個人情報・PC-15 パートナー連携ゲートウェイの前提）。BP 製品は履歴書そのものを自社側で解析するため、統合すると PT-05 の前提が裏返る（個人情報の所在がエージェント側 → 自社側になり、PC-15 の `not_sent` 表示が成り立たなくなる）。**BP 製品で実現する場合、PIPL 評価と保管・削除の経路（PC-10）を先に決める。**`SVCS.pt5.desc` は 1 文字も変えない。

## 3. 判断が要るもの（PM）

- 8 製品のうち、実際に**買う**かどうか（本書はどの管理番号の選択肢になるかまでを決める。価格判断は見積書の実物を見て PM が行う）
- 契約レビュー（DC-11）を作る（内製）か BP 製品を買うか
- 履歴書スクリーニング（PT-05）を BP 製品で実現する場合、PIPL 評価と保管・削除の経路（PC-10）をどう決めるか（§2-8）
- AI ポータルのコンテンツ監査・LLM ゲートウェイをどう取り込むか（`docs/handoff/2026-09-11-bp-usecases.md` §7・§13-2。Dify Enterprise は保留）

## 4. 更新ルール（契約が決まったら／流れたら、どの行をどうするか）

- **契約が決まったとき**：該当行の「判定」欄に決定日と結論（内製／調達）を追記する。データ層（`SVCS`）を動かす場合は別途設計書・Issue を立てる（`CLAUDE.md` §2-9・§4）。DC-11 のように新規採番が要る場合の通番は永久欠番（`CLAUDE.md` §2-11）
- **契約が流れたとき**：行を削除せず「不成立（日付）」を追記して残す（同じ検討を繰り返さないため）
- **見積の更新**：新しい見積書が来ても、本書に転記するのは機能の要約だけ（§0）。価格・条件の変化は本書に書かない
