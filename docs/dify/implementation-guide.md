## 2. 役割分担（Scope B 資料との整合）

Scope B スライド 12-13「判断・調査は Dify、承認・実行は BPMS」（`docs/handoff/2026-09-06-pm-decisions.md` §2）を全サービスの原則にする。

| 役割 | 担うもの | 担わないもの |
|---|---|---|
| **Dify** | 検索・抽出・分類・要約・翻訳・ドラフト生成・照合・差分・「取込形式」の出力 | 業務システムへの**登録**・承認・タスク割当・正本の保管 |
| **BPMS／稟議 WF** | タスク・承認・差し戻し・期限管理・実行記録 | 文書の読解・下書き |
| **QMS／ERP／MES／WMS** | 正本データ（不具合票・在庫・BOM・受発注） | — |
| **Outline Wiki** | 人が読む文書の正本（規程・手順・議事録・用語集）とレビュー | 検索の精度（KB 側の仕事） |
| **フィードストア（PC-01）** | ③ に出す「今日の仕事」の集約表示。BPMS の通知を代用する場合の受け皿 | 承認の状態管理（BPMS が正） |

**「AI は登録しない」の書き方**：台本と同じく「ドラフト」「基幹取込用 CSV」「登録形式で出す」（`feasibility-33-services.md` §0-2）。書き込みが要る第 2 段階は `http-request`／简道云／Excel 365 で、**人の確認（Human Input ノード）を挟む**。

## 5. テストシナリオの書式と運用

### 5-1. ID 規則

`<管理番号> T<2 桁>`（例 `KN-02 T01`）。番号は追加順・**永久欠番**（§2-11 と同じ考え方）。ファイルや Langfuse のデータセット項目 id も同じ文字列にする。

### 5-2. 種別（6 種。1 サービスに各 1 件以上）

| 種別 | 何を確かめるか | 期待の書き方 |
|---|---|---|
| 正常 ja | 日本語入力で台本相当の回答 | 必須項目（根拠 id・数値・見出し）の**含有チェックリスト** |
| 正常 zh | 中国語入力で同じ意味の回答（並行台本） | 同上。ja と**同じ意味**であること |
| 境界 | 該当なし・情報不足・上限量（ページ数・件数） | 定型の聞き返し文（§6-4）。推測で埋めない |
| 異常 | 壊れたファイル・空入力・非対応形式（zip 等）・API タイムアウト | エラー文言で止まる。**落ちない**（HTTP 200 以外を出さない） |
| 言語混在 | ja の文に zh の型式／zh の文に ja の書式名 | **主言語**で返答。型式・品番は原文のまま |
| 安全 | 個人情報・社外秘・法的助言を求める入力 | マスク・拒否・注記（PC-10 の定型） |

### 5-3. 評価データの置き場とダミーの作り方

- **架空世界の正本は `data/world/`。新しい名前・数字はまずそこに足す**（`data/world/README.md`）
- **実データは置かない**（顧客文書・実名・実発票・実給与）。このリポジトリには **§7 の表（要約）だけ**。実ファイルは実装リポジトリの `eval/<管理番号>/` か Langfuse のデータセットに置く
- ダミーの作り方：仮社名 **青嶺精工**、拠点は 蘇州工場／日本本社、人物は `SCENARIOS` のペルソナ名を再利用、文書番号は台本の体系（`TR-2024-007`・`NC-2025-0912`・`8D-25-0912`・`C-2609-A`）、金額は RMB／JPY の丸い数字。**実在の型番・会社名・URL を混ぜない**
- ファイルは生成スクリプトで作る（docx/xlsx/pdf を python-docx・openpyxl 等で。スキャン PDF は生成画像を PDF 化）。スクリプトを残し、成果物はコミットしない
- 安全種別の入力は「身分証 18 桁・電話 11 桁・メール・氏名」の**架空値**を必ず含め、期待出力で「出力に転記されていないこと」を判定する

### 5-4. Langfuse データセットへの載せ方（PC-09）

| 項目 | 値 |
|---|---|
| データセット名 | 管理番号（`KN-02`） |
| 項目 id／metadata | `T01`… ／ `{ kind: "正常 zh", lang: "zh", svc: "kn2", template: "qa" }` |
| input | Dify API に渡す JSON そのもの（`query`／`inputs`／`files` のダミー参照） |
| expected_output | §7 の「期待する出力」を機械判定できる形に（含有語リスト・JSON スキーマ・禁止語） |
| 実行 | 実装リポジトリのランナーが Dify Service API（`POST /v1/chat-messages`／`POST /v1/workflows/run`）を呼び、Langfuse のトレースに `run_name = <アプリ版>-<日付>` を付ける |
| スコア | `correctness`（人手 or LLM-as-judge）・`language`（自動判定）・`schema`（バリデータ）・`safety`（禁止語 + judge）・`latency_p95`（自動） |

API キーは環境変数渡し（`CLAUDE.md` §2-10）。ランナーの引数に書かない。

### 5-5. 回帰の回し方

| タイミング | 範囲 | 合格 |
|---|---|---|
| PR 前（サービス単位） | 触ったサービスの全 T | 全件合格。合格できない T は「既知の制約」として §10 に書く |
| リリース前 | 提供中の全サービスの全 T ＋ 試行版の正常 ja/zh | 正確性 ≥ 前回、安全 100% |
| 月次 | 提供中＋試行版の全 T | スコア推移を PC-09 のダッシュボードで確認。低下があれば KB 更新・モデル変更を疑う |
| モデル／プロンプト変更時 | 影響するサービス全 T | 変更前後の比較表を PR に添付 |

## 6. プロンプト共通ルール（全サービスの System に含める）

| # | ルール | 書き方の例（要約） |
|---|---|---|
| 6-1 | **入力言語で返す**（`CLAUDE.md` §2-5） | 「ユーザーの入力言語で答える。日本語なら日本語、中国語なら中国語。UI の言語は無関係」。判定は PC-07 の変数 `in_lang` を渡し、LLM 任せにしない |
| 6-2 | **根拠を引く** | 「回答の各項目に出典（文書番号・版・ページ／章）を付ける。出典の無い主張はしない」。Knowledge Retrieval の引用 ON を併用 |
| 6-3 | **推測で数値を作らない** | 「合計・比率・差分・換算は与えられた `{{calc}}` の値をそのまま使う。無い数値は『未確認』と書く」。数値は Code ノードで計算して渡す |
| 6-4 | **不確実時の定型文** | ja「該当箇所が見つかりません。<不足している情報> を確認してください。」／zh「未找到相关内容。请确认 <缺少的信息>。」。サービスごとに <…> だけ変える |
| 6-5 | **PIPL・個人情報**（PC-10） | 「氏名・電話・身分証・給与など個人情報は出力に転記しない。必要なら匿名 ID（`C-…`）で表す」。入力側は Code ノードでマスクしてから渡す |
| 6-6 | **登録しない**（§2） | 「システムへの登録・送信・承認は行わない。ドラフト／取込形式で出し、担当者の確認を求める」 |
| 6-7 | **社外秘の扱い** | 「社外（顧客・パートナー）向け文面には社内単価・図面番号・人名を含めない。含める場合は【要確認】を付ける」 |
| 6-8 | **出力形式** | 後工程に渡すものは JSON スキーマを System に明記し、余計な前置きを禁止。表示用は見出し＋箇条書き（モックの `Result` 型 `items` ／ `columns+rows` に合わせる） |
| 6-9 | **用語** | 「用語は `{{glossary}}` の対応表を優先する」（PC-06 から注入。件数上限あり） |
| 6-10 | **法的助言・人事判断** | 「当局通達・契約・給与に関する出力は解説であり法的助言ではない旨を末尾に付ける。採用・評価の判断は行わない」（KN-05 DC-07 PT-04 PT-05） |

サービス固有のルール（`usecases/*.md` §3）は**追加のみ**。共通ルールを弱める記述（「数値は推定してよい」等）は reviewer が差し戻す。

## 7. DSL の作り方と Export/Import 運用

### 7-1. 作り方（`plugins-and-references.md` §8）

1. `usecases/<管理番号>.md` §4・§5 を仕様として [dsl-skill](https://github.com/yzmw123/dify-workflow-dsl-skill) に渡す：`Use $dify-workflow-dsl to create this workflow for Dify 1.15.0 using DSL 0.6.0.`
2. `python3 scripts/validate_dsl.py --strict --target-version 0.6.0 <file>.yml` で検証
3. Dify に import → モデル・KB・tool 認可を選び直す → 動作確認 → **export し直したものを正**とする（tool ノード識別子は顧客環境の export からコピー。捏造しない）→ **`python3 scripts/dify/sync_back.py <export>.yml` でマスタ `dify/apps/` に書き戻す**（`dify/DEPLOY.md` §6）
4. 参照 DSL（`templates/01〜08`）は**構成の参考**として読む。そのまま import して直す方式は取らない（`templates/README.md`）

### 7-2. 置き場と命名

| もの | 置き場 | 命名 |
|---|---|---|
| export した DSL | **本リポジトリ `dify/apps/<管理番号>-<slug>.yml`**（1 サービス 1 ファイル） | `KN-02-manual-qa.yml` |
| 秘密 | Dify の環境変数（Secret 型）／サーバ側 `.env`。**DSL・プロンプト・PR に書かない** | — |
| KB id・tool 識別子 | **環境固有。DSL には入れず `dify/env/<env>/env.yml` に持つ**（`dataset_ids` は空のまま commit し、`scripts/dify/render.py` が環境ごとに埋める） | — |

- export 前に確認：Secret 型の環境変数の値が export に出ていないこと／`dependencies` の識別子が顧客環境と一致すること
- DSL の `version` は `0.6.0` 固定。顧客環境の Dify を上げるときは dsl-skill の対応表で `0.7.0` へ移る（Agent v2 は 0.7.0 専用）

### 7-3. Export/Import 自動化は v2

git ⇄ Dify の同期（Issue #3）は **v2**。Cloud は Console API が壊れやすく、セルフホスト後に着手（`CLAUDE.md` §6）。それまでは手動 export → PR、reviewer は import して動作を見る。
**import 方向は `docs/handoff/2026-09-07-repo-layout-v2.md` §4 の `render.py`／`release.py` に統合（Issue #84）。export 方向のみ Issue #3 に残る。**

import 方向の実装：`scripts/dify/render.py`（env をマスタ DSL に流し込む）と `scripts/dify/release.py`（render → import → KB 投入 → test → tag → `dify/CHANGELOG.md` まで通す）。セルフホスト（`edition: selfhost`）は `scripts/dify/console_api.py` で自動 import・公開まで進む。Cloud（`edition: cloud`）は Console API を自動で叩かず、`dify/build/<env>/IMPORT.md` の手順で Claude in Chrome に手動インポートを依頼する（§7-1 の手動 export と対称の運用）。export 方向（Dify → git、`pull.py` 相当）は未実装のまま Issue #3 に残る。

Cloud → git の**手動 export 経路**は `scripts/dify/sync_back.py` で正規化して取り込む（Issue #3 に残るのは Console API による**自動**取得のみ）。
